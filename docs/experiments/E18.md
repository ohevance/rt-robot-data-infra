# E18 — Raspberry Pi 4, 일반 커널의 기준값("전")
> 한 줄 요약: 실물 보드(Pi 4B)의 **일반 커널**에서 1 kHz 깨어남 지연은? → 한가 max 24.9(60초) / **376**(5분), 부하 max **781**(jitter_bench) / **695**(cyclictest) us. "일반 커널로 충분한가(부하 max < 200, 한가도 안정)?" 에 **아니오** → 커널만 바꿔 본다 → [E19-a](E19a.md).

## 1. 왜 했나 (이유)
- [E02](E02.md) 의 결론 "우선순위는 줄만 세운다 → 커널이 잘라야 한다 → RT 커널, 실물 보드". 그런데 RT 커널을 바로 켜면 **비교할 '전' 값이 없다.** 같은 보드·같은 측정기·같은 부하로 일반 커널 값을 먼저 남겨야 "커널을 바꿨더니 얼마가 됐다"를 말할 수 있다.
- 순서도의 마름모: **"일반 커널로 충분한가? 부하 max < 200, 한가도 안정?"** — 만약 일반 커널이 이미 합격선을 넘는다면 RT 커널은 필요 없다. 그 가능성을 먼저 지워야 한다.
- 합격선 200 us 의 근거: 1 ms 주기에서 깨어남 지연 + 작업 시간(우리 제어+물리는 p99 145 us, E15) + 여유를 생각하면 지연에 줄 수 있는 몫이 200 us 쯤이다. 또 Pi 4 + PREEMPT_RT 의 알려진 수준(100~200 us)이기도 하다.

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 어디서 | Raspberry Pi 4 Model B 4 GB, Ubuntu Server 24.04.5(64-bit), 커널 `6.8.0-1064-raspi`(일반), Wi-Fi, 방열판 없음 |
| 무엇으로 | `jitter_bench --prio 80`(60초) · `cyclictest -m -S -p 90 -i 1000`(CPU 4개에 스레드 하나씩, 한가 300초 / 부하 120초) |
| 부하 | `stress-ng --cpu 4 --io 2 --vm 1`(CPU 4개 + 디스크 I/O 2 + 메모리 1) |
| 준비 | governor `performance`(클럭 고정), 시작 온도 50 °C 아래, 스로틀 플래그 0 확인 |

`docs/SETUP_RT_MEASURE.md` 4단계(11/04 에는 jitter_bench 를 손으로, 이후는 `scripts/jitter_run.sh`):
```bash
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor >/dev/null
sudo ./build/rt_core/jitter_bench --prio 80 --seconds 60 --label pi4_generic_idle --json docs/measurements/jitter_pi4_generic_idle.json
stress-ng --cpu 4 --io 2 --vm 1 --vm-bytes 256M --timeout 75s >/dev/null 2>&1 &
sleep 3; sudo ./build/rt_core/jitter_bench --prio 80 --seconds 60 --label pi4_generic_stress --json docs/measurements/jitter_pi4_generic_stress.json; wait
sudo scripts/cyclictest_run.sh pi4_generic_idle   300
sudo scripts/cyclictest_run.sh pi4_generic_stress 120 stress
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **Raspberry Pi 4B**: 손바닥 크기의 리눅스 보드. CPU 4개(Cortex-A72, 1.5 GHz), 메모리 4 GB. 가상 머신이 아니므로 E01·E02 의 "아래층" 의심이 사라진다.
- **cyclictest**: 리눅스 실시간 지연을 재는 표준 도구(rt-tests). `-S` 는 CPU 마다 스레드 하나, 결과가 CPU 4개 값으로 나오고 표에는 **가장 나쁜 CPU** 값을 적는다(`../GLOSSARY.md` "cyclictest").
- **stress-ng**: 일부러 CPU·디스크·메모리를 괴롭히는 부하 생성기. "바쁠 때도 주기를 지키나"를 보려고 쓴다.
- **governor performance**: CPU 클럭을 최고로 고정. 클럭이 오르내리는 시간이 지연으로 섞이지 않게.
- **온도 단위**: `/sys/class/thermal/thermal_zone0/temp` 는 **밀리도**(°C × 1000). 45277 = 45.277 °C. **스로틀**: 80 °C 를 넘으면 보드가 스스로 클럭을 내리는 것. 플래그가 0 이 아니면 그 측정은 버린다(`../GLOSSARY.md` "스로틀").
- **work time**: 매 주기 50 us 일하는 데 실제로 걸린 시간. max 134.9 = 일하다 85 us 쯤 밀렸다.

### 4-2. 쉬운 예제
- 비유: 한가한 편의점(한가)과 점심시간 편의점(부하). 손님이 없을 때는 계산이 늘 20초(≈ 18 us)지만, 점심시간에는 직원이 물건을 채우다 말고 오느라 가끔 13분(≈ 781 us)이 걸린다. 그리고 한가해도 **5분에 한 번쯤 직원이 창고에 가 있다**(376 us).
- 계산: 부하 중 max 781 us → 781 / 1,000 = **78%** 의 예산을 한 번씩 먹는다. 남는 219 us 안에 50 us 작업을 넣을 수는 있지만(드롭 0 인 이유), 만약 주기가 2 kHz(500 us)였다면 781 > 500 → 그 주기는 깨진다.

### 4-3. 숫자가 말하는 것
- 합격선 **못 넘음** 두 가지: 부하 max 781/695 ≫ 200, 그리고 **한가해도 5분 창에서 376**.
- 확인: 한가 60초 jitter_bench(24.9)와 한가 300초 cyclictest(376)의 차이는 **드문 사건** 때문이다 — 분에 한 번꼴로 커널 내부의 무언가가 수백 us 를 가져간다. 60초만 재면 못 잡는다(E19 의 측정 시간 기준이 여기서 나왔다).
- 추정: 그 "무언가"는 타이머 이동·Wi-Fi 드라이버·백그라운드 서비스 중 하나 이상(어느 것인지는 미확인). 일반 커널에서는 이들이 선점되지 않는다.
- 확인: `work time` max 134.9 — 우선순위 80 인 스레드가 일하는 도중에도 85 us 쯤 밀렸다. E02 와 같은 모양이며, 이번엔 가상 머신이 없으므로 **범인은 커널**로 좁혀졌다.
- 확인(열): 부하 75초에 45 → 75 °C. 80 °C 가 스로틀 경계라 300초 부하는 수치를 오염시킨다 → 부하 측정은 120초로 제한(`docs/DECISIONS.md` 11/04). 스로틀 플래그가 0 이었으므로 위 값은 전부 유효.
- 그래서 다음 질문: **"한가해도 5분에 376? 커널만 바꾸면 얼마가 되나?"** → 같은 보드·같은 명령·라벨만 `pi4_rt_*` 로 → [E19-a](E19a.md).

## 5. 면접 한 문장
- "Pi 4 일반 커널은 부하 중 max 781 us 로 1 ms 예산의 78% 를 한 번씩 먹었고, 한가해도 5분 창에서 376 us 가 나왔다 — '부하가 없으면 안전하다'가 일반 커널에서는 성립하지 않는다는 것을 '전' 값으로 먼저 남기고 RT 커널로 갔다."
