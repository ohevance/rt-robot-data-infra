# E24 — 같은 실시간 루프를 ZeroMQ 로 감싸면 "명령이 RT 루프에 반영되어 돌아오기까지" 몇 ms 인가: 샌드박스 p50 1.0 / p99 1.8 ms (WSL·Pi 값은 아직)
> 한 줄 요약: ROS 2 노드와 **같은 `rt_core`** 를 ZeroMQ 노드(`rt_zmq_node`)로 감쌌다. 클라이언트(Python SDK)가 명령을 보낸 순간부터 **그 명령 번호가 실린 상태를 받기까지 p50 1.02 / p99 1.76 ms**(샌드박스, 같은 PC, 500회, 잃음 0). 그중 RT 루프의 다음 주기를 기다리는 몫이 평균 0.5 ms 다 — 1 kHz 루프에서 이보다 크게 줄일 수는 없다. 상태 1 kHz 흐름은 5,170개 중 빠짐 0. **WSL·Pi 에서는 아직 재지 않았다** — 재기 전의 예측을 5절에 먼저 적어 둔다.

이전: [E23](E23.md) · 결정: DECISIONS 2026-11-11 (ZeroMQ 어댑터 · 통신 패킷 · 공유 메모리 seqlock) · 코드: `rt_control/zmq_adapter/`, `rt_control/rt_core/include/rt_core/wire.hpp`·`shm_seqlock.hpp`, `sdk/python/rtsdk/`

## 1. 왜 했나 (이유)
- 지원하는 자리(위로보틱스 Framework S/W 엔지니어)의 업무가 "실시간 제어 계층과 상위 SW 간 통신 인터페이스(ZeroMQ, 공유 메모리)"와 "ZMQ 통신 패킷 및 Python/C++ SDK"다. 이 저장소에는 DDS·ROS 2·MQTT 는 있었지만 ZeroMQ 는 없었다.
- 11/03 부터 설계 문서가 "미들웨어 교체(ROS 2 ↔ ZeroMQ)는 어댑터 교체"라고 말해 왔다(`docs/ARCHITECTURE.md`). 말만 있고 증거가 없던 문장이다. 이번에 `rt_core` 를 고치지 않고 껍질만 바꿔 그 말이 맞는지 본다.
- 질문: ① 같은 RT 루프를 ZeroMQ 로 감싸면 명령 → 반영 → 상태가 몇 ms 인가, 그중 어느 몫이 어디서 오나 ② 1 kHz 상태를 빠짐없이 흘릴 수 있나 ③ 잘못된 패킷·끊긴 명령에 노드가 안전하게 반응하나 ④ 같은 PC 의 다른 프로세스가 소켓 없이 상태를 읽을 수 있나(공유 메모리).

## 2. 어떻게 쟀나
| 항목 | 값 |
|---|---|
| 노드 | `rt_zmq_node --dof 6 --loop-hz 1000 --publish-hz 1000 --prio 0 --shm ""` (SimLag 백엔드, 일반 스케줄링 — 샌드박스에 RT 권한이 없다) |
| 클라이언트 | `python3 -m rtsdk.bench --n 500 --rate 100 --same-host` (같은 PC) |
| 컴퓨터 | 작성 보조 작업본(샌드박스): 2코어 VM (Xeon 2.1 GHz), 일반 커널, libzmq 4.3.5, Python 3.13. **표①②③ 을 잰 곳이 아니다** — 경향만 본다 |
| 재는 것 | ① ping 왕복: PING → 명령 스레드 → PONG (RT 루프를 거치지 않는다) ② 명령 → 반영: TARGET(seq k) 를 보낸 순간 → `cmd_seq ≥ k` 인 STATE 를 받은 순간 ③ RT → 클라이언트 한 방향: STATE 의 `rt_stamp_ns`(RT 루프가 읽은 시각) → 받은 시각. 같은 PC 라 같은 단조 시계다 ④ 상태 흐름: 받은 수, 빈 번호 |
| 시계 | 전부 클라이언트의 `time.monotonic_ns()` 하나(①②). ③만 노드의 시각과 빼는데, 같은 PC 의 CLOCK_MONOTONIC 이라 뺄 수 있다 (다른 PC 면 E23 처럼 두 시계의 차이가 섞인다) |

```bash
# [WSL 창] 같은 것을 다시 재는 법 (Pi 도 같다 — Pi 는 --prio 80 --cpu 3)
./build/zmq_adapter/rt_zmq_node --dof 6 --publish-hz 1000 --prio 0 --shm "" &
PYTHONPATH=sdk/python python3 -m rtsdk.bench --n 1000 --rate 100 --same-host --json docs/measurements/zmq_bench_wsl_<날짜>.json
kill %1
```

**재기 전의 예측은 적지 않았다.** E23 에서 "예측을 먼저 적고 잰다"를 했는데 이번에는 코드를 쓰며 바로 쟀다 — 그래서 아래 3절의 "몫 나누기"는 결과를 본 뒤의 설명이다. 그 대신 WSL·Pi 값의 예측은 재기 전에 5절에 적는다.

## 3. 결과 (샌드박스, 500회 — `docs/measurements/zmq_bench_sandbox_20261111.json`)
| 무엇 | n | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| ① ping 왕복 (RT 루프 없음) | 500 | **0.33 ms** | 0.50 | 0.85 | 1.77 |
| ② 명령 → 상태에 반영 | 500 | **1.02 ms** | 1.59 | **1.76** | 2.24 |
| ③ RT → 클라이언트 한 방향 | 1,056 | **0.42 ms** | 1.00 | 1.52 | 7.17 |
| ④ 상태 흐름 | 5.22초에 5,170개 (≈ 990 /s) | 빈 번호 **0** | | | |

명령 500개 전부 ACK `ok`, 반영을 못 본 명령 0. 노드 쪽: 상태 11,131개 보냄, 보내기 실패 0, 상태 벨트 버림 0, 불법 전이 0. RT 루프의 깨어남 지연 최대 3.7 ms, 한 주기(1 ms)를 넘은 것 14번 — **일반 커널·2코어 VM 의 값**이다(표① 의 Pi PREEMPT_RT 는 cyclictest 최대 37 µs(한가) · 132 µs(부하), 우리 측정기로 부하 중 격리까지 하면 189 µs). ③의 최대 7.17 ms 도 같은 원인으로 본다(추정 — 같은 시각의 깨어남 지연과 짝지어 보지는 않았다).

**몫 나누기 (결과를 본 뒤의 설명)**: ② = 소켓으로 노드까지(① 의 절반쯤, 약 0.15 ms) + **RT 루프가 다음 주기에 우편함을 열 때까지(0 ~ 1 ms, 평균 0.5 ms)** + 발행 스레드가 벨트를 비우러 깰 때까지(0 ~ 0.2 ms, 평균 0.1 ms — `--pub-poll-us 200`) + 소켓으로 클라이언트까지(약 0.15 ms) + Python 이 받아 푸는 시간. 더하면 약 0.9 ms 로 p50 1.02 ms 와 맞는다. 이 중 가장 큰 몫은 **소켓이 아니라 1 kHz 루프의 주기**다 — 루프가 2 kHz 면 그 몫이 반이 된다.

**같이 확인한 것**
- libzmq 는 TCP 연결에 `TCP_NODELAY` 를 스스로 켠다 — `strace -e setsockopt` 로 양쪽 소켓에서 `setsockopt(…, SOL_TCP, TCP_NODELAY, [1], 4)` 를 봤다. E23 에서 MQTT(paho)가 0.2초 간격일 때 Nagle 에 붙잡힌 것과 달리, 이 경로는 작은 패킷을 바로 보낸다.
- 끝-대-끝 시험(`sdk/python/tests/test_zmq_node.py`, 3번 연속 통과): 목표 0.3 rad 추종 → 상태에 마지막 명령 번호 → 명령을 멈추자 **마지막 명령 51~52 ms 뒤 FAULT**(워치독 50 ms), 0.2초 뒤에도 위치 그대로 → 다시 보내자 READY → 쓰레기 바이트·관절 수 다름·NaN·모르는 type 을 각각 `bad_packet`·`bad_dof`·`bad_value`·`unknown_type` 으로 거절하고 그 뒤에도 응답 → 공유 메모리로 읽은 상태의 나이 최대 0.77 ms → SIGTERM 으로 끝내면 종료 코드 0.
- 공유 메모리 seqlock 시험(`test_shm_seqlock`): 쓰는 스레드가 쉬지 않고 쓰는 동안 받아들인 읽기 36,692번 중 섞임 0, fork 한 자식 프로세스의 읽기도 섞임 0. **번호 확인(s1 ≠ s2 이면 버림)을 지운 변형으로 같은 시험을 3번 돌리면 3번 모두 실패**(섞임 35,711 ~ 76,231)했다 — 시험이 무엇을 잡는지 확인하고 쓴다.

## 4. 처음 읽는 사람을 위한 분석
- **왜 소켓 왕복(0.33 ms)보다 명령 → 반영(1.02 ms)이 세 배인가.** 명령은 노드에 도착해도 바로 로봇에 가지 않는다. RT 루프는 1 ms 마다 한 번 우편함을 연다 — 그 사이에 도착한 명령은 다음 주기까지 기다린다. 이것은 지연이라기보다 **설계**다: RT 스레드가 소켓을 기다리면 주기가 흔들린다(표①이 재는 것). 그래서 소켓은 일반 스레드가 받고, RT 스레드는 락 없는 우편함(spsc_ring)만 본다. 이 구조는 ROS 2 노드와 같다.
- **예시**: 사람이 원격 조작 화면에서 버튼을 누르면 명령이 100 Hz 로 나간다. 각 명령이 로봇에 반영되어 화면에 다시 보이기까지 약 1 ms(같은 PC) + 네트워크 왕복이다. 사람의 반응(수백 ms)에 비하면 작다. 하지만 상위 제어기가 1 kHz 로 닫힌 루프를 돌리려 하면 이 1 ms(한 주기)가 그대로 지연이 된다 — 그때는 같은 프로세스 안에서 돌리거나(지연 0 주기) 공유 메모리(소켓 없음)로 붙는다. 그래서 공유 메모리가 따로 있다.
- **PUB/SUB 의 함정 하나**: 구독자는 "붙은 뒤"의 메시지만 받는다. 그래서 SDK 와 시험은 첫 상태를 하나 받은 뒤에 시작한다. 붙자마자 명령을 보내고 상태를 기다리면 처음 몇 개를 놓칠 수 있다.
- **워치독과 명령 주기**: 시험을 처음 20 Hz 로 썼다가 워치독이 9번 걸렸다. 명령 간격(50 ms)이 워치독(50 ms)과 같으면 조금만 늦어도 걸린다. 명령은 워치독보다 충분히 자주(여기서는 100 Hz = 10 ms) 보낸다 — SDK README 에 적었다.

## 5. 다음 — 재기 전에 적는 예측 (WSL · Pi)
같은 명령(2절)으로 잰다. 예측은 이 절이 들어간 커밋의 시각에 고정된다.

| 어디 | ① ping p50 | ② 명령 → 반영 p50 / p99 | ④ 빈 번호 | 근거 |
|---|---|---|---|---|
| WSL (12코어, 일반 커널, 같은 PC) | 0.1 ~ 0.2 ms | **0.7 ~ 0.9 / < 1.5 ms** | 0 | 샌드박스보다 코어가 많아 소켓·Python 몫이 줄고, 주기 몫(평균 0.5 ms)은 그대로 |
| Pi 4 (PREEMPT_RT, `--prio 80 --cpu 3`, 같은 Pi) | 0.3 ~ 0.6 ms | **0.9 ~ 1.2 / < 2.0 ms** | 0 | CPU 가 느려 소켓·Python 몫이 커진다. RT 루프 깨어남은 표①처럼 작아 p99 꼬리가 샌드박스보다 짧을 것 |
| Pi 노드 ↔ WSL 클라이언트 (집 LAN, Wi-Fi) | 망 왕복 + 0.3 ms | 망 왕복 + 약 1 ms | 0 | 망 왕복은 재 보지 않았다 — Wi-Fi 라 수 ms 로 어림만 한다 |

판정: 같은 PC 의 ② p99 가 **2 ms(두 주기) 안**이면 "ZeroMQ 경로는 1 kHz 루프의 한두 주기 안에 반영된다"로 적는다. 넘으면 어느 몫인지(③ 한 방향, 깨어남 지연)부터 본다.

남은 일: (1) WSL·Pi 값 (2) 같은 조건의 ROS 2 노드(DDS)와 나란히 — 같은 `rt_core` 라 껍질만의 차이가 보인다 (3) `--pub-poll-us` 를 없애고 RT 루프가 쓴 직후 깨우기(eventfd 등)로 평균 0.1 ms 몫을 지우기 (4) Zenoh, C++ 클라이언트, CURVE 암호화.

## 6. 면접 한 문장
"ROS 2 로 감싸던 실시간 루프를 코드 수정 없이 ZeroMQ 로 다시 감쌌습니다. 명령이 반영되어 돌아오기까지 1 ms 안팎인데, 그 절반은 소켓이 아니라 1 kHz 루프가 다음 주기에 우편함을 여는 시간이라서, 더 줄이려면 미들웨어가 아니라 구조(공유 메모리, 같은 프로세스)를 바꿔야 한다는 것까지 숫자로 나눠 봤습니다."
