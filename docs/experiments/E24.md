# E24 — 같은 실시간 루프를 ZeroMQ 로 감싸면 "명령이 RT 루프에 반영되어 돌아오기까지" 몇 ms 인가: WSL p50 0.88 / p99 1.7~1.8 ms — 스케줄링을 바꿔도 거의 같다 (Pi 값은 아직)
> 한 줄 요약: ROS 2 노드와 **같은 `rt_core`** 를 ZeroMQ 노드(`rt_zmq_node`)로 감쌌다. 클라이언트(Python SDK)가 명령을 보낸 순간부터 **그 명령 번호가 실린 상태를 받기까지 WSL 에서 p50 0.88 / p99 1.81 ms**(같은 PC, 1,000회, 잃음 0), RT 스레드를 SCHED_FIFO 로 올려도 **0.88 / 1.71 ms** — 거의 같다. 그 절반은 RT 루프의 다음 주기(1 kHz → 평균 0.5 ms)를 기다리는 몫이라 스케줄러로는 줄지 않는다(3-2절). 상태 1 kHz 흐름은 약 1만 개 중 빠짐 0. 재기 전의 예측(5절)은 넷 중 둘이 맞았다. 시험이 없던 길(느린 구독자)을 재 보니 문서가 틀렸다 — 느리게 읽으면 버려지기 전에 수십 초 동안 **늦게** 오고, 버림은 노드가 모른다(7절). **Pi 에서는 아직 재지 않았다** — 예측은 5절에 재기 전에 커밋했다.

이전: [E23](E23.md) · 결정: DECISIONS 2026-11-11 (ZeroMQ 어댑터 · 통신 패킷 · 공유 메모리 seqlock) · 코드: `rt_control/zmq_adapter/`, `rt_control/rt_core/include/rt_core/wire.hpp`·`shm_seqlock.hpp`, `sdk/python/rtsdk/`

## 1. 왜 했나 (이유)
- 지원하는 자리(위로보틱스 Framework S/W 엔지니어)의 업무가 "실시간 제어 계층과 상위 SW 간 통신 인터페이스(ZeroMQ, 공유 메모리)"와 "ZMQ 통신 패킷 및 Python/C++ SDK"다. 이 저장소에는 DDS·ROS 2·MQTT 는 있었지만 ZeroMQ 는 없었다.
- 11/03 부터 설계 문서가 "미들웨어 교체(ROS 2 ↔ ZeroMQ)는 어댑터 교체"라고 말해 왔다(`docs/ARCHITECTURE.md`). 말만 있고 증거가 없던 문장이다. 이번에 `rt_core` 를 고치지 않고 껍질만 바꿔 그 말이 맞는지 본다.
- 질문: ① 같은 RT 루프를 ZeroMQ 로 감싸면 명령 → 반영 → 상태가 몇 ms 인가, 그중 어느 몫이 어디서 오나 ② 1 kHz 상태를 빠짐없이 흘릴 수 있나 ③ 잘못된 패킷·끊긴 명령에 노드가 안전하게 반응하나 ④ 같은 PC 의 다른 프로세스가 소켓 없이 상태를 읽을 수 있나(공유 메모리).

**몫 나누기 (결과를 본 뒤의 설명)**: ② = 소켓으로 노드까지(① 의 절반쯤, 약 0.15 ms) + **RT 루프가 다음 주기에 우편함을 열 때까지(0 ~ 1 ms, 평균 0.5 ms)** + 발행 스레드가 벨트를 비우러 깰 때까지(0 ~ 0.2 ms, 평균 0.1 ms — `--pub-poll-us 200`) + 소켓으로 클라이언트까지(약 0.15 ms) + Python 이 받아 푸는 시간. 더하면 약 0.9 ms 로 p50 1.02 ms 와 맞는다. 이 중 가장 큰 몫은 **소켓이 아니라 1 kHz 루프의 주기**다 — 루프가 2 kHz 면 그 몫이 반이 된다.

**같이 확인한 것**
- libzmq 는 TCP 연결에 `TCP_NODELAY` 를 스스로 켠다 — `strace -e setsockopt` 로 양쪽 소켓에서 `setsockopt(…, SOL_TCP, TCP_NODELAY, [1], 4)` 를 봤다. E23 에서 MQTT(paho)가 0.2초 간격일 때 Nagle 에 붙잡힌 것과 달리, 이 경로는 작은 패킷을 바로 보낸다.
- 끝-대-끝 시험(`sdk/python/tests/test_zmq_node.py`, 3번 연속 통과): 목표 0.3 rad 추종 → 상태에 마지막 명령 번호 → 명령을 멈추자 **마지막 명령 51~52 ms 뒤 FAULT**(워치독 50 ms), 0.2초 뒤에도 위치 그대로 → 다시 보내자 READY → 쓰레기 바이트·관절 수 다름·NaN·모르는 type 을 각각 `bad_packet`·`bad_dof`·`bad_value`·`unknown_type` 으로 거절하고 그 뒤에도 응답 → 공유 메모리로 읽은 상태의 나이 최대 0.77 ms → SIGTERM 으로 끝내면 종료 코드 0.
- 공유 메모리 seqlock 시험(`test_shm_seqlock`): 쓰는 스레드가 쉬지 않고 쓰는 동안 받아들인 읽기 36,692번 중 섞임 0, fork 한 자식 프로세스의 읽기도 섞임 0. **번호 확인(s1 ≠ s2 이면 버림)을 지운 변형으로 같은 시험을 3번 돌리면 3번 모두 실패**(섞임 35,711 ~ 76,231)했다 — 시험이 무엇을 잡는지 확인하고 쓴다.

**읽는 법 (결과를 본 뒤의 설명)**
- **p50 과 p99 는 스케줄링 정책과 거의 무관하다** (0.88 ↔ 0.88, 1.81 ↔ 1.71). ②의 큰 몫은 RT 루프가 다음 주기에 우편함을 열기까지(0 ~ 1 ms, 평균 0.5) + 발행 스레드의 깨어남(0 ~ 0.2 ms) + 소켓과 Python 이다. 이 중 SCHED_FIFO 가 건드리는 것은 없다. p99 ≈ 1.7 ms 는 "한 주기를 거의 다 기다린 경우 + 나머지 몫의 꼬리"다. 샌드박스(3절)보다 코어가 많은데도 p99 가 같은 이유도 같다 — 줄어든 것은 p50 쪽(1.02 → 0.88)뿐이다.
- **최댓값(19.7 → 3.7 ms)은 SCHED_FIFO 덕이라고 쓰지 않는다.** 19 ms 늦음이 ③(RT 루프가 찍은 시각 → 받은 시각)에도 같은 크기로 있었다. RT 스레드가 늦었다면 시각도 늦게 찍혀 ③에는 나타나지 않는다. 그러니 멈춘 곳은 전달 경로(발행 스레드 · ZeroMQ 의 I/O 스레드 · Python)이고(추정), SCHED_FIFO 는 RT 스레드에만 걸린다(`rt_loop.cpp` 의 `pthread_setschedparam(pthread_self(), …)`). 한 번씩 잰 값이라 원인을 가르지 못한다 — 같은 설정을 번갈아 세 번씩 재면 가를 수 있다(남은 일).
- **③ p99 3.33 ms 도 같은 한 번의 멈춤으로 설명된다**(추정): 막힌 동안 쌓인 상태 여러 장이 한꺼번에 늦게 도착하면 ③의 표본 여러 개(약 1 %)가 함께 커진다. ②는 그때 기다리던 명령 하나만 늦는다 — 그래서 ③ p99 가 ② p99 보다 먼저 흔들린다.
- **WSL 은 가상 머신이다**: SCHED_FIFO 여도 RT 루프의 깨어남이 최대 3.56 ms 늦었고 한 주기를 30번 넘었다 — 샌드박스 VM(3.7 ms, 14번)과 같은 크기다. 리눅스 안의 우선순위는 Windows 가 가상 CPU 를 언제 돌려주는지까지 정하지 못한다. 표①의 Pi PREEMPT_RT(cyclictest 최대 37 / 132 µs)와는 단위가 다르다 — 실시간 판정은 Pi 로 한다.

## 4. 처음 읽는 사람을 위한 분석
- **왜 소켓 왕복(0.33 ms)보다 명령 → 반영(1.02 ms)이 세 배인가.** 명령은 노드에 도착해도 바로 로봇에 가지 않는다. RT 루프는 1 ms 마다 한 번 우편함을 연다 — 그 사이에 도착한 명령은 다음 주기까지 기다린다. 이것은 지연이라기보다 **설계**다: RT 스레드가 소켓을 기다리면 주기가 흔들린다(표①이 재는 것). 그래서 소켓은 일반 스레드가 받고, RT 스레드는 락 없는 우편함(spsc_ring)만 본다. 이 구조는 ROS 2 노드와 같다.
- **예시**: 사람이 원격 조작 화면에서 버튼을 누르면 명령이 100 Hz 로 나간다. 각 명령이 로봇에 반영되어 화면에 다시 보이기까지 약 1 ms(같은 PC) + 네트워크 왕복이다. 사람의 반응(수백 ms)에 비하면 작다. 하지만 상위 제어기가 1 kHz 로 닫힌 루프를 돌리려 하면 이 1 ms(한 주기)가 그대로 지연이 된다 — 그때는 같은 프로세스 안에서 돌리거나(지연 0 주기) 공유 메모리(소켓 없음)로 붙는다. 그래서 공유 메모리가 따로 있다.
- **PUB/SUB 의 함정 하나**: 구독자는 "붙은 뒤"의 메시지만 받는다. 그래서 SDK 와 시험은 첫 상태를 하나 받은 뒤에 시작한다. 붙자마자 명령을 보내고 상태를 기다리면 처음 몇 개를 놓칠 수 있다.
- **워치독과 명령 주기**: 시험을 처음 20 Hz 로 썼다가 워치독이 9번 걸렸다. 명령 간격(50 ms)이 워치독(50 ms)과 같으면 조금만 늦어도 걸린다. 명령은 워치독보다 충분히 자주(여기서는 100 Hz = 10 ms) 보낸다 — SDK README 에 적었다.

## 5. 다음 — 재기 전에 적는 예측 (WSL · Pi)

| WSL (12코어, 일반 커널, 같은 PC) | 0.1 ~ 0.2 ms | **0.7 ~ 0.9 / < 1.5 ms** | 0 | 샌드박스보다 코어가 많아 소켓·Python 몫이 줄고, 주기 몫(평균 0.5 ms)은 그대로 |

판정: 같은 PC 의 ② p99 가 **2 ms(두 주기) 안**이면 "ZeroMQ 경로는 1 kHz 루프의 한두 주기 안에 반영된다"로 적는다. 넘으면 어느 몫인지(③ 한 방향, 깨어남 지연)부터 본다.

**대조 — WSL (11/11 밤, 3-2절)**

| 예측 (WSL 줄) | 일반 스케줄링 | SCHED_FIFO | 맞았나 |
|---|---|---|---|
| ① ping p50 0.1 ~ 0.2 ms | 0.211 | 0.229 | ✗ (조금 넘음) |
| ② p50 0.7 ~ 0.9 ms | 0.883 | 0.878 | ✓ |
| ② p99 < 1.5 ms | 1.813 | 1.714 | ✗ |
| ④ 빈 번호 0 | 0 | 0 | ✓ |

**넷 중 둘.** 판정(② p99 < 2 ms)은 두 번 모두 통과 — "ZeroMQ 경로는 1 kHz 루프의 두 주기 안에 반영된다". 틀린 둘의 이유(결과를 본 뒤의 설명): 예측의 근거는 "코어가 많으면 소켓·Python 몫이 준다"였는데, 준 것은 p50 쪽뿐이고 꼬리는 주기 몫(최대 1 ms)과 비실시간 경로가 정한다 — 코어 수로 줄지 않는다. SCHED_FIFO 실행 전에 대화로 말한 예측("p99 약 1.5 ms, 최댓값은 몇 ms 남는다" — 커밋으로 고정하지 않았다)도 p99 는 틀렸고(1.71) 최댓값은 맞았다(3.74).

남은 일: (1) Pi 값 — 같은 Pi 안(`--prio 80 --cpu 3`)과 Pi 노드 ↔ WSL 클라이언트(집 LAN), 그리고 Pi 에서 끝-대-끝 12단계 (2) 같은 조건의 ROS 2 노드(DDS)와 나란히 — 같은 `rt_core` 라 껍질만의 차이가 보인다 (3) `--pub-poll-us` 를 없애고 RT 루프가 쓴 직후 깨우기(eventfd 등)로 평균 0.1 ms 몫을 지우기 (4) 최댓값의 원인 가르기 — 같은 설정을 번갈아 세 번씩 (5) 느린 구독자의 늦음에 상한 두기 — 보내는 쪽 커널 버퍼(`ZMQ_SNDBUF`)를 작게 (7절) (6) CI 에 arm64 러너로 aarch64 빌드·끝-대-끝 (7) Zenoh, C++ 클라이언트, CURVE 암호화.

## 6. 면접 한 문장
"ROS 2 로 감싸던 실시간 루프를 코드 수정 없이 ZeroMQ 로 다시 감쌌습니다. 명령이 반영되어 돌아오기까지 p50 0.9 ms 인데, 그 절반은 소켓이 아니라 1 kHz 루프가 다음 주기에 우편함을 여는 시간이라서 RT 스레드를 SCHED_FIFO 로 올려도 p50·p99 는 그대로였습니다. 더 줄이려면 스케줄러나 미들웨어가 아니라 구조(공유 메모리, 같은 프로세스, 더 빠른 주기)를 바꿔야 한다는 것까지 숫자로 나눠 봤습니다."
"그리고 시험이 없던 길을 시험하다가, 느린 구독자는 버려지기 전에 수십 초 동안 묵은 상태를 받고 그 버림을 보내는 쪽은 모른다는 것을 찾아 문서와 SDK 사용법을 고쳤습니다."

## 7. 시험이 없던 길에서 찾은 것 — 느린 구독자는 '버려지는' 것이 아니라 '늦게' 받는다 (11/11 밤)
- **계기**: 작성자가 "ZeroMQ 어댑터와 SDK 가 전부 시험되었나?"고 물었다. 목록을 만들어 보니 코드는 있는데 시험이 없는 길이 다섯이었다 — 우편함 가득 참 · 클라이언트 둘 · 노드 재시작 뒤 재연결 · 느린 구독자 · ZeroMQ 노드의 MuJoCo 백엔드(이 빌드에 없다). 그중 느린 구독자부터 쟀다.
- **문서가 말하던 것**: "구독자마다 높은 물 표시 1,000(1 kHz 에서 1초). 넘치면 노드가 버리고(`states_send_dropped`) SDK 는 빈 번호로 센다" (DECISIONS 11/11, 두 README, SDK 머리말).
- **잰 것** (샌드박스, 진짜 libzmq 4.3.5, 노드 1 kHz 발행. 구독자가 정해진 시간 동안 읽지 않다가 1초 동안 다 읽는다 — `sdk/python/tools/slow_subscriber.py`, 설정마다 노드를 새로 띄움):

| 받기 큐(RCVHWM) | 커널 받기 버퍼 | 안 읽은 시간 | 받은 수 | 빈 번호 | 처음 받은 상태의 나이 | 노드의 `states_send_dropped` |
|---|---|---|---|---|---|---|
| 50 | 기본 | 0.2초 | 1,201 | 0 | 0.2초 | 0 |
| 50 | 기본 | 4초 | 5,001 | 0 | 4.0초 | 0 |
| 10,000 (SDK 기본) | 기본 | 4초 | 5,001 | 0 | 4.0초 | 0 |
| 50 | 4 KB | 4초 | 5,000 | 0 | 4.0초 | 0 |
| 50 | 기본 | 12초 | 13,001 | **0** | **12.0초** | 0 |
| 50 | 4 KB | 30초 | 16,418 | **14,582** | 30.0초 | **0** |
| 10,000 (SDK 기본) | 기본 | 45초 | 33,892 | **12,109** | 45.0초 | **0** |

  같은 설정을 앞서 시험용 스크립트로 한 번 더 재었을 때(도구를 만들기 전): 12초 빈 번호 0, 30초 15,065, 45초 12,600 — 노드의 값은 모두 0. 이 컴퓨터의 커널 TCP 버퍼 상한은 보내는 쪽 4 MB(`net.ipv4.tcp_wmem`), 받는 쪽 32 MB(`tcp_rmem`).
- **읽는 법**
  1. **12초를 안 읽어도 빠짐이 0이다.** 13,001개가 전부 도착했는데 첫 장이 **12초 묵은 채로** 왔다. 버리기 전에 커널의 TCP 버퍼와 양쪽 큐(노드 1,000 · 구독자)가 먼저 찬다. SDK 기본값이면 약 33초 분량이다(45초 실행에서 받은 33,892 − 다 읽는 1초 동안 새로 온 약 1,000).
  2. **버려지기 시작해도 오래된 것이 남는다.** 30초·45초 실행에서도 처음 받은 상태의 나이가 안 읽은 시간과 같다 — 넘치면 PUB 는 **새로 오는 것**을 버린다. 느린 구독자는 "오래된 것 한 무더기 → 빈 칸 → 최근 것" 순서로 받는다.
  3. **버림은 노드가 모른다.** 구독자 쪽 빈 번호가 1만 개를 넘었는데 노드의 `states_send_dropped` 는 0이다. PUB 는 넘친 구독자의 몫을 조용히 버리고 `zmq_send` 는 성공을 돌려준다 — 구독자가 여럿일 때 한 명 때문에 보내기가 실패할 수는 없기 때문이다. 이 카운터는 "zmq_send 실패"만 센다(주석을 고쳤다).
  4. **뜻**: 로봇 상태처럼 "지금 값"이 중요한 흐름에서, 느리게 읽는 프로그램은 끊김이 아니라 **수십 초 전의 상태**를 받는다. `wait_state()` 는 쌓인 것 중 가장 오래된 것을 준다. 지금 값이 필요하면 `latest_state()`(쌓인 것을 다 읽고 마지막 것) 또는 `conflate=True`(SUB 가 최신 한 장만 들고 있고, 건너뛴 수는 빈 번호로 센다). 둘 다 SDK 에 있었지만 README 가 경고하지 않았다.
  5. 11/04 의 교훈과 같은 모양이다 — 그때는 "유실 0" 이 측정의 맹점이었고, 이번에는 "빈 번호 0" 이었다. 시험이 0 이 아닌 경우를 한 번도 만들지 않았으니, SDK 의 빈 번호 셈은 0 이 아닌 값을 낸 적이 없었다.
- **고친 것**: 문서(이 문서 · DECISIONS 정정 줄 · `rt_control/zmq_adapter/README.md` · `sdk/python/README.md` 규칙 셋째 · GLOSSARY)와 주석 둘(노드의 카운터, SDK 머리말). **노드의 동작은 바꾸지 않았다** — 기록하는 구독자에게는 "늦더라도 전부"가 맞고, 지금 값이 필요한 구독자는 고를 수 있다(conflate). 늦음에 상한을 두는 것(보내는 쪽 `ZMQ_SNDBUF` 를 작게)은 남은 일(5절).
- **시험에 더한 것** — 끝-대-끝 8 → 12단계 (`sdk/python/tests/test_zmq_node.py`, CI 에서 매 push. 테스트 '건수' 37건은 그대로 — 끝-대-끝은 따로 센다):

| 단계 | 확인하는 것 | 샌드박스 결과 (3번 연속 통과) |
|---|---|---|
| 8) 클라이언트 둘 | 답(ACK)은 보낸 쪽에만 간다(ROUTER 가 보낸 쪽의 신원으로 돌려보낸다), 상태는 둘 다 받는다 | 30/30 · 다른 쪽 0 |
| 9) 느린 구독자 | 1초 안 읽으면 `wait_state()` 는 1초 묵은 상태, `latest_state()` 는 최신, conflate 는 건너뛴 수를 빈 번호로 센다 | 999 ~ 1,001 ms · 0.7 ~ 0.9 ms · 1,009 ~ 1,015장 |
| 11) 노드가 다시 뜨면 | 같은 SDK 객체가 다시 붙고, 번호가 처음으로 돌아간 것을 빈 번호로 세지 않는다 | 새 노드의 상태 번호 1 ~ 2, 빈 번호 셈 그대로 |
| 12) 우편함이 차면 | 10 Hz 노드(100 ms 에 한 번 비움)에 목표 200개를 한꺼번에 → `ring_full` 로 답하고 노드도 같은 수를 센다 | ok 63 · ring_full 137 (64칸 링은 한 칸을 비워 둔다) |

  시험이 무엇을 잡는지도 확인했다 — 일부러 고장 낸 셋: SDK 의 "번호가 처음으로 돌아감" 처리를 지우면 11단계가(빈 번호 4,294,965,089), conflate 를 빼면 9단계가, 노드가 ring_full 을 숨기면 12단계가 실패한다.
