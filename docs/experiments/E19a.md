# E19-a — Raspberry Pi 4, PREEMPT_RT 커널로 바꾸면 ("후", 커널만 바꿈)
> 한 줄 요약: 같은 보드·같은 측정·커널만 실시간으로 → 부하 max **781 → 300.6 us**(jitter_bench, 2.6배), cyclictest 는 한가 **376 → 37**, 부하 **695 → 132 us**. 단 p99 는 146 → 185 로 오히려 나빠졌고, 두 도구의 max 가 2.3배 다르다. "부하 max < 200?" 에 jitter_bench 기준 **아니오(301)** → 남은 300 은 어디서 오나 → [E19-b](E19b.md); 도구 불일치 → [E19-d](E19d.md).

## 1. 왜 했나 (이유)
- [E18](E18.md) 에서 "한가해도 5분에 376? 커널만 바꾸면?" 이 남았다. 변수는 하나(커널)만 바꾼다 — 보드·전원·측정기·부하·시간·라벨 규칙 전부 그대로.
- 순서도의 마름모 두 개: **"부하 max < 200?"** (표①의 합격선) 과 **"표준 도구와 내 측정기가 같은 급인가? (±30%)"** (내가 만든 자가 맞는지).
- 합격선 200 us 의 근거는 E18 §1 과 같다. ±30% 는 두 도구가 측정 방식이 달라(cyclictest 는 깨자마자 다시 잠듦, jitter_bench 는 매 주기 50 us 일함) 어느 정도 차이는 자연스럽지만, 2배가 넘으면 둘 중 하나가 다른 것을 재고 있다는 뜻이기 때문.

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 어디서 | 같은 Pi 4B, Ubuntu 24.04.5, 커널 **`6.8.0-2054-raspi-realtime`**, `/sys/kernel/realtime` = 1 |
| 커널 바꾼 방법 | Ubuntu Pro 개인 무료 구독(기기 5대) → `pro enable realtime-kernel --variant=raspi` → 재부팅 |
| 무엇으로 | `scripts/jitter_run.sh`(jitter_bench 60초 + 온도·스로틀 기록) · `scripts/cyclictest_run.sh`(한가 300초 / 부하 120초) |
| 부하 | E18 과 같은 stress-ng (jitter_run 은 `--vm-bytes 256M`, cyclictest_run 은 512M) |

`docs/SETUP_RT_MEASURE.md` 5·6단계:
```bash
sudo pro attach <토큰>
sudo pro enable realtime-kernel --variant=raspi
sudo reboot
uname -r; cat /sys/kernel/realtime                       # 6.8.0-2054-raspi-realtime / 1
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor >/dev/null
sudo scripts/jitter_run.sh     pi4_rt_idle   60
sudo scripts/jitter_run.sh     pi4_rt_stress 60  stress
sudo scripts/cyclictest_run.sh pi4_rt_idle   300
sudo scripts/cyclictest_run.sh pi4_rt_stress 120 stress
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **PREEMPT_RT**: 리눅스 커널을 "급한 스레드가 오면 커널이 하던 일을 즉시 멈추고 비켜 주게" 고친 것. 인터럽트 처리를 스레드로 바꾸고, 커널 안의 락을 선점 가능한 락으로 바꾼다. 자세한 표와 비유는 `../GLOSSARY.md` "PREEMPT_RT — 실시간 커널은 무엇이 다른가".
- **Ubuntu Pro / `pro enable realtime-kernel`**: Canonical 이 미리 만들어 둔 PREEMPT_RT 커널을 받는 공식 경로. 개인은 무료(기기 5대). `--variant=raspi` 가 Pi 4/5 용.
- **`/sys/kernel/realtime`**: 실시간 커널만 만드는 파일. 내용 1 = PREEMPT_RT. 일반 커널에는 파일이 없다.
- **max 와 p99 의 다른 뜻**: max 는 "최악 한 번", p99 는 "100번 중 1번꼴로 겪는 나쁜 경우". 둘이 반대로 움직일 수 있다 — 이번이 그 경우.
- 단위: us = 100만분의 1초, 1 ms = 1,000 us. 온도는 °C(원본 파일은 밀리도).

### 4-2. 쉬운 예제
- 비유: 일반 커널 가게는 직원이 재고 정리를 시작하면 끝날 때까지 손님이 기다린다(가끔 13분). RT 커널 가게는 손님이 오면 정리를 즉시 멈춘다 — 그런데 "즉시 멈추고 다시 이어 가는" 동작 자체에 몇 초가 들어서, **보통 손님의 대기는 조금 길어지고(p99 146 → 185), 최악의 손님은 훨씬 짧아진다(781 → 301)**.
- 계산 — 2 kHz(주기 500 us) 루프였다면: 일반 커널 max 781 > 500 → 주기를 놓친다. RT 커널 max 301 < 500 → 버틴다. 1 kHz 기준으로는 781 / 1,000 = 78% 에서 301 / 1,000 = **30%** 로.

### 4-3. 숫자가 말하는 것
- 마름모 1 "부하 max < 200?": jitter_bench 기준 **아니오(300.6)**. cyclictest 기준으로는 132 로 **예**. 어느 쪽을 믿느냐가 마름모 2 로 이어진다.
- 확인: RT 커널은 **최악을 잘랐다** — jitter 781 → 301(2.6배), cyclictest 한가 376 → 37(10배), 부하 695 → 132(5배). 어제 "한가해도 5분에 376" 이던 드문 사건이 37 로 — 그 커널 내부 작업이 이제 선점된다.
- 확인: 대신 **보통 나쁜 경우는 조금 나빠졌다** — jitter p99 146 → 185, p99.9 202 → 242. 인터럽트를 스레드로 돌리고 락을 바꾼 고정 비용이다. RT 커널은 "상한을 사는 것"이지 "다 빨라지는 것"이 아니다. 숨길 일이 아니라 먼저 말할 일.
- 확인: 한가 max 는 24.9 → 27.8 로 같은 급(오히려 1 us 높다). 경쟁자가 없을 때는 커널 종류와 무관하게 하드웨어 바닥(약 19 us)이 나온다 — "한가 줄만으로는 아무 커널이나 좋아 보인다"는 것을 숫자로.
- 확인: `work time` max 134.9 → 97.7. 일하는 도중 밀리는 양이 줄었지만 아직 47 us 쯤 밀린다 → CPU 를 누군가와 나누고 있다.
- 추정: 남은 300 us 의 출처는 (a) RT 스레드가 CPU 사이를 옮겨 다니는 비용, (b) 같은 CPU 위의 다른 일(stress 작업·인터럽트 스레드·커널 스레드), (c) 메모리 압박이 만드는 전 CPU 공통 동기화(TLB 동기화 IPI). (a)(b) 는 다음 두 실험이 가른다.
- 마름모 2 "두 도구가 같은 급(±30%)?": **아니오** — 132 vs 301, 2.3배. 가설: jitter_bench 는 매 주기 50 us 를 **실제로 일하므로** 그 동안 인터럽트·IPI 에 노출되고 캐시도 밀려난다. → [E19-d](E19d.md) 에서 검증한 결과 **가설은 기각**(일 0 이어도 270), 같은 설정의 cyclictest 가 274 를 내 **측정기는 맞고**, 차이는 스레드 배치(-S)와 부하 정의(512M vs 256M)였다.
- 그래서 다음: "남은 300 은 CPU 를 옮겨 다녀서인가?" → [E19-b](E19b.md) (CPU 3 고정).

## 5. 면접 한 문장
- "커널만 PREEMPT_RT 로 바꾸자 부하 중 max 가 781 에서 301 us 로, cyclictest 로는 695 에서 132 로 줄었지만 p99 는 146 에서 185 로 오히려 올랐다 — RT 커널은 평균을 사는 게 아니라 상한을 사는 것이고, 그 비용을 숫자로 안 채로 쓰는 것이 제어 엔지니어의 일이다."
