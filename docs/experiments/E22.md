# E22 — 릴리스 → 배포: 태그 하나로 50대에 진짜 산출물이 깔리는 데 몇 초, 깨진 빌드는 몇 대에서 멈추나
> 한 줄 요약: OTA 를 "버전 문자열 흉내"에서 **진짜 설치**(내려받기 → sha256 → A/B 슬롯 → 자가 점검 → 전환)로 바꾸고, `v*` 태그 → 빌드 → 패키지 → 가상 50대 카나리 → Release 게시를 한 워크플로로 이었다. 샌드박스 1차(가짜 브로커, 진짜 설치): 50대 단계 배포 **5 % 0.6 s → 50 % 1.0 s → 100 % 1.2 s, 전체 3.95 s**; 깨진 패키지는 **3대에서 거부(자가 점검 exit 1) → 롤백 0.2 s**. 러너(진짜 Mosquitto) 숫자는 첫 태그 뒤 기입.

이전: [E13](E13.md) (나쁜 펌웨어 롤백, 흉내 OTA) · [E21](E21.md) · 설계와 이유: [`docs/RELEASE.md`](../RELEASE.md), DECISIONS 2026-11-10

## 1. 왜 했나 (이유)
- 공고 주요업무 "실시간 로깅·모니터링·시각화·**업데이트** 시스템 구축"과 자격요건 "Git, Docker, **CI/CD** 활용 능력"이 한 파이프라인으로 이어지는지 보인다. 11/05 까지는 CI(검증)와 OTA(흉내)가 따로 있었고, 설치되는 "것"이 없었다.
- 질문 셋: ① 태그 한 번으로 빌드부터 게시까지 사람 손 없이 가는가 ② 50대에 진짜 파일을 깔고 자가 점검까지 하는 데 몇 초인가(흉내 OTA 는 `apply_s` 로 그냥 잤다) ③ 깨진 빌드는 몇 대에서, 몇 초 만에 멈추나.
- 합격선: ① 초록 + Release 자산 5개. ② 50대 전체 < 60 s(매니페스트 `apply_timeout_s` 가 단계당 60 s). ③ 첫 단계(5 % = 3대)를 넘지 않고 롤백 < 5 s.

## 2. 어떻게 하나
| 항목 | 값 |
|---|---|
| 산출물 | `scripts/package_release.sh`: `bin/jitter_bench` + `robots/*.yaml` + `config/*.params.yaml` + `selftest.sh` + `post_switch.sh` → tar.gz(약 21 KB) + sha256 + `manifest.<arch>.json`. `--bad` 는 selftest 가 exit 1 |
| 장치 | `fleet/agent/ota_apply.py` — 내려받기(200 MB 상한) → sha256·크기 → 풀기(경로 탈출 거부) → selftest(60 s 제한) → `current` 링크 원자적 교체 → 훅. 실패하면 `current` 그대로, 훅 실패면 스스로 복귀 |
| 배포기 | `fleet/ota/rollout.py --manifest …` — 5 → 50 → 100 %, 가상 먼저 실물 마지막, 설치 실패(`state=fault`+`ota_error`)는 헬스 대기 전에 즉시 롤백 |
| 함대 | 가상 50대(`virtual_fleet.py --slot-root`), 장치마다 폴더에 진짜로 푼다. 자가 점검은 jitter_bench 0.5초(드롭 10 % 이하) |
| 환경 | ① 샌드박스: 가짜 브로커(fake_mqtt, 동기 전달) + 진짜 설치 — 메시지 지연이 0 에 가까워 **설치 비용만** 보인다 ② GitHub 러너: 진짜 Mosquitto 컨테이너 + 50대(`release_canary.sh`) — 매 태그 ③ WSL: `integration.sh` 4b/4c(10대) |
| 측정 | 단계별 "전원 적용 완료 (T초)" = 명령 전송 → 그 단계 전원이 새 버전 보고까지(내려받기+검증+풀기+자가 점검 0.5 s+전환 포함). 전체 `total_s`. 깨진 패키지: 닿은 장치 수, 롤백 시간 |

## 4. 처음 읽는 사람을 위한 분석
- **설치 한 번의 비용은 거의 전부 자가 점검(0.5 s)이다.** 21 KB 를 받고 해시하고 푸는 데는 수십 ms. 그래서 한 단계의 적용 완료가 0.6 s(3대) → 1.0 s(22대) → 1.2 s(25대)로 장치 수에 조금씩만 늘어난다 — 25대가 한 PC 에서 동시에 0.5초짜리 루프를 돌리느라 생긴 차이다. 실물 함대에서는 장치가 각자 CPU 를 가지므로 이 증가는 사라지고, 대신 **네트워크(내려받기)** 가 비용이 된다 — 실제 노드 바이너리·모델 파일이 들어가 수십 MB 가 되면 그렇다.
- **깨진 빌드는 헬스 게이트 전에 멈춘다.** 자가 점검이 exit 1 을 내면 장치가 `state=fault` + `ota_error` 를 보고하고, 배포기는 5 s 헬스 대기를 기다리지 않고 0.2 s 안에 롤백을 결정한다. E13 의 흉내 OTA(켜진 뒤 fault → 헬스 대기 → 롤백 1.0 s)보다 빠른 이유다. 닿은 장치는 첫 단계 3대뿐이고, 그 3대도 `current` 를 바꾸지 않았으니 롤백은 "상태를 ok 로 되돌리는" 0.2 s 다.
- **가짜 브로커라는 한계.** 샌드박스의 fake_mqtt 는 메시지를 동기로 전달해 지연이 0 이다. 러너의 진짜 Mosquitto 에서는 명령·텔레메트리 왕복이 더해진다(E13 에서 흉내 OTA 롤백이 WSL 1.0 s, 러너 0.4 s 였던 것과 같은 환경 차이). 첫 태그 값이 진짜 숫자다.
- **흉내 경로를 남긴 이유.** 장애 주입(`inject.py --fault bad_firmware`)과 기존 단위 테스트는 `apply_s` 로 시간을 조절하는 흉내 OTA 를 쓴다. 두 경로는 명령에 `url` 이 있나로 갈리고, 롤백은 슬롯 `state.json` 이 있으면 그것을, 없으면 버전 문자열 기억을 쓴다.
- 한계: 실물 1대라 "실물에서 5 % 멈춤"은 없다. 서명 없음(sha256 = 무결성만). 노드 재시작 훅은 자리만. 러너 숫자 전.
