# E08 — 고친 뒤 재측정: 브로커·수집기 장애에서 유실 0 이 되는가
> 한 줄 요약: E07 에서 찾은 유실 원인 ①(브로커 재시작 경쟁) ②(수집기 종료 순간)를 각각 설정 1줄·코드 20줄로 고친 뒤 같은 장애를 다시 주입 → 브로커 10초 중단 **0 / 1400**, 수집기 10초 중단 **0 / 1311** (고치기 전 53 / 1434). 전 장치 복귀 2.9초 / 1.6초, `diag.py` C절 "틈 없음".

## 1. 왜 했나 (이유)
- 순서도의 마름모: **"원인 ①② 를 고치면 0 이 되나?"** — [E07](E07.md) 에서 유실 측정의 맹점을 고치자 "0" 이던 유실이 53 / 1434 로 드러났고, 원인이 셋으로 나뉘었다. ① 브로커가 재시작되면 수집기의 구독(지속 세션)이 사라져, 수집기보다 먼저 재접속한 장치의 버퍼를 브로커가 버림(50대 중 4~5대 × 12개) ② 수집기가 SIGTERM 으로 죽는 순간, 받아 놓고 아직 DB 에 안 넣은 "그 1초의 pending" 이 사라짐(장치당 1개) ③ 브로커 큐 상한([E12](E12.md)).
- ①은 브로커 설정 `persistence true` + 데이터 볼륨, ②는 수집기가 종료 신호를 받으면 수신을 끊고 마지막 적재를 한 뒤 끝나도록(곱게 종료) 고쳤다. 고친 것이 **겨냥한 유실만 정확히 없앴는지** 같은 조건으로 다시 재야 한다 — 고친 코드가 돌아간다는 것과 유실이 0 이 됐다는 것은 다른 말이다.
- 합격선: **유실 0**, 그리고 그 0 이 다른 증거와 맞아야 한다 — `diag.py` C절(장치별 일련번호 틈)에 "틈 없음". E07 의 교훈이 "숫자 하나만 믿지 말라"였으므로 두 번째 증거를 같이 본다.

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **MQTT**: 장치가 서버로 작은 메시지를 보내는 가벼운 통신 규약. 장치는 서로를 몰라도 되고 **브로커**(우체국)만 알면 된다.
- **브로커(Mosquitto)**: 메시지를 받아 구독자에게 나눠 주는 서버 프로그램. 여기서는 Docker 컨테이너(격리된 작은 실행 환경) 하나.
- **수집기(collector)**: 브로커를 구독해 메시지를 받아 1초치씩 묶어 DB 에 넣는 우리 프로그램.
- **QoS 1 / PUBACK**: "적어도 한 번은 전달" 등급. 받는 쪽이 **PUBACK**(받았다는 영수증)을 보내야 끝나고, 안 오면 다시 보낸다.
- **지속 세션(clean_session=False)**: 구독자가 잠깐 없어도 브로커가 그 구독자 몫의 QoS 1 메시지를 들고 있는 것. 같은 client_id(이름표)로 다시 붙어야 돌려받는다.
- **persistence true**: 브로커가 세션·보관 메시지를 디스크에 적어 두어 **브로커 자신이 재시작돼도** 잊지 않게 하는 설정.
- **SIGTERM**: "곱게 끝나라"는 종료 신호. 프로그램이 받아서 정리할 기회가 있다. **SIGKILL** 은 즉사라 기회가 없다.
- **seq(일련번호)**: 장치가 메시지마다 1씩 올려 붙이는 번호. 받은 쪽에서 빠진 번호 = 유실.
- 단위: **초(s)** 복구 시간, **개** 메시지 수, **대** 장치 수, **msgs/s** 초당 메시지 수, **Hz** 1초에 몇 번.

### 4-2. 쉬운 예제
- 비유: 우체국(브로커)이 공사로 10분 문을 닫았다. 집배원(장치)은 편지를 자기 가방(버퍼)에 모아 두었다가 문이 열리면 한꺼번에 넣는다. 그런데 우체국이 **구독자 명부를 종이에만 적어 두고 재개장하며 버렸다면**(persistence false), 먼저 온 집배원의 편지는 "받을 사람 없음"으로 폐기된다. 명부를 금고에 넣어 둔 것(persistence true)이 이번 수정이다.
- 계산: 50대 × 1 Hz × 10초 = **500개**가 "보호가 없었다면" 잃었을 양. 고치기 전 실제 유실 53개 = 4~5대 × 12개(재시작 경쟁) + 1대 × 5개(쏟는 도중 구독 복구). 고친 뒤 **0개**.

### 4-3. 숫자가 말하는 것
- 합격선 **통과**: 두 장애 모두 유실 0, diag C 틈 없음. 표③-1 의 유실도 0.00%.
- 확인: `persistence true` 가 원인 ①을, 곱게 종료가 원인 ②를 **각각 정확히** 없앴다(다른 숫자 — 복귀 시간 2.9초/1.6초 — 는 고치기 전과 같다. 즉 유실만 줄고 성능 비용은 없었다).
- 확인(부수 발견 1 — client_id 충돌): 장애 주입이 재시작한 수집기(배경)가 살아 있는 채로 터미널에서 또 띄우자 2초마다 `connected, subscribed` 가 찍히고 msgs/s 가 50 / 0 으로 번갈아 나왔다. 같은 client_id "collector" 두 개 → 브로커가 옛 접속을 밀어냄 → 둘이 번갈아 재접속. 해결: `fleet/logs/collector.lock`(flock 잠금)으로 한 번에 하나만, 두 번째는 상대 pid 를 알려 주고 물러난다.
- 확인(부수 발견 2 — 보관 메시지): persistence true 뒤로 브로커 재시작 때 오프라인 이벤트가 20 + 50 으로 늘었다. 종료 때 발행된 유언 "offline" 이 **보관(retained)** 되어 재시작 뒤 수집기가 구독하는 순간 50개가 다시 내려온 것(retain=1). 보관 메시지는 "지금 상태"이지 "방금 일어난 사건"이 아니므로 events 에 넣지 않고 카운터만 센다 → 대시보드 오프라인 수가 뜻대로 돌아왔다.
- 추정(남은 틈): SIGKILL(진짜 크래시)에서는 pending 1초치를 여전히 잃는다. 완전한 해법은 DB 적재 뒤에 PUBACK 을 보내는 수동 ACK — 2주 계획 밖, `DECISIONS.md` 에 보류로 기록.
