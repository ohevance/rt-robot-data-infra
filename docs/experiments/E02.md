# E02 — WSL2 에서 일반 스케줄링 vs SCHED_FIFO: 우선순위만으로 꼬리가 잘리는가
> 한 줄 요약: 우선순위(SCHED_FIFO 80)를 주면 보통 때(p50)는 92 → 37 us 로 좋아지지만 최악(max)은 921 → 937 us 로 **그대로** → "우선순위로 max 가 줄었나?" 에 **아니오**. 꼬리를 자르는 것은 커널의 몫이다 → 실물 보드와 RT 커널로 간다([E18](E18.md)). 곁가지: 노드 안에서도 같은가 → [E03](E03.md).

## 1. 왜 했나 (이유)
- [E01](E01.md) 에서 "가상 머신 탓인가, 커널 탓인가?" 가 남았다. 사용자의 PC(WSL2, Windows 위의 리눅스)에서 **같은 측정기로 두 번** — 일반 스케줄링(`--no-rt`)과 실시간 우선순위(`--prio 80`) — 를 재면, 적어도 "우선순위가 무엇을 바꾸고 무엇을 못 바꾸는가"는 분리해 볼 수 있다.
- 순서도의 마름모: **"우선순위로 max 가 줄었나?"** — 많은 사람이 "실시간 = 우선순위를 높이면 된다"고 생각한다. 그게 맞다면 max 가 눈에 띄게 줄어야 한다.
- 합격선: max 가 분명히 줄 것(절반 이하). 왜 max 인가 — 로봇은 평균이 아니라 가장 늦은 한 번에 사고가 나기 때문.

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 어디서 | WSL2 Ubuntu 24.04, 커널 `6.18.33.2-microsoft-standard-WSL2`(가상 커널, PREEMPT_RT 아님), 12 CPU |
| 무엇으로 | `jitter_bench`, 주기 1,000 us, 매 주기 50 us 작업, 각 5초(5,000 주기) |
| 조건 A | 일반 스케줄링(`--no-rt`): SCHED_FIFO=no, mlockall=ok |
| 조건 B | `--prio 80`(root): SCHED_FIFO=ok, mlockall=ok |

```bash

sudo ./build/rt_core/jitter_bench --prio 80 --seconds 5 --label wsl_fifo --json docs/measurements/jitter_wsl_fifo.json
python3 scripts/make_table1.py --jitter 'docs/measurements/jitter_*.json'
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **SCHED_FIFO**: 리눅스의 실시간 스케줄링 정책. 우선순위 1~99 를 가진 스레드가 준비되면 일반 스레드(우선순위 없음)를 즉시 밀어낸다. 비유: 줄 서지 않는 VIP 통로(`../GLOSSARY.md` "SCHED_FIFO").
- **선점(preemption)**: 지금 CPU 를 쓰는 쪽을 멈추고 다른 쪽에 넘기는 것. 우선순위는 "누가 먼저인가"를 정하지만, **커널이 선점을 허용하지 않는 구간**에서는 아무리 높아도 기다려야 한다.
- **WSL2**: Windows 안에서 도는 리눅스 가상 머신. 커널 이름에 `microsoft-standard-WSL2` 가 붙어 있다. 역시 아래층(Windows 하이퍼바이저)이 CPU 를 가져갈 수 있다.
- **p50 vs max**: p50 은 "보통 때", max 는 "최악의 한 번". 단위는 전부 us(100만분의 1초), 1 ms = 1,000 us.
- **work time**: 매 주기 50 us 동안 바쁘게 도는 데 실제로 걸린 시간. 50 보다 크면 그만큼 중간에 CPU 를 빼앗긴 것.

### 4-2. 쉬운 예제
- 비유: VIP 통로(우선순위)가 있으면 **줄 서는 시간**은 준다(p50 92 → 37). 하지만 계산대 직원이 금고를 열고 정산 중이면(커널의 선점 불가 구간) VIP 도 그 정산이 끝날 때까지 서 있어야 한다(max 921 → 937). 통로는 줄을 바꿀 뿐 직원을 멈추지 못한다.
- 계산: 주기 1,000 us 에서 max 937 us 는 937 / 1,000 = **93.7%** — 예산의 94% 를 한 번씩 먹는다. 50 us 의 일까지 더하면 987 us, 13 us 남는다. 거의 한 주기를 놓치기 직전이다.

### 4-3. 숫자가 말하는 것
- 합격선(max 가 분명히 줄 것) **못 넘음**: 921 → 937, 오히려 조금 늘었다(오차 범위).
- 확인: p50 은 92 → 37 로 2.5배 좋아졌다 → 우선순위는 "보통 때 다른 프로세스와의 경쟁"을 확실히 없앤다. 그런데 p99.9(504 → 664)와 max 는 안 줄었다 → 꼬리를 만드는 것은 **경쟁자가 아니라 커널(과 가상화 계층)** 이다.
- 확인: `work time` max 가 두 조건 모두 ~215 us → 바쁘게 도는 동안에도 165 us 쯤 CPU 를 빼앗겼다. 우선순위 80 인 스레드에게서 CPU 를 가져갈 수 있는 것은 일반 커널의 인터럽트·선점 불가 구간, 또는 가상 머신 호스트뿐이다.
- 추정: WSL2 라서 호스트 간섭이 섞여 있다. 그래서 이 값도 "참고값". 진짜 답은 **가상화 없는 보드 + PREEMPT_RT 커널**에서만 나온다.
- 그래서 두 갈래로 갈라졌다:
  1. "우선순위는 줄만 세운다 → 커널이 잘라야 한다 → 실물 보드에서 먼저 '전' 값" → [E18](E18.md) (Raspberry Pi 4, 일반 커널 기준값) → [E19-a](E19a.md) (PREEMPT_RT).
  2. 곁가지 "측정기가 아니라 **진짜 제어 노드(ROS 2)** 안에서도 드롭 0 인가?" → [E03](E03.md).

## 5. 면접 한 문장
- "SCHED_FIFO 는 p50 을 92 에서 37 us 로 줄였지만 max 는 921 에서 937 로 그대로였다 — 우선순위는 줄을 앞에 세울 뿐 커널이 하던 일을 중단시키지 못하므로, 꼬리는 PREEMPT_RT 가 자른다는 것을 먼저 숫자로 확인하고 Pi 실측으로 갔다."
