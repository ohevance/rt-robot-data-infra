# E06 — 장애 주입 4종 1차: 브로커·DB·수집기·나쁜 펌웨어의 감지·복구·유실
> 한 줄 요약: "장애 종류별로 몇 초 만에 알아채고, 몇 초 만에 돌아오고, 몇 개를 잃나?" → 브로커 10초 중단 → 전 장치 복귀 2.9초 · DB 10초 중단 → backlog 0 까지 1.4초, 뒤늦게 570행 적재 · 수집기 10초 중단(QoS 1) → 1.6초 · 나쁜 펌웨어 → 3/50 에서 롤백 1.0초. 유실은 전부 "0" 으로 나왔지만 — 그 0 은 **측정 맹점**이었다([E07](E07.md)).

## 1. 왜 했나 (이유)
- [E05](E05.md)에서 "끊김 동안 데이터가 보존되나?" → 예(버퍼 654 = 재전송 654). 순서도의 다음 화살표: **"그럼 장애별 숫자는?"** 공고 ②의 "장애 복구"를 말하려면 장애마다 감지·복구·유실 숫자가 있어야 하고, 그 숫자는 주입 스크립트가 따로 재서 알려 주는 것이 아니라 **시스템 자신의 DB 에 남은 것**으로 내야 운영 중에도 쓸 수 있다(`DECISIONS.md` 11/03 D4).
- 합격선: 장애 4종 모두 (1) 사람이 손대지 않아도 복구되고, (2) 유실 0(수집기 QoS 0 조합만 예외로 "n 개"를 숫자로 남김), (3) 나쁜 펌웨어는 5 % 단계에서 멈춰 나머지 95 % 에 닿지 않는다. `fleet/chaos/assert_results.py` 가 이 규칙을 기계적으로 판정한다.

## 2. 어떻게 했나
| 장애 | 주입 방법 | 기대하는 보호 장치 | "복구됨"의 정의 |
|---|---|---|---|
| broker | `docker compose stop mqtt` 10초 → start | 장치 버퍼(store-and-forward) → 재접속 뒤 QoS 1 재전송 | 전 장치가 다시 데이터를 보냄 |
| db | `docker compose stop db` 10초 → start | 수집기 **backlog**(DB 쓰기 실패한 1초 묶음을 메모리에 보관, 매초 재시도) | backlog 가 0 이 됨 |
| collector | 수집기 SIGTERM → 같은 명령으로 재시작 | 지속 세션(QoS 1 + `clean_session=False`) → 브로커가 수집기 몫을 들고 있음 | 전 장치 데이터가 다시 들어옴 |
| bad_firmware | `rollout.py --bad` (5 % → 50 % → 100 %) | 헬스 게이트: 단계마다 state=ok 확인, fault 면 롤백 | 닿은 장치 전부 이전 버전·ok |

환경: WSL2, 가상 50대 1 Hz, 수집기 `--qos 1` + 장치 `--telemetry-qos 1`. 감지·복구 시각은 ±1초(1초 묶음 적재)가 섞인다.
```bash
python3 fleet/chaos/inject.py --fault broker --duration 10
python3 fleet/chaos/inject.py --fault db --duration 10
python3 fleet/chaos/inject.py --fault collector --duration 10 --label qos1
python3 fleet/chaos/inject.py --fault bad_firmware
python3 fleet/chaos/assert_results.py                     # 기대 규칙대로인지 판정
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **장애 주입(chaos / fault injection)**: 일부러 고장을 내고 시스템이 스스로 돌아오는지 보는 시험. "고장 나면 어떻게 되나요?"에 말이 아니라 숫자로 답하기 위해.
- **감지**: 주입 → 수집기 통계(msgs/s = 0)나 DB 프로브가 이상을 처음 본 때. **복구**: 복구 명령 → DB 에 그 사실이 찍힌 때. 둘 다 "초" 단위, ±1초.
- **backlog**: DB 가 죽어 못 넣은 1초 묶음을 수집기가 메모리에 쌓아 두는 것. 상한 20만 행(50대 1 Hz 약 66분, 약 100 MB) — 넘으면 가장 오래된 것부터 버리고 `backlog_dropped` 로 센다(`DECISIONS.md` 11/03 D4).
- **행(row)**: DB 표의 한 줄 = 메시지 1개. "뒤늦게 적재된 570행" = DB 가 죽어 있던 동안 받아 둔 메시지 570개를 복귀 뒤 넣었다는 뜻. 50대 × 약 11초 ≈ 570.
- **지속 세션(persistent session)**: 수집기가 `clean_session=False` + 고정 client_id 로 접속하면, 수집기가 끊긴 동안 브로커가 QoS 1 메시지를 대신 보관했다가 재접속 때 넘겨 준다. 장치도 QoS 1 로 보내야 한다(한쪽만 1 이면 min(0,1)=0 → 보관 안 됨).
- **QoS 0 / 1 (MQTT)**: 0 = 한 번 보내고 끝. 1 = 받았다는 확인(PUBACK)이 올 때까지 다시 보낸다.
- **OTA / 단계 배포 / 헬스 게이트**: 펌웨어를 무선으로 갱신(OTA)하되 5 % → 50 % → 100 % 로 나눠(단계 배포), 단계마다 장치 상태가 ok 인지 확인(헬스 게이트)하고 아니면 되돌린다(롤백). 50대의 5 % = 2.5 → 올림 **3대**.
- **SIGTERM**: 리눅스에서 "곱게 끝나라"는 종료 신호. 프로그램이 받아서 정리하고 끝낼 수 있다(강제 종료 SIGKILL 과 다름).

### 4-2. 쉬운 예제
- 비유(backlog): 은행 창구(DB)가 10분 문을 닫으면 접수 직원(수집기)이 서류를 책상에 쌓아 두었다가(backlog) 문이 열리자마자 한 번에 넘긴다. 책상이 꽉 차면(상한 20만 장) 가장 오래된 서류부터 버리고 몇 장 버렸는지 적는다.
- 계산 예(나쁜 펌웨어): 50대 × 5 % = 2.5 → 올림 3대에게 먼저 설치. 3대가 fault 를 보고하면 즉시 롤백 → 나머지 **47대는 건드리지도 않는다**. 단계 배포가 없었다면 50대 전부가 나쁜 펌웨어를 받는다(표의 "보호 없었다면 50대 전부").
- 계산 예(유실 기대치): 보호 장치가 없었다면 50대 × 10초 × 1 Hz = **500개**를 잃었어야 한다. 표③-2 의 "보호 없었다면 500" 이 이 계산이다.

### 4-3. 숫자가 말하는 것
- 합격선: 복구는 4종 모두 통과(2.9 / 1.4 / 1.6 초, 롤백 1.0초, 3/50). 유실 "0" 도 판정은 ok — **그러나** 순서도의 다음 마름모 "유실 0 이 다른 증거와 맞나?"에서 걸렸다.
- 확인(맹점): 진단 도구 `diag.py` C절(seq 틈)에서 장치 vdev-003·005 가 브로커 중단 직후 **12초 데이터 공백**인데 유실 계산은 0 이었다. 원인: 유실 = (창 안 max(seq) − 창 안 min(seq) + 1) − 받은 행 수를 **장애 창 안에서만** 계산 → 장애 시작 직후 잃은 메시지는 창 안 "첫 번째로 받은" 번호 뒤로 숨는다. 즉 **측정이 0 을 만들었다**. 이것을 고쳐 다시 잰 것이 [E07](E07.md)(53 / 1434).
- 확인(사고): 수집기 재시작이 바로 죽었다. 재시작 명령의 파이썬을 `/proc/<pid>/exe` 로 골랐는데 그것은 심볼릭 링크를 끝까지 푼 `/usr/bin/python3.12` 라 **venv 정보가 사라져** `import paho` 실패. 해결: `/proc/<pid>/environ` 의 `VIRTUAL_ENV`·`PATH` 로 같은 환경 재시작, 1.5초 안에 죽으면 로그를 보여 주고 측정 중단. 배운 것: "같은 명령으로 재시작"은 경로만이 아니라 **환경**까지 같아야 한다 — systemd 가 환경을 통째로 기록하는 이유.
- 확인(부산물): 그 7.5분 공백 덕에 "지속 세션은 무한 보관인가?"를 공짜로 재게 됐다 → [E12](E12.md)(큐 상한 2,450개 버림).
- 추정 → 확인됨: 오프라인 이벤트 20 이 이번에도 정확히 20 — 브로커 종료 시 일괄 유언 가설이 강화됐고 [E09](E09.md)에서 1 ms 안 20개로 확인.
- 그래서 다음에 무엇을 물었나: "유실 0 이 진짜인가?" → 측정 기준점을 고친 [E07](E07.md).
