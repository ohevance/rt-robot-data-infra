# E13 — 같은 장애 4종을 다른 환경(GitHub 러너)에서 돌리면 같은 모양인가
> 한 줄 요약: 내 PC(WSL, 50대 1 Hz)에서 얻은 "유실 0 · 복구 수 초 · 롤백 1초"가 GitHub 의 무료 리눅스 컴퓨터(ubuntu-24.04 러너, 10대 2 Hz, 진짜 컨테이너)에서도 **유실 0 / 318 · 0 / 286 · 0 / 280, 롤백 0.4초**로 같은 모양 → 환경이 아니라 설계가 만든 숫자. push 마다 자동으로 다시 검증된다(CI `fleet_integration` 1분 52초).

## 1. 왜 했나 (이유)
- 순서도의 마름모: **"환경이 달라도 같은 모양?"** [E08](E08.md)까지의 숫자는 전부 내 PC 한 대에서 나왔다. "내 컴퓨터에서는 됩니다"는 면접에서 가장 약한 말이다. 다른 컴퓨터, 다른 장치 수, 다른 주기에서 **같은 설계가 같은 결과**를 내야 "설계의 성질"이라고 말할 수 있다.
- 또 하나: 사람이 손으로 돌린 실험은 다음 코드 수정에서 조용히 깨질 수 있다. CI(push 할 때마다 자동으로 도는 검사)에 같은 시나리오를 넣으면 **깨지는 순간 배지가 빨개진다**.
- 합격선: `assert_results.py` 규칙 전부 통과 — broker 유실 ≤ 장치 수(QoS 0 가장자리 허용), db 유실 0 + 뒤늦게 들어간 행 > 0, collector(qos1) 유실 0, bad_firmware 는 롤백 성공 + 닿은 장치 = 5% 단계(올림) 만, 정상 OTA 는 전 장치 새 버전.
- 배경(첫 시도의 실패): CI 1차에서 `fleet_integration` 이 깨졌다. 컨테이너 안 `pg_isready` 가 "준비됨"이라 한 1초 뒤 `migrate.py` 가 "server closed the connection unexpectedly". TimescaleDB 이미지는 첫 기동 때 **임시 서버(유닉스 소켓만)로 init.sql 을 돌린 뒤 끄고 진짜 서버를 다시 띄우는데**, 안쪽 체크는 그 임시 서버에도 "준비됨"이라 답한다. WSL 에서는 볼륨에 데이터가 이미 있어 init 단계가 없었기에 안 보였다. 해결: 준비 확인을 "밖에서 실제로 붙어 보기"로 — `migrate.py --wait 120`(1초마다 재시도). 배운 것: 헬스 체크는 **소비자와 같은 경로**로 해야 한다.

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **CI(Continuous Integration, GitHub Actions)**: 코드를 push 할 때마다 GitHub 가 빌려주는 새 리눅스 컴퓨터(**러너**)에서 자동으로 빌드·테스트를 돌리는 것. 통과하면 README 의 배지가 초록.
- **컨테이너(Docker)**: 프로그램과 그 환경을 상자 하나에 담아 어디서나 같게 띄우는 것. 브로커·DB 가 각각 상자 하나.
- **통합 테스트**: 가짜가 아니라 진짜 브로커·DB 위에서 끝에서 끝까지 돌려 보는 테스트. 단위 테스트(가짜 브로커·DB, 1초)와 역할이 다르다.
- **헬스 체크 / 준비 확인**: "서버가 요청을 받을 수 있나"를 묻는 것. 어디서 묻느냐(안/밖)에 따라 답이 다를 수 있다 — 1차 실패의 원인.
- **롤백(rollback)**: 나쁜 펌웨어를 받은 장치를 이전 버전으로 되돌리는 것. **5% 단계(올림)**: 10대의 5% = 0.5 → 올림 1대, 50대의 5% = 2.5 → 3대. 나쁜 펌웨어는 이 소수에서 걸려 나머지는 건드리지 않는다.
- 단위: **초**, **개**, **대**, **msgs/s**.

### 4-2. 쉬운 예제
- 비유: 집에서 만든 요리법을 친구 집 부엌(다른 화구, 다른 냄비, 재료 양 1/5)에서 그대로 따라 해 같은 맛이 나면, 그건 "우리 집 부엌 덕"이 아니라 "요리법 덕"이다. 그리고 친구가 요리법을 고칠 때마다 자동으로 한 번 끓여 보는 것이 CI.
- 계산: 러너의 "보호 없었다면" = 10대 × 2 Hz × 5초 = **100개**; PC 는 50 × 1 × 10 = 500개. 규모는 5배 다른데 유실은 둘 다 0. 롤백 때 닿은 장치 = ceil(10 × 5%) = 1, ceil(50 × 5%) = 3 — 둘 다 "5% 단계만".

### 4-3. 숫자가 말하는 것
- 합격선 **통과**: assert 전부 ok. 세 장애 모두 유실 0, 롤백 0.4초, 정상 OTA 10/10.
- 확인: 복구 시간이 환경과 무관하게 **수 초**(1.2~3.2초)이고, 그 순서도 같다(db 가 가장 빠르고 broker 가 가장 느리다 — broker 는 50/10대가 재접속하고 버퍼를 쏟는 시간이 든다). 숫자의 "모양"이 같다는 것은 설계(장치 버퍼·수집기 backlog·지속 세션·헬스 게이트)가 결정한 값이라는 뜻.
- 확인: 러너는 매번 **빈 DB 에서 시작**하므로 init.sql → 마이그레이션 → 적재까지 전 과정이 push 마다 검증된다. PC 에서는 볼륨에 데이터가 남아 있어 못 보던 경로(1차 실패가 그것).
- 추정: 러너의 전달 지연 max 6,661 ms(표③-1 CI)는 장애 복구 때 밀린 메시지의 원래 측정 시각 기준이라 정상(PC 도 같은 이유로 큰 값). 평소 p50 0.2 ms 는 PC(1.0 ms)보다 작다 — 장치 10대라 수집기 묶음이 작아서로 추정.
- 다음: 표③ 가지는 여기서 끝. 이 스크립트가 CI 에 있으므로 이후 코드 수정([E08](E08.md)의 잠금·보관 메시지 처리, [E10](E10.md)의 jitter 옵션)도 push 마다 같은 시나리오를 통과해야 초록이 유지된다.

## 5. 면접 한 문장
- "내 PC 50대와 GitHub 러너 10대에서 같은 장애 4종이 같은 모양(유실 0, 복구 수 초, 5% 에서 롤백)으로 나왔고, 그 시나리오가 CI 에 들어 있어 push 마다 다시 증명된다 — 그리고 CI 가 처음 깨진 이유(DB 초기화 중 임시 서버)가 '헬스 체크는 소비자와 같은 경로로' 라는 교훈을 줬다."
