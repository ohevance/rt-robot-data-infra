# E23 — 서버(시드니)까지 왕복 몇 ms 인가: 첫 측정 707 ms 는 망인가, 재는 방법인가 (예측을 먼저 적고 잰다)
> 한 줄 요약: Pi → 시드니 브로커의 MQTT 왕복을 0.2초 간격으로 쟀더니 **최소 285 / 중앙 707 / 최대 854 ms**. 대시보드의 편도 지연(146 ms)과 맞지 않는다. 가설: 망의 왕복은 약 **285 ms** 이고, 보내는 간격(0.2초)이 그보다 짧아 **양쪽의 Nagle 알고리즘이 메시지를 왕복 두세 번만큼 붙잡았다**. 이 가설을 모형(`fleet/tools/nagle_model.py`)으로 옮기면 285 / 710 / 860 ms — 실측과 거의 같다. 설명만으로는 부족하므로 **다른 조건의 값을 재기 전에 예측해 적어 두고**(2절) 그 뒤에 잰다. 실제 운영(1 Hz)은 간격이 왕복보다 길어 이 현상과 무관하다. **검증 측정은 다음 기입.**

이전: [E22](E22.md) · 결정: DECISIONS 2026-11-11 (운영 기록은 세어서, 왕복 측정의 간격) · 도구: `fleet/tools/mqtt_rtt.py`, `fleet/tools/nagle_model.py`

## 1. 왜 했나 (이유)
- 운영 층을 시드니에 올리면서 "서버 왕복이 들어가는 숫자에는 '서버: 시드니'를 적는다"고 정했다(DECISIONS 11/10). 그러려면 그 왕복이 몇 ms 인지부터 알아야 한다. 대시보드의 "전달 지연"은 (서버가 받은 시각 − 장치가 찍은 시각)이라 두 시계의 차이가 섞인다 — 그래서 시계 하나로 재는 왕복 도구를 만들었다.
- 질문: ① Pi(집, Wi-Fi) ↔ 시드니 브로커의 왕복은 몇 ms 인가 ② 대시보드의 전달 지연(146 ms)은 편도 지연인가, 시계 차이인가 ③ 첫 측정의 707 ms 는 무엇인가.
- 재기 전의 어림은 "왕복 130~160 ms, 편도 70~80 ms, 대시보드 값의 나머지는 시계 차이"였다(`deploy/ec2/README.md` 4b, 11/10). **이 어림은 틀렸다**(4절).

## 2. 어떻게 하나
| 항목 | 값 |
|---|---|
| 도구 | `fleet/tools/mqtt_rtt.py` — 한 클라이언트가 자기만 구독하는 토픽(`rtt/<id>`)에 QoS 0 으로 보내고, 브로커가 되돌려 준 것을 받는다. 보낸 시각·받은 시각을 같은 단조 시계로 잰다. TLS·비밀번호·브로커를 실제 장치와 같은 길로 지난다 |
| 어디서 어디로 | Pi 4(집, Wi-Fi, RT 커널) → 시드니 EC2 의 Mosquitto 8883. 에이전트(1 Hz 보고)는 그대로 돈다 |
| 메시지 | 200바이트(텔레메트리 한 건과 비슷), 개수는 조건마다 60초 분량 |
| 모형 | `fleet/tools/nagle_model.py` — 끝점 둘, 편도 지연 하나, Nagle(미확인 데이터가 있으면 작은 쓰기를 모은다), 지연 ACK 40 ms, 브로커는 메시지마다 따로 쓴다. 진짜 TCP 가 아니다 |

**예측 (재기 전에 적는다 — 첫 측정만 본 상태. 이 절이 들어간 커밋의 시각이 3절 측정 파일의 `measured_at_utc` 보다 앞선다)**. 모형에 왕복 285 ms 를 넣은 값이다. 실측은 Wi-Fi 의 흔들림만큼 퍼질 것이다.

| 조건 | 보내는 간격 | 옵션 | 모형 예측 min / p50 / p95 / max (ms) | 예측의 뜻 |
|---|---:|---|---|---|
| A | 1.00 s | 없음 | 285 / 285 / 285 / 285 | 텔레메트리와 같은 1 Hz. 간격 > 왕복이면 붙잡을 것이 없다 |
| D | 0.35 s | 없음 | 285 / 285 / 285 / 285 | 문턱(0.285 s) 바로 위. 여기서도 평평하면 "문턱은 왕복 시간"이 맞다 |
| C | 0.20 s | 없음 | 285 / 710 / 845 / 860 | 첫 측정의 재현 (첫 측정 285 / 707 / 838 / 854) |
| B | 0.20 s | 클라이언트 `TCP_NODELAY` | 285 / 460 / 610 / 610 | 한쪽만 끄면 절반쯤만 준다 — 브로커 쪽 Nagle 이 남는다 |
| (안 잰다) | 0.20 s | 양쪽 `TCP_NODELAY` | 285 / 285 / 285 / 285 | 브로커 설정(`set_tcp_nodelay true`)과 재시작이 필요하다 — 연속 기록 중이라 지금은 하지 않는다 |

**판정 기준 (역시 미리)**: A 와 D 의 중앙값이 285 ± 30 ms 이고 C 의 중앙값이 그 두 배를 넘으면 "707 은 재는 방법이 만든 값, 망의 왕복은 285"로 확정한다. B 가 C 보다 뚜렷이 작고 A 보다 크면 "양쪽 Nagle"까지 지지된다. A 가 700 근처면 가설을 버린다 — 망이나 브로커가 실제로 느린 것이므로 다시 본다.

```bash
# [Pi 창] 조건 넷을 차례로 (약 4분). 결과 파일에 서버 주소는 없다
cd ~/rt-robot-data-infra && git pull
( set -a; . ~/.config/rt-fleet/fleet.env; set +a
  L="Pi 4 (집, Wi-Fi)"
  python3 fleet/tools/mqtt_rtt.py --interval 1.00 --count 60  --from-label "$L" --out ~/rtt_A_1.00.json
  python3 fleet/tools/mqtt_rtt.py --interval 0.35 --count 170 --from-label "$L" --out ~/rtt_D_0.35.json
  python3 fleet/tools/mqtt_rtt.py --interval 0.20 --count 300 --from-label "$L" --out ~/rtt_C_0.20.json
  python3 fleet/tools/mqtt_rtt.py --interval 0.20 --count 300 --nodelay --from-label "$L" --out ~/rtt_B_0.20_nodelay.json )
python3 fleet/tools/nagle_model.py --rtt-ms 285      # 모형의 표 (어디서나 돈다)
```

## 4. 처음 읽는 사람을 위한 분석
- **첫 측정이 이상하다는 것을 어떻게 알았나.** 왕복이 707 ms 면 편도는 350 ms 쯤이어야 한다. 그런데 서버가 실제로 본 편도(전달 지연)는 146 ms 다. 시계가 200 ms 어긋나 있다는 뜻이 되는데, Pi 도 서버도 NTP 로 시각을 맞추고 있어 그럴 가능성은 낮다. 두 숫자가 다툴 때는 한쪽을 믿기 전에 "재는 방법"을 의심한다.
- **실마리 셋.** ① 최소값 285 ms 는 대시보드 편도 146 의 거의 정확히 두 배다. ② 최대값 854 는 285 의 3.0배, 중앙값 707 은 2.5배다 — 값이 285 의 2배와 3배 사이에 고르게 퍼져 있다(평균 708 ≈ 2.5배). 망이 흔들린 것이라면 이렇게 배수로 떨어지지 않는다. ③ 접속 시간 1,484 ms 는 TCP 연결 + TLS 악수 + MQTT 접속에 왕복이 4~5번 든다고 보면 285 ms 와 맞는다.
- **Nagle 이 무엇을 했다고 보나 (가설).** TCP 는 작은 조각을 많이 보내지 않으려고, "앞에 보낸 것의 수신 확인(ACK)이 아직 안 왔으면 다음 작은 조각은 보내지 않고 모아 둔다"(Nagle 알고리즘). 0.2초마다 한 건씩 쓰는데 ACK 는 0.285초 뒤에야 돌아오니, 둘째 메시지부터는 항상 붙잡힌다. 브로커도 같은 규칙을 쓰고(Mosquitto 의 `set_tcp_nodelay` 기본값은 꺼짐), 메시지마다 따로 쓰기 때문에 한 묶음으로 온 두 건 중 둘째의 되돌림은 첫째의 ACK 를 기다린다 — 그 ACK 는 한 왕복 뒤에 온다. 결과: 메시지는 "다음 보낼 차례"를 0~285 ms 기다리고, 되돌아오는 데 왕복이 두 번 든다 → 570~855 ms 에 고르게.
  - 예: 0.0초에 쓴 1번은 바로 나가 0.285초에 돌아온다(왕복 285 — 이것이 최소값). 0.2초에 쓴 2번은 1번의 ACK 가 오는 0.285초까지 붙잡혔다 나간다. 0.4초에 쓴 3번은 2번의 ACK 를 기다린다… 이렇게 밀린다.
- **모형이 말해 주는 것과 못 하는 것.** 위 규칙 셋만 넣은 모형이 285 / 710 / 845 / 860 을 낸다. 실측 285 / 707 / 838 / 854 와 한 자리까지 맞는다. 그러나 **맞는 설명은 여럿 만들 수 있다** — 그래서 같은 모형으로 아직 재지 않은 조건(A·D·B)의 값을 먼저 적었다. 모형은 계단 모양이고 실측은 Wi-Fi 만큼 퍼진다. 모형에는 혼잡 제어·재전송·TLS 레코드가 없다.
- **틀렸던 어림.** "한국 ↔ 시드니 왕복 130~160 ms"는 AWS 리전 사이의 전용망 수치에 가까운 것이었다. 집의 인터넷에서 시드니까지는(가설이 맞다면) 285 ms — 두 배다. 그리고 "대시보드 값에서 편도 70~80 ms 를 뺀 나머지는 시계 차이"라던 것도 틀렸다: 편도가 142 ms 쯤이면 대시보드의 146 ms 는 **거의 그대로 편도 지연**이고 Pi 와 서버의 시계 차이는 수 ms 다(시간대별 138.6~154.1 → 약 −4 ~ +12 ms, 경로가 대칭이라는 가정 아래의 어림). 어림을 "추정"이라고 적어 둔 것은 옳았고, 그 값을 믿고 설명을 덧붙인 것은 틀렸다.
- **운영에는 무슨 뜻인가.** 텔레메트리는 1 Hz — 간격(1초)이 왕복(0.285초)보다 길어 붙잡힐 것이 없다(예측 A). 영향을 받는 것은 **한 연결로 초당 4건 넘게** 작은 메시지를 주고받는 경우다: 텔레메트리 주기를 올리거나, 명령·응답을 빠르게 주고받을 때. 그때는 장치 쪽 소켓과 브로커 양쪽에 `TCP_NODELAY` 가 필요하다(예측 B: 한쪽만으로는 부족). 지금은 바꾸지 않는다 — 1 Hz 에서는 얻는 것이 없고, 브로커 설정은 재시작이 필요하다.
- 한계: 측정은 한 장소(집 Wi-Fi)·한 시각이다. 편도는 왕복의 절반이라는 어림(경로 대칭 가정). 브로커 쪽 Nagle 을 끈 조건은 재지 않았다.

## 5. 면접 한 문장
"서버까지의 왕복을 쟀더니 707 ms 가 나왔는데, 같은 구간의 편도가 146 ms 라 앞뒤가 안 맞았습니다. 보내는 간격이 왕복보다 짧아 Nagle 이 값을 키운 것이라는 가설을 모형으로 옮기니 실측과 맞았고, 재기 전에 적어 둔 다른 조건의 예측으로 확인했습니다 — 망의 왕복은 285 ms, 대시보드의 지연은 시계 차이가 아니라 거의 그대로 편도였습니다." (검증 측정 뒤 문장을 확정한다)
