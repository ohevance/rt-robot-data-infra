# E23 — 서버(시드니)까지 왕복 몇 ms 인가: 290 ms. 첫 측정 707 ms 는 재는 방법이 만든 값이었다 (예측을 먼저 적고 쟀다 — 넷 중 셋이 맞았다)
> 한 줄 요약: **Pi(집 Wi-Fi) ↔ 시드니 브로커의 MQTT 왕복은 290 ms**(1초 간격 60회 중 59회가 287~293 ms), 편도 어림 145 ms. 대시보드의 전달 지연 146.5 ms 는 거의 그대로 편도이고 두 시계의 차이는 약 +1.5 ms 다. 여기까지 오는 길: 처음 0.2초 간격으로 쟀더니 **최소 285 / 중앙 707 / 최대 854 ms** — 편도 146 ms 와 맞지 않았다. 가설: 보내는 간격이 왕복보다 짧아 **양쪽의 Nagle 알고리즘이 메시지를 왕복 두세 번만큼 붙잡았다**. 가설을 모형(`fleet/tools/nagle_model.py`)으로 옮기니 285 / 710 / 860 ms 로 첫 측정을 재현했고, 설명만으로는 부족하므로 **다른 조건 넷의 값을 재기 전에 예측해 적어 두고**(2절) 쟀다(09:41~09:44). **셋이 맞았다**: 1초 간격 290 ms(예측 285), 0.35초 간격 중앙 288 ms(285), 0.2초 + 클라이언트 `TCP_NODELAY` 464 ms(460). **하나가 틀렸다**: 0.2초 재측정의 중앙값 548 ms(예측 710) — 진짜 TCP 는 세 가지 띠를 오갔고 모형은 그중 하나만 안다. 실제 운영(1 Hz)은 간격이 왕복의 3.4배라 이 현상과 무관하다.

이전: [E22](E22.md) · 결정: DECISIONS 2026-11-11 (운영 기록은 세어서, 왕복 측정의 간격) · 도구: `fleet/tools/mqtt_rtt.py`, `fleet/tools/nagle_model.py`

## 1. 왜 했나 (이유)
- 운영 층을 시드니에 올리면서 "서버 왕복이 들어가는 숫자에는 '서버: 시드니'를 적는다"고 정했다(DECISIONS 11/10). 그러려면 그 왕복이 몇 ms 인지부터 알아야 한다. 대시보드의 "전달 지연"은 (서버가 받은 시각 − 장치가 찍은 시각)이라 두 시계의 차이가 섞인다 — 그래서 시계 하나로 재는 왕복 도구를 만들었다.
- 질문: ① Pi(집, Wi-Fi) ↔ 시드니 브로커의 왕복은 몇 ms 인가 ② 대시보드의 전달 지연(146 ms)은 편도 지연인가, 시계 차이인가 ③ 첫 측정의 707 ms 는 무엇인가.
- 재기 전의 어림은 "왕복 130~160 ms, 편도 70~80 ms, 대시보드 값의 나머지는 시계 차이"였다(`deploy/ec2/README.md` 4b, 11/10). **이 어림은 틀렸다**(4절) — 실측 왕복 290 ms.

## 2. 어떻게 하나
| 항목 | 값 |
|---|---|
| 도구 | `fleet/tools/mqtt_rtt.py` — 한 클라이언트가 자기만 구독하는 토픽(`rtt/<id>`)에 QoS 0 으로 보내고, 브로커가 되돌려 준 것을 받는다. 보낸 시각·받은 시각을 같은 단조 시계로 잰다. TLS·비밀번호·브로커를 실제 장치와 같은 길로 지난다 |
| 어디서 어디로 | Pi 4(집, Wi-Fi, RT 커널) → 시드니 EC2 의 Mosquitto 8883. 에이전트(1 Hz 보고)는 그대로 돈다 |
| 메시지 | 200바이트(텔레메트리 한 건과 비슷), 개수는 조건마다 60초 분량 |

넷 중 셋 충족, 하나 미달. **"망의 왕복은 약 290 ms 이고 707 ms 는 재는 방법이 만든 값"은 A 와 D 가 직접 확정한다** — 이 둘은 모형에 기대지 않는 측정이다(간격을 왕복보다 길게 했더니 값이 내려왔다). "양쪽 Nagle"은 B 가 지지한다. **모형이 0.2초 간격의 중앙값을 틀리게 예측했다는 것은 그대로 남긴다**(4절).

각 측정의 개별 값은 파일의 `samples_ms` 에 보낸 순서대로 있다.
- **A**: 60개 중 59개가 287.2~292.5 ms, 하나가 382.9 ms. 그 하나는 다음 메시지로 번지지 않았다.

- **C**: 세 띠. ① 처음 58개 — 올라가는 4개(276 → 510)와 850 ms 를 넘는 교란 7개를 빼면 **568~833 ms, 중앙 694**. ② 1,187 ms 짜리 교란 뒤 61~204번째(144개) — **336~620 ms, 중앙 473, 평균 474**. ③ 210번째부터 끝까지(90개) — **382~738 ms, 중앙 597**. 띠 안에서는 +73.5, +73.5, (+73.5), −200 ms 의 톱니가 같다.

## 4. 처음 읽는 사람을 위한 분석
- **첫 측정이 이상하다는 것을 어떻게 알았나.** 왕복이 707 ms 면 편도는 350 ms 쯤이어야 한다. 그런데 서버가 실제로 본 편도(전달 지연)는 146 ms 다. 시계가 200 ms 어긋나 있다는 뜻이 되는데, Pi 도 서버도 NTP 로 시각을 맞추고 있어 그럴 가능성은 낮다. 두 숫자가 다툴 때는 한쪽을 믿기 전에 "재는 방법"을 의심한다.
- **실마리 셋.** ① 최소값 285 ms 는 대시보드 편도 146 의 거의 정확히 두 배다. ② 최대값 854 는 285 의 3.0배, 중앙값 707 은 2.5배다 — 값이 285 의 2배와 3배 사이에 고르게 퍼져 있다(평균 708 ≈ 2.5배). 망이 흔들린 것이라면 이렇게 배수로 떨어지지 않는다. ③ 접속 시간 1,484 ms 는 TCP 연결 + TLS 악수 + MQTT 접속에 왕복이 4~5번 든다고 보면 285 ms 와 맞는다.
- **Nagle 이 무엇을 했나.** TCP 는 작은 조각을 많이 보내지 않으려고, "앞에 보낸 것의 수신 확인(ACK)이 아직 안 왔으면 다음 작은 조각은 보내지 않고 모아 둔다"(Nagle 알고리즘). 0.2초마다 한 건씩 쓰는데 ACK 는 0.29초 뒤에야 돌아오니, 둘째 메시지부터는 붙잡힌다. 브로커도 같은 규칙을 쓰고(Mosquitto 의 `set_tcp_nodelay` 기본값은 꺼짐), 메시지마다 따로 쓰기 때문에 한 묶음으로 온 두 건 중 둘째의 되돌림은 첫째의 ACK 를 기다린다.
  - 예: 0.0초에 쓴 1번은 바로 나가 0.29초에 돌아온다(이것이 최소값). 0.2초에 쓴 2번은 1번의 ACK 가 오는 0.29초까지 붙잡혔다 나간다. 0.4초에 쓴 3번은 2번의 ACK 를 기다린다… 이렇게 밀린다.
- **맞은 것 셋 (재기 전에 적은 예측).**
  1. **1초 간격이면 평평하다**: 290 ms, 60회 중 59회가 287~293 ms. 이것이 망의 왕복이다 — 모형 없이도 성립하는 직접 측정.
  2. **문턱은 왕복 시간이다**: 0.35초 간격(왕복보다 60 ms 길다)에서 중앙값 288 ms. 0.2초에서는 548~707 ms.
  3. **한쪽만 Nagle 을 끄면 절반쯤만 준다**: 클라이언트에 `TCP_NODELAY` 를 걸고 0.2초 간격 — 실측 283 / 464 / 605 / 614(평균 473), 모형 285 / 460 / 610 / 610(평균 474). 네 숫자가 모두 6 ms 안에서 맞는다. 브로커 쪽 Nagle 이 남아 있다는 뜻이다.
- **틀린 것 하나.** 0.2초 간격·옵션 없음의 중앙값을 710 으로 예측했는데 548 이 나왔다. 개별 값을 보면 측정은 **세 가지 띠**를 오갔다: 처음 58개는 568~833 ms·중앙 694(모형의 570~855·중앙 710, 첫 측정이 있던 띠), 1.2초짜리 교란 뒤 144개는 336~620 ms·평균 474(위 3번 "한쪽만 Nagle"의 실측 평균 473·모형 474 와 같은 띠), 끝의 90개는 그 사이(중앙 597). 모형은 결정적이라 처음 들어선 띠에 영원히 머문다. 진짜 TCP 에서는 재전송 같은 교란이 "지금 어느 쪽이 붙잡고 있나"의 박자를 바꾸고, 그 뒤 다른 띠에 자리 잡는 것으로 보인다(**추정** — 패킷을 잡아 본 것이 아니다). 첫 측정이 60초 내내 높은 띠에만 있었던 것은 교란이 없었기 때문일 것이다. 그래서 모형의 말은 "간격이 왕복보다 짧으면 2~3배"가 아니라 "**1.2~3배, 어느 띠인지는 그때그때 다르다**"로 고쳐 읽어야 한다. 예측이 맞은 것만 적으면 모형을 실제보다 좋게 보이게 한다.
- **문턱 근처에서는 교란이 번진다 (예측에 없던 발견).** 0.35초 간격에서는 평소 288 ms 지만, 한 번 늦어지면(네 번 있었다: 꼭대기 501 · 504 · 1,163 · 504 ms) 뒤따르는 메시지들이 계단처럼 내려오며 회복했다 — 걸음 17개 중 11개가 **66.9~68.0 ms**. 이 걸음은 (보내는 간격 350 ms − 밀렸을 때의 왕복 282.5 ms) 와 같다 — 밀린 것이 "한 왕복에 한 건"씩만 빠지고, 새 메시지는 350 ms 마다 오니, 한 건마다 67.5 ms 씩만 따라잡는다. 1초 간격에서는 같은 종류의 교란(383 ms 한 번)이 다음 메시지에 아무 영향을 주지 않았다. 주기가 왕복에 가까운 연결은 평균은 멀쩡해 보여도 꼬리가 길다.
- **틀렸던 어림.** "한국 ↔ 시드니 왕복 130~160 ms"는 AWS 리전 사이의 전용망 수치에 가까운 것이었다. 집의 인터넷에서 이 서버까지는 290 ms — 두 배다. 그리고 "대시보드 값에서 편도 70~80 ms 를 뺀 나머지는 시계 차이"라던 것도 틀렸다: 편도 어림은 145 ms(왕복의 절반)이고 대시보드의 전달 지연은 146.5 ms — **거의 그대로 편도 지연**이며 Pi 와 서버의 시계 차이는 +1.5 ms 쯤이다(시간대별 138.6~154.1 ms → 약 −6 ~ +9 ms. 올라가는 길과 내려오는 길이 같다는 가정 아래의 어림). 어림을 "추정"이라고 적어 둔 것은 옳았고, 그 값을 믿고 설명을 덧붙인 것은 틀렸다.
- **운영에는 무슨 뜻인가.** 텔레메트리는 1 Hz — 간격(1초)이 왕복(0.29초)의 3.4배라 붙잡힐 것이 없다(예측 A 확인). 영향을 받는 것은 **한 연결로 초당 3건 넘게** 작은 메시지를 주고받는 경우다: 텔레메트리 주기를 올리거나, 명령·응답을 빠르게 주고받을 때. 그때는 장치 쪽 소켓과 브로커 **양쪽**에 `TCP_NODELAY` 가 필요하다(한쪽만으로는 464 ms — 예측 B 확인). 지금은 바꾸지 않는다 — 1 Hz 에서는 얻는 것이 없고, 브로커 설정은 재시작이 필요하다(DECISIONS 11/11).
- 접속 한 번(TCP 연결 + TLS 악수 + MQTT 접속)은 1.2~1.5초 — 왕복의 4~5배다(다섯 번의 측정: 1,484 · 1,494 · 1,491 · 1,444 · 1,215 ms). 브로커가 재시작됐을 때 장치가 다시 붙는 데 드는 시간의 바닥이 이것이다.
- 한계: 측정은 한 장소(집 Wi-Fi)·한 시각(평일 오전 9시 40분대)이고 조건마다 한 번씩이다. 편도는 왕복의 절반이라는 어림. 브로커 쪽 Nagle 을 끈 조건은 재지 않았다. 세 띠의 원인은 추정이다.

## 5. 면접 한 문장
"서버까지의 왕복을 쟀더니 707 ms 가 나왔는데, 같은 구간의 편도가 146 ms 라 앞뒤가 안 맞았습니다. 보내는 간격이 왕복보다 짧아 Nagle 이 값을 키웠다는 가설을 모형으로 옮기고, 재기 전에 다른 조건의 값을 예측해 적어 둔 뒤 쟀습니다. 넷 중 셋이 맞아 망의 왕복은 290 ms 로 확정했고, 틀린 하나에서는 진짜 TCP 가 모형과 달리 여러 상태를 오간다는 것을 배웠습니다. 대시보드의 지연은 시계 차이가 아니라 거의 그대로 편도였습니다."
