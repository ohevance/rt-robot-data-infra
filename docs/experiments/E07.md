# E07 — 유실 "0" 은 진짜였나: 측정 기준점을 고치자 53 / 1434, 원인은 셋
> 한 줄 요약: "유실 0 이 다른 증거(12초 공백)와 안 맞는다 — 측정이 틀렸나?" → 틀렸다. 기준점을 "장애 창 안 첫 번호"에서 **"장애 직전 마지막 번호"**로 바꾸자 브로커 10초 중단의 유실이 **53 / 1434** 로 드러났고, 장치·번호 단위로 추적하니 원인이 **세 가지**(브로커 재시작 경쟁 · 수집기 종료 순간 · 큐 상한)로 갈라졌다.

이전: [E06](E06.md) (장애 4종 1차) · 다음: [E08](E08.md) (고친 뒤 재측정) · 곁가지: [E12](E12.md) (큐 상한)

## 1. 왜 했나 (이유)
- [E06](E06.md)의 유실은 전부 "0" 이었는데, 진단 도구 `diag.py` C절은 장치 vdev-003·005 에 브로커 중단 직후 **12초 데이터 공백**을 보였다. 1 Hz 장치가 12초 비었는데 유실 0 — 둘 중 하나는 거짓이다. 순서도의 마름모 **"유실 0 이 다른 증거와 맞나?" → 아니오**.
- 합격선: 유실 계산이 **진단 도구의 seq 틈과 일치**할 것. 숫자가 서로를 설명하지 못하면 둘 다 못 믿는다.
- 이 실험은 숫자를 좋게 만드는 것이 아니라 **나쁘게 만드는** 실험이다. 포트폴리오에서 가장 중요한 줄이 여기서 나온다: "0 을 의심해서 53 을 찾았다".

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 환경 | WSL2, 가상 50대 1 Hz, 수집기·장치 QoS 1 (E06 과 같음) |
| 고친 것 | `fleet/chaos/inject.py` 의 `measure_loss`: 기준점을 장애 **직전 30초의 마지막 seq** 로 |
| 추적 도구 | `fleet/tools/diag.py` C절 — 장치별 `lag(seq)` 로 번호 틈을 초 단위로 묶어 "유실 / 장치 멈춤 / 순서 뒤바뀜" 분류 |
| 재측정 | 브로커 10초 중단 1회 |

유실 계산식(고친 뒤):
```
장치별 기대 개수 = 창 안 max(seq) − 장애 직전 마지막 seq
장치별 유실      = 기대 개수 − 창 안에서 실제 받은 행 수
전체 유실        = 장치별 유실의 합        (SQL: inject.py measure_loss 의 WITH w ..., b ... )
```
왜 "직전 마지막 seq" 인가: 창 안 min(seq) 를 기준으로 하면, 장애 시작 직후 잃은 메시지는 "창 안에서 처음 받은 번호"보다 앞에 있어서 **계산 범위 밖**이 된다 — 그 장치가 12개를 잃어도 창은 13번째부터 시작하니 0 으로 보인다. 직전 30초에 데이터가 없는 장치만 예전 방식(min(seq) − 1)으로.

```bash
python3 fleet/chaos/inject.py --fault broker --duration 10
python3 fleet/tools/diag.py --minutes 15          # C절: 어느 장치가 어느 번호를 잃었나
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **seq(일련번호)**: 장치가 메시지마다 1씩 올려 붙이는 번호. 1, 2, 3, 5 가 왔으면 4 를 잃은 것. 유실을 "세는" 유일한 근거.
- **장애 창(window)**: 주입 시각부터 복구 + 정착(settle 15초)까지의 시간 구간. 그 안의 행만 세면 **창 가장자리**에서 틀린다 — 이번 맹점의 정체.
- **PUBACK**: QoS 1 에서 받는 쪽이 보내는 "받았다" 확인. 이것을 보낸 순간부터 **보관 책임이 받는 쪽으로** 넘어온다. 수집기는 PUBACK 을 보내고 1초 뒤에 DB 에 넣으므로 그 사이에 죽으면 그 1초치가 사라진다.
- **지속 세션 / 구독**: 수집기가 "나 없는 동안 내 몫을 보관해 달라"고 브로커에 남긴 약속. `persistence false` 면 브로커가 재시작할 때 이 약속도 메모리와 함께 사라진다.
- **persistence(브로커)**: Mosquitto 가 세션·보관 메시지를 디스크에 써 두는 설정. 켜면 재시작을 넘긴다.
- **max_queued_messages**: 브로커가 구독자 하나를 위해 들고 있을 수 있는 QoS 1 메시지의 최대 개수(여기서는 20,000).
- **행 / 개**: DB 의 행 1 = 메시지 1개. "53 / 1434" = 그 창에서 장치들이 만든 1,434개 중 53개가 DB 에 없다.

### 4-2. 쉬운 예제
- 비유(맹점): 출석부를 "교실에 들어온 첫 학생부터" 센 것. 수업 시작 직후 결석한 학생은 **첫 학생보다 앞 번호**라서 명단에 애초에 없다. 고친 방법은 "어제 마지막 출석 번호 다음부터" 세는 것.
- 계산 예(①): 장치 1대가 13초 동안 1 Hz 로 보냈으니 기대 13개, 실제 받은 것 1개 → 12개 유실. 그런 장치가 4대 = 48, 042 가 5개 → 53. 전체 창에서 50대가 만든 1,434개 중 53 = **3.7 %**.
- 계산 예(③): 50대 × 412초(보관된 구간) ≈ 20,600 ≈ 상한 20,000. 그 뒤 49초 × 50대 = 2,450개가 버려짐.

### 4-3. 숫자가 말하는 것
- 합격선(유실 계산 = 진단 도구의 틈): **고친 뒤 일치**. C절이 보여 준 공백과 유실 53 이 장치·번호 단위로 맞는다. 하지만 "유실 0" 합격선은 **못 넘는다** — 그래서 고칠 것이 생겼다.
- 확인: ①의 원인은 설정 한 줄(`persistence true` + 데이터 볼륨). 구독이 재시작을 넘겨 살아 있으면 먼저 온 장치 버퍼도 큐에 담긴다. ②는 수집기가 SIGTERM 을 받으면 수신을 끊고 **마지막 flush 를 한 뒤** 종료하는 것(`shutdown()`, 20줄). 둘 다 고쳐 다시 잰 것이 [E08](E08.md).
- 확인: ③은 "고장"이 아니라 상한의 뜻이다 — 지속 세션은 "무한 보관"이 아니라 "**상한이 있는 보관**". 상한은 "허용 중단 시간(분) × 장치 수 × Hz" 로 정하고, 그 이상은 장치 버퍼(store-and-forward)가 맡는 것이 맞는 역할 분담.
- 추정(미확정): 20,057개가 1초에 쏟아진 직후 전 장치가 1개씩 더 잃고 50대가 동시에 재접속했다. 단일 스레드 브로커가 큐 방류에 묶여 keepalive 응답을 못 해 전원이 끊겼다 돌아온 것(천둥 떼, thundering herd)으로 보이나 브로커 로그(`log_type all`)가 없어 미확정.
- 남는 틈(보류): ②는 SIGKILL(진짜 크래시)에서는 여전히 잃는다. 완전한 해법은 "DB 에 넣은 뒤 PUBACK"(paho manual_ack) — 묶음 적재와 ACK 순서를 엮어야 해 2주 계획 밖, `DECISIONS.md` 에 보류로 기록. 면접에서 "다음 단계"로 말한다.
- 그래서 다음에 무엇을 물었나: "①② 를 고치면 0 이 되나?" → [E08](E08.md). "상한을 넘기면 정말 버리나?" → [E12](E12.md).

## 5. 면접 한 문장
- "장애 주입의 유실이 0 으로 나왔지만 진단 도구의 12초 공백과 맞지 않아 측정식을 의심했고, 기준점을 장애 직전 번호로 고치자 53 이 나왔다 — 원인 셋 중 둘은 설정 한 줄과 종료 처리 20줄로 막혔고, 셋째(큐 상한)는 설계 규칙이 됐다."
