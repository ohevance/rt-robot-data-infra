# E20 — 로봇 안 고주기 기록 파이프라인: rosbag2(MCAP) → CSV → 검증 요약, 첫 실행
> 한 줄 요약: "로봇 안의 100 Hz 원본 데이터를 기록하고, 사람이 안 보고도 '제대로 기록됐나'와 '제어가 제대로 됐나'를 뽑을 수 있나?" → 30초 기록에서 `/joint_states` 2,964행 **100.0 Hz · 틈 0**, `/joint_command` 50.0 Hz, `/rt_status` 1.0 Hz, 드롭 0, 그리고 추종 오차 표에 **shoulder_lift 0.0191 rad(≈1.1°)** 의 중력 처짐이 자동으로 나왔다. 단, 첫 시도는 스크립트 버그(timeout 과 터미널)로 멈췄다.

## 1. 왜 했나 (이유)
- 공고 문장 ③ "센서 스트리밍·로깅·전처리 자동화". 지금까지의 `fleet` 은 **관제** 길이다 — 장치마다 1 Hz 요약을 MQTT 로 서버에 보내고 DB 에 넣는다. 로봇 **안**에서 생기는 100 Hz 원본(관절 위치·속도, 1 kHz 루프의 통계)은 그 길로 보내지 않는다(양이 100배, 네트워크가 끊겨도 남아야 함). 그래서 별도의 길이 필요하다: 로컬 파일에 기록(rosbag2) → 표(CSV) → 검증 요약.
- [E03](E03.md) 에서 노드가 100 Hz `/joint_states` 를 낸다는 것은 봤지만 "기록되나, 기록이 믿을 만한가"는 안 봤다. [E16](E16.md) 의 중력 처짐은 `ros2 topic echo` 로 **눈으로** 읽은 값이었다 — 그것이 기록 파이프라인에서 **자동으로** 나오면 "전처리 자동화"의 증거가 된다.
- 코드는 D6(11/04)에 만들었지만 샌드박스에 ROS 2 가 없어 **가짜 rosbag2_py 로 논리만** 검증했다(`docs/LOG.md` 11/04 "D6 시작"). WSL 첫 실행이 곧 실험이다.
- 합격선: 세 토픽의 실제 Hz 가 설계값(100 / 50 / 1)과 1% 안에서 맞고, 틈(설계 주기의 3배 넘는 공백) 0, `rt_status` 드롭 0. 그리고 추종 오차 표에 E16 의 처짐(약 0.02 rad)이 어깨에서 보여야 한다.

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **rosbag2 / MCAP**: ROS 2 의 "블랙박스 녹화기"와 그 파일 형식. 여러 토픽의 메시지를 시각과 함께 한 파일에 순서대로 담는다. 나중에 파이썬(`rosbag2_py`)으로 그대로 읽는다. `../GLOSSARY.md` "MCAP / rosbag2".
- **토픽**: ROS 2 에서 데이터가 흐르는 이름표. `/joint_states`(관절 위치·속도, 노드가 100 Hz 로 냄), `/joint_command`(목표, 50 Hz 로 넣음), `/rt_status`(1 kHz 루프의 1초 통계 JSON).
- **Hz(헤르츠)**: 1초에 몇 번. 100 Hz = 10 ms 마다 한 번. "실제 Hz" = 메시지 수 ÷ 기간 = 2,964 ÷ 29.6 = 100.1 → 반올림 100.0.
- **틈(gap)**: 연속한 두 메시지 사이가 설계 주기의 3배(100 Hz 면 30 ms)보다 벌어진 곳. 0 이면 기록이 한 번도 끊기지 않았다.
- **추종 오차**: 같은 시각의 |목표 − 실제 위치|. 단위 rad(라디안). 1 rad = 57.3°, 0.0191 rad × 57.3 = **1.09°**.
- **p99 / max (rt_status)**: 1초 동안 1,000번 깬 것 중 99번째로 늦은 것 / 가장 늦은 것. WSL 은 실시간 커널이 아니라 참고값([E18](E18.md)·[E19a](E19a.md) 의 Pi 값과 비교하지 않는다).
- **SIGTTIN / 프로세스 그룹**: 터미널은 "앞에 있는" 프로세스 그룹에만 키보드를 준다. 뒤에 있는 프로세스가 키보드를 읽으려 하면 커널이 **정지 신호(SIGTTIN)** 를 보내 그 프로세스를 멈춘다(죽이지 않는다). 첫 시도가 멈춘 이유.

### 4-2. 쉬운 예제
- 비유: 자동차 블랙박스. 관제(fleet)는 보험사에 1분마다 "속도·위치 요약"을 보내는 것, 기록(rosbag2)은 차 안 SD 카드에 30 fps 영상을 남기는 것. 사고 분석은 영상으로 하고, 영상이 **빠짐없이 30 fps 로** 찍혔는지는 사람이 다 볼 수 없으니 자동 검사(틈 0, fps 확인)가 있어야 한다 — 그것이 `summary.md`.
- 계산: 30초 × 100 Hz = 3,000개가 기대값인데 2,964개 = 29.6초치. 기록기가 토픽 구독을 끝내기까지 0.1초, 종료 절차 0.3초가 빠진 것이지 유실이 아니다 — 유실이면 **틈**이 잡힌다(틈 0). 어깨 처짐: 목표 −0.200, 실제 −0.181 → |차| 0.019 rad = 1.1°.

### 4-3. 숫자가 말하는 것
- 합격선 통과: 세 토픽 모두 설계 Hz 그대로, 틈 0, 드롭 0 — **기록 파이프라인은 30초 동안 한 번도 끊기지 않았다**.
- 확인: E16 에서 눈으로 읽은 중력 처짐(어깨 1.1°)이 **자동 요약 표에 그대로** 나왔다. 게다가 E16 땐 지나쳤던 것 — **팔꿈치도 0.0094 rad(0.5°) 처진다**(팔꿈치 아래 손목·그리퍼 무게). 중력이 걸리는 관절 둘 다 보인다. "전처리 자동화"가 사람의 눈보다 하나 더 찾았다.
- 확인: 평균 = 최대인 이유는 명령이 고정값이고 기록 시작 전에 이미 정상 상태였기 때문. 목표가 뛰는 구간을 기록하면 최대가 커진다(변화량 제한 0.05 rad/주기로 따라가는 동안).
- 확인(참고값): `rt_status` 의 wake p99 288~606 us, max 최대 2,984 us 는 WSL 의 가상 커널 값으로 [E03](E03.md) 과 같은 급. 드롭 0 이므로 기록 중에도 1 kHz 루프는 주기를 지켰다. Pi RT 커널이면 이 열이 수십 us 가 된다([E19c](E19c.md)).
- 깨진 것과 해결(확인): 첫 시도의 멈춤은 `record.sh` 가 `timeout` 으로 recorder 를 감쌌는데 `--foreground` 가 없어서 recorder 가 **뒤 프로세스 그룹**에 놓였고, recorder 의 키보드 제어(SPACE 일시정지)가 터미널을 읽다 SIGTTIN 으로 정지된 것. 정지된 프로세스는 30초 뒤의 SIGINT 도 못 받아 스크립트가 영원히 기다렸다. 해결: `timeout --foreground` + `--disable-keyboard-controls` + `--topics`. 두 번째 시도는 바로 통과. 배운 것: **"조용히 안 끝남"은 죽은 게 아니라 정지된 것일 수 있다** — `pkill -CONT` 로 깨운 뒤 `-INT`.
- 추정: 시작 0.1초가 빠진 것은 recorder 의 토픽 구독이 끝나기 전 메시지. 더 정확히 하려면 구독 뒤에 명령을 시작하면 된다(안 함 — 요약의 "틈" 이 유실 여부를 이미 가린다).
- 그래서 다음: 이 요약을 E16 의 "중력 보상 필요"의 두 번째 근거로 붙이고, 영상 한 장면(MCAP 생성 → summary 출력)으로 쓴다. 기록 → 관제 연결(요약 숫자를 fleet 에 1 Hz 로 올리기)은 보류 항목.

## 5. 면접 한 문장
- "관제는 1 Hz 요약을 서버로, 기록은 100 Hz 원본을 로봇 안 MCAP 으로 — 두 길을 나눴고, 기록 쪽은 CSV 와 검증 요약까지 자동이라 30초 기록에서 '100.0 Hz·틈 0·드롭 0' 과 중력 처짐 1.1°(그리고 눈으로는 놓쳤던 팔꿈치 0.5°)가 사람 손 없이 나온다."
