# E19-b — RT 커널 + RT 스레드를 CPU 3 에 고정(pin): 옮겨 다니는 비용이 범인인가
> 한 줄 요약: PREEMPT_RT 에서 남은 부하 max 301 us 가 "스레드가 CPU 사이를 옮겨 다녀서" 인지 확인하려고 CPU 3 에 못 박았다 → max **311.5 us**, 변화 없음. "고정으로 줄었나?" 에 **아니오** → 그 CPU 위의 다른 일이 범인인가 → [E19-c](E19c.md).

## 1. 왜 했나 (이유)
- [E19-a](E19a.md) 의 질문: **"남은 300 은 CPU 를 옮겨 다녀서인가?"** — 리눅스는 스레드를 비는 CPU 로 옮긴다(마이그레이션). 옮길 때마다 캐시가 식고 스케줄러 비용이 든다. 흔한 처방이 "RT 스레드를 CPU 하나에 고정하라"이므로 그것부터 시험한다.
- 순서도의 마름모: **"고정으로 줄었나?"** — 줄면 처방 확정, 안 줄면 범인은 다른 데 있다.
- 합격선: E19-a 의 301 보다 분명히 낮을 것(가령 200 아래). 한 변수(고정 여부)만 바꾸고 커널·부하·시간은 그대로.

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 어디서 | Pi 4B, `6.8.0-2054-raspi-realtime`, `/sys/kernel/realtime` = 1 (E19-a 와 동일) |
| 바꾼 것 | `jitter_run.sh` 의 4번째 인자 `3` → `jitter_bench --cpu 3`(RT 스레드의 CPU 친화도를 CPU 3 하나로) |
| 그대로인 것 | 우선순위 80, 60초, 50 us 작업, stress-ng 같은 부하. 이때 CPU 3 에는 stress 작업·인터럽트·커널 스레드도 **여전히** 올라온다 |
| 열 | 식힌 뒤 시작(52 °C 아래까지 대기), 51.1 → 73.5 °C, 스로틀 0 |

`docs/SETUP_RT_MEASURE.md` 6단계:
```bash
while [ $(cat /sys/class/thermal/thermal_zone0/temp) -gt 52000 ]; do sleep 5; done     # 식을 때까지 대기
sudo scripts/jitter_run.sh pi4_rt_stress_pin 60 stress 3
```

## 3. 결과
출처: `docs/measurements/jitter_pi4_rt_stress_pin.json(.meta)` (2026-11-05). 출력 머리에 `cpu_pin: ok`.

| 부하 중, jitter_bench 60 s | p50 | p99 | p99.9 | **max** | work time max |
|---|---:|---:|---:|---:|---:|
| RT, 고정 없음 (E19-a) | 26.1 | 185.2 | 241.5 | **300.6** | 97.7 |
| **RT + CPU 3 고정** | 26.4 | 169.1 | 216.1 | **311.5** | 86.1 |

같은 60초 동안 60,000 주기, 드롭 0. 온도 51.1 → 73.5 °C(부하 측정 중 가장 높았지만 80 °C 경계 아래), 스로틀 플래그 0 → 유효한 측정.

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **CPU 친화도(affinity) / 고정(pin)**: "이 스레드는 CPU 3 에서만 돌아라"고 못 박는 것. `jitter_bench --cpu 3`. 비유: 직원 한 명을 3번 계산대에만 세우는 것.
- **마이그레이션(migration)**: 스케줄러가 스레드를 다른 CPU 로 옮기는 것. 옮기면 그 CPU 의 캐시(최근 쓴 데이터를 가까이 두는 작은 메모리)가 비어 있어 처음 몇 us 가 느리다.
- **캐시(cache)**: CPU 바로 옆의 작은 고속 메모리. 책상 위(캐시)에 있는 서류는 바로 보지만 서고(메인 메모리)에 있으면 걸어가야 한다.
- **인터럽트(IRQ)**: 장치(Wi-Fi, SD 카드, 타이머)가 "지금 봐 달라"고 CPU 를 부르는 신호. RT 커널에서는 대부분 스레드로 처리되지만, 가장 첫 부분(하드 인터럽트)은 여전히 하던 일을 잠깐 멈춘다.
- **IPI(프로세서 간 인터럽트)**: 한 CPU 가 다른 CPU 들에게 보내는 신호. 메모리 매핑이 바뀌면(TLB 동기화) 모든 CPU 가 잠깐 멈춰 응답한다 — 우선순위로 막을 수 없다.
- 단위: us = 100만분의 1초.

### 4-2. 쉬운 예제
- 비유: 직원을 3번 계산대에 못 박았지만, 3번 계산대 앞에는 여전히 다른 손님(stress 작업)이 줄 서 있고, 매장 방송(인터럽트)이 울리면 직원은 여전히 멈춘다. "자리를 옮기느라 늦은 것"이 아니었던 것이다.
- 계산: 고정 전후 max 300.6 → 311.5, 차이 +10.9 us = 3.6%. 60초 측정의 반복 오차 범위 안(한가 측정에서 24.9 vs 27.8 처럼 몇 us 는 늘 흔들린다). "효과 없음"으로 읽는다.

### 4-3. 숫자가 말하는 것
- 마름모 "고정으로 줄었나?" → **아니오**. 합격선(200 아래) 못 넘음.
- 확인: max 는 그대로(301 → 311), p99·p99.9 는 10~25 us 줄고 `work time` max 는 97.7 → 86.1. 즉 고정은 "옮겨 다니는 작은 비용"은 조금 덜어 주지만, **꼬리를 만드는 큰 사건은 CPU 를 옮기는 것과 무관**하다.
- 확인: 측정 머리글에 `cpu_pin: ok` — 고정이 실제로 적용된 상태였다(안 됐다면 결론이 무효).
- 추정: 꼬리의 출처는 CPU 3 위에서 함께 도는 것들 — stress-ng 작업 4개 중 하나, 인터럽트 스레드, 커널 스레드(ksoftirqd·kworker 등), 그리고 전 CPU 공통 IPI. 우선순위 80 은 일반 작업은 밀어내지만 하드 인터럽트와 IPI 는 못 막는다.
- 그래서 다음 질문: **"그 CPU 의 다른 일(stress·IRQ·커널 스레드) 때문인가?"** → CPU 3 을 커널의 일반 스케줄링에서 아예 떼어 내는 `isolcpus=3` → [E19-c](E19c.md). 고정(E19-b)과 격리(E19-c)를 **따로** 재야 "CPU 하나 주면 되는 것 아닙니까?" 라는 질문에 "주는 것만으로는 안 되고 비워야 한다"고 답할 수 있다(`docs/DECISIONS.md` 2026-11-05).

## 5. 면접 한 문장
- "RT 스레드를 CPU 에 고정만 해서는 max 가 301 에서 311 로 그대로였다 — 꼬리는 스레드가 옮겨 다녀서가 아니라 그 CPU 위의 다른 일 때문이었고, 그래서 고정이 아니라 격리(isolcpus)가 답이었다."
