# E05 — 관제 기본: 가상 장치 50대 1 Hz 의 전달 지연, 그리고 브로커가 10초 죽으면
> 한 줄 요약: "장치 50대가 1초에 한 번씩 보내는 데이터가 서버에 제때 닿나? 중간(브로커)이 10초 끊기면 데이터는 어디로 가나?" → 전달 지연 p50 0.9 / p95 1.8 ms, 끊긴 10초 동안 장치가 **654개를 버퍼에 모았다가 654개를 그대로 재전송**, 50대 전부 재접속.

이전: [E04](E04.md) (DDS 표②) · 다음: [E06](E06.md) (장애 4종 1차) · 곁가지: [E09](E09.md) (왜 20?), [E10](E10.md) (왜 10초마다 튀나?)

## 1. 왜 했나 (이유)
- 공고 ②③은 "실시간 로깅·모니터링·시각화·업데이트"와 "센서 스트리밍·로깅 자동화"다. 로봇 **밖**의 길 — 장치 수십~수백 대 → 서버 → DB → 대시보드 — 가 돌아간다는 것을 숫자로 보여야 한다. 그 첫 숫자가 "정상일 때 얼마나 빨리 닿나"와 "끊기면 잃나"다.
- 순서도의 첫 마름모: **"끊김 동안 데이터가 보존되나?"** 이 실험은 그 답을 내고, 답이 "예"여야 장애별 세부 숫자([E06](E06.md))로 갈 수 있다.
- 합격선: (1) 전달 지연 p95 가 수 ms(1 Hz 데이터에 1초 묶음 적재가 더해지므로 ms 단위면 충분), (2) 브로커 중단 중 장치 버퍼에 쌓인 수 = 재접속 뒤 재전송된 수(= 안 잃었다), (3) 50대 전부 재접속.

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **MQTT**: 장치 ↔ 서버 메시지 규약. 장치는 서버에 직접 보내지 않고 **브로커**(우체국)에 "주제(topic)"를 붙여 올리고, 서버(수집기)는 그 주제를 구독해서 받는다. 장치 수백 대가 공유기·LTE 뒤에 있어도 브로커 하나만 바라보면 되는 구조(`DECISIONS.md` 11/03 D2).
- **브로커(Mosquitto)**: MQTT 우체국 프로그램. 여기서는 도커 컨테이너.
- **수집기(collector)**: 브로커에서 받은 메시지를 DB 에 넣는 서버 프로그램(`fleet/collector/collector.py`).
- **텔레메트리**: 장치가 주기적으로 보내는 상태값 묶음(관절 상태, 온도, 일련번호 등). 여기서는 장치당 1 Hz = 1초에 1개.
- **msgs/s**: 초당 메시지 수. 50대 × 1 Hz = 50 msgs/s.
- **전달 지연(transit latency)**: 장치가 값을 **측정한 시각**부터 수집기에 **도착한 시각**까지. DB 에 보일 때까지는 1초 묶음 적재가 최대 1초 더 걸린다(설계상, `DECISIONS.md` 11/03 D2 "1초 묶음 + COPY").
- **COPY**: PostgreSQL 에서 여러 행을 한 번에 넣는 빠른 명령. 행마다 INSERT 하면 DB 왕복이 50회/초, 묶으면 1회/초.
- **p50 / p95**: 100개 중 가운데 값 / 100개 중 95번째로 나쁜 값. 관제는 p95 로 본다(제어처럼 p99.9 까지는 안 간다 — 사람이 보는 화면이므로).
- **store-and-forward(모았다 보내기)**: 끊기면 장치가 메모리에 쌓아 두고(최대 1시간 분), 재접속하면 QoS 1 로 재전송. 버퍼 수·재전송 수·재접속 수를 텔레메트리에 같이 실어 보낸다 → 서버가 장치의 "끊김 이력"을 숫자로 받는다.
- **seq(일련번호)**: 장치가 메시지마다 1씩 올려 붙이는 번호. 서버는 번호의 빈칸으로 유실을 센다.

### 4-2. 쉬운 예제
- 비유: 지점 50곳이 본사에 1분마다 매출 문자를 보낸다. 통신사(브로커)가 10분 먹통이 되면 — 지점 직원이 그동안의 문자를 **메모장에 적어 뒀다가** 복구되자마자 몰아서 보낸다(버퍼 → 재전송). 본사에는 10분치가 1분 안에 한꺼번에 도착하므로 "초당 문자 수"가 평소의 10배로 치솟고(폭주 600 msgs/s), 문자에 적힌 "측정 시각"은 10분 전이라 "도착 − 측정" 차이가 최대 10분(여기서는 12.5초)으로 찍힌다. 이것은 **유실이 아니라 지연**이다.
- 계산 예: 50대 × 10초 × 1 Hz = **500개**가 끊긴 동안 생긴다. 실제 버퍼는 654 — 끊김 감지·재접속에 걸린 시간(≈ 3초)만큼 더 쌓였다: 654 ÷ 50 ≈ 13초. 재전송도 654 → 쌓인 것과 보낸 것이 같으니 그 구간 유실 0.

### 4-3. 숫자가 말하는 것
- 합격선: **통과**. p95 1.8 ms(합격선 "수 ms"), 버퍼 654 = 재전송 654, 재접속 50/50.
- 확인: 전달 지연 max 12.5 s 는 장애의 흔적이지 결함이 아니다 — 측정 시각 기준으로 잰 값이고, 그래야 "이 데이터가 얼마나 늦게 왔나"가 대시보드에 보인다. 이름을 "수집 지연"에서 **"전달 지연"**으로 고친 것도 이때다(`LOG.md` D2 용어 정정).
- 추정 → 뒤에 확인됨: 오프라인 이벤트가 50 이 아니라 20 인 것은 "브로커가 종료되며 모든 접속의 유언(LWT — 장치가 미리 맡겨 둔 '나 끊겼다' 메시지)을 한꺼번에 발행하다가 소켓을 닫아 앞쪽 20개만 수집기에 닿았다"는 가설 → [E09](E09.md) 에서 확인.
- 추정 → 뒤에 확인됨: 10초마다 전달 지연이 튀는 것은 장치 50대의 keepalive(10초마다 보내는 "나 살아 있다" 신호)가 같은 박자로 몰려서 → [E10](E10.md) A/B 로 확인.
- 그래서 다음에 무엇을 물었나: "끊기면 버퍼가 일한다"는 것은 봤다. 그럼 **장애 종류별로**(브로커·DB·수집기·나쁜 펌웨어) 감지·복구에 몇 초 걸리고 몇 개를 잃는지를 **시스템 자신의 DB 숫자로** 내는 것 → [E06](E06.md).

## 5. 면접 한 문장
- "장치 50대 1 Hz 의 전달 지연은 p95 1.8 ms 였고, 브로커를 10초 죽이자 장치가 654개를 모았다가 654개를 그대로 재전송했다 — 유실은 '없게'가 아니라 '세게' 만들어 두어야 이런 문장을 숫자로 말할 수 있다."
