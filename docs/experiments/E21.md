# E21 — 위로보틱스 공개 모델 ALLEX(48 자유도)를 같은 노드로: 물리 한 주기 비용은 6 자유도의 몇 배인가
> 한 줄 요약: 제어 코드·백엔드는 그대로 두고 로봇 프로필만 `robots/allex.yaml` 로 바꿔 **48 자유도 상체 휴머노이드**를 돌린다. **결과(11/06)**: 물리 한 주기가 WSL 1 kHz 에서 p50 336 / p99 622 / max 1,785 us — 같은 PC 의 6 자유도(4.9 / 6.3 / 20.8)의 **약 70~100배**. 러너 1 kHz 는 382 / 458 / 609(전부 1 ms 안). p99 가 예산의 46~62 % 라 제어·통신·기록에 남는 몫이 작고 모델의 기본 걸음이 2 ms 이므로 ALLEX 프로필은 **500 Hz 기본**(DECISIONS 11/06). 500 Hz 실측(WSL)은 327 / **1,000** / 1,589 us — p99 가 2 ms 의 50 % 로, "비용은 같고 예산만 2배"라는 어림(31 %)보다 나빴다(4절). 바뀐 제어 코드: 없음.

이전: [E16](E16.md) (물리가 보여 준 새 사실) · 다음: 없음

## 1. 왜 했나 (이유)
- 지원하는 회사가 2026-06-29 에 ALLEX 시뮬레이션 모델을 공개했다(MJCF · USD · URDF, BSD-3). 공고 ④(시뮬레이션)에 "회사의 로봇으로" 답할 수 있는 기회다.
- 이 저장소의 주장 — "로봇을 바꾸는 일은 설정 파일을 바꾸는 일이다"(백엔드 인터페이스 + 이름으로 관절 잇기) — 를 6 자유도 팔이 아닌 **48 자유도 휴머노이드**로 검증한다. 바뀌는 파일이 프로필 하나(+ 모델 받는 스크립트)뿐인지가 첫 번째 확인 항목이다.
- 물리 비용은 자유도와 접촉 수에 따라 커진다. E15 의 0.9 %(6 자유도)가 48 자유도에서 몇 % 가 되는지가 두 번째 확인 항목이다. 1 ms 예산표(설계서 3.7절)의 "제어 + 물리" 줄이 이 값으로 바뀐다.
- 합격선: E15 와 같다. 한 주기(물리 한 걸음 + 상태 읽기) **p99 < 주기의 90 %**(1 kHz 면 900 us). 더 엄격한 목표는 예산의 10 % 아래.

## 2. 어떻게 하나
| 항목 | 값 |
|---|---|
| 모델 | `wirobotics-rih/allex_model` 커밋 5e12052(v0.2.0), `mjcf/scene.xml`. 관절 60(수동 12 포함, 백엔드 출력 `nq=60`), **position 액추에이터 48**(`nu=48`), timestep 2 ms |
| 프로필 | `robots/allex.yaml` — dof 48, `mujoco.joints` 48개(MJCF 액추에이터 순서). 수동 관절(손가락 DIP·IP, 허리 링크)은 등식 제약으로 따라 움직이므로 명령 대상이 아니다 |
| 걸음 맞추기 | 모델 timestep 2 ms. **500 Hz 면 `mj_step` 1번 = 모델 기본 걸음 그대로.** 1차 측정은 1 kHz 로 했고 이때는 올림 규칙으로 걸음을 1 ms 로 줄여 1번. 두 경우 모두 한 주기에 `mj_step` 1번이라 **물리 비용은 거의 같고, 달라지는 것은 예산(1 ms ↔ 2 ms)** 이다 |
| 바뀐 코드 | `test_mujoco_backend.cpp` 가 관절 수·이름·출력 파일·주기를 환경변수로 받게 한 것뿐(`RT_MUJOCO_DOF` · `RT_MUJOCO_JOINTS` · `RT_MUJOCO_OUT` · `RT_MUJOCO_PERIOD_US`). `control_step.cpp` · `mujoco_backend.cpp` · 노드는 그대로 — `git show --stat f1e89cb` 로 확인(4절) |
| 테스트 | 관절 0(R_Shoulder_Pitch) 에 +0.3 rad, 나머지 47 관절은 현재 위치 유지, 2초 분량(1 kHz 는 2,000주기, 500 Hz 는 1,000주기), 한 주기 비용 p50/p99/max |
| 환경 | ① WSL 단독 테스트(1 kHz → 500 Hz) ② GitHub 러너 — CI `mujoco` 잡의 ALLEX 단계는 **프로필과 같은 500 Hz 게이트**(아티팩트 `mujoco-ci`/`mujoco_backend_allex_ci.json`). 1 kHz 러너 값은 patch-23 시점의 run 42172730308 한 번(그때는 단계가 1 kHz 였다) ③ WSL ROS 2 노드 안 `work_us`(500 Hz) |

CI 를 1 kHz 가 아니라 500 Hz 로 두는 이유: CI 는 "운영점에서 통과하는가"를 묻는 게이트이고, 1 kHz 는 "어디까지 되는가"를 묻는 측정이다. 측정을 게이트에 넣으면 러너 상태에 따라 빨갛게 되는 날이 생긴다.

```bash
# [WSL 창] 모델 받기 (약 250 MB, 한 번) → 테스트 빌드는 E15 와 같은 build/rt_core_mj
bash scripts/get_allex.sh
cmake --build build/rt_core_mj -j

# 1차(11/06 에 실행한 것): 1 kHz
RT_MUJOCO_MODEL=$PWD/third_party/allex_model/mjcf/scene.xml RT_MUJOCO_DOF=48 \
RT_MUJOCO_JOINTS="$(python3 scripts/profile_joints.py robots/allex.yaml)" RT_MUJOCO_OUT=mujoco_backend_allex_wsl_1khz.json \
LD_LIBRARY_PATH=$PWD/third_party/mujoco/lib ./build/rt_core_mj/test_mujoco_backend

# 2차: 프로필과 같은 500 Hz (주기 2000 us)
RT_MUJOCO_MODEL=$PWD/third_party/allex_model/mjcf/scene.xml RT_MUJOCO_DOF=48 RT_MUJOCO_PERIOD_US=2000 \
RT_MUJOCO_JOINTS="$(python3 scripts/profile_joints.py robots/allex.yaml)" RT_MUJOCO_OUT=mujoco_backend_allex_wsl_500hz.json \
LD_LIBRARY_PATH=$PWD/third_party/mujoco/lib ./build/rt_core_mj/test_mujoco_backend
```
노드 안에서(③): `backends/mujoco/README.md` §6.

## 4. 처음 읽는 사람을 위한 분석
- **바뀐 파일이 첫 결과다.** `git show --stat f1e89cb`(ALLEX 커밋): 13개 파일 — 프로필 `robots/allex.yaml`, 받는 스크립트 `get_allex.sh`, 이름 뽑는 `profile_joints.py`, 생성된 `allex_mujoco.params.yaml`, 테스트의 환경변수 처리, CI 단계, 문서 7개. `control_step.cpp` · `mujoco_backend.cpp` · `rt_control_node.cpp` 는 없다. "로봇을 바꾸는 일은 설정 파일을 바꾸는 일"이라는 주장은 48 자유도에서도 성립한다.
- **비용은 약 70~100배**(p50 ×69, p99 ×99, max ×86 — 같은 PC 의 6 자유도 대비). 자유도는 8배인데 비용이 그보다 훨씬 큰 이유는 손가락 30개 관절의 접촉과 등식 제약 12개로 제약 풀이(solver) 일이 커지기 때문으로 **본다(추정)**. 확인하려면 손을 뺀 모델로 한 번 더 재면 되는데, 회사 모델을 그대로 돌린다는 요점과 어긋나 하지 않았다.
- **1 kHz 는 "통과했지만 여유가 없다".** WSL 에서 p99 622 us 는 합격선 안이지만 max 1,785 us > 1,000 us — 2,000주기 중 적어도 한 번은 한 주기가 주기를 넘었고, 노드라면 마감 놓침(drop)이다. 러너에서는 max 609 로 1 ms 안이었다 — **max 초과는 WSL(RT 아님)의 꼬리**다. 환경을 떠나 남는 사실은 p99 가 예산의 46~62 % 라는 것: 제어·통신·기록에 남는 것이 380~540 us 이고, 설계서 1 ms 예산표의 "제어 + 물리 ≈ 9 us" 는 ALLEX 에선 성립하지 않는다.
- **그래서 500 Hz.** 모델 작성자가 2 ms 걸음으로 조정해 공개한 모델이라 2 ms 제어 주기가 모델의 운영점이기도 하다. 바꾸는 데 코드는 없었다(프로필의 숫자 하나). 1 kHz 가 정말 필요해지면 물리를 별도 스레드로(비동기) 두거나 손가락을 간소화한 모델을 쓰는 길이 있는데 둘 다 지금은 안 한다(이유는 DECISIONS 11/06).
- **어림이 틀렸다 — 500 Hz 실측 p99 는 31 % 가 아니라 50 %.** "500 Hz 로 바꿔도 한 주기에 `mj_step` 1번이니 물리 비용은 같고 예산만 2배" 라고 적었는데, 2차 실측은 p50 327(같음) / **p99 1,000**(1 kHz 의 622 보다 큼) / max 1,589. p50 은 같고 꼬리만 나빠졌다. 후보는 둘: (1) 걸음이 1 → 2 ms 로 커지면 접촉·등식 제약 풀이의 반복 수가 늘어 "한 걸음의 일"이 같지 않다 — 어림의 전제가 틀렸을 수 있다. (2) 1,000주기의 p99 는 큰 쪽 10번째 값이라 WSL 의 스케줄링 꼬리에 2,000주기보다 민감하다. 한 번씩 잰 값으로는 못 가른다 — 같은 조건을 세 번씩, 그리고 10초(5,000주기)로 재는 것이 다음이다. **결정(500 Hz)은 유지한다**: 2 ms 예산에서 p99 50 % / max 79 % 는 1 kHz 의 62 % / 178 %(WSL) 보다 낫고, 모델 기본 걸음과 같다. 다만 "p99 31 %" 라고 적은 곳(DECISIONS 11/06, 설계서)은 실측으로 고쳤다.
- **관절 0 은 명령에 반응했다.** 0.298 / 0.300 rad — 오차 0.002 rad(0.1°). SO-101 어깨의 중력 처짐 1.1°(E16)의 10분의 1 인데, ALLEX 어깨 액추에이터가 kp 5000 의 강한 서보여서로 **본다(추정)** — 자세와 중력 방향이 달라 직접 비교는 아니다.
- 한계: 조건마다 1회(WSL 1 kHz 2,000주기 · WSL 500 Hz 1,000주기 · 러너 1 kHz 2,000주기). 중력 보상·관절별 변화량 제한은 없다(E16 과 같은 처짐이 48 관절에서 어떻게 나오는지는 기록 파이프라인(E20)으로 따로 본다).
