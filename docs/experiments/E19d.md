# E19-d — 두 도구가 왜 2.3배 다른가: cyclictest 132 vs jitter_bench 301 (가설 검증)
> 한 줄 요약: 같은 부하·같은 RT 커널에서 표준 도구 cyclictest 는 max 132 us, 우리 측정기 jitter_bench 는 301 us. 가설 "jitter_bench 는 매 주기 50 us 를 **실제로 일하는** 동안 간섭에 노출된다" 를 `--work-us 0`(일 없이 깨기만) 으로 검증한다 → **결과: 측정 대기 (2026-11-05)**.

## 1. 왜 했나 (이유)
- [E19-a](E19a.md) 의 두 번째 마름모: **"표준 도구와 내 측정기가 같은 급인가? (±30%)"** → **아니오: cyclictest 132 vs jitter_bench 301**. 방향(RT 가 max 를 자른다)은 같지만 크기가 2.3배 다르다.
- 왜 중요한가: 표①의 jitter_bench 줄은 **내가 만든 자**로 잰 값이다. 표준 자와 2배 넘게 다르면 "측정기가 틀린 것 아닙니까?" 라는 반박을 못 막는다(`docs/DECISIONS.md` 2026-11-05 "반박 하나당 줄 하나"). 차이가 **측정기의 버그**인지 **재는 대상이 다른 것**인지 가려야 한다.
- 합격선: `--work-us 0` 으로 돌린 jitter_bench 의 max 가 cyclictest 의 132 와 같은 급(±30%, 즉 약 90~170 us)으로 내려오면 가설 확정. 300 근처에 머물면 가설 기각 → 측정기 코드를 들여다본다.

## 2. 어떻게 했나
| 항목 | 값 |
|---|---|
| 어디서 | Pi 4B, `6.8.0-2054-raspi-realtime`, isolcpus=3 적용 상태 |
| 비교 기준 | [E19-b](E19b.md) 고정 조건(격리 안 된 CPU, 50 us 일함) max 311.5 |
| 바꾼 것 | `--work-us 0`(매 주기 깨기만 하고 일하지 않음, cyclictest 와 같은 방식), 격리 안 된 CPU 2 에 고정, 같은 stress-ng 부하 |
| 그대로인 것 | 우선순위 80, 60초, 주기 1,000 us. 식힌 뒤 시작, 끝나면 온도·스로틀 확인 |

(`jitter_run.sh` 에는 아직 `--work-us` 인자가 없어 측정기를 직접 부른다):
```bash
while [ $(cat /sys/class/thermal/thermal_zone0/temp) -gt 52000 ]; do sleep 5; done
stress-ng --cpu 4 --io 2 --vm 1 --vm-bytes 256M --timeout 75s >/dev/null 2>&1 &
sleep 3; sudo ./build/rt_core/jitter_bench --prio 80 --cpu 2 --seconds 60 --work-us 0 --label pi4_rt_stress_pin_work0 --json docs/measurements/jitter_pi4_rt_stress_pin_work0.json; wait
cat /sys/class/thermal/thermal_zone0/temp; cat /sys/devices/platform/soc/soc:firmware/get_throttled
```

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **cyclictest 의 측정 방식**: "1 ms 뒤에 깨워 달라" → 깨면 시각만 적고 **곧바로 다시 잠든다**. CPU 를 쓰는 시간이 거의 0 이다.
- **jitter_bench 의 측정 방식**: 깨면 시각을 적고 **50 us 동안 바쁘게 돈다**(진짜 제어 루프처럼 일한다) → 다시 잠든다. `--work-us 0` 으로 하면 cyclictest 와 같은 "깨기만" 이 된다.
- **노출(exposure)**: 스레드가 CPU 를 쓰는 동안 하드 인터럽트·IPI(다른 CPU 가 보내는 신호)에 맞을 수 있는 시간. 잠들어 있으면 맞을 일이 없고, 일하고 있으면 그 시간만큼 맞는다. 깨어남 지연 자체는 깨는 순간만 재지만, 일하다 맞은 간섭이 **다음 주기의 깨어남 시각을 밀 수 있다**(캐시가 식고, 늦게 잠들고).
- **캐시 밀려남**: stress-ng 가 메모리를 마구 쓰면 우리 스레드가 쓰던 데이터가 CPU 옆 캐시에서 쫓겨나고, 다음에 깼을 때 메인 메모리까지 다녀와야 한다(수 us ~ 수십 us).
- **가설 검증**: 원인이라고 생각하는 변수 **하나만** 바꿔 결과가 예측대로 움직이는지 본다. 여기서 바꾸는 변수는 "일하는 시간 50 → 0".
- 단위: us = 100만분의 1초.

### 4-2. 쉬운 예제
- 비유: 두 직원이 같은 가게에서 "호출벨이 울리면 얼마나 늦게 반응하나"를 쟀다. A(cyclictest)는 벨이 울리면 손만 들고 다시 앉는다. B(jitter_bench)는 벨이 울리면 50초 동안 상자를 나른다. 매장 방송·배달 수령(인터럽트)은 둘 다 맞지만 B 는 일하는 중에 맞아 다음 벨에 늦기 쉽다. B 에게 "상자는 나르지 말고 손만 들어" 하면(`--work-us 0`) A 와 같아져야 한다 — 같아지면 "자가 틀린 게 아니라 하는 일이 달랐다".
- 계산: 가설이 맞으면 결과 max 는 132 ± 30% = **92~172 us** 사이. 311 근처(±30% = 218~405)면 가설 기각. 그 사이(170~220)면 "일부만 설명" — 그때는 두 도구의 차이점을 하나 더 지운다(우선순위 80 → 90, `--vm-bytes` 256M → 512M).

### 4-3. 숫자가 말하는 것
- 결과가 들어오면 마름모 **"work 0 이면 ~130 으로 내려오나?"** 에 답한다:
  - **예(92~172)** → 확인: 차이는 "50 us 일하는 동안의 노출"이다. 표①의 jitter_bench 줄은 **"진짜로 일하는 제어 루프가 겪는 지연"**, cyclictest 줄은 **"커널이 제공하는 깨어남 바닥"** 으로 뜻이 다르다고 적는다. 둘 다 표에 남기고 비고에 그 뜻을 쓴다. 로봇에 가까운 숫자는 jitter_bench 쪽이다.
  - **아니오(≈311)** → 가설 기각: 일하는 시간과 무관하게 측정기가 cyclictest 보다 2배 나쁘게 잰다. 측정기 코드(`rt_loop.cpp` 의 타이머·시각 읽기, 기록 벨트, 우선순위 80 vs 90)를 하나씩 cyclictest 와 맞춰 가며 다시 잰다. 그때까지 표①의 jitter_bench 줄에는 "표준 도구와 2.3배 차이, 원인 조사 중" 을 붙인다.
- 어느 쪽이든 **E19-c 의 결론(격리로 189, 표① 통과)은 바뀌지 않는다** — 같은 측정기로 같은 조건을 비교한 상대값이기 때문. 바뀌는 것은 "절대값을 어느 도구 기준으로 말하느냐"다.
- 지금까지 확인된 것: cyclictest 와 jitter_bench 는 일반 → RT 에서 같은 방향으로 움직였다(695 → 132, 781 → 301). 한가 상태에서는 두 도구가 같은 급(cyclictest 37 vs jitter 27.8). 차이는 **부하 중에만** 벌어진다 — 이것 자체가 "노출" 가설을 지지하는 정황(추정).

## 5. 면접 한 문장
- "표준 도구와 내 측정기가 부하 중 2.3배 달라서 그냥 두지 않고 `--work-us 0` 으로 변수 하나만 바꿔 검증했다 — 측정기를 믿는 것이 아니라 측정기의 다른 점을 지워 가며 확인하는 것이 측정의 일이다." (결과에 따라 뒷문장 추가)
