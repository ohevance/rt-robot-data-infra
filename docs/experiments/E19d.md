# E19-d — 두 도구가 왜 2.3배 다른가: cyclictest 132 vs jitter_bench 301 (가설 검증 → 측정기는 맞다, 차이는 설정과 부하 정의)
> 한 줄 요약: 같은 부하·같은 RT 커널에서 표준 도구 cyclictest 는 max 132 us, 우리 측정기 jitter_bench 는 301 us. 가설 "50 us 일하는 동안의 노출"은 **기각**(일을 없애도 270). 대신 **같은 설정으로 맞춘 cyclictest 가 274** 를 내서 측정기는 맞다는 것이 확인됐고, 차이는 **① CPU 마다 스레드를 두는 배치(약 60 us) ② 부하 정의 — 메모리 버퍼 512M vs 256M 과 격리 전·후의 CPU 당 부하(약 80 us, 추정)** 로 나뉘었다.

## 1. 왜 했나 (이유)
- [E19-a](E19a.md) 의 두 번째 마름모: **"표준 도구와 내 측정기가 같은 급인가? (±30%)"** → **아니오: cyclictest 132 vs jitter_bench 301**. 방향(RT 가 max 를 자른다)은 같지만 크기가 2.3배 다르다.
- 왜 중요한가: 표①의 jitter_bench 줄은 **내가 만든 자**로 잰 값이다. 표준 자와 2배 넘게 다르면 "측정기가 틀린 것 아닙니까?" 라는 반박을 못 막는다(`docs/DECISIONS.md` 2026-11-05 "반박 하나당 줄 하나"). 차이가 **측정기의 버그**인지 **재는 대상·조건이 다른 것**인지 가려야 한다.
- 합격선: 변수를 하나씩 지워 가며 두 도구의 max 가 ±30% 안에 들어오는 지점을 찾는다. 끝까지 안 맞으면 측정기 코드를 들여다본다.

## 2. 어떻게 했나
한 번에 변수 하나. 전부 Pi 4B, `6.8.0-2054-raspi-realtime`, **isolcpus=3 적용 상태**(CPU 3 은 비워 두고 격리 안 된 CPU 2 를 쓴다), 부하는 stress-ng `--cpu 4 --io 2 --vm 1 --vm-bytes 256M`, 60초, 식힌 뒤 시작, 끝나면 온도·스로틀 확인.

| 단계 | 바꾼 변수 하나 | 명령(요지) | 답하는 질문 |
|---|---|---|---|
| A-1 | jitter_bench 의 일 50 → **0 us** (cyclictest 처럼 깨기만) | `jitter_bench --prio 80 --cpu 2 --work-us 0` | 일하는 동안의 노출이 차이의 원인인가? |
| A-2 | cyclictest 를 **jitter_bench 와 같은 설정**으로: 스레드 1개, CPU 2 고정, 우선순위 80 | `cyclictest -m -p 80 -a 2 -t 1 -i 1000 -h 1000 -q -D 60` | 설정이 같으면 두 도구가 같은 값을 내나? (측정기 검증) |
| B | jitter_bench 우선순위 80 → **90** (cyclictest_run 과 같게) | `jitter_bench --prio 90 --cpu 2 --work-us 0` | 80 과 90 사이에 끼어드는 커널 스레드가 있나? |
| C | cyclictest 를 **CPU 마다 스레드**(`-S`)로, 단 부하는 jitter 와 같은 256M | `cyclictest -m -S -p 80 -i 1000 -h 1000 -q -D 60` | 스레드 배치가 원인인가, 부하 정의(512M vs 256M)가 원인인가? |

```bash
# 각 줄 앞에: while [ $(cat /sys/class/thermal/thermal_zone0/temp) -gt 52000 ]; do sleep 5; done
# 부하:      stress-ng --cpu 4 --io 2 --vm 1 --vm-bytes 256M --timeout 75s >/dev/null 2>&1 &  ;  sleep 3
sudo ./build/rt_core/jitter_bench --prio 80 --cpu 2 --seconds 60 --work-us 0 --label pi4_rt_stress_pin_work0     --json docs/measurements/jitter_pi4_rt_stress_pin_work0.json
sudo cyclictest -m -p 80 -a 2 -t 1 -i 1000 -h 1000 -q -D 60 > docs/measurements/cyclictest_pi4_rt_stress_cpu2_p80.txt
sudo ./build/rt_core/jitter_bench --prio 90 --cpu 2 --seconds 60 --work-us 0 --label pi4_rt_stress_pin_work0_p90 --json docs/measurements/jitter_pi4_rt_stress_pin_work0_p90.json
sudo cyclictest -m -S -p 80 -i 1000 -h 1000 -q -D 60 > docs/measurements/cyclictest_pi4_rt_stress_S_p80_vm256.txt
```
(이 네 번은 손으로 돌렸고 `.meta` 를 손으로 적었다. 이후부터는 `jitter_run.sh` 가 `JITTER_WORK_US`·`JITTER_PRIO`·`STRESS_VM_BYTES` 환경 변수를 받고, 부하 정의는 `scripts/lib_stress.sh` 한 곳에서 나온다.)

## 4. 결과 분석 — 처음 읽는 사람을 위한 설명
### 4-1. 용어와 단위
- **cyclictest 의 측정 방식**: "1 ms 뒤에 깨워 달라" → 깨면 시각만 적고 **곧바로 다시 잠든다**. `-S` 는 CPU 마다 스레드 하나씩, `-t 1 -a 2` 는 스레드 하나를 CPU 2 에.
- **jitter_bench 의 측정 방식**: 깨면 시각을 적고 **50 us 동안 바쁘게 돈다**(진짜 제어 루프처럼) → 다시 잠든다. `--work-us 0` 이면 cyclictest 와 같은 "깨기만".
- **노출(exposure)**: 스레드가 CPU 를 쓰는 동안 하드 인터럽트·IPI 에 맞을 수 있는 시간. 가설은 "일하는 50 us 가 노출을 만들어 max 를 키운다"였다.
- **IPI(Inter-Processor Interrupt)**: 한 CPU 가 다른 CPU 들에게 보내는 "지금 당장 이것 해라" 신호. 메모리 매핑을 지울 때(munmap) 다른 CPU 의 주소 변환 캐시(TLB)를 비우라고 전부에게 보낸다. **우선순위도 isolcpus 도 막지 못한다.**
- **`--vm-bytes`**: stress-ng 메모리 작업자가 한 번에 잡는 버퍼 크기. 작을수록 mmap → 채움 → munmap 주기가 짧아 **munmap(= IPI)이 잦다**(추정).
- 단위: us = 100만분의 1초. ±30% = "같은 급"의 합격선.

### 4-2. 쉬운 예제
- 비유: 두 직원 A(cyclictest)·B(jitter_bench)가 "호출벨에 얼마나 늦게 반응하나"를 쟀더니 B 가 2배 늦었다. B 에게 "상자 나르지 말고 손만 들어"(일 0) 해도 여전히 늦었다 → B 가 느린 게 아니라 **B 가 서 있던 자리와 그날 매장 상태가 달랐던 것**. A 를 B 와 같은 자리에 세우자(A-2) 둘이 똑같이 늦었다(274 vs 270).
- 계산: 차이 301 − 132 = 169 us 를 분해하면, 스레드 배치(C: 274 → 210) ≈ 60 us, 나머지 부하 정의·격리 전후(210 → 132) ≈ 80 us, 일 50 us 의 몫(311 → 270) ≈ 40 us 는 p99 쪽에 더 크게 나타났다(169 → 116).

### 4-3. 숫자가 말하는 것
- 마름모 "work 0 이면 ~130 으로 내려오나?" → **아니오(270)**. 확인: 일하는 50 us 는 **p99(보통 나쁜 경우)** 를 169 → 116 으로 낮추지만 **max** 는 거의 그대로다. 가설은 max 에 대해 기각.
- **확인(가장 중요): 측정기는 맞다.** 같은 설정(1 스레드·CPU 2·prio 80·일 0·256M)의 cyclictest 274 vs jitter_bench 270 — 1.5% 차이. "내가 만든 자가 틀렸다"는 반박은 닫힌다.
- 확인: 우선순위 80 vs 90 은 무관(270 vs 290, 잡음 범위). 80 과 90 사이에 끼어드는 커널 스레드는 없다.
- 확인: **CPU 마다 RT 스레드를 두면 max 가 274 → 210 으로 준다**(C). 추정: 모든 CPU 에서 1 ms 마다 stress 작업자가 선점되므로 메모리 작업자의 munmap 폭풍이 잦아들어 IPI 가 줄거나, 각 CPU 가 깊은 유휴 상태로 못 들어가 깨어남이 고르다. 어느 쪽인지는 안 갈랐다.
- 추정: 남은 210 → 132 는 **부하 정의**다 — E19-a 의 cyclictest 는 `--vm-bytes 512M`(버퍼가 커서 munmap 이 드물다 → IPI 적음)이고 **격리 전**이라 stress 4개가 CPU 4개에 퍼져 CPU 당 부하가 낮았다. 두 요인을 따로 가르려면 한 번 더(512M 로 C 반복) 재면 되지만 여기서 멈춘다 — 표①의 결론(E19-c 격리로 189, 통과)에 영향이 없고, 배운 것은 이미 충분하다.
- **내 실수 하나가 드러났다**: 두 측정 스크립트의 부하가 달랐다(cyclictest_run 512M, jitter_run 256M). 도구를 비교하려면 부하까지 같은 함수에서 나와야 한다 → `scripts/lib_stress.sh` 로 묶고 `.meta` 에 `stress_vm_bytes` 를 남기게 고쳤다(`docs/DECISIONS.md` 11/05).
- 표① 읽는 법이 정해진다: **cyclictest 줄은 "커널이 주는 깨어남 바닥"(4 CPU 에 스레드, 큰 버퍼 부하), jitter_bench 줄은 "일하는 스레드 하나가 겪는 지연"(작은 버퍼 부하)**. 로봇 제어 루프에 가까운 것은 후자이고, 둘의 상대 변화(일반 → RT → 격리)는 같은 방향이다.

## 5. 면접 한 문장
- "표준 도구와 내 측정기가 부하 중 2.3배 달라서 변수를 하나씩 지워 갔다 — 일(50→0)도, 우선순위(80→90)도 아니었고, 같은 설정으로 맞추자 274 대 270 으로 일치했다. 차이는 스레드 배치와 부하 정의였고, 그 과정에서 내 스크립트 둘의 부하가 달랐던 실수를 찾아 한 함수로 묶었다."
