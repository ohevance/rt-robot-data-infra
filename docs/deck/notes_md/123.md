# 장표 123 — Jenkins 에 익숙한 사람을 위한 대응표
*위치: 6부 믿을 수 있나 · CI — Jenkins 대응표*

## 1. 이 장표가 왜 있나
바로 앞 장표(107)까지 "CI 가 매 push 마다 3개 잡을 돌리고, 결과가 빨간색이면 무엇부터 보나"를 설명했다. 그런데 회사에서 오래 일한 사람 대부분은 CI 를 Jenkins 로 배웠다. Jenkins 와 GitHub Actions 는 하는 일이 같은데 **부르는 이름이 한 칸씩 어긋나 있어서**, 같은 단어("job")가 서로 다른 것을 가리킨다. 이 장표는 그 어긋남을 표 한 장으로 맞춘다. 실제로 이 저장소를 만드는 중에 작성자 스스로 "Jenkins job 하고 GitHub 의 job 이 헷갈린다"고 했고, 그 설명을 `docs/ENVIRONMENT.md §5-6` 에 옮겨 둔 것이 이 표의 원본이다. 이 장표가 끝나면 6부(숫자를 어떻게 믿나)가 끝나고, "그러면 왜 이렇게 만들었고 무엇이 깨졌나"(7부)로 넘어간다.

## 2. 장표를 하나씩 읽기
표는 세 열이다. 왼쪽 **Jenkins** 열은 Jenkins 에서 부르는 이름, 가운데 **GitHub Actions** 열은 같은 것을 GitHub 가 부르는 이름, 오른쪽 **이 저장소** 열은 그것이 우리 저장소에서 구체적으로 무엇인지다.

- **Jenkins 서버(직접 운영) ↔ GitHub 가 운영 ↔ —**: Jenkins 는 회사가 서버를 사서 설치하고 관리한다. GitHub Actions 는 GitHub 가 자기 데이터센터에서 운영하므로 우리가 관리할 서버가 없다. 그래서 세 번째 칸이 비어 있다("—"). 공개 저장소는 무료다.
- **빌드 노드 / agent ↔ runner ↔ runs-on: ubuntu-24.04 (매번 새 VM)**: 실제로 명령을 실행하는 컴퓨터. Jenkins 에서는 "노드" 또는 "에이전트", GitHub 에서는 "러너". 우리 설정 파일에는 `runs-on: ubuntu-24.04` 라고 적혀 있고, 이것은 "우분투 24.04 가상 머신을 새로 하나 켜서 거기서 돌려라"는 뜻이다. 매번 새 VM 이라 지난번에 깐 프로그램이 남아 있지 않다(그래서 매번 apt 부터 다시 깐다 — 장표 119).
- **Job(파이프라인 하나) / Jenkinsfile ↔ workflow (yml 파일 하나) ↔ .github/workflows/ci.yml**: Jenkins 에서 "job" 은 파이프라인 전체(하나의 빌드 작업)를 뜻하고 그 내용을 Jenkinsfile 에 적는다. GitHub 에서는 그 전체를 **workflow** 라 부르고 yml 파일 하나에 적는다. 우리 저장소의 그 파일이 `.github/workflows/ci.yml` 이다(파일 안 이름은 `name: ci`).
- **트리거(polling·webhook·수동) ↔ on: ↔ push · pull_request · workflow_dispatch**: 언제 돌릴지. Jenkins 는 주기적으로 저장소를 들여다보거나(polling) 알림을 받거나(webhook) 사람이 버튼을 누른다. GitHub 는 yml 의 `on:` 아래에 적는다. 우리는 셋을 다 켜 두었다: `push`(코드를 올릴 때마다), `pull_request`(PR 을 열 때), `workflow_dispatch`(Actions 탭의 "Run workflow" 버튼).
- **stage ↔ job (각자 다른 runner) ↔ rt_core · fleet_integration · mujoco**: 여기가 가장 헷갈리는 줄이다. Jenkins 의 "stage" 는 파이프라인 안의 한 단계(빌드 → 테스트 → 배포)이고, GitHub 에서는 그 단계 하나하나를 **job** 이라 부른다. 그리고 GitHub 의 job 은 각각 **다른 러너(다른 VM)** 에서 돈다. 우리 workflow 의 job 은 셋: `rt_core`(C++ 빌드·단위 테스트·파이썬 단위 테스트), `fleet_integration`(진짜 브로커·DB 컨테이너로 장애 주입), `mujoco`(물리 엔진 테스트).
- **sh 한 줄 / 플러그인 ↔ step (run:) / action (uses:) ↔ 'Configure & build' … / checkout@v5, upload-artifact@v5**: job 안의 명령 한 줄 한 줄. Jenkins 에서 `sh 'make'` 처럼 쓰던 것이 GitHub 에서는 `run:` 으로 시작하는 **step** 이고, Jenkins 플러그인에 해당하는 것이 `uses:` 로 가져다 쓰는 **action** 이다. 우리 yml 에는 `Configure & build`, `Unit tests …` 같은 step 들과, 저장소를 받아 오는 `actions/checkout@v5`, 결과 파일을 보관하는 `actions/upload-artifact@v5` 두 action 이 있다. `@v5` 는 그 action 의 버전이다(11/04 에 v4 → v5 로 올렸다).
- **upstream/downstream ↔ needs: ↔ 2단계 둘이 needs: rt_core → 병렬**: 잡 사이의 순서. Jenkins 는 "이 job 이 끝나면 저 job" 을 upstream/downstream 으로 엮고, GitHub 는 job 에 `needs:` 를 적는다. 우리 yml 에서 `fleet_integration` 과 `mujoco` 둘 다 `needs: rt_core` 라서, 1단계 `rt_core` 가 통과해야만 둘이 **동시에(병렬로)** 시작한다. 1단계가 실패하면 2단계는 돌지 않는다 — 싼 검사부터.
- **Build #123 / 콘솔 출력 ↔ run (ID) / job 로그 ↔ gh run list · gh run view <ID> --log-failed**: 한 번 돌린 결과. Jenkins 의 "Build #123" 이 GitHub 의 **run**(긴 숫자 ID)이고, 콘솔 출력이 job 로그다. 터미널에서는 `gh run list` 로 최근 run 들의 ✓/✗ 를 보고, `gh run view <ID> --log-failed` 로 실패한 step 의 로그만 본다(장표 122 의 첫 명령).
- **JUnit 리포트 화면 ↔ (없음 — 로그의 OK/FAIL) ↔ 필요하면 JUnit XML + 리포터 액션**: Jenkins 는 테스트 케이스별 통과/실패 표를 그려 준다. 우리 workflow 에는 그 화면이 없고, 로그에 찍히는 `OK: …` / `100% tests passed` 로 본다. 필요하면 ctest 와 파이썬 테스트가 JUnit XML 을 내게 하고 리포터 액션을 붙이면 되는데(약 30분 일), 우선순위가 낮아 안 했다.
- **아래 비고**: "Jenkins 의 'job' = GitHub 의 'workflow', GitHub 의 'job' = Jenkins 의 'stage' — 이름이 한 칸씩 어긋난다." 이 한 줄이 표 전체의 요약이다.
- **다음 ▶**: "7부 — 코드·숫자·검증이 한 벌이 됐다. 왜 이렇게 만들었고(버린 대안), 무엇이 깨졌고, 어떻게 일했나?" 6부가 끝났다는 신호다.

## 3. 용어와 단위
- **CI(Continuous Integration, 지속적 통합)**: 코드를 올릴 때마다 자동으로 빌드하고 테스트하는 것. "내 컴퓨터에서는 됐는데"를 막는 장치.
- **Jenkins**: 오래된 오픈소스 CI 서버. 회사가 직접 설치해 쓴다.
- **GitHub Actions**: GitHub 에 붙어 있는 CI 서비스. 설정은 저장소 안 `.github/workflows/*.yml`.
- **runner(러너)**: 실제로 명령을 실행하는 컴퓨터(가상 머신). 우리는 GitHub 가 제공하는 `ubuntu-24.04`.
- **workflow / job / step / action**: 전체 → 단계 → 명령 → 남이 만든 명령 묶음. 포함 관계로 외우면 된다.
- **needs:**: "이 job 은 저 job 이 끝난 뒤에" 라는 순서 지정.
- **run**: workflow 가 한 번 실행된 것. 번호(ID)가 붙는다. 한 번의 push = run 하나 = job 3개.
- **artifact(아티팩트)**: job 이 끝난 뒤 보관해 두는 결과 파일(예: `jitter_ci.json`, `table1_ci.md`).
- **JUnit XML**: 테스트 결과를 적는 표준 파일 형식. 리포터가 이것을 읽어 표를 그린다.
- **gh**: GitHub 를 터미널에서 다루는 명령줄 도구(GitHub CLI).

## 4. 쉬운 예시
- 비유: Jenkins 는 **내 집 주방**이다 — 가스레인지도 내가 사고 고장도 내가 고친다. GitHub Actions 는 **공유 주방**이다 — 예약(push)하면 깨끗이 비워진 주방(새 VM)을 내주고, 요리가 끝나면 치운다. 레시피(ci.yml)는 내가 들고 간다. "stage" 와 "job" 의 어긋남은, 어떤 식당에서는 "코스" 를 job 이라 부르고 다른 식당에서는 "코스 안의 한 접시" 를 job 이라 부르는 것과 같다.
- 숫자 예시: 작성자가 `git push` 를 한 번 하면 run 이 하나 생기고, 그 안에서 job 3개가 돈다. `rt_core` 약 1분 10초 → 통과하면 `fleet_integration` 약 2분과 `mujoco` 약 30초가 동시에 → 전부 합쳐 약 2분 20초 뒤 README 배지가 초록이 된다(11/04 실측: rt_core 1m13s · mujoco 25s · fleet_integration 1m52s).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 표의 내용 — `docs/ENVIRONMENT.md` §5-6 "Jenkins 에 익숙한 사람을 위한 대응표".
- 확인: 트리거 셋, job 이름 셋, `needs: rt_core`, `checkout@v5`, `upload-artifact@v5` — `.github/workflows/ci.yml` (`grep -n "on:\|needs:\|uses:" .github/workflows/ci.yml`).
- 확인: job 별 실행 시간 — `docs/LOG.md` 2026-11-04 "CI 2차 — 3잡 전부 통과".
- 다시 보는 법: 저장소 디렉터리에서 `gh run list -L 3` (최근 run 3개), `gh run view <ID>` (job 별 결과), `gh run view <ID> --log-failed | tail -40` (실패 로그만).

## 6. 자주 하는 오해·함정
- "GitHub 의 job 하나 = Jenkins 의 job 하나"로 읽으면 틀린다. GitHub 의 job 은 Jenkins 의 stage 에 가깝고, 게다가 각 job 은 **다른 VM** 에서 돈다(Jenkins 의 stage 는 보통 같은 노드에서 이어진다). 그래서 job 끼리 파일을 그냥 주고받을 수 없고 artifact 로 넘겨야 한다.
- 러너는 작성자의 노트북이 아니다. 노트북을 꺼도 CI 는 돈다. 반대로 노트북(WSL)에서 되는 것이 러너에서 안 될 수 있다 — 11/04 CI 1차 실패(TimescaleDB 초기화 경쟁)가 그 예다(장표 128).
- "테스트 케이스 등록" 화면을 찾지 말 것. 이 저장소의 테스트는 전부 코드 파일이고, 등록이 아니라 push 가 실행 조건이다(장표 115).

## 7. 면접 한 문장
"Jenkins 로 치면 저장소의 ci.yml 이 Jenkinsfile 이고, rt_core·fleet_integration·mujoco 세 job 이 stage 입니다 — 차이는 stage 마다 새 VM 이 켜진다는 것이고, 그래서 1단계가 통과한 뒤에야 2단계 둘이 병렬로 돕니다."
