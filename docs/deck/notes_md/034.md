# 장표 034 — 단계 5 — 상태 머신 코드 (1/2) — if 문이 아니라 전이표 한 장 (kTable)
*위치: 1부 로봇을 움직이는 길 · 단계 5/10 제어 단계(안전) · ② 코드 — 전이표*

## 1. 이 장표가 왜 있나
- 앞 장표(033)의 그림이 코드로는 어떻게 생겼는지 보인다. 상태 머신을 구현하는 방법은 둘이다: 상태마다 `switch`/`if` 를 늘어놓는 방법과, **전이표 하나**를 두고 훑는 방법. 이 저장소는 후자를 택했고(DECISIONS D3), 그 표가 이 장표의 `kTable`(전이 15줄) 이다.
- 이 장표는 "표"만 보인다. 표를 훑어 상태를 바꾸는 함수 `handle()` 은 다음 장표(035)다. 둘을 나눈 이유는 표 자체가 한 화면에 전부 보이는 것이 이 설계의 핵심 가치이기 때문이다 — 면접에서 "FAULT 에서 바로 RUNNING 으로 갈 수 있습니까?"라는 질문에 표를 가리키며 "그 줄이 없습니다"라고 답할 수 있다.
- 위치 `rt_control/rt_core/src/robot_state_machine.cpp:15-32`. 바로 위 9~13줄에 `struct Transition { RobotState from; RobotEvent event; RobotState to; };` 가 있다.

## 2. 장표를 하나씩 읽기
- `static const Transition kTable[] = {` — `static` 은 이 파일 안에서만 보이는 변수, `const` 는 바뀌지 않는 값. 프로그램이 뜰 때 읽기 전용 메모리에 놓이고, 할당이 없다.
- 각 줄 `{RobotState::X, RobotEvent::Y, RobotState::Z}` = "상태 X 에서 사건 Y 가 오면 상태 Z 로". 그림(033)의 화살표 하나와 같다. 15줄 = 전이 화살표 15개.
  - 1줄: `INIT, INIT_DONE → READY` — 백엔드 준비가 끝나면 대기. ControlStep 생성자(`control_step.cpp:21`)가 이 사건을 넣는다.
  - 2~3줄: `READY, COMMAND → RUNNING` / `READY, WATCHDOG_TRIP → READY`(주석 "대기 중 명령 없음은 정상 (자기 자신으로)").
  - 4~5줄: `RUNNING, COMMAND → RUNNING`("계속 움직임") / `RUNNING, WATCHDOG_TRIP → FAULT`.
  - 6~7줄: `FAULT, WATCHDOG_TRIP → FAULT`("계속 끊겨 있음") / `FAULT, COMMAND → RECOVERING`. 여기에 `FAULT, COMMAND → RUNNING` 이 **없다**는 것이 설계다.
  - 8~10줄: `RECOVERING, COMMAND → RECOVERING`("복구 확인 중") / `RECOVERING, WATCHDOG_TRIP → FAULT`("복구 중 또 끊기면 다시 FAULT") / `RECOVERING, RECOVERED → READY`.
  - 11~15줄: 다섯 상태 각각 `STOP → INIT`. "어느 상태에서든 STOP 은 처음으로".
- `};` 그리고 `static const std::size_t kTableSize = sizeof(kTable) / sizeof(kTable[0]);` — 표의 줄 수를 컴파일러가 세게 한다(전체 바이트 ÷ 한 줄 바이트 = 15). 줄을 더하거나 빼도 이 숫자는 자동으로 맞는다.
- **오른쪽 요점**
  - "한 줄 = 그림의 화살표 하나" — 코드를 다 읽지 않아도 전이가 보인다.
  - "표에 없는 조합은 전부 불법" — 예: FAULT + RECOVERED(복구 확인도 안 했는데 복구 완료?), INIT + COMMAND(준비도 안 됐는데 명령?). 그림에 화살표가 없는 것과 1:1.
  - "STOP 은 어느 상태에서든 INIT 으로".
  - "표에 줄을 더하면 전이가 늘고, 코드는 안 바뀐다" — handle() 은 표를 훑기만 하므로 손댈 일이 없다.
  - 결정 기록 DECISIONS 11/03 (D3).

## 3. 용어와 단위
- **전이표(transition table)**: `{from, event, to}` 줄의 모음. 데이터로 표현한 상태 머신.
- **static const**: 파일 안에서만 보이고 바뀌지 않는 전역 상수. RT 코드에서 "할당 없음"을 만족하는 방법.
- **sizeof(kTable) / sizeof(kTable[0])**: C/C++ 에서 배열 길이를 구하는 관용구. 각 Transition 은 1바이트 enum 셋이므로 3바이트(정렬에 따라 그 이상), 15줄.
- **자기 전이(self-transition)**: `READY → READY`, `RUNNING → RUNNING` 처럼 같은 상태로 도는 것. 상태는 안 바뀌지만 "그 사건이 그 상태에서 정상"임을 표에 적어 두는 뜻이 있다. `handle()` 은 이것을 `state_transitions` 로 세지 않는다(`to != state_` 일 때만 센다).
- **switch/if 방식(버린 대안)**: 상태마다 분기문을 쓰는 방식. 전이가 코드 곳곳에 흩어져 "빠진 경우"를 찾기 어렵다(DECISIONS).
- **읽기 전용 메모리(.rodata)**: `static const` 데이터가 놓이는 영역. 실행 중 바뀌지 않으므로 여러 스레드가 읽어도 안전하다.

## 4. 쉬운 예시
- **지하철 노선표 비유**: "A역에서 2호선을 타면 B역" 같은 줄을 전부 적은 표가 노선표다. 노선표에 없는 이동(A역에서 9호선 — 그 역에 9호선이 없다)은 할 수 없다. 노선표를 보는 사람(handle)은 표만 훑으면 되고, 역이 하나 늘면 표에 줄을 더할 뿐 사람의 일은 바뀌지 않는다. if 문 방식은 역마다 안내원이 외운 말로 안내하는 것이라, 안내원 하나가 빠뜨리면 아무도 모른다.
- **표로 답하는 질문들**: "FAULT 에서 바로 RUNNING?" → 그 줄 없음, 불가. "READY 에서 명령이 없으면?" → 3줄, READY 유지(정상). "복구 중 또 끊기면?" → 9줄, FAULT. "어디서든 STOP 하면?" → 11~15줄, INIT.
- **숫자 예시**: 5 상태 × 5 사건 = 25가지 조합 중 15가지만 표에 있다. 나머지 10가지(INIT+COMMAND, INIT+WATCHDOG_TRIP, INIT+RECOVERED, READY+INIT_DONE, READY+RECOVERED, RUNNING+INIT_DONE, RUNNING+RECOVERED, FAULT+INIT_DONE, FAULT+RECOVERED, RECOVERING+INIT_DONE)는 전부 불법으로 세어진다. 테스트는 그중 둘(RUNNING+INIT_DONE, RUNNING+RECOVERED)을 넣어 `illegal_events` 가 2 느는지 본다.

## 6. 자주 하는 오해·함정
- "표 방식은 느리다" — 최대 15번의 정수 비교 두 개씩. 1 ms 예산에서 수십 ns. if 문과 차이가 없고, RT 규칙(할당·락·파일 없음)을 만족한다.
- "표에 없는 조합은 컴파일 때 막힌다" — 아니다. 실행 중에 `handle()` 이 표를 훑어 없으면 `illegal_` 을 올리고 상태를 유지한다(035). 컴파일 때 막으려면 다른 기법이 필요하고, 그러면 표의 "한눈에 보임"을 잃는다.
- "자기 전이 줄(READY→READY 등)은 없어도 된다" — 없으면 그 사건이 불법으로 세어진다. "그 상태에서 그 사건은 정상"을 표에 적는 것이 그 줄의 역할이다.
- "STOP 전이가 5줄이면 중복이다" — `from` 을 "아무 상태"로 쓰는 특수 표기를 두면 줄은 줄지만 handle() 이 복잡해진다. 다섯 줄을 그대로 적는 쪽이 읽기 쉽다는 판단이다.

## 7. 면접 한 문장
"상태 머신은 `{지금 상태, 사건, 다음 상태}` 15줄짜리 정적 표 하나이고 그림의 화살표와 1:1 입니다 — 'FAULT 에서 바로 RUNNING?' 에 그 줄이 없다고 표를 가리켜 답할 수 있고, 표에 없는 25−15 = 10가지 조합은 전부 불법으로 세어지며, 전이를 더할 때 코드는 바꾸지 않고 줄만 더합니다."
