# 장표 139 — 덧붙임 (11/11) — 릴리스의 숫자: 태그에서 게시까지 2분 안, 깨진 빌드는 3 / 50 에서 멈춘다, 실물 Pi 의 설치 한 번은 약 1초
*위치: 7부 왜·사고·방식 · 덧붙임 릴리스 → 배포 3/3 숫자 (11/11)*

## 1. 이 장표가 왜 있나
앞의 두 장표는 그림(137)과 코드(138)였다. 그림과 코드는 "이렇게 되어 있다"까지만 말한다. 이 저장소의 규칙은 그다음을 요구한다 — **실제로 돌렸더니 몇이 나왔나.** 릴리스 → 배포에 대해 물을 것은 셋이다. ① 태그 하나로 정말 사람 손 없이 게시까지 가는가, 몇 분에. ② 50대에 진짜 파일을 깔고 켜 보는 데 몇 초인가(흉내 경로는 정해 준 시간만큼 그냥 잤다). ③ 깨진 빌드는 몇 대에서, 몇 초 만에 멈추나. 그리고 가상 장치만으로는 답할 수 없는 넷째 — ④ 러너가 만든 파일이 실물 Pi 에서 켜지는가, 설치 한 번에 얼마나 걸리나. 이 장표는 그 넷을 큰 숫자 넷으로 답하고, 숫자를 어떻게 읽어야 하는지와 그 과정에서 찾은 버그 하나를 글머리표로 붙인다. 숫자는 11/11 오전의 것이고, 실험 페이지는 E22 다. 다음 장표(140)는 눈을 돌려 "관제 쪽은 어디에 두나"로 간다.

## 2. 장표를 하나씩 읽기
큰 숫자 네 개를 왼쪽에서 오른쪽으로, 그다음 글머리표 네 줄, 바닥 줄 순서.

- KPI 1 "1분 27초 / 태그 push → Release 게시 (v0.9.0) / rc1 은 1분 52초 — 둘 다 첫 실행에 통과": 사람이 `git push origin v0.9.0` 을 한 순간부터 GitHub 의 Releases 화면에 파일 다섯 개가 올라올 때까지의 시간. 그 사이에 러너 두 대가 각자 빌드하고 패키지를 만들고, 셋째 러너가 가상 50대에 깔아 보고, 넷째가 게시했다. 시험 태그 `v0.9.0-rc1`(11/11 아침)은 1분 52초, 정식 `v0.9.0`(같은 날 09:48 무렵)은 1분 27초였다. "첫 실행에 통과"는 이 워크플로가 러너에서 처음 돌았을 때 고칠 것 없이 끝까지 갔다는 뜻이다 — 전날 서버와 Pi 의 설치 스크립트가 첫 실행에서 일곱 번 걸린 것과 대조된다(장표 141). 제목의 "2분 안"은 이 두 값을 한마디로 한 것이다.
- KPI 2 "50 / 50 / 가상 50대에 진짜 설치 (러너) / 1.2 → 2.2 → 2.2초, 전체 14.6초": v0.9.0 의 카나리. 가상 장치 50대 전부가 패키지를 내려받아 설치하고 새 버전이 됐다. 세 숫자는 단계마다 "명령을 보낸 순간부터 그 단계의 장치 전부가 새 버전을 보고할 때까지" — 5 % 단계(3대) 1.2초, 50 % 단계(새로 22대) 2.2초, 100 % 단계(새로 25대) 2.2초. 전체 14.62초에는 단계마다 3초씩 건강을 지켜보는 시간(헬스 대기 3초 × 3 = 9초)이 들어 있다.
- KPI 3 "3 / 50 / 깨진 패키지가 닿은 장치 / 자가 점검이 거부, 롤백 1.0초": 같은 50대에 일부러 깨뜨린 패키지를 배포한 결과. 첫 단계의 3대만 명령을 받았고, 셋 다 자가 점검에서 거부했다. 배포기는 그것을 1.0초에 보고 되돌리기 명령을 보냈고, 1.0초 뒤 3대가 모두 "새 버전이 아니고 정상"으로 보였다. 나머지 47대는 깨진 패키지를 받은 적이 없다. 2부의 "3 / 50, 1.0초"(장표 100)와 숫자는 같지만 일어난 일이 다르다 — 거기서는 나쁜 펌웨어가 **켜진 뒤** 고장을 내고 서버가 헬스 대기 뒤에 잡았고, 여기서는 장치가 **켜 보기 전에** 거부해서 서버가 헬스 대기를 기다리지 않았다.
- KPI 4 "약 1초 / 실물 Pi 4 의 설치 한 번 (0.98~1.62초) / 그중 자가 점검 0.67초": 가상 장치가 아니라 진짜 Pi 4 가 GitHub 에서 rc1 패키지(aarch64, 21.7 KB)를 받아 설치한 시간. 세 번 재어 1.62초, 1.01초, 0.98초. 그 가운데 0.67초가 자가 점검이다(1 kHz 루프를 0.5초 돌리고 판정).
- 글머리표 1 "읽는 법: 러너의 숫자에는 '장치의 다음 보고(1 Hz)까지 최대 1초'가 들어 있다 — 배포기는 장치의 다음 텔레메트리에서야 새 버전과 복귀를 안다. 0.05초마다 보고하는 장치로 잰 값(가짜 브로커, 11/10)은 0.6 → 1.0 → 1.2초, 롤백 0.2초였다. 설치 자체의 비용은 거의 전부 자가 점검(0.5초짜리 1 kHz 루프)이다": KPI 2 · 3 을 과장 없이 읽는 법. 배포기는 장치에게 "끝났니?"라고 묻지 않는다 — 장치가 1초에 한 번 보내는 텔레메트리의 버전 문자열을 볼 뿐이다(장표 079). 그러니 설치가 0.6초에 끝나도 서버가 아는 것은 다음 보고 때이고, 숫자에는 0~1초의 기다림이 섞인다. 전날 작업본에서 **0.05초마다 보고하는** 장치와 가짜 브로커로 같은 일을 했을 때는 0.6 → 1.0 → 1.2초, 롤백 0.2초였다 — 두 환경의 차이가 보고 주기와 같다. 그래서 "설치 자체는 약 0.6~1.2초, 러너의 값은 거기에 보고를 기다린 시간이 더해진 것"으로 읽는다(러너에서 설치 시간만 따로 잰 것은 아니므로 추정이다). 그리고 그 설치 시간의 대부분은 0.5초짜리 자가 점검이다 — 21 KB 를 받고 지문을 재고 푸는 데는 수십 ms 다.
- 글머리표 2 "러너 두 번(진짜 Mosquitto, 가상 50대): rc1(11/11 08:59) 1.2 → 2.0 → 2.2초 · 전체 14.41초 · 거부 0.6초 뒤 롤백 1.0초 / v0.9.0(09:48) 1.2 → 2.2 → 2.2초 · 14.62초 · 거부 1.0초 뒤 롤백 1.0초. 전체에는 헬스 대기 3초 × 3 이 들어 있다. 합격선(50대 < 60초 · 첫 단계 3대에서 멈춤 · 롤백 < 5초)은 둘 다 통과": 한 번의 값이 아니라는 줄. 같은 워크플로가 서로 다른 태그로 두 번 돌았고 값이 거의 같다(둘째 단계 2.0 과 2.2, 전체 14.41 과 14.62). 깨진 패키지를 서버가 알아챈 시각만 0.6초와 1.0초로 다른데, 위 글머리표의 이유(다음 보고까지 0~1초)로 설명되는 범위다. 합격선 셋은 재기 전에 E22 에 적어 둔 것이다 — 50대 전체가 60초 안(매니페스트의 단계당 제한 시간), 깨진 것은 첫 단계의 3대를 넘지 않을 것, 롤백 5초 안.
- 글머리표 3 "실물: 러너(ubuntu-24.04-arm)가 만든 aarch64 바이너리가 Pi 4 의 RT 커널에서 자가 점검 500주기 드롭 0 으로 통과했다(깨어남 p99 158 us). 시험용 슬롯에 설치해, 돌고 있는 서비스와 연속 기록은 건드리지 않았다. 정식 v0.9.0 은 Pi 서비스가 새벽 03~05시에 스스로 받는다 — 첫 자율 설치의 결과는 E22 에 적는다": KPI 4 의 뒷이야기 셋. ① 아키텍처의 증명 — GitHub 의 arm 러너가 빌드한 실행 파일이 집에 있는 Pi 4 에서 실제로 켜졌다. 0.5초 동안 500주기를 돌아 드롭 0, 깨어남 지연 p99 158 us(실시간 우선순위 없이 돌린 값이라 성능 수치로 쓰지 않는다 — "켜진다"의 증거다). ② 어디에 깔았나 — 운영 중인 자리(`~/rt-slots`)가 아니라 시험용 자리(`~/rt-slots-test`)에 한 번만 설치하는 명령(`pi_agent.py --once`)으로 했다. 그때 Pi 의 에이전트 서비스는 서버로 연속 보고 중이었고(장표 140), 그것을 끊지 않으려는 것이다. ③ 아직 안 일어난 일 — 정식 v0.9.0 을 서비스가 스스로 받는 것은 다음 새벽이다. 이 장표를 만든 시점(11/11 오전)에는 결과가 없고, 생기면 E22 에 적는다.

## 3. 용어와 단위
- 태그 push → 게시: 사람이 태그를 올린 때부터 Release 가 보일 때까지의 벽시계 시간. GitHub 가 워크플로 실행 옆에 적어 준다.
- rc1(release candidate 1): 정식 릴리스 전의 첫 시험판. 태그 이름 `v0.9.0-rc1`.
- "50 / 50", "3 / 50": 새 버전(또는 깨진 패키지의 명령)이 닿은 장치 수 / 전체 장치 수.
- 적용 완료 시간(초): 한 단계에서 명령 전송 → 그 단계 장치 전부가 새 버전을 보고. 내려받기 + 검증 + 풀기 + 자가 점검 + 전환 + 다음 보고까지의 기다림.
- 헬스 대기: 단계마다 판단 전에 지켜보는 시간. 카나리는 3초(매니페스트의 정책 값은 5초인데 카나리 스크립트가 3초로 준다).
- 롤백 시간(초): 되돌리기 결정 → 닿은 장치 전부가 "새 버전이 아니고 정상"으로 보일 때까지.
- 1 Hz: 1초에 한 번. 가상 장치와 Pi 가 텔레메트리를 보내는 주기.
- 가짜 브로커: 작업본에서 쓰는, 메시지를 지연 없이 바로 전달하는 파이썬 모듈(장표 116). 진짜 Mosquitto 와 달리 네트워크가 없다.
- 깨어남 p99 158 us: 0.5초 자가 점검 동안 1 ms 주기로 깨어난 500번 가운데 99 % 가 이 값 이내. 1 us = 0.001 ms.
- 시험용 슬롯: 운영 중인 설치 자리와 다른 폴더. 거기에 깔면 운영 중인 것은 그대로다.
- 21.7 KB: 패키지 하나의 크기(실행 파일 하나와 작은 설정 파일들). 실제 로봇 소프트웨어라면 수십 MB 가 될 것이다.

## 4. 쉬운 예시
- 비유: 택배 도착 알림. 택배(패키지)는 0.6초에 문 앞에 놓였는데, 받는 사람이 1초에 한 번만 "도착했어요" 문자를 보낸다면, 보낸 사람이 아는 시각은 0.6초가 아니라 그다음 문자 때다. KPI 2 의 1.2 → 2.2 → 2.2초는 "택배가 놓인 시각"이 아니라 "문자를 받은 시각"이다. 문자를 0.05초마다 보내는 사람으로 재면 0.6 → 1.0 → 1.2초가 나온다.
- 숫자 예시(전체 14.62초의 속): 3대 적용 1.2초 → 헬스 대기 3초(4.2초) → 22대 적용 2.2초(6.41초) → 대기 3초(9.41초) → 25대 적용 2.2초(11.62초) → 대기 3초(14.62초) → "완료: 50/50". 적용만 더하면 1.2 + 2.2 + 2.2 = 5.6초, 나머지 9초는 일부러 지켜본 시간이다. 정책 값(헬스 대기 5초)으로 돌리면 전체는 약 20.6초가 된다(계산값 — 그렇게 돌려 잰 것은 아니다).
- 숫자 예시(Pi 4, 둘째 설치 1.009초의 속): 매니페스트 읽기 0.182 + 내려받기 0.117 + 검증 0.001 + 풀기 0.026 + 자가 점검 0.674 + 전환 0.000 + 훅 0.009. 자가 점검이 3분의 2 다.
- 깨진 패키지의 타임라인(v0.9.0): 0.0초 "단계 5%: 3대에 ota 전송" → 1.0초 "설치 실패 3대 … 사유 … selftest 실패 (exit 1) … → 롤백" → 1.0초 "롤백: 3대에 ota_rollback 전송" → 2.0초 "롤백 완료: 3대 복구, 1.0초".

## 6. 자주 하는 오해·함정
- "50대에 2.2초면 장치 하나에 0.04초"라는 계산은 틀리다. 장치들은 **동시에** 설치한다. 2.2초는 가장 늦은 장치가 보고한 시각이고, 그 대부분은 0.5초 자가 점검과 다음 보고를 기다린 시간이다.
- "러너의 1.2초 > 가짜 브로커의 0.6초이니 진짜 브로커가 느리다"는 오해: 차이의 대부분은 브로커가 아니라 장치의 보고 주기(1초 대 0.05초)다.
- "Pi 는 한 번에 약 1초"를 함대의 숫자로 쓰지 않는다. 실물 1대가 시험용 자리에 세 번 설치한 값이다. 실물에서 "5 % 에서 멈추기"는 보인 적이 없다 — 바닥 줄의 첫 한계.
- 자가 점검의 p99 158 us 를 실시간 성능으로 말하지 않는다. 0.5초, 실시간 우선순위 없음. Pi 의 실시간 숫자는 표①(부하 중 최대 189 us)이다.
- "자율 업데이트가 됐다"고 말하려면 다음 날의 확인이 있어야 한다. 이 장표의 숫자는 승인도 자율도 아닌 **시험 설치**(`--once`)와 러너의 카나리다.
- 14.6초를 "배포가 14.6초 걸린다"로만 말하면 헬스 대기를 일부러 넣었다는 것이 빠진다. "설치 5.6초 + 지켜본 9초"로 말한다.
- 깨진 패키지의 "롤백 1.0초"에서 장치가 한 일은 상태를 정상으로 돌린 것뿐이다. 설치를 거부했으므로 되돌릴 파일이 없었다.

## 7. 면접 한 문장
"태그를 올리고 1분 27초 뒤에 게시됐고, 그 사이 러너가 가상 50대에 진짜 패키지를 14.6초에 깔았으며, 일부러 깨뜨린 패키지는 첫 3대가 켜 보기 전에 거부해 1초에 되돌렸습니다. 같은 워크플로를 두 번 돌려 값이 같았고, 러너가 만든 arm 바이너리를 실물 Pi 가 받아 약 1초에 설치하는 것도 확인했습니다. 숫자에는 장치의 다음 보고까지 최대 1초가 들어 있다는 것과, 태그를 올리기 전에 코드를 다시 읽다 롤백 순서 버그를 찾은 것도 같이 적어 두었습니다."
