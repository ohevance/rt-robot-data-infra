# 장표 093 — 단계 4 검증 — 표① 실험 사슬 (3/3) — E19-d: 내 측정기가 맞나? (도구 불일치 2.3배의 정체)
*위치: 3부 검증 · 단계 4 RT 1 ms 루프 · 실험 사슬 3/3 (측정기 검증)*

## 1. 이 장표가 왜 있나
앞 장표(092)의 E19-a 에서 두 숫자가 나란히 나왔다 — 표준 도구 cyclictest 는 부하 중 max 132 us, 내가 만든 측정기 jitter_bench 는 301 us. 방향(RT 커널이 최악을 줄인다)은 같지만 크기가 2.3배 다르다. 표①의 jitter_bench 줄은 전부 **내가 만든 자**로 잰 값이므로, 표준 자와 2배 넘게 다르면 "측정기가 틀린 것 아닙니까?"라는 반박을 못 막는다. 그래서 변수를 하나씩 지워 가며 차이의 정체를 가렸다. 결론: **측정기는 맞다**(같은 설정이면 274 vs 270). 차이는 스레드 배치와 부하 정의였고, 그 과정에서 내 두 스크립트의 부하 설정이 달랐던 실수가 드러나 `lib_stress.sh` 한 곳으로 묶었다. 이 장표가 있어야 표①을 "자기 자가 맞는지까지 확인한 표"라고 말할 수 있다.

## 2. 장표를 하나씩 읽기
전부 Pi 4B, RT 커널 `6.8.0-2054-raspi-realtime`, isolcpus=3 적용 상태(격리된 CPU 3 은 비워 두고 격리 안 된 CPU 2 를 씀), 부하는 stress-ng `--cpu 4 --io 2 --vm 1 --vm-bytes 256M`, 각 60초, 식힌 뒤 시작, 끝나면 온도·스로틀 확인(전부 0).

- **상자 "E19-a 에서 발견 — cyclictest 132 vs jitter_bench 301"**: 출발점. 같은 부하·같은 RT 커널에서 두 도구의 max 가 2.3배 차이.
- **마름모 "두 도구가 같은 급(±30%)?"**: 합격선 ±30%. "같은 것을 재는 두 자는 이 안에 들어야 한다."
  - **답 "아니오 → 가설: 50 us 일하는 동안의 노출"**: 첫 가설. cyclictest 는 깨면 시각만 적고 바로 다시 잔다. jitter_bench 는 깨서 50 us 동안 바쁘게 돈다(진짜 제어 루프처럼). 그 50 us 동안 인터럽트·IPI 에 맞아 max 가 커지는 것 아닐까?
- **상자 "A-1 jitter_bench --work-us 0 (깨기만, CPU 2)"**: 가설 검증 — 일을 0 으로 해서 cyclictest 처럼 "깨기만" 하게 한다. CPU 2 고정, 우선순위 80.
- **마름모 "work 0 이면 ~130 으로?"**:
  - **답 "아니오: 270 (p99 만 169→116) → 가설 기각"**: max 270.0 us. 일을 없애도 거의 그대로. 일하는 50 us 는 p99(보통 나쁜 경우)를 169.1 → 116.0 으로 낮추지만 max 에는 영향이 작다. 첫 가설은 max 에 대해 기각.
- **상자 "A-2 cyclictest 를 같은 설정으로 — -t 1 -a 2 -p 80, 256M"**: 생각을 뒤집는다 — jitter_bench 를 cyclictest 처럼 만드는 대신, cyclictest 를 jitter_bench 와 **똑같은 설정**(스레드 1개, CPU 2 고정, 우선순위 80, 부하 256M)으로 돌린다. 설정이 같으면 두 도구가 같은 값을 내야 한다.
- **마름모 "두 도구가 같은 값?"**:
  - **답 "예: 274 vs 270 ✓ 측정기는 맞다"**: cyclictest 274 us, jitter_bench 270 us — 1.5% 차이. 내가 만든 자는 표준 자와 같다. 그렇다면 처음의 132 vs 301 은 **자의 차이가 아니라 재는 조건의 차이**였다.
- **상자 "B prio 90 → 290 (무관) / C -S 스레드 배치 → 210"**: 조건 차이를 하나씩 확인. B: jitter_bench 우선순위를 cyclictest_run 과 같은 90 으로 → 289.7 us, 80 과 다르지 않다(잡음 범위) → 우선순위는 무관. C: cyclictest 를 `-S`(CPU 마다 스레드 하나씩, 격리된 CPU 3 제외 3개)로, 단 부하는 256M 그대로 → max 210 us(CPU 별 204·99·210). 스레드를 CPU 마다 두면 274 → 210 으로 준다.
- **끝 상자 "차이 = 스레드 배치(~60) + 부하 정의 512M vs 256M(~80, 추정) → lib_stress.sh 한 곳으로"**: 301 − 132 = 169 us 의 분해. 스레드 배치(274 → 210) 약 60 us 는 확인. 나머지 210 → 132 약 80 us 는 **부하 정의**로 추정 — E19-a 의 cyclictest 는 메모리 버퍼 512M(munmap 이 드물어 IPI 가 적음)이고 격리 전이라 stress 작업자 4개가 CPU 4개에 퍼져 CPU 당 부하가 낮았다. 두 요인을 완전히 가르려면 512M 로 C 를 한 번 더 재면 되지만, 표①의 결론(격리로 189, 통과)에 영향이 없어 여기서 멈췄다. 그리고 드러난 실수: `cyclictest_run.sh` 는 512M, `jitter_run.sh` 는 256M 으로 부하가 달랐다 → `scripts/lib_stress.sh` 의 `start_stress` 하나로 묶고 `.meta` 에 `stress_vm_bytes` 를 남기게 고쳤다.
- **아래 설명 "배운 것: 도구를 비교하려면 부하까지 같은 함수에서 나와야 한다"**: 이 실험의 교훈이자 DECISIONS 11/05 의 결정.

## 3. 용어와 단위
- **cyclictest**: 리눅스 RT 표준 측정 도구. "1 ms 뒤 깨워 달라" → 깨면 시각만 적고 곧바로 다시 잔다. `-S` = CPU 마다 스레드 하나, `-t 1 -a 2` = 스레드 하나를 CPU 2 에, `-p 80` = 우선순위 80, `-i 1000` = 1,000 us 간격.
- **jitter_bench 의 `--work-us`**: 깬 뒤 바쁘게 도는 시간. 기본 50, 0 이면 cyclictest 와 같은 "깨기만".
- **노출(exposure)**: 스레드가 CPU 를 쓰는 동안 인터럽트·IPI 에 맞을 수 있는 시간.
- **IPI(Inter-Processor Interrupt)**: 한 CPU 가 다른 CPU 들에게 보내는 "지금 당장 이것 해라" 신호. 메모리 매핑을 지울 때(munmap) 다른 CPU 의 주소 변환 캐시(TLB)를 비우라고 전부에게 보낸다. 우선순위도 isolcpus 도 막지 못한다.
- **`--vm-bytes`**: stress-ng 메모리 작업자가 한 번에 잡는 버퍼 크기. 작을수록 mmap → 채움 → munmap 주기가 짧아 munmap(= IPI)이 잦다(추정).
- **±30%**: "같은 급"의 합격선. 274 vs 270 은 1.5%.
- **us**: 마이크로초. 169 us 차이 = 0.169 ms.

## 4. 쉬운 예시
- 비유: 두 직원 A(cyclictest)·B(jitter_bench)가 "호출벨에 얼마나 늦게 반응하나"를 쟀더니 B 가 2배 늦었다. B 에게 "상자 나르지 말고 손만 들어"(일 0)라고 해도 여전히 늦었다 → B 가 느린 게 아니라 B 가 서 있던 자리와 그날 매장 상태가 달랐던 것. A 를 B 와 같은 자리에 세우자(A-2) 둘이 똑같이 늦었다(274 vs 270). 그다음 "자리"(스레드 배치)와 "매장 상태"(부하 크기)를 하나씩 바꿔 가며 2배의 정체를 나눴다.
- 숫자 예시: 169 us 의 분해 — 스레드 배치 약 60(확인) + 부하 정의·격리 전후 약 80(추정) + 일 50 us 의 몫 약 40(311 → 270, 주로 p99 에 나타남) ≈ 169.

## 6. 자주 하는 오해·함정
- "표준 도구와 다르면 내 측정기가 틀렸다" — 먼저 조건을 같게 맞춰 보아야 한다. 같게 맞추니 1.5% 차이였다.
- "일(work)이 max 를 키운다" — 직관과 달리 max 에는 영향이 작았고 p99 에 나타났다. 가설은 실험으로 기각할 수 있어야 한다.
- 내 실수: 두 스크립트의 부하 설정이 달랐던 것은 측정기 버그가 아니라 **측정 조건 관리**의 실수다. 그래서 고친 것도 코드가 아니라 "부하 정의는 한 곳, 쓴 값은 .meta 에"라는 규칙이다.
- 이 실험은 isolcpus=3 이 적용된 상태에서 CPU 2 로 돌렸다. 격리된 CPU 3 의 189 와 직접 비교하면 안 된다 — 비교 대상은 격리 전 E19-b(311)와 E19-a cyclictest(132)다.
- 표① 읽는 법: cyclictest 줄은 "커널이 주는 깨어남 바닥"(CPU 마다 스레드, 큰 버퍼 부하), jitter_bench 줄은 "일하는 스레드 하나가 겪는 지연"(작은 버퍼 부하). 로봇 제어 루프에 가까운 것은 후자.
