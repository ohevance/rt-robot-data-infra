# 장표 126 — 결정 기록 (2/3) — 관제 쪽
*위치: 7부 왜·사고·방식 · 결정 2/3 관제*

## 1. 이 장표가 왜 있나
앞 장표(125)가 로봇 안(실시간) 쪽의 결정이었다면, 이 장표는 로봇 밖, 즉 2부에서 따라간 **데이터의 길(관제)** 쪽 결정 9건이다. 왜 로봇 밖은 ROS 2 가 아니라 MQTT 인가, 왜 1초씩 묶어 DB 에 넣나, 끊기면 누가 데이터를 들고 있나, 대시보드 설정은 왜 코드로 만드나, OTA 롤백은 누가 결정하나, 수집기가 DB 를 못 쓸 때 어디에 쌓나, QoS 는 왜 기본 0 인가, 유실 53 을 보고 무엇을 바꿨나, keepalive 는 왜 그대로 두었나. 2부의 코드와 표③ 숫자가 "무엇"이라면 이 표는 그 "왜"이고, 특히 뒤의 두 줄(11/04)은 **실측 결과를 보고 내린 결정**이라 순서도의 "기준을 못 넘었을 때 분기"가 결정으로 남은 예다.

## 2. 장표를 하나씩 읽기
열은 앞 장표와 같다: 결정 (날짜) · 이유 · 버린 대안. "(D2)·(D3)·(D4)" 는 11/03 의 설계 꼬리표, "(11/04)" 는 실측 뒤의 결정이다.

- **장치 → 서버는 MQTT, 서버 안은 ROS 2 가 아니다 (D2)**: 장치의 텔레메트리는 MQTT 브로커를 거쳐 서버로 가고, ROS 2 는 로봇 안(제어·센서)에서만 쓴다. RT 노드는 `/rt_status` 를 다리(ros_status_bridge)로 MQTT 에 올린다(1부 단계 10). 이유: DDS 의 자동 발견(discovery)은 같은 네트워크 안 수십 대까지가 편하고, 수백 대·NAT·LTE 뒤의 장치에는 브로커 중계 모델이 맞다. 게다가 MQTT 는 유언(LWT)·보관 메시지·QoS 1 재전송으로 "끊김" 처리를 거의 공짜로 준다. 버린 대안: DDS 를 WAN(사무실 밖 네트워크)까지 — 네트워크 경계를 넘는 순간 발견·멀티캐스트 문제가 생긴다.
- **수집기는 1초 묶음 + COPY (D2)**: 메시지마다 INSERT 하지 않고 1초 모아 PostgreSQL 의 COPY 로 한 번에 넣는다. 이유: 300대 × 1 Hz 를 행 단위로 넣으면 DB 왕복 300회/초, 묶으면 1회/초. 대신 DB 에 보이기까지 최대 1초가 더해지는데, 이 비용을 숨기지 않고 표③의 비고에 적었다. 관제(모니터링)에는 1초 지연이 문제없고, 제어는 애초에 이 길을 타지 않는다. 버린 대안: 행마다 INSERT.
- **끊김 처리는 장치 쪽 버퍼(store-and-forward) (D2)**: 브로커와 끊기면 장치가 메모리에 모아 두고(최대 1시간 분 = 3,600개), 재접속 때 QoS 1 로 재전송한다. 이유: 유실은 "없게"보다 "세게" 만드는 것이 먼저다 — 일련번호(seq)로 서버가 유실을 계산하고, 버퍼·재전송 카운터로 장치가 자기 상태를 말한다. 괄호의 "654 = 654" 는 E05 실측: 브로커 10초 중단 뒤 버퍼에 쌓인 654개가 전부 재전송되었다. 버린 대안: 서버 쪽에서만 보관 — 끊긴 동안 서버에는 애초에 도착하지 않으므로 보관할 것이 없다.
- **대시보드 JSON 은 생성기로 (D2)**: `fleet/grafana/make_dashboard.py` 가 Grafana 대시보드 JSON 을 만든다. 손으로 고치지 않는다. 이유: 수백 줄짜리 JSON 은 사람이 읽고 설명할 수 없지만, 패널 14개의 SQL 이 파이썬 한 파일에 보이면 리뷰·수정이 되고 CI 가 파싱 검사까지 한다(장표 119 의 "대시보드 JSON 생성 → 파싱 검사"). 버린 대안: Grafana 화면에서 손으로 만들고 export — 다시 만들 수 없고 차이를 설명할 수 없다.
- **OTA 롤백 결정은 서버가 (D3)**: 장치는 "적용(updating → 새 버전)"과 "되돌리기"만 하고, 단계(5 → 50 → 100%)·헬스 판정·롤백 명령은 전부 서버의 `rollout.py` 가 한다. 이유: 장치 하나는 자기 고장만 안다. "3대 중 1대가 fault" 같은 집단 판단은 전체를 보는 쪽만 할 수 있고, 장치가 스스로 롤백하면 서버는 왜 되돌아갔는지 모른다. 판단 기준(헬스 게이트·허용 수 max_fail)이 한 곳에 있다. 버린 대안: 장치가 스스로 롤백. 장표의 "11/10 보탬: 켜 보기 전의 거부(sha256·자가 점검)와 훅 실패 뒤 복귀는 장치가 스스로 — 함대 차원의 결정은 그대로 서버"는 진짜 설치가 들어오며 이 결정의 경계를 다시 그은 줄이다. 장치가 스스로 하는 것이 둘 생겼다 — ① 받은 파일을 **켜 보기 전에** 거부하기(지문이 다르거나 자가 점검이 실패하면 `current` 를 바꾸지 않는다), ② 전환 직후의 훅(`post_switch.sh`)이 실패하면 스스로 이전 슬롯으로 돌아가기. 둘 다 "내 몸에 이 파일을 들일 것인가"라는 장치 한 대의 문제라 장치가 가장 잘 안다. 반면 "이 릴리스를 함대의 다른 장치에도 계속 깔 것인가, 전부 되돌릴 것인가"는 여전히 서버만 정한다 — 장치는 거부한 사실과 사유를 텔레메트리로 알릴 뿐이다(DECISIONS 11/10 "장치 설치는 A/B 슬롯 …", 11/11 "`ota_rollback` 을 받으면 …").
- **수집기 backlog 는 메모리, 상한 두고 버림 (D4)**: DB 쓰기가 실패하면 1초 묶음을 메모리 리스트에 보관하고 매초 재시도한다. 200,000행(50대 1 Hz 로 약 66분)을 넘으면 가장 오래된 묶음부터 버리고 `backlog_dropped` 로 센다. 이유: DB 중단은 보통 수 초~수 분이고, 디스크 큐는 구현과 복구 경로가 두 배로 복잡하다. 2주 안에는 "복구되고 유실을 센다"가 먼저. 상한은 메모리 보호(행당 약 500 B → 약 100 MB). 버린 대안: 디스크 WAL/SQLite 큐 — 수 시간 중단까지 견디지만 지금 단계의 복잡도가 아니다.
- **텔레메트리 QoS 기본 0, 옵션 1, 차이를 표로 (D4)**: 장치의 `--telemetry-qos 0` 이 기본이고, 수집기 끊김 때 유실 0 이 필요하면 장치 QoS 1 + 수집기 `--qos 1`(지속 세션)을 옵션으로 켠다. 이유: QoS 1 은 메시지마다 확인(PUBACK) 왕복이 붙어 비용이 있다 — 그 비용이 "있는 선택"임을 숫자로 남기기 위해 같은 장애를 두 번 돌렸다: QoS 0 은 유실 508, QoS 1 은 0(표③-2 두 줄). 버린 대안: 무조건 QoS 1.
- **브로커 persistence true, 수집기 곱게 종료, 수동 ACK 보류 (11/04)**: 실측에서 유실 53 이 나왔고 원인이 셋이었다 — ① 브로커 재시작 때 수집기의 구독(지속 세션)이 사라져 먼저 재접속한 장치의 버퍼를 브로커가 버림, ② 수집기 종료 순간 아직 DB 에 안 넣은 1초치 pending, ③ 큐 상한. ①은 Mosquitto 설정 `persistence true` + 데이터 볼륨 한 줄, ②는 SIGTERM/Ctrl+C 를 받아 마지막 flush 를 하고 끝내는 시그널 처리 20줄로 막힌다. 수동 ACK(DB 에 넣은 뒤 PUBACK, paho 의 manual_ack) 는 SIGKILL 까지 막는 완전한 해법이지만 묶음 적재와 ACK 순서를 엮어야 해서 코드가 두 배로 복잡 — 2주 밖으로 보류하고 면접에서 "다음 단계"로 말한다. 버린 대안: paho 의 자동 ACK 를 그대로 두고 무시.
- **keepalive 기본 10초 유지, jitter 는 옵션 (11/04)**: 장치의 keepalive 는 10초(끊김 감지 15초)를 유지하고, 50대가 같은 박자로 PINGREQ 를 보내 10초마다 지연이 튀는 문제는 `--keepalive-jitter N` 으로 장치마다 0~N 초를 더해 박자를 흩뜨린다. 이유: 값을 30초로 늘리면 튐은 사라지지만 "죽은 장치를 45초 뒤에야 안다"는 비용이 생긴다. jitter 는 감지 시간을 거의 그대로 두고 동기화만 깬다 — 주기 작업이 같은 박자로 몰리는 문제의 교과서적 처방. 버린 대안: 기본값을 30초로 — 대시보드의 "오프라인" 판정이 느려진다.

## 3. 용어와 단위
- **MQTT / 브로커**: 발행·구독 방식의 가벼운 메시지 규약과 그 중계 서버(우체국). 장치는 발행, 서버(수집기)는 구독.
- **DDS 발견(discovery)**: ROS 2 노드들이 서로를 자동으로 찾는 절차. 같은 네트워크 안에서는 편하지만 NAT(공유기 안쪽) 를 넘기 어렵다.
- **유언(LWT) / 보관 메시지(retained)**: 비정상 종료 때 브로커가 대신 발행하는 메시지 / 마지막 값을 새 구독자에게 바로 주는 메시지.
- **COPY**: PostgreSQL 의 묶음 적재 명령. 행마다 INSERT 보다 훨씬 빠르다.
- **store-and-forward**: 못 보내면 모아 두었다가 연결되면 보내는 방식.
- **backlog**: DB 가 죽은 동안 수집기가 메모리에 들고 있는 묶음. 200,000행 상한.
- **QoS 0 / 1(MQTT)**: 0 은 보내고 잊음, 1 은 받았다는 확인(PUBACK)이 올 때까지 재전송.
- **지속 세션(clean_session=False)**: 구독자가 없는 동안 브로커가 QoS 1 메시지를 대신 보관하는 설정. 브로커가 재시작해도 남으려면 persistence true 가 필요.
- **수동 ACK(manual ack)**: 받자마자가 아니라 DB 에 넣은 뒤에 "받았다"고 답하는 방식. 이 저장소에서는 보류.
- **keepalive / PINGREQ**: 이 시간 동안 조용하면 장치가 "살아 있다" 신호(PINGREQ)를 보내고, 1.5배 안에 없으면 브로커가 끊는다. 10초면 감지는 15초.
- **단위**: 1 Hz = 1초에 1개. 50대 × 1 Hz × 10초 = 500개 — "보호가 없었다면" 잃을 수.

## 4. 쉬운 예시
- 비유(MQTT 와 브로커): 동네 안에서는 서로 얼굴을 보고 말하면 되지만(ROS 2/DDS, 로봇 안), 전국의 지점 수백 곳과 연락하려면 우체국(브로커)을 거치는 편이 낫다. 우체국은 받는 사람이 자리에 없으면 편지를 보관해 주고(지속 세션), 보낸 사람이 쓰러지면 미리 맡긴 "유언"을 대신 전해 준다.
- 숫자 예시(1초 묶음): 300대가 1초에 한 번씩 보내면 초당 300개. 한 개씩 DB 에 넣으면 초당 300번 왕복, 1초 모아 넣으면 1번. 대신 화면에 보이기까지 최대 1초 늦는다 — 관제 화면은 그래도 되고, 로봇 제어는 이 길을 타지 않는다.

## 6. 자주 하는 오해·함정
- "지속 세션이면 무한히 보관된다"는 오해 — 브로커 큐에는 상한(`max_queued_messages 20000`)이 있고, 넘으면 Mosquitto 는 **새 메시지**를 버린다. 11/04 에 수집기가 7.5분 비어 있는 동안 2,450개가 그렇게 버려졌다(E12). 상한은 "허용 중단 시간 × 장치 수 × Hz" 로 정한다.
- "QoS 1 이면 끝"이 아니다 — 구독자와 발행자 모두 QoS 1 이어야 브로커가 큐에 담는다. 한쪽만 1 이면 min(0, 1) = 0 이 되어 유실된다. 그래서 장애 주입 collector 는 qos0/qos1 두 줄을 남겼다.
- "곱게 종료"는 SIGTERM/Ctrl+C 에만 통한다. SIGKILL(진짜 크래시)에서는 여전히 그 1초를 잃는다 — 그것까지 막는 것이 보류한 수동 ACK 다.
