# 장표 107 — 왜 네 곳인가 — 한 곳으로는 안 되는 이유 (각 곳이 '못 하는 것'이 다음 곳을 만든다)
*위치: 5부 어디서 · 왜 네 곳*

## 1. 이 장표가 왜 있나
앞 장표(106)의 그림에서 컴퓨터 네 곳과 그 사이의 길을 보았다. 그러면 바로 "왜 네 곳이나 필요한가, 노트북 한 대로 하면 안 되나"라는 질문이 나온다. 이 장표는 그 질문에 표로 답한다. 열 네 개 중 마지막 열 "못 하는 것"이 핵심이다. 각 곳이 못 하는 것이 있어서 다음 곳이 생겼다는 논리가 행을 따라 내려가며 이어진다. ① 은 실시간 수치를 못 재서 ② 가 필요하고, ② 는 커밋을 못 해서 ③ 이 기준점이 되고, ③ 은 지연 수치를 못 재서 "돌아간다"의 증거만 되며, ④ 는 진짜 환경이 없어서 진짜 첫 실행은 항상 ① 이다. 이 장표를 이해하면 "그 숫자는 어디서 잰 것인가"라는 질문에 네 곳 중 하나를 바로 짚을 수 있다.

## 2. 장표를 하나씩 읽기
표의 열(헤더)은 넷이다. "곳"은 네 곳의 번호와 이름, "하는 일"은 거기서 실제로 돌리는 것, "왜 여기여야 하나"는 다른 곳으로 옮길 수 없는 이유, "못 하는 것"은 그 곳의 한계다. 행을 위에서 아래로 읽는다.

- 행 ① "개발 PC (WSL2 Ubuntu 24.04)": 하는 일은 "모든 코드를 실제로 돌린다 — ROS 2 노드, 관제 컨테이너 3개, 가상 장치 50대, 장애 주입, 기록". 1부와 2부의 모든 것이 처음 실제로 도는 곳이다. 왜 여기여야 하나는 "12 CPU · Docker · ROS 2 가 있는 유일한 곳. Grafana 화면도 여기" — 노트북에 CPU 가 12개 있고 Docker 와 ROS 2 가 설치된 유일한 컴퓨터이며, 사람이 보는 대시보드 화면도 이 노트북에 뜬다. 못 하는 것은 "실시간 지연 수치 — 가상 커널이라 max 가 1 ms 턱밑(921~2,026 us). 전부 '참고값' → ② 가 필요" — WSL2 의 리눅스는 윈도우 위의 가상 머신이라 깨어남 지연의 최악값이 921~2,026 us 로 1 ms 예산에 걸린다. 그래서 WSL 의 지연 숫자는 전부 참고값으로 표기하고, 진짜 값을 재기 위해 ② 가 생겼다.
- 행 ② "Raspberry Pi 4B 4 GB": 하는 일은 "표① 하나만 잰다 — 일반 커널 vs PREEMPT_RT, 고정, 격리". 표①(실시간 깨어남 지연)만 재고 다른 일은 하지 않는다. 왜 여기여야 하나는 "진짜 하드웨어 + 진짜 RT 커널. 4코어라 격리 실험이 된다" — 가상이 아닌 진짜 보드에 진짜 실시간 커널을 깔 수 있고, 코어가 4개라 그중 하나(CPU 3)를 격리하는 실험이 가능하다. 못 하는 것은 "ROS 2·Docker·MuJoCo 없음. GitHub 로그인 없음 — 측정만, 커밋은 ①" — 4 GB 메모리의 작은 보드에 ROS 2 와 Docker 를 깔지 않았고, GitHub 자격 증명도 두지 않아 커밋과 push 는 ① 에서만 한다.
- 행 ③ "GitHub (ohevance/rt-robot-data-infra)": 하는 일은 "저장소(이력 전체) + CI(push 마다 자동 검사) + 공개 링크" — 코드와 문서의 원본과 변경 이력, push 마다 자동으로 도는 검사, 이력서·영상에서 가리킬 공개 주소다. 왜 여기여야 하나는 "어느 PC 에서도 같은 코드를 받는 기준점. 러너는 매번 새 VM" — PC 도 Pi 도 작업본도 전부 GitHub 의 main 에서 받으므로 기준이 하나가 되고, CI 러너는 매번 새 가상 머신이라 "내 PC 에서만 되는" 문제를 걸러 낸다. 못 하는 것은 "RT 커널·권한 없음 → 지연 수치 못 잼. '돌아간다'의 증거" — 러너에는 실시간 커널도 실시간 우선순위 권한도 없어 CI 의 숫자는 빌드되고 테스트가 통과한다는 증거이지 얼마나 빠른지의 증거가 아니다.
- 행 ④ "작성 보조 작업본 (Claude 샌드박스)": 하는 일은 "코드·문서 초안, 컴파일·단위 테스트, git bundle 전달" — AI 가 코드와 문서의 초안을 쓰고, 컴파일과 단위 테스트까지 해 본 뒤 패치 묶음 파일(bundle)로 넘긴다. 왜 여기여야 하나는 "작은 패치 단위로 작성자가 검토할 수 있게" — 한 주제가 한 번들이 되어 작성자가 읽고 검토한 뒤 push 하는 흐름을 만들기 위해서다. 못 하는 것은 "ROS 2·Docker·MuJoCo·네트워크 없음 → 가짜 위에서 논리만. 진짜 첫 실행은 항상 ①" — 샌드박스에는 네트워크가 막혀 ROS 2·Docker·MuJoCo 를 깔 수 없다. 가짜 브로커·가짜 DB·MuJoCo 스텁 위에서 논리만 검증하므로, 진짜 환경에서의 첫 실행은 항상 ① 이고 그때 깨진 것은 `docs/LOG.md` 에 남긴다.
- 아래 글 "비유: ① 작업장, ② 계측실(진동 없는 방), ③ 도면 보관소 겸 검사원, ④ 설계 사무실. 출처: docs/ENVIRONMENT.md §1": 네 곳의 역할을 공장에 비유한 것과 이 표의 원본 위치다.

## 3. 용어와 단위
- WSL2: 윈도우 안에서 리눅스를 가상 머신으로 돌리는 기능. 커널이 가상이라 실시간 수치는 참고값이다.
- 가상 커널 / 진짜 커널: 가상 머신 안의 리눅스 커널은 아래의 윈도우(호스트)가 CPU 를 빼앗을 수 있어 최악 지연을 보장하지 못한다. 진짜 보드의 커널은 그 위에 아무것도 없다.
- us(마이크로초): 100만분의 1초. 921~2,026 us 는 약 0.9~2.0 ms 다. 1 ms 주기 루프에서 2 ms 지연은 주기를 두 번 놓친다는 뜻이다.
- PREEMPT_RT: 리눅스 커널을 실시간용으로 바꾸는 패치. "고정"은 RT 스레드를 특정 CPU 에 붙이는 것(pin), "격리"는 그 CPU 에서 다른 작업을 치우는 것(isolcpus).
- CI(Continuous Integration, 지속적 통합): 코드가 올라올 때마다 자동으로 빌드하고 테스트하는 것. 여기서는 GitHub Actions.
- 러너(runner): CI 를 실제로 돌리는 컴퓨터. GitHub 가 매번 새로 켜 주는 리눅스 가상 머신(VM).
- VM(가상 머신): 소프트웨어로 흉내 낸 컴퓨터 한 대.
- git bundle: 커밋 묶음을 파일 하나로 만든 것. 네트워크 없이 파일로 옮겨 `git pull` 할 수 있다.
- 샌드박스(sandbox): 바깥과 격리된 실행 환경. 여기서는 네트워크가 막힌 리눅스 컨테이너.
- 가짜(fake) 브로커·DB: 진짜 Mosquitto 와 PostgreSQL 대신 같은 함수 이름으로 동작을 흉내 내는 파이썬 모듈. 컨테이너 없이 1초 만에 단위 테스트를 돌릴 수 있게 한다(장표 116).

## 4. 쉬운 예시
- 비유: 자동차 공장에 비유하면 ① 은 조립 라인과 시운전장(모든 부품을 실제로 끼워 돌려 보는 곳), ② 는 소음·진동 계측실(한 가지 수치를 정밀하게 재기 위해 다른 소음을 전부 치운 방), ③ 은 도면 보관소 겸 품질 검사원(원본을 보관하고 들어오는 도면마다 다시 조립해 보는 곳), ④ 는 설계 사무실(도면을 그리고 계산은 해 보지만 진짜 부품은 없는 곳)이다. 계측실에서 조립 라인을 돌리거나, 설계 사무실에서 시운전을 할 수는 없다.
- 숫자 예시: 깨어남 지연의 최악값(max)을 세 곳에서 보면 WSL2 921~2,026 us(참고값), Pi 4 일반 커널 781 us, Pi 4 실시간 커널 + 격리 189 us 다. GitHub 러너는 숫자 대신 "2초 동안 드롭 0"만 확인한다. "지연이 189 us" 라고 말할 때 어디서 잰 값인지를 빼면 세 배 넘게 다른 숫자들과 섞인다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 표의 글자 전부 — `docs/ENVIRONMENT.md` §1 의 표와 비유.
- 확인: WSL2 max 921~2,026 us — `docs/measurements/table1.md`(WSL 실측), `docs/experiments/E02.md`(921 → 937), `docs/LOG.md` 2026-11-03 "D0, WSL2 실측".
- 확인: 12 CPU — `docs/SETUP_WSL.md` 와 `docs/LOG.md` 의 WSL 환경 설명.
- 확인: 컨테이너 3개, 가상 장치 50대 — `fleet/docker-compose.yml`, `fleet/agent/virtual_fleet.py --count 50`.
- 확인: Pi 4B 4 GB, 4코어 — `docs/SETUP_RT_MEASURE.md` §0 준비물(64-bit Cortex-A72 4코어).
- 확인: 러너는 매번 새 VM(ubuntu-24.04) — `.github/workflows/ci.yml` 의 `runs-on`, `docs/ENVIRONMENT.md` §5-1.
- 확인: 샌드박스에 ROS 2·Docker·MuJoCo·네트워크 없음 — `docs/ENVIRONMENT.md` §6.
- 다시 확인하는 법(WSL 창): `nproc` 으로 CPU 수, `docker ps` 로 컨테이너, `uname -r` 로 WSL 커널 이름(`-microsoft-standard-WSL2` 가 붙는다). Pi 창: `nproc` 이 4, `uname -r` 이 `-raspi-realtime`.

## 6. 자주 하는 오해·함정
- "WSL 숫자가 나쁘니 코드가 나쁘다": 아니다. 같은 코드가 Pi 4 실시간 커널에서는 189 us 다. WSL 의 max 는 가상 커널의 한계이고, 그래서 참고값이다.
- "CI 가 초록이면 실시간 성능도 보장된다": CI 는 빌드와 논리(테스트)를 보장한다. 러너에는 실시간 커널이 없어 지연 수치는 ② 에서만 나온다.
- "Pi 에서 바로 커밋하면 편하지 않나": 자격 증명이 두 곳에 있으면 관리가 어렵고 이력이 갈라진다. Pi 는 측정만 하고, 커밋 주체는 ① 하나로 두는 것이 규칙이다(장표 108).
- "작업본(④)에서 테스트가 통과했으니 끝": 가짜 위에서 통과한 것은 "논리가 맞다"이지 "진짜 위에서도 된다"가 아니다. 11/04 의 venv 소실, 11/05 의 `record.sh` 정지(SIGTTIN)처럼 진짜 첫 실행(①)에서 깨진 것들이 `docs/LOG.md` 에 있다.

## 7. 면접 한 문장
"컴퓨터 네 곳은 각자 못 하는 것이 있어서 생겼다 — WSL 은 실시간 수치를 못 재서 Pi 가, Pi 는 커밋을 안 해서 GitHub 가 기준이, 러너는 RT 커널이 없어 '돌아간다'의 증거만, 작업본은 가짜 위라 진짜 첫 실행은 항상 WSL 이다."
