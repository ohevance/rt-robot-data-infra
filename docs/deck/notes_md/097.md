# 장표 097 — 2부 ⑦⑧ 검증 — 표③ 실험 사슬 (1/3) — E05 → E06 → E07: '유실 0' 이 다른 증거와 안 맞는다
*위치: 3부 검증 · 2부 ⑦⑧ 관제 · 표③ 사슬 1/3 ('0' 이 가짜)*

## 1. 이 장표가 왜 있나
2부의 끝 장표(085)에서 "장애를 일으킨 뒤 숫자를 통과/실패로 바꾸는 도구(assert_results.py)와, 이상한 숫자의 이유를 찾는 도구(diag.py)"를 보았다. 그러면 자연스럽게 다음 질문이 생긴다. "그 도구로 실제로 장애를 일으켜 재 보니 어떤 숫자가 나왔고, 그 숫자는 믿을 만했나?" 이 장표는 그 답의 첫 부분이다. 관제(데이터의 길)의 실험은 E05 → E06 → E07 → E08 → E13 으로 이어지는 하나의 사슬인데, 이 장표는 그중 앞 세 개를 다룬다. 결론을 먼저 말하면, 첫 측정에서 "유실 0" 이라는 아주 좋아 보이는 숫자가 나왔지만 그것은 측정 방법의 맹점이 만든 가짜 0 이었고, 측정을 고치자 53 이라는 진짜 숫자가 드러났다. 이 장표가 있는 이유는 "좋은 숫자를 그대로 믿지 않고 다른 증거와 대조했다"는 과정 자체가 이 포트폴리오에서 가장 중요한 이야기이기 때문이다. 순서도 논리로 보면, 마름모(기준)마다 "예/아니오"가 갈리고, "아니오"가 나올 때마다 다음 실험이 생긴다.

## 2. 장표를 하나씩 읽기
장표는 뱀처럼 흐르는 상자 8개다. 왼쪽 위에서 시작해 오른쪽으로 가고, 둘째 줄은 오른쪽에서 왼쪽으로 돌아온다.

- 상자 1 "E05 가상 50대 1 Hz 기본 — 전달 지연 p50 0.9 / p95 1.8 ms": 첫 실험 E05 는 장애를 일으키기 전의 "평소 모습"을 재는 실험이다. 가상 장치 50대가 1초에 1개씩(1 Hz) 데이터를 보내고, 서버의 수집기가 받아 DB 에 넣는다. 전달 지연은 "장치가 값을 측정한 시각"부터 "수집기에 도착한 시각"까지의 시간인데, 절반의 메시지는 0.9 ms 안에(p50), 95% 는 1.8 ms 안에(p95) 도착했다. 같은 PC 안에서 도는 실험이라 네트워크 거리가 거의 없어 이렇게 짧다.
- 마름모 1 "끊김 동안 데이터가 보존되나?" → 화살표 글 "예: 브로커 10초 중단 → 버퍼 654 = 재전송 654 ✓": 왜 이 기준인가 하면, 장치와 서버 사이의 우체국 역할(브로커)이 끊기는 일은 반드시 일어나는데, 그때 데이터를 잃으면 "유실 0" 은 애초에 불가능하기 때문이다. E05 에서 브로커 컨테이너를 10초 멈췄더니 장치들이 끊긴 동안 654개를 메모리에 모았다가(버퍼), 다시 붙자 654개를 그대로 재전송했다. 모은 수와 보낸 수가 같으니 그 구간에서 잃은 것이 없다. 그래서 "예" 로 다음 상자로 간다.
- 상자 2 "E06 장애 4종 1차 — 복구 2.9 / 1.4 / 1.6 s, 롤백 1.0 s, 유실 '0'": 평소 모습과 "끊겨도 보존된다"를 봤으니, 이제 장애 종류별로 숫자를 낸다. 브로커 중단은 전 장치가 돌아오기까지 2.9초, DB 중단은 밀린 묶음(backlog)이 0 이 되기까지 1.4초, 수집기 종료·재시작은 1.6초, 나쁜 펌웨어는 1.0초 만에 롤백. 유실은 전부 0 으로 나왔다. 따옴표가 붙은 '0' 인 이유는 뒤에 이것이 가짜로 밝혀지기 때문이다.
- 마름모 2 "유실 0 이 다른 증거(diag)와 맞나?" → "아니오: 두 장치에 12초 공백인데 0": 이 기준이 중요한 이유는 "숫자 하나만 보지 말라"는 원칙이다. 진단 도구 diag.py 의 C절은 장치별 일련번호(seq)가 연속인지 본다. 그런데 장치 두 대(vdev-003·101)에 브로커 중단 직후 12초짜리 데이터 공백이 있었다. 1초에 1개씩 보내는 장치가 12초 비었는데 유실 계산은 0 — 둘 중 하나는 거짓이다. 그래서 "아니오".
- 상자 3 "E07 유실 기준점 수정 — 창 안 min(seq) → 장애 직전 마지막 seq": 유실 계산식이 틀렸다는 가설로 식을 고쳤다. 원래 식은 장애 구간(창) 안에서 받은 번호 중 가장 작은 번호(min)를 기준으로 셌는데, 장애 시작 직후 잃어버린 번호들은 "창 안에서 처음 받은 번호"보다 앞에 있어서 계산 범위 밖이 된다. 고친 식은 장애 직전 30초 동안 받은 마지막 번호를 기준으로 삼아, 그 다음 번호부터 전부 센다.
- 마름모 3 "다시 재면 0 인가?" → "아니오: 53 / 1434": 고친 식으로 같은 브로커 10초 중단을 다시 재니 장치들이 만든 1,434개 중 53개가 DB 에 없었다. 약 3.7% 다.
- 붉은 상자 "원인 셋: ① 브로커 재시작 경쟁(persistence false, 4~5대 × 12) ② 수집기 종료 순간 장치당 1개 ③ 큐 상한": 53 을 장치·번호 단위로 추적하니 원인이 세 갈래였다. ① 브로커 설정 persistence 가 false 라 브로커가 재시작되면 수집기의 구독(지속 세션)이 사라지고, 수집기보다 먼저 재접속한 장치 4~5대가 버퍼를 쏟을 때 받을 구독자가 없어 12개씩 버려졌다. ② 수집기가 종료 신호(SIGTERM)를 받는 순간, 받았다는 확인(PUBACK)은 이미 보냈지만 아직 DB 에 넣지 않은 "그 1초치"가 장치당 1개씩 사라졌다. ③ 브로커가 수집기 몫으로 들고 있을 수 있는 메시지 수에 상한(20,000개)이 있어, 긴 공백 뒤에는 새 메시지를 버렸다(이건 곁가지 E12 에서 확인).
- 진한 끝 상자 "→ E08 고치고 재측정": 원인 ①②를 고친 뒤 같은 장애를 다시 재는 실험이 다음 장표(098)의 E08 이다.
- 아래 상자 "측정이 틀리면 '0' 은 가장 위험한 숫자다": 이 사슬의 교훈 한 줄이다. 0 은 "완벽하다"처럼 보이지만, 측정이 잘못되면 가장 먼저 나오는 숫자이기도 하다.

## 3. 용어와 단위
- 유실(loss): 장치가 만들었지만 서버 DB 에 끝내 들어오지 않은 메시지 수. "53 / 1434" 는 1,434개 중 53개를 잃었다는 뜻이다.
- seq(일련번호): 장치가 메시지마다 1씩 올려 붙이는 번호. 1, 2, 3, 5 가 오면 4 를 잃은 것이다. 유실을 "세는" 유일한 근거다.
- 브로커(Mosquitto): MQTT 우체국. 장치는 브로커에 올리고 서버(수집기)는 브로커에서 받는다.
- 버퍼 / 재전송(store-and-forward): 끊긴 동안 장치가 메모리에 모아 두었다가(버퍼) 다시 붙으면 몰아서 보내는 것(재전송).
- backlog: DB 가 죽어 못 넣은 1초 묶음을 수집기가 메모리에 쌓아 두는 것. "backlog 0 까지 1.4초" = DB 가 돌아온 뒤 밀린 것을 다 넣는 데 1.4초.
- 롤백: 나쁜 펌웨어를 받은 장치를 이전 버전으로 되돌리는 것.
- persistence(브로커 설정): 세션·구독 정보를 디스크에 써 두는 것. false 면 재시작 때 메모리와 함께 사라진다.
- PUBACK: MQTT QoS 1 에서 받는 쪽이 보내는 "받았다" 확인. 이것을 보낸 순간부터 보관 책임이 받는 쪽으로 넘어온다.
- 단위: ms(밀리초) = 1/1,000초. p50/p95 = 100개 중 가운데 값 / 95번째로 나쁜 값. Hz = 1초에 몇 번(1 Hz = 1초에 1개).

## 4. 쉬운 예시
- 출석부 비유(맹점): 결석을 "교실에 들어온 첫 학생부터" 세면, 수업 시작 직후 결석한 학생은 첫 학생보다 앞 번호라 명단에 아예 없다. 그래서 결석 0 처럼 보인다. 고친 방법은 "어제 마지막 출석 번호 다음부터" 세는 것이다. 이것이 min(seq) → 장애 직전 마지막 seq 로 바꾼 뜻이다.
- 숫자 예시: 장치 1대가 1 Hz 로 보내다가 브로커가 10초 끊겼다. 장치는 10개쯤(실제로는 끊김 감지·재접속 시간까지 13개쯤)을 모았다가 다시 보낸다. 그런데 브로커가 재시작되면서 수집기의 구독이 사라진 사이에 이 장치가 먼저 붙어 13개를 쏟으면, 받을 사람이 없어 12개가 버려지고 1개만 남는다. 그런 장치가 4대(48개)와 절반만 잃은 1대(5개)를 더해 53 이다.

## 6. 자주 하는 오해·함정
- "유실 0 이면 끝" 이 아니다. 측정식이 틀리면 0 이 가장 먼저 나온다. 그래서 이 저장소는 유실 숫자와 진단 도구(seq 틈)를 항상 같이 본다.
- 복구 시간과 유실은 다른 축이다. E06 의 복구 2.9 / 1.4 / 1.6초는 고친 뒤에도 그대로였다(E08). 즉 측정 맹점은 "얼마나 잃었나"에만 있었다.
- "버퍼 654 = 재전송 654" 는 장치 쪽이 안 잃었다는 뜻이지, 서버 DB 에 전부 들어갔다는 뜻은 아니다. 브로커가 중간에서 버린 것(원인 ①)은 장치 카운터로는 보이지 않는다 — 그래서 DB 의 seq 로 세야 한다.
- 원인 ③(큐 상한)은 "고장"이 아니라 설정의 뜻이다. 자세한 것은 장표 099 의 E12.

## 7. 면접 한 문장
"장애 주입의 유실이 0 으로 나왔지만 진단 도구의 12초 공백과 맞지 않아 측정식을 의심했고, 기준점을 장애 직전 번호로 고치자 53 이 나왔다 — 좋은 숫자일수록 다른 증거와 대조한다."
