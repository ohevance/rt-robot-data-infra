# 장표 130 — 2주 일정 — 무엇을 언제 만들었나 (D0 ~ D8, 그리고 11/10~11)
*위치: 7부 왜·사고·방식 · 2주 일정*

## 1. 이 장표가 왜 있나

앞 다섯 장표(125~129)에서 결정 25행과 사고 11건을 봤다. 그것들이 **언제** 일어났는지를 한 줄로 늘어놓은 것이 이 장표다. 질문은 둘이다. "2주라면서 왜 날짜는 11/03 ~ 11/06 나흘과 11/10~11 이틀인가?"와 "그 며칠에 이게 다 가능한가?". 첫 질문의 답은 D 꼬리표(D0~D8)가 **달력 날짜가 아니라 작업 묶음 번호**라는 것이고(아래 각주), 둘째 질문의 답은 다음 장표(131, AI 와 일한 방식)로 넘어간다. 즉 이 장표는 7부의 "왜·사고"에서 "방식"으로 넘어가는 다리다.

## 2. 장표를 하나씩 읽기

화살표 모양 칸 여덟 개가 왼쪽에서 오른쪽으로 이어진다. 칸마다 머리(기간)와 세 줄(그때 만든 것). 일곱째 칸(D8)은 장표 본편을 만든 다음 날(11/06), 여덟째 칸(11/10~11)은 11/11 에 더했다. 칸이 여덟이 되면서 칸 하나가 좁아져, 머리는 두 줄로(위 D 번호, 아래 날짜) 나누고 글자를 조금 줄였다.

- "D0 11/03 — rt_core 뼈대: 링 버퍼·RT 루프·측정기 / WSL 일반 vs FIFO 비교 (E01·E02) / 표① 생성기": 첫 묶음. ROS 2 없는 순수 C++ 핵심(`rt_control/rt_core`: SPSC 링 버퍼, 1 ms 루프, jitter_bench 측정기)을 만들고, WSL2 에서 일반 스케줄링 vs SCHED_FIFO 를 1 kHz × 5초로 비교했다(E01·E02). 결과는 p50 92 → 37 us 로 좋아졌지만 max 921 → 937 us 로 꼬리는 그대로 — "우선순위는 줄을 앞세울 뿐 꼬리는 커널이 자른다"는 표①의 첫 줄이 여기서 나왔다. 표① 생성기 `scripts/make_table1.py` 도 이때.
- "D1~D2 — ROS 2 노드 + 제어 단계·워치독 / DDS 표② 16조합 / 관제: 브로커·수집기·DB·Grafana, 가상 50대": 노드(`rt_control_node.cpp`)와 제어 단계(ControlStep: 최신 명령, 변화량 제한 0.05 rad, 워치독)를 붙였고, DDS 왕복 지연을 구현체 2(Cyclone/Fast DDS) × 신뢰성 2 × 크기 4 = 16조합으로 재서 표②를 만들었다(64 B~64 KB 는 손실 0, RTT p50 0.9~1.2 ms; 1 MB 는 Fast DDS best_effort 99.8% 손실). 관제 쪽은 Mosquitto·수집기·TimescaleDB·Grafana 와 가상 장치 50대 1 Hz 를 docker compose 로 세웠다.
- "D3~D4 — 상태 머신(전이표), OTA 단계 배포·롤백 / 수집기 backlog, 장애 주입 4종, 판정 / CI 2단계(가짜 → 진짜 컨테이너)": 상태 머신을 if 문이 아닌 전이표로, OTA 5 → 50 → 100% 단계 배포와 서버 쪽 헬스 게이트 롤백, 수집기의 DB 장애 대비 backlog(메모리, 상한 200,000행), 장애 주입 4종(broker·db·collector·bad_firmware)과 판정 스크립트, 그리고 CI 잡 2개 구조. 이 묶음은 샌드박스(AI 쪽)에서 가짜 브로커·가짜 DB 로 논리만 검증된 채 넘어왔고, 진짜 첫 실행은 다음 묶음이다.
- "D5 11/04 — MuJoCo 백엔드 + SO-ARM100 / 장애 실측 1·2차 → 유실 53 → 0 / GitHub 공개, CI 3잡 초록": 물리 엔진 백엔드를 붙여 WSL 노드에 연결(어깨 처짐 1.1° 발견, E15·E16). 장애 실측 1차에서 측정 기준점을 고치자 유실이 0 이 아니라 53 / 1434 로 드러나고(E07), 원인 셋을 고친 2차에서 0 으로(E08). 같은 날 저장소를 GitHub 에 공개하고 CI 1차 실패(TimescaleDB 임시 서버) → 2차에서 3잡 초록.
- "D6 11/04 밤 — Pi 4 세팅(Ubuntu 24.04) / 일반 커널 기준값 4줄 / 열·스로틀 기록 스크립트": Raspberry Pi 4 에 Ubuntu 24.04 를 올리고, RT 커널로 바꾸기 **전**의 일반 커널 기준값(한가·부하 × cyclictest·jitter_bench = 4줄)을 먼저 쟀다 — 나중에 "일반이면 얼마였는데요?"를 막는 줄. 측정 전·후 온도와 스로틀 플래그를 `.meta` 에 적는 `scripts/lib_thermal.sh` 도 이때. Ubuntu One 가입 실패(장표 129)로 RT 커널은 다음 날로.
- "D7 11/05 — PREEMPT_RT: 커널 → 고정 → 격리 / 도구 불일치 검증 4회 / 기록 파이프라인 첫 실행, 실험 페이지 21장, 이 장표": 아침에 토큰을 받아 `6.8.0-2054-raspi-realtime` 커널로 바꾸고 한 번에 변수 하나씩 — 커널만(781 → 301 us), CPU 고정(→ 311, 효과 없음), 격리 isolcpus=3(→ 189). 표준 도구 cyclictest 가 132 로 2.3배 다르게 나와 변수를 하나씩 지우는 네 번의 실험(E19-d: A-1 일 0 us, A-2 cyclictest 같은 설정, B 우선순위 90, C 스레드 배치 -S)으로 274 vs 270 일치를 확인. 오후에 기록 파이프라인(rosbag2 MCAP 30초 → CSV → 요약) 첫 실행(E20), 실험 페이지 21장 정리, 그리고 이 장표 138장(그날의 수 — 지금은 실험 페이지 24장, 장표 145장).
- "D8 11/06 — 제출 서류(이력서·설계서, 저장소 밖) / 공개 문서 점검 — IP·계정·경로 제거 / ALLEX 48 자유도: 프로필 하나로, E21 → 500 Hz": 제출용 이력서·자기소개서와 포트폴리오 설계서 PDF 를 저장소 밖에서 썼고, 그 과정에서 공개 저장소의 로그·설정 안내에 Pi 의 사설 IP·계정 이름·개인 PC 경로가 남아 있던 것을 찾아 자리표시로 바꿨다(LOG 11/06). 그리고 지원 회사가 공개한 ALLEX 모델(48 자유도)을 프로필 `robots/allex.yaml` 하나로 같은 노드에 붙여 E21 을 돌렸다 — 물리 한 주기 p99 가 1 ms 의 46~62% 라 그 프로필의 주기를 모델 기본 걸음과 같은 500 Hz 로 정했다(장표 136).
- "11/10 ~11/11 — 릴리스 → 배포: 진짜 설치, 태그 → 카나리 → 게시(E22) / 운영 층을 클라우드(시드니)에, Pi 가 보고 시작 / 첫 릴리스 v0.9.0 · 왕복 290 ms(E23)": 서류를 내기 전 주에 한 이틀. D 꼬리표가 없다 — 2주 계획에 없던 일이라 날짜로만 적는다. 첫 줄: OTA 를 버전 문자열 흉내에서 진짜 파일 설치(내려받기 → sha256 → A/B 슬롯 → 자가 점검 → 전환)로 바꾸고, 태그 하나로 빌드 → 가상 50대 카나리 → 게시까지 가는 릴리스 워크플로를 만들었다(11/10, 장표 137~139). 둘째 줄: 브로커·수집기·DB·Grafana 를 AWS 시드니의 서버 한 대에 올리고, Pi 가 TLS 와 비밀번호로 접속해 1 Hz 보고를 시작했다(11/10 저녁, 장표 140). 셋째 줄: 11/11 오전에 시험 태그 `v0.9.0-rc1` 이 첫 실행에 게시까지 갔고 이어 정식 `v0.9.0` 을 게시했다. 같은 날 Pi ↔ 서버 왕복을 재다가 첫 값 707 ms 가 재는 방법이 만든 값임을 찾아 290 ms 로 확정했다(장표 142). 이 이틀에 나온 사고 9건은 장표 141.
- 각주 "D0~D4 는 날짜 표기가 '11/03 (D1)' 처럼 DECISIONS 의 꼬리표를 따른다(하루에 여러 D). 출처: docs/LOG.md, docs/HANDOVER.md": D 는 "Day" 를 뜻하는 계획상의 작업 묶음 번호다. 원래 하루에 하나씩 할 계획이었지만 11/03 하루에 D0~D4 의 코드 초안이 여러 묶음 나왔고(샌드박스 작업), 11/04 에 D5·D6, 11/05 에 D7 이 실행됐다. 그래서 LOG 와 DECISIONS 의 제목이 "2026-11-03 (D1)" 처럼 날짜와 D 를 같이 적는다.
- `다음 ▶` 다리 "작성 방식 — 2주에 이만큼이 가능했던 이유와, 그래서 생기는 질문('AI 가 다 한 거 아냐?')에 대한 답": 사흘에 이 분량은 혼자 손으로는 어렵다. 어떻게 가능했고 무엇이 작성자의 것인지가 장표 131.

## 3. 용어와 단위

- D0~D8: 계획의 작업 묶음 번호(Day 0 ~ Day 8). 달력 날짜와 1:1 이 아니다 — 11/03 에 D0~D4, 11/04 에 D5·D6, 11/05 에 D7, 11/06 에 D8. 11/10~11 에는 번호가 없다.
- 화살표 칸: 오른쪽 끝이 뾰족한 오각형 도형. 시간 순서를 나타낼 때 쓴다(칸이 일곱 이하일 때는 화살촉 모양인 셰브론을 썼다).
- 태그(tag) · 릴리스(release): 저장소의 한 커밋에 붙이는 이름표(`v0.9.0`)와, 그 태그로 만들어 게시한 패키지 묶음. 이름에 `-rc1` 처럼 `-` 가 있으면 시험판(pre-release)이다.
- 카나리(canary): 전체에 내보내기 전에 일부(여기서는 가상 50대의 5 %)에 먼저 깔아 보는 것.
- 뼈대(skeleton): 돌아가는 최소 구조. 링 버퍼 + 루프 + 측정기만 있고 ROS 2·로봇은 없는 상태.
- 16조합: 표②의 측정 행 수. 2 구현체 × 2 신뢰성 × 4 메시지 크기.
- 가상 50대: 진짜 장치 대신 파이썬 프로세스가 흉내 내는 로봇 50대(`fleet/agent/virtual_fleet.py`), 1 Hz 로 상태를 보낸다.
- 기준값(baseline): 바꾸기 전의 값. RT 커널 효과를 말하려면 일반 커널 값이 먼저 있어야 한다.
- 실험 페이지 21장: 11/05 의 수 — `docs/experiments/E01 ~ E20`(E14·E17 없음, E19 는 a/b/c/d 네 장). 그 뒤 E21(ALLEX) · E22(릴리스 → 배포) · E23(왕복)이 더해져 지금은 24장이다.

## 4. 쉬운 예시

- 비유: 집을 짓는 공정표. D0 기초(뼈대), D1~D2 골조와 배선(노드·DDS·관제), D3~D4 안전장치와 점검 체계(상태 머신·OTA·장애 주입·CI), D5 입주 점검에서 문제 발견·수정(유실 53 → 0), D6~D7 다른 터(Pi)에 같은 집을 세워 땅이 달라도 서는지 확인(일반 → RT 커널). 11/10~11 은 입주 뒤의 두 가지 — 고칠 부품을 안전하게 갈아 끼우는 길(릴리스 → 배포)과 24시간 지켜보는 관리실(클라우드 운영 층). 설계도(DECISIONS)와 사고 일지(LOG)는 공정마다 적었다.
- 숫자 예시: D0 의 WSL 측정 max 921 us 는 1 ms 주기의 92% — 거의 한 주기를 놓친 값. D7 의 Pi RT 격리 max 189 us 는 주기의 19%. 같은 1 kHz 루프 코드가 환경에 따라 이렇게 다르고, 그 차이를 사흘 동안의 줄들이 하나씩 설명한다.
- "하루에 여러 D": 11/03 하루에 D0~D4 다섯 묶음 — 코드 초안은 AI 가 샌드박스에서 빠르게 냈지만 **진짜 실행**(WSL 실측)은 D0·D1·D2 만 그날 됐고 D3~D4 는 11/04 에 처음 돌았다(LOG "D3~D5, 샌드박스 작업" 항목). 그래서 D5 에 사고가 몰렸다.

## 6. 자주 하는 오해·함정

- "D8 = 8일째"라는 오해: D 는 계획의 묶음 번호다. 실제로는 나흘(11/03~11/06)이고, 그 뒤 이틀(11/10~11)은 번호 없이 날짜로 적는다. 발표에서 "D7" 이라 말하면 반드시 "11/05" 를, "D8" 은 "11/06" 을 붙인다.
- "11/03 에 D0~D4 를 다 돌렸다"는 오해: 코드 초안은 나왔지만 D3~D4(상태 머신·OTA·장애 주입·CI)의 **진짜 첫 실행**은 11/04 다. 그래서 11/04 에 사고 6건이 몰렸다(장표 128).
- "순서가 실시간 → 관제 → 물리 → Pi 로 깔끔했다"는 인상: 실제로는 11/04 하루에 관제 실측·CI·MuJoCo·Pi 세팅이 겹쳤고, Ubuntu One 장애로 RT 커널이 하루 밀렸다. 일정표는 요약이고 LOG 가 원문이다.
- 기준값 4줄을 RT 커널 **뒤에** 재면 안 된다 — 커널을 바꾸면 되돌리기 어렵고, 같은 조건의 "전" 값이 없어진다. D6 이 D7 앞에 있는 이유.

## 7. 면접 한 문장
