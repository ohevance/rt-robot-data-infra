# 장표 070 — ③ 그림 — 수집기 안의 두 스레드와 1초 묶음: 받는 쪽은 넣기만, 1초마다 묶어서 DB 로, 안 되면 들고 있는다
*위치: 2부 데이터의 길 · ③ 수집기 · ② 그림 — 두 스레드와 1초 묶음*

## 1. 이 장표가 왜 있나
바로 앞 장표(069, ③ 들머리)에서 수집기의 문제를 정했다: 초당 50개(최대 수백 개)의 메시지를 DB 에 빠르게 넣되, DB 가 죽어도·수집기 자신이 죽어도 잃지 않아야 한다. 기준은 "DB 중단 중 유실 0, 종료 때 마지막 1초 보존, 한 번에 하나만 뜬다"였다. 그래서 생기는 질문: 그 기준을 만족시키는 수집기는 안에서 **어떻게 생겼나**? 이 장표는 코드로 들어가기 전에 수집기 한 프로세스 안의 **스레드 두 개**와 그 사이를 흐르는 데이터(pending → batch → backlog → DB)를 도형으로 그린 것이다. 다음 세 장표(071~073)의 코드는 이 그림의 상자 하나하나를 그대로 펼친 것이다.

## 2. 장표를 하나씩 읽기
그림은 왼쪽에서 오른쪽으로 읽는다. 큰 회색 상자 두 개가 "스레드"이고, 그 안의 작은 상자가 함수, 육각형이 데이터가 쌓이는 자리, 마름모가 판단, 원통이 데이터베이스다.

- 왼쪽 큰 회색 상자 "paho 콜백 스레드": paho 는 파이썬 MQTT 라이브러리 이름이고, 브로커에서 메시지가 올 때마다 이 라이브러리가 **자기 스레드**에서 우리 함수를 불러 준다. 이 스레드는 DB 를 절대 만지지 않는다 — 메시지가 밀려 들어올 때 DB 가 느리면 수신이 막히기 때문이다.
- 그 안의 파란 상자 "on_message(msg)": 네 줄이 하는 일 순서대로. ① 토픽 이름(`fleet/<장치>/telemetry` 또는 `.../status`)을 쪼개 어느 장치의 무슨 메시지인지 안다. ② `parse_telemetry` 가 메시지 안의 측정 시각(ts_ns, 나노초)과 지금 도착 시각의 차이를 계산한다 = **전달 지연(ms)**. ③ `with lock:` 잠금을 잡고 `pending_rows` 목록 끝에 행 하나를 붙인다 — 잠금을 잡는 이유는 다른 스레드(메인)가 같은 목록을 통째로 가져가기 때문이다. ④ status 메시지 중 `retain=1`(브로커가 "보관"해 둔 과거 값)은 지금 일어난 사건이 아니므로 events 표에 넣지 않는다. 이 네 번째 줄은 11/04 사고(보관된 유언이 재구독 때 다시 내려와 오프라인 이벤트가 두 배로 세졌던 일)에서 나온 규칙이다.
- 화살표 "append" → 노란 육각형 "pending (이번 1초 치)": 아직 DB 에 안 간, 이번 1초 동안 모인 행들. 육각형은 "쌓이는 자리"를 뜻한다.
- 화살표 "1초마다" → 오른쪽 큰 회색 상자 "메인 스레드 — 1초마다 flush_once()": 수집기를 시작한 바로 그 스레드가 1초에 한 번 `flush_once` 를 부른다. 1초 묶음(batch)의 박자가 여기서 나온다.
- 민트 상자 "take_batch: pending 을 통째로 Batch 하나로 (락 한 번)": 잠금을 **한 번만** 잡고 pending 목록 전체를 떼어 와 빈 목록으로 바꿔 놓는다. 행마다 잠금을 잡지 않으므로 콜백 스레드를 거의 막지 않는다. 같은 자리에서 "온라인 장치 수"(최근 5초 안에 본 장치)도 센다.
- 화살표 "append" → 노란 육각형 "backlog (묶음 목록), 상한 200,000행 넘으면 오래된 것 버림": 방금 만든 묶음을 backlog **끝**에 붙인다. DB 가 멀쩡하면 backlog 에는 이 묶음 하나뿐이고 바로 비워진다. DB 가 죽어 있으면 1초마다 묶음이 하나씩 쌓인다. 200,000행은 50대 × 1 Hz 로 약 66분치 — 메모리를 지키는 상한이고, 넘으면 가장 오래된 묶음부터 버리되 버린 행 수(backlog_dropped)를 센다.
- 마름모 "drain: 맨 앞 묶음 write_db(COPY) 성공?": backlog 의 **가장 오래된** 묶음부터 DB 에 COPY(여러 행을 한 번에 넣는 PostgreSQL 명령)로 넣어 본다. 마름모는 판단 — 성공했나?
- 화살표 "예" → 민트 상자 "예: pop → 다음 묶음(순서 유지)": 성공하면 그 묶음을 backlog 에서 빼고(pop) 다음 묶음으로 넘어간다. 점선 화살표 "다음 묶음"이 다시 backlog 로 돌아가는 고리다 — backlog 가 빌 때까지 반복.
- 화살표 "아니오" → 붉은 상자 "아니오(DB 죽음): db_errors++, 연결 버리고 멈춤 → 다음 초에 같은 묶음부터": 실패하면 오류 수를 하나 올리고 DB 연결을 버린 뒤 **거기서 멈춘다**. 다음 초의 flush_once 가 다시 같은 묶음부터 시도한다. 그래서 순서가 지켜지고, 죽은 동안의 데이터는 메모리에 남는다.
- 화살표 "COPY" → 회색 원통 "TimescaleDB": 데이터가 최종적으로 들어가는 곳. 원통은 데이터베이스의 관례 기호다.
- 흰 문서 모양 "통계 한 줄 write_stats — msgs/s · insert_ms · 지연 p50/p95/max · online · backlog_rows · db_errors": take_batch 에서 점선으로 이어진다. 1초마다 통계 한 줄을 collector_stats 표에 넣고 화면에도 찍는다. 운영자가 "backlog_rows 가 늘어난다 = DB 가 죽었다"를 이 줄로 본다(5부의 개발 PC '정상 신호' 표와 같은 줄).
- 아래 글 상자 "왜 1초 묶음 + COPY": 300대 × 1 Hz 를 행마다 INSERT 하면 DB 왕복이 초당 300번, 묶으면 초당 1번. 대신 DB 에 보이기까지 최대 1초가 더 걸린다(표③ 비고에 적어 둔 설계상의 지연). 11/04 실측에서 DB 를 10초 죽였더니 뒤늦게 570행이 들어가고 유실은 0 / 1341 이었다 — backlog 가 실제로 일한 증거.
- 맨 아래 legend "소스 위치": 이 그림의 상자가 어느 줄인지. on_message 153-181, take_batch 184-205, flush_once 207-232, enforce_backlog_limit 234-240, drain_backlog 241-255, 상한 상수 MAX_BACKLOG_ROWS 60줄, 종료 처리 request_stop 325 / shutdown 343-353(11/10~11 에 파일이 바뀌어 11/05 의 번호에서 3~8줄씩 밀렸다), 단일 인스턴스 잠금은 별도 파일 `fleet/common/single_instance.py`.

## 3. 용어와 단위
- 스레드: 한 프로그램 안에서 동시에 도는 실행 줄기. 여기서는 "받는 줄기"와 "DB 에 넣는 줄기"가 따로 있어 한쪽이 느려도 다른 쪽이 막히지 않는다.
- paho: 파이썬용 MQTT 클라이언트 라이브러리(paho-mqtt). 메시지 수신을 자기 스레드에서 처리하고 우리 콜백(on_message)을 부른다.
- 콜백: 라이브러리가 "일이 생기면 이 함수를 불러 달라"고 등록해 둔 우리 함수.
- pending / batch / backlog: 아직 처리 안 된 것 / 1초치 묶음 / 넣지 못해 들고 있는 묶음들의 줄.
- 잠금(lock): 두 스레드가 같은 목록을 동시에 고치지 못하게 막는 자물쇠. 잠금을 잡는 횟수가 적을수록 서로 덜 기다린다.
- COPY: PostgreSQL 의 묶음 적재 명령. 행마다 INSERT 하는 것보다 왕복이 훨씬 적다.
- TimescaleDB: PostgreSQL 에 시간 데이터용 기능(하이퍼테이블 = 시간으로 자동 분할되는 표)을 더한 것.
- 전달 지연: 장치가 측정한 시각(ts_ns, 나노초 = 10억분의 1초)과 수집기 도착 시각의 차이. ms(밀리초, 1,000분의 1초)로 적는다. 같은 PC 시계라 뺄 수 있다.
- p50 / p95 / max: 1초 동안 들어온 지연 값들을 줄 세웠을 때 가운데 값 / 95% 지점 값 / 가장 큰 값.
- Hz: 1초에 몇 번. 50대 × 1 Hz = 초당 50개 메시지.

## 4. 쉬운 예시
우체국 비유: 창구 직원(paho 콜백 스레드)은 편지를 받아 **바구니(pending)** 에 넣기만 한다. 1분마다 배달원(메인 스레드)이 바구니를 통째로 들고(take_batch, 바구니를 빈 것으로 바꿔 놓고) 트럭(backlog)에 싣는다. 창고(DB) 문이 열려 있으면 바로 내려놓고(COPY), 문이 닫혀 있으면 트럭에 실은 채로 기다렸다가 다음 분에 다시 간다. 트럭이 꽉 차면(200,000행) 가장 오래된 상자부터 버리고 버린 수를 적는다.

숫자 예시: 50대가 1초에 한 개씩 보내면 1초 묶음에 약 50행. DB 가 10초 죽으면 묶음 10개(≈500행)가 backlog 에 남았다가 DB 가 돌아온 첫 초에 오래된 것부터 전부 들어간다 — 11/04 실측에서 "뒤늦게 들어간 행 570"이 그 숫자다(묶음 경계 때문에 500 보다 조금 많다).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 상한 200,000행 — `fleet/collector/collector.py` 60줄 `MAX_BACKLOG_ROWS = 200000` (주석에 "50대 1 Hz 면 약 66분, 300대면 약 11분").
- 확인: db 장애 10초 → 유실 0 / 1341, 뒤늦게 들어간 행 570, 복구(backlog 0) 1.4초 — `docs/measurements/table3.md` 표③-2 db 줄(2026-11-04 02:39).
- 확인: 함수 줄 번호 — `grep -n "def on_message\|def take_batch\|def flush_once\|def enforce_backlog_limit\|def drain_backlog\|def request_stop\|def shutdown" fleet/collector/collector.py`.
- 확인: "300대 × 1 Hz = 왕복 300번/초 → 묶으면 1번" — `docs/DECISIONS.md` 11/03 (D2) "수집기는 1초 묶음 + COPY".
- 추정: "최대 수백 개"는 300대 설계 가정에서 나온 말이고, 실측은 50대(WSL2)와 10대(CI 러너)뿐이다.
- 다시 보기: 수집기를 띄우고(`python3 fleet/collector/collector.py --qos 1`) 1초마다 찍히는 통계 줄에서 `backlog=0 db_err=0` 을 보면 이 그림의 정상 상태다. `docker compose -f fleet/docker-compose.yml stop db` 로 DB 를 멈추면 backlog 가 1초마다 약 50씩 늘고, `start db` 뒤 한 번에 0 으로 돌아온다.

## 6. 자주 하는 오해·함정
- "DB 가 죽으면 데이터가 날아간다"고 생각하기 쉽지만, 죽은 동안의 데이터는 backlog(메모리)에 남는다. 날아가는 것은 **상한을 넘긴 가장 오래된 묶음**뿐이고 그 수를 센다(backlog_dropped).
- "메모리에 두는데 수집기 자체가 죽으면?" — 그래서 QoS 1 지속 세션(브로커가 대신 보관)과 곱게 종료(shutdown 이 마지막 flush_once 를 한다)가 따로 있다. 074 장표가 그 길이다.
- 11/04 사고: `/proc/<pid>/exe` 로 수집기를 재시작하니 venv 를 잃고 바로 죽었다 → `/proc/<pid>/environ` 의 VIRTUAL_ENV·PATH 로 같은 환경에서 재시작하도록 고쳤다(장애 주입 도구 쪽).
- 11/04 사고: 수집기 두 개가 같은 client_id 로 떠서 2초마다 서로 밀어냈다 → 단일 인스턴스 잠금(flock)을 넣었다. 그림에는 legend 로만 적혀 있다.
- "1초 묶음이니 지연이 1초 늘어난다"는 맞다. 그래서 표③의 전달 지연은 "수집기 도착까지"이고 "DB 에 보일 때까지"는 최대 1초가 더 걸린다고 비고에 써 두었다 — 숨기지 않는다.

## 7. 면접 한 문장
"수집기는 받는 스레드가 넣기만 하고 메인 스레드가 1초마다 묶어 COPY 로 넣습니다. DB 가 죽으면 묶음을 메모리 backlog 에 순서대로 들고 있다가 돌아오면 오래된 것부터 넣고, 상한을 넘기면 버린 수를 셉니다 — 11/04 에 DB 를 10초 죽였을 때 570행이 뒤늦게 들어가고 유실은 0 이었습니다."
