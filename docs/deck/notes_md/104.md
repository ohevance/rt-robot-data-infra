# 장표 104 — 숫자 한눈에 ② — 관제·장애·OTA·물리 (WSL2 + CI 러너) — 표③과 물리가 답하는 것
*위치: 4부 출발 · 숫자 한눈에 ② 관제·물리*

## 1. 이 장표가 왜 있나
앞 장표(103)는 공고 ①(실시간)의 숫자 넷이었다. 이 장표는 나머지 — 공고 ②(관제·업데이트), ③(스트리밍·기록), ④(시뮬레이션·CI) — 를 숫자 넷으로 접는다. 제목에 "WSL2 + CI 러너"를 적은 것은 103 과 짝을 맞추기 위해서다: 이 숫자들은 개발 PC 의 WSL2 와 GitHub 의 CI 러너에서 나왔고, 진짜 하드웨어 실측(Pi 4)이 아니다. 하지만 관제·장애·OTA·물리의 숫자는 **지연의 절대값**이 아니라 "잃었나(0 인가)", "되돌렸나(몇 대, 몇 초)", "예산의 몇 % 인가" 같은 것이어서 WSL2 에서도 의미가 있다. 4부의 마지막 장표이고 `다음 ▶` 가 5부(환경)로 넘어간다.

## 2. 장표를 하나씩 읽기
큰 숫자 네 개를 왼쪽에서 오른쪽으로.

- KPI 1 "0 / 1400 / 브로커 10초 중단 뒤 유실 (전 장치 복귀 2.9초)": 가상 장치 50대가 1 Hz 로 보내는 중에 MQTT 브로커 컨테이너를 10초 멈췄다 살렸다. 그 창에서 장치들이 만든 1,400개 중 DB 에 없는 것 0개. 50대가 전부 다시 붙는 데 2.9초.
- KPI 2 "508 / 1312 / 같은 장애, QoS 0 이면 유실 (QoS 1 지속 세션은 0 / 1311)": 이번엔 **수집기**를 10초 죽였다. 보호 없이(QoS 0) 보내면 1,312개 중 508개를 잃고(예측 500 = 50대 × 10초), QoS 1 + 지속 세션이면 브로커가 수집기 몫을 보관해 줘서 0 / 1311. 같은 장애에서 설정 하나가 508 과 0 을 가른다.
- KPI 3 "3 / 50, 1.0초 / 나쁜 펌웨어: 닿은 장치 / 롤백 시간 (5% 단계 헬스 게이트)": 고장 나는 펌웨어를 50대에 단계 배포하면 첫 단계(5% = 3대)에서 헬스 게이트가 잡고 1.0초 안에 이전 버전으로 되돌린다. 47대는 명령을 받은 적도 없다(2부 장표 078).
- KPI 4 "0.9% · 46% / MuJoCo 물리 한 주기 p99 / 1 ms 예산 — 6축 8.5 us · ALLEX 48축 458 us (러너)": 1 ms 제어 주기 안에서 진짜 물리(중력·접촉·관절 한계)를 한 걸음 계산하는 비용. 6축 팔(SO-ARM100)은 p99 8.5 us — 예산의 0.9%. 지원 회사가 공개한 ALLEX(48 자유도, 11/06 에 더함)는 같은 러너에서 p99 457.8 us — 예산의 46%. 둘 다 CI 러너에서 1 kHz 2,000주기 측정. 같은 코드에 모델만 바뀐 것인데 비용이 50배 넘게 차이 나는 이유는 자유도 8배에 손가락 접촉·등식 제약이 더해져서로 본다(추정, E21).
- 글머리표 1 "유실 0 은 처음부터 0 이 아니었다 — 측정 맹점을 고치자 53 이 나왔고, 원인 셋(브로커 재시작 경쟁·종료 순간·큐 상한)을 추적해 설정과 종료 처리로 0 을 만들었다 (2부 ⑦⑧, 3부 표③ 사슬 장표 97~)": KPI 1 의 0 에 붙는 각주다. 처음 잰 0(E06)은 유실 SQL 의 기준점이 틀려 보지 못한 0 이었고, 고치자 53 / 1434(E07). 원인은 브로커가 재시작하며 지속 세션을 잃는 것(persistence false), 수집기 종료 순간의 장치당 1개, 브로커 큐 상한 20,000. 앞 둘을 고쳐 0(E08).
- 글머리표 2 "물리가 들어오자 어깨 관절이 목표보다 0.019 rad(1.1°) 처졌다 = 중력. 기록 파이프라인의 자동 요약에도 같은 숫자가 나온다 (1부 단계 7·9)": KPI 4 의 각주. 물리를 넣었더니 수식 모델(SimLag)에서는 안 보이던 것이 보였다 — 팔 무게가 걸린 어깨 Pitch 가 목표 −0.200 에 못 미치는 −0.180 rad. 11/05 기록 파이프라인의 추종 오차 요약표에도 shoulder_lift 평균 0.0191 rad 로 같은 숫자가 자동으로 나왔다 — 두 길(눈으로 본 것, 기록이 센 것)이 일치한다.
- 글머리표 3 "같은 장애 4종을 GitHub 러너(10대 2 Hz)에서 매 push 마다 다시 돌린다: 유실 0·0·0, 롤백 0.4초 (6부)": WSL2 의 숫자를 다른 환경에서 재현한다. 장치 10대 2 Hz 로 줄였지만 모양은 같다 — 브로커 0 / 318, DB 0 / 286, 수집기(QoS 1) 0 / 280, 나쁜 펌웨어 롤백 0.4초(1 / 10 대).
- 글머리표 4 "회사가 공개한 ALLEX 모델(48 자유도)은 프로필 하나로 붙었고 제어 코드는 안 바뀌었다(11/06). 물리 비용은 6축의 약 70~100배라 제어 주기를 모델 기본 걸음인 500 Hz 로 — 실측 p99 러너 510 us(2 ms 의 26%), WSL 1,000 us(50%) (7부 장표 136)": 로봇을 바꾸는 일이 설정 파일 하나였다는 1부 단계 6 의 주장이 회사의 로봇으로 확인됐다는 줄이고, 동시에 "물리가 1 ms 의 절반 가까이를 먹으면 주기를 500 Hz 로 낮춘다"는 결정(DECISIONS 11/06)을 숫자와 함께 적은 줄이다. 70~100배는 같은 PC(WSL)에서 6축 4.9 / 6.3 / 20.8 → 48축 336 / 622 / 1,785 us 의 배수.
- 글머리표 5 "11/10~11 보탬 — OTA 가 흉내에서 진짜 설치로: 태그 하나로 러너가 가상 50대에 14초에 깔고, 깨진 빌드는 3 / 50 에서 거부해 1.0초에 되돌린다. 실물 Pi 는 한 번에 약 1초. 운영 층은 시드니 서버에서 24시간 — Pi 14.8시간 53,167건 유실 0, 서버까지 왕복 290 ms (7부 장표 137~142)": 본편(11/05) 뒤에 생긴 숫자 다섯을 한 줄로 접었다. ① KPI 3 의 "3 / 50, 1.0초"는 버전 문자열만 바꾸는 흉내였다 — 11/10 부터는 진짜 파일을 내려받아 설치하고, 릴리스 카나리(v0.9.0)가 러너의 가상 50대에 14.62초에 깔았다(5 → 50 → 100 %, 헬스 대기 3초 × 3 포함). ② 일부러 깨뜨린 패키지는 첫 단계 3대가 자가 점검에서 거부했고 1.0초에 되돌렸다 — KPI 3 과 같은 숫자지만 이번에는 장치가 **켜 보기 전에** 걸렀다. ③ 실물 Pi 4 가 GitHub 에서 받아 설치하는 데 한 번에 0.98~1.62초(그중 자가 점검 0.67초). ④ 브로커·수집기·DB·Grafana 를 시드니의 서버 한 대에 올려 24시간 켜 두었고, Pi 가 1 Hz 로 보낸 53,167건을 서버가 전부 받았다(14.77시간, 일련번호로 셈). ⑤ Pi ↔ 서버 MQTT 왕복은 p50 290 ms. 글자 크기가 12 에서 11 로 줄어든 것은 이 한 줄이 늘어서다.

## 3. 용어와 단위
- 브로커(MQTT broker): 장치와 수집기 사이의 우체국. Mosquitto 컨테이너.
- 유실 "a / b": 그 장애 창에서 장치가 만든 b개 중 DB 에 없는 a개. seq(일련번호)로 센다.
- QoS 0 / 1: 보내고 잊음 / 받았다는 확인(PUBACK)까지. 지속 세션(clean_session=False): 수집기가 없는 동안 브로커가 QoS 1 메시지를 보관.
- 헬스 게이트·롤백: 단계 배포 후 상태(ok/fault)를 보고 되돌리는 것. "닿은 장치" = 나쁜 펌웨어 명령을 받은 장치 수.
- p99: 100번 중 99번은 이 값 이내. 8.5 us = 1 ms 의 0.85% ≈ 0.9%.
- rad(라디안): 각도 단위. 0.019 rad × 57.3 ≈ 1.1°.
- SO-ARM100: MuJoCo Menagerie 의 6축 팔 모델(실물 SO-101 과 같은 계열).
- CI 러너: GitHub 가 push 마다 빌려 주는 새 가상 컴퓨터(ubuntu-24.04).

## 4. 쉬운 예시
우체국 비유(KPI 1·2): 우체국(브로커)이 10초 문을 닫아도 장치가 편지를 들고 있다가 다시 보내니 잃는 것이 없다(0 / 1400). 반대로 받는 사람(수집기)이 10초 자리를 비울 때, 등기(QoS 1 + 사물함 = 지속 세션)로 보냈으면 우체국이 보관해 주지만 일반 우편(QoS 0)은 문 앞에 두고 가서 508통이 사라진다.

숫자 예시(KPI 4): 1 ms = 1,000 us 예산에서 물리 8.5 us 를 쓰면 991.5 us 가 남는다. 제어 계산과 발행까지 합친 노드 안 work_us 의 p99 는 WSL 에서 145 us 였으니 그래도 85% 가 남는다.

## 6. 자주 하는 오해·함정
- "유실 0" 을 그대로 믿으면 안 된다 — 이 저장소의 0 은 "틀린 0(E06) → 53(E07) → 고친 0(E08) → 다른 환경에서도 0(E13)"의 이력이 있는 0 이다. 그 이력이 없으면 0 은 가장 위험한 숫자다.
- KPI 2 의 508 은 실패가 아니라 **의도한 비교**다. "보호가 없으면 이만큼 잃는다"를 숫자로 남겨 QoS 1 의 가치를 보여 준다(판정 규칙도 qos0 이면 유실 > 0 이 정상).
- 롤백 1.0초는 "롤백 결정 → 3대 전부 이전 버전·ok"까지이고, 사고 발생부터 끝까지는 적용 대기 + 헬스 게이트를 더해 약 5~6초다.
- 0.9% 는 CI 러너(x86 서버급 CPU) 값이다. Pi 4 나 로봇의 임베디드 CPU 에서는 더 걸린다 — 그래서 "예산의 몇 %" 로 말하고 절대 us 로 자랑하지 않는다.
- 글머리표 5 의 숫자는 KPI 넷과 **잰 곳이 다르다**. KPI 는 WSL2 와 CI 러너, 글머리표 5 는 러너(가상 50대) · 실물 Pi · 시드니 서버다. 특히 290 ms 는 한국 ↔ 시드니의 거리 값이라 WSL 의 전달 지연 0.9 ms 와 나란히 놓고 비교하면 안 된다.
- "Pi 는 한 번에 약 1초"는 시험용 슬롯에 rc1 패키지를 세 번 설치한 값이다. 자율 업데이트(밤 03~05시)로 v0.9.0 을 받은 기록은 이 장표를 만든 시점에 아직 없다.
- 어깨 처짐 1.1° 는 버그가 아니라 물리가 **맞게** 보여 준 것이다. 실물에서도 같은 자리에서 나는 일이고, 중력 보상이 필요하다는 숫자 근거(지원 후 보류 항목).

## 7. 면접 한 문장
"관제 쪽은 브로커 10초 중단에 유실 0 / 1400, 같은 장애를 QoS 0 으로 두면 508 을 잃는다는 것까지 표로 남겼고, 나쁜 펌웨어는 3대에서 1초 안에 되돌렸습니다 — 그리고 물리는 1 ms 의 0.9% 로 싸면서 어깨의 중력 처짐 1.1° 라는 새 사실을 보여 줬습니다."
