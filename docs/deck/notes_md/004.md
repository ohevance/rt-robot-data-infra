# 장표 004 — 목차 — 부마다 '질문 → 답 → 장표 번호'
*위치: 0 · 목차(표)*

## 1. 이 장표가 왜 있나
앞 장표(003)는 전체를 순서도로 보여 줬지만 그림이라 "몇 번 장표부터 몇 번까지가 1부인가"를 찾기 어렵다. 이 장표는 같은 내용을 표로 옮겨 부마다 (이 장이 답하는 질문, 답의 요약, 장표 번호 범위)를 한 줄씩 적는다. 발표 중 "3부는 어디부터죠?"라는 질문에 바로 답하기 위한 색인이고, 설명 문서(이 파일들)도 같은 번호라서 "N번 장표의 문서"를 찾는 기준표이기도 하다.

## 2. 장표를 하나씩 읽기
열(헤더)의 뜻부터: "부" = 장 이름, "이 장이 답하는 질문" = 앞 장을 다 보고 나면 생기는 질문, "답(요약)" = 그 장의 내용 한 줄, "장표" = 시작–끝 번호.

- 1부 로봇을 움직이는 길 (5–58, 54장): 질문 "명령 하나가 로봇의 움직임이 되기까지 무엇을 거치나? (왕초보 → 핵심 소스 코드)". 답: 10단계, 단계마다 들어온 것 → 문제 → 기준 → 코드(파일:줄) → 결과 → 판단. 시험은 번호만 적고 3부로. 가장 긴 부인 이유: 단계마다 들머리 + 그림 + 코드 여러 장이 붙기 때문.
- 2부 데이터의 길 (59–85, 27장): 질문 "로봇(수십 대)의 숫자를 잃지 않고 서버까지 가져오고, 장애·업데이트를 견디나?". 답: 8단계 — 에이전트 → 브로커 → 수집기 → DB·Grafana → OTA → 장애 주입·판정·진단 (코드 포함).
- 3부 검증 (86–100, 15장): 질문 "1·2부에서 '확인 → 장표 N' 으로 미뤄 둔 기준들을 정말 넘었나? 숫자는 어떻게 나왔나?". 답: 단계 순서대로 표② DDS → 표① 1 ms 루프(일반 → RT → 격리) → 물리 → 표③ 관제(유실 53 → 0).
- 4부 출발 (101–104, 4장): 질문 "이 길과 숫자가 공고 네 항목을 다 덮나? 무엇을 숫자로 증명했나?". 답: 공고 ↔ 산출물 ↔ 수치 ↔ 상태 한 표 · 숫자 한눈에 ①②. "출발"이라는 이름은 원래 이 일의 출발점(채용 공고)이라는 뜻 — 순서상으로는 뒤에 온다.
- 5부 어디서 (105–110, 6장): 질문 "그 숫자는 어디서, 어떤 조건에서 만들었고 어디까지 믿나?". 답: 네 곳(개발 PC · Pi 4 · GitHub CI · 작업본)과 각 곳의 '정상 신호'.
- 6부 믿을 수 있나 (111–123, 13장): 질문 "이 숫자들을 누가, 무엇으로, 언제 다시 재나?". 답: 측정 스크립트(온도·부하 기록) · 테스트 31건 · CI 3잡 매 push.
- 7부 왜·사고·방식 (124–142, 19장): 질문 "왜 이렇게 만들었고(버린 대안), 무엇이 깨졌고, 어떻게 일했나?". 답: 결정 25건 · 사고 11건 · 2주 일정 · AI 와 일한 방식 · 남은 일 · 용어 · 덧붙임 7장(11/06 ALLEX · 11/10~11 릴리스 → 배포 3장 · 클라우드 운영 층 · 사고 · 왕복 290 ms). 덧붙임은 본편(11/05) 뒤에 한 일이라 번호를 흔들지 않게 7부 끝에 모았다.
- 끝 (143–145, 3장): 질문 "그래서 로봇은 어떻게 움직이나?". 답: 한 장 요약 — 명령 50 Hz 에서 관제 대시보드까지, 숫자와 함께.
- 아래 각주: 장표 번호는 오른쪽 아래 숫자와 같고, 설명 문서도 같은 번호(예: 37번 장표 → notes/037.docx). 1·2부 안의 '확인 → 장표 N' 도 같은 번호 체계다.

## 3. 용어와 단위
- 장표 번호: 슬라이드 오른쪽 아래의 쪽 번호. 1부터 145까지.
- 공고: 지원하는 회사의 채용 공고. 네 항목(실시간 Linux·ROS 2/DDS, 로깅·모니터링·시각화·업데이트, 센서 스트리밍·로깅·전처리, 시뮬레이션·CI)이 4부의 표 첫 열이다.
- OTA: Over-The-Air — 무선으로 장치 소프트웨어를 갱신하는 것.
- CI 3잡: GitHub Actions 에서 push 마다 도는 작업 셋(rt_core · fleet_integration · mujoco).
- Pi 4: Raspberry Pi 4, 실시간 커널로 표①을 잰 보드.

## 4. 쉬운 예시
비유: 책 앞의 목차와 같은데, 각 장 제목 옆에 "이 장을 왜 읽나(질문)"가 한 줄 더 붙어 있는 꼴이다. 숫자 예시: 1부 단계 4 들머리(22번)에서 "확인 → 3부 장표 89~95" 를 보면 이 표에서 3부가 86–100 임을 확인하고, 89번 장표의 설명 문서 `notes/089.docx` 를 열면 된다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 각 범위 — `docs/deck/SLIDES.md` 의 번호와 부 열. 빌드 때 `make_slides.py` 가 `{{range:N}}` 자리를 실제 범위로 채우므로 장표를 끼워도 표가 자동으로 맞는다.
- 확인: 총 145장 — `python3 -c "import json;print(len(json.load(open('docs/deck/build/slides.json'))))"`.
- 확인: 설명 문서 수 — `ls docs/deck/notes | wc -l`.

## 6. 자주 하는 오해·함정
- "4부 출발"이 맨 앞이어야 하지 않나? — 이름은 출발점(공고)이지만, 왕초보에게는 과정을 먼저 보여 주는 것이 낫다는 결정(7부 결정 기록, `docs/DECISIONS.md` 2026-11-05 (장표))에 따라 뒤에 둔다.
- 장표 수가 많다고 전부 발표하는 것이 아니다. 발표는 1부 중심으로 하고 나머지는 질문이 나올 때 번호로 찾아가는 색인 역할을 한다(`docs/deck/README.md` §2).

## 7. 면접 한 문장
"목차 표의 둘째 열이 전부 질문입니다 — 각 부는 앞 부를 다 보고 나면 생기는 질문 하나에 답하도록 짜여 있어서, 어느 장표에서 질문이 나와도 '그 답은 N부 M번'으로 바로 갈 수 있습니다."
