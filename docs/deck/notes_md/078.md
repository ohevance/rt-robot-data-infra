# 장표 078 — ⑥ 그림 — 나쁜 펌웨어 한 번의 흐름(순서도): 5% 세 대에서 헬스 게이트가 잡고 1초 안에 되돌린다, 47대는 명령을 받은 적도 없다
*위치: 2부 데이터의 길 · ⑥ OTA · ② 그림 — 나쁜 펌웨어 한 번의 흐름*

## 1. 이 장표가 왜 있나
앞 장표(077, ⑥ 들머리)는 OTA(무선 펌웨어 갱신)의 문제와 기준을 정했다: 50대에 한 번에 내리면 나쁜 펌웨어가 50대를 고장 내니, 5% 부터 단계적으로 내리고 서버가 건강을 보고 되돌려야 한다. 그러면 "나쁜 펌웨어 한 번"은 **시간 순서로** 정확히 어떻게 흘러가나? 이 장표는 그 한 번을 순서도(시퀀스 다이어그램)로 그린 것이다. 다음 세 장표(079~081)의 코드 run_stage · rollback 은 이 그림의 서버 쪽 화살표를 그대로 코드로 옮긴 것이다.

## 2. 장표를 하나씩 읽기
그림(`img/ota_seq.png`, 원본 `build/diagrams/ota_seq.mmd`)은 세로줄 네 개(참여자)와 위에서 아래로 내려가는 화살표로 되어 있다. 참여자는 왼쪽부터 "rollout.py (서버)", "브로커", "장치 3대 (5% 단계)", "나머지 47대".

- 화살표 1 (서버 → 브로커) "텔레메트리 3초 듣기 → 살아 있는 50대": 서버는 명령을 보내기 전에 3초 동안 텔레메트리 토픽을 듣고 지금 살아 있는 장치 목록을 만든다. 죽은 장치에 보내 놓고 기다리면 안 되기 때문이다.
- 화살표 2 (서버 → 장치 3대) "cmd ota {version 1.2.0-bad, apply_s 1, bad true}": 5% 단계의 장치 3대에만 명령을 보낸다. 50대의 5% = 2.5 → 올림(ceil)으로 3대. 명령 안의 `apply_s 1` 은 장치가 적용에 쓰는 시간(초), `bad true` 는 "이 펌웨어는 켜지면 고장 난다"를 흉내 내는 실험용 표시다.
- 화살표 3 (장치 → 브로커) "telemetry state=updating": 장치는 적용 중임을 텔레메트리로 알린다.
- 메모(장치 3대) "apply_s 1초 → fw_version 교체 → state=fault": 1초 뒤 펌웨어 버전을 바꾸고, 나쁜 펌웨어라서 상태가 fault 가 된다.
- 화살표 4 (장치 → 브로커) "telemetry fw=1.2.0-bad, state=fault": 새 버전 이름과 고장 상태가 서버에 보인다.
- 서버 자기 화살표 "적용 대기 → 전원 적용 1.6초": 서버는 3대 모두의 fw_version 이 새 버전으로 바뀔 때까지 기다린다 — 이 실행에서 1.6초 걸렸다.
- 서버 자기 화살표 "헬스 게이트 3초 → 비정상 3/3 > 허용 0": 헬스 게이트 시간(이 실행은 3초) 동안 지켜본 뒤 새 버전을 받은 장치들의 state 를 본다. 비정상 3대가 허용치 0 을 넘었다 → 롤백 결정.
- 화살표 5 (서버 → 장치 3대) "cmd ota_rollback": 이전 버전으로 돌아가라는 명령.
- 화살표 6 (장치 → 브로커) "telemetry fw=1.0.0, state=ok": 장치가 이전 버전(1.0.0)으로 돌아가 정상이 된다.
- 서버 자기 화살표 "롤백 완료 0.8~1.0초 → 중단": 3대 전부 돌아온 것을 확인하는 데 0.8~1.0초. 50% · 100% 단계는 시작하지 않는다.
- 메모(나머지 47대) "47대는 명령을 받은 적이 없다": 카나리(canary) 배포의 핵심 — 나쁜 펌웨어가 닿은 장치는 3대뿐.

장표 오른쪽 글머리표 여섯 줄은 위 흐름의 요약이다. 여섯째 줄이 소스 위치: `fleet/ota/rollout.py:141-172 run_stage`(한 단계: 보내기 → 적용 대기 → 헬스 게이트), `:174-188 rollback`, 장치 쪽 `fleet/agent/device_agent.py:176 apply_ota`(updating → 버전 교체 → ok 또는 fault). 실측 표는 3부 장표 100.

## 3. 용어와 단위
- OTA(Over-The-Air): 무선으로 펌웨어(장치 소프트웨어)를 갱신하는 것.
- 단계 배포(카나리): 소수(5%)에 먼저 내려 보고 괜찮으면 50%, 100% 로 넓힌다. 광산의 카나리아 새에서 온 말.
- 헬스 게이트: 단계마다 "건강한가"를 보는 문. 여기서는 장치의 state 가 ok 인지만 본다(단순함이 장점).
- 롤백: 이전 버전으로 되돌리기. 장치는 prev_fw_version 을 기억하고 있다.
- apply_s: 장치가 적용에 쓰는 시간(초). 실험이라 sleep 으로 흉내 낸다.
- 텔레메트리: 장치가 주기적으로 올리는 측정값·상태 메시지(1 Hz).
- 시퀀스 다이어그램: 참여자 세로줄과 시간 순서의 화살표로 "누가 누구에게 언제 무엇을"을 그리는 그림.

## 4. 쉬운 예시
식당 비유: 새 조리법(펌웨어)을 전 지점 50곳에 한꺼번에 바꾸지 않고, 먼저 3곳에서 하루 써 본다(5% 단계). 세 곳 모두에서 손님 항의(state=fault)가 나오면 본사가 "옛 조리법으로 돌아가라"(롤백)고 하고 나머지 47곳은 애초에 바꾼 적이 없다.

숫자 예시: 50대 × 5% = 2.5 → 3대. 적용 대기 1.6초 + 헬스 게이트 3초 + 롤백 1.0초 ≈ 5.6초 만에 사고가 끝나고, 피해 범위는 3/50 = 6%.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 닿은 장치 3/50, 롤백 1.0초 — `docs/measurements/table3.md` 표③-3 (1.2.0-bad 줄, 2026-11-04). 리허설(11/05)에서는 0.8초 — `docs/LOG.md` 11/05.
- 확인: 기본값 — `fleet/ota/rollout.py` 인자: `--stages 5,50,100`, `--apply-s 2.0`, `--health-wait 5.0`, `--max-fail 0`, `--discover-s 3.0`. 그림의 apply_s 1·헬스 3초는 그 실행에서 준 값이고, 표③-3 의 "적용/헬스 대기 2.0 / 5.0" 은 기본값으로 돈 실행이다.
- 확인: 5% 의 올림 계산 — `fleet/chaos/assert_results.py` 49줄 `canary = int(math.ceil(devices_total * 0.05))`.
- 확인: 장치 쪽 동작 — `fleet/agent/device_agent.py:176-186 apply_ota` (state updating → sleep(apply_s) → prev_fw_version 저장 → fw_version 교체 → bad 면 fault, 아니면 ok).
- 확인: CI 러너(10대)에서는 닿은 장치 1/10, 롤백 0.4초 — `docs/measurements/table3_ci.md`.
- 다시 보기: `python3 fleet/ota/rollout.py --version 1.2.0-bad --bad --apply-s 1 --health-wait 3` (관제 컨테이너와 가상 장치가 떠 있을 때). 결과 JSON `docs/measurements/ota_<version>.json` 과 DB 의 events(kind='ota')·ota_rollouts 표.

## 6. 자주 하는 오해·함정
- "장치가 스스로 고장을 알아채고 되돌리면 되지 않나?" — 그러면 판단 기준이 50곳에 흩어진다. 이 설계는 서버 한 곳이 판단하고 장치는 적용/복원만 한다(DECISIONS 11/03 D3).
- "헬스 게이트가 이번 단계 3대만 보나?" — 아니다. 지금까지 새 버전을 받은 **모든** 장치를 본다(50% 단계면 누적 25대). 그림은 5% 단계라 3대뿐이다.
- 종료 코드: 나쁜 펌웨어 실행은 롤백으로 끝나는 것이 **정상 결과**인데 프로그램은 실패(1)로 끝난다. 통합 테스트 스크립트가 `|| true` 로 받는 이유.
- 롤백 시간 0.8~1.0초는 "롤백 결정 → 3대 전부 이전 버전·ok"까지이지, 사고 발생부터가 아니다.

## 7. 면접 한 문장
"나쁜 펌웨어는 5% 단계의 세 대에서 헬스 게이트가 잡아 1초 안에 롤백하고, 나머지 47대는 명령을 받은 적도 없습니다 — 판단은 서버 한 곳(rollout.py)에서, 장치는 적용과 복원만 합니다."
