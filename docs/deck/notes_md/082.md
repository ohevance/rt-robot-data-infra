# 장표 082 — ⑦⑧ 들머리 — 장애 주입·판정·진단: 일부러 죽여서 재고, 그 숫자를 믿을 수 있게
*위치: 2부 데이터의 길 · ⑦⑧ 장애·판정·진단 · 들머리*

## 1. 이 장표가 왜 있나
2부의 ①~⑥(에이전트 → 브로커 → 수집기 → DB·Grafana → OTA)까지는 **정상일 때** 데이터가 어떻게 흐르는지였다. 앞 장표(081, 롤백 코드)의 `다음 ▶` 는 "정상 동작은 확인됐다. 각 부품을 일부러 죽여 얼마나 잃고 얼마나 빨리 돌아오는지 재는 도구들"이었다. 그래서 이 묶음의 질문은 둘이다: 브로커·DB·수집기가 각각 죽으면 얼마나 잃고 얼마나 빨리 돌아오나? 그리고 그렇게 나온 숫자(특히 "유실 0")를 **믿어도 되나**? 이 들머리는 그 두 질문에 대한 문제·기준·확인 방법·결과·판단을 여섯 상자로 요약한다. 실제 실험 사슬(E05 → E13)과 표③은 3부(장표 97~100)로 미뤄 두었고, 2부 안에서는 도구(코드) 세 장(083~085)만 본다.

## 2. 장표를 하나씩 읽기
들머리는 늘 같은 여섯 상자다. 왼쪽 위에서 오른쪽으로, 그다음 아래 줄은 오른쪽에서 왼쪽으로(뱀 모양) 읽는다.

- 회색 "들어온 것": "정상 동작하는 길 ①~⑥ + 유실을 세는 열쇠 seq". 앞 묶음들에서 길이 정상으로 돈다는 것, 그리고 장치가 메시지마다 붙이는 일련번호 seq(①에서 나왔다)가 들어온다. seq 가 없으면 무엇을 잃었는지 셀 방법이 없다.
- 민트 "문제": "'유실 0' 은 측정이 틀려도 0 으로 나온다. 각 부품(브로커·DB·수집기)이 죽으면 얼마나 잃고 얼마나 빨리 돌아오나 — 그리고 그 숫자가 다른 증거와 맞나?" 핵심은 앞 문장이다. 유실을 세는 식이 틀리면 0 이 나오고, 0 은 보기 좋아서 의심을 안 하게 된다. 그래서 "다른 증거(진단 도구)와 맞나"가 문제에 들어 있다.
- 마름모 "기준": "broker 유실 ≤ 장치 수 · db 0 · collector(QoS 1) 0, 복구 수초, diag 의 seq 틈·오프라인 군집과 일치하나?" 왜 broker 만 ≤ 장치 수인가: 브로커가 죽는 **그 순간** 소켓에 실려 있던 메시지 1개/장치는 QoS 0 에서 잃을 수 있어 장치 수만큼은 허용한다(판정 규칙 assert_results.py 35줄). db 는 수집기 backlog 가 있으니 0 이어야 하고, collector 는 QoS 1 지속 세션이면 브로커가 대신 보관하니 0 이어야 한다. 마지막 조건 "diag 와 일치"가 '0 을 믿을 수 있나'의 기준이다.
- 파란 "확인 방법": "inject.py 4종(stop/start · SIGTERM 재시작 · --bad) → 유실 SQL(기준점 = 장애 직전 마지막 seq) → assert_results.py 판정 → diag.py 진단 (E06 → E13 → 3부 장표 97~100)". 도구 네 개가 순서대로 쓰인다: 장애를 넣는 도구(083 장표의 SQL 이 이 안에 있다), 통과/실패를 가르는 도구, 이상한 숫자를 파고드는 도구(085 장표). 실험 번호 E06~E13 은 3부에서 사슬로 본다.
- 보라 테두리 "결과": "E06 '0' 은 가짜(맹점) → E07 기준점 수정 → 53 → 원인 셋(세션·종료·큐) → E08 0 / 1400·0 / 1341·0 / 1311 → E13 CI 에서도 0·0·0". 한 줄에 이야기가 다 있다. 처음 잰 0(E06)은 유실 SQL 의 기준점이 "장애 창 안 첫 번호"라서 창 앞가장자리의 유실을 못 보는 맹점이었다. 기준점을 "장애 직전 마지막 번호"로 고치자(E07) 브로커 10초 중단에서 53 / 1434 가 나왔고, 원인은 셋 — 브로커 재시작 때 지속 세션이 사라지는 것(persistence false), 수집기 종료 순간 장치당 1개, 브로커 큐 상한(20,000). 설정 한 줄(persistence true)과 종료 처리를 고친 뒤(E08) broker 0 / 1400, db 0 / 1341, collector(QoS 1) 0 / 1311. CI 러너(10대 2 Hz, E13)에서도 0 / 318 · 0 / 286 · 0 / 280.
- 진한 민트 "판단 → 다음": "표③ 통과(3부에서 확인) → 2부 끝. 다음은 3부: 1·2부에서 미뤄 둔 시험을 단계 순서대로". 2부의 마지막 묶음이라 다음은 단계가 아니라 3부 검증이다.
- 아래 상자 "이 묶음의 장표": ② 유실 SQL 코드(083) · ③ 장애 4종 표(084) · ② 판정·진단 도구(085). 실험 사슬 3장과 표③ 1장은 3부. "넘어가는 조건: 기준을 못 넘은 측정(E06·E07)마다 원인과 고친 것이 있고, 환경을 바꿔도(CI) 같은 모양" — 즉 '0' 하나가 아니라 **틀렸던 0 → 53 → 0 의 이력**과 다른 환경 재현이 있어야 믿는다.

## 3. 용어와 단위
- 장애 주입(fault injection): 일부러 부품을 죽였다 살려 복구 능력을 재는 시험. 여기서는 `docker compose stop/start`(브로커·DB)와 프로세스에 SIGTERM(수집기), 나쁜 펌웨어 배포(`--bad`).
- seq(일련번호): 장치가 메시지마다 1씩 올려 붙이는 번호. 받은 쪽에서 빠진 번호 = 잃은 메시지.
- 유실 행: DB 의 행 1 = 메시지 1개. "0 / 1400" = 그 창에서 장치들이 만든 1,400개 중 0개가 없다.
- 기준점: 유실을 셀 때 "어디부터 세나". 장애 직전 마지막 seq 부터 세어야 장애 시작 직후에 잃은 것이 잡힌다.
- 판정(assert): 숫자를 규칙에 대어 통과/실패로 바꾸는 것. 종료 코드 0 = 전부 통과(CI 가 이 코드를 본다).
- 진단(diag): 통과/실패가 아니라 "왜 이런 숫자인가"를 파는 도구. A 오프라인 군집, B 지연 튐, C seq 틈.
- 지속 세션(clean_session=False): 수집기가 없는 동안 브로커가 QoS 1 메시지를 대신 보관하는 MQTT 기능.
- QoS 0 / 1: 보내고 잊음 / 받았다는 확인(PUBACK)까지.
- 복구 수초: 표③-2 의 복구(전 장치/backlog 0) 2.9 · 1.4 · 1.6초 — 초 단위.

## 4. 쉬운 예시
택배 비유: 택배 회사(관제)가 "분실 0건"이라고 발표했는데, 고객 센터(진단 도구)에는 "12일 동안 아무것도 안 왔다"는 민원이 있다. 둘 중 하나는 틀렸다. 알고 보니 분실 집계가 "사고 뒤 첫 배송부터" 세고 있어서 사고 직후 사라진 상자를 못 세고 있었다(맹점). 집계 기준을 "사고 직전 마지막 송장 번호부터"로 고치니 53건이 나왔고, 원인 셋을 찾아 둘은 고치고 하나는 창고 용량 규칙으로 정리했다.

숫자 예시(E07 의 원인 ①): 장치 1대가 13초 동안 1 Hz 로 보냈으니 기대 13개, 실제 1개 → 12개 유실. 그런 장치 4대 = 48, 다른 한 대 5개 → 53. 50대가 만든 1,434개 중 53 = 3.7%.

## 6. 자주 하는 오해·함정
- "유실 0 이 나왔으니 끝"이 가장 큰 함정이다. 이 저장소에서 가장 중요한 줄은 "0 을 의심해서 53 을 찾았다"다(E07). 측정이 틀리면 0 은 가장 위험한 숫자다.
- broker 장애의 허용치 "≤ 장치 수"를 "유실을 봐준다"로 읽기 쉽지만, QoS 0 에서 죽는 순간의 1개는 설계상 잃을 수 있어 그만큼만 허용하는 것이고, 실측은 0 이었다.
- 11/04 사고: 재시작한 수집기가 venv 를 잃고 바로 죽음(`/proc/<pid>/exe`) → `/proc/<pid>/environ` 으로 같은 환경 재시작. 11/04 사고: 진단 A 절이 "이전 이벤트 기준"으로 군집을 이어 붙여 209개짜리 거대 군집이 됨 → "첫 이벤트 기준 0.5초"로 고침.
- "CI 에서 0 이면 WSL 에서도 0" 이 아니라, 환경을 바꿔도 **같은 모양**(0·0·0, 롤백만 더 빠름)인 것이 설계가 만든 숫자라는 증거다.

## 7. 면접 한 문장
"장애 주입의 유실이 0 으로 나왔지만 진단 도구의 12초 공백과 맞지 않아 측정식을 의심했고, 기준점을 장애 직전 번호로 고치자 53 이 나왔습니다 — 원인 셋 중 둘은 설정 한 줄과 종료 처리로 막아 0 으로 만들었고, 셋째(큐 상한)는 설계 규칙이 됐습니다."
