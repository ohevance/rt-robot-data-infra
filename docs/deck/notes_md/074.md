# 장표 074 — ③ 수집기 — 종료할 때 마지막 1초를 잃지 않는 길 (11/04 실측에서 고침)
*위치: 2부 데이터의 길 · ③ 수집기 · ④ 판단 — 종료 때 마지막 1초*

## 1. 이 장표가 왜 있나
앞 세 장표(071~073)에서 수집기(`collector.py`)가 평소에 어떻게 일하는지 보았다. 받는 스레드가 메시지를 파싱해 `pending` 에 모으고, 1초마다 `flush_once` 가 묶음을 `backlog` 끝에 붙여 오래된 것부터 DB 에 넣는다. 그러면 남는 질문은 "수집기를 **끝낼 때**는 어떻게 되나?"이다. 받아 두었지만 아직 DB 에 안 넣은 "그 1초의 pending" 이 프로세스와 함께 사라지면, 장치당 1행씩 50행이 없어진다. 11/04 실측(E07)에서 실제로 그랬다 — 유실 원인 ②.

이 장표는 ③ 수집기 묶음의 판단 장표다. 종료 신호가 들어온 순간부터 프로세스가 끝나는 순간까지를 순서도로 그려 "마지막 1초를 잃지 않는 길"을 보여 주고, 그 길이 코드의 어느 줄인지 적는다. 이것으로 ③ 묶음의 기준("DB 가 죽어도·내가 죽어도 잃지 않게")을 모두 넘었다고 판단하고 ④⑤ DB·Grafana 로 넘어간다.

## 2. 장표를 하나씩 읽기
상자 여덟 개가 한 줄에 네 개씩 두 줄로 이어지고, 일곱째는 마름모(판단), 여덟째는 진한 둥근 상자(결론)다.

- 상자 1 "SIGTERM / Ctrl+C 도착": 운영체제가 보내는 종료 신호다. `kill` 명령·장애 주입 도구(`inject.py --fault collector`)는 SIGTERM 을, 터미널에서 Ctrl+C 를 누르면 SIGINT 를 보낸다. 둘 다 같은 길로 들어간다(`main()` 369~370줄에서 두 신호에 같은 핸들러를 건다).
- 상자 2 "request_stop(): STOP 플래그만 세운다 (핸들러 안에서 DB·소켓 금지)": 신호를 받으면 실행되는 함수(317줄)는 `STOP["requested"] = True` 한 줄만 한다. 왜 그 안에서 DB 에 쓰거나 소켓을 닫지 않나: 신호 핸들러는 프로그램이 무엇을 하는 중이든 끼어들어 실행되므로, 그 안에서 DB·소켓 같은 공유 자원을 만지면 하던 일과 뒤엉킬 위험(재진입)이 있다. 그래서 "깃발만 올리고" 실제 일은 메인 루프에 맡긴다.
- 상자 3 "메인 루프: while not STOP → 0.2초씩 자며 매초 flush_once": `main()` 의 `while not STOP["requested"]:`(374줄)가 깃발을 매번 확인한다. 1초 주기까지 남은 시간을 한 번에 자지 않고 `time.sleep(min(delay, 0.2))` 로 0.2초씩 쪼개 자는 이유는, 신호가 와도 최대 0.2초 안에 깨어나 깃발을 보기 위해서다(377줄 주석). 깨어나서 주기가 되면 `flush_once()` 로 1초 묶음을 DB 에 넣고 통계 한 줄을 출력한다.
- 상자 4 "루프 탈출 → shutdown(c)": 깃발이 올라가 있으면 while 조건이 거짓이 되어 루프를 빠져나오고, 바로 `shutdown(c)`(383줄)를 부른다.
- 상자 5 "loop_stop → disconnect (지속 세션이면 그 뒤 메시지는 브로커가 보관)": `shutdown` 의 첫 두 줄(337~338줄). 브로커에서 받는 일을 먼저 멈춘다. 순서가 중요하다 — 받기를 멈추지 않고 마지막 적재를 하면 적재 도중 새 메시지가 또 들어와 끝이 없다. 수집기가 QoS 1 지속 세션(`--qos 1`)으로 붙어 있었다면, 끊은 뒤에 오는 메시지는 브로커가 들고 있다가(장표 067~068) 다음에 켜질 때 전달하므로 잃지 않는다.
- 상자 6 "마지막 flush_once: pending + backlog 전부 적재": `last = c.flush_once()`(341줄). 받아 두고 아직 넣지 않은 pending 과, DB 장애로 밀려 있던 backlog 를 마지막으로 넣는다. 11/04 전에는 이 한 줄이 없었다.
- 마름모 7 "backlog 가 남았나?" → 화살표 글 "0 이면 '마지막 n행까지 적재 완료' / 남으면 'DB 가 죽어 있음' 안내": 342~345줄. 마지막 적재 뒤에도 `backlog_rows` 가 0 보다 크면 DB 가 지금 죽어 있다는 뜻이므로 "종료 시 DB 에 못 넣은 행 N개(버린 행 M개) — DB 가 죽어 있음" 을 출력한다. 0 이면 "마지막 n행까지 적재 완료, 남은 backlog 0" 을 출력한다. 왜 이 기준인가: 종료 때 데이터를 잃었는지 아닌지를 사람이 로그 한 줄로 알 수 있어야 하기 때문이다.
- 상자 8 "종료 코드 0 (11/04 전: 즉시 종료로 장치당 1행 = 50행 유실 → E07 원인 ②)": `main()` 이 0 을 돌려주며 정상 종료한다. 괄호 안이 이 장표가 있는 이유다 — 고치기 전에는 신호를 받으면 바로 죽어 장치당 1행, 50대면 50행이 사라졌고, 그것이 E07 에서 찾은 유실 원인 ②였다. 고친 뒤 재측정(E08)에서 collector 장애 유실은 0 / 1311.

아래 줄 "코드: collector.py request_stop(317) · shutdown(335-346) · main(348-383). 11/05 CI 사고: 잠금 공용화 패치에서 request_stop 이 통째로 지워져 NameError → main() 한 바퀴 스모크 테스트 추가 (test_collector_resilience 8번째)":
- 코드 위치 세 곳. 핸들러 `request_stop` 317줄, 곱게 끝내기 `shutdown` 335~346줄, 진입점 `main` 348~383줄.
- 11/05 CI 사고: 11/04 의 다른 패치(단일 인스턴스 잠금을 공용 모듈로 옮기는 수정)에서 `request_stop` 함수가 통째로 지워졌다. 단위 테스트는 `Collector` 클래스만 쓰고 `main()` 을 타지 않아 잡지 못했고, WSL 에서도 그 뒤 수집기를 다시 띄운 적이 없어, CI 의 통합 테스트에서만 수집기가 시작 직후 `NameError` 로 죽어 빨갔다. 해결은 함수 복원 + `test_collector_resilience` 에 `main()` 을 한 바퀴 도는 스모크 테스트(`test_main_entry_smoke`: STOP 깃발을 미리 세워 루프 0바퀴 → shutdown, 시그널 핸들러 직접 호출) 추가. 배운 것: 진입점은 단위 테스트가 최소 한 번은 타야 한다. 확인: 지금 `fleet/tests/test_collector_resilience.py` 에는 테스트 함수가 6개 있고 스모크 테스트는 그중 마지막(6번째)이다 — 장표의 "8번째" 는 파일의 실제 개수와 다르다.

## 3. 용어와 단위
- SIGTERM / SIGINT: 리눅스가 프로세스에 보내는 신호. SIGTERM 은 "끝내라"(`kill` 기본), SIGINT 는 Ctrl+C. 신호를 받으면 미리 등록한 함수(핸들러)가 실행된다.
- 신호 핸들러 / 재진입: 핸들러는 프로그램이 무슨 일을 하던 중이든 끼어든다. 그 안에서 하던 일과 같은 자원을 만지면 두 번 들어간(재진입) 상태가 되어 꼬일 수 있다. 그래서 핸들러는 깃발만 세운다.
- 플래그(깃발): 참/거짓 하나를 담는 변수. 여기서는 `STOP["requested"]`.
- pending: 받았지만 아직 DB 에 넣지 않은 행. 1초마다 묶음으로 바뀐다.
- backlog(밀린 일): DB 에 넣으려다 실패해 메모리에 들고 있는 묶음들. 상한을 넘으면 오래된 것을 버리고 센다(`backlog_dropped`).
- flush_once: "1초마다 한 번 비우기". 묶음을 만들어 DB 에 넣고 통계를 내는 함수.
- loop_stop / disconnect: paho-mqtt(MQTT 클라이언트 라이브러리)에서 수신 스레드를 멈추는 것 / 브로커와의 연결을 끊는 것.
- 지속 세션: 끊긴 뒤 오는 QoS 1 메시지를 브로커가 보관해 주는 접속 방식(장표 067).
- 종료 코드: 프로그램이 끝날 때 운영체제에 돌려주는 숫자. 0 = 정상. 이 프로그램은 잠금 실패 3, 스키마 불일치 2 도 쓴다.
- 스모크 테스트: "켜 보니 연기가 나는가" 정도의 가장 기본적인 동작 확인 테스트.

## 4. 쉬운 예시
식당 마감 비유: 영업 종료 벨(SIGTERM)이 울렸을 때, 벨을 들은 직원이 그 자리에서 금고를 정리하면(핸들러 안에서 DB 작업) 손님 응대와 뒤엉킨다. 대신 "마감" 표지판만 세우고(깃발), 홀 담당이 다음 순회 때 표지판을 보고 입구를 닫은 뒤(disconnect) 주방에 남은 주문을 모두 내보내고(마지막 flush_once) 문을 잠근다. 입구를 먼저 닫는 이유는, 닫지 않으면 마감 중에도 새 손님이 계속 들어오기 때문이다. 닫힌 뒤 온 손님은 옆 대기실(브로커 큐)에서 다음 영업 때까지 기다린다.

숫자 예시: 장치 50대가 1 Hz 로 보내므로 pending 에는 매 순간 최대 50행이 들어 있다. 고치기 전에는 종료할 때마다 그 50행이 사라졌다(E07: SIGTERM 때마다 장치당 1개, 11:39:16 50대 = 50행). 고친 뒤에는 종료 신호 → 최대 0.2초 안에 루프가 깨어남 → disconnect → 마지막 적재, 그래서 collector 10초 장애의 유실이 0 / 1311.

## 6. 자주 하는 오해·함정
- "신호를 받으면 그 자리에서 정리하고 끝내면 되지 않나"는 오해. 핸들러 안에서 DB·소켓을 만지면 재진입 문제가 생긴다. 깃발만 세우고 메인 루프가 정리하는 것이 표준적인 방법이다.
- "disconnect 를 먼저 하면 그 사이 메시지를 잃지 않나"는 걱정. 지속 세션(QoS 1)이면 브로커가 보관하므로 잃지 않는다. QoS 0 이면 잃는다 — 그래서 표③-2 에 QoS 0 은 508 / 1312, QoS 1 은 0 / 1311 로 나란히 적어 두었다.
- 함정(11/04): 즉시 종료로 50행을 잃고도 처음에는 몰랐다. 유실 측정식의 맹점(장표 083) 때문에 "0" 으로 보였기 때문이다.
- 함정(11/05): 함수 하나가 지워져도 단위 테스트가 다 통과했다. 테스트가 진입점(`main`)을 안 탔기 때문이다. 그래서 스모크 테스트를 추가했고, 문서 커밋이라도 push 뒤 CI 를 본다는 규칙이 생겼다.
- 이 방법은 SIGTERM/Ctrl+C 같은 "곱게 끝내는" 신호에만 통한다. SIGKILL(강제 종료)이나 정전은 핸들러가 실행되지 않으므로 pending 을 잃는다. 그것까지 막는 방법("DB 에 넣은 뒤 ACK")은 코드가 두 배로 복잡해져 2주 안에서는 보류했다(DECISIONS 11/04).

## 7. 면접 한 문장
"수집기 종료 때 장치당 1행씩 50행이 사라지는 것을 실측에서 찾아, 신호 핸들러는 깃발만 세우고 루프가 끝난 뒤 수신을 끊고 마지막 적재를 하도록 고쳐 유실을 0 / 1311 로 만들었습니다 — 그 뒤 그 함수가 패치에서 지워져 CI 가 빨개진 사고로, 진입점을 타는 스모크 테스트도 추가했습니다."
