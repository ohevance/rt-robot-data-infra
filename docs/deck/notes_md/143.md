# 장표 143 — 덧붙임 (11/11 저녁) — 같은 RT 루프를 ZeroMQ 로: 명령이 반영되어 돌아오기까지 0.9 ms, 그 절반은 소켓도 스케줄러도 아니라 루프의 주기
*위치: 7부 왜·사고·방식 · 덧붙임 ZeroMQ 1/2 그림 (11/11 저녁)*

## 1. 이 장표가 왜 있나
11/11 저녁에 지원하는 공고를 하나로 정했다 — 위로보틱스의 Framework S/W 엔지니어(장표 102, `docs/DECISIONS.md` 2026-11-11). 그 공고의 필수 역량을 이 저장소와 한 줄씩 맞춰 보니 빈칸이 하나 있었다: "ZeroMQ, DDS, ROS/ROS2 등 메시징 기반 분산 시스템 경험". DDS · ROS 2 · MQTT 는 있었지만 ZeroMQ 는 없었다. 주요 업무에도 "ZeroMQ·ROS 기반 통신 패킷과 Python/C++ SDK 설계"가 있다.

마침 이 저장소에는 11/03 부터 말만 있고 증거가 없던 문장이 하나 있었다 — `docs/ARCHITECTURE.md` 의 "미들웨어 교체(ROS 2 ↔ ZeroMQ)는 어댑터 교체다". 실시간 핵심(`rt_core`)이 ROS 2 를 모르게 짜여 있으니, 껍질만 바꾸면 다른 미들웨어로도 같은 로봇 루프를 돌릴 수 있다는 주장이다. 이 장표는 그 주장을 코드와 숫자로 보인 것이다: `rt_core` 를 고치지 않고 ZeroMQ 노드(`rt_zmq_node`)와 Python SDK(`rtsdk`)를 만들고, "명령이 RT 루프에 반영되어 상태로 돌아오기까지" 몇 ms 인지, 그 몫이 어디서 오는지를 쟀다.

같은 날 밤의 일 두 가지도 이 한 장에 들어 있다. ① 작성자가 WSL 에서 같은 측정을 두 번 했다 — 일반 스케줄링, 그리고 RT 스레드만 SCHED_FIFO 로. ② 작성자가 "ZeroMQ 어댑터와 SDK 는 전부 시험되었나?"라고 물었고, 답은 "아니다"였다. 시험이 없던 길 하나(느린 구독자)를 재 보니 문서가 틀려 있었다. 그래서 순서도는 질문 → 구조 → 숫자 → 시험 → 틀린 것 → 한계 → 결론으로 흐른다. 다음 장표(144)는 같은 노드의 코드 한 조각, 패킷 하나를 받았을 때의 판정이다.

## 2. 장표를 하나씩 읽기
순서도는 왼쪽 위에서 시작해 한 줄에 네 칸씩 세 줄이고, 둘째 줄은 오른쪽에서 왼쪽으로 간다(뱀 모양). 회색은 들어온 것, 민트는 실행되는 과정, 마름모는 기준과 그 답, 연파랑은 확인 방법(코드·시험), 흰 상자는 결과, 연빨강은 실패 · 한계, 진한 상자는 결론.

- 회색 상자 "공고(Framework S/W)의 필수 역량: 메시징 분산 시스템(ZeroMQ · DDS · ROS 2) — 이 저장소에는 DDS·ROS 2·MQTT 뿐 — ZeroMQ 가 빈칸": 출발점. 공고 문구를 필수 역량 표로 맞춰 본 결과다(DECISIONS 11/11 "지원하는 자리를 … 좁히고"). 빈칸을 메우는 방법으로 "ZeroMQ 를 써 본 작은 예제"가 아니라 "이미 있는 실시간 루프를 ZeroMQ 로 감싼 노드"를 골랐다 — 그래야 지연 · 안전 · 상태 머신까지 같은 기준으로 비교된다.
- 마름모 "rt_core 를 고쳐야 하나?" → 답 "아니오: 껍질만 바꾼다 — 명령 번호 필드 둘(seq · cmd_seq)만 더함": 첫 기준. 바뀐 것은 `JointCommand::seq`(명령 번호)와 `JointStateSample::cmd_seq`(이 주기까지 반영된 마지막 명령 번호) 두 필드뿐이고, `control_step.cpp` 의 줄 번호도 흔들리지 않게 같은 줄에 넣었다. 이 두 필드가 있어야 클라이언트가 "내 명령이 RT 루프에 들어갔다"를 상태로 확인할 수 있다.
- 연파랑 상자 "Python SDK: TARGET(seq = k) 를 DEALER 로 — 노드의 ROUTER → 명령 스레드: 형식 · 관절 수 · NaN 검사 → ACK": 명령이 들어가는 길. 클라이언트는 목표 위치를 번호 k 와 함께 보낸다. 소켓은 DEALER ↔ ROUTER — "보내고 받기"를 번갈아야 하는 REQ/REP 와 달리 연달아 보내고 답(ACK)은 번호로 맞춘다. 노드의 명령 스레드가 패킷을 판정하고 모든 패킷에 답한다. 판정의 코드가 다음 장표다.
- 민트 상자 "명령 우편함(spsc_ring) → RT 루프가 다음 주기에 꺼냄 (0 ~ 1 ms) — 워치독 · 변화량 제한 → 상태에 cmd_seq = k": 통과한 명령은 락 없는 우편함에 들어간다. RT 스레드는 1 ms 마다 한 번 깨어 우편함을 열고 최신 것 하나만 꺼낸다 — 그 사이에 도착한 명령은 다음 주기까지 기다린다(0 ~ 1 ms). 그다음은 1부와 같은 안전 검사(워치독 50 ms, 변화량 제한 0.05 rad/주기)이고, 그 주기의 상태에 cmd_seq = k 가 실린다.
- 민트 상자 "상태 벨트 → 발행 스레드(200 us 마다) → PUB 1 kHz — 같은 PC 의 다른 프로세스는 공유 메모리(seqlock)로": 상태가 나가는 길. RT 스레드는 소켓을 모른다 — 상태를 벨트(다른 spsc_ring)에 올릴 뿐이고, 발행 스레드가 200 us 마다 깨어 벨트를 비워 PUB 소켓으로 보낸다. 같은 PC 의 다른 프로그램은 소켓 없이 공유 메모리에서 최신 한 장을 읽는다(seqlock — 쓰는 쪽은 기다리지 않는다, 6부 장표 115 의 시험).
- 마름모 "cmd_seq ≥ k 인 상태가 돌아오기까지?" → 답 "WSL p50 0.88 / p99 1.81 ms (1,000회, 잃음 0) · 상태 1만 개 빈 번호 0": 이 장표의 중심 숫자. 클라이언트가 보낸 순간부터 자기 명령 번호가 실린 상태를 받은 순간까지를 **클라이언트 시계 하나로** 잰다. 1,000번 보내 1,000번 다 돌아왔고, 같은 10초 동안 1 kHz 상태 10,327개를 빈 번호 없이 받았다. 재기 전에 적은 판정 기준("p99 가 2 ms — 두 주기 — 안")을 넘었다.
- 마름모 "RT 스레드를 SCHED_FIFO 로 올리면?" → 답 "p50 0.88 / p99 1.71 — 거의 그대로": 같은 측정을 `sudo … --prio 80`(RT 스레드만 실시간 우선순위 80, 프로세스 전체 메모리 잠금)으로 다시. p50 은 그대로, p99 는 0.1 ms 줄었다. 우선순위로 줄일 수 있는 몫이 거의 없다는 뜻이다.
- 흰 상자 "몫 나누기: 소켓 왕복 0.21 ms · 루프 주기 대기 평균 0.5 ms · 발행 깨어남 평균 0.1 ms — 스케줄러가 줄일 몫이 아니다": 그 이유. 0.88 ms 를 나누면 소켓으로 노드까지 약 0.1 + 다음 주기까지 기다림 평균 0.5 + 발행 스레드가 깰 때까지 평균 0.1 + 소켓으로 돌아오는 길 약 0.1 + Python 이 받아 푸는 시간이다. 가장 큰 몫은 **1 kHz 루프의 주기 자체**이고, 이것은 설계다 — RT 스레드가 소켓을 기다리면 주기가 흔들린다(표①이 재는 것). 줄이려면 우선순위가 아니라 구조(같은 프로세스, 공유 메모리, 더 빠른 주기)를 바꿔야 한다.
- 연파랑 상자 "CI 끝-대-끝 12단계(진짜 libzmq · pyzmq): 워치독 51~52 ms 뒤 FAULT · 나쁜 패킷 넷 · 클라이언트 둘 · 느린 구독자 · 다시 연결 · 우편함 가득 참": 숫자 말고 동작의 증거. push 마다 GitHub 러너가 진짜 노드를 띄워 SDK 로 12단계를 확인한다(`sdk/python/tests/test_zmq_node.py`). 명령을 멈추면 마지막 명령 51~52 ms 뒤 FAULT, 위치 그대로. 쓰레기 바이트 · 관절 수 다름 · NaN · 모르는 type 은 이유와 함께 거절. 뒤의 넷(클라이언트 둘 · 느린 구독자 · 다시 연결 · 우편함 가득 참)은 11/11 밤에 더한 것이다.
- 연빨강 상자 "시험이 없던 길(느린 구독자): 12초 안 읽어도 빈 번호 0 — 전부 묵은 채 도착 / 45초면 빈 번호 12,109, 그래도 노드의 버림 카운터는 0": 틀렸던 것. 문서는 "구독자 큐 1,000개(1초)를 넘으면 노드가 버리고 센다"고 말했다. 재 보니 12초를 안 읽어도 하나도 버려지지 않았다 — 대신 첫 장이 12초 묵은 채로 왔다. 버리기 전에 커널의 TCP 버퍼(수 MB)와 양쪽 큐가 먼저 차기 때문이다(SDK 기본값으로 약 33초 분량). 45초를 안 읽자 그제야 빈 번호 12,109 — 그런데 노드의 카운터는 0. PUB 소켓은 넘친 구독자의 몫을 조용히 버리고 "보냈다"고 돌려준다. 문서와 주석을 고치고 시험 9단계로 이 동작을 고정했다(E24 7절).
- 연빨강 상자 "한계: WSL 은 가상 머신 — SCHED_FIFO 여도 깨어남 최대 3.56 ms (한 주기 넘음 30번). Pi(PREEMPT_RT) 값은 아직 — 예측만 E24 5절": 숨기지 않는 한계 둘. ① WSL 은 Windows 위의 가상 머신이라, 리눅스 안에서 우선순위를 올려도 RT 루프가 3.56 ms 늦게 깬 적이 있고 23초 동안 한 주기를 30번 넘었다. 실시간 판정은 Pi(표①: cyclictest 최대 37 / 132 us)로 한다. ② Pi 에서는 아직 재지 않았다 — 예측은 재기 전에 E24 5절에 커밋해 두었다.
- 진한 상자 "결론: 미들웨어 교체 = 어댑터 교체 (11/03 의 설계 문장을 코드로) — 더 줄이려면 구조(공유 메모리 · 같은 프로세스) · 지금 값은 conflate": 결론 셋. 설계 문장이 증거를 얻었고, 지연을 더 줄이는 손잡이는 미들웨어나 스케줄러가 아니라 구조에 있으며, 지금 값이 필요한 프로그램은 `conflate=True`(최신 한 장만)를 쓴다.
- 아래 줄 "읽는 법: …": 노드가 소켓을 기다리는 일반 스레드와 우편함만 보는 RT 스레드로 나뉜다는 것(ROS 2 노드와 같은 모양), 그래서 명령의 기다림은 지연이 아니라 설계라는 것, 숫자를 어디서 쟀는지(WSL2 두 번, 느린 구독자는 샌드박스)와 최댓값(19.7 vs 3.7 ms)의 원인은 가르지 않았다는 것, 그리고 출처.
- `다음 ▶` 다리 "노드가 패킷 하나를 받으면 — 형식 · 관절 수 · NaN 을 어떻게 판정하고, 거절은 어떻게 알리나? (handle_packet)".

## 3. 용어와 단위
- ZeroMQ: 브로커 없이 프로그램끼리 메시지를 주고받는 라이브러리. 소켓의 "모양(패턴)"을 골라 쓴다. MQTT 처럼 가운데 서버(브로커)가 있는 것이 아니라 직접 연결이다.
- PUB / SUB: 한쪽이 뿌리고(PUB) 여럿이 받는다(SUB). 상태 흐름에 쓴다. 보내는 쪽은 받는 쪽을 기다리지 않는다.
- DEALER / ROUTER: 요청을 연달아 보내고 답은 번호로 맞추는 짝. ROUTER 는 보낸 쪽의 신원을 기억해 답을 그쪽에만 돌려보낸다.
- ACK: "받았다"는 답. 여기서는 거절도 ACK 로 — 이유(status)를 실어 돌려준다.
- seq / cmd_seq: 명령의 번호 / 상태에 실린 "반영된 마지막 명령 번호".
- 우편함(spsc_ring): 쓰는 쪽 하나, 읽는 쪽 하나인 락 없는 링 버퍼(64칸). 1부 단계 3.
- 공유 메모리 seqlock: 같은 PC 의 프로세스들이 같은 메모리를 보고, 번호 두 번 읽기로 "쓰는 도중에 읽었나"를 판정한다. 쓰는 쪽은 기다리지 않는다.
- SCHED_FIFO / mlockall: 리눅스의 실시간 우선순위 정책 / 프로세스의 메모리를 잠가 페이지 폴트를 막는 것. 1부 단계 4.
- p50 / p99 / 최댓값: 1,000번 중 가운데 / 위에서 열 번째 / 가장 느린 것.
- conflate: SUB 가 최신 한 장만 들고 있게 하는 옵션. 건너뛴 것은 SDK 가 빈 번호로 센다.
- 높은 물 표시(HWM): 소켓이 쌓아 둘 최대 개수. 그 앞에 커널의 TCP 버퍼가 따로 있다.
- WSL2: Windows 안에서 도는 리눅스(가상 머신). 단위: ms(1,000분의 1초), us(100만분의 1초). 1 kHz = 1초에 1,000번 = 1 ms 마다.

## 4. 쉬운 예시
- 비유(왜 우선순위로 안 줄었나): 우체국 창구(명령 스레드)는 편지를 언제든 받지만, 집배원(RT 루프)은 정확히 1 ms 마다 한 번 우편함을 연다. 편지가 아무 때나 도착하면 평균 0.5 ms 기다린다. 집배원에게 "다른 일보다 먼저"(SCHED_FIFO)라는 완장을 채워도 "1 ms 마다 한 번"은 그대로라 평균 기다림은 그대로다. 완장이 줄이는 것은 집배원이 가끔 지각하는 일뿐이다.
- 숫자 예시(몫 나누기): 0.1(가는 소켓) + 0.5(주기 기다림 평균) + 0.1(발행 깨어남 평균) + 0.1(오는 소켓) + 약 0.1(Python) ≈ 0.9 ms. 실측 p50 0.88 ms. 최악 쪽은 주기 기다림이 1 ms 를 거의 다 채우고 발행 깨어남이 0.2 ms 를 다 채운 경우 + 나머지의 꼬리 → p99 1.7 ~ 1.8 ms.
- 비유(느린 구독자): 신문을 2주 동안 안 가져가면, 신문사는 신문을 버리지 않고 우편함(커널 버퍼)과 경비실(큐)에 쌓아 둔다. 돌아와서 맨 위부터 읽으면 2주 전 뉴스다. 공간이 다 찬 뒤에야 새로 오는 신문을 버리는데, 신문사(노드)는 버린 줄 모른다 — 독자가 날짜(번호)의 빈 칸을 보고 안다. 오늘 뉴스만 원하면 "가장 최근 것 한 부만 남겨 달라"(conflate).
- 숫자 예시(그 실험): 12초 안 읽기 → 받은 13,001장, 빈 번호 0, 첫 장의 나이 12.0초. 45초(SDK 기본 큐) → 받은 33,892장, 빈 번호 12,109, 첫 장의 나이 45.0초, 노드의 `states_send_dropped` 0. 버려지기 시작해도 오래된 것이 남는다 — PUB 는 새로 오는 것을 버린다.

## 6. 자주 하는 오해·함정
- "ZeroMQ 가 느려서 1 ms 가까이 걸린다": 소켓 왕복은 0.21 ms 다. 나머지는 RT 루프의 주기와 발행 간격 — 설계로 생기는 기다림이다.
- "SCHED_FIFO 를 켰는데 안 줄었으니 실패한 실험이다": 실험의 답은 "줄일 몫이 다른 곳에 있다"다. 우선순위는 늦게 깨는 일(꼬리)을 줄이는 손잡이지, 주기의 기다림을 줄이는 손잡이가 아니다.
- "최댓값이 19.7 → 3.7 ms 로 줄었으니 SCHED_FIFO 의 효과다": 한 번씩 잰 값이고, 19 ms 늦음이 RT 스레드와 무관한 구간에도 있었다. 원인을 가르려면 같은 설정을 번갈아 세 번씩 재야 한다(E24 남은 일).
- "빈 번호 0 이니 느린 구독자도 문제없다": 빈 번호 0 은 "늦게라도 다 왔다"는 뜻이다. 로봇 상태에서는 늦게 온 것이 빠진 것보다 위험할 수 있다 — 화면은 12초 전의 로봇을 보여 준다.
- "노드가 버린 수를 센다": PUB 의 버림은 노드가 모른다. 받는 쪽의 빈 번호가 유일한 증거다.
- "WSL 값으로 실시간 성능을 말한다": WSL 은 가상 머신이라 깨어남이 몇 ms 늦기도 한다. 실시간은 Pi + PREEMPT_RT 의 표①로 말한다.
- "ZeroMQ 경로는 암호화된다": 이 노드는 CURVE(ZeroMQ 의 암호화)를 켜지 않았다. 로봇 한 대 안 · 옆(같은 PC, LAN)의 경로이고, 인터넷을 건너는 관제는 MQTT(TLS + 비밀번호)가 맡는다.

## 7. 면접 한 문장
"ROS 2 로 감싸던 실시간 루프를 코드 수정 없이 ZeroMQ 로 다시 감쌌습니다. 명령이 반영되어 돌아오기까지 p50 0.9 ms 인데 그 절반은 1 kHz 루프가 다음 주기에 우편함을 여는 시간이라, RT 스레드를 SCHED_FIFO 로 올려도 p50·p99 는 그대로였습니다 — 더 줄이려면 구조를 바꿔야 한다는 것까지 숫자로 나눴고, 시험이 없던 길을 시험하다가 '느린 구독자는 버려지기 전에 수십 초 묵은 상태를 받는다'는 것을 찾아 문서와 SDK 사용법을 고쳤습니다."
