# 장표 144 — 끝 — 결국 로봇은 이렇게 움직인다 (한 장 요약, 숫자와 함께)
*위치: 끝 · 한 장 요약*

## 1. 이 장표가 왜 있나
이 발표는 처음부터 "위에서 아래로, 끝은 로봇이 이렇게 움직인다"는 순서로 짜였다. 1부에서 로봇을 움직이는 10단계를 장표 46장(11~56)에 걸쳐 코드와 함께 보였고, 시험과 검증은 3부(86~100)로 미뤄 두었다. 바로 앞 장표(143)는 그 전체를 한 질문으로 접었다. "그래서 로봇은 어떻게 움직이나?" 이 장표가 그 답이다. 10단계를 상자 10개로 한 장에 다시 놓고, 상자마다 (1) 무슨 일이 일어나는지, (2) 그것을 보여 주는 숫자 하나, (3) 그 코드나 증거가 있는 파일 이름을 붙였다. 발표를 끝내는 장표이자, 면접에서 "처음부터 끝까지 한 번에 말해 보라"는 질문을 받았을 때 그대로 따라 읽는 지도다.

## 2. 장표를 하나씩 읽기
상자는 다섯 개씩 두 줄이다. 윗줄 왼쪽에서 오른쪽(1~5), 그다음 아랫줄 왼쪽에서 오른쪽(6~10) 순서로 화살표를 따라 읽는다. 상자 아래의 작은 글씨는 근거(파일이나 표)다. 상자 색은 동네를 나눈다 — 로봇 밖에서 들어오는 길(1·2), RT 쪽(3·4·5·8), 로봇 쪽 갈아 끼우는 부분(6), 움직인 결과(7), 기록과 관제(9·10).

- 상자 1 "명령 50 Hz — 목표 [0.3, −0.2, 0.1, 0, 0, 0.5] rad" (근거 `/joint_command`): 관절 6개의 목표 각도 6개가 한 묶음이다. 1초에 50번(20 ms 마다) 같은 명령을 보낸다. 시연에서는 `ros2 topic pub -r 50 /joint_command …` 한 줄이 상위 제어기 역할을 한다. 1부 단계 1(장표 11~13).
- 상자 2 "DDS 전달 — 작은 메시지 손실 0, RTT p50 ≈ 1 ms" (근거 표②): 64 B~64 KB 메시지는 두 구현체·두 QoS 모두 500개 중 손실 0, 왕복 지연 중앙값은 868~1,236 us(한 방향은 그 절반쯤). 1부 단계 2(장표 14~16), 검증 87~88.
- 상자 3 "우편함 — 락 없는 링 64칸, 꽉 차면 버리고 센다" (근거 `spsc_ring.hpp`): 노드의 일반 스레드가 명령을 64칸짜리 링에 넣고, RT 스레드가 꺼낸다. 서로 기다리지 않는다. 꽉 차면 cmd_ring_full 카운터로 센다(그 값은 rt_status 에 실리지만 커밋된 기록 CSV 에는 없는 열이다, 5절). 1부 단계 3(장표 17~21).
- 상자 4 "1 ms 루프 — Pi RT: max 189 us(격리), 드롭 0. WSL: 참고값" (근거 표① · `rt_loop.cpp`): RT 스레드가 1 ms 마다 절대 시각에 깬다. Pi 4 실시간 커널 + CPU 3 격리, 부하 중 60초에 가장 늦게 깬 한 번이 189.3 us, 버린 샘플 0. WSL2 의 숫자는 가상 커널이라 합격 판정에 쓰지 않는다. 1부 단계 4(장표 22~26), 검증 89~95.
- 상자 5 "안전 검사 — 최신 명령 · 워치독 50 ms · 0.05 rad/주기 · 상태 머신 RUNNING" (근거 `control_step.cpp`): 한 주기에 우편함을 비우고 마지막 명령만 쓰고, 50 ms 동안 명령이 없으면 그 자리에 멈추고, 목표가 한 주기에 0.05 rad 넘게 뛰지 못하게 자르고, 상태 머신이 RUNNING 일 때만 로봇에 쓴다. 1부 단계 5(장표 27~36).
- 상자 6 "백엔드 — MuJoCo ctrl → mj_step, p99 6축 8.5 us · ALLEX 48축 458 us" (근거 `mujoco_backend.cpp`): 제어 코드는 같은 세 함수만 부르고, 그 아래에서 MuJoCo 가 목표를 ctrl 에 넣고 물리를 한 걸음 진행한다. CI 러너에서 2,000 주기 측정: 6축 팔은 p50 6.4 / p99 8.5 / max 29.4 us — p99 가 1 ms 예산의 1% 도 안 되고, max 도 3% 이하다. 같은 백엔드에 지원 회사의 ALLEX 48 자유도 모델을 프로필 하나로 얹으면 p99 458 us(1 kHz, 러너) — 그래서 그 프로필은 500 Hz 를 쓴다(장표 136). 1부 단계 6(장표 37~43).
- 상자 7 "로봇이 움직인다 — 어깨 −0.181(처짐 1.1°), 팔꿈치 0.109, 나머지 목표 그대로" (근거 `/joint_states`): 목표 −0.200 rad 인 어깨만 0.019 rad(1.1°) 덜 갔다. 팔 무게가 걸리는 관절의 중력 처짐이다. 팔꿈치는 목표 0.1 에 대해 0.109(차이 0.009 rad, 약 0.5°), 나머지 네 관절은 차이 0.003 rad 이하. 1부 단계 7(장표 44~46), 검증 96.
- 상자 8 "상태 100 Hz — 실제 100.0 Hz, rt_status 1 Hz JSON" (근거 `rt_control_node.cpp`): 노드가 10 ms 마다 `/joint_states` 를, 1초마다 자기 설명 JSON(`/rt_status`)을 낸다. 30초 기록에서 실제로 100.0 Hz 였다. 1부 단계 8(장표 47~50).
- 상자 9 "기록 — MCAP 30초 → CSV → 요약: 틈 0, 처짐 자동 검출" (근거 `data_pipeline/`): `record.sh 30` 이 rosbag2(MCAP, 1.07 MB)로 남기고, `bag_to_csv.py` 가 CSV 3개와 요약을 만든다. 요약이 "주기 틈 0"과 "어깨 0.0191 rad 처짐"을 사람 손 없이 찾아냈다. 1부 단계 9(장표 51~53).
- 상자 10 "관제 — 브로커 → 수집기 → DB → Grafana. 브로커 장애 유실 0 / 1400(가상 50대), 실물 Pi → 시드니 서버 14.8시간 유실 0" (근거 `fleet/ · deploy/`): RT 노드의 1 Hz 요약을 다리 프로그램(`ros_status_bridge.py`)이 장치 `rt-node-1` 로 MQTT 에 올린다. 같은 브로커 → 수집기 → DB 길에서 가상 장치 50대로 브로커를 10초 멈춘 실험의 유실은 1,400행 중 0행이다(RT 노드를 붙인 상태로 잰 값은 아니다, 5절). 둘째 숫자는 11/10~11 에 더한 것이다: 같은 운영 층(브로커·수집기·DB·Grafana)을 클라우드 서버(시드니)에 올리고 실물 Pi 4 가 1 Hz 로 보고하게 했더니, 14.77시간 동안 보낸 53,167건이 한 건도 빠지지 않았다(장표 140). 근거 칸에 `deploy/`(서버·Pi 설치 스크립트)가 더해진 이유다. 1부 단계 10(장표 54~56), 검증 97~100.
- 아래 띠: "이 한 줄기가 저장소의 전부다… 그 답이 docs/experiments/, docs/DECISIONS.md, 그리고 장표마다 붙은 설명 문서에 있다." 어느 상자에서 질문이 와도 '숫자의 출처 · 코드 위치 · 그렇게 한 이유' 세 가지로 답한다는 약속이다.

## 3. 용어와 단위
- Hz: 1초에 몇 번. 50 Hz = 20 ms 마다, 100 Hz = 10 ms 마다, 1 kHz = 1 ms 마다.
- rad(라디안): 각도 단위, × 57.3 = 도. 0.019 rad ≈ 1.1°.
- us(마이크로초): 100만분의 1초. 1 ms = 1,000 us.
- RTT(왕복 시간): 보내고 답이 돌아올 때까지. 한 방향 ≈ RTT/2.
- p50 / p99 / max: 절반이 이 값 이내 / 100번 중 99번이 이 값 이내 / 가장 나쁜 한 번.
- 드롭: 링이 꽉 차서 버린 샘플 수. 0 이면 하나도 안 버렸다.
- MCAP: rosbag2 의 기록 파일 형식. CSV: 쉼표로 나눈 표 파일. JSON: 이름표가 붙은 글자 데이터.
- 틈(>3주기): 메시지 간격이 설계 주기의 3배를 넘은 곳. 0 이면 끊긴 곳이 없다.
- ctrl / mj_step: MuJoCo 의 액추에이터 입력 배열 / 물리를 한 걸음 진행하는 함수.

## 4. 쉬운 예시
명령 하나를 따라가 보자. 처음 자세가 모두 0 이라고 가정한다.
- 0 ms: 상위 제어기가 [0.3, −0.2, 0.1, 0, 0, 0.5] 를 보낸다. 다음 명령은 20 ms 뒤에 온다.
- 약 0.5 ms 뒤: DDS 가 노드에 전달한다(같은 PC 의 RTT 868~1,236 us 의 절반쯤). 노드가 우편함에 넣는다.
- 다음 1 ms 경계: RT 스레드가 깨서(Pi 에서 늦어도 189 us) 우편함을 비우고 마지막 명령만 쓴다. 명령은 20 ms 마다 오고 우편함은 1 ms 마다 비워지므로 보통 한 칸만 찬다. 64칸이 다 차려면 RT 스레드가 64 × 20 ms = 1.28초 동안 한 번도 못 돌아야 한다. 최악으로 늦게 깬 189 us 의 약 6,800배나 긴 정지다(추정: 설계에서 나온 계산, 측정 아님).
- 변화량 제한: 집게(Jaw) 0 → 0.5 rad 는 0.5 / 0.05 = 10 주기 = 10 ms 에 걸쳐 나눠 간다. 회전 0.3 rad 는 6 주기 = 6 ms.
- 매 주기 MuJoCo 가 ctrl 에 목표를 넣고 한 걸음(p99 8.5 us) 진행한다. 몇 초 뒤 팔은 거의 목표에 서고, 어깨만 −0.181 에서 멈춘다(1.1° 처짐).
- 그동안 10 ms 마다 상태가 나가고(29.6초에 2,964개), 1초마다 rt_status 가 나가고, 그것이 기록되고, 관제 화면의 51번째 장치로 보인다.

## 6. 자주 하는 오해·함정
- "이 숫자들은 한 기계에서 한 번에 잰 것"이라는 오해: 아니다. 189 us 는 Pi 4 실시간 커널(측정기 jitter_bench, MuJoCo 없음), 8.5 us 는 GitHub CI 러너, 100.0 Hz 와 1.1° 처짐은 WSL2 의 30초 기록, 0 / 1400 은 WSL2 의 가상 50대, 14.8시간 유실 0 은 실물 Pi 와 시드니의 서버다. 상자마다 그 숫자를 가장 정직하게 잴 수 있는 곳에서 쟀다(5부 어디서). 발표할 때 "어디서 잰 숫자인지"를 같이 말한다.
- WSL 숫자를 합격 근거로 쓰는 함정: 같은 30초 기록의 wake_us p99 최대 606.4 us 는 가상 커널의 참고값이다. 1 ms 루프의 합격 판정은 Pi 4 의 189 us 로만 한다.
- "RTT ≈ 1 ms = 네트워크 1 ms"라는 오해: 같은 PC 안의 두 프로세스 왕복이다(공유 메모리 전송이 섞인다). 선을 타는 숫자가 아니다.
- 두 처짐 숫자가 다르다는 혼란: E16 의 −0.180 은 11/04 화면을 눈으로 읽은 값, −0.181 은 11/05 기록의 자동 요약에서 나온 값이다. 둘 다 약 1.1° 다.
- 기록 첫 시도의 함정: 처음에는 `record.sh` 가 `timeout` 으로 recorder 를 감쌌는데 `--foreground` 가 없어 recorder 가 뒤쪽 프로세스 그룹에 놓였고, 키보드를 읽으려다 정지 신호(SIGTTIN)를 받아 멈췄다 → `--foreground` 를 붙여 고쳤다(E20). "틈 0"은 고친 뒤 2차 기록의 값이다.

## 7. 면접 한 문장
"50 Hz 명령이 DDS(같은 PC 왕복 약 1 ms)로 들어와 64칸 락프리 우편함을 거치고, Pi 4 실시간 커널에서 최악 189 us 늦게 깨는 1 ms 루프가 워치독 50 ms·0.05 rad 제한으로 안전하게 MuJoCo 에 쓰면 어깨만 1.1° 처진 채 목표를 따라가며, 그 상태를 100 Hz 로 틈 없이 기록하고 관제로 올려 브로커를 죽여도 유실 0 — 상자마다 숫자와 파일이 있습니다."
