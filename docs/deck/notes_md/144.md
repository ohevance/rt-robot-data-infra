# 장표 144 — 덧붙임 (11/11 저녁) — 패킷 하나의 판정: 형식 → 관절 수 → NaN → 우편함, 거절은 이유와 함께 (rt_zmq_node.handle_packet)
*위치: 7부 왜·사고·방식 · 덧붙임 ZeroMQ 2/2 코드 (11/11 저녁)*

## 1. 이 장표가 왜 있나
앞 장표(143)의 순서도에서 한 칸 — "노드의 ROUTER → 명령 스레드: 형식 · 관절 수 · NaN 검사 → ACK" — 을 코드로 연다. 지원하는 공고의 주요 업무에 "통신 패킷과 Python/C++ SDK 설계"가 있다(장표 102 의 ④ 줄). 통신 패킷을 설계할 때 가장 먼저 물어야 하는 것은 "잘못된 바이트가 오면 어떻게 하나"다. 로봇 쪽 노드는 바깥에서 오는 바이트를 믿을 수 없다 — SDK 가 아니라 다른 언어의 클라이언트일 수도, 잘린 패킷일 수도, 버그가 만든 NaN 일 수도 있다. 그리고 이 함수를 통과한 것만 RT 루프의 우편함에 들어가 로봇을 움직인다.

그래서 이 함수에는 원칙이 둘 있다. ① **판정은 싼 것부터**: 머리(24바이트)만 보고 걸러지는 것을 먼저, 그다음 본문의 크기와 관절 수, 마지막에 값 하나하나. ② **모든 패킷에 답한다**: 거절도 이유(status)와 함께. 조용히 버리면 클라이언트는 "노드가 느린 것"과 "내가 틀린 것"을 구분하지 못한다. 이 장표는 그 두 원칙이 코드 31줄(199~229)에서 어떻게 보이는지를 짚는다.

## 2. 장표를 하나씩 읽기
코드 상자 위의 경로는 `rt_control/zmq_adapter/src/rt_zmq_node.cpp:199-229` (handle_packet 의 앞부분)이다. 줄 번호는 파일의 것이다.

- 199 `wire::WireError e = wire::decode_header(p, len, h);`: 머리 24바이트를 읽는다. 판정은 `rt_core/src/wire.cpp` 185~204줄 — 길이가 24 보다 짧으면 TOO_SHORT, 처음 4바이트가 magic "RTW1" 이 아니면 BAD_MAGIC, version 이 1 이 아니면 BAD_VERSION, 머리에 적힌 본문 길이(payload_len)와 실제 받은 길이가 다르면 LENGTH_MISMATCH. 본문은 아직 한 바이트도 읽지 않았다.
- 200~204 `if (e != OK) { … BAD_PACKET … return encode_ack(…, 0, BAD_PACKET); }`: 머리가 틀리면 형식 오류로 세고 바로 답한다. 답의 acked_seq 가 **0** 인 이유가 주석(202줄)에 있다 — 머리를 못 읽었으면 그 안의 seq 도 믿을 수 없다. 클라이언트는 "형식 오류"만 알게 된다.
- 206~210 `switch (h.type) { case TARGET: … decode_target(p, len, h, cmd, bad_value);`: 머리가 맞으면 type 으로 갈린다. TARGET(목표 위치)이면 본문을 푼다 — `wire.cpp` 206~233줄: 본문이 고정 부분(관절 수 u16 + 빈칸 u16)보다 짧거나, 관절 수가 0 이거나 최대(kMaxJoints)를 넘거나, 전체 길이가 "머리 + 4 + 관절 수 × 8" 과 다르면 BAD_DOF. 값은 하나씩 `std::isfinite` 로 보고, NaN · 무한대가 하나라도 있으면 bad_value 를 켠다(227~228줄).
- 211~217 판정 순서: `BAD_DOF` → `BAD_PACKET` → `BAD_VALUE`. 212줄의 조건이 두 갈래인 것을 본다 — 형식상 관절 수가 이상한 것(`e == BAD_DOF`)과, 형식은 맞는데 **이 노드의 관절 수와 다른 것**(`cmd.dof != o.dof`). 6축 노드에 7축 명령이 오면 형식은 맞아도 거절이다.
- 218~222 `cmd.stamp_ns = now_ns(); if (!g_cmd_ring.push(cmd)) { st = RING_FULL; }`: 통과하면 노드의 단조 시계로 받은 시각을 찍어 명령 우편함(spsc_ring, 64칸)에 넣는다. 넣지 못하면 RING_FULL — 주석대로 "RT 스레드가 우편함을 비우지 못한다"는 신호이고, 정상이면 0 이다. RT 스레드는 다음 주기에 우편함에서 **최신 것 하나**만 꺼낸다(앞 장표).
- 224~228 `if (st == OK) targets_ok += 1; else rejected[st] += 1;`: 받은 것과 거절한 것을 이유별로 센다. 노드를 끝낼 때(`--status-json`) 이 수가 JSON 으로 나온다 — 11/11 밤 WSL 측정에서는 이유별 거절이 전부 0, 받은 명령 1,000.
- 229 `return encode_ack(reply, cap, out_seq, now_ns(), h.seq, st);`: 답. 클라이언트가 보낸 seq 를 그대로 돌려줘 클라이언트가 번호로 맞춘다(DEALER 는 답을 기다리지 않고 연달아 보낼 수 있으므로 번호가 유일한 짝 맞추기다).
- 오른쪽 설명 여섯 줄: ① 머리부터 — 틀리면 본문을 읽지 않고, acked_seq 0. ② TARGET — 관절 수 다름은 BAD_DOF, NaN·무한대는 BAD_VALUE: NaN 은 변화량 제한의 비교(`delta > max`)를 늘 거짓으로 통과해 마지막 안전장치가 뚫린다. ③ 통과하면 우편함에 — 차면 RING_FULL: 10 Hz 로 띄운 노드에 200개를 한꺼번에 넣으면 ok 63 · ring_full 137(64칸 링은 한 칸을 비워 둔다, 끝-대-끝 12단계). ④ 모든 패킷에 답한다 — 거절 수는 이유별로. ⑤ 패킷 형식은 `wire.hpp` 머리말의 표 하나, C++ 와 Python 이 같은 바이트를 기대하는 골든 시험 둘. ⑥ 끝-대-끝 시험(CI, 12단계)이 나쁜 패킷 넷을 각각 거절하고 그 뒤에도 ping 에 답하는지, 답이 보낸 클라이언트에게만 가는지 확인한다.
- 각주 "한계: 암호화·인증 없음(CURVE 를 켜지 않았다 — LAN·같은 PC 경로), Zenoh·C++ 클라이언트는 아직": 이 판정은 "형식이 틀린 바이트"를 막는 것이지 "누가 보냈나"를 막는 것이 아니다. 그래서 기본 bind 가 모든 주소라는 것을 README 에 경고했다.
- `다음 ▶` 다리 "끝 — 1~7부와 덧붙임을 한 줄기로 접으면: 결국 로봇은 이렇게 움직인다".

## 3. 용어와 단위
- 패킷: 한 번에 보내는 바이트 묶음. 여기서는 머리 24바이트 + 본문.
- 머리(header): magic u32 "RTW1" · version u16 · type u16 · seq u32 · payload_len u32 · stamp_ns i64 — 합쳐 24바이트, 리틀엔디언(작은 자리부터).
- magic / version: "이 형식이 맞나"를 보는 고정 값 / 형식의 판. 다르면 본문을 읽지 않는다.
- type: TARGET(목표 위치) · ACK(답) · STATE(상태) · PING/PONG · GET_INFO/INFO.
- AckStatus: OK 0 · BAD_DOF 1(관절 수) · RING_FULL 2(우편함 가득) · BAD_PACKET 3(형식) · UNKNOWN_TYPE 4(모르는 type) · BAD_VALUE 5(NaN·무한대) — `wire.hpp` 49~56줄.
- NaN(Not a Number): 0/0 같은 계산이 만드는 "숫자 아님". NaN 과의 크기 비교(`<`, `>`)는 늘 거짓이다.
- `std::isfinite`: 값이 NaN 도 무한대도 아니면 참.
- seq / acked_seq: 보낸 쪽이 붙인 번호 / 답에 실어 돌려주는 그 번호.
- 골든 바이트: "이 입력이면 정확히 이 바이트가 나와야 한다"고 시험에 박아 둔 값. C++ 와 Python 구현이 어긋나지 않게 한다.
- 단조 시계(`now_ns`): 뒤로 가지 않는 시계. 한 기계 안의 시간 차이를 잰다.

## 4. 쉬운 예시
- 비유(택배 접수 창구): 먼저 송장(머리)을 본다 — 송장이 찢어졌으면 송장 번호도 못 믿으니 "형식이 틀렸다"고만 알린다. 송장은 멀쩡한데 상자 칸 수가 우리 창고(6축)와 다르면 "칸 수가 다르다"(BAD_DOF). 내용물에 숫자가 아닌 것이 섞였으면 "값이 이상하다"(BAD_VALUE). 다 맞는데 선반(우편함 64칸)이 꽉 찼으면 "선반이 찼다"(RING_FULL). 어느 경우든 접수증(ACK)은 꼭 준다.
- 숫자 예시(NaN 이 왜 위험한가): 현재 위치 0.10 rad, 목표 NaN, 한 주기 변화량 한도 0.05 rad. `delta = NaN − 0.10 = NaN`. `NaN > 0.05` 는 거짓 → 한도에 "걸리지 않았다"고 판단 → 목표 NaN 이 그대로 다음 단계로 간다. 시뮬레이터는 NaN 으로 터지고, 실물이면 모터 드라이버가 무엇을 할지 모른다. 그래서 우편함에 넣기 전, 문 앞에서 막는다.
- 숫자 예시(우편함 가득): 10 Hz 노드는 100 ms 에 한 번 우편함을 비운다. 그 사이에 목표 200개를 한꺼번에 보내면 63개가 들어가고(64칸 링은 한 칸을 비워 둔다) 나머지 137개는 RING_FULL 로 답한다. 노드가 끝날 때 센 `rejected.ring_full` 도 137 — 끝-대-끝 12단계가 이 둘이 같은지 본다.
- 숫자 예시(골든 바이트): seq 0x01020304, 시각 0x1122334455667788, 관절 2개, [1.0, −0.5] 인 TARGET 은 머리 24 + 본문 4 + 16 = 44바이트이고, 그 44바이트를 C++ 시험과 Python 시험이 똑같이 기대한다.

## 6. 자주 하는 오해·함정
- "SDK 가 보내기 전에 NaN 을 막으니 노드는 안 막아도 된다": 노드는 SDK 가 아닌 클라이언트(다른 언어, 손으로 만든 바이트, 버그)도 받는다. 노드가 믿을 것은 자기 검사뿐이다. 그래서 끝-대-끝 시험은 SDK 를 거치지 않는 날 바이트로 NaN 을 보낸다.
- "거절한 패킷은 조용히 버리면 깔끔하다": 그러면 클라이언트는 시간 초과만 보게 되고, 노드가 느린 것인지 자기가 틀린 것인지 모른다. 이유를 붙여 답하면 클라이언트 쪽 로그 한 줄로 끝난다.
- "머리가 깨진 패킷에도 받은 seq 로 답해 주면 친절하다": 머리가 깨졌으면 seq 도 깨졌을 수 있다. 틀린 번호로 답하면 다른 명령의 답으로 오해된다 — 그래서 0.
- "ACK ok 면 로봇이 움직였다": ACK 는 "우편함에 들어갔다"까지다. RT 루프에 반영된 것은 상태의 cmd_seq 로 본다(앞 장표).
- "RING_FULL 은 클라이언트의 잘못이다": 정상이면 0 이고, 나오면 RT 루프가 우편함을 못 비우고 있다는 경보다 — 명령을 주기보다 훨씬 빨리 보내거나 RT 루프가 멈춘 경우.
- "형식 검사가 있으니 보안도 된다": 이 검사는 "틀린 바이트"를 막지 "허락 안 된 사람"을 막지 않는다. 인증·암호화(CURVE)는 켜지 않았다.

## 7. 면접 한 문장
"로봇 노드가 바깥에서 받는 바이트는 전부 이 함수 하나를 지나는데, 싼 검사부터 — 머리, 관절 수, 값 순서로 — 판정하고 모든 패킷에 이유를 붙여 답합니다. 특히 NaN 은 변화량 제한의 비교를 늘 통과해 버리기 때문에 RT 루프에 들어가기 전 문 앞에서 막고, 그 동작을 날 바이트를 보내는 끝-대-끝 시험으로 고정했습니다."
