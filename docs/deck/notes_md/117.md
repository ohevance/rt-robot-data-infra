# 장표 117 — 통합 테스트 스크립트 (1/2) — 릴리스 패키지를 만들고, 컨테이너를 띄워 DB 가 '진짜' 준비될 때까지, 수집기와 장치 10대 (integration.sh)
*위치: 6부 믿을 수 있나 · 테스트 — 통합 1/2 (준비)*

## 1. 이 장표가 왜 있나
앞 장표(116)는 단위 테스트의 바닥인 가짜 브로커·가짜 DB 를 보여 주었다. 덕분에 컨테이너 없이 몇 초 만에 수집기·에이전트의 논리를 시험할 수 있다. 그러나 그 장표의 각주가 못 박았듯, 가짜 위에서 통과한 것은 "논리가 맞다"이지 "진짜 위에서도 된다"가 아니다. 그래서 이런 질문이 남는다. "진짜 Mosquitto(MQTT 브로커)와 진짜 TimescaleDB 를 띄워 놓고, 장애를 일부러 일으켜도 데이터를 안 잃는지를 어떻게 매번 같은 방법으로 확인하나?"

그 답이 통합 테스트 스크립트 `fleet/tests/integration.sh` 다. CI 2단계(`fleet_integration` 잡)가 push 때마다 이 스크립트를 돌리고, 내 PC(WSL)에서도 같은 스크립트를 돌린다. 스크립트는 길어서 장표 두 장으로 나눴다. 이 장(1/2)은 **준비** 단계다. 정리 규칙을 걸고, 릴리스 패키지를 만들어 내려받을 곳을 열고(11/10 에 더한 0단계), 브로커·DB 를 띄우고, DB 가 정말로 쓸 수 있게 될 때까지 기다리고, 수집기와 가상 장치 10대를 붙인다. 다음 장(118, 2/2)은 그 위에서 장애 3종·나쁜 펌웨어·정상 OTA·진짜 패키지 설치를 일으키고 판정해 표를 만든다.

## 2. 장표를 하나씩 읽기
장표 위의 파일 표시 `fleet/tests/integration.sh:29-57` 은 이 파일의 29~57줄이라는 뜻이다(11/05 에는 26~39줄 열네 줄이었다 — 0단계가 들어와 길어졌고, 그래서 코드 글자가 작다). 코드를 읽기 전에 그 위(13~28줄)에 무엇이 정해져 있는지 먼저 알아야 한다.
- 13줄 `set -euo pipefail`: 명령 하나라도 실패하면(종료 코드가 0 이 아니면) 스크립트를 즉시 멈춘다. 정의 안 된 변수를 쓰면 오류로 친다. 파이프 중간의 실패도 실패로 친다. 테스트 스크립트가 "실패를 못 본 척하고 계속 가는 것"을 막는 설정이다.
- 15~19줄: 기본값을 정한다.
  - `COUNT=${COUNT:-10}`: 장치 10대(환경 변수로 바꿀 수 있음).
  - `RATE=${RATE:-2}`: 장치당 초당 2개.
  - `OUT=build/integration`: 결과·로그 폴더.
  - `COMPOSE="docker compose -f fleet/docker-compose.yml"`: 컨테이너 정의 파일을 고정한 명령.
- 21~28줄 `cleanup()`: 끝날 때 할 정리다. 순서는 다음과 같다.
  1. 가상 장치에 SIGINT(Ctrl+C 와 같은 신호)를 보낸다. 장치는 곱게 끝나며 각자 "offline" 상태를 남긴다.
  2. 1초 기다린다.
  3. 수집기에 SIGTERM 을 보낸다. 수집기는 마지막 묶음까지 DB 에 넣고 끝난다.
  4. 패키지를 내주던 HTTP 서버가 떠 있으면 끝낸다(26줄, 11/10).
  5. `KEEP=0` 일 때만 `docker compose down -v` 로 컨테이너와 데이터 볼륨까지 지운다.

이제 장표의 코드를 줄마다 읽는다.
- **29줄 `trap cleanup EXIT`**: "이 스크립트가 끝나는 순간, 어떤 이유로 끝나든 `cleanup` 을 불러라"는 예약이다. 정상 종료든, `set -e` 때문에 중간에 멈추든, Ctrl+C 로 끊든 정리가 돈다. 다만 SIGKILL 같은 강제 종료는 예외다. 이것이 없으면 실패한 테스트가 수집기와 장치 10대를 배경에 남겨 둔다. 남은 프로세스는 잠금 파일을 쥐고 계속 메시지를 보내므로, 다음 실행이 꼬인다.
- **31줄 `echo "--- 0) 릴리스 패키지 (산출물 OTA 용). 없으면 jitter_bench 를 빌드해 만든다"`**: 0단계의 표지판. 11/10 에 OTA 가 "버전 문자열 흉내"에서 "진짜 파일 설치"로 바뀌면서 생긴 단계다 — 장치가 내려받을 진짜 패키지가 있어야 한다.
- **32~33줄 `PKG_DIR=${PKG_DIR:-build/release}` / `if [ ! -f "$PKG_DIR/manifest.json" ]; then`**: 패키지 폴더(기본 `build/release`)에 매니페스트가 이미 있으면 다시 만들지 않는다. 없을 때만 아래를 한다.
- **34~37줄**: `build/rt_core/jitter_bench` 가 없으면 cmake 로 그것만 빌드한다. 패키지 안에 넣을 실행 파일이다 — ROS 2 없이 어디서나 켜 볼 수 있는 유일한 "로봇 쪽" 프로그램이라 이것을 넣는다. CI 의 이 잡은 새 러너라 앞 잡(rt_core)의 빌드 결과가 없고, 그래서 여기서 다시 빌드한다.
- **38~39줄 `bash scripts/package_release.sh 0.0.0-ci --out "$PKG_DIR"` / `… --bad`**: 패키지를 두 개 만든다. 정상 패키지(버전 `0.0.0-ci`)와, 자가 점검이 일부러 실패하는 **깨진** 패키지(`0.0.0-ci-bad`). 패키지 하나는 tar.gz 한 덩어리이고(실행 파일 · 로봇 프로필 · 버전 · 커밋 · 자가 점검 스크립트), 스크립트가 그 파일의 sha256 과 크기를 재어 아키텍처별 매니페스트(`manifest.x86_64.json`)에 적는다.
- **40~41줄 `python3 scripts/merge_manifests.py --out "$PKG_DIR/manifest.json" "$PKG_DIR"/manifest.*.json`**(깨진 것도 같은 방법으로 `manifest-bad.json`): 아키텍처별 매니페스트를 하나로 합친다. 러너에서는 아키텍처가 x86_64 하나뿐이지만, 릴리스 워크플로(x86_64 + aarch64)와 **같은 모양의 매니페스트**를 쓰게 하려고 같은 도구를 거친다.
- **43~45줄 `HTTP_PORT=${HTTP_PORT:-8089}` / `python3 -m http.server "$HTTP_PORT" --bind 127.0.0.1 --directory "$PKG_DIR" > "$OUT/http.log" 2>&1 &` / `HTTP_PID=$!`**: 패키지 폴더를 이 컴퓨터 안에서만 닿는(127.0.0.1) 작은 웹 서버로 내준다. 다음 장의 4b · 4c 단계에서 장치가 `http://127.0.0.1:8089/…` 로 내려받는다 — 실물에서는 이 자리가 GitHub Release 의 주소다. `$!` 는 방금 띄운 배경 프로세스의 번호이고, 정리 함수(26줄)가 이 번호로 서버를 끝낸다.
- **47줄 `echo "--- 1) 브로커·DB 올리기"`**: 로그에 단계 제목을 찍는다. CI 로그는 수백 줄이라, 어디서 멈췄는지 바로 찾게 하려는 표지판이다.
- **48줄 `$COMPOSE up -d mqtt db`**: `fleet/docker-compose.yml` 에서 두 서비스만 띄운다.
  - `mqtt` 는 Mosquitto 브로커(이미지 `eclipse-mosquitto:2`, 포트 1883)다.
  - `db` 는 TimescaleDB(이미지 `timescale/timescaledb:latest-pg16`, 포트 5432)다.
  - `-d` 는 배경(detached)으로 띄우고 바로 다음 줄로 넘어간다는 뜻이다.
  - 같은 파일에 있는 grafana(대시보드)와 collector 컨테이너(프로필 `collector` 로만 뜸)는 띄우지 않는다. 수집기는 아래 54줄처럼 컨테이너가 아니라 이 컴퓨터의 프로세스로 띄운다.
  - 장애 주입 스크립트는 두 경우를 다 다룬다. 수집기가 컨테이너면 docker stop/start, 프로세스면 SIGTERM 으로 죽이고 같은 명령으로 다시 띄운다(`fleet/chaos/inject.py` 머리말).
- **49줄 주석**: "DB 준비 확인은 밖에서 실제로 붙어 보는 `migrate.py --wait` 로. 컨테이너 안 `pg_isready` 는 init 중 임시 서버에도 'accepting' 이라고 답한다." 이 한 줄에 11/04 CI 첫 실패의 교훈이 들어 있다(아래 읽는 포인트 셋째).
- **50줄 `python3 fleet/db/migrate.py --wait 120`**: 두 가지 일을 한 번에 한다.
  - 첫째, **기다리기**. `connect_with_wait`(`fleet/db/migrate.py:39-53`)가 1초마다 TCP 로 DB 에 실제 접속을 시도한다. 시도 한 번의 제한 시간은 3초다. 120초 안에 붙으면 다음으로 가고, 못 붙으면 마지막 오류를 그대로 내며 실패한다. 그러면 `set -e` 로 스크립트가 멈추고 `cleanup` 이 돈다. 기다리는 동안 첫 시도와 10번째 시도마다 "DB 대기 중 (N초)" 를 찍는다.
  - 둘째, **표 맞추기(마이그레이션)**. `fleet/db/migrations/` 의 번호 붙은 SQL(`002_ota.sql`, `003_collector_resilience.sql`)을 순서대로 본다. 아직 `schema_migrations` 표에 기록되지 않은 것만 실행하고 기록한다.
  - 순서가 중요하다. 수집기는 시작할 때 003 이 적용됐는지 확인한다. 안 됐으면 "DB 스키마가 옛 버전입니다" 를 찍고 종료 코드 2 로 끝난다. 그래서 수집기보다 먼저 돌린다.
- **52줄 `echo "--- 2) 수집기(지속 세션) + 가상 장치 ${COUNT}대 @ ${RATE} Hz (QoS 1)"`**: 두 번째 단계 표지판이다. 변수가 채워져 "가상 장치 10대 @ 2 Hz" 로 찍힌다.
- **53줄 `pkill -TERM -f collector/collector.py || true`**: 혹시 앞서 띄워 둔 수집기가 남아 있으면 끝낸다.
  - 수집기의 MQTT 접속 이름(client_id)은 "collector" 로 고정이다. 둘이 동시에 뜨면 브로커가 같은 이름의 새 접속을 받을 때마다 옛 접속을 끊는다. 그러면 두 수집기가 번갈아 끊긴다(11/04 실측 2차에서 겪음). 그래서 수집기는 잠금 파일(`fleet/logs/collector.lock`)로 하나만 뜨게 되어 있다.
  - `-f` 는 프로그램 이름이 아니라 명령줄 전체에서 찾으라는 뜻이다.
  - `|| true` 는 "찾은 것이 없어도 성공으로 쳐라"다. pkill 은 맞는 프로세스가 없으면 종료 코드 1 을 내는데, 13줄의 `set -e` 때문에 그것만으로 스크립트가 멈춰 버리기 때문이다. CI 러너처럼 처음부터 깨끗한 곳에서는 늘 "찾은 것 없음"이다.
- **54줄 `python3 fleet/collector/collector.py --qos 1 > "$OUT/collector.log" 2>&1 &`**: 수집기를 띄운다.
  - `--qos 1` 이면 "지속 세션"(clean_session=False, 고정 client_id)으로 구독한다. 수집기가 잠깐 죽어 있는 동안 브로커가 QoS 1 메시지를 대신 들고 있다가, 다시 붙으면 넘겨 준다.
  - 그래서 다음 장의 수집기 장애에서 유실 0 이 나올 수 있다.
  - `> "$OUT/collector.log" 2>&1` 은 일반 출력과 오류 출력을 모두 로그 파일로 보낸다.
  - 끝의 `&` 는 배경으로 실행하고 기다리지 않는다는 뜻이다.
  - 수집기는 1초마다(`--interval` 기본 1.0) 모인 메시지를 한 묶음으로 DB 에 넣고, 그때마다 `msgs/s=… online=… backlog=…` 한 줄을 찍는다.
- **55줄 `python3 fleet/agent/virtual_fleet.py --count "$COUNT" --rate "$RATE" --telemetry-qos 1 --prefix ci --slot-root "$OUT/devices" > "$OUT/fleet.log" 2>&1 &`**: 가상 장치 10대를 띄운다. 줄 끝 `2>&1 &` 는 오류 출력까지 로그 파일에 모으고 뒤에서 돌리라는 뜻이다.
  - `--count 10 --rate 2`: 10대가 각자 초당 2개, 합쳐서 초당 20개의 텔레메트리를 보낸다.
  - `--telemetry-qos 1`: 장치도 QoS 1 로 보낸다. 수집기만 QoS 1 이어서는 안 되고, 보내는 쪽도 QoS 1 이어야 브로커가 대신 들고 있어 준다(수집기 머리말 주석).
  - `--prefix ci`: 장치 이름이 `ci-001` … `ci-010` 이 되고, 잠금 이름도 `fleet_ci` 가 된다(`virtual_fleet.py:81`, `:91`).
  - `--slot-root "$OUT/devices"`(11/10): 장치마다 `build/integration/devices/ci-001/` 같은 폴더에 A/B 슬롯(두 칸 설치 자리)을 둔다. 이 옵션이 있어야 장치가 주소가 든 ota 명령을 받아 진짜로 설치한다. 이 경로가 **상대 경로**라는 점이 11/10 밤 사고의 원인이었다(다음 장, 장표 141).
- **56줄 `sleep 8`**: 8초 기다린다. 장치 10대가 브로커에 다 붙고, 수집기가 첫 묶음들을 DB 에 넣을 시간을 준다.
- **57줄 `tail -n 2 "$OUT/collector.log"`**: 수집기 로그의 마지막 두 줄을 화면(CI 로그)에 보여 준다. 이 스크립트에서 수집기의 상태를 처음 눈으로 확인하는 자리다. 정상이면 `msgs/s=` 줄이 보이고, 수집기가 시작하자마자 죽었다면 그 오류의 끝줄이 보인다.
- 여기까지가 준비다. 59줄 `echo "--- 3) 장애 주입"` 부터가 다음 장(118)이다.

**읽는 포인트 다섯 줄**
- **"trap cleanup EXIT: 어떻게 끝나든(실패 포함) 수집기·장치·HTTP 서버를 정리한다. 컨테이너는 KEEP=0 일 때만 내린다(CI) — WSL 에서는 기본 KEEP=1 이라 그대로 둔다"**
  - GitHub 의 CI 러너는 잡이 끝나면 컴퓨터째 버려지므로, 정리를 안 해도 다음 실행에 남는 것이 없다.
  - 내 PC 의 WSL 은 계속 쓰는 환경이라, 정리가 없으면 남은 수집기·장치가 잠금을 쥐고 다음 실험을 망친다. HTTP 서버가 남으면 다음 실행이 같은 포트(8089)를 못 연다.
  - 정확히 말하면, 프로세스(장치·수집기·HTTP 서버)는 언제나 정리한다. 컨테이너는 `KEEP=0` 일 때만 지운다.
  - CI 는 `KEEP=0 bash fleet/tests/integration.sh` 로 부르므로 컨테이너와 볼륨까지 지운다. WSL 에서 그냥 부르면 컨테이너는 남겨 둔다(2~11줄 머리말: "끝나면 컨테이너는 그대로 둔다").
- **"0) 릴리스 패키지(11/10): 매니페스트가 없으면 jitter_bench 를 빌드해 정상·깨진 패키지를 만들고(package_release.sh, --bad) 아키텍처별 매니페스트를 하나로 합친 뒤 로컬 HTTP(127.0.0.1:8089)로 서빙 — 4b·4c 의 장치가 여기서 내려받는다"**
  - 위 31~45줄의 요약이다. 요점은 "릴리스 때 쓰는 것과 **같은 스크립트**로 만든 진짜 패키지"를 매 push 마다 깔아 본다는 것이다. 패키지 만드는 스크립트가 깨지면 태그를 올리는 날이 아니라 그 push 에서 안다.
  - 깨진 패키지를 일부러 만드는 이유: "깨진 빌드는 첫 단계에서 거부된다"는 주장은 깨진 빌드를 실제로 넣어 봐야 증명된다.
- **"1) docker compose up mqtt db → migrate.py --wait 120: 컨테이너 안 pg_isready 는 init 중 임시 서버에도 '준비됨'이라 한다 → 밖에서 TCP 로 진짜 붙어 보며 기다린다(11/04 CI 1차 실패의 해결)"**
  - TimescaleDB(PostgreSQL) 이미지는 처음 뜰 때 세 단계를 거친다.
    1. 유닉스 소켓(같은 컴퓨터 안에서만 쓰는 연결 통로)만 여는 **임시 서버**로 `init.sql` 을 실행한다.
    2. 임시 서버를 끈다.
    3. 진짜 서버를 다시 띄운다.
  - 컨테이너 안의 `pg_isready` 는 임시 서버에도 "accepting connections" 라고 답했다. 그 1초 뒤 밖에서 TCP 로 붙은 `migrate.py` 는 "server closed the connection unexpectedly" 로 끊겼다.
  - 내 PC 에서는 볼륨에 데이터가 이미 있어 이 초기화 단계가 없었다. 그래서 CI 에서 처음 드러났다.
  - 해결은 "실제로 쓸 사람과 같은 길(같은 호스트, TCP)로 붙어 보며 기다리기"였다.
- **"2) 수집기(--qos 1) + 가상 장치 10대 2 Hz(--prefix ci, --slot-root: 장치마다 A/B 슬롯 폴더). 로그는 $OUT 에"**
  - 내 PC 실험(E06·E08)은 50대 × 1 Hz 였다. CI 는 10대 × 2 Hz(E13)다. 장치 수는 5분의 1이고, 대신 장치당 빈도를 두 배로 했다.
  - 로그는 `build/integration/` 에 쌓인다. CI 는 잡이 실패해도 이 폴더를 결과물(artifact) `fleet-integration` 으로 올린다(`if: always()`). 그래서 빨간불의 원인을 나중에 내려받아 볼 수 있다.
- **"sleep 8: 장치가 전부 붙고 첫 묶음이 DB 에 들어갈 시간"**: 바로 장애를 일으키면 "원래 들어오던 데이터"라는 기준선이 없어 유실을 셀 수 없다. 그래서 정상 흐름을 몇 초 먼저 만든다.

## 3. 용어와 단위
- **통합 테스트(integration test)**: 진짜 구성 요소(브로커·DB·수집기·장치)를 모두 붙여 한 번에 돌려 보는 테스트. 단위 테스트(가짜 위에서 함수 하나씩)와 짝을 이룬다.
- **CI(지속적 통합)와 러너(runner)**: push 할 때마다 테스트를 자동으로 돌리는 체계, 그리고 그 일을 하는 GitHub 의 일회용 리눅스 컴퓨터(`ubuntu-24.04`).
- **bash 스크립트**: 터미널 명령을 순서대로 적어 둔 파일. 줄 번호는 파일 첫 줄을 1로 센다.
- **종료 코드(exit code)**: 프로그램이 끝나며 남기는 숫자. 0 은 성공, 그 밖은 실패다. `pkill` 은 아무것도 못 찾으면 1 을 낸다.
- **`set -euo pipefail`**: 실패 즉시 멈춤(-e), 정의 안 된 변수 금지(-u), 파이프 중간 실패도 실패(pipefail).
- **trap / EXIT**: "이 신호나 사건이 오면 이 함수를 불러라"는 예약. EXIT 는 스크립트가 끝나는 사건이다.
- **시그널 SIGINT / SIGTERM**: 프로세스에 보내는 "멈춰 달라" 신호. SIGINT 는 Ctrl+C, SIGTERM 은 기본 종료 요청이다. 둘 다 프로그램이 받아서 곱게 끝낼 수 있다. SIGKILL 은 받을 기회 없이 즉시 죽인다.
- **`&`, `>`, `2>&1`, `$!`**: 각각 배경 실행, 출력을 파일로, 오류 출력도 같은 곳으로, 방금 배경으로 띄운 프로세스의 번호.
- **릴리스 패키지 / 매니페스트(manifest)**: 장치가 받아 설치하는 한 덩어리 파일(tar.gz)과, 그 파일의 이름 · sha256 · 크기 · 배포 정책을 적은 목록 파일(JSON).
- **sha256**: 파일 내용에서 계산한 64자리 지문. 받은 파일이 보낸 파일과 같은지 맞춰 본다.
- **A/B 슬롯**: 버전마다 폴더를 따로 두고 `current` 링크로 "지금 쓰는 것"을 가리키는 설치 방식. 새 버전은 다른 칸에 풀고 링크만 바꾼다(장표 138).
- **127.0.0.1(로컬호스트)**: 자기 자신을 가리키는 주소. 여기에만 묶은 서버는 다른 컴퓨터에서 닿지 않는다.
- **docker compose / 컨테이너 / 볼륨**: 여러 컨테이너(격리된 작은 실행 환경)를 파일 하나로 정의해 함께 띄우는 도구 / 그 실행 환경 / 컨테이너를 지워도 남는 데이터 저장소. `down -v` 는 볼륨까지 지운다.
- **Mosquitto / MQTT 브로커**: 장치가 보낸 메시지를 받아 구독자(수집기)에게 전해 주는 우체국 서버.
- **TimescaleDB / PostgreSQL**: 시간 순서 데이터에 강한 PostgreSQL 확장 DB. 텔레메트리가 여기 쌓인다.
- **pg_isready**: PostgreSQL 이 접속을 받는지 묻는 작은 도구.
- **유닉스 소켓 vs TCP**: 같은 컴퓨터 안에서만 쓰는 연결 통로 vs 네트워크(포트 번호)로 붙는 연결. 임시 서버는 앞의 것만 열었다.
- **마이그레이션(migration)**: 이미 데이터가 있는 DB 에 번호 붙은 SQL 파일로 표·컬럼을 추가해 가는 방법. 두 번 돌려도 안전하게 만든다.
- **QoS 0 / QoS 1**: MQTT 의 전달 약속. 0 은 한 번 보내고 끝(잃어도 모름), 1 은 받았다는 답(PUBACK)이 올 때까지 다시 보낸다(적어도 한 번).
- **지속 세션(clean_session=False)과 client_id**: 브로커가 그 이름(client_id)의 구독 정보와 못 전한 QoS 1 메시지를 기억해 두는 접속 방식. 이름이 고정이어야 브로커가 "같은 수집기"로 알아본다.
- **Hz**: 1초에 몇 번. 2 Hz = 0.5초마다 한 번.

## 4. 쉬운 예시
- 비유: 식당 개점 점검을 생각한다.
  - 먼저 "어떻게 끝나든 마감 청소는 한다"는 규칙을 문에 붙인다(trap cleanup).
  - 오늘 시험할 새 메뉴의 재료 상자 두 개 — 멀쩡한 것과 일부러 상하게 한 것 — 를 창고 앞에 내놓는다(0단계: 정상 패키지와 깨진 패키지, 로컬 HTTP).
  - 그다음 가스와 전기를 켠다(컨테이너).
  - 주방 앞의 "영업 중" 표지판(pg_isready)만 보고 손님을 받지 않는다. 실제로 손님이 들어오는 문(TCP)으로 들어가 시험 주문을 넣어 보고, 음식이 나올 때까지 기다린다(migrate --wait).
  - 11/04 에 표지판은 "영업 중"이었는데 주방은 아직 개업 준비(임시 서버) 중이었다.
  - 그 뒤 계산원(수집기)을 앉히고, 손님 10명(장치)을 들인다. 8초 뒤 계산대 화면(tail)을 한 번 본다.
- 숫자 예시
  - 장치 10대 × 2 Hz = 초당 20개. 8초를 기다리면 장치가 붙는 데 걸린 시간을 빼고 최대 약 160개가 흘러 들어온다.
  - 정상이라면 수집기 로그에 `msgs/s` 가 20 근처, `online` 이 10 인 줄이 보일 것이다(추정 — 코드의 출력 형식과 설정으로 계산한 기대값이고, 저장소에 이 로그 사본은 없다).
  - 다음 장의 5초짜리 장애 동안 보호 장치가 없다면 10 × 2 × 5 = 100개가 위험해진다(E13 의 계산). 그래서 장치당 2 Hz 가 의미 있다.
  - `--wait 120` 은 1초 간격이므로, DB 가 늦게 뜨면 최대 약 120번 다시 붙어 본다.
  - 패키지 하나는 약 21 KB 다(릴리스 v0.9.0 의 x86_64 패키지 21,446바이트 — 실행 파일 하나와 작은 설정 파일들). 10대가 내려받아도 0.2 MB 남짓이다.

## 6. 자주 하는 오해·함정
- **"컨테이너가 떴다 = DB 를 쓸 수 있다"**: 아니다. 컨테이너 안의 검사는 "프로세스가 있다"를 말할 뿐, "밖에서 쓸 수 있다"를 말하지 않는다. 헬스 체크(준비 확인)는 실제로 쓰는 쪽과 같은 길로 해야 한다(LOG 11/04 의 '배운 것').
- **"내 PC 에서 되면 CI 에서도 된다"**: 11/04 에는 반대였다. 내 PC 는 DB 볼륨에 데이터가 이미 있어 초기화 단계가 없었고, CI 는 늘 새 볼륨이었다. 깨끗한 환경을 재현하려면 `KEEP=0` 으로 지우고 다시 돌린다.
- **"`|| true` 는 오류를 숨기는 나쁜 습관이다"**: 여기서는 "없으면 그만"인 정리 명령에만 붙였다. 실패를 알아야 하는 명령(`migrate.py`, 패키지 만들기, 다음 장의 판정)에는 붙이지 않는다. 다음 장의 나쁜 펌웨어 주입과 깨진 패키지 배포는 예외다. 롤백이 일어나면 종료 코드 1 이 정상이라 따로 `|| true` 를 붙였다(63줄, 71줄).
- **"수집기만 QoS 1 이면 유실 0"**: 아니다. 장치도 `--telemetry-qos 1` 로 보내야 브로커가 메시지를 맡아 둔다. QoS 0 으로 보낸 메시지는 수집기가 없는 동안 사라진다. 그 차이가 표③에 숫자로 남아 있다.
- **"단위 테스트가 다 초록이면 안심"**: 11/05 에 수집기의 `request_stop` 함수가 지워진 채 push 됐다. 단위 테스트는 통과했지만, 통합 테스트에서 수집기가 시작 직후 `NameError` 로 죽어 CI 가 빨개졌다(LOG 11/05). 11/10 에도 같은 일이 있었다 — 진짜 설치의 단위 테스트는 절대 경로 슬롯만 썼고, 이 스크립트의 상대 경로 `--slot-root` 에서 첫 장치부터 실패했다(LOG 11/10 밤). 진입점과 실제 인자를 그대로 써 보는 곳이 이 스크립트다.
- **"0단계가 매번 패키지를 새로 만든다"**: `manifest.json` 이 이미 있으면 건너뛴다. WSL 에서 옛 패키지가 `build/release` 에 남아 있으면 그것을 쓴다 — 패키지 스크립트를 고친 뒤에는 `rm -rf build/release` 하고 돌린다.
- 추정: 이미 수집기가 떠 있는 WSL 에서 이 스크립트를 돌리면 경쟁이 생길 수 있다.
  - 53줄 pkill 은 신호만 보내고 기다리지 않는다. 옛 수집기가 마지막 적재를 끝내고 잠금을 놓기 전에 54줄의 새 수집기가 잠금을 시도할 수 있다.
  - 그러면 새 수집기가 "이미 수집기가 떠 있습니다" 를 찍고 물러난다.
  - CI 는 늘 빈 러너라 해당이 없고, 이런 사고가 기록된 적은 없다. WSL 에서는 돌리기 전에 손으로 띄운 수집기를 먼저 끝내 두는 편이 안전하다.

## 7. 면접 한 문장
"통합 테스트는 push 마다 진짜 Mosquitto·TimescaleDB 를 띄우는데, 처음엔 컨테이너 안 pg_isready 가 초기화용 임시 서버에 속아 CI 가 깨졌습니다. 그래서 '실제로 쓸 사람과 같은 길로 붙어 보며 기다리기'로 바꿨고, 어떻게 끝나든 정리가 도는 trap 을 걸어 같은 스크립트를 제 PC 와 CI 에서 똑같이 돌립니다. 지금은 릴리스 때와 같은 스크립트로 만든 진짜 패키지도 여기서 매번 깔아 봅니다."
