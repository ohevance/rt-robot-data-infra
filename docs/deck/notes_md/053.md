# 장표 053 — 단계 9 — 기록(rosbag2)과 관제(MQTT)는 다른 길 — 왜 둘인가
*위치: 1부 로봇을 움직이는 길 · 단계 9/10 기록 · ④ 판단 — 기록 vs 관제, 왜 둘인가*

## 1. 이 장표가 왜 있나
바로 앞 장표(052)에서 기록 파이프라인(E20)이 30초 동안 세 토픽을 설계 주기대로 빠짐없이 남기고, 요약표에 중력 처짐까지 자동으로 뽑아냈다는 것을 보았다. 그러면 자연스럽게 이런 질문이 생긴다. "이미 2부에 '관제'라는 길이 있어서 장치의 숫자를 서버로 올리는데, 왜 로봇 안에 따로 '기록'이라는 길을 또 만들었나? 하나로 합치면 안 되나?" 이 장표는 그 질문에 답하는 **판단 장표**다. 두 길을 '무엇을 · 어디에 · 왜 · 어떻게 검증하나' 네 줄로 나란히 놓고, 서로 목적이 달라서 둘 다 필요하다는 결론을 낸다. 이 판단이 서야 다음 장표(단계 10, 다리)로 넘어갈 수 있다 — "원본은 로봇 안에 남겼으니, 서버로는 요약만 보내자"가 다리의 설계 전제이기 때문이다.

## 2. 장표를 하나씩 읽기
장표는 왼쪽(기록)과 오른쪽(관제) 두 기둥으로 되어 있고, 각 기둥에 네 줄(무엇 · 어디에 · 왜 · 검증)이 있다. 같은 줄끼리 비교하며 읽으면 된다.

### 왼쪽 기둥 — "기록 — 로봇 안, 100 Hz 원본"
- 머리글의 뜻: 기록은 로봇 **안**(로봇에 붙은 컴퓨터)에서, 데이터를 **줄이지 않고 원본 그대로** 남기는 길이다. 100 Hz 는 `/joint_states` 토픽의 발행 주기(1초에 100번)다.
- "무엇: /joint_states 100 Hz · /joint_command 50 Hz · /rt_status 1 Hz 를 그대로" — 기록 대상은 세 토픽이다. `/joint_states`(관절의 실제 위치·속도, 노드가 100 Hz 로 냄), `/joint_command`(상위가 내린 목표, 50 Hz), `/rt_status`(1 kHz 루프의 1초 통계 JSON, 1 Hz). "그대로"가 핵심 — 평균을 내거나 솎아내지 않고 메시지 하나하나를 시각과 함께 저장한다.
- "어디에: 로봇 안 디스크(MCAP). 네트워크가 끊겨도 남는다" — 저장 위치는 로봇 안의 디스크이고, 파일 형식은 MCAP(rosbag2 의 기본 저장 형식)이다. 왜 로봇 안인가: 네트워크(무선·서버)가 끊겨도 기록은 계속된다. 사고가 나는 순간은 대개 네트워크도 불안한 순간이라, 사고 분석용 데이터를 네트워크 너머에 두면 정작 필요할 때 없다.
- "왜: 사고 분석·제어 튜닝은 원본으로 한다 (블랙박스 영상)" — 1초 요약으로는 "0.3초 동안 관절이 어떻게 흔들렸나"를 알 수 없다. 제어 이득(게인)을 조정하거나 사고 원인을 찾으려면 10 ms 단위의 원본이 필요하다. 자동차 블랙박스 영상과 같다.
- "검증: 설계 Hz 대로 찍혔나, 틈은 없나, 추종 오차는 얼마나 — summary.md 가 자동으로" — 기록 파일이 있다는 것과 기록이 **믿을 만하다**는 것은 다르다. 그래서 `bag_to_csv.py` 가 자동으로 (1) 실제 Hz 가 설계값(100/50/1)과 맞나, (2) 설계 주기의 3배 넘게 벌어진 공백(틈)이 있나, (3) 목표와 실제의 차이(추종 오차)는 얼마나 되나를 `summary.md` 에 쓴다. 11/05 실측: 100.0 / 50.0 / 1.0 Hz, 틈 0, shoulder_lift 0.0191 rad.

### 오른쪽 기둥 — "관제 — 서버로, 1 Hz 요약"
- 머리글의 뜻: 관제는 로봇 **밖**(서버)으로, 데이터를 **1초에 한 번 요약**해서 보내는 길이다.
- "무엇: rt_status 의 요약(wake p99, 드롭, 상태)과 장치 상태" — 서버로 가는 것은 100 Hz 관절값이 아니라 `rt_status` 안의 요약 숫자들이다. wake p99(1초 동안 1,000번 깬 것 중 99번째로 늦은 깨어남 지연), 드롭(로깅 벨트가 버린 수), 상태(READY/RUNNING/FAULT 등). 실제로 다리(ros_status_bridge.py)의 `metrics()` 함수가 보내는 필드는 loop_hz, wake_p99_us, wake_max_us, work_p99_us, timing_drops, watchdog_trips, rmw, backend, sched_fifo 다(파일 45~60줄).
- "어디에: MQTT → 수집기 → TimescaleDB → Grafana (2부)" — 서버 쪽 길. MQTT 브로커가 중계하고, 수집기가 1초 묶음으로 DB(TimescaleDB)에 넣고, Grafana 가 화면에 그린다. 이 길의 자세한 내용이 2부다.
- "왜: 수십 대를 한 화면에서 — 원본 100 Hz × 50대를 서버로 보내면 양이 100배" — 관제의 목적은 '한 대를 자세히'가 아니라 '여러 대를 한눈에'다. 한 대가 100 Hz 로 보내면 1 Hz 요약보다 100배 많은 메시지가 서버로 간다. 50대면 초당 5,000개. 묶음 적재(1초 1번 COPY)로 설계한 수집기(2부 ③)의 전제가 깨진다.
- "검증: 전달 지연 p95, 유실 0, 장애 복구 시간 (표③)" — 관제 길의 품질은 다른 잣대로 잰다: 장치에서 측정한 시각과 수집기 도착 시각의 차이(전달 지연) p95, 장애 때 잃은 메시지 수(유실, seq 로 센다), 장애 뒤 전 장치가 돌아오는 시간. 이것이 표③이다.

## 3. 용어와 단위
- **rosbag2 / MCAP**: ROS 2 의 '녹화기'와 그 파일 형식. 여러 토픽의 메시지를 받은 시각과 함께 한 파일에 순서대로 담는다. 나중에 파이썬(`rosbag2_py`)으로 그대로 읽는다.
- **MQTT**: 장치와 서버 사이의 가벼운 메시지 프로토콜. 가운데 '우체국'(브로커)이 있어 장치는 발행만 하고 서버는 구독만 한다.
- **토픽**: 이름표가 붙은 데이터 흐름. ROS 2 에도 MQTT 에도 같은 말이 있다(둘은 다른 시스템이다).
- **Hz(헤르츠)**: 1초에 몇 번. 100 Hz = 10 ms 마다 한 번, 50 Hz = 20 ms 마다, 1 Hz = 1초에 한 번.
- **p99 / p95**: 100번 중 99번째(95번째)로 나쁜 값. 평균보다 '꼬리'를 보기 위한 통계.
- **wake(깨어남 지연)**: 1 ms 마다 깨기로 한 RT 스레드가 실제로는 얼마나 늦게 깼나. 단위 us(마이크로초, 100만분의 1초). 1 ms = 1,000 us.
- **드롭(drop)**: RT 스레드가 로깅 벨트(링 버퍼)에 올리려다 벨트가 꽉 차서 버린 수. 0 이어야 정상.
- **추종 오차**: 같은 시각의 |목표 − 실제 위치|. 단위 rad(라디안). 1 rad = 57.3°. 0.0191 rad ≈ 1.1°.
- **틈(gap)**: 연속한 두 메시지 사이가 설계 주기의 3배보다 벌어진 곳. 100 Hz 면 30 ms 넘는 공백.
- **TimescaleDB / Grafana**: 시간 데이터용 PostgreSQL 확장 / 그 데이터를 그래프로 보여 주는 웹 화면.
- **seq(일련번호)**: 장치가 메시지마다 1씩 올려 붙이는 번호. 빠진 번호 = 유실.

## 4. 쉬운 예시
- 비유: 자동차 블랙박스와 보험사 앱. 블랙박스(기록)는 차 안 SD 카드에 30 fps 영상을 빠짐없이 남긴다 — 사고 분석은 이걸로 한다. 보험사 앱(관제)은 1분마다 "속도 60 km/h, 위치 OK" 한 줄만 서버로 보낸다 — 수천 대의 차를 한 화면에서 보려고. 영상을 전부 서버로 보내면 통신비도, 서버도 감당이 안 된다. 그리고 영상이 **빠짐없이 30 fps 로** 찍혔는지를 사람이 다 볼 수 없으니 자동 검사(틈 0, fps 확인)가 있어야 한다 — 그것이 `summary.md` 다.
- 숫자 예시: 로봇 50대가 100 Hz 원본을 서버로 보내면 초당 50 × 100 = 5,000개 메시지. 1 Hz 요약이면 초당 50개. 100배 차이. 수집기는 1초에 한 번 묶어서 DB 에 넣는데(2부 ③), 5,000개 × 6 관절 × 2(위치·속도) 숫자를 매초 적재하면 설계를 처음부터 다시 해야 한다.

## 6. 자주 하는 오해·함정
- "기록도 서버에 두면 안전하지 않나?" — 반대다. 네트워크가 끊긴 순간의 데이터가 가장 중요한데, 서버에만 두면 그 순간이 비어 있다. 로봇 안에 먼저 남기고, 필요하면 나중에 파일을 올린다.
- "요약을 보내니 관제는 정보를 잃는 것 아닌가?" — 관제의 질문은 "지금 어느 로봇이 이상한가"이지 "0.3초 동안 어떻게 흔들렸나"가 아니다. 질문이 다르니 데이터의 굵기도 다르다. 이상한 로봇을 찾으면 그 로봇의 기록 파일을 연다.
- 실제로 겪은 함정(11/05): 기록 첫 시도가 조용히 안 끝났다. `timeout` 이 recorder 를 뒤 프로세스 그룹에 두어 키보드 읽기에서 정지 신호(SIGTTIN)를 받은 것. `timeout --foreground` + `--disable-keyboard-controls` 로 해결(장표 052, `docs/LOG.md` 11/05).
- `/rt_status` 는 두 길 모두에 나온다. 기록 길에서는 원본 JSON 을 그대로 파일에, 관제 길에서는 그 JSON 의 몇 필드를 장치 텔레메트리로. 같은 데이터가 두 번 쓰이는 것이지 모순이 아니다.

## 7. 면접 한 문장
"관제는 1 Hz 요약을 서버로, 기록은 100 Hz 원본을 로봇 안에 — 목적이 달라서 두 길이고, 기록 쪽은 CSV 와 검증 요약까지 자동이라 30초 기록에서 100.0 Hz·틈 0·처짐 1.1° 가 사람 손 없이 나온다."
