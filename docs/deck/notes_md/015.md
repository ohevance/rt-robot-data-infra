# 장표 015 — 단계 2 그림 — ROS 2 / DDS: 두 프로세스 사이를 미들웨어가 잇는다 (발견 → 직렬화 → 전송 → 콜백)
*위치: 1부 로봇을 움직이는 길 · 단계 2/10 DDS 전달 · ② 그림 — 두 프로세스 사이*

## 1. 이 장표가 왜 있나
들머리(014)에서 "전달은 DDS 가 하고, 우리 크기에서는 손실 0" 이라는 결론을 봤다. 그러면 "그 DDS 가 실제로 두 프로세스 사이에서 무엇을 하나, 우리 코드는 어디서 끝나고 어디서 다시 시작하나"가 궁금해진다. 이 장표는 발행자 프로세스에서 구독자 프로세스까지 메시지가 지나가는 층을 왼쪽 위 → 아래 → 오른쪽 → 위 순서의 U 자로 그린다. 우리 코드는 양 끝(발행 명령줄과 `on_command()`)에만 있고, 가운데 다섯 상자는 전부 ROS 2 와 DDS 가 한다는 것을 보이는 것이 목적이다. 오른쪽 좁은 상자는 그 전달의 성격을 정하는 QoS 세 가지다.

## 2. 장표를 하나씩 읽기
도형을 U 자 순서로 따라간다. 색: 회색 = 바깥에서 들어온 것, 파란 = ROS 2 층, 보라 육각형 = DDS, 노란 = 전송 매체와 QoS, 민트 = 우리 노드.

- 회색 "발행자 프로세스 (ros2 topic pub · 계획기)": 단계 1 의 명령을 내는 프로세스. 이 그림의 출발점.
- ↓ 파란 "rclcpp/rclpy → RMW 층 (rmw_fastrtps_cpp 또는 rmw_cyclonedds_cpp)": 발행자가 쓰는 ROS 2 클라이언트 라이브러리(C++ 는 rclcpp, 파이썬은 rclpy)가 RMW(ROS MiddleWare, ROS 2 와 DDS 사이의 어댑터 층)를 부른다. 어댑터 이름이 곧 구현체 이름이다 — `rmw_fastrtps_cpp` 면 Fast DDS, `rmw_cyclonedds_cpp` 면 Cyclone.
- ↓ 보라 육각형 "DDS 참여자 — 발견(discovery) · 직렬화 · 전송": DDS 가 하는 세 가지. 발견 = 같은 토픽 이름을 쓰는 상대를 네트워크에서 찾기, 직렬화 = 메시지 구조체를 바이트 열로 펴기, 전송 = 보내기.
- → 노란 물결 "같은 PC: 공유 메모리/루프백, 다른 PC: UDP 멀티캐스트": 실제로 바이트가 지나가는 매체. 표②의 측정은 같은 PC 였으므로 공유 메모리와 루프백(자기 자신에게 보내는 가상 네트워크)이 섞인 수치다 — 두 기기 사이의 UDP 는 재지 않았다.
- 화살표 글 "표②: 64 B~64 KB 손실 0, RTT p50 0.9~1.2 ms": 이 매체를 왕복한 결과. 들머리의 결과와 같은 숫자.
- → 보라 육각형 "DDS 참여자 — 수신 · 역직렬화 · QoS 처리": 받는 쪽 DDS. 바이트 열을 다시 구조체로 만들고(역직렬화), QoS 에 따라 재전송 요청·버리기 등을 처리한다.
- ↑ 파란 "RMW 층 → rclcpp 실행기 (콜백 스레드, 일반 우선순위)": 받은 메시지가 ROS 2 실행기 스레드로 올라간다. 010 장표의 왼쪽 세계가 여기다 — 일반 우선순위.
- ↑ 민트 "구독자 프로세스 rt_control_node — on_command() 가 불린다 (단계 3)": 우리 코드가 다시 시작하는 지점. 노드 입장에서는 "`on_command(msg)` 가 불렸다"가 전부다.
- 노란 세로 상자 "QoS (품질 약속)": `reliable` = 못 받으면 재전송, `best_effort` = 빠르지만 잃을 수 있음, `depth 10` = 큐 깊이(보관하는 최근 메시지 수). 점선으로 받는 쪽 DDS 에 붙어 있다 — QoS 처리가 거기서 일어나기 때문. 우리 노드의 구독은 깊이 10 으로 선언되어 있다(`rt_control_node.cpp:110-111`).
- 가운데 글 네 줄:
  - "발행자와 구독자는 서로를 모른다 — DDS 가 토픽 이름으로 '발견'한다": 발행 명령줄은 노드가 있는지 몰라도 되고, 노드는 누가 보내는지 모른다.
  - "노드는 메시지가 어떻게 왔는지 모른다 — on_command(msg) 만 불린다": 그래서 노드 코드에는 통신 코드가 한 줄도 없다.
  - "구현체는 환경 변수 RMW_IMPLEMENTATION 으로 바꾼다. rt_status 에 실제 쓰인 rmw 가 찍힌다": 노드가 `rmw_get_implementation_identifier()` 로 자기 구현체 이름을 1초 상태에 넣는 이유 — 어느 구현체였는지 모르면 숫자를 설명할 수 없다.
  - "큰 메시지(1 MB)에서는 구현체·QoS 에 따라 손실이 갈린다 — 영상·점군을 보낼 때의 문제": 표②의 1 MB 결과를 가리킨다.
- 범례: 소스 위치 — 구독 선언(QoS depth 10) `rt_control_node.cpp:110-111`, 측정기 `dds_bench/rtt_bench.py`(ping/pong), 표 `scripts/make_table2.py → docs/measurements/table2.md`, 실험 사슬은 3부 장표 87~88.

## 3. 용어와 단위
- 프로세스: 운영체제가 따로 띄운 프로그램 하나. 메모리를 공유하지 않으므로 사이를 오가려면 통신이 필요하다.
- rclcpp / rclpy: ROS 2 의 C++ / 파이썬 클라이언트 라이브러리. 노드·토픽·타이머를 만드는 API.
- RMW(ROS MiddleWare): ROS 2 가 DDS 구현체를 갈아 끼우는 어댑터 층. `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` 처럼 환경 변수로 고른다.
- DDS 참여자(participant): DDS 통신에 참가하는 단위. 프로세스마다 보통 하나.
- 발견(discovery): 같은 토픽 이름을 쓰는 상대를 찾는 과정. 다른 PC 에서는 UDP 멀티캐스트로 "나 여기 있다"를 알린다.
- 직렬화 / 역직렬화: 메모리 속 구조체 ↔ 바이트 열. 보내려면 펴고(직렬화), 받으면 다시 세운다(역직렬화).
- 공유 메모리 / 루프백: 같은 PC 안에서 쓰는 빠른 전송. 공유 메모리는 복사 없이 같은 메모리를 보는 방식, 루프백은 자기 자신에게 보내는 가상 네트워크.
- UDP 멀티캐스트: 네트워크로 여러 수신자에게 한 번에 보내는 방식. DDS 의 기본 발견 수단.
- QoS depth 10: KEEP_LAST 10 — 최근 10개만 보관, 11번째가 오면 가장 오래된 것을 버린다.
- RTT p50 0.9~1.2 ms: 왕복 중앙값. 1 ms = 1,000 us.

## 4. 쉬운 예시
비유: 국제 우편이다. 보내는 사람(발행자)이 편지를 쓰면 우체국 창구(rclcpp → RMW)가 받아 분류소(DDS 참여자)로 넘기고, 분류소는 주소(토픽 이름)로 받을 분류소를 찾아(발견) 봉투에 넣어(직렬화) 운송(전송)한다. 받는 쪽 분류소가 봉투를 열고(역직렬화) 등기면 누락 확인을 하고(QoS 처리), 집배원(실행기 스레드)이 문을 두드리면 받는 사람(on_command) 이 봉투를 받는다. 보내는 사람과 받는 사람은 서로 얼굴을 모른다. 숫자 예시: 왕복 1.0 ms 면 편지가 가는 데 약 0.5 ms — 그런데 그 1.0 ms 에는 파이썬 측정기의 오버헤드 수백 us 가 들어 있다(C++ 끼리는 더 짧을 것 — 추정).

- 확인: rt_status 에 rmw 이름 — `rt_control_node.cpp:39` (`#include "rmw/rmw.h"  // rmw_get_implementation_identifier`) 와 `publish_status()` (:233-291).
- 확인: 표② 숫자 — `docs/measurements/table2.md`. 64 B~64 KB 12줄 손실 0.0, p50 868~1,236 us.
- 확인: 같은 PC 공유 메모리가 섞인다는 것 — `table2.md` 각주 "같은 호스트에서는 공유 메모리 전송이 섞이므로 네트워크 수치가 아니다", `E04.md` §2.
- 확인: 두 구현체 이름 — `E04.md` §2 (`rmw_fastrtps_cpp` · `rmw_cyclonedds_cpp`).
- 추정: 다른 PC 사이 UDP 멀티캐스트 경로의 지연 — 이 저장소에서는 재지 않았다. 그림의 "다른 PC" 상자는 일반적인 DDS 동작 설명이다.

## 6. 자주 하는 오해·함정
- "노드 코드 어딘가에 소켓 코드가 있겠지" — 없다. 노드는 `create_subscription` 한 줄과 `on_command()` 만 가진다. 통신은 전부 RMW 아래에서 일어난다.
- 같은 PC 수치를 네트워크 수치로 옮겨 말하면 안 된다. 두 기기 사이는 UDP 라서 지연·손실 특성이 다르다.
- 함정(LOG 11/04): `ros2 topic echo` 가 토픽을 못 보는데 노드는 살아 있었다. 원인은 아침에 다른 RMW 로 떠 있던 ros2 데몬. `ros2 daemon stop` 으로 해결. RMW 를 바꿔 가며 실험하면 데몬을 지운다.
- depth 10 은 "10개까지 보관"이지 "10개까지 보장"이 아니다. 100 Hz 로 밀려드는 1 MB 는 재전송 전에 밀려났다(E04 §4).

## 7. 면접 한 문장
"우리 코드는 양 끝에만 있습니다 — 보내는 쪽의 publish 와 받는 쪽의 on_command — 그 사이의 발견·직렬화·전송·QoS 처리는 전부 DDS 가 하고, 어느 구현체가 그 일을 했는지는 노드가 rt_status 에 찍어 두기 때문에 표②의 숫자를 설명할 수 있습니다."
