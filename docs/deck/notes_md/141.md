# 장표 141 — 덧붙임 (11/10~11) — 사고와 해결 (3): 실제 기계에서 처음 돌리자 나온 것, 그리고 같은 실수 두 번
*위치: 7부 왜·사고·방식 · 덧붙임 사고 3/3 (11/10~11)*

## 1. 이 장표가 왜 있나
앞의 네 장표(137~140)는 11/10~11 에 만든 것 — 릴리스 → 배포와 클라우드 운영 층 — 을 그림 · 코드 · 숫자로 보였다. 잘된 쪽만 보인 셈이다. 이 저장소는 7부에서 "결정대로 만들었지만 전부 처음부터 돌지는 않았다"를 따로 적어 왔고(장표 128~129, 11건), 그 표는 11/05 에서 끝난다. 그 뒤 이틀은 성격이 달랐다 — 처음으로 **내 것이 아닌 기계**(클라우드 서버)와 **오래 꺼 두었던 기계**(Pi)에 설치 스크립트를 돌렸고, 처음으로 서버를 밤새 켜 두었다. 작업본에서는 문법과 인증서까지만 확인할 수 있었던 것들이다. 그래서 질문은 "실제 기계에서 처음 돌리자 무엇이 나왔나, 그리고 거기서 무엇을 배웠나"다. 이 장표는 그 이틀의 아홉 건을 "무엇 · 원인 · 해결 · 기록(날짜)" 네 열의 표로 적는다. 제목의 "같은 실수 두 번"은 아홉 건 가운데 둘이 **이미 겪고 문서에 적어 둔 실수의 반복**이었다는 고백이다. 다음 장표(142)는 여덟째 줄 — 틀린 숫자 707 ms — 을 어떻게 갈랐는지를 따로 편다.

## 2. 장표를 하나씩 읽기
표는 머리말 한 줄 + 아홉 행. 열은 넷이다 — "무엇"(겉으로 보인 증상), "원인"(왜 그랬나), "해결"(무엇을 고쳤나 — 그 자리만이 아니라 다시 안 나오게), "기록"(날짜, 원문은 `docs/LOG.md` 의 그날 항목). 위에서 아래로 시간 순이다.

- 행 1 "서버 설치의 보존 정책 단계 실패(add_retention_policy does not exist)" / 원인 "DB 컨테이너의 초기화용 임시 서버에 pg_isready 가 '준비됨'이라 답했다 — 11/04 CI 에서 겪은 것과 같은 원인을 새 스크립트에 다시 썼다" / 해결 "'응답하는가'가 아니라 '확장 1 + 표 3 이 생겼는가'를 기다린다. 새로 쓸 때는 실패 사례 표부터 본다" / 11/10: 서버 설치 스크립트(`deploy/ec2/setup.sh`)의 마지막 단계는 DB 에 "14일 지난 기록은 지워라"는 보존 정책을 넣는다. 그 명령이 "그런 함수가 없다"로 실패했다. DB 컨테이너는 처음 켜질 때 초기화용 임시 서버를 잠깐 띄우는데, "준비됐니?"라고 묻는 도구(`pg_isready`)는 그 임시 서버에도 "예"라고 답한다 — 그래서 초기화 스크립트가 확장 기능과 표를 만들기 전에 명령을 보낸 것이다. **이것은 11/04 에 CI 에서 겪고 실패 사례 표에 적어 둔 것과 같은 원인이다**(장표 117, 128). 그때는 통합 테스트 스크립트만 고쳤고, 일주일 뒤 새 스크립트를 쓰면서 같은 기다리는 방식을 다시 썼다. 해결은 두 겹 — 스크립트는 "응답하는가"가 아니라 "필요한 것(확장 1개와 표 3개)이 실제로 생겼는가"를 기다리게 고쳤고, 규칙으로는 "DB 를 기다리는 코드를 새로 쓸 때는 실패 사례 표를 먼저 본다"를 더했다. 같은 실수 두 번의 첫째다.
- 행 2 "서버가 장치를 거부하는데 장치 화면은 정상 때와 똑같다" / 원인 "여러 줄을 한꺼번에 붙여 넣어 비밀번호 입력(read -s)이 건너뛰어짐 → 0자" / 해결 "한 줄씩 + 글자 수 확인. Pi 설치 스크립트가 빈 값·자리표시·공백을 서비스 등록 전에 거부" / 11/10: 비밀번호를 화면에 보이지 않게 입력받는 명령(`read -s`)을 다른 명령들과 함께 한꺼번에 붙여 넣으면, 붙여 넣은 다음 줄이 비밀번호 자리로 들어가거나 입력이 건너뛰어진다. 비밀번호가 0자가 됐다. 장치 쪽 화면은 평소와 똑같은 시작 문구를 찍었고("TLS user=fleet"), 서버만 조용히 거부했다 — 증상이 "아무 일도 없어 보임"이라 찾기 어려웠다. 해결: 안내를 "한 줄만 실행 → 붙여 넣기 → 글자 수 확인"으로 바꾸고, Pi 설치 스크립트(`deploy/pi/install.sh`)가 설정 값이 비어 있거나, 예시의 자리표시 그대로이거나, 공백이 섞여 있으면 서비스를 등록하기 **전에** 멈추게 했다.
- 행 3 "Pi 에서 에이전트가 뜨지 않음" / 원인 "paho 가 없었고 안내한 apt 패키지는 1.6(필요 2.0 이상) — 틀린 안내였다. pip 설치는 자동 보안 업데이트가 dpkg 잠금을 30분 넘게 쥐어 막혔다" / 해결 "PyPI 의 순수 파이썬 휠을 받아 sha256 확인 뒤 사용자 폴더에(deploy/pi/get_paho.py)" / 11/10: 두 가지가 겹쳤다. ① Pi 에는 MQTT 라이브러리(paho)가 없었고, 설치 안내에 적어 둔 우분투 패키지는 버전이 1.6 이었다 — 에이전트는 2.0 이상의 방식으로 쓰여 있다. 안내가 틀렸던 것이다. ② 다른 방법(pip)을 깔려고 했더니, 오래 꺼 두었던 Pi 가 켜지자마자 보안 업데이트 70개쯤을 한꺼번에 깔고 있어서 패키지 설치의 잠금을 30분 넘게 쥐고 있었다. 업데이트를 강제로 끊지 않았다. 돌아간 길: 라이브러리의 배포 파일(순수 파이썬이라 컴파일이 필요 없다)을 직접 내려받아 지문을 확인하고 사용자 폴더에 풀었다. 이 방법을 스크립트(`deploy/pi/get_paho.py`)로 넣어 설치 스크립트가 필요할 때 부른다.
- 행 4 "대시보드 '온라인 장치 4' (실제 1대), 지연 패널은 빨강" / 원인 "수집기가 본 적 있는 장치 전부의 last_seen 을 매초 지금으로 덮어썼다. 패널은 색 기준이 없어 기본값(80)이 걸렸다" / 해결 "최근 5초 안에 보낸 장치만, 그 장치의 마지막 도착 시각으로 + 테스트. 패널마다 색 기준을 명시" / 11/10: 서버에 붙어 있는 것은 Pi 1대인데 대시보드의 "온라인 장치" 숫자가 4 였다 — 30분 전에 시험하고 끈 가상 장치 3대가 살아 있는 것으로 보였다. 수집기가 "한 번이라도 본 장치 전부"의 마지막 본 시각을 매초 **지금**으로 덮어쓰고 있었기 때문이다. 지금까지 안 보인 이유: 실험이 끝나면 수집기도 같이 내렸다. "수집기는 계속 돌고 장치만 떠난" 상태는 24시간 서버에서 처음 생겼다. 고친 것: 최근 5초 안에 메시지를 보낸 장치만 갱신하고, 값은 그 장치의 마지막 메시지가 도착한 시각으로(장표 071). 고치기 전 코드에서 실패하고 고친 뒤 통과하는 테스트를 더했다. 같은 화면의 지연 패널이 빨갰던 것은 별개 — 색의 기준을 주지 않아 대시보드 도구의 기본값(80 이상이면 빨강)이 걸렸고, 먼 서버의 지연 150 ms 가 빨갛게 보였다. 패널마다 기준을 적었다.
- 행 5 "CI 가 3시간 빨강 — 산출물 OTA 가 첫 장치에서 exit 127" / 원인 "통합 테스트는 상대 경로 슬롯, 단위 테스트는 절대 경로만 썼다. 패치 다섯 개를 한꺼번에 push 하고 CI 를 보지 않았다(11/05 에 적은 규칙을 어겼다)" / 해결 "설치·자가 점검·훅이 경로를 절대 경로로 굳힌다 + 상대 경로 테스트" / 11/10: 원인이 둘이다. 기술적 원인 — 통합 테스트는 장치의 설치 자리를 상대 경로로 주는데, 설치 코드가 그 자리 안으로 들어가서 자가 점검 스크립트를 부르며 그 상대 경로를 그대로 써서 파일을 못 찾았다(종료 코드 127 = 그런 파일 없음, 장표 118 · 138). 단위 테스트와 손으로 한 확인은 절대 경로만 써서 통과했었다. 사람의 원인 — 패치 다섯 개(26~30)를 한꺼번에 push 하고는 서버 작업을 하느라 CI 결과를 보지 않았다. 빨간 배지가 3시간 동안 저장소 첫 화면에 걸려 있었다. **"문서 커밋이라도 push 뒤 CI 를 본다"는 11/05 에 사고를 겪고 적어 둔 규칙이다**(장표 129). 같은 실수 두 번의 둘째다. 해결: 설치 코드가 경로를 절대 경로로 굳히고(장표 138 의 201줄), 상대 경로 자리에 설치하는 테스트를 더했다 — 고치기 전 코드에서 CI 와 같은 오류 문장으로 실패하는 것을 확인했다.
- 행 6 "'다음 부팅도 RT 커널인가'의 확인 기준이 다음 날 서로 다른 답을 냈다" / 원인 "/boot/vmlinuz 링크는 마지막에 설치된 패키지일 뿐, Pi 가 부팅 때 읽는 것은 /boot/firmware 의 파일" / 해결 "부팅 파일의 sha256 을 RT 커널 파일과 직접 비교 — 기준은 '그 시스템이 실제로 읽는 것'으로" / 11/11: 깨진 것이 코드가 아니라 **확인 방법**인 경우. Pi 의 자동 업데이트 목록에 일반 커널이 있어서, 다시 켰을 때도 실시간(RT) 커널로 올라오는지가 걱정이었다(표①의 숫자는 RT 커널에서만 나온다). 11/10 에는 "명령 둘의 결과가 모두 realtime 이면 안전"이라고 기준을 적었다. 다음 날 아침 그 둘이 서로 다른 답을 냈다 — 하나는 RT 커널, 하나(`/boot/vmlinuz` 링크)는 일반 커널. 알고 보니 그 링크는 "마지막에 설치된 커널 패키지"를 가리킬 뿐이고, Pi 가 켜질 때 실제로 읽는 파일은 다른 폴더(`/boot/firmware`)에 있다. 그 파일의 지문을 RT 커널 파일과 직접 비교해 같음을 확인했다. 배운 것: 확인 기준을 정할 때는 그 시스템이 **실제로 읽는 것**을 직접 본다.
- 행 7 "깨진 패키지를 거부한 장치가 한 세대 뒤로 내려감 (실행 전에 찾음)" / 원인 "ota_rollback 이 '이전 슬롯이 있는가'를 먼저 봤다 — 시험은 전부 빈 슬롯에서 시작해 우연히 옳은 가지로 갔다" / 해결 "'직전 설치가 실패했는가'를 먼저 본다 + '정상 2번 → 깨진 것' 테스트" / 11/11: 아홉 건 가운데 유일하게 **돌려서가 아니라 읽어서** 찾은 것. 장치가 되돌리기 명령을 받았을 때의 판단 순서가 틀려 있었다(장표 081, 139). 깨진 패키지를 거부한 장치는 아무것도 바꾸지 않았으니 되돌릴 것이 없는데, 그 전에 정상 릴리스가 두 번 깔려 있었다면 멀쩡한 현재 버전에서 한 세대 옛 버전으로 내려갔을 것이다. 모든 시험이 빈 자리에서 "정상 1번 → 깨진 것 1번"으로 시작해 우연히 옳은 길로 갔다. 첫 태그를 올리기 전에 릴리스 경로의 코드를 처음부터 다시 읽다가 찾았다.
- 행 8 "서버까지 왕복 707 ms (같은 구간의 편도는 146 ms)" / 원인 "보내는 간격 0.2초가 왕복보다 짧아 양쪽의 Nagle 이 붙잡았다 — 재는 방법이 만든 값" / 해결 "기본 간격을 1초로 → 290 ms. 예측을 먼저 적고 검증(다음 장표)" / 11/11: 깨진 것이 **숫자**인 경우. 서버까지의 왕복 시간을 재는 도구를 만들어 처음 쟀더니 707 ms 가 나왔다. 같은 구간의 편도가 146 ms 로 보이는데 왕복이 707 일 수는 없다. 원인은 재는 방법이었다 — 0.2초마다 한 건씩 보냈는데 그 간격이 왕복(약 0.29초)보다 짧아, 통신 규약(TCP)의 "작은 조각은 모아서 보낸다"는 기능이 메시지를 붙잡았다. 간격을 1초로 하니 290 ms. 이 줄의 자세한 경위가 다음 장표다.
- 행 9 "공개한 장표(pptx) 108번에 계정 이름이 남아 있었다" / 원인 "11/06 의 점검은 git grep — pptx·docx 안(ZIP)은 보지 못한다. 장표 생성 코드 폴더도 .gitignore 의 build/ 에 걸려 저장소에 없었다" / 해결 "pptx·docx 를 풀어서 보는 점검 스크립트 + 생성 코드를 저장소에" / 11/11: 깨진 것이 **점검**인 경우. 11/06 에 공개 저장소의 문서에서 사설 주소 · 계정 이름 · 개인 PC 경로를 찾아 자리표시로 바꾸고 "점검했다"고 적었다. 그런데 이 장표 파일의 108번 장표(환경 사이의 복사 명령)에 계정 이름이 그대로 있었다. 그때의 점검 명령은 저장소의 **글자 파일**만 찾는다 — 발표 파일(pptx)과 설명 문서(docx)는 압축된 묶음이라 그 안의 글자를 보지 못한다. 그리고 장표를 만드는 코드 폴더(`docs/deck/build/`)가 무시 목록의 `build/` 규칙에 걸려 저장소에 올라가 있지 않아, 원본 글에서 찾을 수도 없었다. 해결: 장표의 그 글을 자리표시로 고치고, pptx 와 docx 를 풀어서 안을 보는 점검 스크립트를 만들고, 생성 코드를 저장소에 넣었다. 한계: 저장소의 **이전 이력**에는 옛 pptx 가 남아 있다(계정 이름일 뿐 비밀번호나 주소는 아니다 — 이력을 다시 쓰지는 않았다).

## 3. 용어와 단위
- 보존 정책(retention policy): 오래된 기록을 자동으로 지우는 DB 의 설정. 여기서는 14일.
- `pg_isready`: DB 가 접속을 받는지 묻는 작은 도구. "받는다"가 "쓸 준비가 됐다"는 뜻은 아니다.
- 확장(extension): DB 에 기능을 더하는 꾸러미. 시계열 기능(TimescaleDB)이 확장이다.
- `read -s`: 터미널에서 입력을 화면에 보이지 않게 받는 명령. 비밀번호 입력에 쓴다.
- 자리표시: 예시 파일에 `<값>` 처럼 채워 넣으라고 비워 둔 자리.
- paho / 휠(wheel) / PyPI: 파이썬의 MQTT 라이브러리 / 파이썬 꾸러미의 배포 파일 형식 / 파이썬 꾸러미 저장소.
- dpkg 잠금: 우분투가 꾸러미를 설치하는 동안 다른 설치를 막는 잠금. 한 번에 하나만 설치할 수 있다.
- 자동 보안 업데이트(unattended-upgrades): 우분투가 스스로 보안 패치를 내려받아 설치하는 기능.
- `last_seen`: 장치 목록 표에 적는 "그 장치를 마지막으로 본 시각".
- 종료 코드 127: 셸이 "그런 명령(파일)을 못 찾았다"고 알리는 번호.
- 상대 경로 / 절대 경로: 지금 있는 폴더를 기준으로 한 경로(`build/…`) / 맨 위부터 적은 경로(`/home/…`). 폴더를 옮기면 상대 경로는 다른 곳을 가리킨다.
- RT 커널: 실시간 패치(PREEMPT_RT)가 들어간 리눅스 커널. `/boot/firmware`: Raspberry Pi 가 켜질 때 커널 파일을 읽는 폴더.
- Nagle: 작은 데이터 조각을 모았다가 한 번에 보내는 TCP 의 기능(다음 장표).
- pptx · docx: 파워포인트 · 워드 파일. 속은 여러 파일을 묶은 압축 파일(ZIP)이라 글자 찾기 도구가 안을 보지 못한다.
- `.gitignore`: 저장소에 넣지 않을 파일의 목록. `build/` 한 줄이 이름이 build 인 폴더를 전부 뺀다.

## 4. 쉬운 예시
- 비유(행 1 과 "같은 실수 두 번"): 식당이 "영업 중" 팻말을 걸었지만 주방은 아직 재료를 손질하는 중이다. 팻말만 보고 주문을 넣으면 "그런 메뉴 없습니다"가 돌아온다. 일주일 전에 같은 일을 겪고 "팻말이 아니라 메뉴판이 걸렸는지 본다"고 수첩에 적어 두었는데, 새 지점을 열면서 수첩을 안 보고 다시 팻말만 봤다. 수첩은 적는 것으로 끝나지 않는다 — 새 지점을 열 때 먼저 펴 봐야 한다.
- 비유(행 6): "가게 문이 잠겼나"를 확인하려고 열쇠 보관함의 열쇠 위치를 봤다. 그런데 보관함은 "마지막에 쓴 열쇠"를 보여 줄 뿐이다. 확인하려면 문고리를 직접 당겨 본다.
- 숫자 예시(행 4): 붙어 있는 장치 1대, 30분 전에 끈 장치 3대. 고치기 전 — 수집기가 네 대 모두의 마지막 본 시각을 매초 지금으로 덮어쓰니 "최근 5초 안에 본 장치"가 4. 고친 뒤 — 지금 보내는 1대만 갱신되어 1.

- 숫자 예시(대조): 11/10 서버 · Pi 설치 — 첫 실행에서 일곱 번 멈춤. 11/11 릴리스 워크플로 — 첫 실행에 1분 52초 만에 게시까지. 달라진 것은 "러너에서 처음 돌 것을 미리 읽고 돌려 본 것"이다.

## 6. 자주 하는 오해·함정
- "사고가 아홉 건이나 났으니 준비가 부족했다"는 오해: 아홉 건 가운데 행 1~4 는 실제 기계가 아니면 볼 수 없는 것이다. 준비의 문제로 볼 것은 행 1 과 5 — 이미 적어 둔 것을 다시 한 둘 — 이고, 장표는 그것을 제목에 올렸다.
- "실패 사례 표를 적어 두었으니 반복하지 않는다"는 믿음: 행 1 이 반례다. 적은 것은 찾아보지 않으면 없는 것과 같다. 그래서 규칙을 "적는다"에서 "새로 쓸 때 먼저 본다"로 바꿨다.
- "규칙을 문서에 적었으니 지킨다"는 믿음: 행 5 가 반례다. "push 뒤 CI 를 본다"는 규칙은 바쁜 날(서버를 처음 올리던 날) 어겨졌다. 묶음이 클수록, 바쁠수록 본다.
- "테스트가 통과했으니 실제 호출도 된다"는 오해: 테스트가 쓰는 입력의 **모양**(절대 경로)이 실제 호출의 모양(상대 경로)과 달랐다(행 5). 그리고 모든 시험이 같은 출발점(빈 슬롯)에서 시작했다(행 7).
- 행 9 를 "작은 일"로 넘기지 않는다. 계정 이름은 비밀번호가 아니지만, 요점은 "점검했다"는 말이 점검 도구의 범위만큼만 참이라는 것이다. 무엇을 **못 보는** 도구인지 알고 써야 한다.
- 이전 이력의 pptx: 저장소의 지난 커밋에는 옛 파일이 남아 있다. 지금 파일만 고쳤다는 것을 숨기지 않는다.
- 행 2 의 교훈은 스크립트만이 아니다 — 증상이 "정상과 똑같아 보임"인 실패가 가장 오래 걸린다. 설정 값을 받는 쪽이 이상한 값을 **시끄럽게** 거부해야 한다.
