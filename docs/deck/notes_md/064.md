# 장표 064 — ① 장치 에이전트 — 재접속하면 버퍼를 QoS 1 로 비운다, 비정상 종료는 유언이 말한다
*위치: 2부 데이터의 길 · ① 장치 에이전트 · ② 코드 — on_connect · flush_buffer · 유언*

## 1. 이 장표가 왜 있나
앞 장표(063)에서 끊긴 동안 메시지가 버퍼에 들어가는 것을 봤다. 모아 둔 것은 다시 붙었을 때 반드시 나가야 하고, 그것도 "브로커가 받았다"는 확인을 받으며 나가야 끊긴 구간 유실 0 이 된다. 그리고 장치가 조용히 죽는 경우 — 전원이 나가거나 프로세스가 강제 종료되면 장치는 아무 말도 못 한다 — 를 서버가 알 방법이 필요하다. 이 장표는 그 두 가지를 담당하는 코드다: 재접속 콜백 `on_connect` → `flush_buffer`, 그리고 접속 설정 다섯 줄 가운데 유언(`will_set`)과 자동 재접속(`reconnect_delay_set`). 들머리(062)의 기준 ②("비정상 종료도 서버가 아나?")의 답이 여기 있다.

## 2. 장표를 하나씩 읽기
상자 위의 파일 위치: `fleet/agent/device_agent.py:149-167 + 유언·보안 설정(:82-87)`. 위 여섯 줄은 생성자 안의 접속 설정(실제 줄 82~87), 아래는 콜백 세 함수(149~167). 여섯째 줄(87)은 11/10 에 더한 것이다.

- `self.client.will_set(self.topic_status, payload="offline", qos=1, retain=True)` (82): 유언. 접속할 때 브로커에 "내가 비정상으로 끊기면 status 토픽에 offline 을 QoS 1, 보관으로 발행해 달라"를 맡긴다. 장치가 아무 말 없이 사라져도 브로커가 keepalive 1.5배(기본 15초) 안에 알아채고 대신 발행한다.
- `self.client.on_connect = self.on_connect` / `on_disconnect` / `on_message` (83~85): paho 가 접속 성공·끊김·메시지 도착 때 부를 함수 등록. paho 네트워크 스레드에서 불린다(148줄 주석).
- `self.client.reconnect_delay_set(min_delay=1, max_delay=5)  # 끊기면 1~5초 간격으로 자동 재접속` (86): 끊기면 paho 가 1초, 2초, 4초, 5초… 간격으로 스스로 다시 붙는다. 우리 코드에 재접속 루프가 없는 이유.
- `self.security = mqtt_conn.apply_security(self.client)  # 환경변수에 TLS·인증이 있으면 건다 (클라우드 브로커용)` (87): 11/10 에 더한 줄. 환경변수 `FLEET_TLS_CA`(서버 인증서를 확인할 우리 CA 파일)가 있으면 TLS 로 붙고, `FLEET_USER` · `FLEET_PASS` 가 있으면 아이디·비밀번호를 건다. 둘 다 없으면 아무것도 하지 않는다 — 개발(같은 PC, 평문 1883)과 운영(클라우드, 8883 TLS + 비밀번호)이 같은 코드로 돈다. 비밀값을 코드나 저장소에 넣지 않으려고 환경변수로 받는다(Pi 는 서비스의 환경 파일, 서버는 `.env`). 함수는 `fleet/common/mqtt_conn.py`(85줄), 수집기·배포기도 같은 함수를 부른다.
- `def on_connect(self, client, userdata, flags, reason_code, properties):` (149): 처음 접속과 모든 재접속 때 불린다.
- `if reason_code.is_failure: return` (150~151): 접속 거절이면 아무것도 안 한다(paho 가 다시 시도).
- `client.publish(self.topic_status, payload="online", qos=1, retain=True)` (152): "나 살아 있다"를 보관 메시지로. 유언 offline 과 같은 토픽이라 마지막 값 하나만 남는다 — 온·오프라인은 이 토픽의 현재 값.
- `client.subscribe(self.topic_cmd, qos=1)` (153): 서버 명령(cmd) 토픽 구독. 재접속마다 다시 구독해야 한다(clean 세션이면 구독이 사라지므로).
- `self.flush_buffer()` (154): 끊긴 동안 모은 것을 바로 비운다. 접속 직후라 순서가 중요하다 — online 발행 → 구독 → 재전송.
- `def flush_buffer(self):` (156) 와 docstring (157): "끊긴 동안 모아 둔 것을 QoS 1(최소 한 번 도착 보장)로 재전송".
- `with self.lock: items = list(self.buffer); self.buffer.clear()` (158~160): 잠금 안에서 버퍼를 통째로 복사하고 비운다. 잠금 밖에서 publish 하므로 재전송이 오래 걸려도 주기 스레드의 tick 이 막히지 않는다.
- `for topic, payload in items: self.client.publish(topic, payload, qos=1); self.flushed_total += 1` (161~163): 하나씩 QoS 1 로 보내고 누계를 올린다. 옵션인 `telemetry_qos` 와 달리 여기서는 항상 1 — 밀린 데이터는 확인까지 받아야 '안 잃었다'가 된다. flushed_total 이 다음 tick 의 `"flushed"` 로 서버에 간다 → E05 의 654.
- `def on_disconnect(self, client, userdata, disconnect_flags, reason_code, properties):` (165) `if self.running: self.reconnects += 1` (166~167): 끊김을 센다. `running` 이 거짓이면(우리가 stop 으로 끊은 것) 세지 않는다. 재접속 자체는 paho 가 한다.

오른쪽 요점 다섯 줄 가운데 마지막 "11/03 D2 실측: 브로커 10초 중단 → 버퍼 654 = 재전송 654 (E05)"는 이 코드가 실제로 동작했다는 숫자다. 넷째 줄 "apply_security(11/10): …"는 위 87줄의 요약이다.

## 3. 용어와 단위
- 콜백(callback): 어떤 일이 일어났을 때 라이브러리가 대신 불러 주는 우리 함수. on_connect / on_disconnect / on_message.
- paho: 파이썬 MQTT 클라이언트 라이브러리. `loop_start()` 로 네트워크 스레드 하나를 만든다(95줄).
- 유언(LWT): 접속 시 맡기는 메시지. 브로커가 장치의 비정상 끊김을 감지하면 발행. 정상 종료(`disconnect`)에는 발행되지 않는다.
- 보관(retain=True): 토픽의 마지막 메시지를 브로커가 저장. 같은 토픽에 online/offline 을 보관으로 쓰면 '현재 상태' 가 된다.
- QoS 1: 브로커의 PUBACK 확인까지. 재전송은 항상 이것.
- reconnect_delay_set(1, 5): 재접속 간격 최소 1초, 최대 5초(지수적으로 늘다 5초에서 멈춤).
- keepalive 1.5배: 브로커가 장치 소식이 없을 때 끊김으로 판정하는 시간. keepalive 10초면 15초.
- reason_code.is_failure: 접속 응답이 실패인지. paho 2.x 콜백 API(VERSION2, 79줄)의 꼴.

## 4. 쉬운 예시
비유 — 통신 복구 뒤의 지점: 통신사가 돌아오자 지점 전화가 자동으로 다시 연결된다(paho 자동 재접속, 1~5초). 연결되면 직원이 ① 문 앞 팻말을 "영업 중"으로 바꾸고(online 보관) ② 본사 지시 채널을 다시 열고(cmd 구독) ③ 서랍의 메모(버퍼)를 꺼내 전부 등기(QoS 1)로 보낸다 — 보낸 장수를 센다(flushed). 지점이 정전으로 갑자기 꺼지면 직원은 아무 말도 못 하지만, 통신사가 15초 안에 눈치채고 미리 받아 둔 "영업 종료" 팻말(유언)을 본사에 대신 보낸다.

숫자 예시 — 브로커 10초 중단: 50대가 각자 약 13개씩 모아 654개. 브로커가 돌아오고 1~5초 안에 50대가 다시 붙으며 각자 on_connect → flush_buffer 로 13개씩 QoS 1 발송 → flushed 합계 654. 그 순간 수집기에는 초당 600개가 몰리고(평소 50), 밀린 메시지의 전달 지연은 측정 시각 기준 최대 12.5초 — 지연이지 유실이 아니다. 유언: keepalive 10초 장치가 갑자기 죽으면 최대 15초 뒤 status 가 offline 으로 바뀐다(E09 의 '왜 20?' 은 브로커 자신이 죽을 때의 다른 이야기).

## 6. 자주 하는 오해·함정
- "flush 중에 또 끊기면?" — 보내지 못한 publish 는 paho 가 실패를 돌려주거나 내부 큐에 남는다. 우리 버퍼는 이미 비웠으므로 그 메시지는 우리 카운터로는 잃을 수 있다. 실험 범위(10초 중단 한 번)에서는 일어나지 않았고, 그래도 '잃었으면 센다'(seq)가 뒤를 받친다.
- "online 을 보관으로 두면 장치가 죽어도 online 으로 남지 않나?" — 유언 offline 이 같은 토픽을 덮어쓴다. 브로커 자체가 죽는 경우(E09)는 예외라 그 사고가 기록돼 있다.
- "재접속 뒤 cmd 를 다시 구독하는 이유?" — 장치 쪽은 clean 세션이라 끊기면 구독이 사라진다. 서버 명령을 계속 받으려면 매번 구독.
- "reconnects 가 1,675 처럼 큰 수가 나오면?" — 같은 client_id 두 벌이 서로 밀어내는 사고다(11/04, 066 의 단일 인스턴스 잠금). 네트워크 문제가 아니다.
- 함정: 콜백은 paho 네트워크 스레드에서 돈다. 그 안에서 오래 걸리는 일을 하면 수신이 막힌다 — flush_buffer 는 publish 만 하고(빠름), OTA 적용(apply_ota)은 별도 스레드로 뺀 이유(065).

## 7. 면접 한 문장
"재접속 콜백은 세 줄입니다 — online 을 보관 메시지로 발행하고, 명령 토픽을 다시 구독하고, 모아 둔 버퍼를 QoS 1 로 전부 재전송합니다 — 그리고 장치가 아무 말 없이 죽는 경우는 접속 때 브로커에 맡긴 유언이 offline 을 남기므로, 서버는 '조용히 사라진 장치'도 15초 안에 압니다."
