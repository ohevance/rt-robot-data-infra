# 장표 108 — 코드와 숫자가 오가는 길 — 언제, 무엇이 움직이나
*위치: 5부 어디서 · 길과 트리거*

## 1. 이 장표가 왜 있나
앞 장표(107)에서 네 곳이 각각 왜 필요한지 알았다. 그러면 다음 질문은 "그 네 곳 사이를 코드와 숫자가 실제로 어떻게 오가나, 그리고 그 길은 언제(무슨 일이 생기면) 움직이나"다. 장표 106 의 그림에서 화살표 하나하나가 길이었는데, 이 장표는 그 길 여섯 개를 표로 풀어 각 길의 트리거(움직이게 하는 사건), 실제로 치는 명령, 그리고 "제대로 갔다"를 무엇으로 확인하는지를 적는다.

이 장표가 중요한 이유는 두 가지 규칙 때문이다. 첫째, 커밋 주체는 ① 개발 PC 하나다(Pi 도 작업본도 push 하지 않는다). 둘째, 숫자는 원본 파일과 함께 저장소에 들어간다. 이 두 규칙이 지켜지는 길만 있으면 "이 숫자가 어디서 왔나"를 언제든 되짚을 수 있다.

## 2. 장표를 하나씩 읽기
표의 열은 넷이다. "길"은 어느 곳에서 어느 곳으로 가는지(①~④ 번호), "트리거"는 그 길이 움직이는 조건, "명령"은 실제로 치는 것(앞의 [WSL]·[Pi] 는 어느 창에서 치는지), "결과 확인"은 성공했는지 보는 방법이다.

- 행 1 "④ → ① 패치 전달": 트리거는 "작업본이 커밋을 만들면". 작성 보조 작업본(AI 샌드박스)이 코드·문서를 고쳐 커밋을 만들 때마다 움직인다. 명령은 "patch-NN.bundle 이 Downloads 에 → [WSL] git pull --no-rebase --no-edit /mnt/c/Users/…/patch-NN.bundle main" — 커밋 묶음 파일이 윈도우의 Downloads 폴더에 놓이고, WSL 창에서 그 파일을 `git pull` 의 원격처럼 지정해 main 에 받는다. `--no-rebase` 는 받은 커밋을 그대로 이어 붙이라는 뜻, `--no-edit` 은 병합 메시지 편집기를 열지 말라는 뜻이다. 결과 확인은 "Fast-forward 와 파일 목록 (--rebase 금지: 이력을 다시 써서 충돌, 11/04)" — 출력에 `Fast-forward` 와 바뀐 파일 목록이 보이면 성공이다. 11/04 에 `--rebase` 로 받았다가 이미 push 된 이력이 다시 쓰여 충돌이 났기 때문에 `--rebase` 는 금지다.
- 행 2 "① → ③ 공개": 트리거는 "사람이 결정할 때". 자동이 아니다. 명령은 "git push (push 는 항상 사람이)" — 받은 패치를 사람이 확인한 뒤 GitHub 에 올린다. 결과 확인은 "main -> main, 몇 분 뒤 CI" — push 출력에 `main -> main` 줄이 보이고, 몇 분 뒤 GitHub Actions 의 CI 가 돈다(장표 119~121).
- 행 3 "③ → ④ 기준 맞추기": 트리거는 "패치 만들기 전". 작업본이 새 패치를 만들기 전마다 움직인다. 명령은 "작업본이 git fetch (읽기 전용)" — 공개 저장소를 읽기 전용으로 받아 사용자의 main 과 같은 커밋에서 패치를 시작한다. 결과 확인은 "번들의 기준 커밋 = 사용자의 main" — 기준이 같아야 행 1 의 `git pull` 이 "lacks prerequisite" 같은 오류 없이 Fast-forward 된다.
- 행 4 "③ → ② Pi 갱신": 트리거는 "측정 스크립트가 바뀌면". Pi 는 측정 스크립트가 바뀔 때만 코드를 새로 받는다. 명령은 "[Pi] git pull" — Pi 창에서 GitHub 의 main 을 받는다(공개 저장소라 로그인 없이). 결과 확인은 "untracked 결과 파일이 있으면 막힘 → rm 뒤 pull" — Pi 에서 측정하며 `sudo` 로 만든 결과 파일이 저장소 폴더에 남아 있으면 `git pull` 이 "would be overwritten by merge" 로 막힌다. 같은 파일이 이미 GitHub 에 올라가 있으므로 `rm -f docs/measurements/*pi4*` 로 지우고 다시 pull 한다(11/05 에 실제로 겪었다).
- 행 5 "② → ① → ③ 측정 결과": 트리거는 "측정이 끝나면". 명령은 "[WSL] scp '<사용자>@<Pi IP>:…/docs/measurements/*pi4*' docs/measurements/ → make_table1.py → commit → push" — WSL 창에서 scp 로 Pi 의 결과 파일(`*pi4*`: JSON·텍스트·.meta)을 WSL 의 저장소 폴더로 복사하고, `make_table1.py` 로 표①을 다시 만들고, 커밋해 push 한다. 결과 확인은 "table1_pi4.md 줄 수, 각 줄 '스로틀 0'" — 표의 줄 수가 측정 조건 수와 같은지, 각 줄의 비고에 "스로틀 0" 이 붙어 있는지(열 때문에 클럭이 내려간 측정이 아닌지) 본다.
- 행 6 "① 기록 → 저장소": 트리거는 "기록 실험 뒤". 1부 단계 9 의 기록 파이프라인을 돌린 뒤 움직인다. 명령은 "summary.md · rt_status.csv 만 docs/measurements 로 (MCAP 원본 1 MB 는 build/, 제외)" — 요약 문서와 상태 CSV 만 저장소에 넣고, 녹음 원본 MCAP(약 1.07 MB)은 `build/bags/` 에 두고 저장소에서 제외한다(이진 파일로 저장소가 커지는 것을 막기 위해). 결과 확인은 "record_* 파일" — `docs/measurements/record_*` 이름의 파일이 생겼는지 본다.
- 아래 글 "규칙: 커밋 주체는 ① 하나(Pi 도 작업본도 push 하지 않는다). 숫자는 원본 파일과 함께. 출처: docs/ENVIRONMENT.md §2": 여섯 길이 지키는 두 규칙이다. 커밋 주체가 하나면 이력이 한 줄로 남고 GitHub 자격 증명이 한 곳에만 있다. 숫자가 원본 파일과 함께 들어가면 표의 숫자를 원본 JSON 으로 되짚을 수 있다(`docs/measurements/README.md` 규칙).

## 3. 용어와 단위
- 트리거(trigger): 어떤 일을 시작하게 하는 사건. "측정이 끝나면"처럼 조건으로 적는다.
- git bundle: 커밋 묶음을 파일 하나로 만든 것. `git pull <파일> main` 처럼 원격 저장소 대신 파일을 지정해 받을 수 있다.
- Fast-forward: 내 가지 끝에 받은 커밋을 그대로 이어 붙일 수 있는 상태. 병합 커밋이 생기지 않는다.
- rebase: 내 커밋을 다른 기준 위에 다시 쓰는 것. 이미 push 된 커밋을 다시 쓰면 다른 곳의 이력과 어긋나 충돌한다.
- fetch / pull / push: 원격의 변경을 받아 두기만 / 받아서 합치기 / 내 커밋을 원격에 올리기.
- untracked 파일: git 이 추적하지 않는, 저장소 폴더 안에 새로 생긴 파일.
- scp: SSH 위에서 파일을 복사하는 명령. `scp 원격:경로 로컬경로` 꼴이다. 장표의 `<Pi IP>` 는 Pi 의 주소 자리이고 실제 값은 문서에 쓰지 않는다.
- .meta: 측정 스크립트가 결과 옆에 남기는 작은 텍스트 파일. 커널·부하·온도 전후·스로틀 플래그가 `key=value` 로 적혀 있다.
- 스로틀(throttle): Pi 4 가 80 °C 를 넘으면 펌웨어가 클럭을 내리는 것. 그 상태의 측정은 버린다.
- MCAP: rosbag2 가 토픽을 녹음하는 파일 형식. 1 MB = 약 100만 바이트.
- CI(Continuous Integration): push 마다 자동으로 빌드·테스트하는 것(GitHub Actions).

## 4. 쉬운 예시
- 비유: 택배로 비유하면 ④ → ① 은 설계 사무실이 도면을 봉투(bundle)에 담아 작업장 우편함(Downloads)에 넣는 것, ① → ③ 은 작업장 책임자가 봉투를 열어 확인하고 도면 보관소에 등록(push)하는 것, ③ → ② 는 계측실이 보관소에서 최신 측정 절차서를 받아 오는 것, ② → ① → ③ 은 계측실의 결과지를 작업장이 받아 표로 정리해 보관소에 등록하는 것이다. 등록(push)은 항상 작업장 책임자 한 사람만 한다.
- 숫자 예시: 11/05 에 Pi 에서 측정 조건 하나(격리 CPU 3 에서 부하 중 60초)를 재면 `jitter_pi4_rt_stress_isol.json` 과 `.meta` 두 파일이 생긴다. scp 로 가져와 `make_table1.py` 를 돌리면 `table1_pi4.md` 에 한 줄이 늘어 14줄이 되고, 그 줄의 비고에 "온도 44.8→64.8 °C, 스로틀 0" 이 붙는다. 이 줄이 보이면 행 5 의 길이 제대로 간 것이다.

## 5. 숫자의 출처와 다시 확인하는 법

- 확인: `--rebase` 금지와 11/04 충돌 — `docs/HANDOVER.md` §2 git 규칙, `docs/ENVIRONMENT.md` §2.
- 확인: Pi 의 untracked 결과 파일로 pull 이 막힌 일 — `docs/LOG.md` 11/05(`rm -f docs/measurements/*pi4*` 뒤 pull).
- 확인: MCAP 원본 1.07 MB 는 저장소 제외 — `docs/measurements/README.md`, `docs/LOG.md` 11/05 "기록 파이프라인 2차".
- 확인: 표①이 14줄 — `docs/measurements/table1_pi4.md`.
- 다시 확인하는 법: WSL 창에서 `git log --oneline -5` 로 Fast-forward 된 커밋을, `git status` 로 untracked 파일을 본다. 표 다시 만들기는 `python3 scripts/make_table1.py --out docs/measurements/table1_pi4.md`. push 뒤에는 `gh run list -L 1` 로 CI 가 시작됐는지 본다.

## 6. 자주 하는 오해·함정
- "`git pull --rebase` 가 더 깔끔하다": 이 저장소에서는 금지다. 11/04 에 이미 push 된 이력을 다시 써서 충돌이 났다. 항상 `--no-rebase`.
- "Pi 에서 바로 커밋하면 scp 가 필요 없다": Pi 에는 GitHub 자격 증명을 두지 않는다. 커밋 주체를 ① 하나로 두는 것이 규칙이다.
- "표의 숫자만 올리면 된다": 원본 파일(JSON·.meta)이 같이 올라가야 나중에 "이 줄의 부하 크기는 얼마였나"를 되짚을 수 있다. 11/05 에 두 스크립트의 vm 크기가 달랐던 것을 알아낸 것도 .meta 덕분이다.
- 함정(실제로 겪은 것): WSL 용 명령을 Pi 창에 쳐서 복사·커밋이 실패했다(11/04). 그래서 모든 명령 앞에 [WSL]·[Pi] 를 붙인다. 또 Pi 에서 측정한 결과 파일은 untracked 로 남아 다음 `git pull` 을 막는다(11/05) — GitHub 에 이미 올라간 것을 확인한 뒤 지우고 pull 한다.

## 7. 면접 한 문장
"코드와 숫자가 오가는 길을 여섯 개로 정하고 두 규칙을 지켰다 — 커밋과 push 는 개발 PC 한 곳에서만, 숫자는 원본 파일과 .meta 를 함께 — 그래서 표의 어느 숫자도 어느 보드·어느 커널·어떤 부하·몇 도에서 나왔는지 되짚을 수 있다."
