# 장표 003 — 목차 = 순서도 — '로봇을 움직이고 싶다'에서 출발해 '결국 로봇은 이렇게 움직인다'로 끝난다
*위치: 0 · 목차(순서도)*

## 1. 이 장표가 왜 있나
읽는 법(002)에서 "순서는 과정부터, 시험은 뒤에"라고 약속했다. 그러면 "그래서 전체가 어떤 모양인가"를 한 장으로 보여 줘야 한다. 보통 목차는 제목 나열인데, 이 장표는 목차를 순서도로 그렸다. 이유는 사용자의 요구 — 목차와 내용이 순서도의 논리처럼 처음부터 끝까지 이어져야 이해하기도 쉽고 발표하기도 쉽다 — 때문이다. 상자 하나가 부(장) 하나이고, 마름모는 "앞 장을 다 보고 나면 생기는 질문"이며, 그 질문의 답이 다음 부다. 이 장표를 이해하면 138장 전체의 뼈대를 한 번에 잡는다.

## 2. 장표를 하나씩 읽기
순서도는 왼쪽 위에서 시작해 오른쪽으로 가고, 줄이 바뀌면 뱀처럼 반대 방향으로 돈다(4개씩 세 줄).

- 회색 상자(들어온 것) "출발: 로봇을 움직이고 싶다 — 관절 6개짜리 팔에 '이 각도로'를 전하면 실제로 움직이게 하려면?": 출발점은 공고도 측정도 아니고 가장 소박한 바람이다. 관절 6개는 이 저장소의 로봇(SO-ARM100 모델)의 관절 수.
- 파란 상자(확인 방법 색) "1부 로봇을 움직이는 길 10단계": 명령 → DDS → 우편함 → 1 ms 루프 → 안전 검사 → 백엔드 → 움직임 → 상태 → 기록 → 관제. 단계마다 핵심 코드(파일:줄). 파란색을 쓴 이유는 이 부가 "실제로 어떻게 하는지를 보여 주는 길"이기 때문.
- 파란 상자 "2부 데이터의 길 8단계": 로봇 → 에이전트 → 브로커 → 수집기 → DB·Grafana → OTA → 장애 주입·판정 (코드). 1부의 마지막 단계(관제로 올린다)가 2부의 첫 상자로 들어간다.
- 마름모 "각 단계의 기준을 정말 넘었나?" → 화살표 글 "3부 검증": 1·2부에서 번호만 적어 둔 실험이 여기 있다. 왜 이 질문이 여기서 생기나: 1·2부의 들머리마다 '결과' 한 줄이 있는데, 그 숫자가 어떻게 나왔는지는 아직 안 보였기 때문.
- 상자 "표② DDS 손실·RTT → 표① 1 ms 루프(일반 → RT → 격리) → 물리 → 표③ 관제(유실 53 → 0)": 3부의 내용 순서. 단계 순서(2 → 4 → 7 → 2부 ⑦⑧)와 같다. "유실 53 → 0"은 처음 측정이 틀려 0 으로 나왔다가, 고치니 53 이 나왔고, 원인을 잡아 진짜 0 이 된 이야기.
- 마름모 "공고가 요구한 것을 다 덮었나? 어떤 숫자로?" → "4부": 과정과 검증을 다 본 뒤에야 "그래서 이것이 채용 공고의 네 항목을 덮나"를 묻는다.
- 상자 "공고 네 항목 ↔ 산출물 ↔ 수치 ↔ 상태 한 표 · 숫자 한눈에 ①②": 4부의 내용.
- 마름모 "그 숫자는 어디서, 어떤 조건에서?" → "5부": 숫자를 믿으려면 어디서 쟀는지를 알아야 한다.
- 상자 "환경 네 곳 — 개발 PC(WSL2) · Pi 4(RT 커널) · GitHub CI · 작업본 + 각 곳의 '정상 신호'": 5부의 내용. '정상 신호'란 그 곳이 제대로 돌고 있다고 판단하는 기준(예: 수집기 로그의 online=50).
- 마름모 "이 숫자들을 어떻게 믿나?" → "6부": 환경을 알았으면 다음은 "누가, 무엇으로, 언제 다시 재나".
- 상자 "측정 스크립트(온도·부하·커널 기록) · 테스트 20건 · CI 3잡이 매 push 다시 잰다 → ◇왜 이렇게, 무엇이 깨졌나? → 7부 결정 18 · 사고 11 · 일정 · AI · 용어": 6부와 7부를 한 상자에 묶었다(자리 때문). 7부로 가는 질문은 "왜 이렇게 만들었고, 무엇이 깨졌나".
- 진한 둥근 상자(결론) "끝: 결국 로봇은 이렇게 움직인다 (한 장 요약, 숫자와 함께)": 출발 질문의 답으로 돌아와 끝난다.
- 아래 설명 상자 "읽는 법": 1·2부는 '길' 자체라 질문이 아니라 단계로 내려가고, 단계 안에서 같은 꼴(들어온 것 → 문제 → 기준 → 코드 → 결과 → 판단)이 반복되며, 시험은 '확인 → 장표 N' 으로 3부를 가리킨다. 마름모(질문)마다 다음 부가 그 답이다.

## 3. 용어와 단위
- 순서도(flowchart): 일의 흐름을 상자와 화살표로 그린 그림. 마름모는 갈림길(질문), 사각형은 일, 둥근 진한 상자는 끝.
- 표①·표②·표③: 이 저장소가 만든 측정 표 셋. 표① = 1 ms 루프의 깨어남 지연(Pi 4), 표② = DDS 왕복 지연·손실, 표③ = 관제의 처리량·유실·복구·OTA.
- DDS: ROS 2가 통신에 쓰는 미들웨어. RTT: 왕복 시간(round-trip time).
- RT 커널 / 격리: 리눅스 실시간 커널(PREEMPT_RT), 그리고 CPU 하나를 다른 일에서 떼어 두는 것(isolcpus).
- CI(GitHub Actions): 코드를 올릴(push) 때마다 자동으로 빌드·테스트를 돌리는 장치. "3잡"은 그 작업 세 개.
- 유실: 보냈는데 저장되지 않은 메시지 수.

## 4. 쉬운 예시
비유: 집을 지은 뒤 손님에게 설명하는 순서와 같다. 먼저 현관부터 방까지 실제로 걸어 보여 주고(1·2부), "이 벽 튼튼한가요?"라는 질문에 검사 성적서를 꺼내고(3부), "요구 사항대로 됐나요?"에 요구서를 대조하고(4부), "어디서 검사했나요?"(5부), "검사를 믿을 수 있나요?"(6부), "왜 이렇게 설계했나요, 공사 중 무엇이 문제였나요?"(7부)로 이어진다. 숫자 예시: 마름모 "각 단계의 기준을 정말 넘었나?"의 답 중 하나가 "1 ms 루프의 깨어남 지연 max 가 일반 커널 781 us 에서 실시간 커널+격리로 189 us" 인데, 이 숫자는 1부 단계 4 들머리에 한 줄로 먼저 나오고 3부 장표 92~95 에서 어떻게 나왔는지가 펼쳐진다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 각 부의 장표 범위 — 4번 장표의 표와 `docs/deck/SLIDES.md` (1부 5–58, 2부 59–85, 3부 86–100, 4부 101–104, 5부 105–110, 6부 111–123, 7부 124–136, 끝 137–139).
- 확인: "테스트 20건" — C++ ctest 4건 + MuJoCo 1건 + 파이썬 15건(6 + 3 + 6). `rt_control/rt_core/CMakeLists.txt` 의 add_test 5개, `grep -c "^def test_" fleet/tests/test_*.py`.
- 확인: "결정 18 · 사고 11" — 7부 장표(결정 기록 3장 18건, 사고와 해결 2장 11건). 전체 결정은 `docs/DECISIONS.md`, 사고는 `docs/EXPERIMENTS.md` §4 와 `docs/LOG.md`.
- 확인: "유실 53 → 0" — `docs/experiments/E07.md`(53 / 1434), `E08.md`(0 / 1400).

## 6. 자주 하는 오해·함정
- 순서도의 화살표 글("3부 검증", "4부")은 측정값이 아니라 "그 질문의 답이 있는 부"다. 다른 순서도 장표에서는 화살표 글이 실제 측정값이다(그림 약속은 같다 — "기준에 대한 답").
- 1·2부에 마름모가 없다고 기준이 없는 것이 아니다. 기준은 각 단계의 들머리 장표 안(마름모 상자)에 있다.
- 6부와 7부가 한 상자에 들어 있는 것은 공간 때문이고, 실제 장표는 6부 13장, 7부 12장으로 따로 있다.

## 7. 면접 한 문장
"목차를 순서도로 그렸습니다 — '로봇을 움직이고 싶다'에서 출발해 과정 두 부를 지나고, 그 뒤는 '기준을 넘었나, 공고를 덮었나, 어디서 쟀나, 어떻게 믿나, 왜 이렇게 했나'라는 질문 하나에 부 하나씩 답하고 '결국 로봇은 이렇게 움직인다'로 돌아옵니다."
