# 장표 102 — 공고(Framework S/W 엔지니어) 주요 업무 ↔ 산출물 ↔ 수치 ↔ 상태 — 여섯 묶음 중 다섯에 코드와 숫자, EtherCAT 은 없다
*위치: 4부 출발 · 공고 ↔ 산출물 ↔ 숫자*

## 1. 이 장표가 왜 있나
앞 장표(101, 4부 표지)가 세운 질문은 "이 길과 숫자가 공고(Framework S/W 엔지니어)의 주요 업무를 덮나, 무엇을 숫자로 증명했나"였다. 이 장표가 그 답을 **한 표**로 준다. 왼쪽 열이 공고의 주요 업무, 그 오른쪽으로 갈수록 "그래서 무엇을 만들었고(코드) → 무엇을 쟀고(표·실험) → 지금 어디까지 됐나(상태)"다. 한 행을 왼쪽에서 오른쪽으로 읽으면 "요구 → 증거"가 되고, 한 열을 위에서 아래로 읽으면 "빠진 업무가 없나"가 된다. 빠진 것이 실제로 하나 있다 — ⑤ EtherCAT. 그 줄을 지우지 않고 "없음"으로 남긴 것이 이 표의 태도다.

저장소 `README.md` 의 첫 표와 같은 일곱 줄이라, 면접관이 저장소를 열었을 때 처음 보는 표와 발표의 이 표가 같다. 11/10 까지 이 표는 다른 공고 문구의 네 항목(① 실시간 Linux 미들웨어 · ② 로깅·모니터링·업데이트 · ③ 센서 스트리밍 · ④ 시뮬레이션·CI)으로 나뉘어 있었다. 11/11 에 지원하는 공고를 하나로 정하면서 같은 산출물을 그 공고의 주요 업무로 다시 나눴다(`docs/DECISIONS.md` 2026-11-11).

## 2. 장표를 하나씩 읽기
표는 머리말 한 줄 + 일곱 행, 열은 넷(공고 주요 업무 · 산출물(코드) · 수치(표·실험) · 상태)이다. 글이 많아 글씨를 작게(9) 했고, 산출물 열이 가장 넓다 — 코드 폴더와 괄호의 장표 위치가 길기 때문.

- 행 ① "Linux 로봇 프레임워크 · 프로세스 구조·미들웨어 · 멀티스레드 데이터 흐름 · IPC" → 산출물 "rt_core: RT 스레드 ↔ 일반 스레드를 락 없는 우편함(spsc_ring)으로 · 같은 핵심을 노드 둘이 감쌈(ROS 2 · ZeroMQ) · 같은 PC 는 공유 메모리 seqlock · 백엔드 하나 뒤에 6 자유도 팔과 ALLEX 48 자유도(프로필만 다름) (1부 단계 2~7)": 프레임워크의 뼈대 셋이다. ① 스레드 구조 — 1 kHz RT 스레드는 소켓도 디스크도 모르고, 일반 스레드와는 락 없는 링 버퍼로만 만난다(1부 단계 3). ② 미들웨어 교체가 어댑터 교체 — 같은 `rt_core` 를 ROS 2 노드와 ZeroMQ 노드가 각각 감싼다(덧붙임 143). ③ 하드웨어 추상화 — 로봇은 `Backend` 인터페이스 하나 뒤에 있어, 지원 회사가 공개한 ALLEX 48 자유도 모델도 프로필 하나로 붙었다(덧붙임 136). → 수치 "1 kHz 루프 드롭 0(Pi 4, 14조건) · seqlock 섞인 읽기 0 / 36,692 · ALLEX 500 Hz 물리 p99 510 us(2 ms 의 26 %)". → 상태 "완료".
- 행 ② "실시간 제어 환경(Xenomai · PREEMPT_RT) · 지연 최적화" → 산출물 "PREEMPT_RT + SCHED_FIFO + mlockall + CPU 고정 + isolcpus(Pi 4), 측정기 jitter_bench 와 cyclictest 교차 확인 (1부 단계 4, 3부 표①)": 1 ms 루프가 늦게 깨는 것을 줄이는 손잡이를 한 번에 하나씩 돌린 사슬이다(커널 → 고정 → 격리). 측정기를 직접 만들고 표준 도구와 같은 설정으로 맞춰 차이를 설명했다. → 수치 "부하 중 깨어남 max 781 → 189 us · cyclictest max 695 → 132 us · 측정기 vs cyclictest 270 vs 274 us". → 상태 "PREEMPT_RT 완료. Xenomai 는 안 함": Xenomai(리눅스 옆에 실시간 핵을 따로 두는 방식)는 하지 않았다고 그대로 적었다. 11/11 밤에는 Pi 를 다시 켜 재부팅 뒤에도 RT 커널 · 격리 코어가 유지되는 것을 확인했다.
- 행 ③ "상태 머신 · 오류 복구 시나리오" → 산출물 "robot_state_machine: INIT → READY → RUNNING → FAULT → RECOVERING, 전이 표 + 불법 전이 카운터 · 워치독 → FAULT(자리 유지) → 명령이 다시 오면 복구 (1부 단계 5)": 상태 다섯과 전이 열다섯 줄이 표 하나에 있고, 표에 없는 전이는 거부하고 센다. 명령이 끊기는 것이 대표 오류 시나리오다 — 워치독이 걸리면 FAULT 로 가서 지금 자리를 지키고, 명령이 다시 오면 RECOVERING 을 거쳐 100 ms 연속 정상일 때 READY 로 돌아온다. → 수치 "명령이 끊기면 51~52 ms 뒤 FAULT(워치독 50 ms) · 불법 전이 0 — 끝-대-끝이 매 push". → 상태 "완료".
- 행 ④ "ZeroMQ · ROS 통신 패킷 · Python/C++ SDK" → 산출물 "wire.hpp(머리 24바이트 + 본문, C++·Python 골든 바이트) · rt_zmq_node(DEALER↔ROUTER 명령, PUB 상태) · Python SDK rtsdk · ROS 2 노드 · dds_bench (7부 덧붙임 ZeroMQ)": 11/11 에 빈칸을 메운 줄이다. 패킷 형식을 파일 한 장(`wire.hpp` 머리말)에 정하고, C++ 와 Python 이 같은 바이트를 기대하는지 골든 시험으로 지킨다. ROS 2 쪽(노드와 DDS 측정, 표②)은 본편부터 있었다. → 수치 "명령 → 반영 → 상태 p50 0.88 / p99 1.81 ms(WSL, 1,000회, 잃음 0) · 상태 1만 개 빈 번호 0 · 표② DDS". → 상태 "완료(11/11). C++ 소켓 클라이언트·Pi 값은 아직": C++ 쪽은 노드와 패킷 형식까지이고, C++ 로 쓴 클라이언트 SDK 는 아직 없다. Pi 에서는 아직 재지 않았다(예측만 E24 5절).
- 행 ⑤ "EtherCAT 마스터 · 슬레이브 진단 · 오류 복구" → 산출물 "없음 — 하드웨어가 없다. 들어갈 자리는 Backend 인터페이스 하나(SimLag · MuJoCo 가 같은 자리)" → 수치 "—" → 상태 "없음(지원 뒤 판단)": 숨기지 않는 줄. EtherCAT 마스터는 실물 드라이버(슬레이브)가 있어야 의미 있는 일이다. 이 저장소에서 그 일이 들어갈 자리는 이미 있다 — `rt_core/backend.hpp` 의 `Backend`(지금은 1차 지연 흉내 SimLag 와 물리 MuJoCo 가 그 자리를 쓴다). 하드웨어가 필요한 우대 사항은 지원 뒤에 판단한다고 정했다(DECISIONS 11/11).
- 행 ⑥ "OTA 업데이트 · 로그 수집·분석" → 산출물 "fleet: MQTT → TimescaleDB → Grafana, 장애 주입 4종 · 릴리스: 태그 → 빌드 → 가상 50대 카나리 → 게시 → 장치가 sha256·A/B 슬롯·자가 점검으로 설치 · 로봇 안 기록 rosbag2 → CSV · 클라우드 운영 층 (2부, 7부 덧붙임)": 2부의 데이터의 길 전체와 11/10~11 의 릴리스 파이프라인(장표 137~139), 클라우드 운영 층(장표 140)이다. → 수치 "50대 설치 14.62 s · 깨진 패키지 3/50 에서 거부 → 롤백 1.0 s · 브로커 중단 유실 0 / 1400 · 실물 Pi 53,167건 유실 0". → 상태 "완료. v0.9.0 게시(11/11)".
- 행 "필수 역량: Git · Docker · CI/CD" → 산출물 "CI 3잡(단위 → 통합 컨테이너 · MuJoCo 헤드리스 × 2 모델) + 릴리스 워크플로(태그 → 4잡) (6부)" → 수치 "테스트 37건(C++ 7 · Python 30) + 끝-대-끝 셋 · 태그 → 게시 1분 27초" → 상태 "완료, CI 초록": 주요 업무가 아니라 필수 역량이지만, 공고가 이름을 들어 요구한 도구라 한 줄로 따로 뒀다. 끝-대-끝 셋은 컨테이너 통합 · 릴리스 카나리 · ZeroMQ 노드 12단계다.
- 아래 주석 "출처: README.md 첫 표(11/11 에 공고를 Framework S/W 엔지니어로 바꿔 다시 나눔 — 산출물은 같다, DECISIONS 11/11). '완료'는 코드가 있고 실제로 돌려 숫자를 얻었다는 뜻이지 '제품 수준'이라는 뜻이 아니다. 필수 역량 중 Linux C/C++ · 멀티스레드·네트워크 · ZeroMQ/DDS/ROS 2 · 상태 머신은 ①~④ 줄에 있다": '완료' 의 정의를 스스로 좁혀 둔 줄과, 필수 역량의 나머지가 어디에 있는지 알려 주는 줄.

## 3. 용어와 단위
- IPC(프로세스 사이 통신): 서로 다른 프로그램(또는 스레드)이 데이터를 주고받는 방법. 여기서는 락 없는 링 버퍼(스레드 사이), 소켓(ZeroMQ · DDS), 공유 메모리(같은 PC 의 프로세스 사이).
- seqlock: 쓰는 쪽은 기다리지 않고, 읽는 쪽이 번호를 두 번 읽어 "쓰는 도중이었나"를 판정하는 공유 메모리 방식.
- PREEMPT_RT / Xenomai: 리눅스 커널 자체를 실시간에 가깝게 바꾸는 방식 / 리눅스 옆에 실시간 핵을 따로 두는 방식.
- isolcpus: 특정 CPU 코어에 일반 작업이 올라오지 못하게 비워 두는 커널 설정.
- 상태 머신: 상태(INIT · READY · RUNNING · FAULT · RECOVERING)와 허용된 전이의 표. 표에 없는 전이는 "불법 전이"로 세고 거부한다.
- 워치독: 명령이 일정 시간(50 ms) 안 오면 "끊겼다"고 판단하는 장치.
- 골든 바이트: "이 입력이면 정확히 이 바이트"를 박아 둔 시험 값.
- EtherCAT 마스터 / 슬레이브: 산업용 이더넷에서 주기를 정하고 묻는 쪽(컴퓨터) / 답하는 쪽(모터 드라이버 등).
- OTA · 카나리 · A/B 슬롯: 원격 소프트웨어 갱신 · 일부에 먼저 깔아 보기 · 설치 자리 두 칸(실패하면 이전 칸으로).
- 단위: us(100만분의 1초), ms(1,000분의 1초), s(초).

## 4. 쉬운 예시
건물 준공 검사 비유: 발주서(공고)에 "① 골조 ② 내진 ③ 비상 대피 ④ 통신 배선 ⑤ 엘리베이터 ⑥ 관리 시스템"이 있으면, 검사표는 항목마다 "설치한 것(산출물) · 측정값(수치) · 판정(상태)"을 한 줄씩 적는다. 엘리베이터를 아직 들이지 않았다면 그 줄을 빼는 것이 아니라 "없음 — 승강로는 이렇게 비워 두었다"고 적는다. 그래야 검사관이 나머지 줄을 믿는다.

숫자 예시: 행 ②의 사슬 "일반 → RT → 고정 → 격리"는 표①의 부하 중 max 781 → 301 → 311 → 189 us 네 값에 대응한다. 행 ④의 p50 0.88 ms 중 약 0.5 ms 는 1 kHz 루프가 다음 주기에 우편함을 열기까지의 기다림이다(장표 143). 필수 역량 줄의 37건 = C++ 7(ctest 6 + MuJoCo 1) + Python 30(fleet 9 · 3 · 7 · 7 + SDK 4).

## 6. 자주 하는 오해·함정
- "완료 = 제품 수준"으로 읽으면 안 된다. 주석이 그 정의를 "코드가 있고 돌려서 숫자를 얻었다"로 좁혔다. 뺀 것(실물 서보, 중력 보상, 수동 ACK 등)은 7부.
- 행 ②의 숫자만 Pi 4 실측이고, 나머지 행의 숫자는 WSL2 · CI 러너 · 샌드박스 · 실물 Pi → 서버 등 서로 다른 곳에서 나왔다 — 같은 "완료"라도 숫자의 급이 다르다(장표 103·104 제목과 5부).
- "ZeroMQ 를 공고에 맞춰 급히 붙였다"는 인상을 피하는 법: 붙인 방식이 설계 문장(11/03 의 "미들웨어 교체 = 어댑터 교체")의 증거였다는 것, 그리고 시험이 없던 길에서 문서 오류를 찾아 고친 것까지 함께 말한다(장표 143).
- 행 ④의 "C++ SDK" 는 절반만 했다 — 노드와 패킷 형식은 C++ 이지만, 노드에 붙는 C++ 클라이언트 라이브러리는 아직 없다. "Python/C++ SDK 를 만들었다"고 뭉뚱그리지 않는다.
- ⑤ EtherCAT 을 "곧 한다"고 말하지 않는다. 하드웨어가 필요하고, 지원 뒤에 판단하기로 정했다. 대신 들어갈 자리(`Backend`)와 그 자리를 이미 두 백엔드가 쓰고 있다는 것을 말한다.
- 11/10 까지의 네 항목 표를 기억하는 사람에게: 산출물은 그대로이고 나누는 칸만 바뀌었다. 옛 ④ "시뮬레이션 · CI" 의 내용은 새 ①(백엔드)과 필수 역량 줄(CI)로 나뉘어 들어갔다.
