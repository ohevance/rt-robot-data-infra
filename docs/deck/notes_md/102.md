# 장표 102 — 공고 요구 ↔ 산출물 ↔ 수치 ↔ 상태 — 네 항목 전부에 코드와 숫자가 붙어 있다
*위치: 4부 출발 · 공고 ↔ 산출물 ↔ 숫자*

## 1. 이 장표가 왜 있나
앞 장표(101, 4부 표지)가 세운 질문은 "이 길과 숫자가 공고 네 항목을 다 덮나, 무엇을 숫자로 증명했나"였다. 이 장표가 그 답을 **한 표**로 준다. 왼쪽 열이 공고의 요구, 그 오른쪽으로 갈수록 "그래서 무엇을 만들었고(코드) → 무엇을 쟀고(표) → 지금 어디까지 됐나(상태)"다. 한 행을 왼쪽에서 오른쪽으로 읽으면 "요구 → 증거"가 되고, 한 열을 위에서 아래로 읽으면 "네 요구에 빠진 것이 없나"가 된다. 저장소 `README.md` 의 첫 표를 그대로 옮긴 것이라, 면접관이 저장소를 열었을 때 처음 보는 표와 발표의 이 표가 같다.

## 2. 장표를 하나씩 읽기
표는 머리말 한 줄 + 네 행, 열은 넷(직무 요구(공고) · 산출물(코드) · 수치(표) · 상태)이다. 열 너비는 산출물 열이 가장 넓다 — 코드 폴더와 괄호의 장표 위치가 길기 때문.

- 행 ① "실시간 Linux 미들웨어, ROS 2/DDS" → 산출물 "rt_control/rt_core RT 루프·측정기·제어 단계·상태 머신, ros2_adapter 노드, dds_bench (1부 단계 2~5)": 1부의 단계 2(DDS 가 전달한다)~단계 5(제어 단계)가 이 코드다. rt_core 는 ROS 2 와 무관한 순수 C++ 핵심(1 kHz 루프·SPSC 링 버퍼·ControlStep·상태 머신), ros2_adapter 는 그것을 ROS 2 노드 `rt_control_node` 로 싸는 층, dds_bench 는 DDS 구현체·QoS·크기별 왕복 지연·손실을 재는 도구. → 수치 "표① 지연·지터(p99.9/max) · 표② DDS 손실·지연 · 노드 rt_status (3부)": 표①은 1 ms 루프의 깨어남 지연, 표②는 DDS, rt_status 는 노드가 1 Hz 로 내는 자기 상태(JSON: wake/work us·드롭·state). 어떻게 나왔는지는 3부. → 상태 "완료. Pi 4 실측(일반 → RT → 고정 → 격리)": 네 조건을 한 변수씩 바꾼 Pi 4 실측이 끝났다.
- 행 ② "실시간 로깅·모니터링·시각화·업데이트" → 산출물 "fleet 수집 → TimescaleDB → Grafana 14 패널, OTA 단계 배포·헬스 게이트·롤백, 장애 주입 4종 (2부)": 2부의 데이터의 길 전체. 수집기(1초 묶음 COPY), 시계열 DB, 대시보드 패널 14개(생성기로 만든다), OTA 5 → 50 → 100% 배포와 롤백, 장애 주입 4종(브로커·DB·수집기 중단, 나쁜 펌웨어). → 수치 "표③-1 처리량·전달 지연 · ③-2 장애 감지·복구·유실 · ③-3 OTA 롤백 시간 (3부)". → 상태 "완료, WSL 실행 확인": 개발 PC 의 WSL2 에서 실제로 돌려 표③을 얻었다.
- 행 ③ "센서 스트리밍·로깅·전처리 자동화" → 산출물 "장치 에이전트(가상 50 + RT 노드 1), store-and-forward, 수집기 backlog, QoS 0/1 (2부) · data_pipeline rosbag2 → CSV → 요약 (1부 단계 9)": 두 갈래다. 관제 쪽(2부)은 장치 50대 + RT 노드 1대가 51번째 장치로 올리는 텔레메트리와 끊김 보호(장치 버퍼 store-and-forward, 수집기 backlog, QoS). 로봇 안(1부 단계 9)은 100 Hz 기록 → CSV → 자동 검증 요약. → 수치 "초당 메시지, 전달 지연 p95, 유실 % · 기록 실제 Hz·틈·추종 오차". → 상태 "완료 (기록 11/05 첫 실행)": 기록 파이프라인은 11/05 에 처음 실제로 돌렸다(E20).
- 행 ④ "시뮬레이션 · CI" → 산출물 "rt_core/mujoco_backend (Menagerie SO-ARM100 6 자유도 · 위로보틱스 공개 ALLEX 48 자유도, 프로필만 다름) (1부 단계 6·7, 7부 덧붙임), CI 3잡(단위 → 통합 컨테이너 · MuJoCo 헤드리스 × 2 모델) (6부)": 물리 백엔드는 1부 단계 6(백엔드가 로봇에 쓴다)·7(로봇이 움직인다), 지원 회사가 공개한 ALLEX 모델을 같은 백엔드로 돌린 것은 7부 덧붙임(장표 136, 11/06), CI 는 6부. "프로필만 다름"은 두 로봇의 차이가 `robots/so101.yaml` 과 `robots/allex.yaml` 뿐이라는 뜻이다. → 수치 "CI 배지, 테스트 수(C++ 5 · Python 15 · 통합 1), 물리 한 주기 비용 p99 (6 · 48 자유도)": C++ 5 = ctest 4 + MuJoCo 1(같은 테스트 바이너리가 CI 에서 두 모델을 돈다), Python 15 = 6 + 3 + 6. p99 는 6축 8.5 us, 48축 458 us(러너 1 kHz). → 상태 "완료, CI 초록 (ALLEX 11/06)".
- 아래 주석 "출처: README.md 첫 표. '완료'는 코드가 있고 실제로 돌려 숫자를 얻었다는 뜻이지 '제품 수준'이라는 뜻이 아니다 — 2주 범위에서 뺀 것은 7부 결정 기록 참고": '완료' 의 정의를 스스로 좁혀 둔 줄. 과장으로 읽히지 않게 하는 안전장치다.

## 3. 용어와 단위
- 미들웨어: 두 프로그램 사이에서 메시지를 전달해 주는 층. ROS 2 는 DDS 라는 미들웨어 위에 있다.
- 지터(jitter): 주기가 흔들리는 정도. 1 ms 마다 깨야 하는데 얼마나 늦게 깨나(깨어남 지연)의 분포로 본다. p99.9 = 1,000번 중 999번은 이 값 이내, max = 최악.
- TimescaleDB: 시계열(시간 순 데이터)에 맞춘 PostgreSQL 확장. Grafana: 그 DB 를 그래프로 보여 주는 도구.
- OTA·헬스 게이트·롤백: 무선 펌웨어 갱신, 단계마다 건강 확인, 이전 버전으로 되돌리기(2부 ⑥).
- store-and-forward: 연결이 끊기면 장치가 보관했다가 이어지면 다시 보내는 방식.
- rosbag2(MCAP): ROS 2 의 토픽 기록 도구와 파일 형식. CSV 로 풀어 요약한다.
- Menagerie SO-ARM100: MuJoCo 공식 모델 모음(Menagerie)의 6축 팔 모델.
- CI 3잡: rt_core(빌드·단위·연기·fleet 단위) → fleet_integration(진짜 컨테이너) · mujoco(헤드리스 물리).

## 4. 쉬운 예시
건물 준공 검사 비유: 발주서(공고)에 "① 전기 ② 수도 ③ 환기 ④ 소방"이 있으면, 검사표는 항목마다 "설치한 것(산출물) · 측정값(수치: 전압, 수압 …) · 판정(상태)"을 한 줄씩 적는다. 항목 하나가 비어 있으면 준공이 안 된다 — 이 표의 네 행이 전부 채워져 있다는 것이 이 장표의 요점이다.

숫자 예시: 행 ④의 "C++ 5 · Python 15 · 통합 1" = 단위 테스트 20건 + 통합 1벌. 행 ①의 상태 "일반 → RT → 고정 → 격리"는 표①의 부하 중 max 781 → 301 → 311 → 189 us 네 값에 대응한다.

## 6. 자주 하는 오해·함정
- "완료 = 제품 수준"으로 읽으면 안 된다. 주석이 그 정의를 "코드가 있고 돌려서 숫자를 얻었다"로 좁혔다. 뺀 것(중력 보상, 실물 서보 연결, 수동 ACK 등)은 7부.
- 행 ①의 숫자는 Pi 4 실측, 행 ②~④는 WSL2·CI 러너다 — 같은 "완료"라도 숫자의 급이 다르다(장표 103·104 제목과 5부).
- "C++ 5" 를 ctest 로 세면 4 다. 다섯째(MuJoCo)는 빌드 옵션이 켜진 mujoco 잡에서만 돈다.
- 행 ③의 "가상 50 + RT 노드 1" — RT 노드는 가상 장치가 아니라 진짜 제어 노드가 다리(ros_status_bridge.py)를 통해 51번째 장치로 올라오는 것이다(1부 단계 10).

## 7. 면접 한 문장
"공고 네 항목을 표 한 장으로 대응시켰습니다 — 항목마다 코드 폴더, 표의 숫자, 현재 상태가 붙어 있고, '완료'의 뜻은 제품 수준이 아니라 '돌려서 숫자를 얻었다'로 적어 두었습니다."
