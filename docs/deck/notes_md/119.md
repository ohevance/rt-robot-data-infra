# 장표 119 — CI 잡 1 — rt_core (1단계, 러너 VM 1, 약 1분 10초): 빌드 → 단위 테스트 → 연기 → 표 생성기 → fleet 단위 15건
*위치: 6부 믿을 수 있나 · CI 잡 1 rt_core*

## 1. 이 장표가 왜 있나
앞 장표(117·118)까지 테스트를 모두 보았다. C++ 단위 테스트, 가짜 브로커·DB 위의 파이썬 단위 테스트 15건, 진짜 컨테이너 위의 통합 테스트다. 그런데 테스트는 사람이 돌릴 때만 돈다. 바쁘거나 깜빡하면 깨진 코드가 그대로 저장소에 올라간다. 그래서 질문이 생긴다. "누가 push 할 때마다 빠짐없이, 그것도 내 PC 가 아닌 깨끗한 컴퓨터에서 다시 돌려 주나?" 답은 GitHub Actions(CI)이고, 세 개의 잡(job)으로 나뉜다. 이 장표는 그 첫 번째이자 나머지 둘의 문지기인 `rt_core` 잡을 순서도로 보여 준다. 핵심은 "싼 검사를 먼저 한다" — 1분 남짓 안에 논리가 깨졌는지 보고, 여기서 떨어지면 비싼 2단계(진짜 컨테이너·물리)는 아예 돌리지 않는다.

## 2. 장표를 하나씩 읽기
순서도는 왼쪽 위에서 시작해 뱀처럼(첫 줄 왼쪽 → 오른쪽, 둘째 줄 오른쪽 → 왼쪽) 내려간다.

- 상자 1(회색, 들어온 것) "push · pull_request · 수동 실행 → GitHub 가 새 VM(ubuntu-24.04)을 켠다. 내 노트북이 아니고 매번 백지": CI 를 깨우는 방아쇠(트리거)는 세 가지다 — 아무 브랜치에 push, pull request, Actions 화면의 "Run workflow" 버튼(workflow_dispatch). 그러면 GitHub 가 빌려주는 리눅스 가상 컴퓨터(러너, runner)가 새로 켜진다. 매번 아무것도 깔려 있지 않은 상태라 "내 PC 에만 우연히 깔려 있던 것" 덕에 통과하는 일이 없다.
- 상자 2 "apt: cmake g++ python3 → cmake 빌드 rt_core": 백지 컴퓨터에 빌드 도구를 먼저 깔고(apt), RT 핵심 라이브러리 `rt_control/rt_core` 를 Release 로 빌드한다. ROS 2 가 없는 컴퓨터에서도 빌드되도록 RT 핵심을 ROS 2 와 떼어 놓은 결정(7부 결정 기록)이 여기서 효과를 낸다.
- 마름모 1(기준) "ctest 4건 통과? 링 버퍼 · 제어 단계 · 상태 머신 · 1 kHz 2초 드롭 0": ctest 는 CMake 에 등록된 테스트를 한꺼번에 돌리는 도구다. 등록된 4건은 spsc_ring(링 버퍼가 두 스레드 사이에서 순서를 지키고 꽉 차면 버리는지), control_step(최신 명령·워치독·변화량 제한), state_machine(허용 전이와 불법 전이 거부), jitter_smoke(1 kHz 루프를 2초 돌려 드롭 0 인지)다. 화살표 글 "예 → 계속 / 아니오 → 잡 실패, 배지 빨강": 하나라도 실패하면 이 잡이 빨간색이 되고, README 첫 화면의 배지도 빨개진다.
- 상자 3(파랑, 확인 방법) "jitter_bench --no-rt 2초 → JSON → make_table1 ('돌아간다'의 증거, 지연 수치 아님 — 러너엔 RT 없음)": 측정기를 일반 스케줄링(`--no-rt`)으로 2초 돌려 결과를 JSON 으로 쓰고, 그 JSON 으로 표① 생성기(`scripts/make_table1.py`)를 돌린다. 목적은 "측정기와 표 생성기가 고장 나지 않았다"를 확인하는 것이다. 러너는 RT 커널도 RT 권한도 없는 공용 가상 컴퓨터라 여기서 나온 지연 숫자는 의미가 없다. 지연 숫자는 Pi 4 실측(표①)에서만 말한다.
- 마름모 2(기준) "fleet 단위 15건 전부 OK? (가짜 브로커·DB 위)": 파이썬 테스트 파일 3개 — `test_fleet_logic.py` 6건, `test_ota_rollout.py` 3건, `test_collector_resilience.py` 6건, 합계 15건. 진짜 브로커·DB 컨테이너 없이 가짜 모듈(`fake_mqtt.py`, `fake_psycopg.py`) 위에서 몇 초 만에 끝난다. 화살표 글 "예 / 아니오 → 로그의 FAIL: 줄": 실패하면 잡 로그에 `FAIL:` 로 시작하는 줄이 찍히므로 그 줄부터 본다.
- 상자 4 "대시보드 JSON 생성 → 파싱 검사 (make_dashboard.py)": Grafana 대시보드(패널 14개)는 손으로 만들지 않고 파이썬 생성기가 JSON 을 만든다. CI 는 생성기를 돌리고, 결과 파일이 올바른 JSON 인지 파이썬 `json.load` 로 읽어 본다. 생성기 코드를 고치다 JSON 을 망가뜨리면 여기서 걸린다.
- 상자 5(진한 결론) "✓ 아티팩트 jitter-ci(jitter_ci.json · table1_ci.md) → needs: 로 2단계 두 잡이 병렬 시작": 통과하면 결과 파일 두 개를 아티팩트(내려받을 수 있게 남겨 두는 파일)로 올린다. 그리고 `needs: rt_core` 가 걸린 두 잡 — fleet_integration 과 mujoco — 가 각자 다른 러너에서 동시에 시작한다.
- 아래 글 "1단계의 뜻 … 싼 검사부터(DECISIONS 11/03 D4) …": 1단계는 빠른 실패용, 2단계는 진짜 환경 증명용이다. 2단계가 깨졌을 때 1단계가 통과했는지를 보면 "논리 문제냐, 환경 문제냐"를 먼저 가를 수 있다. 출처는 `.github/workflows/ci.yml` 의 rt_core 잡과 `docs/ENVIRONMENT.md` 5절이다.

## 3. 용어와 단위
- CI(Continuous Integration, 지속적 통합): 코드를 올릴 때마다 자동으로 빌드·테스트하는 체계. 여기서는 GitHub Actions.
- 워크플로(workflow)·잡(job)·스텝(step): 워크플로 = `ci.yml` 파일 하나, 잡 = 러너 한 대에서 도는 작업 묶음(여기서는 3개), 스텝 = 잡 안의 명령 한 줄. Jenkins 에 익숙하면 "Jenkins 의 job = GitHub 의 workflow, GitHub 의 job = Jenkins 의 stage" 로 이름이 한 칸씩 어긋난다(장표 123).
- 러너(runner): 잡을 실제로 돌리는 컴퓨터. `runs-on: ubuntu-24.04` = GitHub 가 빌려주는 우분투 24.04 가상 컴퓨터, 매번 새로 켜진다.
- ctest: CMake 에 `add_test` 로 등록된 테스트를 모아 돌리는 도구. `--output-on-failure` 면 실패한 테스트의 출력만 보여 준다.
- 연기 테스트(smoke test): "켜지기는 하나, 연기가 나지는 않나"를 보는 가장 얕은 테스트. 숫자의 좋고 나쁨이 아니라 "돌아간다"를 본다.
- 아티팩트(artifact): 잡이 끝난 뒤 내려받을 수 있게 남긴 파일.
- `needs:`: "이 잡이 성공한 다음에만 시작하라"는 의존 관계.
- 단위: 1 kHz = 1초에 1,000번(1 ms 마다 한 번). "2초" = 2,000주기. "약 1분 10초" = 잡 하나가 끝날 때까지의 벽시계 시간.

## 4. 쉬운 예시
- 비유: 공항 보안 검색의 1차 X-레이. 짐을 모두 열어 보는 정밀 검사(2단계)는 비싸고 오래 걸리니, 먼저 X-레이(1단계)로 빠르게 훑고, 여기서 걸리면 정밀 검사대로 보낼 것도 없이 탑승을 막는다.
- 숫자 예시: 11/04 의 한 번의 push 에서 rt_core 1분 13초, 그 뒤 fleet_integration 1분 52초와 mujoco 25초가 동시에 돌았다. 그래서 전체는 약 1분 13초 + 1분 52초 ≈ 3분 남짓이다. 만약 rt_core 의 ctest 가 2초 만에 실패했다면, 2단계 두 잡은 시작하지 않으므로 약 2분을 아낀다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 트리거·러너·스텝 순서는 `.github/workflows/ci.yml` 19~66줄(push · pull_request · workflow_dispatch, `runs-on: ubuntu-24.04`, apt → cmake → ctest → jitter_bench → make_table1 → fleet 테스트 3파일 → 대시보드 JSON → upload-artifact `jitter-ci`).
- 확인: ctest 4건은 `rt_control/rt_core/CMakeLists.txt` 의 `add_test` 4개(spsc_ring, control_step, state_machine, jitter_smoke `--no-rt --seconds 2 --period-us 1000`). mujoco_backend 테스트는 `RT_CORE_WITH_MUJOCO` 옵션이 켜진 3번 잡에서만 등록된다.
- 확인: fleet 단위 15건 = `grep -c "^def test_"` 로 센 6 + 3 + 6.
- 확인: "약 1분 10초"는 `docs/ENVIRONMENT.md` 5-3 의 그림, 실측 1분 13초는 `docs/LOG.md` 11/04("rt_core 1m13s · mujoco 25s · fleet_integration 1m52s").
- 확인: "싼 검사부터"는 `docs/DECISIONS.md` 2026-11-03 (D4) "CI 는 2단계: 가짜로 빠르게, 진짜로 한 번".
- 다시 보기: `gh run list -L 1`(마지막 run 의 ✓/✗), `gh run view <ID>` (잡별 시간), 실패하면 `gh run view <ID> --log-failed | tail -40`.

## 6. 자주 하는 오해·함정
- "CI 의 jitter_bench 숫자가 나쁘니 코드가 느리다"는 오해: 러너에는 RT 커널도 SCHED_FIFO 권한도 없다. 여기 숫자는 "돌아간다"의 증거일 뿐이다(ci.yml 머리말 14~15줄도 같은 말).
- `ci.yml` 머리말 주석은 아직 "~2분 · ~5분 · ~3분"이라고 적혀 있다. 처음 설계할 때의 어림이고, 실측은 1분 13초 · 1분 52초 · 25초다(LOG 11/04). 숫자를 말할 때는 실측을 쓴다.
- 1단계가 통과했다고 다 된 것은 아니다. 11/05 의 CI 빨강(`NameError: request_stop`)은 1단계를 통과하고 2단계 fleet_integration 에서 잡혔다 — 당시 단위 테스트가 수집기의 `main()` 을 타지 않았기 때문이다. 그래서 `main()` 한 바퀴 스모크 테스트를 추가해 지금은 1단계에서도 잡힌다(그 결과가 test_collector_resilience 의 6번째 테스트).
- "문서만 고쳤으니 CI 는 안 봐도 된다"는 함정: 문서 커밋도 push 마다 3잡이 전부 돈다. 규칙은 push 뒤 `gh run list -L 1` 확인이다(빨간 배지는 포트폴리오 첫 화면).

## 7. 면접 한 문장
"CI 1단계는 1분 남짓 안에 C++ 단위 테스트 4건과 파이썬 단위 테스트 15건을 백지 러너에서 돌리고, 여기서 떨어지면 비싼 2단계는 돌리지 않습니다 — 싼 검사부터 하고, 2단계가 깨지면 논리 문제인지 환경 문제인지를 1단계 결과로 먼저 가릅니다."
