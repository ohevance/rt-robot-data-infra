# 장표 127 — 결정 기록 (3/3) — 측정·검증·범위
*위치: 7부 왜·사고·방식 · 결정 3/3 측정·검증·범위*

## 1. 이 장표가 왜 있나

7부는 "왜 이렇게 만들었고, 무엇이 깨졌나"를 답하는 장이다. 결정 기록 세 장 중 앞 둘(125 실시간 쪽, 126 관제 쪽)은 **무엇을 어떻게 만들지**의 결정이었다. 이 장표는 나머지 한 묶음 — **어떻게 재고(측정), 어떻게 믿게 하고(검증), 어디까지 할지(범위)** — 를 모은다. 3부 검증과 6부 CI 에서 본 숫자들이 "왜 그 조건으로 쟀나"라는 질문을 받으면 답이 여기 있다. 각 행은 `docs/DECISIONS.md` 의 한 항목을 "결정 / 이유 / 버린 대안" 세 칸으로 줄인 것이다. 다음 장표(128)부터는 "결정대로 만들었지만 처음부터 돌지는 않았다"는 사고 11건이다.

## 2. 장표를 하나씩 읽기

표의 세 칸은 결정(날짜 또는 D 꼬리표), 이유, 버린 대안이다. 괄호의 D1·D4·D5 는 2주 일정의 날짜 꼬리표(장표 130)다.

- 1행 "DDS 지연은 왕복(RTT)으로 (D1) / 두 컴퓨터의 시계 차이와 무관. 한 방향 ≈ RTT/2 / 한 방향 지연 — 시계 맞춤 필요": 표②(3부)의 DDS 지연은 ping 을 보내고 pong 이 돌아오기까지의 왕복 시간이다. 보낸 쪽 시계 하나로 재니 두 컴퓨터의 시계가 몇 ms 어긋나도 상관없다. 한 방향 지연은 "보낸 시각(A 시계) − 받은 시각(B 시계)"이라 시계가 다르면 수십 ms 씩 틀린다.
- 2행 "장애 주입은 docker stop/start 와 kill, 측정은 전부 DB 로 (D4) / 재현 가능하고, 숫자는 수집기가 이미 DB 에 남기는 것으로 / 네트워크 장애 도구(tc) — 2주 밖": 브로커·DB 는 컨테이너를 멈추고 다시 켜고, 수집기는 SIGTERM 으로 죽인다. 감지·복구·유실 숫자는 주입 스크립트가 따로 재지 않고 수집기가 DB 에 남긴 `collector_stats`·`telemetry(seq)` 를 **질의**해서 낸다 — 시스템이 자기 숫자로 장애를 설명해야 운영 중에도 쓸 수 있다. 패킷을 지연·유실시키는 `tc`(리눅스 트래픽 제어)는 더 현실적이지만 2주 안에 넣지 않았다.
- 3행 "CI 는 2단계: 가짜로 빠르게, 진짜로 한 번 (D4) / 1분 안에 논리, 2분 더에 진짜 컨테이너. 싼 검사부터 / 통합만 / 단위만": 장표 119~121 의 구조. 단위만 있으면 진짜 환경 문제를 못 잡고(11/04·11/05 사고가 증거), 통합만 있으면 매번 느리고 어느 층이 깨졌는지 못 가른다.
- 4행 "MuJoCo 는 Backend 의 한 구현, 빌드 옵션 기본 OFF (D5) / MuJoCo 없는 환경(CI 1단계·Pi)에서도 빌드. 제어 코드 무변경 확인 / MuJoCo 를 필수 의존성으로": 장표 121 의 근거. 필수로 만들면 MuJoCo 가 없는 Pi 와 1단계 러너에서 빌드가 깨진다.
- 5행 "부하 측정은 120초, 온도·스로틀 기록, Pi 는 측정만 (11/04) / 80 °C 스로틀이 수치를 오염시킨다. 자격 증명은 WSL 한 곳 / 방열판 달고 300초 — 조건이 바뀌면 일반 커널도 다시": 방열판 없는 Pi 4 는 부하 75초에 45 → 75 °C 까지 올랐고, 80 °C 부터 펌웨어가 클럭을 내린다(스로틀). 그 상태의 지연은 "커널 때문"과 "클럭 때문"을 가를 수 없어 부하 측정을 120초로 자르고, 측정 전·후 온도와 `get_throttled` 플래그를 `.meta` 에 적어 표 비고에 붙인다. 플래그가 0 이 아닌 줄은 표에 올리지 않고 다시 잰다. "Pi 는 측정만": Pi 에는 GitHub 로그인(gh)을 두지 않고 결과만 `scp` 로 WSL 에 가져와 커밋한다 — 측정 장비에 자격 증명을 넣지 않고 커밋 주체를 하나로.
- 6행 "표①의 조건은 커널 × 부하 × 고정/격리 × 도구 × 시간 (11/05) / 줄 하나가 반박 하나를 막는다 / RT 부하 한 줄만": 표①은 한 번에 변수 하나만 바꾼 대조 실험 모음이다. 일반 커널 줄이 없으면 "일반이면 얼마였는데요?", 한가 줄이 없으면 "한가하면 다 그렇다"(실제 한가 max 는 일반 24.9 / RT 27.8 us 로 같았고 차이는 부하에서만 781 → 301 로 났다), 고정과 격리를 안 나누면 "CPU 하나 주면 되지 않나"(고정만 301 → 311 로 효과 없음, 격리가 189), 내 측정기만 있으면 "측정기가 틀렸다"(표준 cyclictest 가 같은 방향·같은 급), 60초만 재면 분당 한 번꼴 사건을 놓친다(한가 60초 24.9 vs 300초 376 us), 온도가 없으면 "스로틀 아니냐". 반대로 조건을 더 늘리는 것(여러 우선순위·주기)은 질문이 늘지 않는데 줄만 는다.
- 7행 "부하 정의는 lib_stress.sh 한 곳, 쓴 값은 .meta (11/05) / 도구 비교 중 vm 512M vs 256M 차이가 측정기 차이로 보였다 / 스크립트마다 따로": E19-d 에서 "cyclictest 132 vs jitter_bench 301" 의 차이를 쫓다 보니 일부는 측정기가 아니라 **부하 정의**(stress-ng 메모리 버퍼 512M vs 256M → munmap/IPI 빈도)의 차이였다. 그래서 두 스크립트의 stress-ng 기동을 `scripts/lib_stress.sh` 의 `start_stress <초> <vm_bytes>` 하나로 묶고, 쓴 값을 `.meta` 에 적는다. 기본값(cyclictest 512M, jitter 256M)은 통일하지 않았다 — 이미 14줄이 각자의 값으로 쟀고 같은 도구 안의 전·후 비교는 그 값으로 성립하기 때문. 두 도구를 직접 비교할 때만 `STRESS_VM_BYTES` 를 같게 준다.
- 8행 "6주 계획을 2주로 줄이며 뺀 것 (11/03) / 실물 서보 백엔드·중력 보상·TLS 인증·디스크 큐·수동 ACK — 자리와 문서만 남김(TLS + 비밀번호는 11/10 에 운영 설정으로 넣었다) / 전부 하기 — 기한 안에 아무것도 증명 못 함": 지원일을 11/17 로 당기며 범위를 줄였다. 얇아도 전부 설명되는 저장소가 우선. 괄호는 뺀 것 다섯 가운데 하나가 11/10 에 돌아왔다는 표시다 — 운영 층을 인터넷에 여는 서버로 옮기면서 브로커의 바깥 문(8883)에 TLS 와 비밀번호를 걸었다(장표 140). 장치마다 인증서를 따로 주는 것(mTLS)은 아직 뺀 채다. 주의 — 이 행의 "뺀 것" 목록은 DECISIONS 파일의 2026-11-03 항목(실물 팔 SO-101, ALLEX 프로필, Isaac Sim, MCAP 전체 파이프라인, 가상 300대 → 50대, ZMQ SDK, EtherCAT)과 다르다. 장표의 다섯 가지는 파일 여러 곳(E16 "중력 보상 보류", D5 실측 "수동 ACK 보류", D4 "backlog 는 메모리(디스크 큐 아님)", HANDOVER 보류 목록)에 흩어진 **보류 항목**을 모은 것이다. 발표에서는 "파일의 뺀 것 7가지 + 뒤에 보류로 돌린 것들"로 말한다.
- 아래 비고 "출처: docs/DECISIONS.md. 파일에는 전체 46건(11/11 기준 — 11/05 까지 28건, 그 뒤 18건은 7부 덧붙임 장표에서), 여기는 11/05 까지에서 면접에서 물을 만한 25건(세 장 8 + 9 + 8 행)": 결정 장표 세 장이 파일의 어디까지를 덮는지 적은 줄이다. 11/05 까지의 28건 가운데 25건을 실었고(빠진 셋은 로봇 프로필에 관한 둘 — 1부 단계 6 에서 다뤘다 — 과 장표 자체에 관한 하나), 11/06 뒤의 18건(ALLEX 3 · 릴리스와 운영 8 · 11/11 의 7)은 덧붙임 장표(136~144)와 4부가 다룬다 — 11/11 의 일곱은 롤백 가지 순서 · 세어서 남기기 · 왕복 측정 간격(장표 141·142), 공개 전 점검을 pptx·docx 안까지(장표 141 의 마지막 행) · 세는 단위(장표 115 의 비고), 그리고 저녁의 둘 — 지원 기준을 Framework S/W 엔지니어로(장표 102) · ZeroMQ 어댑터(장표 143·144)다. 11/05 의 장표에는 "전체 24건 · 여기는 18건"이라고 적혀 있었다 — 둘 다 실제와 달랐고(그때 파일은 28건, 장표의 행은 25) 11/11 에 세어서 바로잡았다.

## 3. 용어와 단위

- RTT(Round-Trip Time, 왕복 시간): 보내고 되돌아오기까지. 한 방향 ≈ RTT/2.
- `tc`(traffic control): 리눅스에서 네트워크 지연·유실·대역폭 제한을 흉내 내는 도구.
- 스로틀(thermal throttling): 온도가 한계(Pi 4 는 80 °C)에 닿으면 펌웨어가 클럭을 내리는 것. `vcgencmd get_throttled` 의 플래그가 0 이 아니면 걸린 적이 있다는 뜻.
- `.meta`: 측정 결과 파일 옆에 붙는 작은 메타데이터 파일(커널, 부하 값, 온도 전·후, 플래그).
- 고정(pin, CPU affinity)과 격리(isolcpus): 고정은 "내 스레드를 이 CPU 에서만", 격리는 "이 CPU 에 다른 일이 못 오게". 둘은 다르다(301 → 311 vs 189).
- stress-ng `vm` 부하와 512M/256M: 메모리를 할당·해제하며 두드리는 부하 종류와 그 버퍼 크기(바이트). 크기가 다르면 munmap(메모리 해제)·IPI 의 빈도가 달라져 지연 분포가 바뀐다.
- 자격 증명(credential): GitHub 로그인 토큰 같은 비밀값. 측정 장비(Pi)에는 두지 않는다.

## 4. 쉬운 예시

- 왕복으로 재는 이유: 서울에서 부산으로 소포를 보내 "며칠 걸렸나"를 알고 싶다. 부산 친구 시계가 하루 틀려 있으면 한 방향 측정은 하루 틀린다. 내가 보내고 내가 받기까지(왕복)를 내 시계로 재면 친구 시계는 상관없고, 반으로 나누면 한 방향 어림값이다.
- 120초 상한: 체온이 오르면 달리기 기록이 나빠진다. 선수 비교를 공정하게 하려면 모두 같은 시간(120초) 동안만 뛰게 하고 체온을 기록해 두는 것. 300초 뛰게 하면 더 많은 데이터가 나오지만 열이 기록을 오염시킨다.
- 범위 줄이기 숫자: 6주 계획을 2주로, 가상 장치 300대를 50대로. 11/17 지원까지 "다 설명되는 것"이 "많은 것"보다 우선이라는 판단.

## 6. 자주 하는 오해·함정

- "결정 기록은 잘된 선택만 적는다"는 오해: 7행은 내 스크립트 둘의 부하가 달랐던 **실수**에서 나온 결정이고, 5행의 "Pi 는 측정만"은 11/04 밤 창을 헷갈려 root 소유 파일로 커밋이 막힌 사고에서 나왔다. 버린 대안 칸이 있는 이유도 "다른 길도 봤다"를 남기기 위해서다.
- "부하 값을 통일하지 않은 것은 게으름"이라는 오해: 통일하면 이미 잰 14줄의 전·후 비교가 깨진다. 같은 도구 안의 비교는 같은 값이면 되고, 도구 간 직접 비교 때만 같게 준다 — 그래서 `.meta` 에 값을 적는 것이 핵심이다.
- "왕복/2 = 한 방향"은 어림이다. 가는 길과 오는 길이 비대칭이면 틀릴 수 있다. 같은 호스트 프로세스 간(표②)에서는 대칭에 가깝다.
- "120초는 짧아서 통계가 약하다": 1 kHz 면 120초에 120,000 샘플이다. 드문 사건(분당 한 번꼴)을 보려는 한가 측정만 300초로 늘렸다.
- 이 장표의 "뺀 것" 다섯 가지와 파일의 일곱 가지를 섞어 말하지 않는다 — 질문이 나오면 파일을 연다.

## 7. 면접 한 문장

"측정에 관한 결정은 전부 '반박 하나를 막는 줄 하나'였습니다 — 왕복으로 재서 시계 차이를 지우고, 일반 커널·한가·고정·표준 도구·300초 줄을 각각 두어 '커널 덕이 아니다'라는 반박을 하나씩 막고, 부하 정의를 한 함수로 묶어 제 두 스크립트가 다른 부하를 쓰던 실수까지 기록에 남겼습니다."
