# 장표 133 — 면접 한 문장 모음 — 장표에서 바로 꺼내 쓰는 문장 12개
*위치: 7부 왜·사고·방식 · 면접 한 문장 12*

## 1. 이 장표가 왜 있나

앞 장표(132)가 "면접에서 다음 단계로 말할 것"으로 끝났다. 이 장표는 반대로 **이미 한 것**을 면접에서 한 문장으로 말하는 연습장이다. 1~6부에서 본 숫자와 판단을 주제 12개(표①, 비용, 측정기, 열, 구조, 안전, 물리, 관제, QoS, OTA, 기록, CI)로 묶어, 각각 "숫자 하나 + 그 숫자가 뜻하는 판단 하나"로 압축했다. 설명 문서 145개의 7절("면접 한 문장")이 장표마다 있지만, 이 장표의 12개는 그중 **가장 자주 물을 질문**에 대한 답이다. 각 문장은 반드시 저장소의 숫자로 되어 있어서, 뒤에 "그 숫자 어디 있나?"가 와도 파일을 열어 보여 줄 수 있다. 뒤에는 부록 용어 2장(134·135)과 끝(136~138)이다.

## 2. 장표를 하나씩 읽기

글머리표 12개. 각 문장의 숫자가 어디서 왔고 무슨 판단인지 하나씩 읽는다.

- 표① "우선순위는 줄을 앞세울 뿐이고 꼬리를 자르는 건 커널이다 — WSL 에서 p50 은 좋아졌지만 max 는 그대로였던 이유. Pi 에서 커널만 바꿔 781 → 301, 격리로 189": WSL2 에서 SCHED_FIFO 를 켜자 p50 92 → 37 us 로 좋아졌지만 max 는 921 → 937 us 로 그대로(E01·E02). Pi 4 부하 중 max 가 일반 커널 781 us → RT 커널 301 us(커널만 바꿈) → isolcpus=3 격리 189 us(E18·E19). 판단: 우선순위(스케줄러)는 대기열 순서를 바꾸고, 꼬리(max)는 커널이 선점 불가 구간을 얼마나 짧게 하느냐가 정한다.
- 비용 "RT 커널은 상한을 사고 평균을 조금 내준다 — 부하 p99 가 146 → 185 로 나빠진 것도 표에 그대로 적었다": 표①의 jitter_bench 부하 줄에서 p99 가 일반 145.7 → RT 185.2 us 로 **나빠졌다**. RT 커널은 선점 가능 지점을 늘려 최악(max)을 자르지만 그만큼 평균적인 길이 조금 길어진다. 나쁜 숫자를 표에서 빼지 않았다는 것이 둘째 요점.
- 측정기 "표준 도구와 2.3배 달라서 변수를 하나씩 지웠다 — 같은 설정에서 274 대 270 으로 일치했고, 차이는 스레드 배치와 부하 정의였으며, 그 과정에서 내 스크립트 둘의 부하가 달랐던 실수를 찾았다": RT 부하 중 cyclictest max 132 vs jitter_bench 301 us(2.3배, E19-d). 일(50 → 0 us)도 우선순위(80 → 90)도 아니었고, cyclictest 를 jitter_bench 와 같은 설정(스레드 1개, CPU 2 고정, 우선순위 80)으로 맞추자 274 vs 270. 나머지 차이는 `-S`(CPU 마다 스레드) 배치와 stress-ng 메모리 버퍼 512M vs 256M — 내 두 스크립트가 다른 부하를 쓰고 있었다. 결과가 DECISIONS 2026-11-05 lib_stress.sh 결정.
- 열 "임베디드 보드의 지연 측정은 열 조건을 같이 기록하지 않으면 재현도 비교도 안 된다 — 표①의 모든 Pi 줄에 온도와 스로틀 여부가 붙어 있는 이유": Pi 4 는 80 °C 부터 클럭을 내린다(스로틀). 표①의 Pi 줄 14개 모두 `.meta` 에 측정 뒤 온도와 `throttled_after=0` 이 있고, 측정 전·후 온도가 둘 다 있는 8줄은 표 비고에 "온도 45.8→70.1 °C, 스로틀 0" 식으로 찍힌다(손으로 돌린 E19-d 4줄과 11/04 일반 커널 jitter 2줄은 전 온도가 na).
- 구조 "제어 코드는 ROS 2 와 로봇에서 떼어 두었다 — 백엔드를 SimLag 에서 MuJoCo 로 바꿨는데 제어 코드는 한 줄도 안 바뀌었다": `rt_core` 는 ROS 2 없는 순수 C++, 로봇은 `Backend` 인터페이스(init/write_command/read_state) 뒤에. `SimLagBackend` → `MujocoBackend` 교체에 `control_step.cpp` 와 노드가 바뀌지 않았다(E15, DECISIONS D5).
- 안전 "명령이 50 ms 끊기면 지금 자리에 멈추고 FAULT, 명령이 다시 와도 100 ms 연속 정상이어야 READY — 전이표 밖의 길은 전부 막혀 있다": ControlStep 의 워치독 50 ms, 상태 머신의 전이표(`state_machine.cpp`), 복귀 조건 100 ms 연속 정상. if 문이 아니라 표 하나라서 적지 않은 전이는 일어날 수 없다(1부 단계 5, 장표 125).
- 물리 "물리가 들어오자 어깨가 1.1° 처졌다 — SimLag 로는 절대 못 보는, 중력 보상이 필요하다는 숫자 근거": 목표 −0.200 rad 에 실제 −0.180(E16) / −0.181(E20 기록 요약) rad, 0.02 rad ≈ 1.1°. 수식 한 줄 모델(SimLag)에는 중력이 없다. 다음 단계(중력 보상)의 근거 숫자.
- 관제 "유실 0 은 처음부터 0 이 아니었다 — 측정 맹점을 고치자 53, 원인 셋을 추적해 둘은 설정과 종료 처리로 막고 하나는 큐 상한의 설계 수치로 정리했다": E07 에서 기준점을 "장애 직전 마지막 번호"로 고치자 브로커 10초 중단의 유실 53 / 1434. 원인 셋 — 브로커 재시작 경쟁(persistence true 로), 수집기 종료 순간(곱게 종료로), 큐 상한(장치 버퍼 크기의 설계값으로 문서화). 고친 뒤 0 / 1400(E08, 표③).
- QoS "보호가 없으면 얼마를 잃는지도 쟀다 — QoS 0 은 508, QoS 1 지속 세션은 0": 수집기 종료 10초에 QoS 0 은 508 / 1312 유실, QoS 1 지속 세션은 0 / 1311(표③ collector 줄 둘, 소실험 11/04). 보호의 값을 숫자로 보인 줄.
- OTA "나쁜 펌웨어는 5%, 세 대에서 헬스 게이트가 잡아 1초에 롤백하고 47대는 건드리지도 않는다": 50대의 5% = 3대(ceil)에만 나쁜 펌웨어가 닿고, 헬스 게이트가 state 를 보고 1.0초에 롤백, 나머지 47대는 배포 자체가 안 된다(표③ bad_firmware 줄, 2부 ⑥).
- 기록 "관제는 1 Hz 요약을 서버로, 기록은 100 Hz 원본을 로봇 안에 — 30초 기록에서 100.0 Hz·틈 0·처짐 1.1° 가 사람 손 없이 나온다": 관제(MQTT)는 1 Hz 요약, 기록(rosbag2 MCAP)은 100 Hz 원본을 로봇 안 디스크에. E20 의 30초 기록: `/joint_states` 2,964행 100.0 Hz, 틈 0, 추종 오차 표에 어깨 0.0191 rad ≈ 1.1° 가 자동으로.
- CI "푸시마다 러너가 1 kHz 루프, 물리, 장애 3종과 롤백, 진짜 설치를 다시 돌린다 — 그리고 실제로 세 번 나를 잡았다": 잡 1(1 kHz 2초 연기 드롭 0), 잡 3(물리 2,000주기), 잡 2(장애 3종 + 롤백 + OTA + 진짜 패키지 설치와 깨진 패키지 거부). 11/04 TimescaleDB 초기화 경쟁, 11/05 request_stop 삭제, 11/10 상대 경로 슬롯 — 셋 다 CI 만 빨갰다(장표 120·122). "진짜 설치"와 "세 번"은 11/11 에 고친 말이다(11/05 에는 "두 번").

## 3. 용어와 단위

- p50 / p99 / max: 중앙값 / 100번 중 99번 이내 / 최악 한 번. 단위 us(마이크로초, 100만분의 1초). 1 ms = 1,000 us.
- 꼬리(tail): 분포의 오른쪽 끝, 즉 드물지만 큰 값들(p99.9, max). 제어 루프는 평균이 아니라 꼬리로 죽는다.
- 격리(isolcpus): 부팅 옵션으로 CPU 하나를 일반 스케줄링에서 떼어 둔 것. 고정(pin)과 다르다.
- 스로틀: 온도 한계에서 클럭을 내리는 보호 동작. 측정값을 오염시킨다.
- 전이표: (지금 상태, 사건) → 다음 상태 를 적은 표. 표에 없는 조합은 무시된다.
- 워치독 50 ms / 복귀 100 ms: 명령 공백 허용 시간 / FAULT 에서 READY 로 돌아오려면 연속 정상이어야 하는 시간.
- 유실 "53 / 1434": 1434 = 장애 창에서 만들어진 메시지 수, 53 = 못 받은 수(장치별 일련번호로 센다).
- QoS 0 / 1, 지속 세션: 보내고 잊음 / 받았다는 확인(PUBACK) / 구독자가 없는 동안 브로커가 보관.
- 헬스 게이트, 카나리 5%: 단계마다 장치 상태를 보고 통과/롤백 / 처음 5% 에만 먼저 배포.
- Hz, 틈(gap): 1초에 몇 번 / 연속 메시지 간격이 설계 주기의 3배를 넘은 곳.

## 4. 쉬운 예시

- 쓰는 법: 질문 "실시간 커널이 왜 필요했나요?" → 표① 문장. "그 측정 믿을 수 있나요?" → 측정기 + 열 문장. "유실 0 이라는데 정말인가요?" → 관제 + QoS 문장. "실물 없이 뭘 증명했나요?" → 구조 + 물리 문장. "운영은요?" → OTA + 기록 + CI 문장. 12개 중 질문에 맞는 둘을 고르면 거의 모든 기술 질문이 덮인다.
- 숫자 예시(표①): 1 ms 주기에서 max 781 us 는 예산의 78%, 189 us 는 19%. 같은 코드가 커널과 격리만으로 4배 여유가 생겼다.
- 숫자 예시(OTA): 50대 × 5% = 2.5 → 올림 3대. 3대가 나쁜 펌웨어를 받고 헬스 게이트가 1.0초에 잡는다. 러너(10대)에서는 1대, 0.4초.
- 말하는 요령: 문장마다 **숫자 → 판단** 순서다("781 → 301 → 189 … 그래서 꼬리는 커널이 자른다"). 판단만 말하면 주장, 숫자만 말하면 암기다.

## 6. 자주 하는 오해·함정

- 문장을 **암기**하지 않는다. 숫자의 출처 파일을 한 번씩 열어 본 뒤라야 뒤따르는 질문("어떤 조건에서?")에 답할 수 있다. 조건(WSL2 참고값 / Pi 4 실측 / 러너)을 빼고 숫자만 말하는 것이 가장 흔한 실수.
- "RT 커널이 모든 것을 좋게 했다"고 말하지 않는다 — 비용 문장이 바로 반례다(p99 146 → 185). 나쁜 숫자를 먼저 말하면 좋은 숫자가 믿을 만해진다.
- "유실 0" 을 처음부터 0 이었던 것처럼 말하지 않는다. 53 을 찾은 과정(E07)이 이 저장소에서 가장 중요한 줄이다.
- 1.1° 는 "버그"가 아니라 물리가 보여 준 **정상 상태 오차**다. 다음 단계(중력 보상)의 근거로 말한다.
- "열" 문장의 "모든 Pi 줄"은 `.meta` 기준이다. 표 비고에 온도가 없는 줄을 지적받으면 `.meta` 를 연다.
- CI 가 "나를 잡았다"는 말은 약점이 아니라 검사가 작동한다는 증거로 말한다 — 그리고 그 뒤 생긴 규칙 둘(장표 129)을 붙인다.

## 7. 면접 한 문장

"열두 문장은 전부 '숫자 하나와 그 숫자가 가른 판단 하나'입니다 — 781 → 301 → 189 로 꼬리는 커널이 자른다, 146 → 185 로 RT 는 평균을 조금 내준다, 53 → 0 으로 유실 0 은 의심해서 얻은 숫자다 — 어느 숫자든 저장소의 어느 파일 몇 줄인지 바로 열어 드릴 수 있습니다."
