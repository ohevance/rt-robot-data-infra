# 장표 135 — 부록 · 용어 (2/2) — 관제·미들웨어·물리 쪽
*위치: 7부 부록 · 용어 2/2 관제·물리*

## 1. 이 장표가 왜 있나
앞 장표(134)는 실시간 쪽 말(PREEMPT_RT, p99.9, SCHED_FIFO, SPSC 링, IPI)을 모았다. 그런데 이 저장소에는 동네가 세 곳 더 있다. 로봇 안에서 프로그램끼리 말을 주고받는 미들웨어(1부 단계 2, 장표 14~16, 검증은 87~88), 로봇 밖 장치 50대의 데이터를 서버로 모으는 관제(2부 데이터의 길, 장표 59~85, 검증은 97~100), 그리고 명령이 정말 팔을 움직였는지 보여 주는 물리 시뮬레이션(1부 단계 6·7, 장표 37~46, 검증은 96)이다. 질문은 이렇다. "데이터가 로봇 밖으로 나가고, 서버에 쌓이고, 물리로 움직임을 확인하는 이야기를 하려면 최소한 어떤 말을 알아야 하나?" 이 장표는 그 답으로 여섯 묶음을 카드 한 장씩에 적었다. 이 장이 1~7부의 마지막 장표이고, 다음부터는 '끝' 세 장(136~138)이다.

## 2. 장표를 하나씩 읽기
카드 여섯 장을 윗줄 왼쪽부터 오른쪽으로, 그다음 아랫줄 순서로 읽는다. 동그라미 글자(R2, MQ, LWT, DB, OTA, MJ)는 카드 표시다.

- 카드 1 "ROS 2 · 토픽 · DDS · RMW · QoS"
  - "토픽 = 이름표 붙은 데이터 흐름. DDS 가 발견·전달": 이 저장소의 토픽은 셋이 핵심이다 — 명령 `/joint_command`(50 Hz), 상태 `/joint_states`(100 Hz), 자기 설명 `/rt_status`(1 Hz). 보내는 프로그램과 받는 프로그램은 서로를 모르고 토픽 이름만 안다. 서로를 찾아 주고(발견) 실제로 실어 나르는(전달) 일은 DDS 가 한다.
  - "RMW = ROS 가 DDS 를 부르는 층(Fast DDS / Cyclone)": DDS 구현체는 여럿이다. 어느 것을 쓸지는 환경변수 `RMW_IMPLEMENTATION` 하나로 고른다. 표②가 바로 두 구현체를 같은 조건으로 비교한 표다.
  - "QoS: reliable(재전송) vs best_effort(잃을 수 있음), depth(큐 깊이)": reliable 은 등기 우편(분실되면 다시 보낸다), best_effort 는 일반 우편(빠르지만 잃을 수 있다). depth 는 "최근 몇 개까지 담아 두나"이고, 측정기 `rtt_bench.py` 의 기본값은 10 이다.
- 카드 2 "MQTT · 브로커 · QoS 0/1 · 지속 세션"
  - "브로커 = 우체국. 장치는 발행, 서버는 구독": 브로커는 Mosquitto 다. 장치는 `fleet/<id>/telemetry` 같은 토픽에 1초마다 보내고(발행), 수집기는 그 토픽들을 받아 간다(구독). 장치는 서버 주소를 몰라도 되고 브로커만 안다.
  - "QoS 0 보내고 잊음 / 1 받았다는 확인(PUBACK)": QoS 0 은 확인이 없어 가장 가볍다. QoS 1 은 "받았다"는 답(PUBACK)이 올 때까지 다시 보낸다(적어도 한 번 도착). 텔레메트리는 기본 0, 끊겼다 붙었을 때 몰아 보내는 버퍼와 명령은 1 이다.
  - "지속 세션(clean_session=False) = 없는 동안 브로커가 대신 보관": 수집기를 `--qos 1` 로 띄우면 고정 이름(client_id "collector")으로 지속 세션을 맺는다. 수집기가 잠깐 죽어 있는 동안 브로커가 수집기 몫의 QoS 1 메시지를 들고 있다가, 다시 붙으면 넘겨 준다. 결과(표③-2): 수집기 10초 재시작에서 QoS 0 은 1,312개 중 508개 유실, QoS 1 지속 세션은 1,311개 중 0개 유실.
- 카드 3 "유언 · 보관 메시지 · keepalive"
  - "유언(LWT) = 비정상 종료 때 브로커가 대신 발행하는 'offline'": 장치가 접속할 때 "내가 소리 없이 사라지면 이 메시지를 대신 보내 달라"고 맡겨 둔다. 전원이 뽑혀도 서버는 `offline` 을 받는다. 코드: `device_agent.py` 의 `will_set(..., payload="offline", qos=1, retain=True)`.
  - "보관(retained) = 마지막 값을 새 구독자에게 바로 — '지금 상태'": 브로커가 그 토픽의 마지막 값을 기억해 두었다가, 나중에 구독을 시작한 쪽에도 바로 준다. 장치의 online/offline 상태(`fleet/<id>/status`)를 이렇게 보내므로, 수집기를 새로 띄워 `fleet/+/status` 를 구독하는 순간 다음 메시지를 기다리지 않고 50대의 "지금 상태"를 한꺼번에 받는다.
  - "keepalive = 이 시간 동안 조용하면 PINGREQ, 1.5배 넘으면 끊김": 장치는 기본 10초 동안 주고받은 것이 없으면 "살아 있다"(PINGREQ)를 보낸다. 브로커는 1.5배(15초) 동안 아무 소리가 없으면 연결을 끊고 그 장치의 유언을 발행한다.
- 카드 4 "TimescaleDB · 하이퍼테이블 · COPY · backlog"
  - "시간으로 자동 분할되는 PostgreSQL 표": 보통 표처럼 쓰지만 안에서는 시간 구간별로 잘게 나뉘어 있어서 "최근 10분" 같은 질의가 빠르다. 이 저장소에서는 telemetry, events, collector_stats 세 표가 하이퍼테이블이다.
  - "COPY = 묶음 적재(행마다 INSERT 보다 DB 왕복이 훨씬 적다)": 수집기는 1초 동안 받은 행을 모아 한 번에 밀어 넣는다. 코드 주석의 계산: 장치 300대 × 1 Hz 를 한 행씩 넣으면 DB 왕복이 초당 300번, 묶어서 COPY 하면 초당 1번. 그래서 장표는 배수를 말하지 않고 '왕복이 적다'고만 쓴다(5절).
  - "backlog = DB 가 죽은 동안 수집기가 들고 있는 묶음": DB 가 돌아오면 오래된 묶음부터 넣는다(`drain_backlog()`). 상한은 20만 행 — 50대 × 1 Hz 면 약 66분, 300대면 약 11분을 버틴다. 넘으면 가장 오래된 묶음을 버리고 센다. 대시보드 패널 12 에 보인다.
- 카드 5 "OTA · 단계 배포 · 헬스 게이트 · 롤백"
  - "OTA = 무선 펌웨어 갱신": Over-The-Air. 여기서는 가상 장치가 "적용하는 척" 2초(기본값)를 쓰는 시뮬레이션이다.
  - "단계 배포(카나리) = 5% 먼저, 괜찮으면 50%, 100%": `rollout.py --stages 5,50,100`(누적 퍼센트). 단계별 대수는 올림으로 정한다 — 50대의 5% = 2.5 → 3대.
  - "헬스 게이트 = 단계마다 state 를 보고 통과/롤백": 단계마다 5초(기본) 지켜보고, state 가 ok 가 아닌 장치가 허용 수(기본 0)보다 많으면 새 버전을 받은 장치 전부를 이전 버전으로 되돌린다. 결과(표③-3): 나쁜 펌웨어는 3/50 대에만 닿았고, 롤백 1.0초, 나머지 47대는 건드리지도 않았다.
- 카드 6 "MuJoCo · Menagerie · 중력 처짐 · 추종 오차"
  - "MuJoCo = 물리 엔진(중력·접촉·모터). Menagerie = 검증된 로봇 모델 모음": 팔 모델은 `third_party/mujoco_menagerie/trs_so_arm100/scene.xml`. 코드 속 용어 — mjModel(설계도, 읽기 전용), mjData(지금 이 순간의 상태), qpos(관절 각), qvel(관절 속도), ctrl(액추에이터 입력), mj_step(물리를 한 걸음 진행).
  - "중력 처짐 = 목표 아래로 쳐지는 정상 상태 오차(어깨 1.1°)": 어깨에 −0.200 rad 를 줬는데 −0.180 rad 에서 멈췄다. 위치 제어 모터는 유한한 힘(kp)으로 끌어당기므로 팔 무게가 걸리는 관절만 조금 덜 간다.
  - "추종 오차 = |목표 − 실제|, rad(× 57.3 = 도)": 11/05 기록의 자동 요약에서 어깨 0.0191 rad × 57.3 ≈ 1.1°, 팔꿈치 0.0094 rad ≈ 0.5°.

## 3. 용어와 단위
- Hz(헤르츠): 1초에 몇 번. 50 Hz = 20 ms 마다, 100 Hz = 10 ms 마다, 1 Hz = 1초마다 한 번.
- rad(라디안): 각도 단위. 1 rad ≈ 57.3°, 한 바퀴 = 2π ≈ 6.28 rad.
- 발행/구독(publish/subscribe): 보내는 쪽은 토픽 이름에 올려 두기만 하고, 받는 쪽은 그 이름을 구독해서 가져간다. 서로의 주소를 몰라도 된다.
- PUBACK / PINGREQ: MQTT 짧은 신호의 이름. PUBACK = "받았다", PINGREQ = "나 아직 살아 있다".
- client_id: MQTT 접속 이름표. 지속 세션은 같은 이름으로 다시 붙어야 이어진다.
- 행(row): DB 표의 한 줄. 여기서는 장치 1대의 1초치 텔레메트리 한 건.
- 정상 상태 오차(steady-state error): 충분히 기다린 뒤에도 남는 목표와 실제의 차이.
- 카나리(canary): 탄광에 카나리아를 먼저 들여보내듯, 일부에 먼저 써 보고 이상하면 멈추는 방식.

## 4. 쉬운 예시
- 비유: 우편 제도로 한 번에 보면 이렇다. ROS 2/DDS 는 건물 안 사내 우편(가깝고 빠르다), MQTT 브로커는 동네 우체국(멀리 흩어진 50집의 편지), 지속 세션은 우체국의 "부재중 보관" 서비스(보관함 20,000통 한도), 유언은 "연락이 끊기면 이 엽서를 대신 부쳐 달라"고 맡긴 편지, 보관 메시지는 우체국 게시판에 붙여 둔 "지금 상태", COPY 는 편지 300통을 한 자루에 담아 한 번에 나르기, backlog 는 배달 못 간 자루를 창고에 쌓아 두기(20만 통 한도)다.
- 숫자 예시 1 (OTA): 50대에 5% → 2.5 → 올림 3대. 이 3대 중 1대라도 5초 안에 state 가 ok 가 아니면(허용 0) 롤백 → 나머지 47대(94%)는 나쁜 펌웨어를 아예 받지 않는다.
- 숫자 예시 2 (keepalive): 10초로 두면 조용히 죽은 장치를 15초 안에 안다. 30초로 늘리면 10초마다 튀던 전달 지연은 사라지지만(실험: 172초 동안 튐 0회) 감지가 45초로 늦어진다. 맞교환이다.
- 숫자 예시 3 (처짐): 0.020 rad × 57.3 ≈ 1.1°. 팔 길이를 30 cm 로 가정하면(예시용 가정, 실제 모델 치수 아님) 끝이 0.30 m × 0.020 = 0.006 m, 약 6 mm 내려간다. 컵을 집는 일이라면 무시하기 어려운 크기다.

## 6. 자주 하는 오해·함정
- "QoS 1 이면 유실 0" 이라는 오해: 장치만 QoS 1 이어서는 안 된다. 수집기도 `--qos 1`(지속 세션)이어야 수집기가 죽은 동안의 메시지를 브로커가 들고 있는다. 둘 다 필요하다.
- 지속 세션의 함정 둘 — ① 브로커가 재시작되면 세션도 사라진다. 그래서 `persistence true` 를 켰다(11/04 실측: 수집기보다 먼저 다시 붙은 장치 4~5대의 버퍼가 통째로 버려졌다). ② 보관함에는 상한이 있다. 7.5분 공백 동안 20,000개가 차서 마지막 49초분 2,450개(= 50대 × 1 Hz × 49초)가 버려졌다.
- client_id 충돌: 이름이 "collector" 로 고정이라 수집기 두 개가 뜨면 브로커가 2초마다 서로를 밀어내고 메시지를 반반 받는다. 그래서 `fleet/logs/collector.lock` 으로 하나만 뜨게 했다.
- "reliable 이면 제시간에 온다"는 오해: reliable 은 도착 보장이지 시간 보장이 아니다. 다시 보내느라 늦게 올 수 있다. 늦은 명령을 막는 것은 QoS 가 아니라 RT 쪽의 "최신 명령만" 규칙과 50 ms 워치독(1부 단계 5)이다.
- "처짐은 버그"라는 오해: 버그가 아니라 물리다. 실물에서도 같은 관절에서 같은 일이 난다. 그래서 중력 보상(토크를 미리 더해 주는 것)이 필요하다는 숫자 근거가 되었고, 2주 계획에서는 보류 항목으로 남겼다.
- "COPY 가 수십 배"를 실측처럼 말하는 함정: 면접에서는 "왕복 횟수가 초당 300번 → 1번으로 준다"는 구조적 이유로 말한다.

## 7. 면접 한 문장
"로봇 안은 ROS 2(DDS), 로봇 밖 50대는 MQTT 로 길을 나눴고, 유실 0 은 QoS 1 하나로 되는 게 아니라 수집기 지속 세션, 브로커 persistence, 보관함 상한까지 맞춰야 나온다는 것을 수집기를 일부러 죽여서 QoS 0 은 508개 유실, QoS 1 은 0개라는 숫자로 확인했습니다."
