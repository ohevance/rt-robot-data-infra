# 장표 112 — 표① 한 줄이 만들어지는 길 — 스크립트 다섯 개 (조건을 결과 옆에 적는다)
*위치: 6부 믿을 수 있나 · 측정 스크립트 5개*

## 1. 이 장표가 왜 있나
앞 장표(111)는 6부의 문을 여는 장 구분 장표였다. 5부에서 "숫자는 어디서, 어떤 조건에서 나왔나"를 알았으니, 6부의 질문은 "이 숫자들을 어떻게 믿나 — 누가, 무엇으로, 언제 다시 재나"다. 표①(실시간 깨어남 지연)의 한 줄은 사람이 손으로 명령을 쳐서 나온 것이 아니라 스크립트 다섯 개가 이어져 만든다. 이 장표는 그 다섯 개를 셰브론(화살촉 모양 상자) 다섯 개로 왼쪽부터 오른쪽으로 보여 준다.

핵심 문장은 제목의 괄호 "조건을 결과 옆에 적는다"다. 측정값만 남기면 나중에 "그때 부하는 얼마였나, 온도는 몇 도였나"를 알 수 없다. 그래서 측정 스크립트가 결과 파일 옆에 `.meta` 파일을 남기고, 표 생성기가 그 조건을 표의 비고 칸에 옮긴다. 장표 113·114 는 이 다섯 개 중 두 개(온도·스로틀 함수, 부하 함수)의 코드를 그대로 보여 준다.

## 2. 장표를 하나씩 읽기
셰브론 다섯 개를 왼쪽부터 읽는다. 각 셰브론의 머리가 스크립트 이름이고, 그 아래 줄들이 하는 일이다.

- 셰브론 1 "jitter_run.sh": 우리가 만든 측정기 `jitter_bench` 를 한 조건으로 돌리는 스크립트다.
  - "<label> <초> [stress] [cpu]": 인자 네 개. 라벨(결과 파일 이름이 된다), 측정 시간(초), 부하를 걸지(`stress`, 안 쓰면 한가), RT 스레드를 고정할 CPU 번호(선택).
  - "온도 읽기 → (부하 시작) → jitter_bench → .meta(커널·RT·부하·vm·prio·work·온도 전후·스로틀)": 순서다. 먼저 온도를 읽고, `stress` 면 부하를 시작하고, 측정기를 돌리고, 끝나면 `.meta` 에 조건을 적는다. `.meta` 의 항목은 라벨·날짜·커널 이름·실시간 플래그·측정 시간·부하 여부·부하 vm 크기·CPU·우선순위(prio)·주기당 일(work_us)·온도 전후·스로틀 플래그다.
  - "환경 변수: JITTER_PRIO · JITTER_WORK_US · STRESS_VM_BYTES(256M)": 인자로 안 받는 조건은 환경 변수로 바꾼다. 우선순위 기본 80, 주기당 일 기본 50 us, 부하의 메모리 버퍼 기본 256M. 11/05 에 우선순위 80 과 90 은 결과가 같다는 것을 확인했다(E19-d B).
- 셰브론 2 "cyclictest_run.sh": 표준 도구 cyclictest 를 같은 모양으로 돌리는 스크립트다. 우리 측정기와 표준 도구를 나란히 두어 서로 검증하기 위해 둘 다 있다.
  - "<label> <초> [stress]": 인자 세 개(CPU 고정 인자는 없다 — cyclictest 는 모든 CPU 에 스레드를 하나씩 띄운다).
  - "cyclictest -m -S -p 90 -i 1000 -h 1000 -q -D": 옵션의 뜻은 `-m` 메모리 잠금(스왑으로 쫓겨나지 않게), `-S` 모든 CPU 에 스레드 하나씩, `-p 90` SCHED_FIFO 우선순위 90, `-i 1000` 주기 1,000 us, `-h 1000` 히스토그램 상한 1,000 us, `-q` 조용히, `-D` 지속 시간(초).
  - ".meta 에 같은 항목(vm 512M)": jitter_run 과 같은 꼴의 `.meta` 를 남기되 부하 vm 크기의 기본값이 512M 다. 두 기본값이 다른 것이 11/05 의 교훈이 되었다(셰브론 4).
  - "CPU 마다 스레드 → 가장 나쁜 CPU 값을 표에": `-S` 로 CPU 네 개에 스레드가 하나씩 돌아 히스토그램이 네 개 나오는데, 표에는 그중 가장 나쁜 CPU 의 값을 올린다. 제어 루프는 최악을 기준으로 판단하기 때문이다.
- 셰브론 3 "lib_thermal.sh": 두 측정 스크립트가 `source` 해서 쓰는 공용 함수 모음(온도·스로틀).
  - "read_temp_mc: /sys/class/thermal/…/temp (밀리도)": 온도를 밀리도 정수로 읽는다. 51608 이면 51.6 °C.
  - "read_throttled: …/get_throttled (0 = 깨끗)": Pi 펌웨어의 스로틀 플래그를 읽는다. 0 이면 부팅 후 클럭이 내려간 적이 없다.
  - "thermal_meta_lines · thermal_summary": `.meta` 에 덧붙일 세 줄(측정 전 온도, 후 온도, 스로틀)과 사람이 보는 한 줄 요약을 만든다.
  - "없는 환경(WSL·러너)이면 na": 그 파일이 없는 곳(WSL2, GitHub 러너, 노트북)에서는 `na` 를 적는다. 스크립트가 죽지 않게 하는 것이 우선이다.
- 셰브론 4 "lib_stress.sh": 부하(stress-ng) 정의를 한 곳에 모은 공용 함수.
  - "start_stress <초> <vm>: stress-ng --cpu N --io 2 --vm 1 --vm-bytes": CPU 작업자를 코어 수만큼, I/O 작업자 2개, 메모리 작업자 1개(버퍼 크기 `vm`)를 지정한 초 동안 뒤에서 돌린다.
  - "stop_stress: timeout 까지 기다림": 측정이 먼저 끝나도 부하 프로세스가 스스로 끝날 때까지 기다린다.
  - "11/05 교훈: 부하 정의는 한 곳, 쓴 값은 .meta 에": 두 스크립트가 각자 stress-ng 를 띄우던 때 버퍼 크기가 달랐고(512M vs 256M), 그 차이가 "표준 도구 132 vs 우리 측정기 301" 비교를 흐렸다(E19-d). 그래서 함수 하나로 묶고 쓴 값을 `.meta` 에 적는다.
- 셰브론 5 "make_table1.py": 결과 파일들을 읽어 표①을 만드는 파이썬 생성기.
  - "cyclictest 히스토그램 → p99/p99.9/max(최악 CPU)": cyclictest 출력의 CPU 별 히스토그램에서 백분위수와 최악값을 계산하고 가장 나쁜 CPU 의 값을 고른다.
  - "jitter JSON → 그대로": `jitter_bench` 는 이미 p50·p99·p99.9·max 를 JSON 으로 내므로 그대로 읽는다.
  - ".meta → 비고에 '온도 a→b °C, 스로틀 0' / '⚠ 스로틀'": `.meta` 의 온도와 플래그를 표의 비고 칸에 문장으로 옮긴다. 플래그가 0 이 아니면 경고 표시를 붙인다.
  - "→ docs/measurements/table1_pi4.md": 결과가 이 파일이다(장표 094 가 그 14줄 중 8줄).
- 아래 글 "전부 Pi 에서 sudo 로 돈다(RT 우선순위). 결과는 scp 로 WSL 에 가져와 커밋 — Pi 에는 GitHub 로그인이 없다. 출처: scripts/, docs/SETUP_RT_MEASURE.md": 측정 스크립트는 실시간 우선순위(SCHED_FIFO)를 쓰므로 root 권한이 필요해 `sudo` 로 돈다. 결과 파일은 장표 108 의 길(② → ① → ③)로 저장소에 들어간다.

## 3. 용어와 단위
- 셰브론(chevron): 화살촉 모양 상자. 순서가 있는 단계를 왼쪽에서 오른쪽으로 보여 줄 때 쓴다.
- jitter_bench: 이 저장소가 만든 측정기(C++). "1 ms 마다 깨어나 50 us 일하기"를 반복하며 깨어남 지연과 일한 시간을 기록해 JSON 으로 낸다.
- cyclictest: rt-tests 패키지의 표준 측정 도구. "1 ms 마다 깨워 달라"고 해 놓고 실제로 얼마나 늦게 깨는지를 수십만 번 잰다.
- SCHED_FIFO / prio: 리눅스의 실시간 스케줄링 정책과 그 우선순위(1~99, 클수록 급함). root 권한이 필요하다.
- stress-ng: 시스템에 부하를 주는 도구. `--cpu` CPU 작업자 수, `--io` I/O 작업자 수, `--vm` 메모리 작업자 수, `--vm-bytes` 그 버퍼 크기, `--timeout` 지속 시간.
- vm / --vm-bytes: 메모리 작업자가 할당하고 쓰고 해제하는 버퍼의 크기(256M = 256 메가바이트). 버퍼가 작을수록 해제(munmap)가 잦아 다른 CPU 로 가는 IPI 가 늘어 지연이 커진다(추정, `lib_stress.sh` 머리말).
- .meta: 결과 파일 옆에 남기는 `key=value` 조건 기록.
- 히스토그램: 지연 값이 몇 us 였던 횟수를 1 us 칸마다 센 표. 여기서 p99·p99.9·max 를 계산한다.
- p99 / p99.9 / max: 100번 중 99번 / 1,000번 중 999번은 이 값 이내 / 가장 나쁜 한 번.
- 밀리도(m°C): 1,000분의 1 도. 51608 = 51.6 °C.
- us(마이크로초): 100만분의 1초. 주기 1,000 us = 1 ms.
- source: 셸에서 다른 스크립트의 함수를 현재 셸로 불러오는 명령.

## 4. 쉬운 예시
- 비유: 과학 실험 노트다. 결과 숫자만 적은 노트와 "몇 도에서, 어떤 시약을 얼마나, 어떤 기구로" 조건까지 적은 노트의 차이다. 조건이 없는 결과는 재현할 수 없고, 두 결과가 다를 때 원인을 찾을 수도 없다. 다섯 스크립트는 "측정하는 사람이 조건 적기를 잊을 수 없게" 만든 노트 양식이다.
- 숫자 예시: 11/05 에 `sudo scripts/jitter_run.sh pi4_rt_stress_isol 60 stress 3` 을 돌리면 `jitter_pi4_rt_stress_isol.json`(p50 23.5 / p99 108.3 / p99.9 146.2 / max 189.3 us)과 `.meta`(kernel=6.8.0-2054-raspi-realtime, stress=stress, stress_vm_bytes=256M, cpu=3, prio=80, work_us=50, 온도 전후, throttled_after=0)가 생긴다. `make_table1.py` 가 이것을 표①의 한 줄 "pi4_rt_stress_isol … 189.3 … 온도 44.8→64.8 °C, 스로틀 0" 으로 바꾼다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 인자·환경 변수·기본값(prio 80, work 50 us, vm 256M) — `scripts/jitter_run.sh` 머리말과 변수 정의.
- 확인: cyclictest 옵션 `-m -S -p 90 -i 1000 -h 1000 -q -D` 와 vm 512M — `scripts/cyclictest_run.sh`.
- 확인: `.meta` 항목 이름 — 두 스크립트의 `{ echo … } > …meta` 블록, `scripts/lib_thermal.sh` 의 `thermal_meta_lines`.
- 확인: 가장 나쁜 CPU 값, 비고 문장 "온도 a→b °C, 스로틀 0" / "⚠ 스로틀" — `scripts/make_table1.py`(`parse_cyclictest`, `thermal_note`).
- 확인: 11/05 교훈(512M vs 256M, 132 vs 301) — `scripts/lib_stress.sh` 머리말, `docs/DECISIONS.md` 2026-11-05, `docs/experiments/E19d.md`.
- 확인: 우선순위 80 과 90 이 같다 — `docs/measurements/table1_pi4.md` 의 `pi4_rt_stress_pin_work0`(prio 80, max 270.0) vs `pi4_rt_stress_pin_work0_p90`(prio 90, max 289.7), `docs/experiments/E19d.md` B.
- 다시 확인하는 법(Pi 창): `sudo scripts/jitter_run.sh <label> 120 stress 3`, `sudo scripts/cyclictest_run.sh <label> 120 stress`. (WSL 창) 결과를 scp 로 가져온 뒤 `python3 scripts/make_table1.py --out docs/measurements/table1_pi4.md`. 스크립트는 전부 `sudo` 가 필요하다(SCHED_FIFO).

## 6. 자주 하는 오해·함정
- "측정기 하나면 충분하다": 우리 측정기와 표준 도구가 다르게 나왔을 때(132 vs 301) 둘이 있어야 "측정기 문제인가, 조건 문제인가"를 가를 수 있었다. 답은 조건(부하 vm 크기, 일하는 시간 50 us vs 0)이었다.
- "표에 숫자가 있으면 믿을 수 있다": 비고의 "스로틀 0" 과 `.meta` 가 있어야 믿을 수 있다. 조건이 없는 옛 결과는 표에서 비고가 `-` 다.
- "stress 라고 쓰면 다 같은 부하다": vm 버퍼 크기가 다르면 다른 실험이다. 그래서 부하 정의를 함수 하나로 묶었다.
- 함정(실제로 겪은 것): 11/04 에 조건 하나마다 명령 3줄(부하 시작 → sleep → 측정기 → wait)을 손으로 쳤다. 라벨과 파일 이름이 어긋나기 쉽고 온도 확인을 빼먹었다. 그래서 스크립트로 묶었다(`jitter_run.sh` 머리말).

## 7. 면접 한 문장
"표①의 한 줄은 사람이 친 명령이 아니라 스크립트 다섯 개가 만든다 — 측정기 둘, 온도·스로틀 함수, 부하 함수, 표 생성기 — 그리고 조건(커널·부하 크기·우선순위·온도 전후·스로틀)을 결과 옆 .meta 에 남겨서, 두 숫자가 다를 때 측정기 탓인지 조건 탓인지를 가를 수 있게 했다."
