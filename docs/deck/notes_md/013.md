# 장표 013 — 단계 1 — 명령이 생긴다 — 누가, 무엇을, 얼마나 자주
*위치: 1부 로봇을 움직이는 길 · 단계 1/10 명령이 생긴다 · ② 무엇·누가·얼마나 자주*

## 1. 이 장표가 왜 있나
들머리(011)에서 단계 1의 기준과 결과를 요약했다. 이 장표는 그 안의 세 가지 결정 — 무엇을(형식), 누가(발행자), 얼마나 자주(주기) — 를 하나씩 풀어 쓰고, 왜 rad 인지, 명령이 "틀릴" 수 있는 경우와 "끊길" 수 있는 경우까지 미리 짚는다. 단계 1에는 코드 장표가 없다. 명령을 만드는 쪽은 이 저장소 밖(상위 계획기)이거나 시험용 한 줄 명령이기 때문이다. 대신 오른쪽 말풍선에 "이 단계의 소스"(메시지 형식·토픽 이름·시험 발행 문서)를 모아 두었다.

## 2. 장표를 하나씩 읽기
왼쪽 글머리표 일곱 줄과 오른쪽 말풍선, 아래 "다음 ▶" 다리 순서로 읽는다.

- **"무엇: 관절 6개의 목표 위치(rad) 배열 하나. ROS 2 표준 메시지 sensor_msgs/msg/JointState 의 position 필드를 쓴다 (name·velocity 는 비워도 된다)"**: 명령의 내용은 숫자 여섯 개(각 관절이 가야 할 각도)다. 새 메시지 형식을 만들지 않고 ROS 2 가 이미 정해 둔 JointState 를 쓴다 — 다른 ROS 2 도구(`ros2 topic pub`, rosbag2, RViz)가 그대로 알아듣기 때문이다. 이름 칸과 속도 칸은 비워도 노드가 position 만 읽는다.
- **"누가: 실제 로봇이면 상위 계획기(궤적 생성기)나 조작기. 이 저장소에서는 시험용으로 명령줄에서 낸다 — 50 Hz 로 같은 값을 반복"**: 발행자는 바뀔 수 있다. 실물에서는 경로를 계산하는 프로그램이, 시험에서는 터미널 한 줄이 낸다. 중요한 것은 아래 단계들이 발행자가 누구든 똑같이 동작한다는 점이다.
  - 들여쓴 줄 **`ros2 topic pub -r 50 /joint_command sensor_msgs/msg/JointState "{position: [0.3, -0.2, 0.1, 0.0, 0.0, 0.5]}"`**: 실제로 치는 명령. `-r 50` 은 1초에 50번 반복, `/joint_command` 는 토픽 이름, 따옴표 안은 메시지 내용(관절 6개의 목표, 단위 rad). 이 값은 뒤 장표 042(로봇이 이렇게 움직인다)의 목표와 같다.
- **"왜 50 Hz 인가: 제어 루프(1 kHz)보다 느려도 된다. 루프는 매 주기 '가장 최신 명령'을 보고, 명령이 없는 주기는 지난 목표를 유지한다 (단계 5)"**: 50 Hz 는 "상위 계획기가 보통 내는 속도" 정도의 시험값이다. 루프가 1 kHz 인데 명령이 50 Hz 여도 되는 이유가 바로 "최신 명령만, 없으면 유지" 규칙(장표 030).
- **"왜 rad 인가: 각도의 SI 단위. 1 rad = 57.3°. 0.05 rad = 2.9° — 변화량 제한의 단위도 rad"**: ROS 2 와 물리 엔진(MuJoCo)이 모두 rad 를 쓴다. 단계 5의 변화량 제한값 0.05 rad/주기도 같은 단위라 환산 없이 비교된다.
- **"명령이 '틀릴' 수 있는 두 가지: 길이가 관절 수와 다름(단계 3 에서 거름), 값이 갑자기 뜀(단계 5 변화량 제한이 막음)"**: 틀린 명령의 두 종류와 각각을 막는 자리. 길이 오류는 노드의 `on_command()`(장표 019)가 세고 버린다. 값이 튀는 것(예: 0.3 → 1.3 rad 로 한 번에)은 제어 단계의 `limit_step()`(장표 032)이 한 주기 0.05 rad 로 자른다.
- **"명령이 '끊길' 수 있다: 50 ms 동안 안 오면 워치독 → 멈춤 (안전 경로 장표)"**: 명령이 아예 안 오는 경우. 50 ms(=1 kHz 루프 50주기) 동안 새 명령이 없으면 워치독이 "지금 자리에 멈춤"을 건다. 자세한 흐름은 안전 경로 장표(057).
- **말풍선 "이 단계의 소스"**: "메시지 형식: sensor_msgs/JointState (ROS 2 표준) / 토픽 이름: /joint_command (rt_control_node.cpp:110) / 시험 발행: docs/video/CHEATSHEET.md, backends/mujoco/README.md / 실물에서 바뀌는 것: 발행자만 바뀐다(계획기). 아래 단계는 그대로". 토픽 이름은 노드 소스 110~111줄의 `create_subscription<…>("joint_command", 10, …)` 에서 정해진다(큐 깊이 10). 시험 발행 명령의 원문은 `docs/experiments/E03.md`·`E20.md`·`docs/VIDEO_SCRIPT.md` 에 있다(장표의 두 파일에는 echo 명령과 흐름 그림만 있다 — 아래 §5 참고).
- **다음 ▶ 다리**: "단계 2 — 명령은 50 Hz 로 만들어졌다. 다른 프로세스의 노드까지 어떻게, 얼마나 믿을 만하게 가나? (ROS 2 / DDS, 표②)". 명령을 내는 프로그램과 받는 노드는 다른 프로세스라서 "전달"이 다음 걱정이다.

## 3. 용어와 단위
- **필드(field)**: 메시지 안의 칸. JointState 의 position 필드 = 위치 숫자들이 들어가는 칸.
- **토픽 이름 `/joint_command`**: 앞의 `/` 는 최상위 이름 공간. 같은 이름으로 발행·구독해야 연결된다.
- **`-r 50`**: `ros2 topic pub` 의 반복 속도(rate) 옵션, 단위 Hz.
- **rad ↔ °**: 1 rad = 180/π ≈ 57.3°. 0.3 rad = 17.2°, −0.2 rad = −11.5°, 0.5 rad = 28.6°.
- **ms(밀리초)**: 1/1,000 초. 50 ms = 0.05 초 = 1 kHz 루프의 50주기.
- **워치독(watchdog)**: "일정 시간 소식이 없으면 안전 조치"를 하는 감시 장치. 여기서는 50 ms.
- **궤적 생성기**: 시작 자세에서 목표 자세까지 시간에 따른 중간 목표들을 계산해 주는 프로그램(상위 계획기의 한 종류).

## 4. 쉬운 예시
- 비유: 내비게이션(상위 계획기)이 운전자(제어 루프)에게 "다음 교차로에서 좌회전" 같은 지시(명령)를 준다. 내비게이션은 몇 초에 한 번만 말해도(50 Hz), 운전자는 매 순간(1 kHz) 핸들을 조정한다. 말이 없으면 마지막 지시를 따른다. "교차로에서 좌회전"이 아니라 "교차로에서 ■■■" 처럼 알아들을 수 없는 지시(길이가 틀린 명령)는 무시하고 횟수만 센다. 내비게이션이 50 ms 넘게 먹통이면 운전자는 일단 멈춘다(워치독).
- 숫자 예시: 목표 `[0.3, −0.2, 0.1, 0, 0, 0.5]` rad 를 도로 바꾸면 `[17.2°, −11.5°, 5.7°, 0°, 0°, 28.6°]`. 로봇이 0 rad 에서 0.5 rad 까지 가려면 변화량 제한 0.05 rad/주기 때문에 최소 10주기 = 10 ms 가 걸린다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 토픽 이름과 큐 깊이 — `rt_control/ros2_adapter/src/rt_control_node.cpp` 110~111줄 `create_subscription<sensor_msgs::msg::JointState>("joint_command", 10, …)`.
- 확인: 관절 6개 — `robots/so101.yaml` `dof: 6`.
- 확인: 1 rad = 57.3° — 180/π.
- 확인: 50 ms 워치독, 0.05 rad 변화량 제한 — 노드 파라미터 기본값 `watchdog_ms 50`, `max_step_rad 0.05` (`rt_control_node.cpp` 파라미터 선언부), `robots/so101.yaml` `safety:` 절.
- 확인: 시험 발행 명령 원문 — `docs/experiments/E03.md` 24줄, `docs/experiments/E20.md`, `docs/VIDEO_SCRIPT.md`. 장표 말풍선이 가리키는 `docs/video/CHEATSHEET.md` 에는 `ros2 topic echo /joint_states --once --field position`(읽기 명령)이, `backends/mujoco/README.md` 에는 `joint_command → ControlStep → MujocoBackend` 흐름 그림이 있다 — 발행 명령 자체는 E03 쪽을 보는 것이 맞다.
- 다시 보는 법: `ros2 topic info /joint_command` 로 구독자(노드)가 붙어 있는지, `ros2 topic hz /joint_command` 로 실제 50 Hz 인지 본다.

## 6. 자주 하는 오해·함정
- "name 칸을 채워야 노드가 관절을 찾는다"는 오해: 이 노드는 순서(배열 위치)로 관절을 맞추고 name 은 읽지 않는다. 길이(6)만 검사한다.
- position 배열 길이를 5개나 7개로 보내면 조용히 버려진다 — 로그 경고는 100번에 한 번만 찍히므로(장표 019) `bad_commands` 카운터를 봐야 안다.
- 명령을 너무 빨리(예: 1 kHz 이상) 보내면 노드의 우편함(64칸)이 찰 수 있다 — `cmd_ring_full` 카운터가 0 이 아니면 그 신호(장표 019·020).

## 7. 면접 한 문장
"명령은 새 형식을 만들지 않고 ROS 2 표준 JointState 의 position 여섯 개를 rad 로 50 Hz 에 보낸다 — 발행자가 계획기로 바뀌어도 아래 아홉 단계는 한 줄도 안 바뀐다."
