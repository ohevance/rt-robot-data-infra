# 장표 115 — 테스트 목록 — '테스트 케이스 등록'은 따로 없다, 전부 저장소의 코드이고 CI 가 push 마다 돌린다
*위치: 6부 믿을 수 있나 · 테스트 목록 37건*

## 1. 이 장표가 왜 있나
6부 표지(111)의 답 상자에 "테스트 37건(C++ 7 · Python 30)과 끝-대-끝 스크립트"라고 적었다. 그 37건이 **무엇**인지, 어느 파일에 있고, 각각 무엇을 확인하고, CI 의 어느 잡에서 도는지를 한 표로 보여 주는 장표다. 제목의 "'테스트 케이스 등록'은 따로 없다"는 회사의 테스트 관리 도구(케이스를 등록하고 결과를 표로 보는 시스템)에 익숙한 사람을 위한 말이다 — 이 저장소에서는 테스트가 전부 **코드 파일**이고, 등록은 `add_test`(C++)와 `def test_`(Python)이며, 실행은 push 때마다 CI 가 한다. 앞 장표(112~114)가 '측정' 묶음이었고 이 장표부터 '테스트' 묶음(115~118)이 시작된다.

## 2. 장표를 하나씩 읽기
표는 머리말 한 줄 + 일곱 행, 열은 넷(묶음 · 파일 · 케이스 · CI 잡). 위에서 아래로 "빠르고 가짜인 것 → 느리고 진짜인 것" 순이고, 맨 아래 연기 테스트만 따로다. 11/05 의 표는 다섯 행이었다 — 11/10~11 에 Python 행이 15건에서 26건으로 늘고 "릴리스 카나리" 행이 생겼고, 11/11 저녁에 C++ 행에 둘(통신 패킷 · 공유 메모리)이 더해지고 "SDK 패킷 · 끝-대-끝" 행이 생겼다. 글자가 늘어 글자 크기가 11 에서 10 으로(11/10~11), 다시 9 로(11/11 저녁) 줄고 케이스 열이 넓어졌다.

## 3. 용어와 단위
- 단위 테스트: 함수·클래스 하나를 떼어 가짜 환경에서 확인. 통합 테스트: 진짜 부품(컨테이너)을 다 띄워 끝까지. 연기(smoke) 테스트: 켜지고 도는지만.
- ctest / add_test: CMake 의 테스트 실행기와 등록 명령. `ctest --output-on-failure` 로 돌리면 "100% tests passed".
- `def test_…`: 파이썬 테스트 함수. 이 저장소는 외부 프레임워크 없이 파일을 직접 실행한다(`python3 fleet/tests/test_fleet_logic.py`).
- 가짜(fake) 브로커·DB: paho-mqtt 와 psycopg 를 흉내 내는 작은 파이썬 모듈. 네트워크·컨테이너 없이 논리를 확인한다.
- SPSC 링 버퍼: 한쪽만 넣고 한쪽만 꺼내는 락 없는 원형 큐(1부 단계 3 의 우편함).
- 워치독: 명령이 일정 시간 안 오면 멈추게 하는 안전장치. 변화량 제한: 한 주기에 목표가 움직일 수 있는 최대량(max_step_rad).
- JUnit 리포트: 테스트 결과를 케이스별 XML 로 내는 표준 형식. CI 화면에 표로 붙일 수 있다.
- 2,000주기: 1 kHz 로 2초. p99 < 900 us: 100번 중 99번은 0.9 ms 안에.

## 4. 쉬운 예시
자동차 정비 비유: 단위 테스트는 부품 하나씩 벤치에서 돌려 보는 것(브레이크 패드만), 통합 테스트는 차를 실제로 조립해 시험 주행, 연기 테스트는 시동이 걸리는지만. 세 층이 다 있어야 "부품은 멀쩡한데 조립하면 안 돈다"(11/05 의 main() 사고)와 "조립은 됐는데 부품 하나가 느리다"를 다 잡는다.

숫자 예시: 37 = C++ 7(6 ctest + 1 MuJoCo) + Python 30(fleet 9 + 3 + 7 + 7 + SDK 4). 통합 1벌, 릴리스 카나리 1벌, ZeroMQ 끝-대-끝 1벌, 연기 2개는 '건' 수에 넣지 않았다. 다 돌리는 데 CI 에서 rt_core 잡 42초, mujoco 49초, fleet_integration 2분 32초(11/11 밤 run 43020127641, ZeroMQ 단계 포함 — 11/04 에는 1분 13초 · 25초 · 1분 52초였다. 러너 사정과 늘어난 단계에 따라 달라진다).

## 6. 자주 하는 오해·함정
- "케이스 등록 시스템이 없으면 관리가 안 된다" — 코드가 곧 목록이고 git 이력이 곧 변경 기록이다. 다만 케이스별 결과표(JUnit)는 없고, 붙이려면 30분이라고 적어 두었다.
- "C++ 7" 을 WSL 에서 ctest 로 돌리면 6 만 보인다 — MuJoCo 테스트는 빌드 옵션이 켜져야 등록된다.
- 단위 테스트가 다 통과해도 진입점이 깨질 수 있다 — 11/05 `request_stop` 삭제 사고. 그래서 main() 스모크가 단위 테스트 안에 들어갔다. 11/10 에는 같은 모양의 사고가 한 번 더 났다 — 단위 테스트가 쓰는 인자(절대 경로)와 통합 스크립트가 쓰는 인자(상대 경로)가 달랐다.
- "건"과 "확인"을 섞어 세지 않는다. 37건은 함수의 수이고, 함수 안의 `check(...)` 는 fleet 의 Python 네 파일에만 162개다(62 + 15 + 30 + 55).
- 끝-대-끝 단계도 건수에 넣지 않는다 — ZeroMQ 노드 시험은 12단계여도 0건이다. 그래서 11/11 밤에 단계를 8 → 12로 늘렸어도 "테스트 37건"은 그대로다.
- 연기 테스트의 jitter 값은 지연 수치가 아니다. `--no-rt` 2초, '돈다'의 증거.
- 가짜 위의 통과는 "논리는 맞다"이지 "진짜 위에서도 된다"가 아니다 — 그래서 통합(진짜 컨테이너) 잡이 따로 있다(결정 기록 11/03 "CI 는 2단계: 가짜로 빠르게, 진짜로 한 번").

## 7. 면접 한 문장
"테스트는 세 층입니다 — 가짜 위에서 도는 단위 37건(C++ 7 · Python 30), 진짜 컨테이너와 진짜 ZeroMQ 노드를 띄우는 끝-대-끝, '돈다'만 보는 연기 둘 — 전부 저장소의 코드이고 push 마다 CI 가 돌립니다. 태그를 올리면 가상 50대 카나리가 한 번 더 돕니다. 케이스별 결과표는 아직 없다는 것도 적어 두었습니다."
