# 장표 063 — ① 장치 에이전트 — 1 Hz tick 과 '끊기면 모았다가, 붙으면 보낸다'
*위치: 2부 데이터의 길 · ① 장치 에이전트 · ② 코드 — tick · send_or_buffer*

## 1. 이 장표가 왜 있나
들머리(062)의 기준 "끊김 동안 장치가 보존하나"를 코드로 확인하는 첫 장표다. 장치 에이전트의 한 주기는 함수 두 개로 끝난다 — 1초마다 JSON 을 만드는 `tick` 과, 붙어 있으면 보내고 끊겼으면 모으는 `send_or_buffer`. 보는 사람이 확인할 것은 두 가지다: JSON 안에 유실을 셀 번호(seq)와 지연을 잴 시각(ts_ns)이 들어 있는가, 그리고 끊겼을 때 메시지가 버려지지 않고 버퍼에 들어가는가. 재접속 뒤 버퍼를 비우는 쪽은 다음 장표(064).

## 2. 장표를 하나씩 읽기
상자 위의 파일 위치: `fleet/agent/device_agent.py:92-117`. 코드는 저장소 파일 그대로다.

- `def tick(self):` (92): 주기 스레드 `run_loop`(83~90줄)가 `period_s`(1 Hz 면 1.0초)마다 부른다. run_loop 는 `next_tick += period_s` 로 절대 시각을 누적한다 — 1부 단계 4 의 RT 루프와 같은 원리, 정밀도만 낮다(`time.sleep`).
- `metrics = self.metrics_source()` (93): 센서값을 가져오는 함수를 호출한다. 가상 장치는 `VirtualMetrics`(난수 걸음), RT 노드 다리는 rt_status 에서 뽑은 값. 이 한 줄이 "실물과 가상의 차이는 metrics_source 뿐"의 실체다.
- `payload = {` (94) ~ `}` (103): 보낼 JSON 의 뼈대. 항목마다:
  - `"device_id": self.device_id` (95): 장치 이름(예: vdev-001). 토픽에도 들어 있지만 본문에도 넣어 CSV 한 줄만 봐도 알게.
  - `"seq": self.seq` (96): 일련번호. 0 부터 1씩. 서버가 번호의 빈칸으로 유실을 센다 — 2부 전체에서 가장 중요한 한 줄.
  - `"ts_ns": time.time_ns()` (97): 벽시계(UTC) 나노초. 수집기가 (도착 시각 − 이 값)으로 전달 지연을 계산한다. 같은 PC 의 시계라 ms 단위 비교가 된다(장치가 따로 있으면 NTP 동기가 전제).
  - `"fw_version": self.fw_version` (98): 펌웨어 버전. OTA 뒤 바뀌었는지를 서버가 이것으로 본다.
  - `"state": self.state` (99): ok / updating / fault. 헬스 게이트가 보는 값.
  - `"buffered"`, `"flushed"`, `"reconnects"` (100~102): 끊김 이력 카운터. 장치가 자기 끊김을 숫자로 보고한다 — E05 의 654 = 654 가 여기서 나온다.
- `payload.update(metrics)` (104): 센서값(cpu_pct, temp_c, mem_pct, rssi, loop_hz, wake_p99_us)을 합친다. 가상 장치는 loop_hz·wake_p99_us 가 None, RT 노드 다리는 실제 값.
- `self.seq += 1` (105): 다음 번호. 보내기 전에 올리므로 버퍼에 들어간 메시지도 번호가 이어진다 — 재전송돼도 seq 가 그대로라 서버는 "늦게 왔지만 빠지지 않았다"를 안다.
- `self.send_or_buffer(self.topic_telemetry, json.dumps(payload))` (106): 문자열로 바꿔 아래 함수에.
- `def send_or_buffer(self, topic, payload):` (108): 보낼지 모을지 결정.
- `if self.client.is_connected():` (109) `self.client.publish(topic, payload, qos=self.telemetry_qos)` (110) `return` (111): 붙어 있으면 바로 발행. QoS 는 옵션(`--telemetry-qos`, 기본 0). 보내고 끝.
- `with self.lock:` (112): 버퍼는 주기 스레드가 넣고 paho 네트워크 스레드가 비우므로(064 flush_buffer) 잠금이 필요하다.
- `if len(self.buffer) >= MAX_BUFFER:` (113) `self.buffer.popleft()  # 가장 오래된 것을 버린다` (114): 3,600개가 찼으면 가장 오래된 것을 버린다 — 메모리를 지키고, 최근 데이터를 우선한다.
- `self.buffer.append((topic, payload))` (115): (토픽, 내용) 쌍으로 뒤에 붙인다. deque 라 양쪽 끝 넣고 빼기가 O(1).
- `self.buffered_total += 1` (116): 누계. 이 값이 다음 tick 의 `"buffered"` 로 서버에 간다.

오른쪽 요점 네 줄은 위 내용의 요약이다. "3,600개 = 1 Hz 로 1시간"은 24줄의 `MAX_BUFFER = 3600` 과 그 주석.

## 3. 용어와 단위
- tick: 한 주기. period_s 가 1.0 이면 1 Hz.
- seq(일련번호): 메시지마다 1씩 올리는 번호. 서버는 장치별로 번호의 빈칸을 세어 유실로 본다(진단 C, diag.py).
- ts_ns: 측정 시각, 나노초(10억분의 1초) 단위 정수. `time.time_ns()` 는 벽시계(UTC 기준 epoch).
- 전달 지연: 도착 시각 − ts_ns. ms 단위로 본다(E05 p50 0.9 / p95 1.8 ms).
- QoS 0 / 1: 보내고 잊음 / 브로커 확인까지. `telemetry_qos` 는 붙어 있을 때 publish 에만 쓰이고, 재전송은 항상 1.
- deque: 양쪽 끝에서 넣고 빼기가 빠른 파이썬 자료형. `popleft` 가 가장 오래된 것.
- 잠금(Lock): 두 스레드가 같은 자료를 동시에 고치지 않게 하는 장치. `with self.lock:` 블록 안은 한 스레드만.
- JSON: 사람이 읽을 수 있는 키·값 텍스트 형식. `json.dumps` 가 dict 를 문자열로.

## 4. 쉬운 예시
비유 — 번호표가 붙은 일지: 지점 직원이 1분마다 매출 일지를 한 줄 쓴다. 줄마다 번호(seq)와 쓴 시각(ts_ns)을 적는다. 통신이 되면 바로 본사에 보내고(publish), 안 되면 서랍(버퍼)에 넣는다. 서랍은 60장(1시간)까지 — 가득 차면 가장 오래된 한 장을 버리고 새 장을 넣는다. 서랍에 넣은 장수(buffered)도 다음 일지에 적는다. 본사는 번호가 1, 2, 3, 7 로 오면 4~6 이 빠진 것을 알고, 늦게 온 4~6 의 시각을 보고 "지연이었구나"를 안다.

숫자 예시 — 끊김 13초 동안 1 Hz 로 13개가 버퍼에 들어가고 buffered_total 이 13 늘어난다. 50대면 50 × 13 ≈ 654(E05). 1시간 이상 끊기면 3,601번째부터는 가장 오래된 것이 버려지므로 재접속 뒤 서버의 seq 에는 빈칸이 생긴다 — 그때 유실 수 = 빈칸 수. 전달 지연: 12:00:00.000 에 측정(ts_ns)한 메시지가 12:00:00.002 에 도착하면 2 ms, 끊김 뒤 12:00:12.5 에 도착하면 12.5초(E05 max).

## 6. 자주 하는 오해·함정
- "seq 를 보낸 뒤에 올리는 것 아닌가?" — 보내기 전(105줄)에 올린다. 어느 쪽이든 1씩 이어지면 되지만, 버퍼에 들어간 메시지도 같은 규칙이라 재전송 뒤 번호가 그대로 이어진다.
- "ts_ns 는 장치 시계인데 서버와 다르면?" — 실험은 같은 PC 라 문제없다. 실물 장치가 따로 있으면 NTP 동기가 전제이고, 시계가 어긋나면 전달 지연이 음수나 수 초로 나온다 — 그래서 지연 패널은 '참고', 유실은 seq 로 본다.
- "버퍼가 찼을 때 새 것을 버리면 안 되나?" — 최근 값이 더 중요하다(관제는 현재 상태를 본다). 오래된 것을 버리는 것이 설계 선택이고, 버린 수는 seq 빈칸으로 서버가 안다.
- "QoS 1 로 보내면 is_connected 가 false 인 동안도 paho 가 큐에 넣어 주지 않나?" — paho 도 내부 큐가 있지만 상한·동작을 우리가 통제하기 어렵다. 우리 버퍼는 수와 상한을 우리가 세고 보고한다.
- 함정: `tick` 은 주기 스레드, `send_or_buffer` 의 발행은 paho 네트워크 스레드와 상호작용한다. 버퍼를 잠금 없이 만지면 `flush_buffer` 와 겹칠 때 메시지가 사라지거나 중복된다 — 112줄의 `with self.lock` 이 그 이유.

## 7. 면접 한 문장
"장치의 한 주기는 두 함수입니다 — tick 이 일련번호와 측정 시각을 넣은 JSON 을 만들고, send_or_buffer 가 붙어 있으면 보내고 끊겼으면 3,600개 상한의 버퍼에 넣습니다 — 번호 덕에 서버는 '늦게 왔다'와 '빠졌다'를 구분하고, 버퍼 누계를 텔레메트리에 실어 장치가 자기 끊김을 숫자로 보고합니다."
