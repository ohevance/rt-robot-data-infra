# 장표 058 — 실물 로봇(SO-101, Feetech 서보 6개)으로 가면 — 바뀌는 것과 안 바뀌는 것
*위치: 1부 로봇을 움직이는 길 · 마무리 — 실물 로봇으로 가면*

## 1. 이 장표가 왜 있나
본편 10단계와 안전 경로까지, 로봇 안의 길을 **가상 로봇(MuJoCo 물리 시뮬레이션)** 으로 끝까지 따라갔다. 면접관이든 독자든 당연히 이렇게 묻는다. "그래서 진짜 로봇을 붙이면 이 중 얼마나 다시 써야 하나?" 이 장표는 그 질문에 두 기둥(바뀌는 것 / 그대로인 것)으로 답한다. 결론은 "바뀌는 것은 백엔드 한 벌과 숫자 몇 개, 그대로인 것은 나머지 전부"이고, 그것이 가능했던 이유가 제어 코드를 ROS 2 와 로봇에서 떼어 둔 설계(DECISIONS 11/03)다. 실물 작업은 2주 범위 밖으로 뺐으므로(DECISIONS '6주 → 2주') 이 장표는 **계획**이지 실측이 아니다 — 그 점을 분명히 하고 읽는다. 이 장표로 1부가 끝나고 2부(데이터의 길)로 넘어간다.

## 2. 장표를 하나씩 읽기
### 왼쪽 기둥 — "바뀌는 것 (새로 쓸 코드)"
- 1줄 "FeetechSerialBackend: Backend 세 함수 구현 — init(시리얼 포트 열기·서보 ID 확인), write_command(목표 위치 6개를 동기 쓰기 패킷으로), read_state(현재 위치·속도 읽기)". 단계 6(장표 039)에서 본 `Backend` 인터페이스는 함수가 셋뿐이다(backend.hpp 23~32줄). 실물용 구현체는 (1) `init` 에서 시리얼 포트(`/dev/ttyACM0`, 1,000,000 bps — 프로필 `serial` 절)를 열고 서보 ID 1~6 이 응답하는지 확인하고, (2) `write_command` 에서 목표 위치 6개를 서보 프로토콜의 '동기 쓰기(sync write)' 패킷 하나로 보내며, (3) `read_state` 에서 현재 위치·속도를 읽는다. backend.hpp 10줄 주석에 "FeetechSerialBackend : SO-101 실물 서보 (2주 계획 밖)" 으로 자리가 적혀 있다.
- 2줄 "loop_hz: 1000 → 200 (1 Mbps 시리얼 버스에서 6개 서보 왕복 한계, 프로필 loop_hz.real) — RtLoop 은 period_ns 만 바뀐다". 시뮬레이션은 1 kHz(1 ms)지만, 실물은 시리얼 버스로 서보 6개와 매 주기 왕복해야 하므로 200 Hz(5 ms)로 낮춘다. `robots/so101.yaml` 의 `loop_hz: {sim: 1000, real: 200}` — 주석에 "Feetech STS3215 서보 6개, 시리얼 1 Mbps 버스 한계 (실측 후 조정)". RtLoop 코드는 주기 값(period_ns)만 바뀌고 로직은 같다.
- 3줄 "안전: FAULT 진입 때 토크 오프(Backend::safe_stop) — 지금은 '현재 위치 유지'까지". 장표 057 의 안전 경로에서 '멈춤'은 목표를 현재 위치로 두는 것이다. 실물 서보는 그 상태로도 전류가 흐르니, FAULT 때 모터 힘을 끄는 함수(`safe_stop`)를 Backend 에 추가해야 한다(DECISIONS 11/03 D1 이유 줄: "실물에서는 여기서 토크 오프까지 간다(Backend 에 safe_stop 추가 예정)").
- 4줄 "관절 한계(limits_rad)를 모델에서 읽어 변화량 제한 앞에 클램프". 프로필의 `limits_rad: {}` 는 아직 빈 자리다("관절 한계(rad)는 모델 파일에서 읽어 채운다 — 2주차. 아래는 자리만"). 실물에서는 관절이 물리적으로 갈 수 있는 범위를 넘는 목표를 잘라 내야(클램프) 한다 — 변화량 제한(한 주기 0.05 rad)보다 앞단에서.
- 5줄 "중력 보상(토크 피드포워드) — E16 이 보여 준 1.1° 를 없애려면". 단계 7(장표 042·043)에서 어깨가 목표보다 0.019 rad(1.1°) 처지는 것을 보았다. 위치 명령만 주는 지금 구조에서는 남는 정상 상태 오차이고, 없애려면 중력이 만드는 토크만큼 미리 더해 주는 제어(피드포워드)가 필요하다. 보류 항목.

### 오른쪽 기둥 — "그대로인 것"
- 1줄 "단계 1~5·8~10 전부: 명령 토픽, 우편함, RT 루프(준비 5단계·절대 시각), 제어 단계(최신 명령·워치독·변화량 제한·상태 머신), 상태 발행, 기록, 관제 다리". 10단계 중 백엔드(6)와 '로봇이 움직인다'(7)를 뺀 나머지는 코드 한 줄도 바꾸지 않는다. 제어 단계는 `Backend` 세 함수만 부르기 때문이다. 11/04 에 SimLag → MuJoCo 로 바꿀 때 이미 한 번 증명됐다(장표 037 들머리 결과: "제어 코드 무변경").
- 2줄 "측정 방법: 같은 jitter_bench·cyclictest 를 로봇 안 컴퓨터(Pi)에서 — 표①이 이미 그 보드의 숫자". 실물 로봇의 제어 컴퓨터로 Raspberry Pi 4 같은 보드를 쓴다면, 표①(장표 094)의 Pi 4 PREEMPT_RT 숫자가 그대로 그 보드의 기대값이다. 측정 스크립트도 그대로.
- 3줄 "데이터의 길(2부): 서버는 로봇이 가상인지 실물인지 모른다". 단계 10 의 다리가 rt_status 만 보므로 서버 쪽은 변화가 없다.
- 4줄 "테스트: rt_core 단위 테스트 4개는 백엔드와 무관하게 그대로". `test_spsc_ring.cpp`, `test_control_step.cpp`, `test_state_machine.cpp`, 그리고 jitter 연기 테스트는 백엔드 구현체를 모른다(제어 단계 테스트는 1차 지연 모델을 쓴다). 실물 백엔드를 추가해도 깨지지 않는다.

### 아래 각주
"이것이 '제어 코드를 ROS 2 와 로봇에서 떼어 둔' 이유다 (DECISIONS 11/03). 실물 작업은 2주 범위 밖으로 뺐고(DECISIONS '6주 → 2주'), 자리(robots/so101.yaml serial 절, backend.hpp 주석)만 남겨 두었다". DECISIONS 2026-11-03 "6주 계획을 2주로 줄이며 뺀 것"에 "실물 팔(SO-101)" 이 첫 번째로 적혀 있고, 복귀 순서(지원 후 면접 전)의 첫 번째도 "팔"이다.

### '다음 ▶' 다리
"2부 데이터의 길 — 로봇 안은 끝. 다리를 건너온 숫자가 서버에서 유실 없이 저장·표시되고, 장애와 업데이트를 견디는지 따라간다".

## 3. 용어와 단위
- **SO-101**: The Robot Studio 의 저가 6축 로봇팔(LeRobot 공식 지원). 5축 + 그리퍼. 시뮬레이션 모델은 Menagerie 의 SO-ARM100(같은 구성).
- **Feetech STS3215 서보**: SO-101 에 쓰이는 직렬 버스 서보 모터. 한 버스에 여러 개를 ID 로 구분해 연결한다.
- **시리얼 버스 1 Mbps**: 1초에 100만 비트를 보내는 직렬 통신. 서보 6개와 매 주기 명령·응답을 주고받아야 하므로 주기 상한이 생긴다.
- **동기 쓰기(sync write)**: 서보 프로토콜에서 여러 ID 의 목표를 패킷 하나로 보내는 명령. 6개를 따로 보내는 것보다 빠르다.
- **loop_hz 200 Hz**: 1초에 200번 = 5 ms 주기. 1 kHz 는 1 ms.
- **토크 오프**: 모터의 힘(토크)을 끄는 것. 안전 정지.
- **클램프(clamp)**: 값을 허용 범위 안으로 자르는 것. 예: 범위 [−1.5, 1.5] rad 에 2.0 이 오면 1.5 로.
- **중력 보상 / 피드포워드**: 중력이 관절에 주는 힘을 미리 계산해 명령에 더하는 것. 측정값을 보고 고치는 '피드백'과 대비되는 말.
- **rad**: 각도 단위. 1 rad = 57.3°. 0.019 rad ≈ 1.1°.
- **단위 테스트(ctest)**: 함수 몇 개를 자동으로 검사하는 작은 프로그램. CMake 의 테스트 실행기가 ctest.

## 4. 쉬운 예시
- 비유: 자동차의 운전 보조 소프트웨어를 휘발유차에서 전기차로 옮긴다. 바뀌는 것은 '엔진에 명령을 보내고 상태를 읽는 드라이버'(백엔드)와 몇 가지 한계값(최고 회전수 등). 핸들·브레이크 판단 논리(제어 단계), 계기판(상태 발행), 블랙박스(기록), 관제 보고(다리)는 그대로다. 설계할 때부터 '엔진 드라이버'를 세 함수 뒤에 숨겨 두었기 때문이다.
- 숫자 예시: 1 Mbps 버스에서 서보 1개와 한 번 주고받는 데 대략 수백 us 가 든다고 하면(추정), 6개 왕복은 수 ms — 1 ms 주기 안에 못 끝난다. 그래서 5 ms(200 Hz)로 잡았고, 프로필 주석대로 "실측 후 조정"한다. 200 Hz 라도 워치독 50 ms 는 10주기, 변화량 제한 0.05 rad/주기는 초당 10 rad 까지 — 숫자의 뜻이 달라지므로 프로필에서 함께 손봐야 한다.

- 확인: Backend 세 함수와 "FeetechSerialBackend : SO-101 실물 서보 (2주 계획 밖)" — `rt_control/rt_core/include/rt_core/backend.hpp` 8~10줄, 23~32줄.
- 확인: safe_stop 계획 — `docs/DECISIONS.md` 2026-11-03 (D1) '워치독은 멈춤 = 현재 위치 유지' 이유 줄.
- 확인: 2주로 줄이며 뺀 것(실물 팔 첫 줄)과 복귀 순서 — `docs/DECISIONS.md` "2026-11-03 — 6주 계획을 2주로 줄이며 뺀 것".
- 확인: 1.1° 처짐 — `docs/experiments/E16.md`, `docs/measurements/record_summary_wsl_20261105.md`(shoulder_lift 0.0191 rad).
- 확인: 단위 테스트 파일 4개 — `ls rt_control/rt_core/test/` (test_spsc_ring, test_control_step, test_state_machine, test_mujoco_backend; 이 중 mujoco 는 백엔드 테스트라 '백엔드와 무관한 4개'는 앞의 셋 + jitter 연기 테스트를 뜻한다).
- 추정: 서보 왕복 시간과 200 Hz 의 적정성은 실측하지 않았다(프로필 주석도 "실측 후 조정").

## 6. 자주 하는 오해·함정
- "이 장표의 내용을 다 했나?" — 아니다. 왼쪽 기둥은 전부 **할 일**이다. 저장소에는 자리(프로필 serial 절, backend.hpp 주석)만 있다. 면접에서도 "다음 단계"로 말해야지 "했다"고 말하면 안 된다.
- "200 Hz 면 실시간성이 떨어지는 것 아닌가?" — 주기가 길어질 뿐, '정해진 시간 안에 항상'이라는 요구는 같다. 오히려 5 ms 예산에 Pi 의 깨어남 지연 189 us(표①)는 4% 라 여유가 커진다.
- 서보가 위치 명령을 받으면 서보 안의 제어기가 알아서 간다. 그래도 변화량 제한·워치독은 우리 쪽에 둔다 — 서보를 믿고 안전장치를 빼면 안 된다.
- 단위 테스트가 그대로라는 말은 "실물 백엔드에 테스트가 필요 없다"는 뜻이 아니다. 실물 백엔드에는 시리얼 포트를 흉내 내는 가짜 포트 테스트가 새로 필요하다(추정: 아직 없음).

## 7. 면접 한 문장
"실물 SO-101 로 가면 새로 쓰는 것은 Backend 세 함수의 시리얼 구현과 주기 200 Hz·토크 오프·관절 한계 정도이고, 명령·우편함·RT 루프·안전 검사·상태 발행·기록·관제 다리는 그대로다 — 백엔드를 SimLag 에서 MuJoCo 로 바꿀 때 제어 코드가 한 줄도 안 바뀐 것이 그 증거다."
