# 장표 105 — 어디서 — 전체 환경 지도
*위치: 5. 어디서 — 전체 환경 지도*

## 1. 이 장표가 왜 있나
4부에서 숫자 여덟 개를 큼직하게 보여 줬다. 숫자를 보면 바로 나오는 질문이 "그거 어디서 잰 건데?"다 — 같은 "189 us" 라도 노트북 가상 머신에서 잰 것과 진짜 RT 커널이 깔린 보드에서 잰 것은 다른 급의 숫자다. 이 장표는 5부(환경)의 표지로, 코드와 숫자가 **컴퓨터 네 곳** 중 어디서 만들어졌고, 어떤 길로 오가며, 각 곳의 결과를 어떻게 읽나를 다룬다고 예고한다. 부제의 마지막 문장 "이 장이 끝나면 '어느 숫자를 어디까지 믿나'의 규칙이 선다"가 5부의 목표다. 저장소 문서 `docs/ENVIRONMENT.md` 를 장표 다섯 장(106~110)으로 옮긴 것이다.

## 2. 장표를 하나씩 읽기
- 왼쪽 위 큰 번호 "05" 와 제목 "어디서 — 전체 환경 지도": 5부. '어디서'가 질문이고 '지도'가 답의 형식이다.
- 부제 "컴퓨터 네 곳에 무엇이 있고, 코드와 숫자가 어느 길로 오가며, 각 곳의 결과를 어떻게 읽나. 이 장이 끝나면 '어느 숫자를 어디까지 믿나'의 규칙이 선다": 세 가지(무엇이 어디에, 어느 길로, 어떻게 읽나) + 목표 하나.
- 흐름 상자 "들어온 것": "증명한 숫자 셋 — 표① 1 ms 루프 지연 · 표② DDS 전달 · 표③ 관제 유실·복구·OTA (4부)". 4부의 숫자가 입력.
- 흐름 상자 "질문": "그 숫자는 어디서, 어떤 조건에서 만들었고 어디까지 믿나?"
- 흐름 상자 "답": "네 곳: ① 개발 PC WSL2(전부 돈다, 지연 수치는 참고값) ② Raspberry Pi 4(진짜 RT 커널 — 표①은 여기서만) ③ GitHub CI(매 push 재증명, '돌아간다'의 증거) ④ 작업본(초안). 각 곳의 '정상 신호'를 정해 두고 그 신호가 맞을 때의 숫자만 표에 올린다". 네 곳의 역할이 한 줄씩이다. ① 은 ROS 2·Docker·MuJoCo 가 다 있어 모든 코드가 실제로 도는 유일한 곳이지만 가상 커널이라 지연 수치는 참고값. ② 는 진짜 하드웨어 + 진짜 RT 커널이라 표①을 여기서만 잰다(ROS 2·Docker 는 안 깐다). ③ 은 push 마다 새 가상 컴퓨터에서 다시 돌려 "내 PC 에서만 되는" 문제를 걸러 주지만 RT 권한이 없어 지연 수치는 못 잰다. ④ 는 코드·문서 초안을 쓰고 가짜(fake) 위에서 단위 논리까지 확인하는 작성 보조 작업본으로, 진짜 첫 실행은 항상 ①. 마지막 문장 "정상 신호 … 그 신호가 맞을 때의 숫자만"이 5부의 규칙이다 — 예: Pi 의 스로틀 플래그가 0 이 아니면 그 측정은 버린다.
- 차례 첫 줄 "한 장 그림 — 네 곳과 그 사이의 길": 장표 106(그림).
- 차례 둘째 줄 "왜 한 곳으로는 안 되나 · 코드와 숫자가 오가는 길(트리거·명령·확인)": 장표 107(네 곳 각각이 '못 하는 것'이 다음 곳을 만든다) 과 108(언제 무엇이 움직이나 — push 가 CI 를 깨우고, scp 가 Pi 의 결과를 WSL 로 가져오고, bundle 이 작업본의 패치를 넘긴다).
- 차례 셋째 줄 "① 개발 PC 의 '정상' 신호 · ② Pi 4 측정이 유효하려면(확인 5가지)": 장표 109(수집기 1초 통계 `msgs/s=50 online=50 backlog=0 db_err=0`, 노드 `timing_drops: 0`·`state: RUNNING` 같은 신호) 와 110(RT 커널·격리·클럭 고정·열/스로틀·결과 끝줄의 throttled 0 — 하나라도 아니면 버린다).
- 차례 넷째 줄 "→ 다음: 환경을 알았다. 이 숫자들을 누가, 무엇으로, 언제 다시 재나? (6부)": 어디서(5부) 다음은 어떻게 믿나(6부: 측정 스크립트·테스트·CI).

## 3. 용어와 단위
- WSL2: 윈도우 안에서 리눅스를 돌리는 가상 머신. 커널이 가상이라 실시간 지연의 최악값이 1 ms 턱밑(921~2,026 us)까지 튄다 → 참고값.
- Raspberry Pi 4(B): 4코어 ARM 보드. Ubuntu 24.04 에 PREEMPT_RT 커널(`…-raspi-realtime`)을 올려 표①을 잰다. 4코어라 CPU 하나를 격리하는 실험이 된다.
- GitHub Actions(CI): push 마다 GitHub 의 새 가상 컴퓨터(러너)가 저장소를 받아 빌드·테스트·통합 실험을 돈다. 결과는 초록/빨강.
- 작업본(④): 네트워크가 막힌 작성 보조 환경. gcc·cmake·python 과 저장소는 있지만 ROS 2·Docker·MuJoCo 가 없어 가짜(fake_mqtt·fake_psycopg·MuJoCo 스텁) 위에서 논리만 확인한다. 패치는 bundle 로 넘긴다.
- 참고값: 코드가 돌아간다는 것과 상대 비교(A 가 B 보다 낫다)의 증거로만 쓰는 숫자. 절대값은 믿지 않는다.
- 정상 신호: 그 곳이 제대로 돌고 있을 때 보이는 표시(프롬프트의 `(.venv)`, `docker ps` 의 Up, 수집기 통계 줄, Pi 의 throttled 0 등).

## 4. 쉬운 예시
`docs/ENVIRONMENT.md` 의 비유 그대로: ① 작업장(WSL2), ② 계측실(진동 없는 방 = Pi 4), ③ 도면 보관소 겸 검사원(GitHub + CI), ④ 설계 사무실(작업본). 설계 사무실에서 그린 도면(bundle)은 작업장에서 먼저 조립해 보고, 보관소에 올리면 검사원이 매번 다시 조립해 본다(CI). 계측실은 한 가지 측정(지연)만 하고 결과지를 작업장으로 보낸다(scp). 소음 많은 작업장에서 정밀 측정을 하지 않는 것처럼, WSL2 에서 지연 절대값을 믿지 않는다.

숫자 예시: 같은 "부하 중 max" 가 WSL2 에서는 921~2,026 us(1 ms 를 넘김), Pi 4 RT 커널 + 격리에서는 189 us. 환경을 안 적으면 두 숫자 중 어느 것을 말하는지 알 수 없다.

- 확인: 네 곳과 각각의 역할·못 하는 것 — `docs/ENVIRONMENT.md` §1(표), §0 한 장 그림.
- 확인: WSL2 max 921~2,026 us — ENVIRONMENT.md §1 ① 의 "못 하는 것" 칸; 921 은 `docs/measurements/table1.md` wsl_generic.
- 확인: Pi 유효 조건 5가지 — ENVIRONMENT.md §4(RT 커널 `/sys/kernel/realtime` = 1, 격리 `isolated` = 3, governor performance, 시작 온도 50 °C 아래·플래그 0, 결과 끝줄 throttled 0).
- 확인: 개발 PC 정상 신호 — ENVIRONMENT.md §3(터미널·컨테이너 3개·수집기·가상 장치·ROS 2 노드·기록).

## 6. 자주 하는 오해·함정
- "WSL 에서 돌았으니 실시간 성능도 그 값"이 아니다. WSL 숫자는 '돌아간다 + 상대 비교'까지다. 표①의 진짜 값은 Pi 4 만.
- "CI 가 초록이면 빠르다"가 아니다. CI 는 RT 권한이 없어 "돌아간다"의 증거이고 "얼마나 빠르다"의 증거가 아니다. 그래서 CI 의 jitter 연기 테스트는 `--no-rt` 2초다.
- "Pi 에서 잰 값은 전부 믿는다"도 아니다. 유효 조건 5가지(특히 스로틀 0)가 맞을 때만 표에 올린다.
- ④ 작업본에서 가짜 위로 통과한 테스트는 "논리는 맞다"이지 "진짜 위에서도 된다"가 아니다 — 그래서 11/04 venv 소실, 11/05 record.sh SIGTTIN 같은 것은 ① 에서 처음 깨졌다.
- Pi 에는 GitHub 로그인이 없다. 측정 결과는 scp 로 WSL 에 가져와 커밋한다(결정 기록 11/04).

## 7. 면접 한 문장
"숫자마다 어디서 쟀는지를 적었습니다 — 모든 코드는 WSL2 에서 돌지만 지연 절대값은 참고값이고, 표①은 Pi 4 의 진짜 RT 커널에서 유효 조건 5가지가 맞을 때만, CI 는 push 마다 '돌아간다'를 다시 증명하는 곳입니다."
