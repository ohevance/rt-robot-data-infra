# 장표 128 — 사고와 해결 (1/2) — 깨진 것, 원인, 고친 것
*위치: 7부 왜·사고·방식 · 사고 1/2*

## 1. 이 장표가 왜 있나

앞 세 장표(125~127)는 "왜 이렇게 만들었나"였다. 결정대로 만들었다고 처음부터 다 돌지는 않았다 — 2주 동안 깨진 것이 11건이다. 이 장표와 다음 장표(129)는 그 11건을 "무엇이 깨졌나 / 원인 / 해결 / 기록 날짜" 네 칸으로 모은다. 사고를 숨기지 않고 표로 내놓는 이유는 둘이다. 첫째, 면접에서 "뭐가 안 됐고 어떻게 풀었나"는 거의 반드시 나오는 질문이고, 둘째, 각 사고가 저장소의 규칙(단일 인스턴스 잠금, TCP 로 준비 확인, [Pi 창]/[WSL 창] 표기)이 **왜 생겼는지**의 근거다. 이 장표의 6건은 주로 관제(2부)와 CI·ROS 2 쪽이고, 다음 장표의 5건은 노드·Pi·CI 2차·기록 쪽이다.

## 2. 장표를 하나씩 읽기

네 칸: 무엇(증상) / 원인 / 해결 / 기록(LOG 의 날짜). 행마다 읽는다.

- 1행 "재시작된 수집기가 바로 죽음 / /proc/<pid>/exe 는 venv 를 잃은 경로 / /proc/<pid>/environ 의 VIRTUAL_ENV·PATH 로 같은 환경 재시작 / 11/04": 장애 주입(`fleet/chaos/inject.py`)이 수집기를 SIGTERM 으로 죽인 뒤 "같은 명령"으로 다시 띄우는데, 파이썬 실행 파일을 `/proc/<pid>/exe` 로 골랐다. 이 링크는 심볼릭 링크를 끝까지 푼 `/usr/bin/python3.12` 라서 가상환경(venv) 정보가 사라지고, 재시작된 수집기는 `import paho` 에 실패해 즉사했다. 파이썬은 "실행 파일 옆의 pyvenv.cfg" 로 venv 를 알아보므로 `.venv/bin/python3` 경로 그대로 실행해야 한다. 해결은 죽기 전 프로세스의 환경 변수(`/proc/<pid>/environ`)에서 `VIRTUAL_ENV`·`PATH` 를 읽어 같은 환경으로 재시작하는 `pick_python`, 그리고 1.5초 안에 죽으면 로그 끝을 보여 주고 측정을 중단(150초 헛기다림 제거).
- 2행 "수집기 둘·가상 장치 두 벌이 2초마다 서로 밀어냄(reconnects 1,675) / 같은 MQTT client_id / fleet/common/single_instance.py flock 잠금 / 11/04": 장애 주입이 배경에서 재시작한 수집기가 살아 있는데 터미널에서 또 띄웠다. MQTT 브로커는 같은 client_id 가 새로 붙으면 옛 접속을 끊는다 → 둘이 2초마다 번갈아 재접속하며 `connected, subscribed` 가 반복 출력되고 msgs/s 가 50/0 으로 번갈아 나왔다. 가상 장치도 두 벌을 겹쳐 띄워 `reconnects=1675`(50대 × 33회)가 찍혔다. 해결은 파일 잠금(flock)으로 "한 번에 하나만" — 처음엔 수집기의 `fleet/logs/collector.lock` 이었고, 이를 `fleet/common/single_instance.py` 로 빼서 수집기와 가상 장치(prefix 별) 둘 다 쓴다. 두 번째 인스턴스는 먼저 뜬 pid 를 알려 주고 물러난다.
- 3행 "persistence true 뒤 오프라인 이벤트 +50 / 보관된 유언이 재구독 때 다시 내려옴 / retain=1 상태는 사건이 아님 → events 제외 / 11/04": 브로커 `persistence true` 를 켠 뒤 브로커를 재시작하면 offline 이벤트가 20 + 50 으로 늘었다. 장치 종료 때 발행된 유언(LWT) "offline" 이 **보관(retained)** 메시지라서, 재시작 뒤 수집기가 구독하는 순간 50대의 옛 offline 이 한꺼번에 다시 내려온 것. 해결: retain 플래그가 1 인 상태 메시지는 "지금 상태"지 "지금 일어난 사건"이 아니므로 events 표에 넣지 않고 카운터만 갱신한다. 대시보드의 오프라인 수가 제자리로 돌아왔다.
- 4행 "CI fleet_integration 실패(1차) / TimescaleDB 첫 기동의 임시 서버를 pg_isready 가 '준비됨'이라 함 / migrate.py --wait 가 TCP 로 재시도 / 11/04": 장표 120·122 에서 본 사고. 컨테이너 안 `pg_isready` 가 "accepting connections" 라고 한 1초 뒤 `migrate.py` 가 "server closed the connection unexpectedly". TimescaleDB 이미지는 첫 기동 때 임시 서버(유닉스 소켓만)로 init.sql 을 돌린 뒤 끄고 진짜 서버를 다시 띄우는데, 안쪽 체크는 임시 서버에도 준비됨이라 답한다. WSL 은 볼륨에 데이터가 있어 init 단계가 없었기에 안 보였다. 해결: 준비 확인을 소비자와 같은 경로(밖에서 TCP 접속)로, `migrate.py --wait 120`(1초마다 재시도).
- 5행 "ros2 topic echo 가 토픽을 못 봄 / 다른 RMW 로 떠 있던 ros2 데몬 / ros2 daemon stop / 타입을 직접 적기 / 11/04": MuJoCo 노드는 살아 있고 `ros2 node list` 에도 보이는데 `ros2 topic echo` 는 "does not appear to be published yet". 아침 DDS 측정 때 다른 RMW(미들웨어 구현체)로 떠 있던 **ros2 데몬**이 Fast DDS 노드의 토픽을 못 본 것. 데몬은 사용자당 하나이고 처음 뜬 RMW 로 고정된다. 해결은 `ros2 daemon stop` 후 재시도. "타입을 직접 적기"는 `ros2 topic echo /rt_status std_msgs/msg/String` 처럼 메시지 타입을 명령에 써 주면 데몬에게 타입을 물어보지 않아 데몬 상태와 무관하게 받는다는 뜻(장표 16, 단계 2 의 함정 줄)이다.
- 6행 "colcon install 뒤 libmujoco.so 못 찾음 / install 단계에서 rpath 소실 / CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE / 11/03": `colcon build` 로 설치(install)된 실행 파일은 빌드 때 기억한 공유 라이브러리 경로(rpath)를 잃는다. 그래서 `ros2 run` 이 "libmujoco.so.3: cannot open shared object" 로 죽었다. CMake 옵션 `CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE` 로 링크 때 쓴 경로를 설치본에도 남긴다.
- 아래 비고 "출처: docs/EXPERIMENTS.md §4 사고·함정, docs/LOG.md 해당 날짜. 사고마다 '배운 것' 한 줄이 LOG 에 있다": 표는 요약이고 원문은 LOG 다. LOG 의 각 사고 끝에는 "배운 것:" 한 줄이 있다(예: 헬스 체크는 소비자와 같은 경로로; RMW 를 바꿔 실험한 뒤에는 데몬을 지운다).

## 3. 용어와 단위

- `/proc/<pid>/exe`·`environ`·`cmdline`: 리눅스가 실행 중인 프로세스마다 보여 주는 가상 파일. exe = 실행 파일의 실제 경로(링크 풀림), environ = 환경 변수 전체, cmdline = 실행 명령.
- venv(가상환경)와 `VIRTUAL_ENV`: 프로젝트마다 따로 둔 파이썬 패키지 묶음. 활성화하면 `VIRTUAL_ENV` 와 `PATH` 가 그 폴더를 가리킨다. paho 는 MQTT 클라이언트 라이브러리.
- client_id(MQTT): 접속마다 붙는 이름. 같은 이름이 새로 붙으면 브로커가 옛 접속을 끊는다 — 그래서 "둘이 서로 밀어낸다".
- flock: 파일에 잠금을 걸어 "한 번에 한 프로세스만"을 보장하는 리눅스 기능.
- 유언(LWT)·보관(retained): 유언 = 비정상 종료 때 브로커가 대신 발행하는 메시지. 보관 = 토픽의 마지막 값을 새 구독자에게 바로 주는 플래그. 보관된 유언은 "마지막으로 알려진 상태"다.
- `pg_isready`: PostgreSQL 이 접속을 받는지 묻는 명령. TCP(네트워크)와 유닉스 소켓(같은 컴퓨터 안 파일) 두 길이 있다.
- RMW·ros2 데몬: RMW = ROS 2 가 DDS 를 부르는 층(Fast DDS / Cyclone). 데몬 = 토픽·노드 목록을 캐시해 두는 배경 프로세스.
- rpath: 실행 파일 안에 적힌 "공유 라이브러리를 여기서 찾아라" 경로.
- reconnects 1,675 = 50대 × 33회: 재접속 횟수(개), 2초 간격이면 약 66초 동안의 일.

## 4. 쉬운 예시

- 1행 비유: 요리사를 내보냈다 다시 부르면서 "그 사람의 집 주소(exe)"만 적어 두면 그가 쓰던 **앞치마와 도구(venv)** 없이 돌아온다. 그래서 나갈 때 입던 복장(environ)을 적어 두고 그대로 입혀 보낸다.
- 2행 비유: 같은 이름표를 단 사람 둘이 번갈아 출입문을 통과하면 경비(브로커)는 매번 앞사람을 내보낸다 — 1,675번. 이름표를 하나만 발급(flock)하면 끝.
- 3행 숫자: 장치 50대가 종료 때 남긴 "offline" 유언 50개가 보관되어 있다가 수집기가 다시 구독하자 50개가 한꺼번에 내려옴 → 오프라인 수가 20 + 50 = 70 으로 뛰었다. 그중 50 은 "지금 일어난 사건"이 아니다.
- 4행 비유: 가게 문에 "영업 중" 불이 켜졌지만 안에서는 개점 준비 중이라 손님을 받으면 바로 쫓겨난다. 불빛(pg_isready)이 아니라 **문을 직접 밀어 보기**(TCP 접속)로 확인한다.

## 6. 자주 하는 오해·함정

- "사고가 많다 = 품질이 낮다"는 오해: 11건 중 CI 2건은 CI 가 **잡았기 때문에** 기록된 것이고, 나머지는 첫 실행에서 드러난 것들이다. 숨기면 규칙(잠금, TCP 확인, 창 표기)이 왜 있는지 설명할 수 없다.
- `/proc/<pid>/exe` 가 "그 프로세스의 파이썬"이라는 믿음: 맞지만 venv 는 경로 **옆 파일**(pyvenv.cfg)로 식별되므로 링크를 풀면 사라진다.
- "보관 메시지가 온다 = 지금 사건이 났다": retain=1 은 과거의 마지막 값이다. 카운터(지금 상태)와 이벤트(사건)를 구분해야 대시보드 숫자가 맞는다.
- `pg_isready` 가 컨테이너 안과 밖에서 같은 답을 한다는 가정: 안쪽은 유닉스 소켓, 밖은 TCP 다. 헬스 체크는 소비자와 같은 경로로.
- RMW 를 바꿔 가며 실험한 뒤 데몬을 그대로 두면 다음 사람이 "토픽이 없다"고 헤맨다 — 실험 뒤 `ros2 daemon stop` 을 습관으로.
