# 장표 060 — 한 장 그림 — 데이터의 길 8단계
*위치: 2부 데이터의 길 · 한 장 그림 — 8단계*

## 1. 이 장표가 왜 있나
2부의 장 구분(059)은 질문을 세웠다 — "수십 대의 숫자를 잃지 않고 서버까지 가져오고, 장애와 업데이트를 견디나?". 이 장표는 그 답의 지도다. 1부의 "한 장 그림 10단계"(007)와 같은 꼴로, 데이터가 장치에서 대시보드까지 지나는 여덟 상자를 한 줄로 늘어놓고 상자마다 담당 파일을 적었다. 뒤에 오는 ①~⑧ 묶음 장표(062 이후)는 전부 이 상자 중 하나에서 출발하므로, 이 장표를 보고 "지금 어느 상자인가"를 알면 길을 잃지 않는다. 1부와 다른 점도 아래 상자에 적었다 — 여기엔 실시간 요구가 없고, 대신 "잃지 않는 것, 잃었으면 세는 것"이 요구다.

## 2. 장표를 하나씩 읽기
여덟 상자를 윗줄 왼쪽부터 넷, 아랫줄 넷 순서로 읽는다. 상자 색은 역할 묶음이다(장치 쪽 둘, 서버 적재 둘, 화면, 배포, 장애, 진단).

- 1 "장치 에이전트 — 1 Hz tick: seq·ts_ns·fw·state·센서값 JSON. 끊기면 버퍼(3600개), 붙으면 QoS 1 재전송. 유언(offline)·보관(online)" (`fleet/agent/device_agent.py`): 장치 한 대가 1초마다 자기 상태를 JSON 한 개로 발행한다. 일련번호 seq 가 유실을 세는 열쇠, ts_ns 가 전달 지연을 재는 시각. 브로커와 끊기면 메모리에 최대 3,600개(1 Hz 로 1시간)를 모아 두고 다시 붙으면 QoS 1 로 재전송한다. 접속하면 status 에 "online"(보관 메시지), 비정상 종료 땐 브로커가 대신 "offline"(유언)을 남긴다. 장표 062~066.
- 2 "브로커 Mosquitto — 토픽 fleet/<id>/… 중계. persistence true, 지속 세션 큐 20,000, keepalive 1.5배 안에 못 들으면 유언 발행" (`fleet/mosquitto/mosquitto.conf`): MQTT 우체국. 장치는 서버 주소를 모르고 브로커만 본다. 설정 파일의 `persistence true` 는 재시작해도 보관·세션을 잃지 않게, `max_queued_messages 20000` 은 수집기가 없는 동안 지속 세션에 쌓아 둘 상한. keepalive 의 1.5배(기본 10초 → 15초) 안에 장치 소식이 없으면 끊긴 것으로 보고 유언을 발행한다. 장표 067~068.
- 3 "수집기 — 구독 → pending → 1초마다 묶음(COPY) → backlog(DB 죽음) → 통계 한 줄. 곱게 종료, 단일 인스턴스 잠금" (`fleet/collector/collector.py`): 브로커를 구독해 받은 메시지를 `pending` 목록에 쌓고, 메인 스레드가 1초마다 꺼내 PostgreSQL `COPY` 한 번으로 적재한다(행마다 INSERT 면 왕복 50회/초, 묶으면 1회/초). DB 가 죽으면 `backlog`(최대 200,000행)에 들고 있다가 살아나면 넣는다. 1초마다 처리량·지연 백분위수를 `collector_stats` 에 한 줄 남긴다. 종료 신호를 받으면 수신을 멈추고 남은 것을 마지막으로 적재한 뒤 끝낸다(곱게 종료). 두 벌이 뜨지 않게 flock 잠금. 장표 069~074(③ 묶음).
- 4 "TimescaleDB — telemetry·events·collector_stats 하이퍼테이블, devices, ota_rollouts. 마이그레이션 001~003" (`fleet/db/init.sql · migrate.py`): 시계열용 PostgreSQL. 시간순 데이터 세 표는 하이퍼테이블(시간으로 자동 분할), 장치 목록(devices)과 배포 기록(ota_rollouts)은 일반 표. 스키마가 바뀌면 `migrations/NNN_*.sql` 을 번호 순서로 적용하고 `schema_migrations` 에 기록한다 — init.sql 은 컨테이너가 처음 뜰 때 한 번만 돌기 때문. 장표 075~076(④ 묶음).
- 5 "Grafana — Fleet Overview 14 패널 — 온라인·초당 메시지·전달 지연·backlog·펌웨어 버전·이벤트. JSON 은 생성기로" (`fleet/grafana/make_dashboard.py`): 사람이 보는 화면. 패널 14개의 JSON 을 손으로 그리지 않고 파이썬 생성기가 만든다 — 패널을 고치면 코드 리뷰가 되고 다시 만들 수 있다. 장표 075~076(⑤ 묶음).
- 6 "OTA 배포기 — 살아 있는 장치 찾기 → 5%·50%·100% 단계 → 적용 대기 → 헬스 게이트 → 롤백" (`fleet/ota/rollout.py`): 펌웨어 업데이트를 단계적으로. 먼저 5% 에만 보내고 건강(state ok)을 확인한 뒤 50%, 100% 로 넓힌다. 나쁜 펌웨어면 5% 단계의 헬스 게이트에서 걸려 전부 롤백한다. 장표 077~081(⑥ 묶음).
- 7 "장애 주입·판정 — broker·db·collector 를 죽였다 살리고 감지·복구·유실을 DB 로 잰다. 판정 규칙으로 CI 가 통과/실패" (`fleet/chaos/inject.py · assert_results.py`): 브로커·DB·수집기를 10초씩 멈추고 되살리며, 그동안 감지에 몇 초, 복구에 몇 초, 몇 개를 잃었는지를 시스템 자신의 DB 숫자로 낸다. `assert_results.py` 가 합격선(유실 0 등)을 판정해 CI 를 통과/실패시킨다. 장표 082~085(⑦ 묶음).
- 8 "진단 — 이상한 숫자를 들여다본다: 오프라인 군집(A) · 지연 튐(B) · seq 틈(C)" (`fleet/tools/diag.py`): 실측에서 나온 이상한 것 셋을 DB 에서 다시 파고드는 도구. A 오프라인 이벤트가 50 이 아니라 20 인 이유(E09), B 전달 지연이 10초마다 튀는 이유(E10), C seq 틈이 진짜 유실인지 장치가 멈춘 것인지. 장표 085(⑧ 묶음).

아래 상자 "1부의 단계 ⑩(다리)이 여기 1번 상자로 들어온다. 전부 파이썬이고 실시간 요구가 없다 — 대신 '잃지 않는 것'과 '잃었으면 세는 것'이 요구다": 1부 단계 10 의 `ros_status_bridge.py` 가 RT 노드의 rt_status 를 1 Hz 로 받아 DeviceAgent 로 올리므로, 로봇은 가상 장치 50대와 같은 1번 상자로 들어온다(51번째 장치). 2부는 1 ms 가 아니라 초 단위라 전부 파이썬이다. 요구가 다르다: 1부는 "늦지 않게", 2부는 "잃지 않게, 잃었으면 숫자로".

## 3. 용어와 단위
- MQTT: 장치 ↔ 서버 메시지 규약. 발행(publish)·구독(subscribe)·토픽(주제 이름표). 브로커가 가운데서 중계한다.
- 토픽 `fleet/<id>/telemetry · status · cmd · cmd_reply`: 장치별로 측정값 / 온·오프라인 / 서버→장치 명령 / 그 응답.
- QoS 0 / 1: 보내고 잊음 / 브로커가 받았다는 확인(PUBACK)까지. QoS 1 은 최소 한 번 도착을 보장한다(중복 가능, seq 로 가린다).
- 유언(LWT, Last Will and Testament): 장치가 접속할 때 브로커에 맡겨 두는 메시지. 비정상 종료 때 브로커가 대신 발행.
- 보관 메시지(retained): 토픽의 마지막 값을 브로커가 저장해 새 구독자에게 바로 준다. status 가 이것.
- 지속 세션(clean_session=False): 구독자가 끊겨 있는 동안 브로커가 QoS 1 메시지를 쌓아 두는 세션. 상한이 `max_queued_messages`.
- keepalive: 이 시간 동안 소식이 없으면 장치가 PINGREQ 를 보낸다. 브로커는 1.5배 안에 아무것도 못 들으면 끊긴 것으로 본다.
- COPY: PostgreSQL 에서 여러 행을 한 번에 넣는 명령. 하이퍼테이블: TimescaleDB 가 시간으로 자동 분할하는 표.
- 전달 지연: 장치가 측정한 시각(ts_ns)부터 수집기에 도착한 시각까지. 1초 묶음 적재 때문에 DB 에 보일 때까지는 최대 1초가 더 걸린다.
- OTA(Over The Air): 원격 펌웨어 업데이트. 헬스 게이트: 적용 뒤 일정 시간 건강을 지켜보다 실패가 기준을 넘으면 롤백하는 관문.
- 장애 주입(chaos): 일부러 구성 요소를 죽이고 시스템이 어떻게 견디는지 숫자로 재는 것.

## 4. 쉬운 예시
비유 — 지점 50곳과 본사: 지점(장치)이 1분마다 매출 문자(텔레메트리)를 통신사(브로커)에 보낸다. 본사 접수 직원(수집기)이 문자를 모아 1분에 한 번 장부(DB)에 옮겨 적고, 사장은 벽의 현황판(Grafana)을 본다. 통신사가 먹통이면 지점 직원이 메모장(버퍼)에 적어 두고 복구되면 몰아 보낸다. 본사가 새 매뉴얼(OTA)을 배포할 땐 지점 5% 에 먼저 주고 문제없으면 넓힌다. 감사팀(장애 주입)은 일부러 통신사·장부·접수 직원을 10분씩 멈춰 보고 "몇 건을 잃었나"를 장부 번호(seq)로 센다. 이상한 숫자가 나오면 분석팀(diag)이 장부를 뒤진다.

숫자 예시 — 50대 × 1 Hz = 초당 50개. 브로커가 10초 죽으면 50 × 10 = 500개가 끊긴 동안 생기고, 끊김 감지·재접속 약 3초가 더해져 실측은 654개 버퍼 → 654개 재전송(E05). 버퍼 상한 3,600개는 1 Hz 로 1시간이니, 1시간 넘게 끊기면 가장 오래된 것부터 버려진다. 수집기의 backlog 상한 200,000행은 50대 1 Hz 면 약 66분.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 버퍼 3,600 — `fleet/agent/device_agent.py:24` (`MAX_BUFFER = 3600`). QoS 1 재전송 — 같은 파일 126~133줄. 유언·보관 — 56줄, 122줄.
- 확인: persistence true, max_queued_messages 20000 — `fleet/mosquitto/mosquitto.conf`. keepalive 1.5배 — MQTT 규약(장치 쪽 설명은 `device_agent.py:32`).
- 확인: pending → 1초 묶음 COPY, backlog 200,000행, 곱게 종료, 잠금 — `fleet/collector/collector.py` 머리 주석과 59줄(`MAX_BACKLOG_ROWS`), 325~345줄.
- 확인: 하이퍼테이블 셋, devices, ota_rollouts — `fleet/db/init.sql` 13~62줄. 마이그레이션 — `fleet/db/migrations/002_ota.sql`, `003_collector_resilience.sql`, 적용은 `fleet/db/migrate.py`.
- 확인: 패널 14개 — `fleet/grafana/make_dashboard.py` 머리 주석(14개 목록)과 94줄(14번 표 패널).
- 확인: 5 → 50 → 100%, 헬스 게이트, 롤백 — `fleet/ota/rollout.py` 머리 주석 4~9줄.
- 확인: 장애 3종(broker·db·collector) — `fleet/chaos/inject.py:5-7`. 진단 A·B·C — `fleet/tools/diag.py:4-12`.
- 확인: 654 = 654 — `docs/experiments/E05.md` 3절.
- 추정: "마이그레이션 001~003" 의 001 — `migrations/` 폴더에는 002, 003 두 파일만 있고 init.sql 이 첫 스키마 역할을 한다. 001 이 init.sql 을 가리키는 것으로 읽었다.

## 6. 자주 하는 오해·함정
- "MQTT 가 있는데 왜 수집기가 따로 있나?" — 브로커는 중계만 한다. 어딘가에 저장하려면 구독해서 DB 에 넣는 프로그램이 필요하고, 그것이 수집기다.
- "QoS 1 이면 유실이 없나?" — 장치 → 브로커 구간은 그렇다. 수집기가 죽어 있는 동안은 지속 세션이 있어야 브로커가 들고 있고, 그 큐에도 상한(20,000)이 있다. 그래서 '유실 0' 은 설정 세 가지가 맞아야 나오는 숫자다(② 묶음, 3부 표③).
- "1부처럼 실시간이 필요하지 않나?" — 없다. 1 Hz 요약이고 사람이 보는 화면이다. 그 대신 끊김·재시작·죽음을 견디는 것이 요구다.
- "장애 주입은 테스트인데 왜 본편(2부)에 있나?" — 장애를 주입하고 세는 코드가 데이터 길의 일부(⑦⑧)이기 때문이다. 그 코드로 얻은 실험 숫자(표③)는 3부에 있다.
- 함정(11/04): 수집기나 가상 장치를 두 벌 띄우면 같은 client_id 가 서로 밀어내 2초마다 재접속한다 → 단일 인스턴스 잠금(066).

## 7. 면접 한 문장
"관제 쪽은 장치 에이전트 → Mosquitto → 수집기 → TimescaleDB → Grafana 의 다섯 상자에 OTA 배포기·장애 주입·진단 셋을 더한 여덟 단계인데, 실시간 요구가 없는 대신 '잃지 않고, 잃었으면 센다'를 요구로 삼아 seq 번호와 DB 숫자로 유실을 세게 만들었습니다."
