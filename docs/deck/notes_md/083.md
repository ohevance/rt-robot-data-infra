# 장표 083 — ⑦ 장애 주입 — 유실을 세는 SQL: 기준점은 '장애 직전의 마지막 seq' (E07 에서 고침)
*위치: 2부 데이터의 길 · ⑦⑧ 장애·판정·진단 · ② 코드 — 유실 SQL*

## 1. 이 장표가 왜 있나
앞 장표(082, ⑦⑧ 들머리)에서 장애 주입의 기준을 세웠다 — 부품을 일부러 죽였을 때 "얼마나 잃었나(유실)"와 "얼마나 빨리 돌아오나(복구)"를 숫자로 재고, 그 숫자를 믿을 수 있어야 한다. 그러면 가장 먼저 "**유실을 어떻게 세나**"가 문제다. 세는 식이 틀리면 모든 장애 실험의 결론이 틀린다. 실제로 틀렸었다: 11/04 첫 측정에서 유실은 전부 "0" 이었는데 진단 도구는 어떤 장치에 12초 공백을 보였다. 둘 중 하나는 거짓이었고, 거짓은 "0" 이었다(E07). 이 장표는 그 고친 식 — `fleet/chaos/inject.py` 의 `measure_loss`(118~134줄) — 과 "왜 기준점이 장애 직전의 마지막 일련번호여야 하나"를 보인다. 이 저장소에서 가장 중요한 한 줄, "0 을 의심해서 53 을 찾았다"가 여기서 나온다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/chaos/inject.py:118-134`.

- 118줄 `def measure_loss(db, t_from, t_to):` — 입력은 DB 접속 객체와 시간 창 [t_from, t_to](장애 주입 시각부터 집계 시각까지). 출력은 유실 숫자들.
- 119줄 독스트링 첫 줄 `[t_from, t_to] 창의 유실 = 장치별로 (창 안 마지막 seq − 창 직전 마지막 seq) − 받은 행 수.` — 식 전체가 한 줄에 있다. 장치마다: 창 안에서 받은 가장 큰 일련번호에서 창 직전의 마지막 일련번호를 빼면 "장치가 창 동안 만들었어야 할 메시지 수"가 되고, 거기서 실제로 받은 행 수를 빼면 유실이다. 일련번호(seq)는 장치가 메시지마다 1씩 올려 붙이므로, 번호의 차가 곧 만든 개수다.
- 120~121줄 독스트링 `왜 "창 직전 seq" 에 고정하나: 창 안의 min(seq) 를 기준으로 하면, 장애 시작 직후에 잃은 메시지(= 창의 앞 가장자리)가 기준점 뒤로 숨어 유실 0 으로 보인다 (11/04 실측에서 2대 × 12개를 놓칠 뻔함). 직전 30초 안에 데이터가 없는 장치는 min(seq) 로.` — 핵심 이유. 처음 식은 "창 안의 가장 작은 번호"를 기준으로 했다. 그러면 장치가 장애 시작 직후 12개를 잃었어도, 창 안에서 처음 받은 번호가 13번째이므로 계산은 13번째부터 시작해 "빠진 번호 없음 = 0" 이 된다. 잃은 것이 기준점 **앞**에 있어 계산 범위 밖으로 숨는 것이다. 그래서 기준점을 창 **밖**, 장애 직전 30초의 마지막 번호로 옮겼다. 직전 30초에 데이터가 없는 장치(새로 켜진 장치 등)는 어쩔 수 없이 옛 방식(창 안 min(seq) − 1)을 쓴다.
- 122줄 `rows = db.query("""` — SQL 질의 시작. `db.query` 는 DB 가 죽어 있어도 예외를 밖으로 내지 않고 None 을 돌려주는 안전한 질의 함수(58~75줄) — 장애 주입 도중에는 DB 가 실제로 죽어 있을 수 있기 때문이다.
- 123~124줄 `WITH w AS (SELECT device_id, count(*) AS received, max(seq) AS max_seq, min(seq) AS min_seq FROM telemetry WHERE time >= %s AND time <= %s GROUP BY device_id),` — 임시 표 `w`(window, 창): 창 안의 행을 장치별로 묶어 받은 행 수(`received`), 가장 큰 번호(`max_seq`), 가장 작은 번호(`min_seq`)를 구한다. `%s` 두 개에 t_from, t_to 가 들어간다.
- 125~126줄 `b AS (SELECT device_id, max(seq) AS prev_seq FROM telemetry WHERE time >= %s - interval '30 seconds' AND time < %s GROUP BY device_id)` — 임시 표 `b`(before, 직전): 창 시작 직전 30초 동안의 행을 장치별로 묶어 마지막 번호(`prev_seq`)를 구한다. `%s` 두 개 모두 t_from(창 시작)이다. 30초인 이유: 1 Hz 장치라면 30개가 들어 있어 충분하고, 너무 길면 오래전에 꺼진 장치의 옛 번호가 섞인다.
- 127~129줄 `SELECT count(*), coalesce(sum(w.received), 0), coalesce(sum(w.max_seq - coalesce(b.prev_seq, w.min_seq - 1)), 0) FROM w LEFT JOIN b USING (device_id)` — 두 임시 표를 장치 이름으로 이어 붙여(LEFT JOIN: `b` 에 없는 장치도 `w` 쪽은 남긴다) 세 숫자를 낸다. 창 안에 보인 장치 수(`count(*)`), 받은 행 수의 합, 기대 개수의 합. 기대 개수는 장치마다 `max_seq − 기준점`, 기준점은 `prev_seq` 가 있으면 그것, 없으면(`coalesce`) `min_seq − 1`. 바깥 `coalesce(..., 0)` 은 창 안에 아무 행도 없을 때 None 대신 0 을 내게 한다.
- 130줄 `""", (t_from, t_to, t_from, t_from))` — `%s` 네 자리에 들어가는 값. 순서가 SQL 의 `%s` 순서와 같아야 한다.
- 131~132줄 `if not rows:` / `return {"expected": None, "received": None, "lost": None, "devices": None}` — DB 가 응답하지 않으면 네 값 모두 None. 모르는 것을 0 으로 쓰지 않는다.
- 133줄 `devices, received, expected = rows[0]` — 결과 한 행을 세 변수로.
- 134줄 `return {"expected": int(expected), "received": int(received), "lost": int(expected) - int(received), "devices": int(devices)}` — 기대 개수, 받은 개수, 유실(= 기대 − 받음), 장치 수. 이 사전이 장애 주입 결과 JSON 의 `loss` 항목이 되고, `scripts/make_table3.py` 가 읽어 표③-2 의 "유실 행 0 / 1400" 같은 칸을 만든다(앞이 lost, 뒤가 expected).

오른쪽 "읽는 포인트" 네 줄:
- "장치별로 (창 안 마지막 seq − 창 직전 마지막 seq) = 만들었어야 할 메시지 수, 실제 받은 행 수와의 차 = 유실" — 119줄의 식.
- "왜 창 안 min(seq) 가 아닌가: 장애 시작 직후 잃은 메시지는 창의 앞 가장자리라 min(seq) 뒤로 숨는다 → 유실 0 으로 보인다(11/04 맹점, 2대 × 12개)" — 120~121줄. 진단 도구가 처음 보인 것은 장치 두 대(vdev-003·005)의 12초 공백이었고, 식을 고친 뒤 전체를 다시 세자 브로커 10초 중단의 유실이 53 / 1434 로 드러났다.
- "직전 30초에 데이터가 없는 장치는 min(seq)−1 로" — 125~129줄의 `coalesce`.
- "결과: expected · received · lost · devices → JSON → make_table3 → 표③-2" — 134줄에서 표까지의 길.

## 3. 용어와 단위
- seq(일련번호): 장치가 보내는 메시지마다 1씩 올려 붙이는 번호. `telemetry.seq` 열. 번호의 차 = 만든 개수.
- 창(window) [t_from, t_to]: 유실을 셀 시간 구간. 장애 주입 시각부터 집계 시각까지.
- 기준점: 기대 개수를 계산할 때 빼는 번호. 고친 식에서는 "창 직전 30초의 마지막 seq".
- SQL / `WITH … AS`(공통 테이블 식): 질의 안에서 임시 표 `w`, `b` 를 만들어 이름 붙이는 문법.
- `GROUP BY device_id`: 장치별로 묶어 집계. `count`, `max`, `min`, `sum` 은 묶음마다 센다.
- `LEFT JOIN … USING (device_id)`: 두 표를 같은 장치 이름으로 이어 붙이되, 왼쪽 표(`w`)의 장치는 오른쪽(`b`)에 없어도 남긴다.
- `coalesce(a, b)`: a 가 None(NULL)이면 b 를 쓴다.
- `interval '30 seconds'`: PostgreSQL 의 시간 길이 값. `%s - interval '30 seconds'` = 창 시작 30초 전.
- `%s`: 파이썬 DB 라이브러리가 값을 안전하게 끼워 넣는 자리표시(문자열 조립을 하지 않아 SQL 주입을 막는다).
- 유실 행 0 / 1400: lost 0, expected 1,400 (WSL2 가상 50대 1 Hz, 브로커 10초 중단 창).

## 4. 쉬운 예시
출석 번호표 비유: 학생(장치)마다 매일 번호표 한 장을 내는데 번호는 1, 2, 3 … 하루에 하나씩 올라간다. 어느 주(창)에 몇 장 빠졌는지 세려면 "그 주의 첫 번호표부터 마지막까지 빠진 번호"를 세면 될 것 같지만, 그러면 **월요일에 결석해서 아예 안 낸 번호표**는 세지 못한다 — 그 주의 첫 번호표가 화요일 것이라 거기서 시작하기 때문이다. 그래서 "지난주 마지막 번호표"를 기준으로 삼으면 월요일의 공백도 보인다. 그게 `prev_seq` 다.

숫자 예시: 장치 하나가 장애 직전 마지막으로 seq 100 을 보냈다. 브로커가 10초 멈춰 101~112(12개)가 사라지고 113 부터 다시 들어와 창 끝까지 140 이 됐다고 하자. 옛 식: 창 안 min(seq) = 113, max = 140, 받은 행 28, 기대 140 − 113 + 1 = 28 → 유실 0. 고친 식: 기준 prev_seq = 100, 기대 140 − 100 = 40, 받은 행 28 → 유실 12. 50대를 더하면 E07 의 53 / 1434 같은 숫자가 된다.

## 6. 자주 하는 오해·함정
- "유실 0 이 나오면 좋은 결과"라는 함정. 0 은 가장 의심해야 할 숫자다. 다른 증거(진단 도구의 seq 틈, 대시보드의 공백)와 맞는지 꼭 본다. 이 저장소에서는 0 을 의심해서 53 을 찾았고, 그 뒤 고친 설계로 다시 0 을 만들었다 — 두 0 은 전혀 다른 0 이다.
- "창 안의 번호만 보면 된다"는 생각이 바로 맹점이었다. 잃은 것은 창의 앞 가장자리에 있고, 기준점이 창 안에 있으면 그 앞은 보이지 않는다.
- 30초 전에 데이터가 없는 장치는 옛 식으로 돌아가므로 그 장치의 앞 가장자리 유실은 여전히 못 센다. 장애 주입 전 `--settle`(기본 15초) 동안 안정 상태를 만든 뒤 재는 이유 중 하나다.
- 재전송된 중복 메시지(QoS 1 은 두 번 올 수 있다)가 있으면 `received` 가 기대보다 커져 유실이 음수로 보일 수 있다. 수집기가 같은 (장치, seq) 를 다시 넣지 않도록 하는 것은 이 식의 범위 밖이다.
- DB 가 죽어 있는 동안에는 질의가 None 을 돌려준다 — 0 이 아니다. 모름과 0 을 구분하는 것이 측정 도구의 기본이다.

## 7. 면접 한 문장
"처음 유실 측정은 창 안의 첫 번호를 기준으로 해서 장애 직후 잃은 메시지가 계산 밖으로 숨었고, 전부 0 으로 보였습니다. 기준점을 장애 직전 30초의 마지막 번호로 바꾸자 53 / 1434 가 드러났고, 원인 셋을 고친 뒤 같은 식으로 다시 재서 0 / 1400 을 얻었습니다 — 0 을 의심한 것이 이 프로젝트의 가장 중요한 한 줄입니다."
