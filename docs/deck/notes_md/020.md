# 장표 020 — 단계 3 — 우편함의 정체 — 락 없는 SPSC 링 버퍼 push()/pop()
*위치: 1부 로봇을 움직이는 길 · 단계 3/10 우편함 · ② 코드 — SPSC 링 push/pop*

## 1. 이 장표가 왜 있나
- 앞 장표(019)에서 콜백이 `g_cmd_ring.push(cmd)` 를 불렀다. 그 `push` 가 무엇인지, 그리고 RT 스레드가 부를 `pop` 이 무엇인지를 코드로 보이는 장표다.
- 이 코드가 1부 전체에서 가장 중요한 27줄이다. "RT 스레드는 절대 기다리지 않는다"는 원칙이 실제로 어떻게 구현되는지가 여기 있다. 같은 클래스가 명령 우편함(64칸)·상태 벨트(2048칸)·타이밍 링(65536칸) 세 곳에 쓰인다.
- 위치: `rt_control/rt_core/include/rt_core/spsc_ring.hpp:38-64`. 1~37줄은 머리말 주석으로, memory_order 세 가지를 쉬운 말로 설명한다.

## 2. 장표를 하나씩 읽기
**push() — 생산자(넣는 쪽)가 부른다**
- `std::size_t head = head_.load(std::memory_order_relaxed);` — `head_` 는 "내가 다음에 쓸 칸 번호". 생산자 자신만 바꾸는 변수라 `relaxed`(순서 보장 없이 그냥 읽기)로 충분하다.
- `std::size_t next_head = next_index(head);` — 다음 칸 번호. `next_index` 는 `(i + 1) & (N - 1)` 로, 마지막 칸 다음은 0으로 돌아간다(그래서 "링").
- `std::size_t tail = tail_.load(std::memory_order_acquire);` — `tail_` 은 "소비자가 다음에 읽을 칸". 상대가 바꾸는 변수라 `acquire` 로 읽는다.
- `if (next_head == tail) return false;` — 다음 칸이 소비자가 읽을 칸이면 꽉 찼다. 주석: "한 칸은 항상 비워 둔다"는 규칙으로 꽉 참/비어 있음을 구분한다. 칸이 N 개면 실제 담는 수는 N−1 개.
- `buffer_[head] = value;` — **1) 값을 먼저 쓴다.**
- `head_.store(next_head, std::memory_order_release);` — **2) 그 다음에 head 를 공개한다.** `release` 는 "이 저장 전에 내가 써 둔 것(buffer_)이 먼저 보이게 한 뒤 공개"다. 순서가 바뀌면 소비자가 아직 안 쓰인 칸을 읽을 수 있다.

**pop() — 소비자(꺼내는 쪽)가 부른다**
- `tail = tail_.load(relaxed)` — 내 변수. `head = head_.load(acquire)` — 상대 변수. acquire 로 읽으면 생산자가 release 전에 써 둔 `buffer_[...]` 값까지 보이는 것이 보장된다.
- `if (tail == head) return false;` — 비어 있음. 소비자는 그냥 돌아간다(쉰다).
- `out = buffer_[tail];` 그리고 `tail_.store(next_index(tail), release);` — 값을 꺼내고 읽을 칸을 한 칸 전진시켜 공개한다.

**오른쪽 요점**
- SPSC 라서 락이 필요 없다: 각 변수를 바꾸는 스레드가 하나뿐이면 "동시에 바꾸는" 상황 자체가 없다.
- push 는 값 → head 순서, pop 은 head(acquire) 뒤에 값. 이 두 순서가 정확성의 전부다.
- 꽉 차면 false(버린다), 비면 false(쉰다). 어느 쪽도 기다리지 않는다.
- N 은 2의 거듭제곱: `& (N−1)` 이 `% N` 과 같고 나눗셈이 없어 빠르다. `static_assert` 가 컴파일 때 강제한다.
- 세 곳에 쓰인다: 64 · 2048 · 65536.

## 3. 용어와 단위
- **원자 변수(std::atomic)**: 읽기·쓰기 도중에 다른 스레드가 끼어들 수 없는 변수. `head_`, `tail_` 이 그것이다.
- **memory_order**: 원자 변수 접근 때 "주변 메모리 쓰기와의 순서를 얼마나 보장하나"를 정하는 옵션. `relaxed`(보장 없음, 가장 빠름) / `release`(내가 앞서 쓴 것이 먼저 보이게 하고 공개) / `acquire`(상대가 release 로 공개한 것과 그 앞의 쓰기까지 보장받아 읽기). 이 파일 머리말 18~24줄에 같은 설명이 있다.
- **생산자 / 소비자**: 넣는 스레드 / 꺼내는 스레드. 우편함에서는 ROS 2 콜백 / RT 스레드, 벨트에서는 RT 스레드 / 발행 스레드로 역할이 뒤바뀐다.
- **N−1 용량**: 칸 64개면 63개까지 담긴다. 빈 칸 하나가 "꽉 참"과 "비어 있음"(둘 다 head == tail 이 될 수 있음)을 가르는 표지다.
- **alignas(64)**: `head_` 와 `tail_` 을 64바이트(캐시 줄 하나) 간격으로 떨어뜨려 두 스레드가 같은 캐시 줄을 두고 다투지 않게 한다(false sharing 방지). 장표에는 없지만 멤버 선언부에 있다.

## 4. 쉬운 예시
- **회전 초밥 레일**: 요리사(생산자)가 접시를 올리고 손님(소비자)이 집어 간다. 요리사는 "다음에 올릴 자리"(head)만, 손님은 "다음에 집을 자리"(tail)만 움직인다. 요리사가 접시를 **올린 뒤**에 "여기까지 올렸어요" 표지(head)를 옮기니, 손님은 표지 앞의 접시는 안심하고 집는다. 레일이 꽉 차면 요리사는 접시를 뒤로 물리고(버리고) 하나를 센다. 레일이 비면 손님은 기다리지 않고 자기 일을 한다.
- **순서가 바뀌면**: 표지를 먼저 옮기고 접시를 뒤에 올리면, 손님이 빈 자리를 집는다 — 이것이 release/acquire 가 막는 사고다.
- **숫자 예시**: 64칸 우편함에 50 Hz 로 넣고 1 kHz 로 비우면 평상시 0~1개. 상태 벨트 2048칸에 1 kHz 로 넣고 100 Hz 로 비우면 한 번에 10개씩 쌓이고 비워지므로 여유가 200배다. 타이밍 링 65536칸은 1 kHz 샘플을 65초 동안 쌓아도 안 넘친다.

- 확인: 세 곳의 크기 — `joint_types.hpp` `kCommandRingSize = 64`, `kStateRingSize = 2048`; `rt_loop.hpp:63` `kRingSize = 65536`.

- 확인: 결정 기록 — `docs/DECISIONS.md` 2026-11-03 "로깅 큐는 꽉 차면 버린다 (drop-on-full)".

## 6. 자주 하는 오해·함정
- "relaxed 를 쓰면 틀린 코드 아닌가" — 자기 자신만 바꾸는 변수를 읽을 때는 relaxed 가 맞다. 상대 변수는 acquire, 공개는 release. 셋을 섞어 쓰는 것이 정답이고, 전부 seq_cst 로 하면 느리기만 하다.
- "꽉 찼을 때 오래된 것을 덮어쓰면 더 좋지 않나" — 덮어쓰기는 생산자가 소비자의 칸을 건드리는 것이라 SPSC 의 전제가 깨진다. 그래서 새것을 버린다. 명령 우편함에서는 어차피 RT 스레드가 매 주기 전부 비우고 마지막 것만 쓰므로(장표 030) 실질적 차이가 없다.
- "N 을 아무 수로 해도 되지 않나" — `& (N−1)` 트릭은 2의 거듭제곱에서만 맞다. `static_assert` 가 컴파일 때 막는다.
- 생산자나 소비자가 둘 이상이면 이 코드는 틀린다. 머리말 10줄에 "둘 이상이면 이 코드는 틀린다"고 적어 두었다.

## 7. 면접 한 문장
"값을 먼저 쓰고 head 를 release 로 공개하고, 소비자는 head 를 acquire 로 읽은 뒤 값을 읽습니다 — 그 두 순서가 락 없이도 맞는 이유이고, 칸 하나를 비워 꽉 참과 비어 있음을 가르며, 2의 거듭제곱 크기라 인덱스 계산에 나눗셈이 없습니다."
