# 장표 057 — 안전 경로 — 명령이 끊기면 무슨 일이 일어나나 (워치독 → FAULT → 복구)
*위치: 1부 로봇을 움직이는 길 · 가로지르기 — 안전 경로(명령이 끊기면)*

## 1. 이 장표가 왜 있나
본편 10단계(장표 007~056)는 모두 "명령이 정상적으로 계속 오는 동안"의 길이었다. 그런데 실제 로봇에서 가장 위험한 순간은 정상이 아닐 때 — 상위 프로그램이 죽거나 네트워크가 끊겨 **명령이 안 올 때**다. 마지막 목표를 향해 계속 움직이면 로봇이 사람이나 물건을 칠 수 있다. 단계 5(제어 단계)의 워치독과 상태 머신을 각각 코드로 보았지만, "끊기는 순간부터 복구까지" 시간 순서로 한 번에 따라가 본 적은 없다. 이 장표는 그 비정상 경로를 순서도 하나로 보여 주는 **가로지르기** 장표다. 다음 장표(058, 실물로 가면)와 함께 본편의 마무리를 이룬다.

## 2. 장표를 하나씩 읽기
순서도는 상자 8개(2줄 × 4개)로, 위 줄은 왼쪽 → 오른쪽, 아래 줄은 오른쪽 → 왼쪽으로 뱀처럼 이어진다. 마름모는 '판단 기준(코드의 if)', 빨간 상자는 '비정상 진입', 진한 녹색 상자는 결론이다.

- 상자 1 "RUNNING: 50 Hz 명령을 따라 움직이는 중" — 출발점. 상태 머신이 RUNNING 이고, 20 ms 마다(50 Hz) 새 목표가 우편함으로 들어온다. 1 kHz 루프 기준으로 20주기에 한 번 명령이 있고 나머지 19주기는 지난 목표를 유지한다 — 이것은 정상이다.
- 마름모 2 "마지막 명령이 50 ms 보다 오래됐나? (check_watchdog)" — 매 주기(1 ms 마다) `ControlStep::check_watchdog`(control_step.cpp 83~100줄)이 묻는다. `stale = (last_cmd_ns_ == 0) || (now_ns - last_cmd_ns_ > cfg_.watchdog_ns)`. 50 ms 는 로봇 프로필 `robots/so101.yaml` 의 `safety.watchdog_ms: 50` 에서 온다. 왜 50 ms 인가: 50 Hz 명령이면 정상 간격은 20 ms 이므로, 2.5배인 50 ms 동안 아무것도 안 오면 '끊긴 것'으로 본다. 화살표 글 "예 → stale".
- 빨간 상자 3 "tripped = true, 목표 = 현재 위치 / watchdog_trips +1, 사건 WATCHDOG_TRIP" — stale 이면 세 가지가 일어난다. (1) `tripped_ = true`. (2) 목표(desired_)를 지금 위치(position_)로 덮어쓴다 → 로봇은 그 자리에 머문다. 급정지도, 0 위치 복귀도 아닌 '유지'가 기본값인 이유는 DECISIONS 11/03(D1) — "명령이 끊겼을 때 마지막 목표로 계속 가는 것이 가장 위험하다". (3) 정상 → 멈춤으로 **바뀌는 순간에만** `watchdog_trips` 를 1 올리고, `update_state_machine(got_command, stale)` 에 사건 WATCHDOG_TRIP 을 넣는다(103~106줄: `good_cycles_ = 0; sm_.handle(WATCHDOG_TRIP)`).
- 상자 4 "상태 머신: RUNNING → FAULT (rt_status: watchdog tripped, state FAULT)" — 전이표(robot_state_machine.cpp 15~31줄)의 한 줄 `{RUNNING, WATCHDOG_TRIP, FAULT}` 가 적용된다. 바깥에서는 rt_status JSON 의 `"watchdog": "tripped"`, `"state": "FAULT"` 로 보이고, 관제 다리를 거치면 장치 state 가 `fault` 가 되어 Grafana '멈춤·고장 장치' 패널에 잡힌다(장표 054·056).
- 마름모 5 "명령이 다시 오나?" — 끊겼던 상위가 살아나 명령을 다시 보내면, 그 주기에 `take_latest_command` 가 `got_command_this_cycle_ = true` 로 만들고 `last_cmd_ns_` 가 갱신되어 stale 이 false 가 된다. 그러면 `update_state_machine` 의 else 가지에서 사건 COMMAND 를 넣는다(108~110줄). 화살표 글 "예 → 사건 COMMAND".
- 상자 6 "FAULT → RECOVERING / 좋은 주기를 센다 (good_cycles_)" — 전이표 `{FAULT, COMMAND, RECOVERING}`. 여기가 설계의 핵심이다: 명령이 한 번 왔다고 바로 RUNNING 으로 돌아가지 않는다. 네트워크가 깜빡이며 한 개만 왔다가 또 끊길 수 있기 때문이다. RECOVERING 상태에서는 stale 이 아닌 주기마다 `good_cycles_` 를 1씩 올린다(111~112줄).
- 마름모 7 "100주기(100 ms) 연속 정상?" — `good_cycles_ >= cfg_.recover_cycles`(기본 100, control_step.hpp 32줄: "1 kHz 에서 100 ms"). 100주기 연속으로 stale 이 아니면 사건 RECOVERED 를 넣는다(113~116줄). 중간에 한 번이라도 stale 이면 `good_cycles_ = 0` 으로 리셋되고 전이표 `{RECOVERING, WATCHDOG_TRIP, FAULT}` 로 다시 FAULT 다. 화살표 글 "예 → RECOVERED / 중간에 또 끊기면 FAULT".
- 녹색 상자 8 "READY → 다음 명령에 RUNNING / 전이표 밖의 조합은 전부 거부(illegal_events)" — `{RECOVERING, RECOVERED, READY}` 로 READY 가 되고, 다음 COMMAND 에 `{READY, COMMAND, RUNNING}` 으로 다시 움직인다. 전이표에 없는 조합(예: FAULT 상태에서 RECOVERED 사건)은 `handle()` 이 거부하고 `illegal_events` 를 센다 — 0 이어야 정상.

- 아래 상자: "코드: control_step.cpp check_watchdog(83-100) · update_state_machine(103-120), robot_state_machine.cpp 전이표(15-31). 11/03 실측: 명령 발행을 끊자 trips 1, 상태 FAULT → 재개 뒤 RECOVERING → READY. 실물에서는 FAULT 진입 때 토크 오프(Backend::safe_stop 자리)". 코드 위치 셋과, 11/03 노드 시험에서 실제로 이 경로를 밟았다는 기록, 그리고 실물에서 추가될 한 가지(토크 끄기)를 적었다.

- '다음 ▶' 다리: "마무리 — 가상 로봇(MuJoCo)에서 끝까지 갔다. 실물 SO-101 로 가면 무엇이 바뀌고 무엇이 그대로인가?"

## 3. 용어와 단위
- **워치독(watchdog)**: '감시견'. 일정 시간 안에 신호(여기서는 명령)가 안 오면 안전 동작을 하는 장치. 50 ms = 0.05초.
- **stale**: '오래된'. 마지막 명령이 기준 시간보다 오래됐다는 뜻의 bool 변수.
- **tripped**: 워치독이 '걸렸다'. 영어로 차단기가 내려간 상태를 trip 이라 한다.
- **상태 머신(state machine)**: 로봇이 있을 수 있는 상태 몇 개(INIT·READY·RUNNING·FAULT·RECOVERING)와, 어떤 사건(INIT_DONE·COMMAND·WATCHDOG_TRIP·RECOVERED·STOP)이 오면 어느 상태로 가는지를 표로 정한 것.
- **전이표(kTable)**: {지금 상태, 사건, 다음 상태} 한 줄이 화살표 하나. 16줄.
- **사건(event)**: 상태를 바꾸는 계기. 이 장표에는 WATCHDOG_TRIP, COMMAND, RECOVERED 세 가지가 나온다.
- **good_cycles_ / recover_cycles**: 복구 확인 중 연속으로 정상이었던 주기 수 / 그 기준값(100). 1 kHz 에서 100주기 = 100 ms.
- **illegal_events**: 전이표에 없는 (상태, 사건) 조합이 들어온 횟수. rt_status 에 나오며 0 이어야 한다.
- **rt_status**: 노드가 1초마다 내는 상태 JSON(단계 8). `watchdog`(ok/tripped), `state`, `watchdog_trips`, `illegal_events` 가 들어 있다.
- **토크 오프(torque off)**: 서보 모터의 힘을 끄는 것. 실물에서 FAULT 때 할 안전 동작(아직 자리만).

## 4. 쉬운 예시
- 비유: 무전기로 지시를 받으며 걷는 안내견 훈련. 지시(명령)가 20 ms 마다 오다가 50 ms 넘게 조용하면 개는 그 자리에 선다(멈춤, FAULT). 무전이 다시 들려도 바로 뛰지 않고, 100 ms 동안 끊김 없이 들리는지 확인한 뒤(RECOVERING → READY) 다음 지시에 다시 움직인다(RUNNING). 확인 중에 또 끊기면 처음부터 다시 선다.
- 숫자 예시: 명령이 50 Hz(20 ms 간격)로 오다가 t = 0 에서 끊겼다. 1 ms 마다 검사하므로 t = 51 ms 쯤에 `now - last_cmd > 50 ms` 가 참 → tripped, trips 1, FAULT. t = 300 ms 에 명령이 재개되면 그 주기에 COMMAND → RECOVERING. 그 뒤 100주기(t = 400 ms) 동안 20 ms 마다 명령이 계속 오면 stale 이 한 번도 안 되므로 RECOVERED → READY, 다음 명령에 RUNNING. 전체 복구 소요 ≈ 100 ms + 명령 한 간격.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 50 ms — `robots/so101.yaml` `safety.watchdog_ms: 50`; 코드 `cfg_.watchdog_ns`(control_step.cpp 84줄).
- 확인: 100주기 — `rt_control/rt_core/include/rt_core/control_step.hpp` 32줄 `recover_cycles = 100` 주석 "1 kHz 에서 100 ms".
- 확인: 전이표 16줄 — `rt_control/rt_core/src/robot_state_machine.cpp` 15~31줄 (`sed -n '15,31p'`).
- 확인: update_state_machine 103~120줄 — `sed -n '103,120p' rt_control/rt_core/src/control_step.cpp`.
- 확인: 11/03 실측 "워치독 tripped → ok → tripped, trips 1, step_limited 10" — `docs/LOG.md` 2026-11-03 노드 시험 결과 줄. 단위 테스트에서는 20 ms 워치독으로 끊김 → 멈춤, 재개 → 해제를 확인(같은 날 LOG).
- 다시 보려면 [WSL]: 노드를 띄우고 `ros2 topic pub -r 50 /joint_command …` 를 Ctrl+C 로 끊은 뒤 `ros2 topic echo /rt_status std_msgs/msg/String --once` 에서 `"watchdog": "tripped"`, `"state": "FAULT"`, `"watchdog_trips": 1` 을 본다. 다시 발행하면 0.1초 뒤 `READY`, 그 다음 `RUNNING`.
- 추정: "FAULT → 재개 뒤 RECOVERING → READY" 의 중간 상태를 1 Hz rt_status 로는 놓칠 수 있다(RECOVERING 은 100 ms 만 머문다). LOG 의 11/03 줄에는 tripped → ok 전환과 trips 1 이 기록돼 있고, 상태 이름의 순차 관측은 전이표와 단위 테스트(test_state_machine.cpp)로 보증한다.

## 6. 자주 하는 오해·함정
- "명령이 없는 주기는 전부 비정상인가?" — 아니다. 50 Hz 명령이면 1 kHz 루프의 19/20 주기는 명령이 없다. 비정상은 '50 ms 넘게' 없을 때만이다. 그래서 READY 상태에서 WATCHDOG_TRIP 이 와도 전이표는 READY 로 머문다("대기 중 명령 없음은 정상").
- "FAULT 에서 바로 RUNNING 으로 가면 안 되나?" — 전이표에 그 줄이 없다. 넣으려면 표에 한 줄 추가해야 하고, 그 전까지는 illegal 로 거부된다. 이것이 'if 문이 아니라 표'로 만든 이유다(장표 034·035).
- 워치독이 걸려도 RT 루프는 멈추지 않는다. 1 ms 마다 계속 돌며 '현재 위치'를 목표로 쓴다. 멈추는 것은 로봇의 움직임이지 제어 루프가 아니다.
- 시뮬레이션에서는 '위치 유지'가 안전하지만 실물 서보는 전원이 들어간 채 버티므로 과열·충돌 위험이 남는다. 그래서 실물에서는 FAULT 진입 때 토크 오프(`Backend::safe_stop`, 자리만 있음)가 필요하다 — DECISIONS 11/03(D1) 이유 줄.

## 7. 면접 한 문장
"명령이 50 ms 끊기면 지금 자리에 멈추고 FAULT, 명령이 다시 와도 100 ms 연속 정상이어야 READY — 전이표 밖의 길은 전부 막혀 있고, 11/03 노드 시험에서 trips 1 로 실제로 이 경로를 밟았다."
