# 장표 131 — 작성 방식 — AI(Claude)와 어떻게 일했나, 무엇이 작성자의 것인가
*위치: 7부 왜·사고·방식 · AI 와 일한 방식*

## 1. 이 장표가 왜 있나

앞 장표(130)의 일정표는 며칠(11/03~11/06 나흘과 11/10~11 이틀)에 코드·측정·문서·CI 가 다 나왔다고 말한다. 보는 사람은 당연히 "AI 가 다 한 것 아니냐"고 묻는다. 이 질문을 피하지 않고 **먼저** 답하는 장표다 — 왼쪽은 작성자(오문규)가 한 것, 오른쪽은 AI(Claude)가 한 것과 그것을 어떻게 검증했나. AI 가 쓴 커밋에는 `Co-Authored-By: Claude …` 꼬리줄이 있어 숨길 수도 없고 숨길 생각도 없다. 회사가 저장소를 AI 로 분석하면 1분 안에 보이는 사실이므로, 그것을 먼저 말하는 쪽이 신뢰를 얻는다는 판단이다(아래 각주). 다음 장표(132)는 "그래서 지원(11/17)까지 작성자가 직접 할 일"이다.

## 2. 장표를 하나씩 읽기

두 칸이다. 왼쪽 머리 "작성자(오문규)가 한 것", 오른쪽 머리 "AI 가 한 것 · 어떻게 검증했나".

왼쪽 네 줄:
- "무엇을 만들지·범위·일정(6주 → 2주, 뺀 것), git 전환, Pi 구매·세팅 결정": 목표 설정과 범위 결정. 6주 계획을 2주로 줄이며 무엇을 뺄지(DECISIONS 2026-11-03), 파일 전달을 git bundle 로 바꾼 것(11/04), 갖고 있던 Raspberry Pi 4 를 실측 환경으로 삼고 새 SD 카드를 사서 Ubuntu Server 24.04 를 올린 것(LOG 2026-11-04 밤) — 전부 작성자의 결정이다. 장표의 "Pi 구매"는 정확히는 카드 구매·세팅이다. AI 는 선택지를 냈을 뿐 결정하지 않았다.
- "모든 실행과 측정: WSL 과 Pi 에서 명령을 치고 출력을 읽고 다음 질문을 정함(수십 회)": AI 의 샌드박스에는 ROS 2·Docker·MuJoCo·실시간 커널이 없다. 저장소의 **측정 숫자**(표①②③, E01~E23 — 릴리스 카나리처럼 GitHub 러너가 만든 값은 러너의 결과 파일에서 옮겼다)는 작성자가 WSL · Pi · 서버에서 명령을 치고 출력을 붙여 준 것이고, 그 출력을 보고 "다음에 무엇을 재나"를 정한 것도 작성자다. LOG 의 "증상 → 원인 → 해결" 11건은 그 과정에서 나왔다.
- "판단: '왜 하는지와 결과 해석이 문서에 있어야 한다', '순서도에 기준이 있어야 논리가 선다', '측정 조건이 왜 이 조합인가', '녹화는 직접 치는 모습이어야', '장표도 순서도 논리로'": 저장소의 **형태**를 정한 다섯 판단. 첫째는 HANDOVER §2 의 11/05 문서 규칙(채팅 설명은 같은 날 GLOSSARY/EXPERIMENTS/LOG/DECISIONS 로), 둘째는 EXPERIMENTS 순서도의 마름모(기준)와 "왜 그 가지로 갔나", 셋째는 DECISIONS 2026-11-05 표① 조건 항목, 넷째는 영상을 녹화 자동화가 아닌 직접 타이핑 원테이크로(커밋 aace5da), 다섯째가 이 장표의 구조(DECISIONS 2026-11-05 (장표)).
- "검토: 읽기 가이드 29항목과 실험 페이지 25장을 교재로 분석 기간(5회차) + 혼자 하는 과제 3건(Co-Authored-By 없는 커밋)": 아직 남은 일이기도 하다(장표 132). `docs/READING_GUIDE.md` 의 29항목(파일별 "읽을 것·물을 것" — 27번째가 11/10 의 릴리스 → 배포 묶음, 28번째가 11/10~11 의 클라우드 운영 층·실물 장치 묶음, 29번째가 11/11 의 ZeroMQ · SDK 묶음)과 `docs/experiments/` 25장(E21 · E22 · E23 · E24 가 더해졌다)을 교재로 작성자가 다섯 번에 걸쳐 직접 설명해 보고, 각 회차 끝에 AI 없이 혼자 하는 과제(2 kHz 측정 줄 추가, 테스트 1개, 패널 1개 같은)를 3건 커밋한다 — 그 커밋에는 `Co-Authored-By` 가 없어서 이력에서 구분된다.

오른쪽 네 줄:
- "코드 초안·문서 초안·장표 초안. AI 가 쓴 커밋에 Co-Authored-By: Claude 표기(숨기지 않는다. 측정 결과·병합 커밋은 작성자 단독)": AI 가 한 것은 **초안**이다 — C++/파이썬 코드, 문서, 이 장표와 설명 문서. AI 가 쓴 커밋 메시지 끝에 `Co-Authored-By: Claude …` 줄이 있다(11/11 오전 기준 61개 중 51개 — 11/05 에는 43개 중 33개였다. 나머지는 측정 결과·병합·배지 커밋)(`git log --format=%B | grep -c Co-Authored-By`). README "작성 방식" 문단과 같다.
- "AI 의 샌드박스에는 ROS 2·Docker·MuJoCo 가 없어 가짜 위에서 논리만 검증 → 진짜 첫 실행은 항상 작성자의 WSL/Pi/서버 — 그때 깨진 것 11건(11/10~11 에 9건 더)이 LOG 에": AI 쪽 검증의 한계. 11/10 부터는 "진짜 환경"에 클라우드 서버가 더해졌고, 거기와 실물 Pi 에서 처음 돌리며 9건이 더 나왔다(장표 141) — 서버 설치 스크립트의 단계 하나, 장치가 거부당해도 화면이 정상과 같던 것, Pi 에서 에이전트가 안 뜨던 것 등은 샌드박스의 가짜 위에서는 나올 수 없는 종류다. 샌드박스는 네트워크가 막혀 Mosquitto·PostgreSQL·pip·MuJoCo 가 없고(LOG 2026-11-03 D3~D5), 가짜 브로커·가짜 DB(`fleet/tests/fake_mqtt.py`, `fake_psycopg.py`)와 MuJoCo 스텁 헤더로 문법·논리까지만 봤다. 진짜 환경의 첫 실행은 항상 작성자 쪽이었고, 거기서 깨진 11건(장표 128·129)이 그 증거다 — AI 가 다 했다면 LOG 가 비어 있어야 한다.
- "CI 가 매 push 마다 3잡을 다시 돌린다(AI 도 작성자도 아닌 제3의 검사원)": 셋째 검증자. GitHub 러너는 매번 새 가상 머신이라 작성자의 PC 상태도 AI 의 샌드박스 상태도 가져가지 않는다. 그 CI 가 작성자를 두 번 잡았다(장표 120·122).
- "면접 한 문장: 'AI 를 코드 초안과 문서화에 썼고, 무엇을 만들지·무엇을 재고 어떻게 판단할지·결과가 맞는지는 제가 했습니다. 어느 파일이든 열어서 물어보셔도 됩니다'": 마지막 문장이 핵심이다 — 설명할 수 있어야 자기 것이고, 그래서 분석 기간이 있다.

각주 "README '작성 방식' 문단, docs/HANDOVER.md §2. 회사가 AI 로 검증하면 1분 안에 보이는 것을 먼저 말하는 쪽이 신뢰를 얻는다": 출처 둘과 이 장표를 만든 이유.

## 3. 용어와 단위

- `Co-Authored-By`: git 커밋 메시지 끝에 공동 작성자를 적는 관례 줄. GitHub 가 커밋 화면에 두 번째 아바타로 보여 준다. 지우거나 숨길 수 있지만 그러지 않았다.
- 샌드박스(sandbox): AI 가 코드를 쓰고 돌려 보는 격리된 리눅스 환경. 네트워크가 막혀 있고 ROS 2·Docker·MuJoCo·RT 커널이 없다.
- 초안(draft)과 실행(run): 초안은 "이렇게 하면 될 것"이라는 코드·문서. 실행은 진짜 환경에서 돌려 숫자를 얻는 일. 이 저장소에서 둘은 사람이 다르다.
- 가짜 모듈(fake): 테스트용으로 진짜 브로커·DB 의 흉내만 내는 파이썬 파일. 논리는 검사하지만 타이밍·초기화 같은 환경 문제는 못 잡는다.
- 분석 기간(5회차)·혼자 하는 과제 3건: 지원 전 작성자가 장표로 직접 설명해 보는 다섯 번의 세션과, AI 없이 커밋하는 작은 과제 셋. 아직 **남은 일**이다.
- 읽기 가이드 29항목: `docs/READING_GUIDE.md` 의 표 — 파일(묶음) 29개마다 줄 수, 읽을 것, 면접에서 물을 것.

## 4. 쉬운 예시

- 비유: 건축에서 설계 사무소(AI)가 도면 초안을 그려도, **무슨 집을 어디에 얼마짜리로** 지을지 정하고, 공사 현장(WSL·Pi)에서 직접 돌려 보고, 무너진 곳(11건, 그 뒤 9건 더)을 고친 사람이 건축주다. 준공 검사(CI)는 제3자가 한다. 도면에 사무소 이름(Co-Authored-By)을 지우지 않는다.
- 숫자 예시: 저장소의 모든 측정값은 작성자의 환경에서 나왔다 — 표① Pi 4 실측 14줄, 표② 16조합, 표③ 장애 4종 2회차, E01~E24 25장. AI 샌드박스에서 나온 숫자는 "일반 환경 참고값"으로만 표시된 D0 의 한 줄(p99.9 2,568 us)뿐이고, 그것도 표에서 참고값으로 분리돼 있다.
- "AI 가 다 했다면": LOG 의 20건(11 + 9)이 비어 있어야 하고, 사고 3건을 잡은 CI 도 필요 없었을 것이다. 반대로 사고가 있다는 것이 "진짜 환경에서 사람이 돌렸다"의 증거다.

- 확인: 샌드박스 한계 — `docs/LOG.md` 2026-11-03 (D3~D5, 샌드박스 작업) "샌드박스에는 Mosquitto·PostgreSQL·pip·MuJoCo 가 없다(네트워크 차단) … 진짜 물리 위 실행은 WSL/CI 가 처음이다".

- 추정: "혼자 하는 과제 3건"의 구체 내용(2 kHz 측정 줄, 테스트 1개, 패널 1개)은 장표 132 의 예시이고, 저장소 문서에는 "분석 기간 5회차"만 적혀 있다 — 과제 3건은 계획이다.
- 다시 보는 법 [WSL 창]: `git log --format=%B | grep -c "Co-Authored-By"`(공동 작성 커밋 수), `git log --format=%B | grep -c "^"` 와 비교. 분석 기간 뒤에는 `git log --format="%h %s%n%b" | grep -B1 -v Co-Authored` 로 혼자 한 커밋을 찾을 수 있다.

## 6. 자주 하는 오해·함정

- "AI 를 썼다고 말하면 손해"라는 오해: 커밋 이력에 전부 적혀 있어 숨길 수 없고, 회사가 AI 로 저장소를 분석하면 1분 안에 보인다. 먼저 말하고 "무엇이 내 것인가"를 구분해 보여 주는 쪽이 낫다는 것이 이 장표의 전제다.
- "AI 가 코드를 썼으니 AI 가 검증도 했다": AI 는 진짜 환경을 못 돌렸다. 검증은 작성자(WSL·Pi·서버 실행)와 CI(러너) 둘이 했고, 그 결과가 LOG 의 20건과 CI 가 잡은 3건이다.
- "설명할 수 있다"를 지금 시점의 완료로 말하지 않는다: 분석 기간 5회차는 **남은 일**(장표 132)이다. 발표에서는 "그래서 분석 기간을 두었다"로 말한다.
- Co-Authored-By 가 없는 커밋이 "AI 를 안 쓴 커밋"의 증명은 아니다 — 작성자가 그렇게 운영한다는 **약속**이고, 과제 3건 뒤에 이력으로 확인된다.
- 샌드박스에서 돌아간 가짜 테스트(초록)를 진짜 환경의 통과로 말하지 않는다 — 11/05 CI 2차 사고가 그 차이의 실례다.

## 7. 면접 한 문장

"AI 를 코드 초안과 문서화에 썼고 AI 가 쓴 커밋에는 전부 표기했습니다 — 무엇을 만들지, 무엇을 재고 어떻게 판단할지, 결과가 맞는지는 제가 했고, 진짜 환경의 첫 실행은 전부 제 WSL 과 Pi, 그리고 서버였기 때문에 깨진 20건이 LOG 에 있습니다. 어느 파일이든 열어서 물어보셔도 됩니다."
