# 장표 035 — 단계 5 — 상태 머신 코드 (2/2) — 표를 훑어 맞는 줄이 있으면 바꾸고, 없으면 센다 (handle)
*위치: 1부 로봇을 움직이는 길 · 단계 5/10 제어 단계(안전) · ② 코드 — handle()*

## 1. 이 장표가 왜 있나
바로 앞 장표(034)에서 상태 머신의 전이표 `kTable` 을 봤다. 전이표는 "지금 상태 + 사건 → 다음 상태"를 한 줄에 하나씩 적은 표였고, 표에 없는 조합은 전부 불법이라고 했다. 그러면 자연히 질문이 생긴다 — "그 표를 실제로 누가, 어떻게 읽어서 상태를 바꾸나? 표에 없는 조합이 들어오면 정말 아무 일도 안 일어나나?" 이 장표가 그 답이다. `handle()` 한 함수(13줄)가 표를 처음부터 끝까지 훑어 맞는 줄을 찾고, 있으면 상태를 바꾸고, 없으면 "불법 사건" 수만 하나 올리고 상태는 그대로 둔다. 제어 단계(단계 5)의 안전 장치 셋(최신 명령 · 워치독 · 변화량 제한) 중 상태 머신은 "로봇이 지금 어떤 상태인가"를 한 곳에서 책임지는 부품이고, 이 함수가 그 부품의 전부다.

## 2. 장표를 하나씩 읽기
파일 위치는 `rt_control/rt_core/src/robot_state_machine.cpp:34-46` 이다. 장표의 코드를 줄마다 짚는다(줄 번호는 파일 기준).

- 34줄: `bool RobotStateMachine::handle(RobotEvent e) {` — 사건(이벤트) `e` 하나를 받아 처리하고, 처리했으면 `true`, 표에 없어서 무시했으면 `false` 를 돌려주는 함수다. `RobotEvent` 는 사건 다섯 가지(INIT_DONE · COMMAND · WATCHDOG_TRIP · RECOVERED · STOP) 중 하나를 뜻하는 열거형(이름 붙은 정수)이다.
- 35줄: `for (std::size_t i = 0; i < kTableSize; ++i) {` — 전이표를 0번 줄부터 끝까지 차례로 본다. `kTableSize` 는 앞 장표의 32줄에서 `sizeof(kTable) / sizeof(kTable[0])` 로 계산한 줄 수다. 표가 16줄이므로 최악의 경우 16번 비교한다.
- 36줄: `if (kTable[i].from == state_ && kTable[i].event == e) {` — 이 줄의 "출발 상태"가 지금 상태(`state_`)와 같고, "사건"이 들어온 사건 `e` 와 같은가? 둘 다 맞아야 이 줄이 "지금 적용할 화살표"다. 정수 두 개를 비교하는 일이라 매우 싸다.
- 37~39줄: `if (kTable[i].to != state_) { transitions_ = transitions_ + 1; }` — 도착 상태가 지금 상태와 다를 때만 "상태가 바뀐 횟수"(`transitions_`)를 하나 올린다. 표에는 READY→READY, RUNNING→RUNNING 처럼 자기 자신으로 가는 줄도 있는데(앞 장표), 그런 경우는 상태가 바뀐 것이 아니므로 세지 않는다. 이 숫자가 rt_status 의 `state_transitions` 다.
- 40줄: `state_ = kTable[i].to;` — 상태를 표의 도착 상태로 바꾼다. 자기 자신으로 가는 줄이면 같은 값을 다시 넣는 셈이라 아무 변화가 없다.
- 41줄: `return true;` — 처리했다고 알리고 바로 함수를 끝낸다. 표에서 맞는 줄을 하나 찾으면 뒤의 줄은 보지 않는다(표에 같은 조합이 두 번 있을 수 없다는 전제).
- 42~43줄: `}` `}` — if 와 for 가 닫힌다. 여기까지 왔다는 것은 표 16줄 중 어느 것도 맞지 않았다는 뜻이다.
- 44줄: `illegal_ = illegal_ + 1;  // 표에 없는 조합: 상태를 바꾸지 않는다` — 불법 사건 수를 하나 올린다. 상태(`state_`)는 건드리지 않는다. 이 값이 rt_status 의 `illegal_events` 이고, 정상 운전 중에는 0 이어야 한다.
- 45줄: `return false;` — 무시했다고 알린다. 부르는 쪽(제어 단계)은 이 반환값을 따로 쓰지 않지만, 단위 테스트가 "불법 사건은 false 를 돌려준다"를 확인한다.
- 46줄: `}` — 함수 끝.

장표 오른쪽 "읽는 포인트"를 하나씩 풀면:

- "표를 처음부터 훑어 … 줄 수가 16개라 매 주기 정수 비교 16번이 최악" — 이 함수는 1 ms 마다 도는 RT 스레드 안에서 불린다. 실행 시간이 늘 일정해야 하는데, 16줄짜리 표를 정수 비교로 훑는 일은 아무리 길어도 수십 ns 수준이라 1 ms 예산 안에서 무시할 만하다. 해시 맵 같은 더 "빠른" 자료구조를 쓰지 않은 이유이기도 하다 — 줄 수가 작을 땐 단순한 쪽이 더 예측 가능하다.
- "맞는 줄이 있으면 상태를 바꾸고 true. 자기 자신으로의 전이는 transitions 를 세지 않는다" — 37~41줄의 설명 그대로다. READY 에서 명령 없이 기다리는 것(READY→READY)을 "전이"로 세면 숫자가 매 주기 늘어나 의미가 없어진다.
- "없으면 illegal_ +1 하고 false — rt_status 의 illegal_events. 0 이어야 정상(11/05 실측 0)" — 표 밖의 조합은 코드 어딘가에서 사건을 잘못 넣고 있다는 신호다. 그래서 숫자로 바깥에 내보내고(단계 8 의 rt_status), 0 이 아니면 즉시 의심한다.
- "RT 스레드에서 매 주기 불린다: 할당·락·예외 없음" — 메모리 할당(new), 뮤텍스 같은 락, 예외 던지기는 모두 실행 시간을 예측 불가능하게 만든다. 이 함수에는 정수 비교와 대입뿐이다.
- "단위 테스트: test_state_machine.cpp — 정상 전이와 불법 전이 거부를 둘 다 확인" — `rt_control/rt_core/test/test_state_machine.cpp` 가 INIT→READY→RUNNING→FAULT→RECOVERING→READY 를 순서대로 밟아 보고, RUNNING 에서 INIT_DONE·RECOVERED 같은 불법 사건을 넣었을 때 상태가 그대로이고 `illegal_events()` 가 2 늘어나는지, FAULT 에서 COMMAND 가 RUNNING 이 아니라 RECOVERING 으로 가는지까지 확인한다.

이 함수를 누가 부르나(장표 밖이지만 이해에 필요): `control_step.cpp` 의 `update_state_machine()`(103~122줄)이 매 주기 사건을 넣는다 — 명령이 끊겼으면 `WATCHDOG_TRIP`, 이번 주기에 명령이 왔으면 `COMMAND`, RECOVERING 상태에서 정상 주기가 `recover_cycles`(기본 100, 1 kHz 에서 100 ms)만큼 연속이면 `RECOVERED`. 시작할 때 한 번 `INIT_DONE` 을 넣는다(21줄). 그리고 `transitions()` 와 `illegal_events()` 값을 `counters_` 의 원자 변수에 복사해(120~121줄) ROS 2 쪽이 1 Hz 로 읽게 한다.

## 3. 용어와 단위
- 상태 머신(state machine): "지금 상태"와 "들어온 사건"으로 "다음 상태"를 정하는 장치. 이 저장소에서는 상태 5개(INIT · READY · RUNNING · FAULT · RECOVERING), 사건 5개.
- 전이(transition): 상태가 다른 상태로 바뀌는 것. 전이표는 허용된 전이를 전부 적은 표.
- 불법 사건(illegal event): 표에 없는 (상태, 사건) 조합. 코드 논리 오류의 신호. 카운터 이름 `illegal_events`.
- 열거형(enum class): `RobotState::READY` 처럼 이름을 붙인 정수. 비교가 정수 비교라 빠르다.
- `std::size_t`: 배열 크기·첨자를 담는 부호 없는 정수 타입.
- `return true/false`: 함수가 돌려주는 참/거짓. 여기서는 "처리했다/무시했다".
- RT 스레드: 실시간(real-time) 우선순위로 1 ms(= 1,000 us)마다 도는 스레드. 이 안에서 불리는 코드는 실행 시간이 짧고 일정해야 한다.
- `recover_cycles` = 100 주기: 1 kHz(1초에 1,000번)에서 100 주기 = 100 ms = 0.1초.

## 4. 쉬운 예시
비유 — 회사 출입문의 카드 규칙표: "외부인 상태에서 '방문증 발급' 사건이 오면 방문자 상태로", "방문자 상태에서 '퇴실' 사건이 오면 외부인 상태로" 처럼 허용된 경우만 적힌 규칙표가 있다. 경비(`handle`)는 카드가 찍힐 때마다 표를 위에서부터 훑어 "지금 상태 + 이 사건"에 맞는 줄을 찾는다. 있으면 상태를 바꾸고 문을 연다(`true`). 없으면(예: 외부인이 임원실 문을 찍음) 문은 그대로 두고 "이상 시도 1건"만 기록한다(`illegal_ + 1`, `false`). 표에 "방문자 → 방문자(같은 층 이동)" 같은 줄도 있지만 그건 "상태가 바뀐 횟수"에 넣지 않는다.

숫자 예시 — 로봇이 RUNNING 상태에서 50 Hz 명령을 받고 있다가 명령이 끊겼다고 하자. 50 ms(= 50 주기) 뒤 워치독이 `WATCHDOG_TRIP` 을 넣는다 → 표 5번째 줄(RUNNING + WATCHDOG_TRIP → FAULT)이 맞아 `state_ = FAULT`, `transitions_` 가 1 늘어난다. 그 뒤 매 주기 또 `WATCHDOG_TRIP` 이 오지만 FAULT + WATCHDOG_TRIP → FAULT(자기 자신)라서 `transitions_` 는 더 늘지 않는다. 명령이 다시 오면 FAULT + COMMAND → RECOVERING(+1), 100 주기(100 ms) 연속 정상이면 RECOVERED 가 들어와 RECOVERING + RECOVERED → READY(+1). 전부 합쳐 `state_transitions` 는 3 이 늘고 `illegal_events` 는 0 그대로다.

## 6. 자주 하는 오해·함정
- "for 문으로 표를 훑으면 느리지 않나?" — 16줄 정수 비교는 수십 ns 다. 1 ms 예산의 0.01% 도 안 된다. 오히려 복잡한 자료구조가 실행 시간을 예측하기 어렵게 만든다.
- "불법 사건이 들어오면 로봇이 멈추나?" — 아니다. 상태를 바꾸지 않고 숫자만 올린다. 멈춤은 워치독(단계 5 ②)이 목표를 현재 위치로 바꿔서 만들고, 상태 머신은 그 사실을 FAULT 라는 이름으로 기록할 뿐이다.
- "READY 에서 명령이 안 오면 FAULT 아닌가?" — 아니다. 표에 READY + WATCHDOG_TRIP → READY 가 있다. 대기 중에 명령이 없는 것은 정상이다. FAULT 는 "움직이던 중(RUNNING)에 끊겼을 때"만이다.
- "FAULT 에서 명령이 다시 오면 바로 RUNNING?" — 아니다. RECOVERING 을 거쳐 100 주기 연속 정상이어야 READY 가 되고, 그다음 명령에 RUNNING 이 된다. 단위 테스트 48줄이 바로 이 점을 확인한다.

## 7. 면접 한 문장
"상태 머신은 if 문 더미가 아니라 전이표 하나와 13줄짜리 handle 함수입니다 — 표에 없는 조합은 상태를 못 바꾸고 illegal_events 로 세어져 바깥(rt_status)에 보이기 때문에, 'FAULT 에서 바로 RUNNING 이 되나요?' 같은 질문에 표 한 줄로 답할 수 있습니다."
