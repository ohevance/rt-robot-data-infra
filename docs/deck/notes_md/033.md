# 장표 033 — 단계 5 — 상태 머신 — 로봇이 지금 어떤 상태이고 어떤 일이 생기면 어디로 가나
*위치: 1부 로봇을 움직이는 길 · 단계 5/10 제어 단계(안전) · ② 구조 — 상태 머신 그림*

## 1. 이 장표가 왜 있나
- 세 위험 중 마지막 **불법 상태 전이**를 막는 장치가 상태 머신이다. 워치독(031)이 "끊겼다/살아 있다"를 매 주기 판정하지만, 그것만으로는 "끊겼다가 돌아온 직후"와 "원래 정상"을 구분할 수 없다. 로봇이 지금 어떤 **상태**인지와, 어떤 **사건**이 오면 어디로 가는지를 그림 하나로 정한 것이 이 장표다.
- 그림은 `rt_control/rt_core/include/rt_core/robot_state_machine.hpp` 머리말의 ASCII 그림과 `robot_state_machine.cpp` 의 전이표 `kTable` 을 Mermaid 로 그린 것이다. 그림의 화살표 하나 = 코드의 표 한 줄, 1:1 이다. 다음 두 장표(034·035)가 그 코드다.
- 상태 머신은 안전 장치이면서 **관측 창**이기도 하다. rt_status 의 `state` 가 이 상태의 이름이고, 관제 대시보드(2부)와 기록(단계 9)에 그대로 실린다.

## 2. 장표를 하나씩 읽기
**그림의 상태(동그라미) 5개**
- **INIT** — 켜진 직후, 백엔드(로봇) 준비 중. 숫자로는 0.
- **READY** — 준비 끝, 명령을 기다림. 움직이지 않는다. 1.
- **RUNNING** — 명령을 따라 움직이는 중. 2.
- **FAULT** — 워치독으로 멈춤. 지금 자리를 유지. 3.
- **RECOVERING** — 명령이 다시 와서 복구를 확인하는 중. 좋은 주기 100번 연속이면 READY. 4.

**그림의 화살표(사건) — 전이표 15줄 (+ 시작 표시 하나)**
- `[*] → INIT`: 시작. `INIT → READY : INIT_DONE` — 백엔드 준비가 끝나면(ControlStep 생성자에서 넣는다).
- `READY → RUNNING : COMMAND` — 첫 명령이 오면 움직이기 시작. `READY → READY : WATCHDOG_TRIP` — 대기 중에 명령이 없는 것은 **정상**이라 자기 자신으로 돈다(FAULT 가 아니다).
- `RUNNING → RUNNING : COMMAND` — 계속 움직임. `RUNNING → FAULT : WATCHDOG_TRIP` — 움직이던 중 50 ms 끊기면 고장.
- `FAULT → FAULT : WATCHDOG_TRIP` — 계속 끊겨 있음. `FAULT → RECOVERING : COMMAND` — 명령이 다시 오면 **바로 RUNNING 이 아니라** 복구 확인으로.
- `RECOVERING → RECOVERING : COMMAND` — 확인 중. `RECOVERING → FAULT : WATCHDOG_TRIP` — 확인 중 또 끊기면 다시 고장. `RECOVERING → READY : RECOVERED` — 좋은 주기 100번(100 ms) 연속이면 준비 상태로. 그 다음 명령에서 RUNNING.
- `어느 상태 → INIT : STOP` — 5줄. 정지/재시작 요청은 어디서든 처음으로.

**아래 글머리표 5줄**
- 상태 5개·사건 5개의 이름.
- "표(전이표)에 없는 조합은 전부 '불법'으로 막고 센다(illegal_events, 0 이어야 정상)". 예: RUNNING 에서 INIT_DONE, FAULT 에서 RECOVERED. 상태는 바뀌지 않고 카운터만 오른다.
- "FAULT 에서 바로 RUNNING 으로는 못 간다" — 그림에 그 화살표가 없다. 끊김 직후 한 번 온 명령이 진짜 복구인지 알 수 없으므로 100 ms 를 본다.
- "RT 스레드에서 매 주기 불린다 — 정수 비교뿐" — 표를 훑는 것은 최대 15번의 정수 비교 두 개씩. 할당·락·파일 없음.

## 3. 용어와 단위
- **상태 머신(finite state machine, FSM)**: 유한한 상태 집합과, (상태, 사건) → 다음 상태 규칙으로 동작을 정하는 모형. 신호등(빨강→초록→노랑)이 가장 쉬운 예.
- **상태(state)** / **사건(event)** / **전이(transition)**: 지금 어디 / 무슨 일 / 어디로 가나.
- **전이표(transition table)**: 전이를 `{from, event, to}` 줄로 나열한 표. if 문 대신 쓴다(DECISIONS D3).
- **불법 사건(illegal event)**: 표에 없는 (상태, 사건). `illegal_events` 카운터. 0 이어야 정상.
- **recover_cycles = 100**: RECOVERING 에서 READY 로 가기 위해 필요한 연속 정상 주기 수. 1 kHz 에서 100 ms.
- **state_transitions**: 상태가 실제로 바뀐 횟수(자기 자신으로 도는 것은 세지 않는다). rt_status 에 실린다.
- **enum class … : uint8_t**: 상태·사건을 1바이트 정수로 정의한 것. 벨트와 rt_status 에 작은 정수로 싣고, 이름은 `robot_state_name()` 으로 바꾼다.

## 4. 쉬운 예시
- **공장 기계의 안전 운전 비유**: 전원을 켜면 **점검 중(INIT)** → 점검 끝 **대기(READY)** → 작업 지시가 오면 **가동(RUNNING)**. 가동 중 조작반과 연락이 끊기면 **비상 정지(FAULT)**, 그 자리에 멈춤. 연락이 돌아와도 바로 가동하지 않고 **복구 확인(RECOVERING)** 을 거쳐 100 ms 동안 연락이 안정적이면 대기로 돌아간다. 복구 확인 중에 또 끊기면 다시 비상 정지. 비상 정지 버튼(STOP)은 어느 상태에서든 점검 중으로 되돌린다. 대기 중에 지시가 없는 것은 고장이 아니다(READY → READY).
- **숫자 예시**: 50 Hz 명령으로 RUNNING 중 발행을 끊으면 약 50~70 ms 뒤 FAULT. 다시 켜면 첫 명령에서 RECOVERING, 그 뒤 100주기(100 ms) 동안 끊김이 없으면 READY, 그 다음 명령(최대 20 ms 뒤)에 RUNNING. 끊김부터 RUNNING 복귀까지 약 120 ms. 그동안 `state_transitions` 는 4(RUNNING→FAULT, FAULT→RECOVERING, RECOVERING→READY, READY→RUNNING) 늘고 `illegal_events` 는 0 이다.

## 6. 자주 하는 오해·함정
- "READY 에서 명령이 없으면 FAULT 다" — 아니다. 대기 중 명령 없음은 정상이라 READY 에 머문다. FAULT 는 **움직이던 중(RUNNING)** 끊긴 경우와 복구 확인 중 끊긴 경우뿐이다.
- "FAULT 에서 명령이 오면 바로 움직인다" — 아니다. RECOVERING 100 ms 를 거친다. 그동안 로봇은 워치독이 풀려 명령을 따르기는 하지만(`tripped_ = false`), 상태 이름은 RECOVERING 이라 관제에서 "방금 끊겼다 돌아온 로봇"으로 보인다.
- "불법 사건이 생기면 프로그램이 죽는다" — 아니다. 상태를 바꾸지 않고 숫자만 올린다. RT 스레드에서 예외나 종료는 더 위험하다. 0 이 아니면 코드 버그라는 신호로 읽는다.
- "상태 머신은 그림일 뿐이다" — 그림의 화살표가 코드의 표 줄과 1:1 이라 그림이 곧 코드다. 화살표를 하나 더 그리고 싶으면 표에 한 줄 더하는 것이 전부다(034).

## 7. 면접 한 문장
"상태 5개·사건 5개를 전이표 15줄로 정했고 그림의 화살표와 1:1 입니다 — FAULT 에서 명령이 와도 바로 RUNNING 이 아니라 RECOVERING 100주기를 거치고, 표에 없는 조합은 상태를 바꾸지 않고 illegal_events 로 세어 0 인지 늘 봅니다."
