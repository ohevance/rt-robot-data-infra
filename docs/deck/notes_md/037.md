# 장표 037 — 단계 6 들머리 — 백엔드가 로봇에 쓴다: 로봇을 바꿔도 제어 코드는 그대로
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ① 들머리*

## 1. 이 장표가 왜 있나
- 단계 5 까지로 "안전한 목표" 가 만들어졌다. 우편함에서 꺼낸 최신 명령에 워치독과 변화량 제한을 거친 값, 코드에서는 `applied_` 라는 배열이다. 그다음 질문은 당연히 "그 값을 **누가 로봇에 쓰나**?" 다.
- 그런데 이 저장소에는 로봇이 하나가 아니다. 수식 한 줄짜리 가짜 로봇(SimLag), 물리 엔진 위의 로봇(MuJoCo), 그리고 언젠가 붙일 실물(Feetech 서보). 로봇마다 제어 코드를 따로 쓰면 코드도 테스트도 세 벌이 된다. 그래서 단계 6 의 문제는 "로봇을 바꿔도 제어 코드는 그대로 두려면 어떤 **경계(인터페이스)** 를 그어야 하나" 다.
- 들머리 장표는 단계마다 같은 꼴이다: 들어온 것 → 문제 → 기준 → 확인 방법 → 결과 → 판단. 이 한 장만 보면 단계 6 이 왜 필요하고 무엇을 넘어야 다음으로 가는지 알 수 있고, 뒤따르는 코드 장표(039~043)는 그 근거다.

## 2. 장표를 하나씩 읽기
여섯 상자를 순서대로(왼쪽 위에서 오른쪽으로, 아래 줄은 오른쪽에서 왼쪽으로).
- **들어온 것**(회색 상자): "안전 검사를 거친 목표 applied_ (단계 5)". 단계 5 의 산출물이 그대로 들어온다. `desired_`(상위가 원하는 값)가 아니라 `applied_`(제한을 거친 값)라는 점이 중요하다 — 로봇에 실제로 가는 값은 항상 후자다.
- **문제**(민트 상자): "로봇이 셋이다 — SimLag(1차 지연 모델) · MuJoCo(물리) · 실물(Feetech 서보). 로봇마다 제어 코드를 고치면 세 벌이 되고 테스트도 세 벌". 핵심은 유지보수 비용이다. 제어 코드(워치독·변화량 제한·상태 머신)는 로봇과 무관한 논리인데, 로봇별로 복사해 두면 한 군데 버그를 고칠 때 세 군데를 고쳐야 한다.
- **기준**(마름모): 두 가지를 묻는다. 첫째, "Backend 세 함수(init · write_command · read_state)만으로 충분한가?" — 경계가 너무 작으면 로봇마다 예외가 필요해지고, 너무 크면 교체가 어려워진다. 둘째, "RT 스레드 안에서 할당·대기 없이 한 주기 비용이 1 ms 의 10% 아래인가?" — 백엔드가 아무리 깔끔해도 물리 계산이 한 주기(1 ms)의 큰 몫을 먹으면 깨어남 지연(표①)과 합쳐 주기를 넘길 수 있다. 10% 라는 숫자는 "나머지 90% 는 깨어남 지연과 제어 계산에 남겨 두자" 는 여유 기준이다(E15 의 엄격 기준; 테스트 코드의 합격선은 p99 < 900 us 로 더 느슨하다).
- **확인 방법**(파란 상자): 세 가지. ① 11/04 에 SimLag → MuJoCo 로 바꿀 때 제어 코드가 몇 줄 바뀌었는지 센다(0 줄이어야 한다). ② `test_mujoco_backend` 로 2,000주기(1 kHz 로 2초)를 돌려 한 주기 비용의 p50/p99/max 를 잰다(E15). ③ `robots/so101.yaml` 한 파일로 우리 쪽 관절 이름과 모델 안 관절 이름을 잇는다(장표 043).
- **결과**(보라 테두리 상자): "제어 코드 무변경. 물리 한 주기 p50 6.4 / p99 8.5 / max 29.4 us(러너) = 1 ms 의 0.9%. 모델 걸음 2 ms → 1 ms 로 자동 조정". 세 숫자는 GitHub 러너(CI)에서 잰 값이다. p99 8.5 us ÷ 1,000 us = 0.85% ≈ 0.9%. 마지막 문장은 장표 042 의 `tune_timestep` 이야기 — 모델 파일의 기본 걸음이 2 ms 인데 제어 주기가 1 ms 라서 걸음을 1 ms 로 줄여 주기마다 한 번 밟는다.
- **판단 → 다음**(진한 상자): 두 기준을 모두 넘었으니 통과. 목표가 MuJoCo 액추에이터에 들어갔으니, 다음 단계 7 의 질문은 "로봇은 실제로 어떻게 움직였나" 다.

아래 상자(이 단계의 장표): 인터페이스(039) · SimLag(040) · MuJoCo 쓰기/읽기(041) · 걸음 맞추기(042) 코드 4장과 로봇 프로필 YAML(043) 1장. "넘어가는 조건: 백엔드 교체가 '파일 하나 바꾸기' 였고, 물리 비용이 예산 안" — 이 두 문장이 단계 6 의 합격 조건이다.

## 3. 용어와 단위
- **백엔드(backend)**: 여기서는 "로봇 쪽 구현". 제어 단계가 목표를 건네면 실제로 모터를 움직이거나(실물), 움직인 척하거나(SimLag), 물리로 계산하는(MuJoCo) 부분.
- **인터페이스(interface)**: 함수 이름·인자·역할만 정해 둔 약속. C++ 에서는 순수 가상 함수(`= 0`)만 있는 클래스. 약속만 지키면 구현은 무엇이든 끼울 수 있다.
- **SimLag(1차 지연 모델)**: `위치 += (목표 − 위치) × 상수` 한 줄로 "서서히 따라가는" 성질만 흉내 내는 가짜 로봇. 중력·충돌 없음.
- **MuJoCo**: Google DeepMind 의 물리 엔진. 관절·질량·모터를 적은 모델 파일(XML)을 읽어 뉴턴 역학으로 움직임을 계산한다.
- **Feetech 서보**: 실물 SO-101 로봇팔에 들어가는 소형 서보 모터(STS3215). 시리얼 통신으로 명령을 받는다.
- **RT 스레드 안에서 할당·대기 금지**: 메모리를 새로 잡거나(malloc), 락·파일·네트워크를 기다리는 일은 시간이 얼마나 걸릴지 모른다. 1 ms 안에 반드시 끝나야 하는 스레드에서는 금지.
- **p50 / p99 / max**: 2,000번 잰 값을 정렬했을 때 가운데 / 99% 지점 / 가장 큰 한 번. 제어에서는 평균이 아니라 p99 와 max 로 판단한다.
- **us(마이크로초)**: 1/1,000,000 초. 1 ms = 1,000 us. 8.5 us 는 1 ms 의 0.85%.
- **걸음(timestep)**: 물리 엔진이 한 번에 진행시키는 시간. 2 ms 걸음 = 한 번 계산에 세상이 2 ms 흐른다.

## 4. 쉬운 예시
- 비유: **콘센트 규격**. 가전제품(제어 코드)은 "두 구멍 플러그" 라는 약속만 지키면 어느 집(로봇)에서든 꽂힌다. 집이 달라도 가전을 뜯어고치지 않는다. Backend 의 세 함수가 그 플러그 규격이다. 규격이 세 개뿐이라는 점이 중요하다 — 구멍이 열 개짜리 규격이면 새 집마다 맞추기 어렵다.
- 숫자 예시: 1 ms 예산을 1,000원이라 하자. 물리 계산은 p99 기준 8.5원(0.85%)을 쓴다. 깨어남 지연은 Pi 4 격리 조건에서 최악 189원(장표 094). 둘을 합쳐도 약 200원 — 800원이 남는다. 기준 "10% 아래(100원 아래)" 는 넉넉히 통과. 만약 물리가 300원을 썼다면 깨어남 189원과 합쳐 489원, 아직 1,000원 안이지만 2 kHz(500원 예산)로 올리는 순간 깨진다 — 그래서 여유 기준을 10% 로 잡았다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: p50 6.4 / p99 8.5 / max 29.4 us — `docs/measurements/mujoco_backend_ci.json` 의 `step_us`(CI `mujoco` 잡이 만든 파일, `cycles: 2000`, `substeps: 1`). 해석은 `docs/experiments/E15.md` 3절.
- 확인: WSL 단독 테스트는 4.9 / 6.3 / 20.8 us — `docs/LOG.md` 2026-11-04 (D5 MuJoCo). 환경이 달라도 같은 급이다.
- 확인: 제어 코드 무변경 — `docs/experiments/E15.md` 4-3 "제어 코드(control_step.cpp)와 노드는 한 줄도 안 바뀌고", `docs/DECISIONS.md` 2026-11-03 (D5).
- 확인: 걸음 2 ms → 1 ms — 노드 시작 로그 "제어 주기 1.000 ms = mj_step 1번 x 1.000 ms"(`mujoco_backend.cpp` `print_mapping`), `mujoco_backend_ci.json` 의 `substeps: 1`.
- 다시 재는 법: `bash scripts/get_mujoco.sh` 로 MuJoCo 와 모델을 받고, `cmake -S rt_control/rt_core -B build/rt_core_mj -DCMAKE_BUILD_TYPE=Release -DRT_CORE_WITH_MUJOCO=ON -DMUJOCO_DIR=$PWD/third_party/mujoco && cmake --build build/rt_core_mj -j`, 그다음 `RT_MUJOCO_MODEL=$PWD/third_party/mujoco_menagerie/trs_so_arm100/scene.xml ctest --test-dir build/rt_core_mj --output-on-failure`(E15 2절).

## 6. 자주 하는 오해·함정
- "물리 시뮬레이션은 무겁다" — 6자유도 팔 한 걸음은 10 us 안팎으로 매우 싸다. 무거운 것은 화면 그리기(렌더링)이지 역학 계산이 아니다. 단, 관절이 수십 개인 휴머노이드에서는 다시 재야 한다(E15 4-3).
- "인터페이스를 뒀으니 실물도 바로 된다" — 아니다. 실물 백엔드(FeetechSerialBackend)는 아직 **자리만** 있다(장표 058). 인터페이스는 "제어 코드를 안 바꿔도 된다" 를 보장하지, 로봇 쪽 코드가 저절로 생기지는 않는다.
- "기준 10% 와 테스트의 900 us 가 왜 다른가" — 테스트 코드는 "확실히 깨진 것" 만 잡는 느슨한 상한(p99 < 900 us)이고, 10% 는 설계 여유를 위한 엄격한 목표다. 실측 0.9% 는 둘 다 통과.
- 함정(11/04, LOG): colcon install 뒤 `libmujoco.so` 를 못 찾는 rpath 소실 → `CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE` 로 해결. 백엔드 교체 자체는 쉬웠지만 빌드 설정에서 한 번 넘어졌다.

## 7. 면접 한 문장
- "로봇 쪽을 init · write_command · read_state 세 함수로 잘라 두었더니 SimLag 를 MuJoCo 로 바꿀 때 제어 코드는 한 줄도 안 바뀌었고, 물리 한 주기는 p99 8.5 us 로 1 ms 의 0.9% 였습니다 — 실물 서보도 같은 자리에 끼우면 됩니다."
