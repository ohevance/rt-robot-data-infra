# 장표 098 — 2부 ⑦⑧ 검증 — 표③ 실험 사슬 (2/3) — E08 → E13: 고치자 0, 다른 환경에서도 0
*위치: 3부 검증 · 2부 ⑦⑧ 관제 · 표③ 사슬 2/3 (0, CI 도 0)*

## 1. 이 장표가 왜 있나
앞 장표(097)는 "유실 0 은 가짜였고, 진짜는 53 이었으며, 원인은 셋"으로 끝났다. 그러면 다음 질문은 두 가지다. 첫째, 원인 ①(브로커 재시작 경쟁)과 ②(수집기 종료 순간)를 고치면 정말 0 이 되나? 둘째, 내 PC 에서 0 이 나왔다고 해서 다른 컴퓨터에서도 0 인가 — 즉 환경이 만든 숫자인가, 설계가 만든 숫자인가? 이 장표는 그 두 질문에 답하는 E08 과 E13 을 보여 준다. 결론은 "고치자 진짜 0 이 됐고(E08), GitHub 의 깨끗한 컴퓨터에서 장치 수·주기·장애 시간을 바꿔도 같은 모양(E13)" 이다. 순서도에서 "예" 가 두 번 이어지며 표③이 통과한다.

## 2. 장표를 하나씩 읽기
- 상자 1 "E08 persistence true + 곱게 종료 뒤 재측정": E07 의 원인 ①은 브로커 설정 한 줄(`persistence true` + 디스크 볼륨)로, 원인 ②는 수집기가 종료 신호를 받으면 수신을 끊고 마지막 묶음까지 DB 에 넣은 뒤 끝나도록(곱게 종료, `shutdown()`) 고쳤다. 고친 뒤 **같은 장애를 같은 조건으로** 다시 쟀다. 코드가 돌아간다는 것과 유실이 0 이 됐다는 것은 다른 말이기 때문이다.
- 마름모 1 "유실 0? diag C 틈 없음?" → "예: broker 0 / 1400, collector(QoS 1) 0 / 1311 ✓": 기준이 둘인 이유는 E07 의 교훈("숫자 하나만 믿지 말라") 때문이다. 유실 계산이 0 이어야 하고, 동시에 진단 도구 C절(장치별 일련번호 틈)에도 틈이 없어야 한다. 브로커 10초 중단은 1,400개 중 0, 수집기 10초 종료·재시작(QoS 1)은 1,311개 중 0. 고치기 전 53 / 1434 와 비교하면 겨냥한 유실만 정확히 사라졌고, 복귀 시간(2.9초 / 1.6초)은 고치기 전과 같다 — 즉 성능 비용 없이 유실만 없앴다.
- 상자 2 "같은 실행에서 발견 2건: 수집기 두 개(client_id 충돌) → flock / 보관 유언 재수신 → events 제외": 재측정 도중 두 가지 부산물이 나왔다. 하나는 수집기가 실수로 두 개 떠서 같은 MQTT client_id 로 서로를 밀어내며 2초마다 재접속한 사고 — 해결은 파일 잠금(flock)으로 한 번에 하나만 뜨게 한 것. 다른 하나는 persistence 를 켜자 브로커가 보관해 둔 유언(offline 상태 메시지)을 재구독 때 다시 내려 주어 "오프라인 이벤트"가 두 배로 세진 것 — 해결은 보관(retain=1) 메시지는 "지금 상태"이지 "사건"이 아니므로 events 표에 넣지 않는 것.
- 상자 3 "E13 CI 러너(ubuntu-24.04) 10대 2 Hz, 진짜 컨테이너": 두 번째 질문을 위해 환경을 바꿨다. GitHub Actions 의 무료 리눅스 가상 머신(러너)에서, 가상 장치 10대 × 2 Hz, 장애 5초, 매번 빈 DB 에서 시작하는 진짜 Mosquitto·TimescaleDB 컨테이너. 사람이 터미널 4개에서 하던 순서를 `fleet/tests/integration.sh` 한 스크립트가 한다.
- 마름모 2 "환경이 달라도 같은 모양?" → "예: 0/318 · 0/286 · 0/280, 롤백 0.4 s ✓": 브로커 중단 0 / 318, DB 중단 0 / 286, 수집기 종료(QoS 1) 0 / 280, 나쁜 펌웨어 롤백 0.4초. 숫자 자체(분모)는 장치 수와 시간이 달라 다르지만 "유실 0, 복구 수 초, 롤백 1초 안" 이라는 모양이 같다. 복구 시간의 순서(DB 가 가장 빠르고 브로커가 가장 느리다)도 같다 — 브로커 쪽은 장치가 재접속하고 버퍼를 쏟는 시간이 드니까.
- 진한 끝 상자 "표③ 통과 — 환경이 아니라 설계가 만든 숫자 / 매 push 마다 다시 증명": 모양이 같다는 것은 장치 버퍼·수집기 backlog·지속 세션·헬스 게이트라는 **설계**가 숫자를 결정한다는 뜻이다. 그리고 이 스크립트는 CI 의 `fleet_integration` 잡으로 push 할 때마다 다시 돈다.
- 아래 상자 "CI 1차는 실패했었다: TimescaleDB 첫 기동의 임시 서버에 pg_isready 가 속음 → migrate.py --wait 가 TCP 로 진짜 붙어 보며 기다리게 고침": 러너는 매번 빈 DB 에서 시작하는데, TimescaleDB 컨테이너는 첫 기동 때 초기화용 임시 서버를 잠깐 띄운다. 컨테이너 안의 준비 확인 명령(pg_isready)은 그 임시 서버에도 "준비됨"이라 답해서 마이그레이션이 너무 일찍 달려들다 실패했다. 고친 것은 `migrate.py --wait 120` 이 밖에서 TCP 로 진짜 접속이 될 때까지 1초마다 재시도하는 것. 내 PC 에서는 볼륨에 데이터가 남아 있어 이 경로를 한 번도 타지 않았다 — CI 만 잡을 수 있었던 문제다.

## 3. 용어와 단위
- 지속 세션(persistent session): 수집기가 `clean_session=False` + 고정 client_id 로 붙으면, 수집기가 없는 동안 브로커가 QoS 1 메시지를 대신 보관했다가 재접속 때 넘겨 준다.
- 곱게 종료(graceful shutdown): 종료 신호(SIGTERM, Ctrl+C)를 받았을 때 바로 죽지 않고, 받아 둔 것을 마지막으로 DB 에 넣은 뒤 끝내는 것.
- client_id: MQTT 에서 접속하는 쪽의 이름표. 같은 이름표로 둘이 붙으면 브로커가 먼저 것을 끊는다.
- flock: 리눅스의 파일 잠금. 한 프로그램이 잡고 있으면 다른 프로그램은 못 잡는다 → "한 번에 하나만" 보장.
- 유언(LWT) / 보관(retained): 유언은 비정상 종료 때 브로커가 대신 발행하는 "offline" 메시지, 보관은 마지막 값을 새 구독자에게 바로 주는 기능. 보관된 유언은 "지금 상태"이지 새 사건이 아니다.
- CI 러너: GitHub 가 push 마다 새로 켜 주는 리눅스 가상 머신(ubuntu-24.04). 내 노트북이 아니고 매번 백지다.
- pg_isready: PostgreSQL 이 접속을 받을 준비가 됐는지 묻는 명령. TCP 로 "진짜 붙어 본다"는 실제로 접속·질의를 시도한다는 뜻.
- 단위: "0 / 1400" = 1,400개 중 0개 유실. s = 초. 2 Hz = 1초에 2개.

## 4. 쉬운 예시
- 비유(환경 vs 설계): 집에서 만든 요리가 맛있는 것이 "우리 집 가스불" 덕분인지 "레시피" 덕분인지 알려면 다른 집 부엌에서 같은 레시피로 해 봐야 한다. E13 이 그 "다른 집 부엌"(GitHub 러너)이고, 같은 맛(유실 0·복구 수 초)이 나왔으니 레시피(설계)가 맞는 것이다.
- 숫자 예시: 러너에서 장치 10대 × 2 Hz × 5초 중단 = 보호가 없었다면 100개를 잃었어야 한다(표의 "보호 없었다면 100"). 실제는 0 / 318. 내 PC 에서는 50대 × 1 Hz × 10초 = 500개 대신 0 / 1400. 분모가 달라도 분자는 둘 다 0.

## 6. 자주 하는 오해·함정
- "0 이 나왔으니 끝" 이 아니라 "겨냥한 유실만 없어졌고 다른 숫자는 그대로인가"까지 봐야 한다. E08 은 복귀 시간이 고치기 전과 같음을 확인했다.
- 러너의 숫자를 PC 와 직접 비교하면 안 된다(10대 2 Hz 5초 vs 50대 1 Hz 10초). 비교할 것은 "모양"(유실 0, 복구 수 초, 순서)이다.
- 지속 세션은 수집기 재시작에만 보호가 된다. 브로커 자체가 죽는 경우는 장치 쪽 버퍼가 맡는다(E05·E08 의 broker 줄).
- 남은 틈(추정): 수집기가 SIGKILL(강제 종료)로 죽으면 곱게 종료가 돌지 못해 그 1초치를 여전히 잃는다. 완전한 해법(DB 적재 뒤 PUBACK, 수동 ACK)은 2주 범위 밖으로 `docs/DECISIONS.md` 에 보류로 적혀 있다.

## 7. 면접 한 문장
"원인 둘을 설정 한 줄과 종료 처리로 고치자 유실이 53 에서 0 이 됐고, GitHub 러너에서 장치 수·주기·장애 시간을 바꿔도 0·0·0 이었다 — 환경이 아니라 설계가 만든 숫자이고, push 마다 다시 증명된다."
