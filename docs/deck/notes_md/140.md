# 장표 140 — 덧붙임 (11/10~11) — 운영 층을 클라우드에: Pi 가 시드니 서버로 보고한 14.8시간, 53,167건 중 유실 0
*위치: 7부 왜·사고·방식 · 덧붙임 클라우드 운영 층 (11/10~11)*

## 1. 이 장표가 왜 있나
앞의 세 장표(137~139)는 "새 소프트웨어를 로봇에 어떻게 내보내나"였고, 답은 GitHub(만들고 보관) + 장치(스스로 받아 설치)였다. 그러면 남는 것이 있다. 2부에서 만든 관제 — 브로커 · 수집기 · DB · 대시보드, 이 저장소가 "운영 층"이라 부르는 것 — 은 지금까지 개발 PC(노트북)의 WSL 안에서 돌았다. 노트북은 항상 켜 둘 수 없다. 뚜껑을 덮으면 관제가 사라지고, 로봇이 밤새 무엇을 했는지는 아무도 모른다. 그래서 질문은 "운영 층은 어디에 있어야 하고, 거기로 옮기는 데 무엇이 바뀌나, 그리고 옮긴 뒤 정말 끊김 없이 받고 있나"다. 이 장표는 그 답이다 — 11/10 에 운영 층을 클라우드의 서버 한 대로 옮겼고, 실물 Pi 가 인터넷 너머 그 서버로 1초에 한 번 보고하기 시작했으며, 첫 14.8시간의 기록을 **세어서** 유실 0 을 확인했다. 큰 숫자 넷은 결과(유실 0), 구조(서버 1대), 문(8883 하나), 거리의 값(290 ms)이다. 다음 장표(141)는 이 일을 실제 기계에서 처음 돌리며 깨진 것들이다.

## 2. 장표를 하나씩 읽기
큰 숫자 네 개를 왼쪽에서 오른쪽으로, 그다음 글머리표 네 줄, 바닥 줄.

- KPI 1 "유실 0 / 53,167건 중 (Pi → 서버: 시드니) / 14.8시간 · 재시작 0 · 중복 0": 실물 Pi 가 서버로 보낸 텔레메트리 가운데 서버의 DB 에 없는 것이 0건이다. 기간은 11/10 18:37 부터 11/11 09:23 까지 14.77시간(장표는 14.8 로 반올림). Pi 는 1초에 한 건씩 보내고 메시지마다 일련번호(seq)를 붙이므로, 보냈어야 할 수(53,167)와 받은 수(53,167)를 번호로 맞춰 볼 수 있다. "재시작 0"은 그 사이 Pi 의 에이전트가 한 번도 다시 시작되지 않았다는 뜻(다시 시작하면 번호가 0 부터 새로 간다), "중복 0"은 같은 번호가 두 번 들어온 것이 없다는 뜻이다. "(서버: 시드니)"는 이 숫자를 어디로 보낸 것인지의 꼬리표 — 유실 0 자체는 거리와 무관하지만, 서버를 거치는 숫자에는 항상 붙이기로 한 표기다.
- KPI 2 "VM 1대 / 컨테이너 4개(브로커·수집기·DB·Grafana) / docker compose — K8s 는 쓰지 않았다": 운영 층의 모양. 클라우드의 가상 컴퓨터(VM) 한 대에 컨테이너 넷을 올렸다 — 개발 PC 에서 쓰던 `docker compose` 구성 그대로다(개발에서는 수집기를 프로세스로 띄우기도 했는데, 서버에서는 수집기도 컨테이너로 항상 뜬다). 컨테이너 여러 개를 여러 서버에 걸쳐 관리하는 도구인 쿠버네티스(K8s)는 쓰지 않았다 — 이유는 넷째 글머리표.
- KPI 3 "8883 / 밖으로 연 MQTT 포트는 이것 하나 / TLS(자체 CA) + 비밀번호": 서버가 인터넷에 여는 장치용 문은 하나다. 포트 8883 은 암호화된 MQTT 의 관례 번호이고, 여기로 붙으려면 통신이 TLS 로 암호화되어야 하고 아이디와 비밀번호가 맞아야 한다. "자체 CA"는 인증서를 사지 않고 직접 만든 발급처(CA)로 서버 인증서를 만들었다는 뜻 — 장치에는 그 발급처의 인증서 파일(`ca.crt`) 하나만 주면 서버가 진짜인지 확인할 수 있다.
- KPI 4 "290 ms / 서버까지 MQTT 왕복 (다다음 장표) / 대시보드 전달 지연 146.5 ms ≈ 편도": 서버가 멀리(시드니) 있는 값. Pi 가 메시지를 보내 브로커를 거쳐 자기가 다시 받는 데 290 ms 가 걸린다. 대시보드가 보여 주는 "전달 지연" 146.5 ms 는 그 절반(145 ms)과 거의 같아, 이 장치에서는 편도 지연으로 읽어도 된다. 이 숫자가 어떻게 나왔는지 — 처음에는 707 ms 로 잘못 쟀다 — 는 장표 142 의 이야기다.
- 글머리표 1 "왜 했나: 노트북은 항상 켜 둘 수 없다. 실물 Pi 의 텔레메트리를 쌓아 '돌아가는 주소'를 보이려면 운영 층이 항상 켜진 곳에 있어야 한다. 코드는 그대로 두고 접속 설정만 환경변수(FLEET_BROKER · PORT · TLS_CA · USER · PASS)로 읽게 했고(fleet/common/mqtt_conn.py), compose 에 운영 덮어쓰기 파일을 하나 더했다": 이유와 바뀐 것. 옮기면서 바꾼 코드는 "어디에 어떻게 붙나"를 읽는 한 곳뿐이다. 장치 에이전트 · 수집기 · 배포기 · 장애 주입기가 모두 브로커에 붙는데, 그 접속 설정(브로커 주소, 포트, 발급처 인증서 경로, 아이디, 비밀번호)을 환경변수 다섯 개로 읽는 작은 모듈 하나(`mqtt_conn.py`)를 두고 모두가 그것을 부르게 했다. 환경변수가 비어 있으면 전과 똑같이 같은 PC 의 1883 에 암호화 없이 붙는다 — 개발과 운영이 **같은 코드**다. 컨테이너 쪽은 기존 구성 파일 위에 겹쳐 쓰는 작은 파일(`docker-compose.prod.yml`) 하나가 "밖으로는 8883 만, DB 는 밖으로 내지 않기, 대시보드는 로그인, 수집기는 항상, 죽으면 다시 켜기"를 정한다.
- 글머리표 2 "무엇을 열고 닫았나: 인터넷에 열린 브로커는 ota 명령을 받는 문이다 → 암호화와 인증 없이는 열지 않는다. 내부 1883 과 DB 5432 는 컨테이너 네트워크 안에만, 대시보드(3000)와 ssh(22)는 내 IP 에만. 리전이 시드니인 것은 무료 플랜의 조건이고(운영이라면 장치와 가까운 서울) 그 값이 왕복 290 ms — 서버 왕복이 들어가는 숫자에는 '서버: 시드니'를 적는다": 문 단속과 위치.
  - 왜 브로커의 문이 특히 문제인가: 이 브로커를 통해 장치에 `ota`(새 소프트웨어를 깔아라) 명령이 간다. 아무나 붙을 수 있으면 아무나 로봇에 명령을 보낼 수 있다.
  - 문 넷: 8883(장치용, 전 세계에 열되 TLS + 비밀번호가 문지기 — 집의 인터넷 주소가 바뀌어도 장치가 붙어야 해서 주소로 막지 않았다), 1883(암호화 없는 내부용 — 서버 안의 컨테이너끼리만 닿는다), 5432(DB — 역시 안에서만), 3000(대시보드)과 22(서버 관리) — 작성자의 인터넷 주소에서만.
  - 왜 시드니인가: 새로 가입한 클라우드 계정의 무료 조건이 지역을 시드니로 고정했다. 서울을 쓰려면 유료로 바꿔야 했고, 비용 0 을 지연보다 앞에 두었다. 운영이라면 장치와 가까운 곳에 둔다.
  - 그 값: 왕복 290 ms. 그래서 규칙을 하나 정했다 — 서버를 오가는 시간이 들어가는 숫자(전달 지연, 감지 · 복구 시간, 배포 · 롤백 시간)를 이 서버로 잰 것에는 "서버: 시드니"를 붙이고, WSL 이나 러너에서 잰 기존 숫자와 섞지 않는다.
- 글머리표 3 "유실 0 을 무엇이 말하나: 대시보드는 '지금 온라인 1, 오류 0'까지만 보여 준다. 밤새 끊김이 없었다는 말은 장치가 붙인 일련번호(seq)를 서버에서 센 숫자가 한다 — 보냈어야 할 53,167 = 받은 53,167, 이웃한 기록의 가장 긴 간격 1.0초, offline 이벤트 0. 그 사이 수집기 재시작 1회와 Pi 의 자동 보안 업데이트(패키지 70개쯤)가 있었다": KPI 1 의 근거를 따지는 줄. 그래프는 "끊긴 것처럼 보이지 않는다"까지만 말한다 — 하루치 그래프의 한 점은 수십 초의 평균이라 몇 건이 빠져도 보이지 않는다. 번호는 한 건도 숨기지 않는다. 그래서 서버의 DB 에서 번호를 세는 스크립트(`deploy/ec2/soak_report.sh`)를 만들었다: 보냈어야 할 수 · 받은 수 · 빠진 수, 에이전트가 다시 시작된 횟수, 이웃한 두 기록 사이의 가장 긴 간격(1 Hz 니까 1초 안팎이어야 한다 — 1.0초였다), 서버가 아무것도 못 받은 가장 긴 시간(1.6초). 뒷문장은 이 14.8시간이 아무 일도 없던 시간이 아니었다는 것 — 그 사이 서버의 수집기를 고쳐서 한 번 다시 띄웠고(11/10 19:02), Pi 는 오래 꺼 두었던 탓에 보안 업데이트 70개쯤을 한꺼번에 깔았다. 수집기가 없던 동안의 메시지는 브로커가 대신 들고 있다가 넘겼다(2부의 지속 세션, QoS 1).
- 글머리표 4 "K8s 를 쓰지 않은 이유: 노드 1대 · 컨테이너 4개에 필요한 것(죽으면 다시 켜기 · 부팅 때 자동 시작 · 설정을 코드로 · 개발과 같은 구성)은 compose 로 된다. 바꿀 때는 수집기를 여러 대로 늘려야 할 때이고, 그 첫 걸음은 수집기를 상태 없는 복제본으로 만드는 것이다": 쓰지 않은 도구에 대한 답. 쿠버네티스가 푸는 문제는 "여러 서버에 걸친 배치, 자동 복구, 멈추지 않는 교체, 대수 늘리기"다. 여기는 서버가 1대, 컨테이너가 4개다. 필요한 넷은 compose 로 된다 — 죽으면 다시 켜기(`restart: unless-stopped`), 서버가 켜질 때 자동 시작, 설정이 파일로 저장소에 있을 것, 개발 · CI · 운영이 같은 구성일 것. 언제 바꾸나도 적었다: 장치가 수천 대가 되어 수집기를 여러 대로 늘려야 할 때. 그때의 첫 걸음은 쿠버네티스가 아니라 수집기를 "어느 것이 받아도 되는" 복제본으로 만드는 일이다.
- 바닥 줄 "원본: docs/measurements/soak_pi-rt_20261111T0023Z.json(11/10 18:37 ~ 11/11 09:23), deploy/ec2/(README · setup.sh · soak_report.sh), fleet/docker-compose.prod.yml, mosquitto-prod.conf, DECISIONS 11/10 · 11/11. 한계: 비밀번호 하나를 모든 장치가 공유 · Grafana 는 HTTP · 서버 1대": 원본과 한계 셋. ① 모든 장치가 같은 아이디와 비밀번호를 쓴다 — 한 대만 끊을 수 없다(장치마다 인증서를 주는 것이 다음 단계). ② 대시보드는 암호화되지 않은 HTTP 다 — 그래서 작성자의 주소에서만 열었다. ③ 서버가 1대라 서버가 죽으면 운영 층이 멈춘다 — 로봇은 계속 돌고, 텔레메트리는 장치가 1시간치를 들고 있다가 다시 보낸다.

## 3. 용어와 단위
- 운영 층: 로봇 밖에서 로봇들을 지켜보고 지휘하는 부분 — 브로커(메시지 우체국), 수집기(받아서 DB 에 넣는 프로그램), DB(TimescaleDB), 대시보드(Grafana).
- 클라우드 VM: 클라우드 회사가 빌려주는 가상 컴퓨터. 여기서는 AWS 의 EC2, 크기 t3.small, 디스크 20 GB.
- 리전(region): 클라우드의 데이터센터 지역. 시드니(ap-southeast-2), 서울(ap-northeast-2).
- 컨테이너 / docker compose: 프로그램을 상자째 띄우는 방식 / 여러 컨테이너를 파일 하나로 정의해 함께 띄우는 도구.
- K8s(쿠버네티스): 여러 서버에 걸쳐 컨테이너를 배치 · 복구 · 확장하는 도구.
- 포트: 한 컴퓨터 안에서 프로그램을 구분하는 번호. 1883 은 MQTT, 8883 은 암호화된 MQTT, 5432 는 PostgreSQL, 3000 은 Grafana, 22 는 ssh 의 관례 번호.
- TLS: 통신을 암호화하고 상대가 진짜인지 확인하는 방식(웹의 https 와 같은 기술).
- CA(인증 기관) / 자체 CA: 인증서에 도장을 찍어 주는 발급처 / 그 발급처를 직접 만든 것. 도메인 이름이 없어도 되고 비용이 없다.
- 환경변수: 프로그램이 시작할 때 바깥에서 받는 설정값. 비밀번호를 코드나 저장소에 적지 않기 위해 쓴다.
- seq(일련번호): 장치가 메시지마다 1씩 올려 붙이는 번호. 빠진 번호 = 잃은 메시지.
- 연속 기록(soak): 오랫동안 켜 두고 끊김이 없었는지 보는 것.
- 왕복(RTT) / 편도: 보내고 되돌아올 때까지 / 한쪽 방향. 290 ms 왕복이면 편도는 어림 145 ms.
- "서버: 시드니": 서버를 오가는 시간이 섞인 숫자에 붙이는 꼬리표.
- 단위: 14.77시간 = 53,172초쯤. 1 Hz 로 보내면 약 5만 3천 건.

## 4. 쉬운 예시
- 비유: 가게의 CCTV 녹화기를 사장 노트북에 두면 노트북을 덮는 순간 녹화가 멈춘다. 그래서 녹화기를 24시간 켜진 경비 회사 건물(클라우드 서버)로 옮겼다. 건물에는 문이 넷 있다 — 카메라가 영상을 보내는 문(8883)은 누구에게나 열려 있지만 암호(비밀번호)와 봉인된 통로(TLS)가 있어야 지나가고, 직원 통로(1883)와 금고(DB)는 건물 안에서만, 모니터실(대시보드)과 관리실(ssh)은 사장의 주소에서만 들어간다. 건물이 멀리(시드니) 있어 영상이 0.15초 늦게 도착한다. 다음 날 아침 "밤새 빠진 장면이 없나"는 화면을 훑어보는 것이 아니라, 카메라가 장면마다 찍어 둔 번호를 세어서 확인한다 — 53,167번까지 하나도 빠지지 않았다.
- 숫자 예시: 14.77시간 × 3,600초 ≈ 53,172초. 1초에 한 건이면 약 53,170건이어야 하고, 실제로 센 값이 53,167 = 53,167 이다. 만약 30초 동안 연결이 끊겼다면 — 장치가 그동안 30건을 들고 있다가 다시 보내므로 "빠진 수"는 여전히 0 이고, 대신 "서버가 아무것도 못 받은 가장 긴 시간"이 30초로 보였을 것이다. 실제 값은 1.6초다.
- 비용 예시: 이 크기의 서버를 24시간 켜 두면 한 달에 약 25달러(서버 19.3 + 디스크 2 + 공인 주소 3.6, 어림). 무료 크레딧 180달러로 약 7개월분이다.

## 6. 자주 하는 오해·함정
- "대시보드가 초록이니 밤새 문제없었다"는 오해: 대시보드는 지금을 보여 준다. 지난 14시간에 몇 건이 빠졌는지는 세어야 안다 — 그래서 이 장표의 첫 숫자는 그림이 아니라 센 값이다.
- "유실 0 = 한 번도 안 끊겼다"가 아니다. 끊겼어도 장치가 들고 있다가 다시 보내면 유실은 0 이다. 끊김은 "서버가 못 받은 최장 시간"과 offline 이벤트가 말한다(1.6초, 0건).
- "전달 지연 146.5 ms"를 다른 장치의 값과 그대로 비교하지 않는다. 이 값은 (서버가 받은 시각 − 장치가 찍은 시각)이라 두 기계의 시계 차이가 섞인다. Pi 는 왕복과 맞춰 보니 거의 그대로 편도였지만(차이 +1.5 ms), 같은 서버에 대해 WSL 의 가상 장치는 184 ms 로 보였다 — 맞춰 보기 전에는 얼마가 시계 차이인지 모른다.
- "290 ms 면 느린 시스템이다"는 오해: 서버를 한국에서 시드니에 둔 값이다. 로봇 안의 1 ms 제어 루프와는 무관하고, 1초에 한 번 보내는 텔레메트리에도 영향이 없다. 영향을 받는 것은 서버가 장애를 알아채고 명령이 닿는 시간이다.
- "8883 을 전 세계에 열었으니 위험하다"는 걱정: 그래서 TLS 와 비밀번호가 있다. 다만 한계는 그대로다 — 비밀번호 하나를 모든 장치가 같이 쓴다. 장치 하나가 털리면 전부 바꿔야 한다.
- "클라우드로 옮겼으니 개발 PC 의 관제는 필요 없다"는 오해: 장애를 일부러 일으키는 실험은 계속 개발 PC 와 CI 에서 한다. 운영 중인 서버의 브로커를 실험으로 죽이지 않는다.
- 이 숫자는 한 번의 14.8시간이다. 그 뒤에 Pi 를 껐다 켜면(전원 · 재부팅 · 서비스 재시작) 기록은 구간으로 나뉘고 "재시작 N회"와 그때의 공백이 붙는다 — 세는 스크립트가 구간마다 세어 더한다. 더 긴 기간을 다시 센 값은 실험 페이지와 이 장표에 갱신한다.

## 7. 면접 한 문장
"관제를 노트북에서 클라우드 서버 한 대로 옮기면서 바꾼 코드는 접속 설정을 환경변수로 읽는 한 곳뿐이었고, 밖으로는 TLS 와 비밀번호가 걸린 8883 하나만 열었습니다. 실물 Pi 가 14.8시간 동안 보낸 53,167건을 일련번호로 세어 유실 0 을 확인했는데, 그 사이 수집기를 한 번 다시 띄웠는데도 그랬습니다. 서버가 시드니에 있어 왕복이 290 ms 라는 것과 비밀번호를 모든 장치가 같이 쓴다는 한계도 같이 적어 두었습니다."
