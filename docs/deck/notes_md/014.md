# 장표 014 — 단계 2 들머리 — ROS 2 / DDS 가 전달한다: 손실 없이, 제어 주기 급으로 가나
*위치: 1부 로봇을 움직이는 길 · 단계 2/10 DDS 전달 · ① 들머리*

## 1. 이 장표가 왜 있나
단계 1(011~013)에서 명령이 50 Hz 로 `/joint_command` 토픽에 들어간다는 것까지 봤다. 그런데 명령을 내는 프로그램과 받는 노드는 다른 프로세스다. 그 사이를 누가, 어떻게 옮기나 — 그리고 옮기다 잃거나 늦으면 로봇은 지난 목표에 머물거나 늦게 움직인다. 이 장표는 단계 2 의 들머리로, "전달"이라는 걱정을 여섯 상자(들어온 것 → 문제 → ◇기준 → 확인 방법 → 결과 → 판단)로 처리한다. 결론은 "우리 메시지 크기에서는 손실 0 이니 전달은 걱정 목록에서 빼고 다음 걱정(스레드 경계, 단계 3)으로 간다"이고, 그 증명(E04 측정기와 판단 사슬)은 3부 장표 87~88 에 미뤄 둔다.

## 2. 장표를 하나씩 읽기
여섯 상자를 순서대로. 색의 뜻: 회색 = 앞 단계에서 들어온 것, 마름모 = 판단 기준, 파란 = 확인 방법, 화살표 뒤 = 결과(실제 값), 진한 둥근 상자 = 결론.

- 들어온 것(회색) "50 Hz 로 나오는 JointState 명령 (단계 1)": 앞 단계의 출력이 이 단계의 입력이다. 20 ms 마다 position 배열 6개짜리 메시지 하나.
- 문제 "발행자와 노드는 다른 프로세스. 미들웨어(DDS)가 실어 나르는데, 구현체(Fast DDS·Cyclone)와 QoS 에 따라 잃거나 늦을 수 있다": 왜 문제인가 — ROS 2 는 통신을 직접 하지 않고 DDS 에 맡기며, DDS 는 여러 회사가 각자 구현했고(Fast DDS, Cyclone DDS) 설정(QoS)에 따라 동작이 다르다. "ROS 2 를 쓴다"는 말만으로는 잃지 않는다는 보장이 없다. 그래서 직접 잰다.
- 기준(마름모) "관절 명령 크기에서 손실 0, 왕복 지연이 제어 주기(1 ms) 급인가? 큰 메시지는 어디서 깨지나?": 질문 셋. ① 우리 메시지(수십 B)에서 하나도 잃지 않나 ② 왕복 지연이 제어 주기 1 ms 와 같은 급(수 ms 가 아니라)인가 ③ 크기를 키우면 어디서 깨지나(영상·점군을 보낼 때를 위해). 왜 이 기준인가 — 명령을 잃으면 로봇은 지난 목표에 머물고(워치독이 50 ms 뒤에 멈춤), 많이 늦으면 50 Hz 의 뜻이 없어진다.
- 확인 방법(파란) "E04 — dds_bench/rtt_bench.py ping/pong 16조합(구현체 2 × QoS 2 × 크기 4), 500회 × 100 Hz → 3부 장표 87~88": 측정기 `rtt_bench.py` 는 ping 이 보내고 pong 이 되돌려 주는 메아리 구조로 왕복 시간(RTT)과 손실을 센다. 조합은 구현체(Fast DDS·Cyclone) × QoS(reliable·best_effort) × 크기(64 B·1 KB·64 KB·1 MB) = 16. 조합마다 100 Hz 로 500개(발행 자체는 5초분, E04 는 조합당 약 8초로 적는다). 측정기 그림과 E04 판단 사슬은 3부 87~88 번.
- 결과 "64 B~64 KB: 전부 손실 0, RTT p50 0.9~1.2 ms. 1 MB: Fast DDS best_effort 99.8% · reliable 22.8% 손실, Cyclone 0%": 기준 ①② 에 대한 답은 "작은 메시지 12조합 전부 손실 0, 왕복 중앙값 0.9~1.2 ms(한 방향 약 0.5 ms)". 기준 ③ 의 답은 "1 MB 에서 갈린다 — Fast DDS 는 best_effort 로 500개 중 1개만 도착(99.8% 손실), reliable 로도 386개(22.8% 손실), Cyclone 은 둘 다 0". 측정 환경은 WSL2 같은 PC 안 프로세스 간이라 네트워크 수치가 아니다.
- 판단 → 다음(진한) "통과(관절 명령은 수십 B) → 단계 3. 큰 데이터(영상·점군)는 표②로 구현체·QoS 를 고른다": 우리 명령은 64 B 급이라 어느 조합이든 손실 0 이므로 통과. 큰 데이터를 보낼 일이 생기면 표②(3부)를 보고 Cyclone 또는 설정 조정을 고른다 — 그 결정은 지금 안 한다.
- 아래 글(bottom): 이 단계의 장표는 ② 미들웨어·QoS 설명 1장(016)뿐이고, 측정기 그림과 E04 판단 사슬은 3부 검증이다. 넘어가는 조건은 "우리 메시지 크기에서 손실 0" — 그래서 '전달'을 걱정 목록에서 빼고 다음 걱정(스레드 경계)으로 간다.

왜 이 답이 다음 상자(단계 3)로 이어지나: 전달이 믿을 만하다고 확인됐으니, 이제 문제는 "도착한 명령을 일반 스레드에서 RT 스레드로 어떻게 기다림 없이 넘기나"로 바뀐다. 그것이 단계 3 우편함이다.

## 3. 용어와 단위
- DDS(Data Distribution Service): 발행/구독 방식의 표준 통신 미들웨어. ROS 2 토픽은 전부 DDS 위에서 움직인다.
- 구현체: 같은 DDS 표준을 각자 만든 소프트웨어. Fast DDS(eProsima, ROS 2 Jazzy 기본) · Cyclone DDS(Eclipse). 환경 변수 `RMW_IMPLEMENTATION` 으로 고른다.
- QoS(Quality of Service, 품질 약속): reliable = 못 받으면 재전송 요청(등기 우편), best_effort = 한 번 보내고 끝(일반 우편). depth = 보관하는 최근 메시지 수(여기서는 10).
- RTT(Round Trip Time, 왕복 지연): 보낸 시각부터 메아리가 돌아온 시각까지. 한 방향 ≈ RTT ÷ 2. 단위 us(마이크로초, 100만분의 1초) 또는 ms. 0.9~1.2 ms = 900~1,200 us.
- p50: 측정값을 작은 것부터 늘어놓았을 때 가운데(중앙값).
- 손실 % : (보낸 수 − 받은 수) ÷ 보낸 수 × 100. 500개 보내 1개 받으면 99.8%, 386개 받으면 22.8%.
- 64 B · 1 KB · 64 KB · 1 MB: 바이트 단위 크기. 관절 명령은 64 B 급, 카메라 한 장은 수백 KB~MB.

## 4. 쉬운 예시
비유: 두 건물 사이의 사내 우편이다. 봉투(관절 명령)는 어떤 택배사(구현체)와 어떤 등급(QoS)으로 보내도 다 도착했고 왕복 1 ms 쯤 걸렸다. 그런데 큰 소포(1 MB)를 보내자 한 택배사(Fast DDS)는 일반 등급으로는 500개 중 1개만, 등기로도 386개만 전달했고, 다른 택배사(Cyclone)는 전부 전달했다. 우리가 보내는 것은 봉투라서 통과시키되, 소포를 보낼 날을 위해 그 표(표②)를 남겨 둔다. 숫자 예시: 명령 하나 48 B(double 6개)가 왕복 1.0 ms 라면 한 방향 약 0.5 ms — 명령 주기 20 ms 의 2.5% 다. 50 Hz 명령이 2.5% 늦게 도착하는 것은 로봇 입장에서 느낄 수 없다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 16조합 · 500회 × 100 Hz · depth 10 — `docs/experiments/E04.md` §2 표.
- 확인: 64 B~64 KB 손실 0, p50 0.9~1.2 ms — `docs/measurements/table2.md` 12줄(p50 868~1,236 us). 다시 만들기: `bash dds_bench/run_matrix.sh` 뒤 `python3 scripts/make_table2.py`.
- 확인: 1 MB 손실 99.8% / 22.8% / 0% — `table2.md` 의 fastrtps best_effort 1 MB(받음 1), fastrtps reliable 1 MB(받음 386), cyclonedds 1 MB 두 줄(받음 500).
- 확인: 왕복으로 재는 이유 — `docs/DECISIONS.md` 2026-11-03 (D1) "DDS 지연은 한 방향이 아니라 왕복(RTT)으로 잰다".
- 확인: 측정기 — `dds_bench/rtt_bench.py` 머리말(ping/pong 설명, rclpy 오버헤드 주의).
- 추정: "한 방향 약 0.5 ms" — RTT ÷ 2 로 계산한 값. 한 방향을 직접 재지는 않았다(시계 차 때문에 재지 않는 것이 결정).

## 6. 자주 하는 오해·함정
- "ROS 2 면 다 같은 통신"이 아니다. 같은 PC 에서 1 MB 를 100 Hz 로 보내니 구현체에 따라 0% 와 99.8% 로 갈렸다. 그래서 노드는 자기가 어느 RMW 위에서 도는지 `rt_status` 에 찍는다.
- reliable 이 "절대 안 잃는다"는 뜻이 아니다. 재전송은 보관함(depth 10)에 남은 것만 할 수 있어서, 100 Hz 로 밀려드는 1 MB 가 재전송 전에 밀려났다 — 그래서 22.8% 를 잃었다(E04 §4). "보관함 크기 안에서의 보장"이다.
- 이 수치는 WSL2 안 같은 PC 프로세스 간(공유 메모리 전송이 섞임)이라 네트워크 지연이 아니다. 두 기기 사이는 다시 재야 한다.
- 절대값에는 파이썬(rclpy) 오버헤드 수백 us 가 얹혀 있다. 조합 사이의 상대 비교로 쓰고, 절대 지연이 필요하면 C++ 측정기로 다시 잰다(`rtt_bench.py` 머리말).

## 7. 면접 한 문장
"전달 단계의 기준은 '우리 명령 크기에서 손실 0, 왕복이 제어 주기 급'이었고, 16조합 측정에서 64 B~64 KB 는 전부 손실 0, 왕복 중앙값 0.9~1.2 ms 로 통과했습니다. 다만 1 MB 에서는 Fast DDS 기본 설정이 99.8%·22.8% 를 잃고 Cyclone 은 0% 였기 때문에, 큰 데이터는 구현체와 QoS 를 골라야 한다는 표를 남겼습니다."
