# 장표 085 — ⑦ 판정(assert_results.py) 과 ⑧ 진단(diag.py) — 숫자를 통과/실패와 '왜'로 바꾸는 도구
*위치: 2부 데이터의 길 · ⑦⑧ 장애·판정·진단 · ② 도구 — 판정 · 진단*

## 1. 이 장표가 왜 있나
앞 두 장표에서 장애를 넣고(083 유실 SQL, 084 장애 4종 표) 숫자를 얻었다. 그런데 숫자만 있으면 두 가지가 비어 있다. 첫째, 그 숫자가 **합격인가**를 누가 기계적으로 가르나(CI 가 매 push 마다 판단해야 하니 사람이 눈으로 볼 수 없다). 둘째, 숫자가 **이상할 때 왜 그런가**를 어떻게 파나. 이 장표는 그 두 도구 — 판정(assert_results.py)과 진단(diag.py) — 의 규칙을 적는다. 2부의 마지막 장표이고, `다음 ▶` 가 3부 검증으로 넘어간다.

## 2. 장표를 하나씩 읽기
- 굵은 줄 "판정 규칙 (CI 2단계와 integration.sh 의 마지막 단계, 종료 코드 0 = 전부 통과)": assert_results.py 는 장애 주입·OTA 가 남긴 결과 JSON 들을 읽어 규칙에 댄다. 하나라도 어긋나면 종료 코드가 0 이 아니고 → CI 잡이 빨개진다. 통합 테스트 스크립트(6부)의 5) 단계가 바로 이것.
- 하위 줄 "broker: 유실 ≤ 장치 수(…), 전 장치 복귀 시간 있음 · db: 유실 0, backlog 0 복귀 시간 있음": 브로커가 죽는 그 순간 소켓에 이미 실린 메시지 1개/장치는 QoS 0 에서 잃을 수 있으니 장치 수까지만 허용한다. db 는 수집기 backlog 가 받쳐 주니 0 이어야 하고, 추가로 "뒤늦게 들어간 행 > 0"(backlog 가 실제로 쓰였나)도 본다(코드 41줄). "복귀 시간 있음"은 복구가 측정됐다는 뜻 — 영영 안 돌아오면 시간이 비어 실패.
- 하위 줄 "collector: label 에 qos1 이면 유실 0 / qos0 이면 유실 > 0 이어야 정상(…) · bad_firmware: success=false, 닿은 장치 = ceil(5%), 롤백 시간 있음 · ota: success=true": 수집기 장애는 실험 라벨에 따라 **반대** 규칙이다. QoS 1 지속 세션이면 0 이어야 하고, QoS 0 이면 유실이 **있어야** 정상 — "보호가 없으면 잃는다"를 숫자로 보여 주는 실험이기 때문이다(E11: 508 / 1312). 나쁜 펌웨어는 롤백으로 끝나는 것(success=false)이 정상이고 닿은 장치가 5% 의 올림(50대면 3)이어야 하며, 정상 OTA 는 success=true. 11/10 부터 OTA 결과에는 한 종류가 더 있다 — 진짜 파일을 설치한 배포(결과 JSON 의 `mode` 가 `artifact`). 규칙은 `assert_ota`(58~73줄)에 있다: 버전 이름이 `-bad` 로 끝나면 깨진 패키지이므로 롤백으로 끝나야 하고(success=false), 닿은 장치가 첫 단계의 올림 수와 같아야 하고, 롤백 시간이 있어야 하며, 타임라인에 "설치 실패"가 있어야 한다(장치의 자가 점검이 **거부해서** 멈춘 것이지 다른 이유로 멈춘 것이 아님을 본다). 좋은 패키지면 success=true, 전 장치 갱신, 그리고 결과에 산출물의 sha256 이 남아 있어야 한다(어느 파일을 깔았는지 나중에 대 볼 수 있게).
- 굵은 줄 "진단 세 절 — 실측에서 나온 '이상한 것'을 숫자로": diag.py 는 통과/실패를 내지 않는다. 11/04 실측에서 나온 "이상한 숫자" 세 가지를 각각 한 절로 파고든다.
- 하위 줄 "A 오프라인 이벤트: 첫 이벤트 기준 0.5초 안에 몰린 offline(3개 이상) = 브로커 종료 시 일괄 유언. 50대 중 20개만 찍힌 이유는 소켓을 닫기 전까지 쓴 만큼(E09)": 브로커를 멈추면 50대가 다 끊기는데 오프라인 이벤트는 늘 20개였다. 20개가 같은 1 ms 안에 장치 번호 순으로 찍혀 있었다 = 브로커가 종료되며 모든 접속 장치의 유언(offline)을 한꺼번에 발행했고, 수집기 소켓을 닫기 전까지 앞 20개만 전달된 것. 장치는 멀쩡했다. A 절은 0.5초 안에 3개 이상 몰린 offline 을 "군집"으로 묶어 이 경우를 가려낸다.
- 하위 줄 "B 지연 튐: p95 가 중앙값의 3배를 넘는 초, 단 msgs/s 가 3배 이상인 '홍수'(복구 폭주) 제외 → 간격의 중앙값이 10.0초면 keepalive 박자(E10)": 전달 지연 p95 가 평소의 3배를 넘는 초를 "튐"으로 잡되, 장애 복구 때 밀린 메시지가 쏟아지는 초(msgs/s 가 3배 이상)는 튐이 아니라 홍수라서 뺀다. 튐 사이 간격의 중앙값이 정확히 10.0초면 50대가 같은 박자로 보내는 keepalive 신호(PINGREQ) 탓이다 — E10 의 A/B 로 확정(30초로 바꾸면 0회, 10초로 되돌리면 10.0초 간격).
- 하위 줄 "C seq 틈: 연속 행에서 seq 가 1 넘게 뛰면 유실, seq 는 연속인데 3초 넘게 벌어지면 '장치 멈춤'(유실 아님). 표③ 유실 계산이 가장자리에서 놓칠 수 있는 것을 여기서 잡는다": 장치별로 행을 시간순으로 세워 앞 행과 비교한다. 번호가 뛰면 잃은 것, 번호는 이어지는데 시각이 3초 넘게 벌어지면 장치가 잠시 멈춘 것(유실 아님). E07 에서 "유실 0" 과 모순되는 12초 공백을 보여 준 것이 이 C 절이다.
- 일반 줄 "군집 함정(11/04): '이전 이벤트 기준'으로 이어 붙이면 1초마다 오는 이벤트가 209개짜리 거대 군집으로 뭉친다 → '첫 이벤트 기준' 0.5초": A 절을 처음엔 "직전 이벤트와 0.5초 안이면 같은 군집"으로 짰더니 1초마다 하나씩 오는 평범한 이벤트들이 모두 이어 붙어 209개짜리 군집이 됐다. "군집의 첫 이벤트로부터 0.5초 안"으로 고쳤다.
- 마지막 굵은 줄 "이 도구들로 한 실험(표③ 사슬 E05 → E13: '유실 0' 이 가짜였다 → 53 → 원인 셋 → 0, CI 에서도 0)과 표③-2·③-3 은 3부 장표 97~100": 2부에서는 도구까지만. 실험 사슬과 표는 3부.
- 오른쪽 말풍선 "소스": `fleet/chaos/assert_results.py`(94줄 — 11/05 까지 81줄) 의 함수 check · assert_fault · assert_ota(11/10: 산출물 규칙 — 자가 점검이 거부했나 · sha256 이 결과에 남았나), `fleet/tools/diag.py`(316줄) 의 find_cluster_groups(82줄) · classify_offline_events(109) · section_latency_blips(160) · section_seq_gaps(221), 실행 `python3 fleet/tools/diag.py --minutes 15`(최근 15분을 본다).
- 아래 `다음 ▶`: "3부 검증 — 1·2부에서 '확인 → 장표 N' 으로 미뤄 둔 시험을 단계 순서대로 본다: 표② DDS → 표① 1 ms 루프 → 물리 → 표③ 관제".

## 3. 용어와 단위
- 판정(assert): "이래야 한다"는 조건을 코드로 적고, 어긋나면 실패로 끝내는 것. 종료 코드(exit code) 0 = 성공, 그 외 = 실패 — CI 는 이 숫자만 본다.
- 진단: 왜 그런 숫자인지 파는 보고서. 통과/실패를 내지 않는다.
- 군집(cluster): 짧은 시간(0.5초) 안에 몰린 이벤트 묶음. 코드 상수 CLUSTER_WINDOW_S = 0.5, CLUSTER_MIN = 3.
- 유언(LWT, Last Will): 장치가 비정상으로 끊기면 브로커가 대신 발행해 주는 "offline" 메시지.
- p95, 중앙값: 1초 동안의 지연 값들을 줄 세웠을 때 95% 지점 값, 가운데 값. "3배" 는 BLIP_FACTOR = 3.0.
- keepalive / PINGREQ: 장치가 "살아 있다"고 주기적으로 보내는 신호(기본 10초). 1.5배 동안 안 오면 브로커가 끊긴 것으로 본다.
- seq 틈: 일련번호가 1 보다 크게 뛴 자리. STALL_GAP_S = 3.0초는 "멈춤" 판정 문턱.
- ceil(5%): 올림. 50 × 0.05 = 2.5 → 3.

## 4. 쉬운 예시
학교 시험 비유: 판정은 채점 기준표다 — "브로커 문제는 50점 이하 감점 허용, DB 문제는 감점 0 이어야 통과". 진단은 틀린 답안을 보고 "왜 틀렸나"를 적는 오답 노트다 — 같은 시각에 20명이 똑같이 틀렸으면(군집) 문제지가 잘못된 것이지 학생 탓이 아니다.

숫자 예시(B 절): 평소 p95 가 2 ms 면 튐 기준은 6 ms. 05:50:08 과 05:50:18 에 p95 가 10 ms 로 튀었고 간격이 정확히 10.0초 → keepalive 10초 박자. 그 초의 msgs/s 가 평소(50)의 3배(150)를 넘었다면 복구 폭주라서 튐에서 뺀다.

## 6. 자주 하는 오해·함정
- "QoS 0 에서 유실이 나왔는데 왜 통과인가?" — 그 실험의 목적이 '보호 없음을 보여 주기'라서 유실 > 0 이 정상이다. 라벨(qos0/qos1)로 규칙이 갈린다.
- "오프라인 이벤트 20 = 장치 20대가 고장"이 아니다. 브로커 종료 시 일괄 유언 중 20개만 전달된 것이고 장치는 멀쩡했다(E09).
- 진단 B 절에서 홍수(복구 폭주)를 빼지 않으면 장애 직후의 큰 지연이 전부 "튐"으로 잡혀 keepalive 박자가 안 보인다.
- 군집을 "직전 이벤트 기준"으로 잇는 실수는 흔하다 — 1초 간격 이벤트가 끝없이 이어 붙는다. 기준을 "군집의 첫 이벤트"로 고정해야 한다.
