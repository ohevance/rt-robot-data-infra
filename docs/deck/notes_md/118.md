# 장표 118 — 통합 테스트 스크립트 (2/2) — 장애 3종 + 나쁜 펌웨어 + 정상 OTA + 산출물 OTA(4b·4c) → 판정 → 표 (integration.sh)
*위치: 6부 믿을 수 있나 · 테스트 — 통합 2/2 (장애·판정)*

## 1. 이 장표가 왜 있나
바로 앞 장표(117)에서 통합 테스트 스크립트의 앞부분을 보았다. 릴리스 패키지를 만들어 내려받을 곳을 열고, 진짜 브로커(Mosquitto)와 진짜 DB(TimescaleDB) 컨테이너를 띄우고, DB 가 "진짜로" 받아 줄 때까지 기다린 뒤, 수집기 1개와 가상 장치 10대를 2 Hz 로 돌려 두는 데까지다. 그러면 질문이 생긴다. "준비는 됐다. 이제 무엇을 일부러 망가뜨리고, 무엇을 보고 통과·실패를 가르나?" 이 장표가 그 답이다. 2부(데이터의 길)에서 만든 장애 주입 도구와 OTA 배포기를 순서대로 부르고, 11/10 부터는 진짜 패키지를 장치에 깔아 보고 깨진 패키지가 거부되는지도 보며, 그 결과 파일 7개를 판정 스크립트에 넣어 "기대한 대로 됐나"를 기계가 판단하게 하고, 같은 결과로 사람이 읽는 표까지 만든다. 이 장표가 끝나면 "사람이 손으로 돌리는 통합 테스트"가 완성되고, 다음 장표부터는 그것을 누가 매번 자동으로 돌리는지(CI)로 넘어간다.

## 2. 장표를 하나씩 읽기
코드 상자 위의 위치는 `fleet/tests/integration.sh:59-77` — 파일의 끝(77줄)까지다. 긴 줄은 상자 너비에 맞춰 끝이 `…` 로 잘려 있다 — 전체는 파일에서 본다.

- 59줄 `echo "--- 3) 장애 주입"`: 화면(그리고 CI 로그)에 지금 몇 번째 단계인지 찍는다. 앞 장표의 0)·1)·2)에 이어지는 번호다. 로그에서 어디서 멈췄는지 바로 찾게 하려는 표시다.
- 60줄 `inject.py --fault broker --duration 5 --settle 8 --out "$OUT/fault_broker.json"`: 브로커 컨테이너를 5초 동안 멈췄다가(stop → start) 다시 켠다. `--settle 8` 은 다시 켠 뒤 8초를 기다렸다가 유실을 센다는 뜻이다(재전송이 끝날 시간을 준다). 도구의 기본값은 `--duration 10`, `--settle 15` 인데, CI 시간을 줄이려고 5초·8초로 짧게 준다. 결과는 JSON 파일 하나(`$OUT` = `build/integration`).
- 61줄 `--fault db`: 같은 방식으로 DB 컨테이너를 5초 멈춘다. 수집기는 그동안 1초 묶음을 메모리(backlog)에 들고 있다가 DB 가 돌아오면 넣어야 한다.
- 62줄 `--fault collector ... --label qos1`: 수집기 프로세스를 SIGTERM 으로 끄고 5초 뒤 다시 켠다. `--label qos1` 은 결과 파일 이름 꼬리표이자 판정 규칙을 고르는 열쇠다 — 수집기가 QoS 1 지속 세션으로 붙어 있으므로 "유실 0" 이어야 한다.
- 63줄 `--fault bad_firmware ... || true`: 나쁜 펌웨어를 단계 배포(5% → 50% → 100%)하면 5% 단계의 헬스 게이트가 잡아 롤백해야 한다(흉내 경로 — 장치가 버전 문자열을 바꾼 뒤 `fault` 를 낸다). 끝의 `|| true` 는 이 명령이 0 이 아닌 종료 코드를 내도 스크립트가 멈추지 않게 한다. 스크립트 맨 위에 `set -euo pipefail`(명령 하나라도 실패하면 즉시 중단)이 걸려 있기 때문에 필요한 안전장치다. 장표의 읽는 포인트대로, 이 줄 주석의 "롤백이면 종료 코드 1 이 정상"은 옛 설명이다 — 지금 `inject.py` 는 결과 파일을 쓰면 0 을 내고(`rollout.py --bad` 를 직접 부르면 1), 롤백이 됐는지는 5) 판정이 결과 파일로 본다(5절).
- 65~66줄 `echo "--- 4) 정상 OTA (흉내: 버전 문자열)"` / `rollout.py --version 1.1.0 --apply-s 1 --health-wait 2 --out "$OUT/ota_1.1.0.json"`: 이번에는 정상 펌웨어 1.1.0 을 배포한다. 매니페스트 없이 `--version` 만 주었으므로 흉내 경로다 — 장치는 1초(`--apply-s 1`) 동안 `updating` 이다가 버전 문자열만 바꾼다. `--health-wait 2` = 단계마다 2초 동안 건강 상태를 지켜본다(기본값은 각각 2초·5초). 세 단계를 모두 통과해야 `success=true`.
- 68~69줄 `echo "--- 4b) 산출물 OTA: 진짜 패키지 내려받기 → sha256 → A/B 슬롯 → 자가 점검 → 전환"` / `rollout.py --manifest "http://127.0.0.1:$HTTP_PORT/manifest.json" --health-wait 2 --out "$OUT/ota_artifact_good.json"`(11/10): 같은 배포기에 이번에는 `--manifest` 를 준다. 배포기는 앞 장의 0단계가 내주는 매니페스트를 읽어 버전(`0.0.0-ci`)과 파일 주소 · sha256 · 크기를 명령에 실어 보내고(장표 079), 장치는 그 파일을 **진짜로** 내려받아 지문을 맞춰 보고, 자기 슬롯 폴더에 풀고, 자가 점검(패키지 안의 실행 파일을 0.5초 켜 보기)을 통과하면 `current` 링크를 새 버전으로 바꾼다(장표 138). 10대가 1 → 5 → 10대 순서로(5 % · 50 % · 100 % 의 올림) 전부 새 버전이 되어야 통과다.
- 70~71줄 `echo "--- 4c) 산출물 OTA: 자가 점검이 실패하는 패키지 → 첫 단계에서 거부·롤백 (종료 코드 1 이 정상)"` / `rollout.py --manifest "…/manifest-bad.json" --health-wait 2 --out "$OUT/ota_artifact_bad.json" || true`: 일부러 깨뜨린 패키지(`0.0.0-ci-bad`)를 같은 방법으로 배포한다. 첫 단계의 장치 1대가 내려받고 풀어서 자가 점검을 돌리면 실패한다(깨진 패키지의 점검 스크립트는 무조건 1 을 낸다). 장치는 `current` 를 건드리지 않고 `state=fault` 와 사유를 알리고, 배포기는 그것을 보자마자 롤백한다. 나머지 9대는 명령을 받은 적이 없다. 이 경우 `rollout.py` 는 종료 코드 1 을 내는 것이 **정상**이라(배포가 성공하지 않았으므로) `|| true` 를 붙였다.
- 73~75줄 `echo "--- 5) 판정"` / `assert_results.py` 에 결과 파일 7개(broker · db · collector_qos1 · bad_firmware · ota_1.1.0 · ota_artifact_good · ota_artifact_bad)를 넘긴다. 판정 스크립트는 파일마다 규칙을 적용해 줄마다 `ok` 또는 `FAIL` 을 찍고, 하나라도 FAIL 이면 종료 코드 1 을 낸다. 그러면 `set -e` 때문에 스크립트 전체가 실패하고, CI 잡도 빨간색이 된다.
- 76줄 `make_table3.py --minutes 10 --label "integration ${COUNT}대 ${RATE} Hz" --measurements "$OUT" --out "$OUT/table3_ci.md"`: 같은 결과 파일들과 DB 의 최근 10분 통계로 표③(처리량·장애·OTA)을 마크다운으로 만든다. 꼬리표는 기본값으로 "integration 10대 2 Hz" 가 된다.
- 77줄 `cat "$OUT/table3_ci.md"`: 만든 표를 로그에 그대로 찍는다. CI 로그만 열어도 숫자가 보이게 하려는 것이다.

읽는 포인트 다섯 줄:
- "3) 장애 3종 각 5초(settle 8): broker · db · collector(qos1). 나쁜 펌웨어 줄의 || true 는 안전장치 — 63줄 주석의 '종료 코드 1' 은 옛 설명이고, 지금 inject.py 는 결과 파일을 쓰면 0 을 낸다(롤백 여부는 5) 판정에서 본다)": 위 60~63줄 설명 그대로다.
- "4) 정상 OTA 1.1.0(흉내 — 버전 문자열만): 세 단계(5 → 50 → 100%)를 다 통과해야 success=true": 나쁜 펌웨어 시험만 하면 "배포기가 늘 롤백만 하는 고장"을 못 잡는다. 정상 배포가 끝까지 가는 것도 확인해야 한다. 괄호의 "흉내"는 4b 와 구분하려고 11/10 에 붙인 말이다.
- "4b) 산출물 OTA(11/10): 진짜 패키지를 내려받아 sha256 → A/B 슬롯 → 자가 점검 → 전환. 4c) 자가 점검이 실패하는 패키지 → 첫 단계에서 거부·롤백(종료 코드 1 이 정상이라 || true). 11/10 밤 4b 가 상대 경로 슬롯에서 exit 127 — CI 가 잡았다(7부 덧붙임 사고 표)": 위 68~71줄. 마지막 문장은 이 단계가 처음 CI 에서 돌았을 때의 사고다 — 장치의 슬롯 폴더를 상대 경로(`build/integration/devices`)로 주었는데, 설치 코드가 자가 점검을 "슬롯 안으로 들어가서" 돌리면서 스크립트 경로를 그 상대 경로 그대로 썼다. 슬롯 안에서 다시 본 상대 경로에는 파일이 없으니 `selftest.sh: No such file`(종료 코드 127 = 명령을 못 찾음)로 첫 장치부터 실패했다. 단위 테스트는 임시 폴더(절대 경로)만 써서 통과했었다. 경로를 절대 경로로 굳히게 고치고, 상대 경로 슬롯에 설치하는 테스트를 더했다(장표 141).
- "5) assert_results.py 가 JSON 7개를 규칙으로 판정 — 하나라도 어긋나면 종료 코드 ≠ 0 → CI 잡 실패": 규칙은 broker = 유실 ≤ 장치 수이고 전 장치 복귀 시간이 있을 것, db = 유실 0 · backlog 0 복귀 시간 있음 · 뒤늦게 들어간 행 > 0, collector(qos1) = 유실 0 · 재시작 뒤 첫 통계 시각 있음, bad_firmware = success=false · 닿은 장치 = 전체의 5%(올림) · 롤백 시간 있음, OTA = success=true · 전 장치 새 버전. 진짜 설치의 결과(`mode` 가 `artifact`)에는 규칙이 하나씩 더 붙는다 — 정상 패키지는 결과에 산출물의 sha256 이 남아 있을 것, 깨진 패키지(버전이 `-bad` 로 끝남)는 success=false · 닿은 장치 = 첫 단계의 올림 수 · 롤백 시간 있음 · 타임라인에 "설치 실패"가 있을 것(자가 점검이 거부해서 멈춘 것인지를 본다).
- "make_table3.py 가 같은 결과 파일($OUT)과 DB 통계로 table3_ci.md 를 만들어 아티팩트로 — 사람이 읽는 표와 CI 의 판정이 같은 원본. WSL 에서도 같은 스크립트(약 3~4분, E13)": 사람이 읽는 표와 기계의 판정이 같은 원본(JSON)에서 나온다. 그래서 둘이 서로 다른 말을 할 수 없다. 개발 PC 에서 돌린 결과와 CI 러너에서 돌린 결과가 같은 모양이었다는 실험이 E13 이다.

## 3. 용어와 단위
- 장애 주입(fault injection): 일부러 부품을 죽여 시스템이 어떻게 견디는지 재는 시험. 여기서는 컨테이너 stop/start 와 프로세스 종료로 한다.
- settle(안정화 시간): 장애를 풀고 나서 숫자를 세기 전에 기다리는 시간(초). 재전송이 다 끝나기 전에 세면 "유실"로 잘못 센다.
- 종료 코드(exit code): 프로그램이 끝날 때 남기는 숫자. 0 = 성공, 0 이 아니면 실패. CI 는 이 숫자 하나로 초록/빨강을 정한다. 127 은 "그런 명령(파일)이 없다"는 셸의 약속된 번호다.
- `set -euo pipefail`: bash 의 "엄격 모드". 실패한 명령(-e), 정의 안 된 변수(-u), 파이프 중간 실패(pipefail)에서 바로 멈춘다.
- `|| true`: "앞 명령이 실패해도 성공으로 친다". 일부러 실패 코드를 낼 수 있는 명령에만 쓴다.
- 산출물(artifact) OTA: 버전 문자열이 아니라 빌드가 만든 **파일**(패키지)을 장치가 받아 설치하는 배포. 흉내 OTA 와 짝이 되는 말이다. CI 의 "아티팩트"(잡이 남기는 파일)와 영어 낱말은 같지만 다른 것이다.
- 매니페스트(manifest): 패키지의 이름 · sha256 · 크기 · 배포 정책을 적은 목록 파일. `--manifest` 로 주면 배포기가 진짜 설치 명령을 만든다.
- 자가 점검(selftest): 새 슬롯을 **켜기 전에** 장치가 돌려 보는 검사. 실패하면 설치를 거부한다.
- 판정(assert): 결과가 규칙에 맞는지 기계가 확인하는 것. 사람 눈 대신 규칙이 판단한다.
- 아티팩트(CI): CI 가 끝난 뒤 내려받을 수 있게 남겨 두는 파일(여기서는 `build/integration/` 전체).
- 단위: 초(s). `--duration 5` = 5초, `--settle 8` = 8초. "10대 2 Hz" = 장치 10대가 각각 1초에 2번 = 초당 20개 메시지.

## 4. 쉬운 예시
- 비유: 소방 훈련. 앞 장표는 건물에 사람을 들여보낸 것(장치 10대 가동), 이 장표는 실제로 화재 경보를 울리고(장애 주입), 몇 명이 몇 초 만에 나왔는지 세고(유실·복구 시간), 점검표(assert_results.py)에 "전원 대피 · 3분 이내"를 체크하는 것이다. 점검표에 하나라도 X 가 있으면 훈련은 불합격이다. 4b · 4c 는 새 소화기를 실제로 나눠 주는 훈련이다 — 멀쩡한 소화기는 전원이 받아 걸고(4b), 압력계가 0 인 소화기는 첫 사람이 받아 보고 "이건 안 된다"고 돌려보내야 한다(4c). 받는 사람이 직접 눌러 보는 것이 자가 점검이다.
- 숫자 예시: 장치 10대 × 2 Hz = 초당 20개. 브로커를 5초 멈추면 그동안 약 100개(20 × 5)가 장치 버퍼에 쌓였다가 재접속 뒤 다시 보내진다. 판정 규칙은 broker 장애에서 유실 ≤ 10(장치 수)을 허용한다 — 브로커가 죽는 순간 이미 소켓에 실려 있던 메시지가 장치당 1개쯤 사라질 수 있기 때문이다(assert_results.py 머리말의 설명).
- 숫자 예시(4b · 4c): 10대의 단계는 ceil(10 × 5 %) = 1대 → ceil(10 × 50 %) = 5대 → 10대. 4b 는 1 + 4 + 5 = 10대가 전부 새 버전, 4c 는 첫 1대가 거부하고 끝이라 닿은 장치 1 / 10 이다. 판정의 "첫 단계의 올림 수"가 이 1 이다. 같은 일을 50대로 한 릴리스 카나리에서는 3 / 50 이었다(장표 139).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 코드는 `fleet/tests/integration.sh` 59~77줄이다(`sed -n '59,77p' fleet/tests/integration.sh`, `wc -l` = 77 — 11/05 에는 40~53줄, 53줄짜리 파일이었다). 장표의 위치 표기와 같다.
- 확인: `--duration`·`--settle` 기본값 10초·15초, `--fault` 선택지(broker, db, collector, bad_firmware, all)는 `fleet/chaos/inject.py` 429~432줄.
- 확인: `--apply-s` 기본 2.0초, `--health-wait` 기본 5.0초, `--max-fail` 기본 0 은 `fleet/ota/rollout.py` 382~384줄과 405~406줄(11/10 부터 뒤의 둘은 '명령줄 → 매니페스트 → 5 · 0' 순서). `--manifest` 는 380줄.

## 6. 자주 하는 오해·함정
- "유실 0 이 통과 기준이니 broker 장애도 0 이어야 한다"는 오해: broker 규칙만 "유실 ≤ 장치 수"다. 소켓에 이미 실린 메시지까지는 막을 수 없다는 것을 규칙에 정직하게 적어 둔 것이다(QoS 1 · persistence true 를 켠 실측은 0 / 1400 이었다 — E08).
- "나쁜 펌웨어 시험이 실패 코드를 내니 CI 가 빨개진다"는 걱정: 그래서 `|| true` 를 붙였고, 성공 여부는 종료 코드가 아니라 판정 스크립트가 JSON 의 `success=false` 를 보고 정한다. 4c 도 같다.
- "`|| true` 가 붙은 줄은 무슨 일이 나도 통과한다"는 걱정: 그 줄 자체는 넘어가지만, 결과 파일이 없거나 내용이 규칙과 다르면 5) 판정에서 걸린다. 다만 한계가 있다 — 4c 의 규칙은 "닿은 장치 수 · 롤백 시간 · '설치 실패' 문구"만 보고 사유의 **내용**(자가 점검 실패인가, 내려받기 실패인가)까지는 가르지 않는다. 사유는 타임라인에 남으니 사람이 읽는다.
- 3) 의 "나쁜 펌웨어"와 4c 의 "깨진 패키지"는 다른 문에서 걸린다. 앞의 것은 설치된 뒤 켜져서 아픈 것(헬스 게이트, 흉내), 뒤의 것은 켜 보기 전에 장치가 거부한 것(자가 점검, 진짜 파일).
- 판정 규칙을 고쳐서 초록을 만드는 함정: 규칙은 "기대한 동작"이지 "지금 나오는 숫자"가 아니다. 숫자가 틀리면 코드를 고쳐야 한다(11/05 CI 빨강 때 고친 것도 수집기 코드였고 — request_stop 복원 — 11/10 에 고친 것도 설치 코드의 경로였다).
- `--settle` 을 너무 짧게 주면 재전송 중인 메시지를 유실로 세는 함정이 있다. 8초는 CI 시간과 정확도 사이의 타협이다.
