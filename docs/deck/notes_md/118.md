# 장표 118 — 통합 테스트 스크립트 (2/2) — 장애 3종 + 나쁜 펌웨어 + 정상 OTA → 판정 → 표 (integration.sh)
*위치: 6부 믿을 수 있나 · 테스트 — 통합 2/2 (장애·판정)*

## 1. 이 장표가 왜 있나
바로 앞 장표(117)에서 통합 테스트 스크립트의 앞부분을 보았다. 진짜 브로커(Mosquitto)와 진짜 DB(TimescaleDB) 컨테이너를 띄우고, DB 가 "진짜로" 받아 줄 때까지 기다린 뒤, 수집기 1개와 가상 장치 10대를 2 Hz 로 돌려 두는 데까지다. 그러면 질문이 생긴다. "준비는 됐다. 이제 무엇을 일부러 망가뜨리고, 무엇을 보고 통과·실패를 가르나?" 이 장표가 그 답이다. 2부(데이터의 길)에서 만든 장애 주입 도구와 OTA 배포기를 순서대로 부르고, 그 결과 파일 5개를 판정 스크립트에 넣어 "기대한 대로 복구됐나"를 기계가 판단하게 하며, 같은 결과로 사람이 읽는 표까지 만든다. 이 장표가 끝나면 "사람이 손으로 돌리는 통합 테스트"가 완성되고, 다음 장표부터는 그것을 누가 매번 자동으로 돌리는지(CI)로 넘어간다.

## 2. 장표를 하나씩 읽기
코드 상자 위의 위치는 `fleet/tests/integration.sh:40-53` — 파일의 끝(53줄)까지다.

- 40줄 `echo "--- 3) 장애 주입"`: 화면(그리고 CI 로그)에 지금 몇 번째 단계인지 찍는다. 앞 장표의 1)·2)에 이어지는 번호다. 로그에서 어디서 멈췄는지 바로 찾게 하려는 표시다.
- 41줄 `inject.py --fault broker --duration 5 --settle 8 --out "$OUT/fault_broker.json"`: 브로커 컨테이너를 5초 동안 멈췄다가(stop → start) 다시 켠다. `--settle 8` 은 다시 켠 뒤 8초를 기다렸다가 유실을 센다는 뜻이다(재전송이 끝날 시간을 준다). 도구의 기본값은 `--duration 10`, `--settle 15` 인데, CI 시간을 줄이려고 5초·8초로 짧게 준다. 결과는 JSON 파일 하나(`$OUT` = `build/integration`).
- 42줄 `--fault db`: 같은 방식으로 DB 컨테이너를 5초 멈춘다. 수집기는 그동안 1초 묶음을 메모리(backlog)에 들고 있다가 DB 가 돌아오면 넣어야 한다.
- 43줄 `--fault collector ... --label qos1`: 수집기 프로세스를 SIGTERM 으로 끄고 5초 뒤 다시 켠다. `--label qos1` 은 결과 파일 이름 꼬리표이자 판정 규칙을 고르는 열쇠다 — 수집기가 QoS 1 지속 세션으로 붙어 있으므로 "유실 0" 이어야 한다.
- 44줄 `--fault bad_firmware ... || true`: 나쁜 펌웨어를 단계 배포(5% → 50% → 100%)하면 5% 단계의 헬스 게이트가 잡아 롤백해야 한다. 끝의 `|| true` 는 이 명령이 0 이 아닌 종료 코드를 내도 스크립트가 멈추지 않게 한다. 스크립트 맨 위에 `set -euo pipefail`(명령 하나라도 실패하면 즉시 중단)이 걸려 있기 때문에 필요한 안전장치다. 장표의 읽는 포인트대로, 주석의 "롤백이면 종료 코드 1 이 정상"은 옛 설명이다 — 지금 `inject.py` 는 결과 파일을 쓰면 0 을 내고(`rollout.py --bad` 를 직접 부르면 1), 롤백이 됐는지는 5) 판정이 결과 파일로 본다(5절).
- 46~47줄 `rollout.py --version 1.1.0 --apply-s 1 --health-wait 2`: 이번에는 정상 펌웨어 1.1.0 을 배포한다. `--apply-s 1` = 장치가 적용에 쓰는 시간 1초(흉내), `--health-wait 2` = 단계마다 2초 동안 건강 상태를 지켜본다(기본값은 각각 2초·5초). 세 단계를 모두 통과해야 `success=true`.
- 49~51줄 `assert_results.py` 에 결과 파일 5개(broker · db · collector_qos1 · bad_firmware · ota_1.1.0)를 넘긴다. 판정 스크립트는 파일마다 규칙을 적용해 줄마다 `ok` 또는 `FAIL` 을 찍고, 하나라도 FAIL 이면 종료 코드 1 을 낸다. 그러면 `set -e` 때문에 스크립트 전체가 실패하고, CI 잡도 빨간색이 된다.
- 52줄 `make_table3.py --minutes 10 --label "integration ${COUNT}대 ${RATE} Hz" --measurements "$OUT" --out "$OUT/table3_ci.md"`: 같은 결과 파일들과 DB 의 최근 10분 통계로 표③(처리량·장애·OTA)을 마크다운으로 만든다. 꼬리표는 기본값으로 "integration 10대 2 Hz" 가 된다.
- 53줄 `cat "$OUT/table3_ci.md"`: 만든 표를 로그에 그대로 찍는다. CI 로그만 열어도 숫자가 보이게 하려는 것이다.

읽는 포인트 다섯 줄:
- "3) 장애 3종 각 5초(settle 8) … 나쁜 펌웨어는 롤백이 정상 결과라 … `|| true`": 위 41~44줄 설명 그대로다.
- "4) 정상 OTA 1.1.0: 세 단계(5 → 50 → 100%)를 다 통과해야 success=true": 나쁜 펌웨어 시험만 하면 "배포기가 늘 롤백만 하는 고장"을 못 잡는다. 정상 배포가 끝까지 가는 것도 확인해야 한다.
- "5) assert_results.py 가 JSON 5개를 규칙으로 판정": 규칙은 broker = 유실 ≤ 장치 수이고 전 장치 복귀 시간이 있을 것, db = 유실 0 · backlog 0 복귀 시간 있음 · 뒤늦게 들어간 행 > 0, collector(qos1) = 유실 0 · 재시작 뒤 첫 통계 시각 있음, bad_firmware = success=false · 닿은 장치 = 전체의 5%(올림) · 롤백 시간 있음, OTA = success=true · 전 장치 새 버전.
- "make_table3.py 가 같은 결과 파일과 DB 통계로 table3_ci.md": 사람이 읽는 표와 기계의 판정이 같은 원본(JSON)에서 나온다. 그래서 둘이 서로 다른 말을 할 수 없다.
- "WSL 에서도 같은 스크립트 … 약 3~4분 … (E13)": 개발 PC 에서 돌린 결과와 CI 러너에서 돌린 결과가 같은 모양이었다는 실험이 E13 이다.

## 3. 용어와 단위
- 장애 주입(fault injection): 일부러 부품을 죽여 시스템이 어떻게 견디는지 재는 시험. 여기서는 컨테이너 stop/start 와 프로세스 종료로 한다.
- settle(안정화 시간): 장애를 풀고 나서 숫자를 세기 전에 기다리는 시간(초). 재전송이 다 끝나기 전에 세면 "유실"로 잘못 센다.
- 종료 코드(exit code): 프로그램이 끝날 때 남기는 숫자. 0 = 성공, 0 이 아니면 실패. CI 는 이 숫자 하나로 초록/빨강을 정한다.
- `set -euo pipefail`: bash 의 "엄격 모드". 실패한 명령(-e), 정의 안 된 변수(-u), 파이프 중간 실패(pipefail)에서 바로 멈춘다.
- `|| true`: "앞 명령이 실패해도 성공으로 친다". 일부러 실패 코드를 낼 수 있는 명령에만 쓴다.
- 판정(assert): 결과가 규칙에 맞는지 기계가 확인하는 것. 사람 눈 대신 규칙이 판단한다.
- 아티팩트(artifact): CI 가 끝난 뒤 내려받을 수 있게 남겨 두는 파일(여기서는 `build/integration/` 전체).
- 단위: 초(s). `--duration 5` = 5초, `--settle 8` = 8초. "10대 2 Hz" = 장치 10대가 각각 1초에 2번 = 초당 20개 메시지.

## 4. 쉬운 예시
- 비유: 소방 훈련. 앞 장표는 건물에 사람을 들여보낸 것(장치 10대 가동), 이 장표는 실제로 화재 경보를 울리고(장애 주입), 몇 명이 몇 초 만에 나왔는지 세고(유실·복구 시간), 점검표(assert_results.py)에 "전원 대피 · 3분 이내"를 체크하는 것이다. 점검표에 하나라도 X 가 있으면 훈련은 불합격이다.
- 숫자 예시: 장치 10대 × 2 Hz = 초당 20개. 브로커를 5초 멈추면 그동안 약 100개(20 × 5)가 장치 버퍼에 쌓였다가 재접속 뒤 다시 보내진다. 판정 규칙은 broker 장애에서 유실 ≤ 10(장치 수)을 허용한다 — 브로커가 죽는 순간 이미 소켓에 실려 있던 메시지가 장치당 1개쯤 사라질 수 있기 때문이다(assert_results.py 머리말의 설명).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 코드는 `fleet/tests/integration.sh` 40~53줄이다(`sed -n '40,53p' fleet/tests/integration.sh`, `wc -l` = 53). 장표의 위치 표기와 같다.
- 확인: `--duration`·`--settle` 기본값 10초·15초, `--fault` 선택지(broker, db, collector, bad_firmware, all)는 `fleet/chaos/inject.py` 429~432줄.
- 확인: `--apply-s` 기본 2.0초, `--health-wait` 기본 5.0초, `--max-fail` 기본 0 은 `fleet/ota/rollout.py` 292~294줄.
- 확인: 종료 코드. `rollout.py` 는 성공이면 0, 롤백(success=false)이면 1, 결과를 못 얻으면 2 를 돌려준다(309~313줄). 그러나 44줄이 부르는 `inject.py --fault bad_firmware` 는 롤아웃 결과를 얻기만 하면 0 을 돌려주고(결과가 None 일 때만 1, `inject.py` 458~459줄), 이때 내부적으로 apply_s 2.0초·health_wait 5.0초를 쓴다(399~401줄). 즉 44줄 주석의 "종료 코드 1 이 정상"은 rollout.py 를 직접 부를 때의 설명이고, `|| true` 는 어느 경우든 멈추지 않게 하는 안전장치다.
- 확인: 판정 규칙 전부는 `fleet/chaos/assert_results.py` 머리말과 `assert_fault()`·`assert_ota()`.
- 확인: `make_table3.py` 의 `--minutes`·`--label`·`--measurements`·`--out` 옵션은 `scripts/make_table3.py` 160~164줄.
- 확인: "WSL 약 3~4분"은 스크립트 7줄 주석. CI 에서의 실제 시간은 `fleet_integration` 1분 52초(docs/LOG.md 11/04, "rt_core 1m13s · mujoco 25s · fleet_integration 1m52s").
- 다시 보기: `bash fleet/tests/integration.sh` 를 WSL 에서 돌리면 마지막에 `OK: all fault/OTA results as expected` 와 표가 찍힌다. CI 에서는 Actions 의 fleet_integration 잡 로그와 아티팩트 `fleet-integration`.

## 6. 자주 하는 오해·함정
- "유실 0 이 통과 기준이니 broker 장애도 0 이어야 한다"는 오해: broker 규칙만 "유실 ≤ 장치 수"다. 소켓에 이미 실린 메시지까지는 막을 수 없다는 것을 규칙에 정직하게 적어 둔 것이다(QoS 1 · persistence true 를 켠 실측은 0 / 1400 이었다 — E08).
- "나쁜 펌웨어 시험이 실패 코드를 내니 CI 가 빨개진다"는 걱정: 그래서 `|| true` 를 붙였고, 성공 여부는 종료 코드가 아니라 판정 스크립트가 JSON 의 `success=false` 를 보고 정한다.
- 판정 규칙을 고쳐서 초록을 만드는 함정: 규칙은 "기대한 동작"이지 "지금 나오는 숫자"가 아니다. 숫자가 틀리면 코드를 고쳐야 한다(11/05 CI 빨강 때 고친 것도 수집기 코드였다 — request_stop 복원).
- `--settle` 을 너무 짧게 주면 재전송 중인 메시지를 유실로 세는 함정이 있다. 8초는 CI 시간과 정확도 사이의 타협이다.
