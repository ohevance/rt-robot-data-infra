# 장표 137 — 덧붙임 (11/10) — 릴리스 → 배포 한 장 그림: 태그 하나로 빌드 · 가상 50대 카나리 · 게시까지, 로봇에 닿는 마지막 걸음은 사람 또는 장치
*위치: 7부 왜·사고·방식 · 덧붙임 릴리스 → 배포 1/3 그림 (11/10)*

## 1. 이 장표가 왜 있나
앞 장표(136)는 "로봇을 바꾸는 일"이 설정 파일 하나였다는 것을 회사의 공개 모델로 보였다. 이 장표부터 세 장(137~139)은 반대쪽 질문이다 — 로봇은 그대로 두고 **그 위의 소프트웨어를 새 버전으로 바꾸는 일**은 어떻게 하나. 2부 ⑥(장표 077~081)의 OTA 는 단계 배포 · 헬스 게이트 · 롤백의 판단은 진짜였지만 장치가 하는 일은 흉내였다: 버전 문자열을 바꾸고 몇 초 잤다. 설치되는 "것"이 없었고, 그 "것"을 누가 만들어 어디에 두는지도 없었다. 공고의 주요 업무에는 "업데이트 시스템 구축"이, 자격 요건에는 "Git, Docker, CI/CD 활용"이 있다 — 이 둘이 한 줄로 이어져 있어야 한다. 11/10 에 그 빈칸을 채웠고, 이 장표는 그 전체를 순서도 한 장으로 보인다: 사람이 태그를 올리면 → 러너가 빌드하고 패키지를 만들고 → 가상 50대에 먼저 깔아 보고 → 통과하면 게시하고 → 로봇에는 사람의 승인 또는 장치 스스로의 판단으로 닿는다. 다음 장표(138)는 맨 끝 상자 — 장치가 그 파일을 실제로 설치하는 코드 — 이고, 그다음(139)은 이 그림을 실제로 돌린 숫자다.

## 2. 장표를 하나씩 읽기
순서도는 왼쪽 위에서 시작해 한 줄에 네 칸씩 뱀처럼 내려온다. 상자 색의 뜻은 다른 순서도 장표와 같다 — 회색은 앞에서 들어온 것, 마름모는 기준(판단), 연파랑은 확인 방법(코드·시험), 흰 상자는 결과, 민트는 실행 단계, 진한 상자는 결론.

- 회색 상자 "11/05 까지의 OTA 는 '흉내' — 버전 문자열을 바꾸고 apply_s 초 잤다 — 설치되는 '것'이 없었다 (2부 ⑥)": 출발점. 장치의 `apply_ota` 는 상태를 `updating` 으로 바꾸고 `apply_s` 초(기본 2초) 잔 뒤 버전 문자열만 새 값으로 바꿨다(장표 065, 079). 서버 쪽 판단(5 % 에서 멈추기)을 시험하기에는 충분했지만 "무엇을 설치하나"가 비어 있었다.
- 마름모 "이 커밋을 로봇에 내보낼지는 누가?" → 답 "사람 — git tag v0.9.0 && git push origin v0.9.0 (push 마다가 아니다)": 첫 판단. 코드를 올리는 일(push)과 로봇에 내보내는 일(릴리스)을 가른다. push 는 하루에도 여러 번 하고 그때마다 CI 가 검사한다. 그러나 "이 커밋을 로봇에 내보낸다"는 결정은 사람이 **이름표(태그)** 를 붙여서 한다. 태그는 저장소의 한 커밋에 붙이는 이름이고, `v` 로 시작하는 태그가 올라오면 릴리스 워크플로가 깨어난다. push 마다 내보내면 그 결정이 사라진다.
- 연파랑 상자 "package × 2 (release.yml) — x86_64 러너 · aarch64(arm) 러너: 빌드 → ctest → tar.gz + sha256 + manifest (+ 깨진 패키지)": 워크플로의 첫 잡. 같은 일을 두 대의 러너가 한다 — 하나는 보통 PC 와 같은 x86_64, 하나는 Pi 와 같은 aarch64(arm). CPU 종류가 다르면 같은 소스도 따로 빌드한 실행 파일이 필요하기 때문이다(가상 장치는 러너에서 도니 x86_64, 실물 Pi 4 는 aarch64). 각 러너는 rt_core 를 빌드하고, C++ 단위 테스트(ctest)를 돌리고, 패키지 스크립트(`scripts/package_release.sh`)로 한 덩어리 파일(tar.gz)을 만든다. 안에는 실행 파일 `jitter_bench`(1 kHz 루프 측정기 — ROS 2 없이 어디서나 켜 볼 수 있는 유일한 "로봇 쪽" 프로그램), 로봇 프로필, 버전 · 커밋, 자가 점검 스크립트가 들어 있다. 스크립트는 그 파일의 지문(sha256)과 크기를 재어 목록 파일(매니페스트)에 적는다. "(+ 깨진 패키지)"는 자가 점검이 일부러 실패하는 패키지를 하나 더 만든다는 뜻 — 다음다음 상자에서 쓴다.
- 연파랑 상자 "canary: 진짜 Mosquitto + 가상 50대(A/B 슬롯) — 정상 패키지를 5 → 50 → 100 % 로 진짜 설치": 둘째 잡. 게시하기 **전에** 방금 만든 패키지를 함대에 깔아 본다. 러너에 진짜 브로커(Mosquitto 컨테이너)를 띄우고 가상 장치 50대를 붙인다. 장치마다 설치 자리 폴더(A/B 슬롯)가 있어 파일을 진짜로 내려받고, 지문을 맞추고, 풀고, 켜 보고, 전환한다. 배포기(`rollout.py --manifest`)가 2부와 같은 방식으로 3대 → 25대 → 50대 순서로 넓힌다. 스크립트는 `fleet/tests/release_canary.sh`.
- 마름모 "50대 전부 새 버전, 헬스 OK?" → 답 "예: 50 / 50, 1.2 → 2.2 → 2.2초 (v0.9.0)": 정상 패키지의 기준. 세 단계가 모두 통과해 50대 전부가 새 버전이고 상태가 정상이어야 한다. 화살표의 숫자는 정식 릴리스 v0.9.0(11/11)의 실제 값 — 단계마다 "명령을 보내고 그 단계의 장치 전부가 새 버전을 보고할 때까지" 1.2초, 2.2초, 2.2초(자세한 읽는 법은 장표 139).
- 연파랑 상자 "같은 함대에 깨진 패키지 (selftest.sh 가 exit 1)": 이어서 같은 50대에 일부러 깨뜨린 패키지를 배포한다. 깨진 패키지는 자가 점검 스크립트가 무조건 실패(종료 코드 1)한다는 것 말고는 정상 패키지와 같다. "깨진 빌드는 첫 단계에서 멈춘다"는 말은 깨진 빌드를 실제로 넣어 봐야 증명되므로, 릴리스마다 한 번씩 넣는다.
- 마름모 "첫 단계 3대에서 거부·롤백?" → 답 "예: 3 / 50, 롤백 1.0초 / 아니오 → 게시 안 함": 깨진 패키지의 기준. 첫 단계(5 % = 3대)의 장치가 자가 점검에서 거부하고, 배포기가 그것을 보고 되돌려야 한다. v0.9.0 의 값은 닿은 장치 3 / 50, 롤백 1.0초. "아니오 → 게시 안 함"이 이 그림의 문이다 — 두 마름모 중 하나라도 통과하지 못하면 판정(`assert_results.py`)이 실패하고, 다음 잡(publish)은 시작하지 않는다(`needs: canary`).
- 흰 상자 "publish: GitHub Release — tar.gz 2 + manifest.json + 카나리 JSON 2 (태그에 '-' 가 있으면 사전 릴리스)": 셋째 잡이자 결과. 저장소의 Releases 화면에 다섯 파일이 올라간다 — 두 아키텍처의 패키지, 둘을 합친 매니페스트, 그리고 방금 카나리가 남긴 결과 파일 둘(정상 · 깨진 것). 깨진 패키지 자체는 올리지 않는다(카나리 전용). 태그 이름에 `-` 가 있으면(`v0.9.0-rc1`) 사전 릴리스(시험판)로 올린다 — 아래 "자율"의 장치는 정식 릴리스만 받는다.
- 마름모 "로봇에 닿는 마지막 걸음은?" → 답 "둘 중 하나": 여기까지는 GitHub 안의 일이다. 게시된 파일이 실제 장치에 닿는 길은 둘이고, 러너가 직접 밀어 넣는 길은 **없다**(아래 줄의 이유).
- 민트 상자 "승인: 사람이 rollout.py --manifest <Release 주소> — 가상 먼저, 실물(kind=real)은 마지막 단계 / 자율: Pi 가 latest/manifest.json 을 10분마다 — state=ok · 03~05시 · 정식 릴리스만": 두 길.
  - 승인 모드: 운영자가 브로커에 닿는 곳에서 배포기를 직접 돌린다. 게시된 매니페스트의 주소를 주면, 배포기는 함대에 단계 배포를 한다 — 가상 장치가 앞 단계를 맡고 실물(텔레메트리의 `kind` 가 `real`)은 맨 뒤로 정렬되어 마지막 단계에서만 받는다. 로봇에 손대는 마지막 걸음을 사람이 누르는 방식이다.
  - 자율 모드: 실물 Pi 의 에이전트가 10분마다 "최신 정식 릴리스"의 매니페스트(`releases/latest/download/manifest.json`)를 읽고, 자기 버전과 다르면 스스로 설치한다. 조건 셋 — 상태가 `ok` 일 때만, 정해 둔 시간대(03~05시)에만, 정식 릴리스만(`latest` 주소는 사전 릴리스를 가리키지 않는다). 지휘하는 서버가 꺼져 있어도 된다.
- 진한 상자 "장치: 내려받기 → sha256 → 슬롯 → 자가 점검 → current 전환 (다음 장표)": 어느 길로 오든 장치가 하는 일은 같은 코드다(`fleet/agent/ota_apply.py` 의 `install`). 가상 장치 50대와 실물 Pi 가 같은 함수를 쓴다. 그 코드가 다음 장표.
- 아래 줄 "왜 이렇게: '내보낸다'는 결정은 사람이(태그), 함대 차원의 검증은 가상 50대가 릴리스마다, 실물은 지휘소 없이 스스로 — 노트북은 항상 켜 둘 수 없기 때문이다. 러너가 실물에 직접 배포하지 않는 이유: 러너는 집 안의 브로커에 닿지 못하고, 공개 저장소의 self-hosted runner 는 위험하며, 로봇이 태그 하나에 무인으로 바뀌면 안 된다": 이 그림의 모양을 정한 조건과 버린 길.
  - 조건: 개발 PC(노트북)는 항상 켜져 있지 않다. 항상 켜져 있는 것은 GitHub 와 Pi 뿐이다. 그래서 검증과 보관은 GitHub 가, 설치는 장치가 스스로 하게 나눴다. 실물은 1대라 "5 % 에서 멈추기"를 실물로는 보일 수 없으니, 함대 차원의 검증은 가상 50대가 릴리스마다 맡는다.
  - 버린 길 ①: 러너가 집의 브로커에 붙어 직접 배포 — GitHub 의 러너는 집 안 네트워크에 닿지 못한다.
  - 버린 길 ②: Pi 나 PC 를 GitHub 의 "내 러너"(self-hosted runner)로 등록 — 닿기는 하지만, 공개 저장소에서는 남이 보낸 변경 요청의 코드가 내 기기에서 돌 수 있어 GitHub 도 말리는 방식이다.
  - 버린 길 ③: 태그 하나에 실물까지 완전 자동 — 로봇이 사람 없이 밤중에 바뀌는 것은 좋은 설계가 아니다. 자율 모드도 그래서 시간대와 "정식만"으로 묶었다.
- `다음 ▶` 다리 "장치의 설치 — 게시된 파일을 장치는 어떻게 '반쯤 깔린 상태 없이' 설치하나? (ota_apply.install)": 이 그림의 맨 끝 상자를 코드로 연다.

## 3. 용어와 단위
- 릴리스(release): "이 커밋을 내보낸다"고 정해 이름(버전)을 붙이고 패키지를 만들어 게시한 것. 배포(deploy, rollout)는 그 패키지를 장치에 까는 일이다.
- 태그(tag): 저장소의 한 커밋에 붙이는 이름표. `git tag v0.9.0` 으로 만들고 `git push origin v0.9.0` 으로 올린다.
- 워크플로 / 잡: GitHub Actions 의 자동화 파일 하나(`release.yml`)와 그 안의 작업 묶음. 여기서는 package 가 두 번(러너 두 종류), canary, publish — 모두 네 잡.
- 러너(runner): 잡을 돌리는 GitHub 의 일회용 가상 컴퓨터. `ubuntu-24.04`(x86_64)와 `ubuntu-24.04-arm`(aarch64).
- 아키텍처 x86_64 / aarch64: CPU 의 종류. 보통 PC·서버와 러너가 앞의 것, Raspberry Pi 4 가 뒤의 것. 실행 파일은 아키텍처마다 따로 빌드한다.
- tar.gz: 여러 파일을 한 덩어리로 묶어 압축한 파일. 여기서는 약 21 KB.
- sha256: 파일 내용에서 계산한 64자리 지문. 한 글자만 달라도 지문이 달라진다. 받은 파일이 만든 파일과 같은지(무결성) 확인하는 데 쓴다 — 누가 만들었는지(진위)는 말해 주지 않는다.
- 매니페스트(manifest): 릴리스 하나의 목록 파일(JSON) — 버전, 아키텍처별 파일 이름 · sha256 · 크기, 커밋, 배포 정책(단계 비율 · 헬스 대기 · 제한 시간).
- 카나리(canary): 전체에 내보내기 전에 일부에 먼저 깔아 보는 것. 여기서는 두 겹이다 — 릴리스 전체를 게시하기 전에 가상 함대에 깔아 보는 것, 그리고 그 안에서 5 % 부터 넓혀 가는 것.
- A/B 슬롯: 버전마다 폴더를 따로 두고 `current` 링크로 "지금 쓰는 것"을 가리키는 설치 방식(다음 장표).
- 자가 점검(selftest): 장치가 새 버전을 켜기 전에 돌려 보는 검사.
- 사전 릴리스(pre-release): 시험판. GitHub 의 "최신(latest)" 주소가 가리키지 않는다.
- self-hosted runner: GitHub 의 러너 대신 내 컴퓨터를 러너로 등록하는 기능.
- 5 → 50 → 100 %: 누적 비율. 50대면 3대 → 25대 → 50대(올림).

## 4. 쉬운 예시
- 비유: 급식 새 메뉴. 영양사(작성자)가 "이 조리법을 내보낸다"고 도장을 찍으면(태그), 중앙 조리실(러너)이 두 종류의 주방(x86_64 · aarch64)에 맞춰 각각 조리해 도시락(패키지)으로 싸고, 내용물 표(매니페스트)에 무게와 봉인 번호(크기 · sha256)를 적는다. 학교에 보내기 전에 시식단 50명(가상 50대)에게 3명 → 25명 → 50명 순서로 먹여 본다(카나리). 일부러 상한 도시락도 하나 내 본다 — 처음 3명이 "이건 못 먹는다"고 돌려보내야 합격이다. 합격하면 배급소 선반(GitHub Release)에 올린다. 학교(로봇)에 가는 길은 둘 — 영양사가 직접 날짜를 정해 나눠 주거나(승인), 학교가 새벽 3~5시에 선반을 확인해 스스로 가져간다(자율). 조리실 직원이 학교 문을 열고 들어가 직접 배식하지는 않는다.
- 숫자 예시: 정식 릴리스 v0.9.0(11/11 09:48 무렵). 태그를 올린 뒤 게시까지 1분 27초. 그 안에서 가상 50대 설치가 14.62초(3대 1.2초 → 22대 2.2초 → 25대 2.2초, 단계마다 헬스 대기 3초), 깨진 패키지는 1.0초에 3대가 거부했고 1.0초에 되돌렸다. 패키지 크기는 aarch64 21,726바이트 · x86_64 21,446바이트.
- 승인 모드의 명령(주소의 `<owner>/<repo>` 는 이 저장소): `python3 fleet/ota/rollout.py --manifest https://github.com/<owner>/<repo>/releases/download/v0.9.0/manifest.json`. 자율 모드의 장치가 읽는 주소는 `…/releases/latest/download/manifest.json` — 버전 이름 대신 `latest` 다.

## 6. 자주 하는 오해·함정
- "태그를 올리면 로봇이 바로 바뀐다"는 오해: 태그는 게시까지만 한다. 로봇에 닿는 것은 사람의 승인이거나, 장치가 정한 시간대에 스스로다. 11/11 낮에 v0.9.0 이 게시됐어도 Pi 는 새벽 03~05시가 되어야 받는다.
- "가상 50대가 통과했으니 실물도 된다"는 오해: 카나리는 x86_64 패키지를 러너에서 깐 것이다. 실물용 aarch64 패키지가 Pi 에서 켜지는지는 따로 확인해야 하고, 그래서 Pi 가 직접 받아 설치해 본 기록이 있다(장표 139, E22). 카나리가 증명하는 것은 "배포의 판단과 설치 코드"이고, 아키텍처는 실물이 증명한다.
- "sha256 을 확인하니 안전하다"는 과장: 지문은 파일이 깨지지 않았음만 말한다. 누군가 매니페스트와 파일을 함께 바꿔치기하면 지문은 맞는다. 그것을 막는 것은 서명이고 아직 없다(남은 일, 장표 132).
- 깨진 패키지를 게시하지 않는다: 카나리에서만 쓰고 publish 잡이 지운다(`rm -f build/release/*-bad-*`). 게시됐다면 자율 모드의 장치가 받아 갈 수 있다.
- 사전 릴리스의 이름 규칙은 태그의 `-` 하나다. `v0.9.0-rc1` 은 시험판, `v0.9.0` 은 정식. 정식을 시험 삼아 올리면 실물이 그날 밤 받는다 — 그래서 첫 태그는 `-rc1` 이었다.
- "러너가 직접 배포하면 더 자동화된 것 아닌가": 더 자동이지만 더 위험하다. 아래 줄의 세 이유가 그 답이고, 면접에서 "왜 전부 자동이 아닌가"를 물으면 이 줄을 말한다.

## 7. 면접 한 문장
"태그 하나를 올리면 러너가 두 아키텍처로 빌드해 패키지를 만들고, 게시하기 전에 가상 50대에 진짜로 깔아 보고, 일부러 깨뜨린 패키지가 첫 3대에서 거부되는 것까지 확인한 뒤에만 게시합니다. 로봇에 닿는 마지막 걸음은 사람이 승인하거나 장치가 정해진 시간대에 스스로 하게 했습니다 — 러너가 실물에 직접 밀어 넣지 않는 것은 못 해서가 아니라 설계로 정한 것입니다."
