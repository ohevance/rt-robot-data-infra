# 장표 081 — ⑥ OTA 배포기 — 롤백: 새 버전을 받은 모든 장치를 이전 버전으로, 걸린 시간을 잰다
*위치: 2부 데이터의 길 · ⑥ OTA · ② 코드 — rollback*

## 1. 이 장표가 왜 있나
앞 두 장표(079~080)의 `run_stage` 는 두 곳에서 `self.rollback()` 을 부른다 — 적용 시간 초과 때(151줄)와 헬스 게이트에서 비정상이 허용치를 넘었을 때(170줄). 그러면 "되돌린다는 것은 **정확히 무엇을 누구에게** 하는 것이고, 들머리(077)의 기준 '수초 안에 롤백'은 **어떻게 재나**?"가 남는다. 이 장표는 그 함수 `rollback`(174~188줄)이다. 표③-3 의 "롤백 1.0초"라는 숫자가 어느 줄에서 측정되어 어느 파일로 가는지까지가 이 장표의 내용이고, 이것으로 ⑥ OTA 묶음의 코드가 끝난다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/ota/rollout.py:174-188`.

- 174줄 `def rollback(self):` — 인자가 없다. 되돌릴 대상은 항상 `self.updated`(지금까지 새 버전을 받은 모든 장치)이기 때문이다.
- 175줄 독스트링 `"""새 버전을 받은 모든 장치를 이전 버전으로. 걸린 시간을 rollback_s 에 남긴다"""` — 두 일: 되돌리기와 시간 측정.
- 176줄 `t_start = time.monotonic()` — 측정 시작 시각. `monotonic` 은 "항상 앞으로만 가는 시계"로, 컴퓨터의 벽시계가 조정되어도 영향받지 않아 걸린 시간을 재는 데 쓴다. 롤백 시간의 시작점은 "롤백 결정 직후"다.
- 177줄 `self.mark(f"롤백: {len(self.updated)}대에 ota_rollback 전송")` — 타임라인·화면·DB(`events`)에 기록. 5 % 단계에서 멈췄으면 "3대".
- 178~179줄 `for device_id in self.updated:` / `self.w.send(device_id, {"cmd": "ota_rollback"})` — 새 버전을 받은 모든 장치에 `fleet/<id>/cmd` 로 `ota_rollback` 명령(QoS 1). 장치 쪽(`device_agent.py` 165~171줄)은 기억해 둔 `prev_fw_version` 으로 버전을 되돌리고 `state = "ok"` 로 바꾼다. 명령에 버전이 없는 이유: 어느 버전으로 돌아갈지는 장치가 가장 잘 안다(자기가 바꾸기 전 버전).
- 180줄 빈 줄.
- 181줄 `took = wait_until(make_all_restored_check(self), timeout_s=30.0)` — 전부 돌아올 때까지 기다린다. `make_all_restored_check`(201~211줄)는 `updated` 의 모든 장치에 대해 "텔레메트리의 `fw` 가 새 버전이 **아니고** `state` 가 `ok`" 인지 보는 함수. 둘 다 봐야 한다 — 버전만 돌아가고 상태가 아직 fault 면 복구가 아니다. 제한 30초.
- 182~184줄 `if took is None:` / `self.mark("롤백: 시간 초과 (30초) — 수동 확인 필요")` / `self.rollback_s = None` — 30초 안에 전부 돌아오지 않으면 자동으로는 더 할 수 있는 것이 없으므로 "수동 확인 필요"를 남기고 롤백 시간을 None(측정 불가)으로 둔다. 모르는 것을 숫자로 꾸미지 않는다.
- 185~187줄 `else:` / `self.rollback_s = round(time.monotonic() - t_start, 2)` / `self.mark(f"롤백 완료: {len(self.updated)}대 복구, {self.rollback_s}초")` — 걸린 시간을 소수 둘째 자리까지 `rollback_s` 에 넣고 기록한다. 표③-3 의 "롤백 1.0초"가 바로 이 값이다. 끝점은 "닿은 장치 전부가 이전 버전·ok 로 보인 때"다.
- 188줄 빈 줄 — 함수 끝. 반환값은 없다. 호출한 `run_stage` 가 `return False` 로 배포를 중단한다.

오른쪽 "읽는 포인트" 네 줄:
- "ota_rollback 명령 → 장치는 prev_fw_version 으로 돌아가고 state=ok" — 178~179줄과 장치 쪽 코드.
- "전부 돌아올 때까지(30초 제한) 기다려 rollback_s 에 기록 — 11/04: 1.0초, 11/05 리허설: 0.8초" — 181~187줄. 11/04 WSL2 50대 실측은 1.0초(두 번: 1.2.0-bad, 9.9.9-bad-114218). "11/05 리허설 0.8초"는 아래 5절 참고 — 저장소 문서에서 확인되지 않는 숫자다.
- "결과 JSON(ota_<version>.json) + DB events(kind='ota') + ota_rollouts 요약 → 표③-3" — `rollback_s` 는 `run_rollout`(253줄)이 만드는 결과 사전에 들어가 `docs/measurements/ota_<version>.json` 으로 저장되고, `DbLog.summary` 가 `ota_rollouts` 표에 한 줄로 넣는다. `mark` 의 줄들은 `events` 표(kind='ota')에 남는다. `scripts/make_table3.py` 가 JSON 을 읽어 표③-3 을 만든다.
- "나쁜 펌웨어가 닿은 장치 3/50 — 나머지 47대는 명령을 받은 적도 없다(카나리의 뜻)" — 롤백이 가는 대상이 `updated` = 3대라는 것과 같은 말이다. 47대는 `ota` 도 `ota_rollback` 도 받지 않았다.

"다음 ▶" 다리: "⑦⑧ 장애 주입·판정·진단 — 정상 동작은 확인됐다. 각 부품을 일부러 죽여 얼마나 잃고 얼마나 빨리 돌아오는지 재는 도구들 (실험 결과는 3부)". OTA 까지 정상 동작이 확인됐으니 다음 묶음은 고장을 일부러 내는 도구들이다.

## 3. 용어와 단위
- 롤백(rollback): 이전 버전으로 되돌리기.
- `prev_fw_version`: 장치가 새 버전을 적용할 때 기억해 둔 "바꾸기 전 버전". 되돌릴 때 쓰고 비운다.
- `time.monotonic()`: 단조 증가 시계(초). 두 시점의 차로 걸린 시간을 잰다. 벽시계 조정에 영향받지 않는다.
- `round(x, 2)`: 소수 둘째 자리까지 반올림. 1.0초, 0.4초 같은 값이 여기서 나온다.
- 타임아웃 30초: 되돌리기를 기다리는 최대 시간. 적용 대기의 apply_s + 15초와 달리 고정값이다 — 되돌리기는 설치가 아니라 버전 교체라 빠르다고 보고 정한 값.
- `None`: 파이썬의 "값 없음". 측정 불가를 뜻한다.
- `events(kind='ota')`: 배포의 모든 결정이 줄 단위로 남는 DB 표(장표 076). `ota_rollouts`: 배포 한 번의 요약 한 줄.
- 카나리(canary): 소수에 먼저 내려 보는 배포 방식. "닿은 장치 3 / 50"이 그 범위.

## 4. 쉬운 예시
리콜 비유: 새 부품을 단 차 3대(5 %)에서 문제가 나오면 제조사(서버)는 그 3대 소유자에게만 "원래 부품으로 교체하세요" 통지(ota_rollback)를 보낸다 — 어떤 부품이었는지는 정비소(장치)가 기록해 두었다(prev_fw_version). 통지를 보낸 시각부터 3대 모두 "원래 부품, 정상"으로 보고될 때까지 스톱워치를 돌린 것이 롤백 시간이다. 30분 안에 보고가 안 오면 "직접 확인 필요"로 남긴다. 새 부품을 받지 않은 47대는 리콜 대상도 아니다.

숫자 예시: 11/04 WSL2 실측(50대, apply/health 2.0 / 5.0): 5 % 단계 3대 적용 → 헬스 5초 뒤 3 / 3 비정상 → `ota_rollback` 3통 → 장치가 즉시 버전·상태를 바꾸고 다음 1 Hz 텔레메트리에 실림 → 서버가 3대 모두 "이전 버전·ok" 확인 → `rollback_s = 1.0`. 1 Hz 라서 1초 안팎이 바닥이다. CI 러너(10대 2 Hz)에서는 1 / 10 에서 0.4초 — 2 Hz 라 반영이 더 빠르다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 코드 — `sed -n '174,188p' fleet/ota/rollout.py`. `make_all_restored_check`(201~211줄: `fw != version` 이고 `state == "ok"`), `wait_until`(90줄), `run_rollout`(253줄)의 결과 사전과 JSON 저장, `DbLog.event`/`summary`(215~249줄).
- 확인: 장치 쪽 되돌리기 — `fleet/agent/device_agent.py` 165~171줄(`ota_rollback`: `fw_version = prev_fw_version`, `state = "ok"`), 176~186줄(`apply_ota` 가 `prev_fw_version` 을 저장).
- 확인: 롤백 1.0초, 3 / 50 — `docs/measurements/table3.md` 표③-3(1.2.0-bad, 9.9.9-bad-114218 두 실행 모두 1.0초, 2026-11-04), 원본 `docs/measurements/ota_1.2.0-bad.json`, `ota_9.9.9-bad-114218.json`, `fault_bad_firmware.json`(`"rollback_s": 1.0`, `"devices_touched": 3`).
- 확인: CI 러너 0.4초, 1 / 10 — `docs/experiments/E13.md`.
- 추정: 장표의 "11/05 리허설: 0.8초" 는 `docs/LOG.md`·`docs/measurements/` 어디에도 기록이 없다. 그림 078(`ota_seq.mmd`)에 "롤백 완료 0.8~1.0초"로 적혀 있을 뿐이다. 기록된 숫자로는 1.0초(WSL2)와 0.4초(CI)만 말하는 것이 안전하다.
- 다시 재기: `python3 fleet/ota/rollout.py --version 1.2.0-bad --bad`(가상 장치 50대·수집기가 떠 있을 때) → 화면의 "롤백 완료: 3대 복구, N초" 와 `docs/measurements/ota_1.2.0-bad.json` 의 `rollback_s`. DB 에서는 `SELECT version, devices_updated, rollback_s FROM ota_rollouts ORDER BY started_at DESC LIMIT 3;`.

## 6. 자주 하는 오해·함정
- "롤백은 이번 단계 장치만 되돌린다"는 오해. `updated` 전부다. 50 % 단계에서 멈추면 25대가 되돌아간다.
- "버전이 돌아가면 복구"라는 오해. 코드는 버전과 상태 둘 다 본다. 상태가 아직 fault 인 장치는 복구로 치지 않는다.
- 롤백 시간의 바닥은 텔레메트리 주기다. 1 Hz 면 아무리 빨라도 상태 반영에 최대 1초가 걸리므로 "1.0초"는 거의 바닥값이고, 더 빠르게 보이려면 주기를 올려야 한다(CI 의 2 Hz 가 0.4초).
- 30초 시간 초과는 "실패"가 아니라 "자동으로는 모름"이다. `rollback_s` 를 None 으로 두고 사람이 확인하라고 남긴다. 숫자를 지어내지 않는 것이 측정 도구의 기본이다.
- 장치가 꺼져 있어 명령을 못 받으면 QoS 1 이라도 장치가 다시 켜질 때까지 브로커가 들고 있다. 그동안 서버는 30초를 다 기다린 뒤 시간 초과로 끝낸다.
- 장표의 "0.8초(11/05 리허설)"는 문서로 확인되지 않는다. 발표에서는 1.0초(WSL2)·0.4초(CI)를 말한다.

## 7. 면접 한 문장
"롤백은 새 버전을 받은 모든 장치에 ota_rollback 을 보내고, 전부 이전 버전이면서 ok 로 보일 때까지 30초 안에서 기다려 걸린 시간을 rollback_s 에 남깁니다 — 50대 실측에서 1.0초였고 그 숫자가 JSON 과 ota_rollouts 표를 거쳐 표③-3 에 들어갔습니다."
