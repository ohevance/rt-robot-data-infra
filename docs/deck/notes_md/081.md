# 장표 081 — ⑥ OTA 배포기 — 롤백: 새 버전을 받은 모든 장치를 이전 버전으로, 걸린 시간을 잰다
*위치: 2부 데이터의 길 · ⑥ OTA · ② 코드 — rollback*

## 1. 이 장표가 왜 있나
앞 두 장표(079~080)의 `run_stage` 는 세 곳에서 `self.rollback()` 을 부른다 — 설치에 실패한 장치가 보였을 때(203줄, 11/10), 적용 시간 초과 때(210줄), 헬스 게이트에서 비정상이 허용치를 넘었을 때(230줄). 그러면 "되돌린다는 것은 **정확히 무엇을 누구에게** 하는 것이고, 들머리(077)의 기준 '수초 안에 롤백'은 **어떻게 재나**?"가 남는다. 이 장표는 그 함수 `rollback`(249~262줄)이다. 표③-3 의 "롤백 1.0초"라는 숫자가 어느 줄에서 측정되어 어느 파일로 가는지까지가 이 장표의 내용이고, 이것으로 ⑥ OTA 묶음의 코드가 끝난다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/ota/rollout.py:249-262`.

- 249줄 `def rollback(self):` — 인자가 없다. 되돌릴 대상은 항상 `self.updated`(지금까지 새 버전을 받은 모든 장치)이기 때문이다.
- 250줄 독스트링 `"""새 버전을 받은 모든 장치를 이전 버전으로. 걸린 시간을 rollback_s 에 남긴다"""` — 두 일: 되돌리기와 시간 측정.
- 251줄 `t_start = time.monotonic()` — 측정 시작 시각. `monotonic` 은 "항상 앞으로만 가는 시계"로, 컴퓨터의 벽시계가 조정되어도 영향받지 않아 걸린 시간을 재는 데 쓴다. 롤백 시간의 시작점은 "롤백 결정 직후"다.
- 252줄 `self.mark(f"롤백: {len(self.updated)}대에 ota_rollback 전송")` — 타임라인·화면·DB(`events`)에 기록. 5 % 단계에서 멈췄으면 "3대".
- 253~254줄 `for device_id in self.updated:` / `self.w.send(device_id, {"cmd": "ota_rollback"})` — 새 버전을 받은 모든 장치에 `fleet/<id>/cmd` 로 `ota_rollback` 명령(QoS 1). 장치 쪽(`device_agent.py` 203~233줄)이 하는 일은 아래 "읽는 포인트" 첫 줄의 세 가지 중 하나이고, 어느 경우든 끝은 `state = "ok"` 다. 명령에 버전이 없는 이유: 어느 버전으로 돌아갈지는 장치가 가장 잘 안다(자기가 바꾸기 전 버전, 진짜 설치면 슬롯의 `state.json` 이 기억하는 이전 슬롯).
- 255줄 빈 줄.
- 256줄 `took = wait_until(make_all_restored_check(self), timeout_s=30.0)` — 전부 돌아올 때까지 기다린다. `make_all_restored_check`(266~276줄)는 `updated` 의 모든 장치에 대해 "텔레메트리의 `fw` 가 새 버전이 **아니고** `state` 가 `ok`" 인지 보는 함수. 둘 다 봐야 한다 — 버전만 돌아가고 상태가 아직 fault 면 복구가 아니다. 제한 30초.
- 257~259줄 `if took is None:` / `self.mark("롤백: 시간 초과 (30초) — 수동 확인 필요")` / `self.rollback_s = None` — 30초 안에 전부 돌아오지 않으면 자동으로는 더 할 수 있는 것이 없으므로 "수동 확인 필요"를 남기고 롤백 시간을 None(측정 불가)으로 둔다. 모르는 것을 숫자로 꾸미지 않는다.
- 260~262줄 `else:` / `self.rollback_s = round(time.monotonic() - t_start, 2)` / `self.mark(f"롤백 완료: {len(self.updated)}대 복구, {self.rollback_s}초")` — 걸린 시간을 소수 둘째 자리까지 `rollback_s` 에 넣고 기록한다. 표③-3 의 "롤백 1.0초"가 바로 이 값이다. 끝점은 "닿은 장치 전부가 이전 버전·ok 로 보인 때"다.
- 함수는 262줄에서 끝난다. 반환값은 없다. 호출한 `run_stage` 가 `return False` 로 배포를 중단한다.

오른쪽 "읽는 포인트" 네 줄:
- "ota_rollback 명령 → 장치가 하는 일은 셋 중 하나(device_agent.py on_message): 직전 설치를 거부한 장치는 상태만 ok 로(current 가 안 바뀌었으니 되돌릴 것이 없다) / 설치에 성공한 장치는 current 를 이전 슬롯으로 / 흉내 경로면 prev_fw_version 으로" — 253~254줄과 장치 쪽 `device_agent.py` 203~233줄. 장치는 이 순서로 묻는다. ① 직전 설치가 실패했나(`state == "fault"` 이고 `ota_error` 가 있다, 212~216줄): 설치는 `current`(지금 쓰는 슬롯을 가리키는 링크)를 바꾸기 전에 멈췄으므로 되돌릴 슬롯이 없다 — 상태만 `ok` 로 돌린다. ② 슬롯에 이전 버전이 있나(217~226줄): 설치는 성공했는데 같은 단계의 다른 장치가 아파서 서버가 전부 되돌리기로 한 경우다 — `current` 를 이전 슬롯으로 돌린다(`ota_apply.rollback`). ③ 흉내 경로(227~233줄): 기억해 둔 `prev_fw_version` 으로 버전 문자열만 돌린다. 순서가 중요하다 — 11/11 사전 점검에서 ①과 ②의 순서가 뒤바뀌어 있는 것을 찾아 고쳤다(6절).
- "전부 돌아올 때까지(30초 제한) 기다려 rollback_s 에 기록 — 11/04: 1.0초, 11/05 리허설: 0.8초" — 256~262줄. 11/04 WSL2 50대 실측은 1.0초(두 번: 1.2.0-bad, 9.9.9-bad-114218). "11/05 리허설 0.8초"는 아래 5절 참고 — 저장소 문서에서 확인되지 않는 숫자다.
- "결과 JSON(ota_<version>.json) + DB events(kind='ota') + ota_rollouts 요약 → 표③-3" — `rollback_s` 는 `run_rollout`(318줄)이 만드는 결과 사전(353~361줄)에 들어가 `docs/measurements/ota_<version>.json` 으로 저장되고, `DbLog.summary` 가 `ota_rollouts` 표에 한 줄로 넣는다. `mark` 의 줄들은 `events` 표(kind='ota')에 남는다. `scripts/make_table3.py` 가 JSON 을 읽어 표③-3 을 만든다.
- "나쁜 펌웨어가 닿은 장치 3/50 — 나머지 47대는 명령을 받은 적도 없다(카나리의 뜻)" — 롤백이 가는 대상이 `updated` = 3대라는 것과 같은 말이다. 47대는 `ota` 도 `ota_rollback` 도 받지 않았다.

"다음 ▶" 다리: "⑦⑧ 장애 주입·판정·진단 — 정상 동작은 확인됐다. 각 부품을 일부러 죽여 얼마나 잃고 얼마나 빨리 돌아오는지 재는 도구들 (실험 결과는 3부)". OTA 까지 정상 동작이 확인됐으니 다음 묶음은 고장을 일부러 내는 도구들이다.

## 3. 용어와 단위
- 롤백(rollback): 이전 버전으로 되돌리기.
- `prev_fw_version`: 장치가 새 버전을 적용할 때 기억해 둔 "바꾸기 전 버전". 되돌릴 때 쓰고 비운다. 흉내 경로에서만 쓴다.
- 슬롯(A/B) · `current` · `state.json`: 진짜 설치에서 프로그램을 두는 두 칸(A, B)과, 지금 쓰는 칸을 가리키는 링크(`current`), 그리고 "지금 버전 · 이전 버전"을 적어 둔 파일. 새 버전은 쓰지 않는 칸에 풀고 링크만 바꾸므로, 되돌리기는 링크를 다시 바꾸는 일이다(장표 138).
- `ota_error`: 장치가 설치에 실패했을 때 텔레메트리에 싣는 사유 글(200자까지). 이 값이 있으면 "직전 설치를 거부한 장치"다.
- `time.monotonic()`: 단조 증가 시계(초). 두 시점의 차로 걸린 시간을 잰다. 벽시계 조정에 영향받지 않는다.
- `round(x, 2)`: 소수 둘째 자리까지 반올림. 1.0초, 0.4초 같은 값이 여기서 나온다.
- 타임아웃 30초: 되돌리기를 기다리는 최대 시간. 적용 대기의 apply_s + 15초와 달리 고정값이다 — 되돌리기는 설치가 아니라 버전 교체라 빠르다고 보고 정한 값.
- `None`: 파이썬의 "값 없음". 측정 불가를 뜻한다.
- `events(kind='ota')`: 배포의 모든 결정이 줄 단위로 남는 DB 표(장표 076). `ota_rollouts`: 배포 한 번의 요약 한 줄.
- 카나리(canary): 소수에 먼저 내려 보는 배포 방식. "닿은 장치 3 / 50"이 그 범위.

## 4. 쉬운 예시
리콜 비유: 새 부품을 단 차 3대(5 %)에서 문제가 나오면 제조사(서버)는 그 3대 소유자에게만 "원래 부품으로 교체하세요" 통지(ota_rollback)를 보낸다 — 어떤 부품이었는지는 정비소(장치)가 기록해 두었다(prev_fw_version). 통지를 보낸 시각부터 3대 모두 "원래 부품, 정상"으로 보고될 때까지 스톱워치를 돌린 것이 롤백 시간이다. 30분 안에 보고가 안 오면 "직접 확인 필요"로 남긴다. 새 부품을 받지 않은 47대는 리콜 대상도 아니다.

숫자 예시 ①: 11/04 WSL2 실측(50대, apply/health 2.0 / 5.0, 흉내 경로): 5 % 단계 3대 적용 → 헬스 5초 뒤 3 / 3 비정상 → `ota_rollback` 3통 → 장치가 즉시 버전·상태를 바꾸고 다음 1 Hz 텔레메트리에 실림 → 서버가 3대 모두 "이전 버전·ok" 확인 → `rollback_s = 1.0`. 1 Hz 라서 1초 안팎이 바닥이다. CI 러너(10대 2 Hz)에서는 1 / 10 에서 0.4초 — 2 Hz 라 반영이 더 빠르다.

숫자 예시 ②: 진짜 설치, 깨진 패키지(릴리스 카나리 v0.9.0, 러너의 가상 50대, 11/11): 5 % 단계 3대가 자가 점검에서 거부(1.0초에 서버가 봄) → `ota_rollback` 3통 → 세 대는 위 ①의 경우라 상태만 `ok` 로 → 서버가 "새 버전이 아니고 ok" 를 3대 모두 확인 → `rollback_s = 1.0`. 같은 1.0초지만 장치가 한 일은 다르다 — 아무것도 되돌리지 않았다.

## 6. 자주 하는 오해·함정
- "롤백은 이번 단계 장치만 되돌린다"는 오해. `updated` 전부다. 50 % 단계에서 멈추면 25대가 되돌아간다.
- "버전이 돌아가면 복구"라는 오해. 코드는 버전과 상태 둘 다 본다. 상태가 아직 fault 인 장치는 복구로 치지 않는다.
- 롤백 시간의 바닥은 텔레메트리 주기다. 1 Hz 면 아무리 빨라도 상태 반영에 최대 1초가 걸리므로 "1.0초"는 거의 바닥값이고, 더 빠르게 보이려면 주기를 올려야 한다(CI 의 2 Hz 가 0.4초).
- 30초 시간 초과는 "실패"가 아니라 "자동으로는 모름"이다. `rollback_s` 를 None 으로 두고 사람이 확인하라고 남긴다. 숫자를 지어내지 않는 것이 측정 도구의 기본이다.
- 장치가 꺼져 있어 명령을 못 받으면 QoS 1 이라도 장치가 다시 켜질 때까지 브로커가 들고 있다. 그동안 서버는 30초를 다 기다린 뒤 시간 초과로 끝낸다.
- 장표의 "0.8초(11/05 리허설)"는 문서로 확인되지 않는다. 발표에서는 1.0초(WSL2)·0.4초(CI)를 말한다.
- "되돌리기 = 항상 이전 버전으로 내려간다"는 오해(11/11 에 고친 버그). 깨진 패키지를 거부한 장치는 `current` 가 그대로이므로 내려갈 곳이 없다. 고치기 전에는 "슬롯에 이전 버전이 있나"를 먼저 봐서, 두 번째 릴리스 뒤에 깨진 패키지가 오면 거부한 장치가 멀쩡한 현재 버전에서 한 세대 옛 버전으로 내려갔다 — 슬롯이 비어 있던 시험에서는 보이지 않던 것을 태그를 올리기 전 코드 읽기에서 찾았다.

## 7. 면접 한 문장
"롤백은 새 버전을 받은 모든 장치에 ota_rollback 을 보내고, 전부 이전 버전이면서 ok 로 보일 때까지 30초 안에서 기다려 걸린 시간을 rollback_s 에 남깁니다 — 50대 실측에서 1.0초였고 그 숫자가 JSON 과 ota_rollouts 표를 거쳐 표③-3 에 들어갔습니다."
