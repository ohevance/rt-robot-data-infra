# 장표 056 — 단계 10 — 관제로 올린다 — RT 노드가 51번째 장치가 되는 다리 (ros_status_bridge.py)
*위치: 1부 로봇을 움직이는 길 · 단계 10/10 관제로 · ② 코드 — 다리 ros_status_bridge*

## 1. 이 장표가 왜 있나
앞 장표(055)가 로봇 안의 `/rt_status` 가 Grafana 화면까지 가는 길을 그림으로 보여 줬다. 이 장표는 그 길의 첫 상자, 즉 저장소에서 유일하게 ROS 2 와 MQTT 를 동시에 아는 프로그램 `fleet/agent/ros_status_bridge.py`(99줄)를 글머리표 다섯 개로 읽는다. 코드 장표가 아니라 글머리표인 이유는 이 파일이 작고, 요점이 "새 코드를 짠 것이 아니라 가상 장치와 **같은 클래스**를 재사용했다"는 데 있기 때문이다. 오른쪽 말풍선은 1부 10단계를 한 줄로 되짚으며 "본편의 길이 여기서 끝난다"고 선언하고, 남은 두 장(안전 경로 057, 실물로 가면 058)과 2부·3부로의 연결을 예고한다.

## 2. 장표를 하나씩 읽기
- 글머리표 1 "ROS 2 노드(StatusBridge)가 /rt_status 를 구독해 JSON 을 파싱하고, 같은 DeviceAgent 클래스로 fleet/rt-node-1/telemetry 에 1 Hz 로 발행한다 (fleet/agent/ros_status_bridge.py, 99줄)": 파일의 구조. `StatusBridge(Node)` 가 `rt_status` 를 구독해(:31) 받은 JSON 을 파싱해 두고(:33-39), `main()` 이 `DeviceAgent(a.device_id, a.broker, a.port, 1.0 / a.rate, bridge.metrics, …)` 를 만들어(:81) 시작한다. DeviceAgent 가 1초마다 `bridge.metrics()` 를 불러 숫자를 받고 `fleet/rt-node-1/telemetry` 에 발행한다. 메인 루프(:85-87)는 ROS 2 콜백을 돌리면서(`spin_once`) 상태 머신 이름을 장치 상태로 복사한다.
- 글머리표 2 "가상 장치 50대와 다른 것은 metrics_source(어디서 숫자를 가져오나)뿐: 가상 장치는 난수 걸음, 다리는 rt_status 의 wake p99·loop_hz 등": `metrics()`(:41-60)가 돌려주는 dict — `loop_hz`, `wake_p99_us`, `wake_max_us`, `work_p99_us`, `timing_drops`, `watchdog_trips`, `rmw`, `backend`, `sched_fifo`. 가상 장치가 쓰는 `cpu_pct`·`temp_c`·`mem_pct`·`rssi` 는 None 으로 비워 둔다(RT 노드에는 그 센서가 없다). 가상 장치(`virtual_fleet.py`)는 같은 자리에 `VirtualMetrics`(난수 걸음)를 끼운다.
- 글머리표 3 "watchdog 이 tripped 이면 state 도 tripped 로 올라가 Grafana '멈춤·고장 장치' 패널에 잡힌다": 명령이 50 ms 끊기면(단계 5) 노드의 상태 머신이 FAULT 가 되고, 다리의 `state()`(:62-68)가 그 이름을 소문자로 장치 상태에 올린다 → 패널 6 "멈춤·고장 장치 (tripped/fault/updating)" 의 조건(state IN tripped·fault·updating·recovering)에 잡힌다. 지금 코드에서 실제로 올라가는 값은 `fault` 이고, `tripped` 는 JSON 에 `state` 키가 없을 때의 대체값이다(아래 6 절).
- 글머리표 4 "이 다리를 지나면 로봇의 숫자는 2부 '데이터의 길'을 따라간다: 브로커 → 수집기(1초 묶음 COPY) → TimescaleDB → Grafana 'RT 노드: 깨어남 지연 p99' 패널": 다리 이후는 가상 장치와 완전히 같은 길. 수집기가 1초 동안 모은 행을 `COPY` 한 번으로 넣고, 패널 10 이 `telemetry.wake_p99_us` 를 장치별 선으로 그린다.
- 글머리표 5 "실물 로봇도 같다: 로봇 안 컴퓨터(Pi 등)에서 이 다리가 돌고, 관제 서버는 로봇이 가상인지 실물인지 모른다": 다리는 ROS 2 가 있는 쪽(로봇 안)에서 돌고, 서버에는 ROS 2 가 없다. 실물로 바꿔도 이 파일은 그대로다.
- 말풍선 "여기까지가 본편의 길 — ① 명령 → ② DDS → ③ 우편함 → ④ 1 ms 루프 → ⑤ 안전 검사 → ⑥ 백엔드 → ⑦ 움직임 → ⑧ 상태 → ⑨ 기록 → ⑩ 관제. 다음 두 장: 명령이 끊기면(안전 경로) · 실물로 가면 바뀌는 것. 그 다음 2부 데이터의 길, 시험·검증은 3부": 1부의 지도. 10단계가 "정상일 때의 길"이었고, 가로지르기 두 장(057·058)이 비정상과 실물을 다룬다.
- `다음 ▶` "가로지르기 — 10단계는 정상일 때의 길이었다. 명령이 끊기면 무슨 일이 일어나나? (안전 경로)": 057 로의 다리.

## 3. 용어와 단위
- StatusBridge / DeviceAgent: 다리 안의 ROS 2 노드 클래스(구독·파싱) / 관제 쪽 장치 클래스(1초마다 MQTT 발행, 명령 수신, 끊김 때 버퍼). 다리는 전자가 후자에게 숫자를 공급한다.
- metrics_source: DeviceAgent 생성 인자. "호출하면 숫자 dict 를 돌려주는 함수". 다리는 `bridge.metrics`, 가상 장치는 `VirtualMetrics(seed=i)`.
- rclpy / spin_once: ROS 2 파이썬 라이브러리 / 콜백을 한 번 처리하고 돌아오는 함수(0.2초 대기). 메인 루프가 ROS 2 와 상태 복사를 번갈아 하기 위해 쓴다.
- 토픽 이름 규칙 `fleet/<device_id>/telemetry`: 장치마다 다른 주소. 수집기는 `fleet/+/telemetry` 식으로 전부 구독한다.
- 1 Hz / `--rate`: 다리의 발행 주기. 기본 1.0(1초마다). `/rt_status` 도 1 Hz 라 둘이 맞는다.
- 멈춤·고장 장치 패널: `devices` 표에서 state 가 tripped·fault·updating·recovering 인 장치 수를 보여 주는 숫자 패널.
- COPY: PostgreSQL 대량 적재. 1초 묶음으로 DB 왕복을 1번/초로 줄인다.

## 4. 쉬운 예시
- 비유: 외국어(ROS 2)만 하는 직원이 회사 공용 양식(MQTT 텔레메트리)으로 보고하려면 통역(다리) 한 사람만 붙이면 된다. 양식과 결재선(브로커 → 수집기 → DB → 화면)은 다른 직원 50명과 똑같이 쓴다.
- 코드 흐름 예시(한 초 동안): ① 노드가 `/rt_status` 에 `{"loop_hz":1000,"wake_us":{"p99":429.5,…},"state":"RUNNING",…}` 발행 → ② `on_status` 가 파싱해 `latest` 에 저장 → ③ DeviceAgent 의 `tick()` 이 `bridge.metrics()` 를 불러 `{"loop_hz":1000,"wake_p99_us":429.5,…}` 를 받고 `{"device_id":"rt-node-1","seq":N,"state":"running",…}` 와 합쳐 `fleet/rt-node-1/telemetry` 로 발행 → ④ 수집기가 그 초의 51행을 COPY → ⑤ 패널 10 에 점 하나. 명령을 끊으면 50 ms 뒤 `state` 가 `fault` 로 바뀌어 다음 초의 메시지부터 패널 6 숫자가 1 오른다.

## 6. 자주 하는 오해·함정
- "state 도 tripped 로" 는 다리 머리말(:7)과 초기 설계의 표현이고, 현재 `state()` 는 상태 머신 이름을 우선한다 → 워치독이 걸리면 `fault`, 다시 명령이 오면 `recovering` → `ready`. 패널 6 은 네 값을 모두 세므로 동작은 같다. 발표에서는 "비정상 상태로 올라가 패널에 잡힌다"로 말하면 정확하다.
- 다리는 `/rt_status` 가 없으면 빈 dict 를 올린다(`latest = {}` → 모든 값 None, state `unknown`). 노드가 먼저 떠 있어야 한다(`fleet/README.md:104` 주석).
- 다리가 보내는 `wake_max_us`·`work_p99_us`·`timing_drops`·`watchdog_trips` 등은 MQTT 메시지에는 실리지만 수집기 저장 열에 없어 DB 에는 남지 않는다. 장표 2 의 "등" 안에 그 사실이 숨어 있다 — 패널에 보이는 것은 `wake_p99_us`·`loop_hz`·`state` 다.
- 다리의 QoS 는 DeviceAgent 기본값 0(보내고 잊음)이다. 수집기 재시작 중에도 유실 0 이 필요하면 QoS 1 로 띄워야 하는데 다리에는 아직 그 명령줄 인자가 없다.
- 다리는 1 Hz 요약만 올린다. 100 Hz·1 kHz 원본은 단계 9(rosbag2)의 길이다 — 관제와 기록을 나눈 이유는 장표 053.

## 7. 면접 한 문장
"RT 노드를 관제에 올리는 데 새 프로토콜을 만들지 않고, 가상 장치 50대가 쓰는 DeviceAgent 클래스에 '숫자를 어디서 가져오나'만 /rt_status 로 바꿔 끼운 99줄 다리를 붙였습니다 — 서버는 그것이 ROS 2 로봇인지 모르고, 워치독이 걸리면 다른 장치와 같은 멈춤·고장 패널에 잡힙니다."
