# 장표 018 — 단계 3 그림 — 우편함: 일반 스레드가 넣고 RT 스레드가 꺼내는 락 없는 링 버퍼 (한쪽만 넣고 한쪽만 꺼낸다 = SPSC)
*위치: 1부 로봇을 움직이는 길 · 단계 3/10 우편함 · ② 그림 — 링 버퍼 우편함*

## 1. 이 장표가 왜 있나
바로 앞 장표(017, 단계 3 들머리)에서 "명령은 ROS 2 콜백 스레드(일반 우선순위)에서 받고, 제어는 RT 스레드가 한다. 두 스레드 사이에서 RT 스레드가 락(lock, 자물쇠)을 기다리면 그 시간이 전부 지연의 꼬리가 된다"는 문제와 "RT 스레드가 기다리지 않고, 최악 시간이 상수이고, 잃으면 세는가?"라는 기준을 세웠다. 그렇다면 그 '우편함'이 실제로 어떻게 생겼고, 두 스레드가 어디를 만지는지를 눈으로 봐야 다음 두 장(코드 장표 019·020)이 읽힌다. 이 장표는 그 구조를 그림 한 장으로 보여 준다: 왼쪽 회색 영역이 넣는 쪽, 오른쪽 회색 영역이 꺼내는 쪽, 가운데가 칸 64개짜리 링 버퍼(우편함)다. 그림 뒤에 코드(019 on_command, 020 push/pop)와 판단(021 왜 락이 아니라 링인가)이 따라온다.

## 2. 장표를 하나씩 읽기
그림은 왼쪽 → 가운데 → 오른쪽 순서로 읽는다.

- 왼쪽 큰 회색 상자 "ROS 2 실행기 스레드 (일반 우선순위)": 이 영역 안의 일은 전부 ROS 2 가 관리하는 일반 스레드에서 돈다. 일반 우선순위라서 운영체제가 언제든 다른 일을 먼저 시킬 수 있다 — 그래서 이 스레드에는 "제때 끝나야 하는 일"을 두지 않는다.
- 파란 상자 "on_command(msg)": 토픽 `/joint_command` 로 메시지가 올 때마다 불리는 함수다(코드는 019번 장표). 안의 두 줄은 이 함수가 하는 일 두 가지다. 첫째, `position` 배열 길이가 관절 수 6 과 다르면 `bad_commands` 카운터를 1 올리고 그 명령을 버린다 — 틀린 길이의 명령이 RT 쪽으로 넘어가면 배열 밖을 읽을 수 있으므로 여기서 거른다. 둘째, 크기가 고정된 구조체 `JointCommand` 에 값을 복사하고 `stamp_ns = now_ns()` 로 받은 시각을 찍는다. 고정 크기인 이유는 RT 쪽이 메모리 할당 없이 다루게 하기 위해서다.
- 파란 상자 "g_cmd_ring.push(cmd)": 복사한 명령을 링(우편함)에 넣는다. "값을 먼저 쓰고 head 를 release 로 공개"는 순서 규칙이다 — 칸에 값을 다 써 넣은 뒤에야 "여기까지 썼다"는 표시(head)를 공개해야, 꺼내는 쪽이 반쯤 쓰인 값을 읽는 일이 없다. "꽉 차면 false → cmd_ring_full++ (기다리지 않음)": 64칸이 다 찼으면 넣지 못하고 즉시 실패를 돌려주며 카운터만 센다. 기다려서 빈칸이 나길 바라지 않는다.
- 왼쪽 두 파란 상자 사이의 화살표: on_command 가 검사·복사를 끝내면 push 로 간다는 순서.
- 가운데 위 굵은 글 "SpscRing<JointCommand, 64> = 우편함 (칸 64개, 한 칸은 항상 비워 둔다)": 우편함의 정식 이름. `SpscRing` 은 템플릿 클래스이고, `<JointCommand, 64>` 는 "JointCommand 형 값을 64칸에" 라는 뜻이다. 한 칸을 항상 비워 두는 이유는 아래 설명 줄에 있다.
- 가운데 작은 네모 10개: 링의 칸을 그림으로 그린 것이다(실제는 64칸, 그림은 10칸만). 흰 칸은 빈칸, 노란 칸(✉ 표시 4개)은 아직 꺼내지 않은 명령이 들어 있는 칸이다. 50 Hz 명령에 1 kHz 로 비우므로 실제로는 거의 항상 0~1개만 들어 있다 — 노란 칸 4개는 "밀렸다 풀린 순간"을 과장해 그린 것이다.
- "tail ↑ 꺼내는 자리 (RT 가 움직임)" (민트색 글): tail 은 꺼내는 쪽이 다음에 읽을 칸 번호다. RT 스레드만 이 값을 바꾼다.
- "head ↑ 넣는 자리 (ROS 2 가 움직임)" (파란 글): head 는 넣는 쪽이 다음에 쓸 칸 번호다. ROS 2 스레드만 이 값을 바꾼다. 두 번호를 각각 한 스레드만 바꾼다는 것이 "락이 필요 없는" 핵심 조건이다.
- 가운데 아래 설명 세 줄: ① "칸 수가 2의 거듭제곱 → 다음 칸 = (i+1) & 63" — 64 는 2의 6제곱이라 "다음 칸 번호"를 나눗셈(% 64) 대신 비트 연산(& 63)으로 구한다. 결과는 같고 더 빠르다. 63 = 0b111111 이라 64 가 되면 0 으로 되돌아간다. ② "head == tail 이면 비어 있음, 다음 head == tail 이면 꽉 참" — 두 번호가 같으면 빈 것이고, 넣는 쪽의 다음 칸이 꺼내는 쪽 칸과 같아지면 꽉 찬 것으로 본다. 그래서 실제로 담을 수 있는 개수는 63개이고 한 칸은 늘 비어 있다(둘을 구분하기 위한 값싼 규칙). ③ "공유하는 것은 원자 변수 2개(head, tail)뿐 → 락 없음" — 두 스레드가 같이 보는 변수는 딱 둘이고, 둘 다 원자(atomic) 변수라서 읽고 쓰는 도중에 찢어진 값이 보이지 않는다.
- 왼쪽 → 가운데 화살표 "push": push 상자에서 링의 왼쪽 끝으로 들어가는 화살표. 넣는 방향.
- 가운데 → 오른쪽 화살표 "pop": 링의 오른쪽 끝에서 RT 스레드로 나가는 화살표. 꺼내는 방향.
- 오른쪽 큰 회색 상자 "RT 스레드 (SCHED_FIFO 80, 1 kHz)": 이 영역은 실시간 스레드다. `SCHED_FIFO` 는 "더 급한 스레드가 없으면 CPU 를 내놓지 않는" 스케줄링 방식이고 80 은 그 우선순위(1~99), 1 kHz 는 1초에 1,000번 = 1 ms 마다 깬다는 뜻이다(단계 4).
- 민트 상자 "take_latest_command() — 매 주기": 매 주기 우편함을 비우는 함수(코드는 030번 장표). `while (cmd_ring_.pop(cmd)) { }` 는 "꺼낼 것이 없을 때까지 계속 꺼낸다"는 반복문이고, 몸통이 비어 있는 이유는 마지막에 꺼낸 값만 `cmd` 에 남기면 되기 때문이다. "head 를 acquire 로 읽고 tail 의 값을 꺼냄"은 push 의 release 와 짝이 되는 순서 규칙 — head 를 acquire 로 읽으면 그 전에 써 둔 값이 보인다는 것이 보장된다. "전부 비우고 마지막 것만 쓴다"가 정책: 밀렸다 풀린 옛 목표를 순서대로 따라갈 이유가 없다.
- 민트 상자 "desired_[j] = cmd.position[j] / last_cmd_ns_ = now (워치독이 본다) / commands_applied++": 꺼낸 마지막 명령을 목표 배열 `desired_` 에 넣고, 마지막 명령 시각을 적고(워치독이 "50 ms 동안 명령이 없었나"를 이 값으로 판단한다, 단계 5), 적용한 명령 수를 센다.
- 오른쪽 두 민트 상자 사이 화살표: pop 이 끝나면 적용으로 간다는 순서.
- 맨 아래 legend "소스 위치: …": 이 그림의 각 상자가 어느 파일 어느 줄인지. on_command 는 `rt_control_node.cpp:184-201`, 링의 push/pop 은 `spsc_ring.hpp:38-64`, 꺼내는 쪽은 `control_step.cpp:61-79`. "같은 링 클래스가 세 곳에 쓰인다: 명령 우편함 64칸 · 상태 벨트 2048칸 · 타이밍 65536칸" — 클래스 하나를 세 가지 크기로 쓴다(단계 8 에서 벨트와 타이밍 링이 나온다). "왜 락이 아닌가는 두 장 뒤" = 021번 장표.

## 3. 용어와 단위
- 스레드(thread): 한 프로그램 안에서 동시에 도는 실행 흐름. 이 노드에는 ROS 2 실행기 스레드와 RT 스레드가 따로 있다.
- 락(lock, mutex): 두 스레드가 같은 자료를 동시에 만지지 못하게 하는 자물쇠. 하나가 잡고 있으면 다른 하나는 풀릴 때까지 기다린다 — 그 "기다림"이 실시간에서는 독이다.
- 링 버퍼(ring buffer): 칸이 고리처럼 이어진 배열. 끝까지 쓰면 처음으로 돌아간다.
- SPSC: Single Producer / Single Consumer. 넣는 스레드 하나, 꺼내는 스레드 하나. 이 전제가 깨지면(둘 이상이 넣으면) 이 코드는 틀린다.
- head / tail: 넣는 쪽이 다음에 쓸 칸 번호 / 꺼내는 쪽이 다음에 읽을 칸 번호.
- 원자 변수(std::atomic): 읽기·쓰기가 중간에 끊기지 않는 변수. 두 스레드가 같이 봐도 반쯤 바뀐 값이 보이지 않는다.
- release / acquire: 메모리 순서 약속. release 로 공개한 변수를 acquire 로 읽으면, 공개 전에 써 둔 데이터까지 같이 보이는 것이 보장된다.
- SCHED_FIFO 80: 실시간 스케줄링 정책과 우선순위. 1 kHz = 1,000 Hz = 1 ms 마다 한 번.
- 카운터 bad_commands · cmd_ring_full · commands_applied: 각각 길이가 틀려 버린 명령 수, 우편함이 꽉 차 못 넣은 수, RT 가 실제로 적용한 명령 수. 단계 8 의 rt_status 에 1초마다 실린다.

## 4. 쉬운 예시
- 비유: 식당의 주문표 꽂이. 홀 직원(ROS 2 스레드)은 주문표를 꽂이에 꽂기만 하고 주방 문을 두드리지 않는다. 주방장(RT 스레드)은 정해진 박자(1 ms)마다 꽂이를 통째로 걷어 가장 최근 주문만 본다. 꽂이가 가득 차면 홀 직원은 기다리지 않고 "못 꽂았음"을 수첩에 적는다(cmd_ring_full). 홀 직원과 주방장이 서로를 멈춰 세우는 일이 없다.
- 숫자 예시: 명령은 50 Hz(20 ms 에 1개), RT 스레드는 1 kHz(1 ms 에 1번 비움). 20번 비우는 동안 명령은 1개 들어오므로 우편함에는 보통 0개 또는 1개가 있다. 네트워크가 100 ms 밀렸다 풀리면 5개가 한꺼번에 올 수 있는데, 그때도 63개까지는 들어가고 RT 는 그중 마지막 1개만 쓴다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 칸 수 64 는 `rt_control/rt_core/include/rt_core/joint_types.hpp:38` 의 `kCommandRingSize = 64`, 상태 벨트 2048 은 같은 파일 :41, 타이밍 링 65536 은 `rt_loop.hpp:63` (`grep -n "RingSize" rt_control/rt_core/include/rt_core/*.hpp`).
- 확인: "한 칸은 항상 비워 둔다" 와 `(i+1) & (N-1)` 은 `spsc_ring.hpp` 의 `push()`(꽉 참 판정 `next_head == tail`)와 `next_index()` 주석에서 그대로 볼 수 있다 (`sed -n '38,80p' rt_control/rt_core/include/rt_core/spsc_ring.hpp`).
- 확인: release/acquire 짝은 `spsc_ring.hpp` 머리말 주석(memory_order 쉬운 설명)과 push 의 `head_.store(..., release)`, pop 의 `head_.load(..., acquire)`.
- 확인: cmd_ring_full 이 "정상이면 0" 이라는 것은 `rt_control_node.cpp:198-199` 주석. 11/05 실측에서도 0 이었다(`docs/LOG.md` 2026-11-05 오전, rt_status 줄).
- 확인: 노드 안의 전역 링 세 개 선언은 `rt_control_node.cpp:61-63`.

## 6. 자주 하는 오해·함정
- "락 없는 자료구조는 항상 더 빠르다"가 아니다. 여기서 중요한 것은 평균 속도가 아니라 "RT 스레드가 절대 멈춰 기다리지 않는다"는 최악 시간의 상한이다. 021번 장표가 이 차이를 다룬다.
- SPSC 는 넣는 쪽도 하나여야 한다. ROS 2 콜백이 여러 스레드에서 동시에 불리게 실행기를 바꾸면(멀티스레드 실행기) 이 전제가 깨진다 — 이 노드는 콜백(on_command)과 타이머가 하나의 실행기 스레드에서 도는 구조다(`rt_control_node.cpp` 머리말 10줄).
- "버린다"가 데이터 손실처럼 들리지만, 우편함의 명령은 '목표 위치'라서 최신 것만 의미가 있다. 옛 목표를 잃는 것은 손실이 아니다. 반대로 로깅용 벨트(단계 8)에서 버리는 것은 잃는 것이므로 drops 로 센다.
- 그림의 칸 10개와 노란 칸 4개는 설명용이다. 실제 칸은 64개이고 평소에는 거의 비어 있다.

## 7. 면접 한 문장
"두 스레드가 공유하는 것은 원자 변수 두 개(head, tail)뿐인 SPSC 링이라 RT 스레드는 락을 기다리는 일이 없고, 꽉 차면 버리고 세기 때문에 최악 시간이 상수입니다 — 같은 클래스를 명령 64칸, 상태 2048칸, 타이밍 65536칸 세 곳에 씁니다."
