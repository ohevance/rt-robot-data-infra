# 장표 145 — rt-robot-data-infra — 코드와 숫자는 저장소에 있습니다
*위치: 끝*

## 1. 이 장표가 왜 있나
마지막 장표다. 바로 앞(144)에서 "결국 로봇은 이렇게 움직인다"를 상자 10개와 숫자로 접었다. 듣는 사람에게 남는 질문은 하나다. "말한 숫자를 내가 직접 확인하려면 어디를 보면 되나?" 이 장표는 그 답을 네 줄로 준다 — 저장소 주소, 읽는 순서, 장표마다 붙은 설명 문서, 그리고 누가 어떻게 만들었는가. 숫자만 보여 주고 확인할 길을 주지 않으면 그 숫자는 주장일 뿐이다. 그래서 끝은 "코드와 숫자는 저장소에 있습니다"로 닫는다. 이 장표에는 화살표나 다음 장이 없다. 대신 질문이 오면 여기서 저장소로 넘어간다.

## 2. 장표를 하나씩 읽기
- 제목 "rt-robot-data-infra — 코드와 숫자는 저장소에 있습니다": 저장소 이름이 곧 프로젝트 이름이다. "로봇과 무관한 실시간 제어 + 데이터 인프라"라는 뜻이다(README 첫 줄).
- 줄 1 "github.com/ohevance/rt-robot-data-infra — README 첫 표가 공고 ↔ 산출물 ↔ 숫자, 배지가 CI": 저장소 첫 화면(README)의 첫 표는 열이 넷이다 — 직무 요구 · 산출물 · 수치 · 상태. 예를 들어 첫 줄 "① 실시간 Linux 미들웨어, ROS 2/DDS"에는 산출물 `rt_control/rt_core`, `rt_control/ros2_adapter`, `dds_bench` 와 수치 "표① 지연·지터, 표② DDS 손실·지연"이 짝지어 있다. 공고의 문장에서 출발해 코드와 숫자로 한 번에 가는 표다. 그 위의 작은 그림(배지)은 CI 의 최근 결과다. push 할 때마다 GitHub 의 컴퓨터가 잡 3개(rt_core → fleet_integration, mujoco)를 돌리고, 통과하면 초록이 된다.
- 줄 2 "읽는 순서: docs/ENVIRONMENT.md → docs/READING_GUIDE.md(28항목) → docs/EXPERIMENTS.md(순서도) → docs/experiments/(24장) · 릴리스와 운영은 docs/RELEASE.md · deploy/ec2/README.md":
  - ENVIRONMENT: 무엇이 어디서 도는지의 지도. 네 곳 — ① 개발 PC(WSL2, 모든 코드를 실제로 돌린다) ② Raspberry Pi 4(표① 하나만 잰다) ③ GitHub(저장소 + CI) ④ 작성 보조 작업본(코드·문서 초안을 쓰고 컴파일·단위 테스트까지 돌린 뒤 bundle 로 넘긴다). 숫자를 보기 전에 "그 숫자를 어디서 쟀나"부터 알아야 해서 맨 앞이다. 11/10 부터는 다섯째 곳(클라우드 서버 — 운영 층이 24시간 도는 곳)이 더해졌다.
  - READING_GUIDE: 코드 읽는 순서 28항목. D0 측정기(1~8번)부터 D6 기록 파이프라인(26번), 그리고 11/10 의 릴리스 → 배포(27번), 11/10~11 의 클라우드 운영 층·실물 장치(28번)까지 만든 순서대로 묶여 있고, 파일마다 "읽으면서 확인할 것"이 붙어 있다.
  - EXPERIMENTS: 실험의 순서도 한 장과 색인 표 하나. 순서도의 마름모(◇)가 합격 기준이고, 기준을 못 넘으면 화살표가 다음 실험으로 간다. 예: 표①의 합격선은 "부하 중 max < 200 us".
  - experiments/: 실험 한 개에 한 장. E01~E13, E15, E16, E18, E19-a~d, E20~E23 — 모두 24장(+ 안내 README). 11/05 뒤에 더한 것은 E21(ALLEX) · E22(릴리스 → 배포) · E23(서버까지 왕복).
  - RELEASE.md 와 deploy/ec2/README.md: 11/10~11 에 더한 두 문서. 앞의 것은 태그에서 게시까지의 그림과 장치가 설치하는 순서, 뒤의 것은 운영 층을 클라우드 서버에 올린 순서와 확인 방법이다(7부 덧붙임 장표 137~142).
- 줄 3 "장표 설명 문서: docs/deck/notes/NNN.docx (장표 번호와 같다)": 지금 읽는 이 문서 같은 설명이 장표마다 하나씩 있다. 장표 144 의 설명은 `144.docx` 다. 원본 글은 같은 폴더 옆 `docs/deck/notes_md/144.md` 에 있다.
- 줄 4 "작성: 오문규 · AI 보조(Claude, AI 가 쓴 커밋에 Co-Authored-By 표기) · 2026-11-03 ~ 11-11": README "작성 방식"의 내용과 같다 — 설계·검토·측정·해석은 작성자(오문규), 코드 초안과 스크립트·설정 템플릿은 AI 도구(Claude)의 보조로 썼고, 모든 코드는 작성자가 읽고 설명할 수 있게 단순하게 유지한다. AI 가 만든 패치 커밋에는 메시지 끝에 `Co-Authored-By: Claude …` 줄이 붙는다. 날짜는 첫 커밋(11-03)부터 마지막 덧붙임을 넣은 날(11-11)까지다(본편은 11-05). 실제 개수는 5·6절.

## 3. 용어와 단위
- 저장소(repository): 코드·문서·측정 파일과 그 변경 이력 전체를 담은 곳. GitHub 는 그것을 인터넷에 올려 두는 서비스다.
- README: 저장소 첫 화면에 보이는 안내문.
- 배지(badge): README 의 작은 그림. CI 가 통과하면 초록(passing), 실패하면 빨강(failing).
- CI(Continuous Integration, 지속 통합): push 할 때마다 다른 컴퓨터가 빌드와 테스트를 자동으로 돌리는 것. 이 저장소의 세 잡은 11/04 실측으로 1분 13초 · 1분 52초 · 25초 걸렸다.
- 커밋(commit): 저장소에 변경을 한 번 기록하는 단위. 메시지 끝의 `Co-Authored-By:` 줄은 "함께 만든 이" 표기다.
- bundle: git 변경 묶음을 파일 하나로 만든 것. 작업본에서 만든 패치를 작성자 PC 로 옮겨 적용하고 push 하는 데 쓴다.
- 순서도(flowchart): 네모는 한 일, 마름모(◇)는 판단 기준, 화살표의 "예/아니오"가 다음 칸을 정한다.
- .docx: Word 문서 형식. 같은 내용의 원본 글(.md)에서 만들어진다.

## 4. 쉬운 예시
- 면접관이 "Pi 에서 189 us 라는 숫자, 어디서 나왔나요?"라고 묻는다면 네 번 클릭으로 간다. ① README 첫 표 ① 줄의 "표① 지연·지터" → ② `docs/measurements/table1_pi4.md` 의 `pi4_rt_stress_isol` 줄(max 189.3 us, 온도 44.8→64.8 °C, 스로틀 0) → ③ `docs/experiments/E19c.md`(왜 CPU 를 격리했나, 무엇이 남았나) → ④ 코드 `rt_control/rt_core/src/rt_loop.cpp`(절대 시각 타이머, 130줄). 그 측정을 올린 커밋도 `git log` 에서 `measurements: 표① Pi 4 PREEMPT_RT 실측` 으로 찾을 수 있다.
- "AI 가 다 한 것 아닌가요?"라고 묻는다면: 무엇을 잴지, 합격선을 몇으로 둘지, Pi 와 WSL 에서 실제로 돌리고 결과를 해석한 것은 작성자이고, 코드 초안은 AI 보조로 썼다고 README 와 커밋에 적어 두었다고 답한다. 그리고 함수는 40줄 이하, 숫자마다 단위와 이유를 적는 규칙(READING_GUIDE 의 작성 규칙)으로 작성자가 어느 줄이든 설명할 수 있게 했다고 덧붙인다. 장표 145장마다 붙은 설명 문서가 그 준비의 증거다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: README 7줄이 CI 배지(`actions/workflows/ci.yml/badge.svg`), 9줄부터 첫 표(직무 요구 · 산출물 · 수치 · 상태). "작성 방식"은 84줄부터.
- 확인: READING_GUIDE 의 표가 1~28번(27번이 11/10 의 릴리스 → 배포, 28번이 클라우드 운영 층·실물 장치) — `grep -c '^| [0-9]' docs/READING_GUIDE.md`.
- 확인: `docs/experiments/` 의 E 문서 24개(E01~E13, E15, E16, E18, E19a~d, E20~E23)와 README — `ls docs/experiments/E*.md | wc -l`.
- 확인: 설명 문서는 `docs/deck/notes_md/NNN.md` 가 원본이고 `docs/deck/build/make_notes.sh` 가 `docs/deck/notes/NNN.docx` 로 바꾼다.
- 확인: CI 세 잡 시간 `rt_core` 1m13s · `mujoco` 25s · `fleet_integration` 1m52s — `docs/LOG.md` 11/04.
- 확인(11/11, 이 문서를 고칠 때의 git log 기준 — 이 장표를 넣는 커밋 직전): 커밋 61개 중 51개에 `Co-Authored-By: Claude` 줄이 있다. 없는 10개는 측정 결과 커밋 4개(`measurements: …`), D5 실측 커밋 3개, 병합 커밋 2개, README 배지 주소 1개다(11/05 에 셌을 때와 같은 10개). 날짜는 11-03 4개 · 11-04 19개 · 11-05 21개 · 11-06 8개 · 11-10 6개 · 11-11 3개. 커밋이 늘면 숫자도 바뀌므로 말하기 전에 아래 명령으로 다시 센다.
- 추정: 표기가 없는 10개는 작성자가 WSL 에서 직접 만든 커밋(측정 결과 올리기, bundle 병합, 배지 주소 수정)으로 보인다. 정확한 것은 작성자가 확인한다.
- 다시 보기: [WSL 창] `git log --format='%h %ad %s' --date=short | head -20` 과 `git log --format=%B | grep -c "Co-Authored-By: Claude"`.

## 6. 자주 하는 오해·함정
- "모든 커밋에 표기"라고 말하는 함정: 표기는 AI 가 쓴 커밋에만 있다(11/11 기준 61개 중 51개). 면접에서는 "AI 보조로 만든 패치 커밋에는 표기했고, 측정 결과 커밋과 병합은 제가 직접 했습니다"처럼 개수와 맞게 말하는 편이 안전하다. 말하기 전에 위의 `git log` 명령으로 직접 센다.
- "24장인데 번호는 E23 까지" 혼란: E14·E17 번호는 없고, E19 는 a~d 네 장이다 → 13(E01~E13) + 2(E15·E16) + 1(E18) + 4(E19a~d) + 4(E20~E23) = 24. 두 번호가 빈 이유는 문서에 적혀 있지 않다.
- "배지가 초록이면 Pi 숫자도 다시 쟀다"는 오해: CI 는 GitHub 의 일반 가상 컴퓨터에서 돈다. RT 커널도 Pi 도 없다. CI 가 내는 지연 숫자는 `--no-rt` 참고값이고, 표①은 Pi 에서 사람이 잰 것이다(ENVIRONMENT 5절).
- README 첫 문단은 "2주 일정으로 만들고 있다"고 적는다(진행 중인 저장소다): 장표의 숫자와 README 표가 어긋나 보이면 `docs/measurements/` 의 측정 파일이 기준이다.
- 설명 문서는 .md 가 원본이다: 내용을 고칠 때는 .md 를 고치고 docx 를 다시 만든다. docx 만 고치면 다음 생성 때 사라진다.

## 7. 면접 한 문장
"오늘 말씀드린 숫자는 모두 저장소에서 README 첫 표 → 측정 파일 → 실험 문서 → 코드 줄 순서로 1분 안에 확인하실 수 있고, 설계·측정·해석은 제가, 코드 초안은 AI 보조로 썼다는 것도 README 와 커밋에 그대로 적어 두었습니다."
