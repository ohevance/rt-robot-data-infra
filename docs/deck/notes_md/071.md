# 장표 071 — ③ 수집기 — 받는 쪽: on_message 는 파싱해서 pending 에 넣기만 한다
*위치: 2부 데이터의 길 · ③ 수집기 · ② 코드 — on_message*

## 1. 이 장표가 왜 있나

들머리(069)에서 수집기가 풀어야 할 문제 셋(빠르게, DB 가 죽어도, 내가 죽어도)을 정했다. 그 답을 코드로 보여 주는 첫 장표다. 수집기는 두 개의 스레드(동시에 도는 두 갈래 일꾼)로 되어 있다: 브로커에서 메시지가 올 때마다 불리는 **받는 쪽**(paho 라이브러리의 콜백 스레드)과 1초마다 한 번 도는 **넣는 쪽**(메인 스레드). 이 장표는 받는 쪽인 `on_message` 함수다. 핵심 질문은 "받는 쪽은 왜 DB 를 직접 만지지 않고 임시 목록(pending)에 넣기만 하나?" — 답은 빠르고 안전하게 받기 위해서다. 받는 쪽이 DB 를 기다리면 메시지가 밀리고, DB 가 죽으면 받는 것 자체가 멈춘다.

## 2. 장표를 하나씩 읽기

파일은 `fleet/collector/collector.py` 153~181줄. 아래 줄 번호는 그 파일 기준이다.

- 153줄 `def on_message(self, client, userdata, msg):` — paho MQTT 라이브러리가 메시지를 받을 때마다 부르는 함수. `msg` 안에 토픽 이름, 내용(payload), 보관 여부(retain)가 들어 있다.
- 154~156줄 `parts = msg.topic.split("/")`, `if len(parts) != 3: return` — 토픽 이름을 "/" 로 자른다. 우리 토픽은 `fleet/<장치이름>/telemetry` 또는 `fleet/<장치이름>/status` 로 항상 세 조각이다. 세 조각이 아니면 우리 메시지가 아니니 무시한다.
- 157~158줄 `device_id = parts[1]`, `kind = parts[2]` — 가운데 조각이 장치 이름, 마지막 조각이 종류(telemetry 또는 status).
- 159~167줄 상태(status) 메시지 처리.
  - 160~163줄 `if msg.retain: self.retained_status_skipped += 1; return` — 보관(retained) 메시지면 세기만 하고 버린다. 보관 메시지란 브로커가 "마지막 값"을 기억해 두었다가 새 구독자에게 바로 넘겨 주는 것. 그것은 "지금 상태"이지 "방금 일어난 일"이 아니므로 사건(events) 표에 넣으면 안 된다. 11/04 에 브로커 persistence 를 켠 뒤 재시작할 때마다 오프라인 이벤트가 50개씩 더 세어지던 사고의 수정이다.
  - 164줄 `status = msg.payload.decode("utf-8", errors="replace")` — 내용은 "online" 또는 "offline" 글자. 깨진 글자가 있어도 죽지 않게 errors="replace".
  - 165~167줄 `with self.lock: self.pending_status.append((device_id, status, datetime.now(timezone.utc)))` — 잠금(lock)을 잡고 임시 목록에 (장치, 상태, 지금 시각)을 붙인다. 잠금은 받는 스레드와 넣는 스레드가 같은 목록을 동시에 만지지 않게 하는 자물쇠다.
- 168~169줄 `if kind != "telemetry": return` — status 도 telemetry 도 아니면 무시.
- 170줄 `parsed = parse_telemetry(msg.payload, time.time_ns())` — JSON 내용을 행(row)으로 바꾸고 전달 지연을 계산하는 함수(63줄). 두 번째 인자는 **도착 시각**(나노초).
- 171~173줄 `if parsed is None: self.dropped_bad += 1; return` — JSON 이 깨졌거나 device_id·ts_ns 가 없으면 '나쁜 메시지'로 세고 버린다. 수집기가 죽지 않는 것이 먼저다.
- 174줄 `row, latency_ms = parsed` — 행 튜플과 전달 지연(ms)을 받는다.
- 175~181줄 잠금 안에서 네 가지를 기록한다: `pending_rows.append(row)`(행 목록), `pending_latency.append(latency_ms)`(지연 목록 — 1초 뒤 p50/p95/max 통계에 쓴다), `last_seen[device_id] = time.monotonic()`(이 장치를 마지막으로 본 시각 — '온라인' 판정용. 단조 시계라 시각 보정에 흔들리지 않는다), `last_seen_wall[device_id] = datetime.now(timezone.utc)`(179줄, 11/10 에 더한 줄 — 같은 순간의 벽시계 시각. devices 표의 last_seen 칸에 '그 장치의 마지막 메시지가 도착한 시각'으로 쓴다), `fw_of[device_id] = row[9]`, `state_of[device_id] = row[10]`(행의 10번째·11번째 칸 = 펌웨어 버전과 상태 — devices 표 갱신용).

읽는 포인트 네 줄(넷째 줄은 11/10 에 고쳐 썼다):
- "paho 콜백 스레드에서 돈다 — DB 를 만지지 않는다(1초 묶음은 메인 스레드)": 받는 쪽은 목록에 붙이는 일만 하므로 한 메시지 처리에 마이크로초 단위면 끝난다. DB 가 느리거나 죽어도 받는 것은 계속된다.
- "status 메시지 중 retain=1(보관 값)은 '지금 상태'이지 사건이 아니다 → events 에 넣지 않는다": 위 160~163줄.
- "parse_telemetry 가 ts_ns 와 도착 시각으로 전달 지연(ms)을 계산": 장치가 메시지에 넣어 보낸 측정 시각(ts_ns, 나노초)과 수집기 도착 시각의 차 = 장치 → 수집기 전달 지연. 같은 PC 시계일 때만 그대로 뜻이 있다(가상 장치와 수집기가 같은 PC 에 있으므로 성립). 장치와 서버가 다른 기계면(11/10 부터 실물 Pi 와 클라우드 서버) 두 시계의 차이가 섞이므로, 시계 하나로 재는 왕복과 맞춰 본 뒤에 인용한다(장표 142).
- "last_seen(단조 시계)으로 '온라인'(5초 안에 본 장치)을 세고, last_seen_wall(벽시계)은 devices 표에 '그 장치의 마지막 메시지 도착 시각'으로 쓴다 — 11/10 전에는 본 적 있는 장치 전부를 매초 지금 시각으로 덮어써, 꺼진 장치가 온라인으로 보였다(실제 1대, 표시 4대)": 1초마다 묶음을 만들 때(take_batch, 184줄) 최근 5초 안에 메시지를 보낸 장치 수를 online 으로 센다. 11/10 에 운영 층을 클라우드 서버에 올려 처음으로 '수집기는 계속 돌고 장치만 떠난' 상태가 생기자 버그가 보였다: 붙어 있는 것은 Pi 1대인데 Grafana 의 "온라인 장치(최근 5초)" 숫자가 4 였다. 30분 전에 끈 가상 장치 3대의 last_seen 이 매초 새로워지고 있었다 — 수집기가 본 적 있는 장치 전부를 devices 표에 매초 '지금 시각'으로 덮어썼기 때문이다. 그때까지는 실험이 끝나면 수집기도 같이 내려서 보이지 않았다. 고친 뒤(take_batch 196~203줄)에는 최근 5초 안에 보낸 장치만, 그 장치의 마지막 도착 시각(last_seen_wall)으로 쓴다. 테스트는 `test_stale_device_last_seen_not_refreshed`(DECISIONS 11/10).

## 3. 용어와 단위

- **콜백(callback)**: "이런 일이 생기면 이 함수를 불러 달라"고 라이브러리에 맡겨 둔 함수. on_message 는 "메시지가 오면" 불린다.
- **paho**: 파이썬에서 MQTT 를 쓰는 표준 라이브러리 이름(paho-mqtt).
- **스레드(thread)**: 한 프로그램 안에서 동시에 도는 일꾼. 수집기는 받는 일꾼(paho 네트워크 스레드)과 넣는 일꾼(메인)이 따로 돈다.
- **잠금(lock, threading.Lock)**: 두 스레드가 같은 목록을 동시에 고치면 망가질 수 있어, 한 번에 하나만 들어가게 하는 자물쇠.
- **토픽(topic)**: MQTT 의 주소. `fleet/vdev-001/telemetry` 처럼 "/" 로 계층을 나눈다. 수집기는 `fleet/+/telemetry`(+ 는 아무 이름) 로 전 장치를 한 번에 구독한다.
- **payload**: 메시지의 내용물. 여기서는 JSON 글자.
- **retain(보관)**: 발행할 때 retain=1 로 보내면 브로커가 그 토픽의 마지막 값으로 기억해 두었다가 새 구독자에게 즉시 준다.
- **JSON**: `{"device_id": "vdev-001", "seq": 12, ...}` 처럼 이름:값 쌍으로 적는 글자 형식.
- **ts_ns / time.time_ns()**: 나노초(10억분의 1초) 단위의 벽시계 시각. 1 ms = 1,000,000 ns. 지연은 (도착 − 측정) ÷ 1,000,000 으로 ms 가 된다.
- **monotonic 시계**: 뒤로 가지 않는 시계(벽시계를 사람이 바꿔도 영향 없음). "마지막으로 본 지 몇 초 됐나" 같은 경과 시간 계산에 쓴다.
- **pending**: '아직 처리 안 된, 대기 중인' 목록.

## 4. 쉬운 예시

- 비유: 식당 주문 창구(on_message)는 주문서를 받아 주방 바구니(pending)에 넣기만 한다. 창구 직원이 주문마다 직접 요리까지 하면 줄이 길어지고, 주방 가스가 끊기면(DB 죽음) 주문조차 못 받는다. 요리사(메인 스레드)는 1분마다 바구니를 통째로 가져가 한꺼번에 처리한다.
- 숫자 예시: 장치가 12:00:00.000 에 측정한 값(ts_ns)이 12:00:00.001 에 수집기에 도착하면 전달 지연 = 1.0 ms. 50대가 1초에 50개를 보내니 pending_latency 에는 1초에 50개의 지연값이 쌓이고, 1초 뒤 정렬해 p50(가운데 값)·p95·max 를 낸다 — 11/04 실측 p50 약 1 ms, p95 약 2 ms.

## 5. 숫자의 출처와 다시 확인하는 법

- 확인: 코드 줄 — `sed -n '153,182p' fleet/collector/collector.py`.
- 확인: 보관 유언 재수신으로 오프라인 이벤트 +50 사고 — `docs/LOG.md` 11/04 "증상(새 발견): persistence true 뒤로 …", 코드 머리말 "보관(retained) 상태 메시지는 '이벤트'가 아니다".
- 확인: 전달 지연 p50 / p95 ≈ 1 / 2 ms — `docs/measurements/table3.md` 표③-1 (WSL2, 가상 50대).
- 확인: 온라인 = 최근 5초 — `collector.py` 184줄 take_batch 의 `< 5.0`, Grafana 패널 1 "온라인 장치 (최근 5초)".
- 다시 보려면: 수집기를 띄우고 1초마다 찍히는 한 줄 `msgs/s=50 online=50 ... transit ms p50=... p95=...` 을 본다. 나쁜 메시지 수는 같은 줄의 `bad=`.

## 6. 자주 하는 오해·함정

- "받았으면 저장된 것"이 아니다. on_message 는 메모리 목록에 넣을 뿐이고 DB 에는 최대 1초 뒤에 들어간다. 그래서 종료 순간의 1초치를 따로 챙겨야 한다(장표 074).
- 보관(retain) 상태를 사건으로 세면 대시보드의 "오프라인 이벤트"가 실제보다 두 배로 보인다 — 실제로 겪은 사고.
- 전달 지연은 "장치 측정 → 수집기 도착"이지 "→ DB 에 보임"이 아니다. 묶음 적재의 최대 1초는 포함되지 않는다(표③ 각주에 명시).
- 장치와 수집기가 다른 컴퓨터에 있으면 시계가 달라 이 지연값은 뜻을 잃는다. 그래서 DDS 쪽(표②)은 왕복(RTT)으로 쟀다.

## 7. 면접 한 문장

"받는 쪽은 파싱해서 목록에 붙이기만 하고 DB 는 1초마다 메인 스레드가 묶어서 넣는다 — 그래야 DB 가 느리거나 죽어도 받는 것이 멈추지 않고, 보관 메시지는 사건이 아니라고 걸러야 오프라인 수가 두 배로 안 보인다."
