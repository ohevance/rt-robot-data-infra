# 장표 005 — 로봇을 움직이는 길 — 명령에서 움직임까지 (위에서 아래로)
*위치: 1. 로봇을 움직이는 길 — 명령에서 움직임까지*

## 1. 이 장표가 왜 있나
목차(003·004)에서 전체 뼈대를 봤으니 이제 1부로 들어간다. 1부는 이 자료의 몸통이고, 들어가기 전에 "앞에서 무엇을 알았고(출발), 이 장이 어떤 질문에 답하며, 그 답은 어떤 모양으로 올 것인가"를 한 장에 적는 것이 이 장 구분 장표의 역할이다. 모든 부의 첫 장표가 같은 꼴([앞에서 안 것] → ◇[이 장의 질문] → [이 장의 답] + 이 장의 차례)인데, 1부는 그 첫 사례다. 특히 여기서 "시험·검증은 3부로 미루고 번호만 적는다"를 다시 한번 못 박는다.

## 2. 장표를 하나씩 읽기
- 번호 "01" 과 제목 "로봇을 움직이는 길 — 명령에서 움직임까지 (위에서 아래로)": 1부의 이름. "위에서 아래로"는 top-down, 즉 명령이 생기는 꼭대기에서 로봇이 움직이는 바닥까지 한 방향으로 내려간다는 뜻.
- 부제: 명령이 생겨서 관절이 움직이고, 그 결과가 기록·관제까지 가는 10단계. 단계마다 같은 꼴 — 들어온 것 → 문제 → ◇기준 → 핵심 코드(파일:줄) → 결과 → 판단 → 다음. 시험·검증은 3부로 미루고 번호만 적는다.
- 회색 상자 "앞에서 안 것": 출발: 로봇을 움직이고 싶다 — 관절 6개짜리 팔(SO-ARM100 모델)에 '이 각도로 가라'를 전하면 실제로 움직이게 하려면? 이 저장소의 로봇은 MuJoCo 물리 시뮬레이터 안의 SO-ARM100 팔 모델(관절 6개)이다.
- 마름모 "이 장의 질문": 명령 하나가 로봇의 움직임이 되기까지 무엇을 거치고, 각 단계의 코드는 어디에 있고, 어떤 기준을 넘어야 다음으로 가나? 질문이 세 겹이다 — 과정(무엇을 거치나), 위치(코드는 어디에), 기준(무엇을 넘어야).
- 진한 상자 "이 장의 답": 10단계를 위에서 아래로. 먼저 왕초보 바탕 지식과 한 장 그림, 소스 코드 지도. 단계마다 들머리 장표(들어온 것 → 문제 → 기준 → 확인 방법 → 결과 → 판단) 뒤에 핵심 코드 장표. 기준을 넘었다는 증거(실험)는 '확인 → 장표 N' 으로 3부를 가리킨다.
- 이 장의 차례 1: 바탕 지식(관절·rad·Hz·us·실시간) → 한 장 그림 → 소스 코드 지도(단계 ↔ 파일:줄 ↔ 장표). 단계로 들어가기 전의 준비 장표 셋(실제로는 구조도와 '두 세계' 그림까지 다섯 장).
- 이 장의 차례 2: ① 명령이 생긴다 → ② ROS 2/DDS 가 전달 → ③ 노드가 우편함에 넣는다 → ④ RT 스레드가 1 ms 마다 깬다 → ⑤ 제어 단계가 안전하게 만든다 → ⑥ 백엔드가 로봇에 쓴다 → ⑦ 로봇이 이렇게 움직인다 → ⑧ 상태를 읽어 올린다 → ⑨ 기록한다 → ⑩ 관제로 올린다. 왜 이 순서인가: 데이터가 실제로 흐르는 순서다. 명령은 ①에서 생겨 ②로 전달되고 ③에서 RT 스레드로 넘어가 ④⑤⑥을 거쳐 ⑦에서 움직임이 되고, 그 결과가 ⑧⑨⑩으로 밖으로 나간다.
- 이 장의 차례 3: 가로지르기: 명령이 끊기면(안전 경로) · 실물 로봇으로 가면 바뀌는 것 → 다음: 2부 데이터의 길 (시험·검증은 3부). "가로지르기"는 열 단계 중 한 단계에 속하지 않고 여러 단계에 걸치는 주제 둘이다.

## 3. 용어와 단위
- 관절(joint) 6개: SO-ARM100 팔의 shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper (`robots/so101.yaml`).
- SO-ARM100 / SO-101: 저가 로봇팔 모델. 이 저장소는 MuJoCo Menagerie 의 trs_so_arm100 모델을 쓴다(SO-101 과 같은 5축+그리퍼 구성).
- MuJoCo: 물리 시뮬레이터. 중력·접촉·모터를 계산해 "실제처럼" 움직이게 한다.
- 들머리: 단계의 첫 장표. 여섯 상자로 그 단계를 요약.
- RT 스레드: 실시간(real-time) 우선순위로 1 ms 마다 깨는 스레드. ⑤의 "안전하게 만든다"는 워치독·변화량 제한·상태 머신을 뜻한다.
- 백엔드(backend): 제어 코드가 로봇에 값을 쓰고 읽는 창구. SimLag(단순 모델) / MuJoCo(물리) / 실물(자리만) 세 가지.

## 4. 쉬운 예시
비유: 택배가 주문에서 문 앞까지 오는 길을 열 단계로 나눈 안내문과 같다 — 주문(①), 전산 전달(②), 물류센터 입고(③), 정해진 시각마다 출발하는 배송차(④), 안전 검사(⑤), 배달 기사(⑥), 문 앞 도착(⑦), 배송 완료 문자(⑧), 배송 기록(⑨), 본사 관제 화면(⑩). 숫자 예시: ④의 배송차는 1 ms 마다 출발한다(1 kHz). 주문(명령)은 20 ms 마다 하나(50 Hz)씩 오므로 배송차 20대 중 1대만 새 주문을 싣고 나머지는 "지난 주문 그대로"를 실어 나른다 — 단계 1과 5에서 설명한다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 관절 6개와 모델 — `robots/so101.yaml` 의 `dof: 6`, `joints: [...]`, `mujoco.model: third_party/mujoco_menagerie/trs_so_arm100/scene.xml`.
- 확인: 10단계의 각 단계가 어느 파일인지 — 9번 장표(소스 코드 지도).
- 확인: 1부 범위 5–58 — `docs/deck/SLIDES.md`.

## 6. 자주 하는 오해·함정
- "RT 스레드가 1 ms 마다 깬다"를 "명령이 1 ms 마다 온다"로 혼동하기 쉽다. 명령은 50 Hz(20 ms 마다), 제어 루프는 1 kHz(1 ms 마다)로 다르다. 루프는 매 주기 "가장 최신 명령"을 쓴다.
- 1부에서는 측정 결과를 길게 보여 주지 않는다. 들머리의 '결과' 한 줄과 '확인 → 장표 N' 만 있으니, 숫자가 궁금하면 그 번호(3부)로 간다.
- 이 장표의 "로봇"은 시뮬레이션 모델이다. 실물로 가면 무엇이 바뀌는지는 58번 장표.

## 7. 면접 한 문장
"1부는 명령 하나가 관절의 움직임이 되는 열 단계를 데이터가 흐르는 순서 그대로 따라갑니다 — 단계마다 들어온 것, 풀어야 할 문제, 넘어야 할 기준, 그 코드의 파일과 줄 번호, 결과, 판단을 같은 꼴로 보여 줍니다."
