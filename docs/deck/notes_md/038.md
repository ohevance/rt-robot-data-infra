# 장표 038 — 단계 6 그림 — 백엔드: 제어 코드는 '세 함수'만 알고, 로봇은 그 아래에서 갈아 끼운다
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ② 그림 — 인터페이스와 세 구현*

## 1. 이 장표가 왜 있나
앞 장표(037, 단계 6 들머리)에서 "안전 검사를 통과한 값(applied_)을 누가 로봇에 쓰나? 로봇이 수식·시뮬레이터·실물로 바뀔 때 제어 코드가 같이 바뀌면 안 된다"는 문제를 세웠다. 이 장표는 그 답인 **백엔드(Backend) 인터페이스**를 한 장의 층 그림으로 보여 준다. 위층은 제어 단계(단계 5), 가운데는 가상 함수 세 개짜리 인터페이스, 아래층은 그것을 구현한 로봇 셋(A 수식, B 물리, C 실물 자리)이다. 핵심 주장은 한 줄 — "로봇을 바꿔도 제어 코드는 한 줄도 안 바뀐다" — 이고, 그것이 말이 아니라 11/04 에 실제로 일어난 일(SimLag → MuJoCo 교체)이라는 점이다. 다음 장표 039 는 가운데 층의 코드(backend.hpp)다.

## 2. 장표를 하나씩 읽기
위에서 아래로 세 층이고, 왼쪽 위에 "어느 것을 쓸지" 상자, 오른쪽 위에 결론 말풍선이 있다.

- 민트 상자 "ControlStep (제어 단계, 단계 5) — 매 주기 write_command(applied_, dof) → read_state(position_, velocity_, dof)": 단계 5 의 함수가 한 주기에 백엔드를 두 번 부른다. 안전 검사를 통과한 목표 `applied_`(관절 6개)를 쓰고, 로봇의 실제 위치·속도를 읽는다. 제어 단계는 이 두 호출 뒤에 무엇이 있는지 모른다.
- 화살표 "세 함수만 부른다": 위층 → 가운데층. 제어 코드가 로봇에 대해 아는 전부가 이 세 함수의 이름과 인자다.
- 호박색 육각형 "Backend 인터페이스 (backend.hpp:17-33) — 가상 함수 세 개": `init(dof, period_ns)` 는 시작 때 한 번 부르며 여기서는 메모리 할당이 허용된다(RT 스레드 밖). `write_command(target, dof)` 와 `read_state(position, velocity, dof)` 는 RT 스레드에서 매 주기 불리므로 기다리는 일(락·파일·할당)이 금지다. 이 규칙은 `backend.hpp` 머리말 12번째 줄에 그대로 적혀 있다.
- 파란 상자 "A SimLagBackend (sim_lag_backend.cpp:21-38)": 로봇 흉내 1호. 매 주기 `position += (target − position) × 0.02`. 0.02 는 주기 ÷ 시정수 = 1 ms ÷ 50 ms. 50 ms 뒤에 목표의 63% 에 닿는 1차 지연(서보가 목표를 서서히 따라가는 성질)만 흉내 내고, 중력·충돌·관절 한계는 없다. 로봇도 시뮬레이터도 없는 PC 와 CI 러너에서 노드 전체(명령 → 루프 → 발행 → 워치독)를 돌려 보는 용도.
- 보라 상자 "B MujocoBackend (mujoco_backend.cpp:226-252)": 물리 시뮬레이터. 매 주기 `ctrl[액추에이터] ← 목표` 를 넣고 `mj_step` 을 substeps 번 밟은 뒤 `qpos`(위치)·`qvel`(속도)을 읽는다. "걸음 맞추기 :110-125" 는 제어 주기 1 ms 를 모델의 걸음(timestep)으로 나눠 올림(ceil)한 횟수만큼 밟는 함수 `tune_timestep` — 이 모델은 1 ms = `mj_step` 1번. 모델은 DeepMind Menagerie 의 SO-ARM100(5축 + 그리퍼 = 6자유도). 한 주기 비용 p99 8.5 us(GitHub 러너)는 1 ms 예산의 0.9%.
- 회색 점선 상자 "C FeetechSerialBackend (자리만, 2주 밖)": 실물 SO-101 의 Feetech 서보 6개를 시리얼 1 Mbps 버스로 다루는 구현. 아직 코드가 없고 프로필에 자리만 있다(`robots/so101.yaml` 의 `backend.real: feetech_serial`, `serial.baud: 1000000`, `servo_ids` 6개). 버스 한계 때문에 `loop_hz.real: 200` — 실물로 가면 1 kHz 가 아니라 200 Hz 로 돈다. 점선은 "예정"이라는 뜻. "바뀌는 것은 이 상자뿐 — 위 두 층은 그대로"가 이 장표의 요점이다.
- 화살표 "구현 A / 구현 B / 구현 C (예정, 점선)": 인터페이스 하나를 셋이 구현한다(C++ 상속 — `class SimLagBackend : public Backend`).
- 흰 상자 "어느 것을 쓸지: 노드 파라미터 backend: sim_lag | mujoco (make_backend) ← robots/so101.yaml → profile_to_params.py": 어떤 구현을 띄울지는 코드가 아니라 ROS 2 파라미터가 정한다. `rt_control_node.cpp:135` 의 `make_backend()` 가 문자열 `"sim_lag"` 면 SimLag 를, `"mujoco"` 면 MuJoCo 를 만든다(MuJoCo 없이 빌드됐으면 FATAL 로 알려 준다). 그 파라미터 파일은 사람이 두 번 적지 않도록 로봇 프로필 `robots/so101.yaml` 에서 `scripts/profile_to_params.py` 가 만든다. 점선(머리 없음)은 "선택이 인터페이스 층에 꽂힌다"는 표시.
- 호박색 말풍선 "로봇을 바꿔도 제어 코드는 한 줄도 안 바뀐다 — 11/04 SimLag → MuJoCo 교체로 확인": `control_step.cpp` 와 노드는 그대로 두고 백엔드만 바꿨는데 결과가 달라졌다(어깨 처짐, 단계 7). 인터페이스를 둔 이유가 실행으로 증명된 날.
- legend "소스 위치: …": 상자 ↔ 파일:줄. 물리 비용 측정(E15)은 3부 장표 96.

## 3. 용어와 단위
- 인터페이스 / 가상 함수(virtual): "이런 이름·인자의 함수가 있다"만 정한 약속. C++ 에서 `virtual … = 0` 으로 적으면 구현은 자식 클래스가 채운다. 제어 코드는 약속만 보고 부른다.
- 구현(implementation) / 백엔드(backend): 약속을 실제로 채운 클래스. 여기서는 "로봇 쪽"이라는 뜻으로 백엔드라 부른다.
- 1차 지연(first-order lag): `출력이 목표를 향해 차이의 일정 비율씩 다가가는` 가장 단순한 동역학. 시정수(time constant) 50 ms 는 목표의 63% 에 닿는 시간.
- MuJoCo / mj_step / timestep / ctrl / qpos / qvel: 물리 엔진 / 물리를 한 걸음 진행시키는 함수 / 그 걸음 크기(초) / 액추에이터 입력 배열(position 타입이면 "원하는 각") / 관절 위치 배열 / 관절 속도 배열.
- substeps: 제어 주기 하나 안에 `mj_step` 을 밟는 횟수. ceil(주기 ÷ 걸음). 걸음은 모델 값보다 작게만 바꾼다(키우면 물리가 불안정).
- Menagerie: DeepMind 가 검증해 모아 둔 로봇 모델 모음. `scripts/get_mujoco.sh` 가 `third_party/` 에 받는다(저장소에는 안 들어 있다).
- Feetech STS3215 / 시리얼 1 Mbps: SO-101 에 쓰는 서보와 그 통신 버스 속도(초당 100만 비트). 서보 6개를 한 버스로 묻고 답하면 1 kHz 는 무리라 200 Hz.
- dof: 자유도(degrees of freedom) = 관절 수 6.
- us: 마이크로초(1/1,000,000 초). 1 ms = 1,000 us.

## 4. 쉬운 예시
- 비유: 전원 콘센트 규격. 벽(제어 코드)은 "구멍 두 개, 220 V" 라는 약속(인터페이스)만 지키고, 거기에 전기난로(SimLag)든 세탁기(MuJoCo)든 로봇청소기(실물)든 꽂아 쓴다. 가전을 바꿀 때 벽을 뜯지 않는다. 어느 가전을 꽂을지는 사람이 정한다(파라미터).
- 숫자 예시(백엔드만 따로 볼 때): 목표 0.3 rad 를 SimLag 에 주면 1 ms 뒤 0.006 rad(0.3 × 0.02), 50 ms 뒤 약 0.19 rad(63%), 250 ms 뒤 거의 0.3. 노드 안에서는 단계 5 의 변화량 제한이 목표 자체를 0.05 rad 씩 6주기에 나눠 넣으므로 앞부분 모양이 조금 다르다. 같은 목표를 MuJoCo 에 주면 관절 0 이 2초에 0.2988 rad 까지 간다(CI 측정). 어깨(Pitch)에 −0.2 를 주면 SimLag 는 −0.200 에 정확히 닿지만 MuJoCo 는 −0.180 에서 멈춘다 — 중력 때문(단계 7).

## 6. 자주 하는 오해·함정
- "SimLag 도 시뮬레이터"가 아니다. 수식 한 줄이라 물리가 없다 — 그래서 중력 처짐을 못 본다. 노드 배선을 시험하는 도구로만 쓴다.
- `write_command` 안에서 `mj_step` 을 부르는 것은 "쓰기" 함수가 물리까지 진행시킨다는 뜻이다. 읽기(`read_state`)는 진행시키지 않고 읽기만 한다. SimLag 는 반대로 읽을 때 한 주기를 진행시킨다(:29 주석). 어느 쪽이든 "쓰기 → 읽기" 한 쌍이 한 주기만큼 시간이 간다는 약속은 같다.
- 백엔드는 RT 스레드에서 돈다. 그래서 `init` 에서만 할당하고, 매 주기 함수에서는 파일·락·네트워크를 쓰지 않는다. 실물 백엔드도 시리얼 쓰기·읽기를 "기다리지 않게" 짜야 하며, 그 때문에 주기가 200 Hz 로 내려간다.
- 1 kHz 가 지켜지는지는 물리 비용(0.9%)이 아니라 깨어남 지연(단계 4, 표①)이 정한다 — E15 의 결론.
- MuJoCo 는 저장소에 들어 있지 않다(`third_party/`, gitignore). 빌드 옵션 기본 OFF 라 MuJoCo 가 없는 PC 에서도 그대로 빌드된다.

## 7. 면접 한 문장
"제어 코드는 로봇에 대해 init·write_command·read_state 세 함수만 알고, 그 아래를 1차 지연 수식에서 MuJoCo 물리로 갈아 끼웠을 때 제어 코드가 한 줄도 안 바뀐 채 결과(중력 처짐)가 달라졌습니다 — 인터페이스를 둔 이유를 실행으로 증명한 것이고, 실물 서보 백엔드도 같은 자리에 들어갑니다."
