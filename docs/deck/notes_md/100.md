# 장표 100 — 2부 ⑦⑧ 검증 — 표③-2 · ③-3 — 장애 주입과 OTA (WSL2, 가상 50대 1 Hz, 2026-11-04)
*위치: 3부 검증 · 2부 ⑦⑧ 관제 · 표③-2 · ③-3*

## 1. 이 장표가 왜 있나
앞 세 장표(097~099)는 실험 사슬을 순서도로 따라가며 "왜 이 숫자가 나왔고 무엇을 고쳤나"를 보였다. 그 사슬의 **최종 결과**를 한 표로 모은 것이 이 장표다. 공고 ②("실시간 로깅·모니터링·업데이트")에 "장애 복구"와 "업데이트"를 숫자로 답하려면 바로 이 표가 필요하다. 4부의 "숫자 한눈에 ②"(장표 104)에 나온 0 / 1400, 508 / 1312, 3 / 50 · 1.0초가 전부 이 표에서 나온 것이다. 이 장표를 끝으로 2부(데이터의 길)의 판단이 끝나고, 다음 질문 "이 숫자들을 어떻게 믿나?"(6부)로 넘어간다.

## 2. 장표를 하나씩 읽기
먼저 열(헤더) 8개의 뜻이다.
- 장애: 무엇을 죽였나(broker = MQTT 브로커 컨테이너, db = TimescaleDB 컨테이너, collector = 수집기 프로세스, bad_firmware = 나쁜 펌웨어 배포).
- 주입: 어떻게 죽였나(`docker compose stop`, SIGTERM 뒤 같은 명령으로 재시작, `rollout.py --bad`).
- 멈춤: 죽여 둔 시간.
- 감지: 주입 뒤 시스템이 이상을 처음 알아챈 때(수집기 통계의 msgs/s = 0, 또는 DB 프로브). ±1초(1초 묶음 적재 때문).
- 복구(전 장치/backlog 0): 복구 명령 뒤 모든 장치가 다시 데이터를 보내거나(broker·collector), 밀린 묶음이 0 이 될 때까지(db).
- 유실 행: 장애 직전 마지막 일련번호부터 집계 시각까지 장치가 만든 메시지 수 − 실제 받은 행(E07 에서 고친 식).
- 보호 없었다면: 버퍼·지속 세션·backlog 같은 보호 장치가 없을 때 잃었을 개수 = 초당 메시지 × 멈춘 시간 = 50 × 10 = 500.
- 비고: 그 줄의 특징.

이제 행마다.
- broker — stop mqtt, 10초, 감지 1.3초, 복구 2.9초, 유실 0 / 1400, 보호 없었다면 500, 비고 "폭주 431 msgs/s": 브로커가 돌아오자 50대가 버퍼를 한꺼번에 쏟아 초당 메시지가 평소 50 의 약 9배인 431 까지 치솟았다. 이것은 유실이 아니라 밀린 것이 몰려 들어온 것이다. 1,400개 중 0 유실.
- db — stop db, 10초, 감지 0.4초, 복구 1.4초, 유실 0 / 1341, 500, 비고 "뒤늦게 570행": DB 가 죽은 동안 수집기가 묶음을 메모리(backlog)에 들고 있다가 DB 가 돌아오자 570행을 뒤늦게 넣었다(50대 × 약 11초 ≈ 570). 그래서 유실 0.
- collector (qos0) — SIGTERM + 재시작, 10초, 감지 "-", 복구 1.6초, 유실 508 / 1312, 500, 비고 "보호 없음": 수집기와 장치를 모두 QoS 0 으로 두면 수집기가 없는 10초 동안 브로커가 뿌린 메시지는 아무도 받지 않는다. 예측 500 에 가까운 508 을 잃었다. 감지가 "-" 인 것은 수집기 자신이 죽어 있어 통계를 낼 주체가 없기 때문이다.
- collector (qos1) — 같은 장애, 복구 1.6초, 유실 0 / 1311, 비고 "지속 세션": QoS 1 + 지속 세션이면 브로커가 수집기 몫을 들고 있다가 재접속 때 넘겨 유실 0. 복구 시간은 QoS 0 과 같은 1.6초 — 차이는 시간이 아니라 유실이다.
- bad_firmware — rollout --bad, 멈춤·감지 "-", 복구 "롤백 1.0초", 유실 칸에 "닿은 장치 3/50", 보호 없었다면 "50대", 비고 "5% 헬스 게이트": 나쁜 펌웨어를 5% → 50% → 100% 단계로 내리는데 첫 단계(50대의 5% = 올림 3대)에서 장치가 fault 를 보고하자 서버가 1.0초 만에 롤백했다. 나머지 47대는 명령을 받은 적도 없다. 단계 배포가 없었다면 50대 전부가 나쁜 펌웨어를 받았을 것이다.
- CI 러너 (10대 2 Hz) — 같은 4종, 5초, 복구 3.2 / 1.2 / 1.5초, 유실 0/318 · 0/286 · 0/280, 비고 "롤백 0.4초": GitHub 의 깨끗한 가상 머신에서 장치 10대 × 2 Hz, 장애 5초로 같은 4종을 돌린 결과(E13). 분모는 다르지만 유실 0, 복구 수 초, 롤백 1초 안이라는 모양이 같다. 표③-3 의 다른 줄들(정상 OTA 1.1.0 성공 50/50, 러너 10/10)은 장표에 생략했다.
- 아래 비고: "'보호 없었다면' = 초당 메시지 × 멈춘 시간(50 × 10). 전달 지연 p50/p95 ≈ 1 / 2 ms(③-1). 출처: docs/measurements/table3.md, table3_ci.md" — 표③-1(처리량·전달 지연)은 이 장표에 없고 수치만 한 줄로 적었다.

## 3. 용어와 단위
- 장애 주입(fault injection): 일부러 고장을 내고 시스템이 스스로 돌아오는지, 그동안 무엇을 잃는지 재는 시험.
- 감지 / 복구: 감지는 "이상을 처음 본 때", 복구는 "정상으로 돌아왔다고 DB 에 찍힌 때". 둘 다 초 단위이고 1초 묶음 적재 때문에 ±1초의 오차가 있다.
- backlog: DB 가 죽은 동안 수집기가 들고 있는 1초 묶음들. 상한 200,000행.
- 지속 세션: 수집기가 없는 동안 브로커가 QoS 1 메시지를 대신 보관하는 약속(`clean_session=False` + 고정 client_id).
- SIGTERM: "곱게 끝나라"는 리눅스 종료 신호. 수집기는 이것을 받으면 마지막 묶음을 DB 에 넣고 끝낸다.
- 헬스 게이트: OTA 단계마다 장치 상태(state)가 ok 인지 확인하고, 아니면 롤백하는 관문.
- msgs/s: 초당 메시지 수. 평소 50대 × 1 Hz = 50.
- "0 / 1400": 1,400개 중 0개 유실. "3/50": 50대 중 3대에 나쁜 펌웨어가 닿음.

## 4. 쉬운 예시
- 비유(표 전체): 가게 50곳이 1분마다 본사에 매출을 보고한다. 통신사가 10분 끊기면(broker) 각 가게가 메모해 뒀다 몰아서 보내고(폭주), 본사 장부(db)가 10분 닫히면 접수 직원이 서류를 책상에 쌓아 뒀다가 넣고(backlog 570장), 접수 직원이 10분 자리를 비우면(collector) 우체국이 편지를 보관해 주는 계약(QoS 1 지속 세션)이 있을 때만 안 잃는다(508 vs 0). 새 계산기(펌웨어)를 50곳에 돌릴 때는 먼저 3곳에만 주고 고장이면 즉시 회수한다(3/50, 1.0초).
- 숫자 예시: 보호가 없을 때의 손실은 늘 "초당 메시지 × 멈춘 시간"이다. 50 × 10 = 500. 러너에서는 10대 × 2 Hz × 5초 = 100. QoS 0 줄의 508 이 이 예측과 1.6% 차이라는 사실이, 유실 계산식이 맞는다는 또 하나의 증거다.

## 6. 자주 하는 오해·함정
- "복구 2.9초" 는 브로커가 뜨는 시간이 아니라 "복구 명령 뒤 50대 전부가 다시 데이터를 보낼 때까지"다. 브로커 줄이 가장 느린 이유는 50대의 재접속과 버퍼 방출이 더해지기 때문이다.
- collector 두 줄의 복구 시간이 같다(1.6초)고 QoS 가 무의미한 것이 아니다. 차이는 유실 열(508 vs 0)에 있다.
- CI 줄을 WSL 줄과 숫자로 비교하면 안 된다(장치 수·주기·장애 시간이 다르다). 비교할 것은 모양이다.
- 유실 0 은 처음부터 0 이 아니었다(장표 097). 이 표의 0 은 측정식을 고치고(E07) 설정·종료 처리를 바꾼(E08) 뒤의 값이다.
- 재시작 함정(11/04): 수집기를 `/proc/<pid>/exe` 경로로 다시 띄우면 venv 를 잃고 바로 죽는다. 지금은 `/proc/<pid>/environ` 의 환경으로 같은 조건에서 재시작한다(장표 084 비고).
