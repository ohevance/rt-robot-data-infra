# 장표 011 — 단계 1 들머리 — 명령이 생긴다: 무엇을, 어떤 형식·단위·주기로 내나
*위치: 1부 로봇을 움직이는 길 · 단계 1/10 명령이 생긴다 · ① 들머리*

## 1. 이 장표가 왜 있나
앞 두 장표(007·008)에서 "명령 → … → 로봇의 움직임 → 기록·관제"라는 10단계의 길과, 그 길이 들어 있는 소프트웨어 구조를 보았다. 이제 길의 첫 상자로 들어간다. 모든 단계는 같은 꼴의 "들머리" 장표로 시작한다: 들어온 것 → 문제 → ◇기준 → 확인 방법 → 결과 → 판단·다음. 들머리는 "이 단계가 왜 필요하고, 무엇을 넘어야 다음 단계로 가는지"를 한 장에 모은 것이다. 단계 1의 질문은 단순하다. 로봇을 움직이려면 누군가 "관절을 이 각도로" 라고 말해야 한다. 그 말을 **어떤 형식, 어떤 단위, 얼마나 자주** 낼지 정하지 않으면 그 뒤 아홉 단계는 시작조차 못 한다.

## 2. 장표를 하나씩 읽기
여섯 상자를 순서대로 따라간다. 위 줄은 왼쪽 → 오른쪽, 아래 줄은 오른쪽 → 왼쪽(뱀 모양).

- **들어온 것(회색 상자)** — "상위(계획기·조작기·시험용 명령줄)의 의도 — '관절 6개를 이 각도로'": 단계 1 앞에는 사람이든 프로그램이든 "의도"가 있다. 실제 로봇이면 경로를 계산하는 계획기(planner)나 조이스틱 같은 조작기, 이 저장소에서는 시험용으로 터미널에서 치는 명령이다. 관절이 6개인 이유는 이 저장소가 쓰는 로봇 모델 SO-101(6축 팔)이기 때문이다.
- **문제(민트 상자)** — "로봇이 알아듣는 형식·단위·주기가 필요하다. 너무 느리면 반응이 늦고, 틀린 명령이 그대로 가면 위험하다": 의도를 숫자로 바꿔야 한다. 세 가지를 정해야 한다 — 형식(어떤 메시지 모양으로), 단위(각도를 도(°)로 쓸지 라디안(rad)으로 쓸지), 주기(1초에 몇 번). 주기가 너무 느리면 로봇이 굼뜨고, 길이가 틀리거나 값이 튀는 명령이 그대로 모터에 가면 로봇이 부딪힌다.
- **기준(마름모)** — "제어 루프(1 kHz)가 매 주기 '최신 목표'를 가질 수 있고, 틀린 명령(길이 불일치)은 걸러지나?": 합격선 두 가지. (1) 1초에 1,000번 도는 제어 루프가 매번 "지금 따라가야 할 목표"를 가질 수 있어야 한다 — 명령이 루프보다 느려도 괜찮으려면 "명령이 없는 주기는 지난 목표를 유지한다"는 규칙이 필요하다. (2) 관절 수와 길이가 다른 명령은 어딘가에서 걸러져야 한다. 왜 이 기준인가: 로봇은 명령이 "없을 때"와 "틀릴 때"에 가장 위험하기 때문이다.
- **확인 방법(파란 상자)** — "sensor_msgs/JointState · rad · 50 Hz 로 ros2 topic pub → 노드 카운터(commands_received · bad_commands) 확인": 정한 답은 ROS 2 표준 메시지 `sensor_msgs/msg/JointState`, 단위 rad, 주기 50 Hz. 확인은 실제로 50 Hz 로 명령을 쏘고(`ros2 topic pub -r 50 …`) 노드가 1초마다 내는 상태(`/rt_status`)의 카운터 두 개를 본다 — `commands_received`(받은 명령 수)와 `bad_commands`(길이가 틀려 버린 명령 수).
- **결과(보라 테두리 상자)** — "노드가 50 Hz 로 받는다(초당 50 씩 증가). 길이가 6 이 아니면 bad_commands 로 버리고 센다. 명령이 없는 주기는 지난 목표 유지": `commands_received` 가 1초에 50씩 는다는 것은 50 Hz 명령이 노드까지 도착한다는 뜻. 길이 검사는 노드의 `on_command()`(장표 019)가 하고, "없는 주기는 지난 목표 유지"는 제어 단계의 `take_latest_command()`(장표 030)가 한다.
- **판단 → 다음(진한 초록 상자)** — "통과 → 단계 2: 이 명령이 다른 프로세스의 노드까지 어떻게, 얼마나 믿을 만하게 가나?": 형식·단위·주기가 정해졌고 거르는 자리가 있으니 통과. 다음 질문은 "명령을 내는 프로그램과 받는 노드는 서로 다른 프로세스인데, 그 사이를 무엇이 어떻게 실어 나르나" — 단계 2(ROS 2 / DDS).
- **아래 설명 상자** — "이 단계의 장표: ② 무엇·누가·왜 50 Hz(1장). 넘어가는 조건: 형식(JointState)·단위(rad)·주기(50 Hz)가 정해지고, 틀린 명령을 거르는 자리가 있다(단계 3 on_command, 단계 5 변화량 제한)": 단계 1에는 코드 장표가 없고 설명 장표 한 장(013)만 있다. 거르는 자리는 둘이다 — 길이가 틀린 명령은 단계 3의 `on_command`, 값이 튀는 명령은 단계 5의 변화량 제한.

## 3. 용어와 단위
- **상위(上位)**: 제어 루프보다 위에서 "어디로 갈지"를 정하는 쪽. 계획기(planner, 경로를 계산), 조작기(teleop, 사람이 조종).
- **sensor_msgs/msg/JointState**: ROS 2 가 미리 정해 둔 "관절 상태" 메시지. 관절 이름(name), 위치(position), 속도(velocity), 힘(effort) 칸이 있다. 이 저장소는 그중 position 만 명령으로 쓴다.
- **rad(라디안)**: 각도의 SI 단위. 반지름 길이만큼의 호에 해당하는 각. 1 rad = 57.3°, 90° = 1.571 rad, 0.05 rad = 2.9°.
- **Hz**: 1초에 몇 번. 50 Hz = 20 ms 마다 한 번. **1 kHz** = 1,000 Hz = 1 ms 마다 한 번.
- **제어 루프**: 일정한 주기로 "목표를 읽고 → 검사하고 → 로봇에 쓰기"를 반복하는 코드. 여기서는 1 kHz.
- **카운터**: 어떤 일이 몇 번 일어났는지 세는 정수 변수. `commands_received`, `bad_commands` 는 노드가 세어 `/rt_status` 로 내보낸다.
- **dof(degrees of freedom, 자유도)**: 움직일 수 있는 관절 수. SO-101 은 6.

## 4. 쉬운 예시
- 비유: 식당 주방(제어 루프)에 주문서(명령)를 넣는 상황. 주문서 양식(JointState), 단위(그램인지 인분인지 = rad), 주문이 오는 간격(50 Hz)을 정해야 주방이 돌아간다. 주방은 1초에 1,000번 "지금 만들 요리가 뭐지?"를 확인하는데, 주문서는 1초에 50장만 온다. 그러니 새 주문서가 없을 때는 "마지막 주문서"를 계속 만든다. 메뉴 칸이 6개여야 하는데 5개짜리 주문서가 오면 주방은 그것을 버리고 "잘못된 주문서 1장"이라고 적어 둔다(`bad_commands`).
- 숫자 예시: 50 Hz 명령과 1 kHz 루프 — 명령 한 장마다 루프가 20번 돈다. 10초 동안 명령을 쏘면 `commands_received` 는 약 500 이 되어야 한다(50 × 10). 만약 250 밖에 안 됐다면 절반이 도착하지 않은 것이고, 그 원인은 단계 2(전달)에서 찾아야 한다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 관절 6개 — `robots/so101.yaml` 의 `dof: 6`, 노드 시작 로그 `dof=6`.
- 확인: 제어 루프 1 kHz — 노드 파라미터 `loop_hz` 기본값 1000 (`rt_control/ros2_adapter/src/rt_control_node.cpp`).
- 확인: 50 Hz 시험 발행 명령 — `docs/experiments/E03.md`, `docs/experiments/E20.md`, `docs/VIDEO_SCRIPT.md` 의 `ros2 topic pub -r 50 /joint_command sensor_msgs/msg/JointState "{position: [0.3, -0.2, 0.1, 0.0, 0.0, 0.5]}"` (장표 013의 말풍선은 CHEATSHEET·backends/mujoco/README.md 를 가리키지만, 그 두 파일에는 echo 명령과 흐름 그림만 있다).
- 확인: 카운터 이름 — `rt_control_node.cpp` 의 `on_command()`(184~201줄: `bad_commands_`, `cmd_ring_full_`, `commands_received_`), 1 Hz 상태 발행 `publish_status()`(233~307줄).
- 다시 보는 법: 노드를 띄우고 명령을 쏜 뒤 `ros2 topic echo /rt_status std_msgs/msg/String --once` 로 JSON 한 줄을 보면 `commands_received`, `bad_commands` 가 있다.
- 추정: "초당 50 씩 증가"는 설계값(발행 속도)에서 온 기대치다. 실측 로그에 1초 간격의 차이값을 따로 기록해 두지는 않았다.

## 6. 자주 하는 오해·함정
- "명령은 제어 주기와 같은 1 kHz 로 보내야 한다"는 오해: 아니다. 루프는 매 주기 "최신 목표"만 보고, 없으면 지난 목표를 유지하므로 명령은 느려도 된다. 다만 50 ms 이상 끊기면 워치독이 멈춤을 건다(단계 5, 안전 경로 장표 057).
- 단위 혼동: ROS 2 의 JointState.position 은 rad 다. 도(°)로 0.3 을 넣으면 0.3° 가 아니라 0.3 rad = 17.2° 가 된다.
- `ros2 topic pub` 으로 쏘는데 노드가 못 받는 경우(11/04): ros2 데몬이 다른 RMW 로 떠 있던 일 — `ros2 daemon stop` 뒤 재시도(장표 016 함정).

## 7. 면접 한 문장
"명령은 ROS 2 표준 JointState 를 rad 단위로 50 Hz 에 내고, 1 kHz 루프는 매 주기 최신 목표만 보며 없으면 지난 목표를 유지한다 — 길이가 틀린 명령은 노드에서, 튀는 값은 제어 단계에서 거른다."
