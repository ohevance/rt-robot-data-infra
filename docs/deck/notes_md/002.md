# 장표 002 — 이 장표를 읽는 법 — 로봇이 움직이는 과정을 먼저, 시험·검증은 뒤에 번호로
*위치: 0 · 읽는 법*

## 1. 이 장표가 왜 있나
표지(001)는 "무엇에 관한 자료인가"를 답했다. 그러면 바로 "그 많은 장표를 어떤 순서로, 어떤 약속으로 읽어야 하나"가 궁금해진다. 이 장표는 그 약속을 일곱 줄로 정한다. 특히 두 가지가 핵심이라 굵게 되어 있다. 첫째, 순서는 로봇을 움직이는 과정(1부)부터이고 시험·검증은 3부로 뒤에 둔다. 둘째, 1·2부 안에서는 실험을 하지 않고 "확인 → 장표 N" 이라는 번호만 적는다. 이 약속을 모르면 "왜 단계 4에서 측정 결과를 안 보여 주고 번호만 적지?"라고 헷갈리게 되므로, 목차보다 먼저 이 장표가 온다.

## 2. 장표를 하나씩 읽기
- 1번 줄 "목적": 이 자료는 처음 보는 사람(또는 면접관)에게 네 가지를 끊김 없이 설명하기 위한 것이다 — 로봇이 어떻게 움직이고, 그 코드가 어디에 있고, 무엇을 쟀고, 왜 그렇게 판단했나. 네 가지가 각각 1부(과정), 1·2부의 코드 장표(위치), 3·6부(측정), 7부(판단)에 대응한다.
- 2번 줄 "순서"(굵게): 1부 로봇을 움직이는 길은 왕초보 바탕 → 한 장 그림 → 소스 코드 지도 → 단계 1~10 순서이고, 단계마다 핵심 코드와 파일:줄이 붙는다. 그 뒤 2부 데이터의 길 → 3부 검증 → 4부 공고와 숫자 → 5부 환경 → 6부 테스트·CI → 7부 결정·사고·방식 → 끝. 왜 이 순서인가: 처음 보는 사람이 가장 알고 싶은 것("로봇이 어떻게 움직이나")에 4장 만에 닿게 하기 위해서다. 공고나 환경 설명은 과정을 다 본 뒤에 와야 "아, 그 길이 공고의 이 항목을 덮는구나"가 된다.
- 3번 줄 "1·2부 안에서는 시험·검증을 하지 않는다"(굵게): 단계마다 기준을 넘었는지는 들머리 장표의 '결과' 상자에 숫자 한 줄로만 적고, 자세한 실험은 '확인 → 장표 N' 으로 번호만 가리킨다. 3부에서 같은 단계 순서로 그 실험들을 본다. 왜: 과정의 흐름을 끊지 않으려고. 실험 사슬은 한 단계에 3~7장씩이라 과정 안에 두면 "지금 로봇이 어디까지 왔지?"를 잃는다.
- 4번 줄 "같은 꼴": 모든 부의 첫 장표는 [앞에서 안 것] → ◇[이 장의 질문] → [이 장의 답] 모양이고, 모든 단계의 첫 장표(들머리)는 들어온 것 → 문제 → ◇기준 → 확인 방법 → 결과 → 판단 → 다음 모양이다. 그 뒤에 코드 장표가 따라온다. 왜: 꼴이 같으면 어느 장에서 시작해도 읽는 법이 같다.
- 5번 줄 "알약과 다리": 위 오른쪽 알약은 지금 어디인지(부 · 단계 · 코드/확인/판단), 아래 '다음 ▶' 다리는 왜 다음 장으로 넘어가는지를 적는다. 발표할 때 다리 문장을 그대로 읽으면 된다.
- 6번 줄 "그림 약속": 회색 상자 = 앞 단계에서 들어온 것, 민트 상자 = 코드/실험, 마름모 = 판단 기준(합격선), 파란 상자 = 확인 방법, 화살표 글 = 그 기준에 대한 답(실제 값), 진한 둥근 상자 = 결론, 붉은 상자 = 실패·원인. 순서도를 볼 때 색과 모양만으로 역할을 읽게 하려는 약속이다.
- 7번 줄 "숫자 옆의 환경": 숫자 옆에는 항상 어디서 쟀는지가 붙는다. WSL2는 가상 커널이라 참고값, Pi 4는 PREEMPT_RT 커널이라 실측, GitHub 러너는 "돌아간다"의 증거. 단위는 us(마이크로초, 100만분의 1초), ms, rad, Hz.
- 8번 줄 "코드와 설명 문서": 코드는 캡처가 아니라 저장소 파일에서 그대로 읽어 넣었고(2026-11-11 main 기준 — 빌드할 때 저장소 파일에서 읽는다), 코드 상자 위에 파일 경로와 줄 번호가 있다. 장표 하나마다 `docs/deck/notes/NNN.docx` — 왜·용어·단위·쉬운 예시·숫자 출처·면접 한 문장을 담은 설명이 있다.

## 3. 용어와 단위
- 들머리: 각 단계의 첫 장표. "들어가는 머리"라는 뜻으로, 그 단계가 무엇을 받아서 무엇을 해결해야 하는지를 여섯 상자로 요약한다.
- 기준(마름모): 순서도에서 마름모는 "예/아니오로 갈리는 질문"이다. 여기서는 그 단계가 넘어야 할 합격선.
- 참고값 / 실측: 같은 측정이라도 WSL2(윈도우 안의 리눅스, 가상 커널)에서 나온 값은 실제 하드웨어를 대표하지 못해 "참고값", Raspberry Pi 4 + 실시간 커널에서 나온 값은 "실측"이라 부른다.
- us: 마이크로초. 1 us = 100만분의 1초, 1 ms = 1,000 us. rad: 각도 단위(1 rad = 57.3°). Hz: 1초에 몇 번.
- main: git 저장소의 기본 가지(branch) 이름. "2026-11-11 main 기준"은 그 날 그 가지의 파일 내용으로 줄 번호를 적었다는 뜻이다. 처음 만든 11/05 뒤로 파일이 바뀌면 줄이 밀리므로, 장표를 다시 만들 때 줄 범위를 다시 맞춘다(11/11 에 관제 쪽 코드 장표 10장을 그렇게 고쳤다).

## 4. 쉬운 예시
비유: 요리 교실에서 "먼저 요리 과정을 처음부터 끝까지 보여 주고, 각 재료의 영양 분석표는 수업 뒤에 번호를 붙여 나눠 드립니다"라고 하는 것과 같다. 과정을 보는 도중에 분석표를 끼워 넣으면 흐름이 끊긴다. 숫자 예시: 1부 단계 4(1 ms 루프)의 들머리에는 "결과: 781 → 301 → 311 → 189 us" 한 줄과 "확인 → 3부 장표 89~95" 만 적혀 있다. 그 7장(측정기·백분위수·실험 사슬 3장·표·결론)은 3부에 가서 본다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 부 번호와 장표 범위 — 4번 장표(목차 표)와 `docs/deck/SLIDES.md`.
- 확인: "2026-11-11 main 기준" — 저장소에서 `git log -1 --format=%cd` 로 마지막 커밋 날짜를 본다. 코드 장표의 줄 번호는 `docs/deck/build/content_*.py` 의 `code(파일, 시작, 끝)` 호출에 적혀 있고, 빌드할 때마다 그 줄을 파일에서 다시 읽는다.
- 확인: 설명 문서 경로 — `docs/deck/notes/` 폴더.

## 6. 자주 하는 오해·함정
- "검증이 뒤에 있으니 1·2부 숫자는 근거가 없다"고 보면 안 된다. 들머리의 '결과' 상자 숫자는 전부 3부·6부의 측정 파일에서 온 것이고, 번호가 그 자리를 가리킨다.
- 화살표 글(붉은 글씨)은 "질문"이 아니라 "실제 값(답)"이다. 마름모 안이 질문이고, 그 옆 화살표 글이 측정으로 얻은 답이다.
- WSL2 숫자를 실측으로 인용하지 않는다. 특히 깨어남 지연(단계 4)은 WSL2에서 max 가 1 ms 턱밑까지 가는데, 이것은 가상 커널 때문이지 코드 때문이 아니다(3부 장표 91 의 E01→E02).

## 7. 면접 한 문장
"자료는 로봇이 움직이는 과정을 먼저 열 단계로 보여 주고, 각 단계의 실험은 번호만 남겨 3부에서 같은 순서로 다시 봅니다 — 과정의 흐름과 증거를 둘 다 지키기 위한 배치입니다."
