# 장표 048 — 단계 8 그림 — 상태가 밖으로 나가는 길: RT 스레드는 벨트에 올리기만, 발행은 다른 스레드가 자기 박자로
*위치: 1부 로봇을 움직이는 길 · 단계 8/10 상태 발행 · ② 그림 — 벨트와 발행 스레드*

## 1. 이 장표가 왜 있나
앞 장표(047, 단계 8 들머리)가 "로봇이 움직였다는 사실(1 kHz 샘플)을 RT 스레드 밖으로 어떻게 내보내나, 그리고 노드는 자기 상태를 어떻게 설명하나"를 물었다. 이 장표는 그 답의 구조를 한 장에 그린다 — 왼쪽 RT 스레드는 벨트(링 버퍼)에 올리기만 하고, 오른쪽 ROS 2 실행기 스레드가 자기 박자(100 Hz, 1 Hz)로 벨트를 비워 두 토픽(`/joint_states`, `/rt_status`)으로 발행한다. 단계 3 의 우편함(명령이 아래로)과 거울상이다(상태가 위로). 이 그림을 머리에 두고 다음 장표 049(publish_state 코드)와 050~(publish_status 코드)를 읽는다.

## 2. 장표를 하나씩 읽기
왼쪽 큰 회색 상자 = RT 스레드, 가운데 육각형 둘 = 벨트 둘, 오른쪽 큰 회색 상자 = ROS 2 실행기 스레드, 맨 오른쪽 문서 모양 둘 = 토픽.

- 회색 "RT 스레드 (1 kHz)": 단계 4 의 1 ms 루프가 도는 스레드(SCHED_FIFO). 여기서는 메모리 할당·락·네트워크가 금지다.
- 민트 "step() 끝 ⑤: JointStateSample(iter, 시각, dof, 위치·속도·목표) 를 상태 벨트에 push — 꽉 차면 state_drops++": 단계 5 의 다섯 번째 일. 한 주기의 결과를 고정 크기 구조체 `JointStateSample` 에 담아 상태 벨트에 올린다. 구조체에는 그림의 네 가지 외에 깨어남 지연(wake_lat_ns)·워치독 상태·로봇 상태도 들어 있다. 벨트가 꽉 차면 기다리지 않고 버리고 `state_drops` 를 센다.
- 민트 "RtLoop::run (d): 타이밍 Sample(깨어남 지연 · 주기 오차 · 일한 시간) 을 타이밍 링에 push — 꽉 차면 drops++": 단계 4 의 루프가 주기마다 남기는 시간 측정값(`Sample`: iter, wake_lat_ns, period_err_ns, work_ns)을 다른 벨트에 올린다. 꽉 차면 `drops` 를 센다. 이 수가 0 이 아니면 루프 자체가 주기를 놓쳤다는 뜻으로 쓴다.
- 호박색 육각형 "상태 벨트 SpscRing 2048": 생산자 하나(RT) · 소비자 하나(실행기)용 락 없는 링 버퍼. 2048칸 = 1 kHz 에서 약 2초 분량 — 발행 스레드가 2초 넘게 멈춰야 비로소 넘친다.
- 호박색 육각형 "타이밍 링 SpscRing 65536": 같은 링이지만 65,536칸 = 약 65초 분량. 1초마다 비우므로 평소에는 1,000개 정도만 들어 있다.
- 회색 "ROS 2 실행기 스레드 (일반 우선순위, 타이머 2개)": 콜백(on_command)과 타이머 둘(publish_state, publish_status)이 도는 스레드. 실시간 우선순위가 없고, 여기서는 할당·네트워크를 써도 된다.
- 파란 "publish_state() 100 Hz — 벨트를 전부 비우고 마지막 샘플만 (1 kHz 샘플 10개 중 최신 1개)": 10 ms 마다 상태 벨트를 `pop` 으로 전부 비우고 마지막 샘플만 `/joint_states` 로 보낸다. 1 kHz 샘플 10개 중 9개는 버린다 — 상태 토픽의 목적은 "지금 어디"를 알리는 것이라 가장 최신 것 하나면 된다. 벨트가 비어 있으면(RT 가 아직 안 돌았거나 멈춤) 발행하지 않는다.
- 파란 "publish_status() 1 Hz — 지난 1초 샘플 ~1,000개 → p50/p99/max + 카운터 + rt 환경 → JSON 한 줄": 1초마다 타이밍 링을 전부 비워 깨어남 지연(wake_us)과 일한 시간(work_us)의 p50/p99/max 를 정렬로 구하고, 단계 5 의 원자 카운터(드롭·명령·워치독·변화량 제한·상태 머신)와 RT 환경(SCHED_FIFO 성공, mlockall 성공, 실시간 커널 여부, 커널 이름, RMW 이름)을 JSON 한 줄로 발행한다. "노드가 스스로를 설명한다"의 실체.
- 문서 모양 "/joint_states 100 Hz JointState": 표준 메시지 `sensor_msgs/JointState`(이름·위치·속도). 단계 9 가 기록하고, 단계 7 의 숫자가 여기서 나왔다.
- 문서 모양 "/rt_status 1 Hz String(JSON)": `std_msgs/String` 에 JSON 한 줄. 단계 10 의 다리가 이것을 구독해 관제로 올린다.
- 화살표 "push 수십 ns" / "push": RT 쪽 비용이 아주 작다는 뜻(추정, 아래 5 절). "pop 전부": 소비자가 한 번에 전부 비운다.
- 아래 글 1 "왜 이렇게: RT 스레드가 직접 ROS 메시지를 발행하면 메모리 할당과 네트워크가 1 ms 안에 들어와 꼬리(max)가 생긴다. 벨트에 올리는 데는 수십 ns 뿐이고, 바깥 스레드가 자기 박자로 비운다": 설계 이유. ROS 2 발행은 메시지 할당·직렬화·DDS 전송을 수반해 수십~수백 us 가 튈 수 있다. 그것을 1 ms 루프 밖으로 밀어낸 것.
- 아래 글 2 "실측(11/05 기록 30초): /joint_states 실제 100.0 Hz, 틈 0, state_drops 0. rt_status 는 wake_us · work_us · drops · state · rt{sched_fifo, mlockall, kernel_realtime} · rmw 를 1초마다": 이 길이 실제로 작동했다는 숫자(단계 9 의 기록 요약)와 JSON 의 주요 열.
- legend "소스 위치: …": 상자 ↔ 코드 줄(아래 5 절에서 확인).

## 3. 용어와 단위
- 벨트 / SPSC 링 버퍼: 칸이 정해진 원형 대기열. 생산자 하나·소비자 하나(Single-Producer Single-Consumer)만 쓰기 때문에 락 없이 원자 변수 둘(head·tail)로 안전하다. 단계 3 의 우편함과 같은 자료형(`SpscRing<T, N>`).
- push / pop: 벨트에 올리기 / 꺼내기. 꽉 차면 push 가 false 를 돌려주고, 비었으면 pop 이 false.
- 드롭(drops, state_drops): 꽉 차서 버린 샘플 수. "기다리지 않는다"의 대가이자, 0 인지가 건강 신호.
- 실행기(executor) 스레드: ROS 2 가 콜백과 타이머를 돌려 주는 스레드. 이 노드는 하나만 쓴다.
- 타이머 100 Hz / 1 Hz: `create_wall_timer` 로 만든 주기 호출. 10 ms 마다 publish_state, 1 s 마다 publish_status.
- p50 / p99 / max: 1초 동안의 약 1,000개 값을 정렬했을 때 가운데 / 99% 지점 / 가장 큰 값. 단위 us(마이크로초).
- wake_us / work_us: 깨어남 지연(목표 시각보다 늦게 깬 시간) / 한 주기에 일한 시간(제어 단계 + 백엔드 + 벨트 push).
- RMW: ROS 2 가 쓰는 DDS 구현의 이름(Fast DDS, Cyclone DDS 등). JSON 끝에 찍어 "어느 DDS 위에서 잰 값인가"를 남긴다.
- JSON: 중괄호와 이름:값으로 된 글 형식. 사람이 읽을 수 있고 파이썬이 바로 파싱한다(단계 10).

## 4. 쉬운 예시
- 비유: 공장 라인 작업자(RT)는 완성품을 옆 벨트에 올려만 놓고 바로 다음 작업으로 돌아간다. 포장 담당(실행기)은 10초마다 벨트를 싹 비워 가장 새 것 하나만 진열하고(상태 100 Hz), 1분마다 벨트의 기록을 세어 "오늘 몇 개, 가장 느린 작업은 몇 초" 보고서를 쓴다(rt_status 1 Hz). 작업자가 포장까지 직접 하면 라인이 멈칫한다.
- 숫자 예시: 1 kHz 샘플 1,000개/초 중 `/joint_states` 로 나가는 것은 100개/초(10개마다 1개). 상태 벨트 2048칸은 발행 스레드가 2.048초 멈춰야 넘친다. 11/05 30초 기록에서 2,964행이 틈 없이 100.0 Hz 로 나왔고 `state_drops` 는 0 — 발행 스레드는 한 번도 2초 넘게 멈추지 않았다.

## 6. 자주 하는 오해·함정
- "100 Hz 로 발행하니 상태가 10 ms 늦다"가 아니다. 보내는 것은 벨트의 **가장 최신** 샘플이라 최대 10 ms 전 값이고, 평균은 5 ms. 더 자주 보려면 `publish_hz` 파라미터만 올리면 되고 RT 쪽은 바뀌지 않는다.
- 두 벨트는 서로 다른 것을 나른다. 상태 벨트는 "로봇이 어디 있나"(매 주기 1개, 발행은 최신 1개), 타이밍 링은 "루프가 제때 돌았나"(매 주기 1개, 1초마다 통계로 압축). 드롭 카운터도 둘(state_drops, timing_drops)이다.
- `publish_status` 안의 `std::vector`·`std::sort`·`snprintf` 는 할당과 시간이 드는 일이지만 **실행기 스레드**에서 하므로 괜찮다. 같은 코드를 RT 스레드에 두면 단계 4 의 규칙 위반이다.
- `samples_1s` 가 1,000 근처가 아니면(예: 2,000) 타이머가 늦게 불려 2초치를 한 번에 비운 것이다 — 루프가 아니라 실행기 스레드의 사정이고, 루프가 주기를 놓쳤는지는 `timing_drops` 로 본다. (11/05 기록의 rt_status 29줄은 iter 가 매 줄 정확히 1,000 씩 늘어 그런 일이 없었다.)
- `/rt_status` 의 `rt.kernel_realtime` 등은 RT 스레드가 시작할 때 한 번 재서 둔 값이라 1초마다 바뀌지 않는다(`rt_loop_->status()`, :255 주석).

## 7. 면접 한 문장
"RT 스레드는 매 주기 결과를 락 없는 벨트에 올리기만 하고, ROS 2 스레드가 100 Hz 로 벨트를 비워 최신 상태를, 1 Hz 로 지난 1초의 p50/p99/max 와 카운터·RT 환경을 JSON 으로 냅니다 — 할당과 네트워크를 1 ms 루프 밖으로 밀어낸 구조이고, 30초 기록에서 100.0 Hz 틈 0 드롭 0 으로 확인됐습니다."
