# 장표 055 — 단계 10 그림 — 관제로: 로봇 안의 1 Hz 요약이 서버의 화면까지 가는 길 (로봇이 51번째 장치가 된다)
*위치: 1부 로봇을 움직이는 길 · 단계 10/10 관제로 · ② 그림 — 로봇에서 화면까지*

## 1. 이 장표가 왜 있나
앞 장표(054, 단계 10 들머리)가 "로봇 안에서 1초마다 나오는 자기 설명(`/rt_status`)을 로봇 밖 관제 서버의 화면까지 어떻게 올리나, 그것도 가상 장치 50대와 같은 길로"를 물었다. 이 장표는 그 길을 왼쪽(로봇 안 토픽)에서 오른쪽(Grafana 화면)까지 상자 일곱 개로 그린다. 1부 10단계의 마지막 그림이며, 여기서 오른쪽 네 상자(브로커 → 수집기 → DB → Grafana)는 2부 "데이터의 길"에서 하나씩 펼친다. 핵심은 "관제 서버는 로봇이 ROS 2 인지, 가상인지 실물인지 모른다 — 다리(bridge) 하나가 로봇을 51번째 장치로 만든다"는 것이다. 다음 장표 056 은 이 다리의 코드(`ros_status_bridge.py`)를 글머리표로 읽는다.

## 2. 장표를 하나씩 읽기
왼쪽에서 오른쪽으로 화살표를 따라간다.

- 문서 모양 "/rt_status 1 Hz JSON (단계 8)": 단계 8 의 `publish_status()` 가 1초마다 내는 JSON 한 줄(wake_us·work_us 의 p50/p99/max, 드롭, 상태 머신, 워치독, RT 환경, RMW). 이 그림의 입력.
- 민트 "StatusBridge (ROS 2 노드, 파이썬) — 구독 → JSON 파싱 → metrics_source": `fleet/agent/ros_status_bridge.py` 의 클래스. `rt_status` 토픽을 구독해 JSON 을 파싱해 두고(`on_status`), 누가 물으면 마지막 값을 관제의 텔레메트리 필드(loop_hz, wake_p99_us, wake_max_us, work_p99_us, timing_drops, watchdog_trips, rmw, backend, sched_fifo)로 바꿔 돌려준다(`metrics()`). 그 "물어보는 함수"가 바로 다음 상자에 넘겨지는 `metrics_source` 다. 화살표 "1 Hz" 는 토픽 주기.
- 파란 "DeviceAgent (가상 장치와 같은 클래스) — device_id rt-node-1": `fleet/agent/device_agent.py` 의 클래스. 가상 장치 50대를 띄우는 것과 **같은 클래스**를 그대로 쓰되, 숫자를 가져오는 함수(`metrics_source`)만 다리의 `metrics` 로 바꿔 끼운다. 장치 이름은 `rt-node-1`(명령줄 `--device-id`). 1초마다 `tick()` 이 `{device_id, seq, ts_ns, fw_version, state, …}` 에 metrics 를 합쳐 발행한다.
- 호박색 육각형 "MQTT 브로커 fleet/rt-node-1/telemetry (2부 ②)": 발행 토픽 이름은 규칙 `fleet/<device_id>/telemetry`. 화살표 "publish QoS 0/1" — DeviceAgent 는 QoS 0(보내고 잊음)과 1(브로커 확인) 둘 다 지원하고, 다리는 기본값 0 으로 띄운다. 브로커는 Mosquitto.
- 파란 "수집기 1초 묶음 COPY (2부 ③)": `fleet/collector/collector.py`. 브로커를 구독해 받은 행을 1초 동안 모아 PostgreSQL `COPY` 한 번으로 넣는다(장치 300대라도 DB 왕복 1번/초).
- 회색 원통 "TimescaleDB telemetry 표": 시계열 DB. `telemetry` 표의 열 중 RT 노드용은 `loop_hz`, `wake_p99_us` 와 공용 `state`, `fw_version`, `seq`.
- 보라 "Grafana 패널 'RT 노드: 깨어남 지연 p99' '멈춤·고장 장치'": `fleet/grafana/make_dashboard.py` 가 만든 대시보드의 패널 10("RT 노드: 깨어남 지연 p99 (us)", `SELECT time, device_id, wake_p99_us FROM telemetry …`)과 패널 6("멈춤·고장 장치 (tripped/fault/updating)", `devices` 표에서 state 가 tripped·fault·updating·recovering 인 장치 수). 화살표 "SQL".
- 아래 글 1 "가상 장치 50대와 다른 것은 metrics_source(어디서 숫자를 가져오나)뿐: 가상 장치는 난수 걸음, 다리는 rt_status 의 wake p99 · loop_hz · 드롭 · 상태": 코드 재사용의 요점. 가상 장치는 난수를, 다리는 진짜 RT 루프의 숫자를 같은 자리에 넣는다.
- 아래 글 2 "watchdog 이 tripped 이면 state 도 tripped 로 올라가 '멈춤·고장 장치' 패널에 잡힌다 — 관제 서버는 로봇이 가상인지 실물인지, ROS 2 인지 모른다": 명령이 끊겨 워치독이 걸리면 장치 state 가 정상이 아닌 값으로 올라가 패널에 잡힌다. 지금 코드는 상태 머신 이름을 우선 올리므로 실제 값은 `fault`(RUNNING 에서 끊김 → FAULT)이고, `tripped` 는 JSON 에 `state` 가 없을 때의 대체값이다 — 패널은 둘 다 센다(아래 6 절).
- 아래 글 3 "실물 로봇도 같다: 로봇 안 컴퓨터(Pi 등)에서 이 다리가 돌고, 그 뒤는 2부 데이터의 길 그대로": 실물로 가도 바뀌는 것은 단계 6 의 백엔드뿐이고 이 길은 그대로다.
- legend "소스 위치: …": 다리 123줄, DeviceAgent, 토픽 규칙, 패널 SQL 의 파일.

## 3. 용어와 단위
- 관제(fleet): 여러 로봇·장치의 상태를 한 서버에서 모아 보는 일. 이 저장소에서는 MQTT → 수집기 → TimescaleDB → Grafana.
- 다리(bridge): 두 세계(ROS 2 토픽 ↔ MQTT)를 잇는 작은 프로그램. 여기서는 파이썬 123줄(11/05 에는 99줄 — 11/10 에 설치 자리와 자율 업데이트 옵션이 더해졌다).
- MQTT / 브로커 / 토픽: 가벼운 발행-구독 메시지 규약 / 메시지를 중계하는 서버(Mosquitto) / 메시지의 주소 문자열(`fleet/rt-node-1/telemetry`).
- QoS 0 / 1: MQTT 전달 보증 수준. 0 은 한 번 보내고 잊음, 1 은 브로커가 받았다는 확인(PUBACK)까지. 2부 표③에서 수집기 끊김 때 유실 0 에 QoS 1 이 필요했다.
- 텔레메트리(telemetry): 장치가 주기적으로 보내는 상태 숫자 묶음(JSON). `seq` 일련번호가 있어 빠진 번호 = 유실.
- 수집기(collector) / COPY: 브로커에서 받아 DB 에 넣는 프로그램 / PostgreSQL 의 대량 적재 명령(행을 한 줄씩 INSERT 하는 것보다 훨씬 빠름).
- TimescaleDB: PostgreSQL 에 시계열 확장을 얹은 DB. `telemetry` 표는 hypertable(시간으로 자동 분할).
- Grafana / 패널 / stat·timeseries: 화면 도구 / 화면의 네모 하나 / 숫자 하나짜리 패널·시간 그래프 패널.
- metrics_source: DeviceAgent 가 1초마다 호출해 숫자 dict 를 받는 함수. 가상 장치는 난수, 다리는 rt_status.
- device_id: 장치 이름. 가상 장치는 `vdev-001`~`vdev-050`(`virtual_fleet.py --prefix vdev`), RT 노드는 `rt-node-1`.

## 4. 쉬운 예시
- 비유: 회사 출근 기록 시스템에 사람 50명이 카드를 찍는다(가상 장치). 로봇도 같은 카드 리더에 "직원 51번"으로 카드를 찍게 만든 것이 다리다. 인사팀 전산(서버)은 51번이 사람인지 로봇인지 모르고, 지각(워치독 걸림)이면 같은 지각자 명단(멈춤·고장 패널)에 뜬다.
- 숫자 예시: 노드가 1초마다 `{"wake_us": {"p99": 429.5, …}, "loop_hz": 1000, "state": "RUNNING", …}` 을 내면 다리가 `{"device_id": "rt-node-1", "seq": 17, "loop_hz": 1000, "wake_p99_us": 429.5, "state": "running", …}` 로 바꿔 `fleet/rt-node-1/telemetry` 에 올리고, 수집기가 그 초의 다른 장치 50행과 묶어 51행을 COPY 한 번에 넣으면, Grafana 패널 10 에 `rt-node-1` 선이 429.5 us 로 찍힌다(wake p99 값은 11/05 WSL 기록 첫 줄 예시).

## 6. 자주 하는 오해·함정
- 장표의 "state 도 tripped 로" 는 다리 초기 설계의 표현이다. 지금 코드(`state()` :62-68)는 상태 머신 이름(ready/running/fault/recovering)을 우선 올리고, `tripped` 는 JSON 에 `state` 키가 없을 때만 나온다. 워치독이 걸리면 실제로는 `fault` 가 올라가며, 패널 6 은 tripped·fault·updating·recovering 을 모두 세므로 결과는 같다(`fleet/README.md:18` "상태 머신 이름이 장치 state 로").
- 다리가 보내는 숫자 전부가 DB 에 남지는 않는다. 수집기의 저장 열(:56-57)은 `loop_hz`, `wake_p99_us`, `state`, `fw_version`, `seq` 등이고, `wake_max_us`·`work_p99_us`·`timing_drops`·`watchdog_trips`·`rmw`·`backend`·`sched_fifo` 는 MQTT 메시지에는 실리지만 오늘의 표에는 열이 없어 버려진다. 보고 싶으면 `init.sql` 과 `TELEMETRY_COLUMNS` 에 열을 더한다.
- 다리는 ROS 2 가 있는 컴퓨터(로봇 안)에서 돈다. 관제 서버 쪽에는 ROS 2 가 전혀 없다 — 그래서 "서버는 ROS 2 인지 모른다".
- QoS 0 기본은 "가볍게"를 택한 것이다. 2부 표③처럼 수집기가 재시작하는 동안에도 유실 0 이 필요하면 `telemetry_qos=1` 로 띄워야 한다(다리 코드에는 그 인자가 아직 없다).
- `/rt_status` 는 1 Hz 라 이 길로는 1 kHz·100 Hz 원본이 가지 않는다. 원본은 단계 9(기록, rosbag2 MCAP)의 몫 — 관제는 요약, 기록은 원본.

## 7. 면접 한 문장
"RT 노드의 1 Hz 자기 설명을 파이썬 120줄 남짓의 다리가 받아 가상 장치 50대와 같은 DeviceAgent 클래스로 MQTT 에 올리면, 관제 서버는 그것이 ROS 2 로봇인지 모른 채 51번째 장치로 받아 Grafana 에 깨어남 지연 p99 를 그리고, 워치독이 걸리면 멈춤·고장 패널에 잡습니다 — 실물 로봇도 같은 다리를 로봇 안 컴퓨터에서 돌리면 끝입니다."
