# 장표 050 — 단계 8 — rt_status — 1초마다 노드가 스스로를 설명하는 JSON 한 줄
*위치: 1부 로봇을 움직이는 길 · 단계 8/10 상태 발행 · ② 코드 — rt_status 1 Hz JSON*

## 1. 이 장표가 왜 있나
앞 장표(049)는 관절의 위치·속도가 100 Hz 로 나가는 길이었다. 그런데 "노드가 지금 건강한가"는 위치만 봐서는 모른다 — 1 ms 루프가 제때 깨고 있나, 명령이 들어오고 있나, 워치독이 울렸나, 지금 실시간 우선순위로 돌고는 있나. 이 질문들에 답하는 것이 `/rt_status` 다. `publish_status` 가 1초마다 지난 1초의 타이밍 샘플 약 1,000개를 요약하고, 모든 카운터와 실행 환경을 JSON 한 줄에 담아 보낸다. 단계 4 의 표①(3부)에서 본 깨어남 지연 숫자가 '노드 안에서'는 어떻게 나오는지, 단계 10 의 다리(ros_status_bridge)와 단계 9 의 기록(bag_to_csv)이 무엇을 받아 가는지가 전부 이 한 줄에서 출발한다. 이 장표는 코드를 그대로 보이는 대신 JSON 의 항목을 묶음별로 설명한다(코드는 `rt_control_node.cpp:233-291`).

## 2. 장표를 하나씩 읽기
- 첫 줄 "publish_status(1 Hz): 지난 1초의 타이밍 샘플(약 1,000개)을 타이밍 링에서 전부 꺼내 깨어남 지연·작업 시간의 p50/p99/max 를 구한다 (rt_control_node.cpp:233-291)": 생성자 116줄의 `create_wall_timer(seconds(1), publish_status)` 가 부른다. 코드 238~241줄은 `while (g_timing_ring.pop(t))` 로 타이밍 벨트(65,536칸)를 비우며 `wake_lat_ns` 와 `work_ns` 를 두 벡터에 모은다. 1 kHz 이므로 1초면 약 1,000개. 243~252줄은 두 벡터를 정렬(`std::sort`)하고 `size*50/100` 번째 = p50, `size*99/100` 번째 = p99, 마지막 = max 를 꺼내 1000 으로 나눈다(ns → us). 정렬·벡터 할당이 있지만 실행기 스레드이므로 괜찮다.
- 들여쓴 줄 "wake_us {p50, p99, max} — 단계 4 의 깨어남 지연. WSL 참고값: p99 288~606 us. Pi RT 면 수십 us": 깨어남 지연은 '1 ms 뒤에 깨라'고 한 시각보다 얼마나 늦게 깼나(`rt_loop.hpp:31`). 288~606 은 11/05 기록 29줄의 p99 범위(1초 창마다 다른 값). "Pi RT 면 수십 us"는 단계 4 의 Pi 4 RT 커널 측정(표①, p99 수십 us 급)을 가리킨다 — 노드 안 측정은 WSL 에서만 했다.
- 들여쓴 줄 "work_us {p50, p99, max} — ControlStep + 백엔드(물리) 가 걸린 시간. MuJoCo 노드 WSL: 41 / 145 / 247 us": 작업 시간은 `step()` 한 번이 걸린 시간(`rt_loop.hpp:33`) — 단계 5 의 다섯 할 일 + MuJoCo `mj_step` + 상태 벨트 push. 41/145/247 은 11/04 LOG 의 한 줄(p50/p99/max). 11/05 기록 29줄에서는 p99 103~151 us, max 최대 557 us 였다. 1 ms 예산의 15%(p99) 안.
- 들여쓴 줄 "timing_drops · state_drops · commands_received · commands_applied · cmd_ring_full · bad_commands": 세는 것들. timing_drops = 타이밍 벨트 넘침, state_drops = 상태 벨트 넘침(단계 8 기준), commands_received = `on_command` 가 받은 메시지 수, commands_applied = RT 스레드가 실제 적용한 수(단계 5 ①), cmd_ring_full = 우편함(64칸, 단계 3)이 꽉 차 버린 수, bad_commands = 길이가 안 맞거나 NaN 인 명령 수(단계 1~3 의 거름). 11/04 실측: 221 명령 전부 적용, 드롭 0.
- 들여쓴 줄 "watchdog(ok|tripped) · watchdog_trips · step_limited · state(READY|RUNNING|FAULT|…) · state_transitions · illegal_events": 안전 쪽 숫자. watchdog 은 `counters_.watchdog_tripped` 가 참이면 "tripped"(255~258줄), 울린 횟수가 watchdog_trips. step_limited = 한 주기 0.05 rad 넘는 명령을 깎은 횟수(단계 5 ③; 11/04 그리퍼 0.5 rad 명령에 10회). state = 단계 5 ⑤ 상태 기계의 현재 상태 이름(`robot_state_name`), state_transitions = 상태가 바뀐 횟수, illegal_events = 전이표에 없는 사건 수(장표 035).
- 들여쓴 줄 "rt {sched_fifo, mlockall, kernel_realtime, kernel} · backend · loop_hz · rmw — 숫자 옆의 '환경'": 숫자가 어떤 조건에서 나왔는지. `rt_loop_->status()`(254줄)는 RT 스레드가 시작할 때 한 번 써 둔 값 — SCHED_FIFO 적용 성공?, mlockall 성공?, `/sys/kernel/realtime` 이 1 인가?, `uname -r`. backend 는 "sim_lag"/"mujoco"/"feetech_serial", loop_hz 는 `1,000,000,000 / period_ns`, rmw 는 `rmw_get_implementation_identifier()` 가 돌려 주는 DDS 구현체 이름. 왜 넣었나: 11/03 (D0) LOG "SCHED_FIFO·mlockall 이 ok 여도 커널이 RT 가 아니면 소용없다 → 표에 커널·RT 여부를 반드시 같이 적는다", 11/03 (D1) LOG "기본 미들웨어를 가정하지 말고 rt_status 에 RMW 이름을 찍는다".
- 줄 "왜 JSON 문자열인가: 사람이 ros2 topic echo 로 바로 읽고, 다리(ros_status_bridge)가 그대로 관제에 올리고, bag_to_csv 가 CSV 로 편다 — 메시지 타입을 새로 정의하지 않아도 된다": `std_msgs/msg/String` 하나로 끝난다. 새 .msg 를 만들면 패키지·빌드·버전이 하나 늘고, 파이썬 쪽(다리·변환기)도 그 타입을 알아야 한다. 문자열이면 `json.loads` 한 줄.
- 줄 "버퍼 1536바이트 고정, snprintf 한 번 — 발행 스레드에서도 할당을 안 한다": 261줄 `char buf[1536]` 스택 배열에 262~289줄 `snprintf` 한 번으로 전부 찍는다. 발행 스레드는 RT 가 아니라서 꼭 그래야 하는 건 아니지만, 길이가 정해진 출력이라 간단하고 넘칠 걱정이 없다(실제 길이는 약 600~700바이트).
- 오른쪽 상자 "실제 한 줄 (11/05)": 11/05 기록의 한 줄을 요약 꼴로 보인 것. `…` 은 생략. `"p99": 288~606` 은 한 줄의 값이 아니라 29줄의 범위다. `"rt": {"sched_fifo": true, "mlockall": true, "kernel_realtime": false, …}` 와 `"samples_1s": 1000`, `"rmw": "rmw_fastrtps_cpp"` 는 저장소에 남은 CSV(열 13개)에 없는 항목이라 확인하지 못했다(5절).
- 아래 다리 "다음 ▶ 단계 9 — 상태가 토픽으로 나온다. 사고 분석·튜닝용 원본을 어디에 남기고, 남긴 것이 맞는지 누가 보나? (기록, E20)": 토픽 세 개(/joint_states 100 Hz, /joint_command 50 Hz, /rt_status 1 Hz)가 나오니, 다음은 그것을 로봇 안 파일로 남기는 단계 9.

## 3. 용어와 단위
- p50 / p99 / max(백분위수): 1초치 약 1,000개를 작은 것부터 늘어놓고 500번째 / 990번째 / 마지막 값. p99 는 "100번 중 99번은 이보다 빠르다", max 는 최악의 한 번.
- us(마이크로초): 100만분의 1초. 1 ms = 1,000 us. 코드는 ns(10억분의 1초)로 재고 JSON 에는 /1000 해서 us 로 적는다.
- wake_us(깨어남 지연): `clock_nanosleep` 로 정한 시각보다 늦게 깬 시간. work_us(작업 시간): step() 이 걸린 시간. 둘을 더한 것이 1 ms 안이어야 다음 주기가 밀리지 않는다.
- 카운터(counter): 일어난 횟수를 세는 정수. `std::atomic` 으로 RT 스레드가 올리고 실행기 스레드가 읽는다.
- 워치독(watchdog): 명령이 50 ms 안에 안 오면 울리는 감시 타이머(단계 5 ②).
- SCHED_FIFO: 리눅스의 실시간 스케줄링 정책. mlockall: 프로세스 메모리를 RAM 에 고정해 스왑·페이지 폴트를 막는 것. PREEMPT_RT: 커널이 어디서든 끼어들기(선점)를 허용하도록 패치된 실시간 커널.
- RMW(ROS MiddleWare): ROS 2 가 DDS 를 부르는 층. `rmw_fastrtps_cpp`(Fast DDS), `rmw_cyclonedds_cpp`(Cyclone) 등.
- snprintf: 정해진 크기의 버퍼에 형식대로 글자를 찍는 C 함수. 버퍼보다 길면 잘라 준다(넘치지 않는다).

## 4. 쉬운 예시
비유 — 당직 간호사의 1시간 보고: 환자(RT 루프)의 맥박을 1초마다 재서 기록지에 남기고(타이밍 벨트), 1시간마다(여기선 1초마다) 그 기록지를 통째로 가져가 "중앙값, 상위 1% 값, 최고치"를 적고, 투약 횟수·경보 횟수·현재 상태·병실 번호(환경)를 한 줄 보고서(JSON)로 쓴다. 보고서는 사람도 읽고(ros2 topic echo), 병원 전산(관제 다리)에도 그대로 올리고, 월말 통계(bag_to_csv)에도 쓴다. 양식을 새로 만들지 않고 자유 글(문자열)로 쓴 대신 항목 이름을 늘 같게 한다.

숫자 예시 — 어떤 1초 창에서 wake 샘플 1,000개를 정렬했더니 500번째가 99.5 us, 990번째가 488.5 us, 마지막이 1,057.5 us 였다(11/05 CSV 2번째 줄). 그러면 JSON 은 `"wake_us": {"p50": 99.5, "p99": 488.5, "max": 1057.5}`. 같은 창의 work 는 43.5 / 132.4 / 358.8 us. 두 p99 를 더해도 621 us < 1,000 us 라 주기는 밀리지 않았고, 그래서 `timing_drops` 0, `state` RUNNING 이다.

## 6. 자주 하는 오해·함정
- "p99 가 288~606 us 면 1 ms 루프가 깨진 것 아닌가?" — 아니다. 예산 1 ms 안이고 드롭 0 이다. 다만 WSL 참고값이며 실시간 환경이 아니다. 같은 노드를 Pi 4 RT 커널에서 돌리면 단계 4 측정기 기준 수십 us 급이 기대값이다(노드 안 측정은 아직 WSL 만).
- "wake 와 work 를 더한 max 가 1 ms 를 넘으면?" — 그 주기는 밀리고 `period_err_ns` 가 커지지만, 루프는 다음 깨어남 시각을 절대 시각으로 잡으므로(단계 4) 한 번 밀린 것이 누적되지 않는다. 11/05 wake max 2,984 us 가 있었는데도 드롭이 0 인 이유다.
- "rt_status 가 1초에 한 번이라 느린 것 아닌가?" — 이것은 통계 요약이다. 100 Hz 가 필요한 것은 /joint_states 이고, 1 kHz 원본 타이밍은 통계로 압축하는 것이 목적이다. 관제(단계 10)로 올라갈 때도 1 Hz 가 장치 50대와 같은 박자다.
- "JSON 문자열은 비효율적이지 않나?" — 1초에 700바이트다. 비효율이 문제 될 양이 아니고, 타입 정의 없이 세 소비자(사람·다리·변환기)가 그대로 쓰는 이득이 크다. 반면 /joint_states 는 100 Hz 라 표준 바이너리 메시지를 쓴다.
- 함정(11/04 LOG): 다른 RMW 로 떠 있던 ros2 데몬 때문에 `ros2 topic echo` 가 "does not appear to be published yet". `ros2 daemon stop` 뒤 재시도.
