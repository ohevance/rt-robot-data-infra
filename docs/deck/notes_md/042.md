# 장표 042 — 단계 6 — 백엔드 B — 시뮬레이션 걸음을 제어 주기에 맞추는 법 (tune_timestep)
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ② 코드 — 백엔드 B 걸음 맞추기*

## 1. 이 장표가 왜 있나
- 장표 041 의 `write_command` 안에 `for (s < substeps_) mj_step(...)` 이 있었다. "한 주기에 물리를 몇 걸음 밟나" 가 `substeps_` 인데, 그 값이 어디서 오는지를 설명하지 않으면 그 코드는 반쯤만 이해한 것이다. 이 장표가 그 빈칸이다.
- 문제의 본질: 제어 주기(1 ms)와 물리 모델의 기본 걸음(이 모델은 2 ms)은 서로 모르는 값이다. 그냥 두면 1 ms 마다 2 ms 짜리 걸음을 밟아 시뮬레이션 시간이 실제보다 두 배 빨리 흐른다. 그래서 init 때 한 번, 걸음을 제어 주기에 **정확히 나누어떨어지게** 맞춘다.
- 이 함수는 init(RT 밖)에서만 불린다. 즉 1 ms 루프 안에는 계산이 없고, 루프 안에는 결과(`substeps_`)만 쓰인다.

## 2. 장표를 하나씩 읽기
코드는 `mujoco_backend.cpp` 110~125줄. 앞의 네 줄 주석이 규칙을 전부 말한다.
- 110~113줄 주석: "제어 주기 1 ms, 모델 기본 걸음 2 ms 면 → 걸음 1 ms 로 줄여 주기마다 1번. 제어 주기 5 ms, 모델 걸음 2 ms 면 → 걸음 1.67 ms 로 맞춰 주기마다 3번. (올림(ceil)을 쓰는 이유: 걸음은 모델이 정한 값보다 '작게' 만 바꾼다. 키우면 물리가 불안정해진다)".
- 114줄 `tune_timestep(period_ns)`: 제어 주기를 나노초로 받는다(1 kHz 면 1,000,000).
- 115줄 `period_s = period_ns / 1e9`: 초 단위로 바꾼다(0.001 s).
- 116줄 `model_dt = model_->opt.timestep`: 모델 파일이 정한 기본 걸음(초). SO-ARM100 모델은 0.002 s.
- 117줄 `substeps = ceil(period_s / model_dt - 1e-9)`: 주기를 걸음으로 나눈 값을 **올림**한다. 0.001 / 0.002 = 0.5 → 올림 1. 0.005 / 0.002 = 2.5 → 올림 3. `- 1e-9` 는 부동소수점 오차 때문에 정확히 나누어떨어지는 경우(예 2.0000000001)가 3 으로 올라가는 것을 막는 작은 여유.
- 118~120줄: 최소 1 걸음. 주기가 걸음보다 짧아도 한 번은 밟는다.
- 121줄 `substeps_ = substeps`: 루프에서 쓸 값으로 저장.
- 122줄 `sim_timestep_s_ = period_s / substeps`: 새 걸음 = 주기 ÷ 걸음 수. 1 ms ÷ 1 = 1 ms. 5 ms ÷ 3 = 1.67 ms.
- 123줄 `model_->opt.timestep = sim_timestep_s_`: 모델의 걸음을 새 값으로 **덮어쓴다**. 이제 `mj_step` 한 번이 정확히 그만큼 진행한다. (mjModel 은 "읽기 전용" 이라고 머리글에 썼지만 옵션 값은 init 때 고쳐도 된다 — 루프가 돌기 전이므로.)

왜 올림인가(가장 중요한 줄): 내림을 쓰면 걸음이 모델이 정한 값보다 **커진다**(예: 5 ms ÷ 2 = 2.5 ms 걸음). 물리 적분은 걸음이 클수록 불안정해져(스프링이 폭발하듯 발산) 모델 작성자가 "이 걸음 아래로" 라고 정해 둔 값을 넘기면 안 된다. 올림은 걸음을 **작게만** 바꾸므로 안전하다. 대신 걸음 수가 늘어 비용이 조금 는다.

읽는 포인트 네 개는 위 설명과 1:1 이고, 마지막 "노드 시작 로그: '제어 주기 1.000 ms = mj_step 1번 x 1.000 ms'" 는 `print_mapping` 함수(127줄 이후)가 init 끝에 찍는 줄이다. 노드를 띄우면 터미널에서 이 줄로 "걸음 맞추기가 어떻게 됐나" 를 바로 확인할 수 있다.

## 3. 용어와 단위
- **timestep(걸음)**: 물리 엔진이 한 번 계산할 때 진행시키는 시간. 작을수록 정확하고 안정적이지만 계산이 많다.
- **substeps(부분 걸음 수)**: 제어 주기 하나를 몇 걸음으로 나누나.
- **ceil(올림)**: 2.5 → 3, 0.5 → 1. 반대인 floor(내림)는 2.5 → 2.
- **1e-9**: 0.000000001. 부동소수점(컴퓨터의 실수) 계산 오차를 흡수하기 위한 아주 작은 수.
- **수치 적분의 안정성**: 물리 엔진은 "지금 상태 + 걸음 × 변화율" 로 다음 상태를 구한다. 걸음이 너무 크면 스프링·접촉처럼 빠르게 변하는 것을 못 따라가 값이 튀거나 발산한다.
- **ns / ms / s**: 1 s = 1,000 ms = 1,000,000,000 ns. 1 ms = 1,000,000 ns.

## 4. 쉬운 예시
- 비유: **계단 오르기**. 1 m(제어 주기)를 올라야 하는데 이 계단의 최대 허용 단 높이가 2 m(모델 걸음)라면 1 m 단 하나로 충분하다(1걸음). 5 m 를 올라야 하면 2 m 단 2개 + 1 m 단 1개가 아니라, 똑같은 1.67 m 단 3개로 나눈다 — 어느 단도 2 m 를 넘지 않게(올림). 단을 2.5 m 로 키우면(내림) 발을 헛디딘다(불안정).
- 숫자 예시: 실물 모드 `loop_hz.real: 200`(장표 043)처럼 제어 주기가 5 ms 가 되면 — 5 / 2 = 2.5 → 올림 3걸음, 새 걸음 1.667 ms. 1초에 200주기 × 3걸음 = 600걸음. 1 kHz 때(1,000걸음)보다 걸음 수는 오히려 줄지만 한 주기 안 비용은 3배(약 25 us, 추정)가 된다 — 그래도 5 ms 예산의 0.5%.

## 6. 자주 하는 오해·함정
- "걸음을 제어 주기와 같게 하면 끝 아닌가?" — 모델 걸음이 제어 주기보다 **작은** 경우(예: 모델 0.5 ms, 주기 1 ms)에는 주기와 같게 키우면 안 된다. 그래서 올림으로 걸음 수를 정하고 걸음은 항상 모델 값 이하로 둔다.
- "substeps 가 많으면 더 정확하니 크게 두자" — 비용이 비례해서 는다. 필요한 최소(올림 결과)가 정답이다.
- "mjModel 은 읽기 전용이라더니 왜 고치나?" — 머리글의 "읽기 전용" 은 루프 중 이야기다. init 때 옵션을 바꾸는 것은 허용된다. 루프가 시작된 뒤에는 건드리지 않는다.
- 제어 주기를 바꾸면(예: 2 kHz) `substeps_` 가 자동으로 다시 계산되므로 코드를 고칠 필요가 없다 — 그것이 이 함수를 둔 이유다.

## 7. 면접 한 문장
- "제어 주기와 물리 걸음은 서로 모르는 값이라 init 때 한 번 맞춥니다 — 주기를 걸음으로 나눠 올림한 수만큼 밟고, 걸음은 모델이 정한 값보다 작게만 바꿉니다. 키우면 물리가 발산하기 때문이고, 이 모델은 1 ms = 한 걸음이었습니다."
