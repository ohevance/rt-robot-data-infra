# 장표 069 — ③ 들머리 — 수집기: 빠르게, 그러나 DB 가 죽어도·내가 죽어도 잃지 않게
*위치: 2부 데이터의 길 · ③ 수집기 · 들머리*

## 1. 이 장표가 왜 있나

바로 앞 장표(068, 브로커 설정)에서 "브로커(우체국)는 수집기가 없는 동안 메시지를 대신 들고 있고, 재시작해도 잃지 않는다"는 것을 확인했다. 그러면 다음 질문이 자연스럽게 생긴다 — 브로커가 넘겨주는 메시지를 받아 데이터베이스(DB)에 넣는 쪽, 즉 **수집기(collector)** 는 잃지 않나? 수집기는 데이터의 길에서 가장 바쁜 곳이다. 초당 50개(장치 50대 × 1 Hz)를 받아 DB 에 넣어야 하고, DB 가 죽을 수도 있고, 수집기 자신이 죽을 수도 있고, 실수로 두 개가 뜰 수도 있다. 이 장표는 ③ 수집기 묶음의 **들머리(gate)** — 들어온 것 → 문제 → 기준 → 확인 방법 → 결과 → 판단의 여섯 상자로, 이 묶음이 무엇을 풀어야 하고 무엇을 넘어야 다음(④⑤ DB·Grafana)으로 가는지를 한 장에 정리한다. 뒤에 따라오는 장표 071~074 은 이 여섯 상자를 코드와 실측으로 채운다.

## 2. 장표를 하나씩 읽기

**들어온 것(회색 상자)** — "브로커가 넘겨주는 초당 50개 메시지 (②)". 가상 장치 50대가 각각 1초에 1개씩 텔레메트리(측정값 묶음)를 보내므로 수집기 입장에서는 초당 50개가 들어온다. ② 는 앞 묶음(브로커)에서 넘어왔다는 표시다.

**문제(민트 상자)** — 세 가지 위험이 한 상자에 들어 있다.
- "행마다 INSERT 하면 DB 왕복 300번/초(300대)": DB 에 한 줄(행, row) 넣을 때마다 왕복 통신을 하면, 장치가 300대일 때 1초에 300번 왕복한다. 느리고 DB 가 바빠진다. 그래서 1초 동안 모았다가 한 번에 넣는다(묶음, batch).
- "묶으면 빠르지만 DB 가 죽은 동안의 묶음과 종료 순간의 마지막 1초를 잃기 쉽다": 모았다가 넣는 방식의 약점. DB 가 안 받아 주면 그 묶음은 어디로 가나? 수집기가 종료 신호를 받은 순간 손에 들고 있던 '아직 안 넣은 1초치'는? 둘 다 설계로 막아야 한다.
- "두 개가 뜨면 서로 밀어낸다": MQTT 는 같은 이름(client_id)의 새 접속이 옛 접속을 끊는다. 수집기 이름은 "collector" 로 고정이라 실수로 두 개를 띄우면 둘이 2초마다 번갈아 끊기며 메시지를 반반 받는다(11/04 실제 사고).

**기준(마름모)** — "DB 중단 중 유실 0(backlog), 종료 때 마지막 1초 보존, 한 번에 하나만 뜨나(flock)?". 세 위험에 하나씩 대응하는 합격선이다. backlog 는 DB 가 죽은 동안 수집기가 메모리에 들고 있는 묶음 목록, flock 은 리눅스의 파일 잠금 기능이다. 왜 이 기준인가: 관제의 목표가 "잃지 않는 것"이므로 세 순간 모두에서 유실이 0 이어야 하고, 그것을 숫자로 보여야 한다.

**확인 방법(파란 상자)** — "E06·E08 — db 장애·collector 장애(SIGTERM + 재시작) · test_collector_resilience 8건(가짜 DB: 실패 → backlog → 복귀 → 순서 유지 → 상한)". 두 종류의 확인이다. 하나는 진짜 환경에서 일부러 고장 내는 실험(E06 은 1차, E08 은 고친 뒤 재측정): DB 컨테이너를 10초 멈추거나(db 장애), 수집기 프로세스에 종료 신호(SIGTERM)를 보내 죽였다가 같은 명령으로 다시 띄운다(collector 장애). 다른 하나는 가짜 DB(fake_psycopg) 위에서 1초 만에 도는 단위 테스트 — DB 쓰기를 일부러 실패시켜 backlog 에 남는지, 복귀하면 오래된 것부터 순서대로 다 들어가는지, 상한을 넘으면 오래된 묶음을 버리는지를 본다. (확인: 이 테스트 파일의 테스트 함수는 6개이고 그 안의 검사 항목(check)은 26개다. 장표의 "8건"은 docs/ENVIRONMENT.md 의 표기를 따른 것이다.)

**결과(보라 테두리 상자)** — "db 장애 0 / 1341(뒤늦게 570행 적재), collector QoS 1 0 / 1311, QoS 0 508 / 1312(보호 없음). 11/04 전엔 종료 순간 50행 유실".
- "0 / 1341": DB 를 10초 멈춘 창에서 장치들이 만든 메시지 1,341개 중 잃은 것 0개. "뒤늦게 570행"은 DB 가 죽어 있던 동안 수집기가 backlog 에 들고 있다가 복귀 뒤 한꺼번에 넣은 행 수(50대 × 약 11초 ≈ 570).
- "collector QoS 1 0 / 1311": 수집기를 10초 죽였을 때, QoS 1 + 지속 세션이면 브로커가 대신 들고 있다가 넘겨 주어 1,311개 중 유실 0.
- "QoS 0 508 / 1312(보호 없음)": 같은 장애를 보호 없이(QoS 0) 하면 1,312개 중 508개를 잃는다. 예측값 500(50대 × 10초)에 종료·재시작 순간의 8개가 더해진 수. 보호가 있고 없음의 차이를 숫자로 남긴 줄이다.
- "11/04 전엔 종료 순간 50행 유실": 종료 처리를 고치기 전에는 SIGTERM 을 받는 순간 손에 든 1초치(장치당 1개 = 50개)가 사라졌다(E07 의 원인 ②).

**판단 → 다음(진한 상자)** — "통과 → ④⑤: 1초 묶음이 DB 로 들어간다. 시간 데이터를 어떻게 쌓고 사람에게 보이나?". 세 기준을 모두 숫자로 넘었으므로 다음 묶음(DB 와 Grafana)으로 간다.

**아래 상자(이 묶음의 장표)** — ② on_message 코드(071) · ② flush_once·drain_backlog 코드(072·073) · ④ 종료 때 마지막 1초(판단 사슬, 074). "넘어가는 조건: 잃을 수 있는 세 순간(DB 죽음·종료·중복)마다 코드와 테스트와 실측이 있다" — 즉 말이 아니라 코드 위치 + 테스트 + 측정 숫자 셋이 다 있어야 통과다.

## 3. 용어와 단위

- **수집기(collector)**: MQTT 브로커를 구독해 장치의 메시지를 받아 DB 에 넣는 서버 프로그램. `fleet/collector/collector.py`.
- **텔레메트리(telemetry)**: 장치가 주기적으로 보내는 측정값 묶음(온도·CPU·상태·일련번호 등). 여기서는 1 Hz, 즉 1초에 1번.
- **Hz(헤르츠)**: 1초에 몇 번. 50대 × 1 Hz = 초당 50개.
- **행(row)**: DB 표의 한 줄. 메시지 1개 = 행 1개. "570행" = 메시지 570개.
- **INSERT / COPY**: DB 에 데이터를 넣는 명령. INSERT 는 한 번에 한 줄(또는 몇 줄), COPY 는 묶음을 한 번에 흘려 넣는 빠른 방식.
- **묶음(batch)**: 1초 동안 모은 행들을 한 덩어리로 다루는 것.
- **backlog**: DB 에 못 넣어서 수집기가 메모리에 들고 있는 묶음 목록. 밀린 일거리.
- **SIGTERM**: 리눅스에서 "곱게 끝나라"는 종료 신호. `kill` 명령의 기본값. Ctrl+C 는 SIGINT 로 같은 길을 탄다.
- **QoS 0 / 1**: MQTT 의 전달 보장 등급. 0 = 보내고 잊음, 1 = 받았다는 확인(PUBACK)이 올 때까지 재전송.
- **지속 세션(persistent session)**: 구독자가 없는 동안 브로커가 그 구독자 몫의 QoS 1 메시지를 대신 보관하는 설정(clean_session=False).
- **flock**: 리눅스의 파일 잠금. 한 프로세스가 잠근 파일은 다른 프로세스가 잠글 수 없고, 프로세스가 죽으면 커널이 자동으로 푼다.
- **client_id**: MQTT 접속 이름. 같은 이름의 새 접속이 들어오면 브로커가 옛 접속을 끊는다.

## 4. 쉬운 예시

- 비유: 우체국(브로커)에서 편지(메시지)를 받아 장부(DB)에 적는 서기(수집기)를 떠올리자. 편지가 올 때마다 장부가 있는 옆방까지 왕복하면 하루 300번 뛰어야 하니, 1분 동안 모아서 한 번에 옮겨 적는다(묶음). 그런데 옆방 문이 잠겨 있으면(DB 죽음) 모은 편지를 책상 서랍(backlog)에 넣어 두고 문이 열리면 오래된 것부터 옮겨 적는다. 퇴근 명령(SIGTERM)이 떨어져도 손에 든 편지를 다 적고 나간다(곱게 종료). 그리고 서기가 둘이면 서로 편지를 뺏으니(client_id 충돌) 출입문에 "근무 중" 팻말(flock)을 걸어 한 명만 들어온다.
- 숫자 예시: 50대가 1 Hz 로 보내면 10초 동안 500개가 생긴다. 수집기를 10초 죽였을 때 보호가 없으면(QoS 0) 그 500개 정도를 잃는다 — 실측 508. 보호(QoS 1 지속 세션)가 있으면 브로커가 500개를 들고 있다가 수집기가 돌아오면 넘겨 주어 0.

## 6. 자주 하는 오해·함정

- "QoS 1 이면 수집기가 받은 메시지는 안전하다"는 오해: paho 라이브러리는 메시지를 **받는 즉시** 확인(PUBACK)을 보내므로 "받았다 ≠ 저장했다". 그 틈을 종료 처리(마지막 flush)로 메웠고, 완전한 해법(DB 적재 뒤 수동 ACK)은 2주 범위 밖으로 뺐다(DECISIONS 11/04).
- "묶음이라 1초 늦는 것도 유실 아닌가?" — 아니다. 늦게 들어갈 뿐 들어간다. 대신 전달 지연 수치에는 이 1초가 안 들어 있다고 표③에 적어 두었다.
- 재시작 함정(11/04): 죽인 수집기를 `/proc/<pid>/exe` 경로로 다시 띄우니 가상환경(venv)을 잃고 바로 죽었다. 지금은 `/proc/<pid>/environ` 의 VIRTUAL_ENV·PATH 로 같은 환경에서 다시 띄운다(장표 084 비고).
- 테스트 수 표기: 이 파일의 테스트 함수는 6개(검사 항목 26개)인데 문서에는 "8건"으로 적혀 있다. 함수 수와 검사 항목 수를 섞어 세지 않도록 주의.

## 7. 면접 한 문장

"수집기가 잃을 수 있는 순간은 셋 — DB 가 죽을 때, 내가 죽을 때, 둘이 뜰 때 — 이고, 각각 backlog·곱게 종료·flock 으로 막았으며, 셋 다 코드·단위 테스트·실측(0 / 1341, 0 / 1311)으로 증명한다."
