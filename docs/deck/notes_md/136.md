# 장표 136 — 덧붙임 (11/06) — 위로보틱스 공개 모델 ALLEX 48 자유도를 프로필 하나로: 같은 코드, 비용 70~100배, 500 Hz 결정
*위치: 7부 왜·사고·방식 · 덧붙임 ALLEX (11/06)*

## 1. 이 장표가 왜 있나
장표 본편(001~135, 137~139)은 11/05 에 만들었다. 이 장표는 그 다음 날(11/06) 한 일을 한 장으로 덧붙인 것이라 7부의 끝, "끝" 섹션 바로 앞에 둔다 — 중간에 끼우면 장표 번호와 설명 문서 번호가 전부 밀리기 때문이다. 앞 장표(135)까지로 용어 정리가 끝났고, 남은 질문은 하나였다: 1부 단계 6 에서 "로봇을 바꾸는 일은 설정 파일을 바꾸는 일"이라고 했는데, 그것을 6 자유도 팔이 아닌 **지원하는 회사의 로봇**으로도 보일 수 있나? 위로보틱스는 2026-06-29 에 상체 휴머노이드 ALLEX 의 시뮬레이션 모델(MJCF·USD·URDF, BSD-3)을 공개했다. 이 장표는 그 모델을 같은 노드에 붙인 결과 — 바뀐 코드, 물리 비용, 그래서 내린 결정, 그리고 틀렸던 어림 — 를 KPI 네 개와 글머리표 세 줄로 답한다.

## 2. 장표를 하나씩 읽기
KPI 상자 네 개를 왼쪽부터, 그다음 글머리표 세 줄, 바닥 줄, "다음 ▶" 순서로 읽는다.

- KPI 1 "48 / 0줄 — 자유도 / 바뀐 제어 코드, robots/allex.yaml 하나 (+ 받기 스크립트)": 자유도 48 은 ALLEX 의 position 액추에이터 수(오른팔 7 + 오른손 15 + 왼팔 7 + 왼손 15 + 허리 2 + 목 2)다. "0줄"은 `control_step.cpp`·`mujoco_backend.cpp`·`rt_control_node.cpp` 가 한 줄도 안 바뀌었다는 뜻 — ALLEX 커밋(`git show --stat f1e89cb`)의 13개 파일은 프로필, 모델을 고정 커밋으로 받는 `scripts/get_allex.sh`, 관절 이름을 뽑는 `scripts/profile_joints.py`, 생성된 파라미터 파일, 테스트의 환경변수 처리, CI 단계, 문서 7개다. 괄호의 "받기 스크립트"는 모델이 250 MB 라 저장소에 넣지 않고 내려받기 때문이다.
- KPI 2 "×70~100 — 물리 한 주기 비용, 6축 대비. 같은 PC: 4.9/6.3/20.8 → 336/622/1,785 us": 같은 PC(WSL2)에서 1 kHz 로 2,000주기를 돌렸을 때 한 주기(물리 한 걸음 + 상태 읽기)의 p50 / p99 / max. 6축 팔 4.9 / 6.3 / 20.8 us 가 48축에서 336.2 / 622.0 / 1,784.5 us — 각각 ×69, ×99, ×86 이라 "약 70~100배"로 적었다. 자유도는 8배인데 비용이 그보다 큰 이유는 글머리표 2 에.
- KPI 3 "458 · 622 — 1 kHz 물리 p99 (us), 러너 · WSL = 1 ms 예산의 46~62%": 같은 1 kHz 측정을 GitHub 러너에서도 했다(CI 아티팩트). 러너 p99 457.8 us(46%), WSL 622.0 us(62%). 합격선(p99 < 주기의 90% = 900 us)은 두 환경 모두 넘었다. 그러나 물리만으로 1 ms 의 절반 가까이가 사라지면 제어·통신·기록에 남는 몫이 380~540 us 뿐이고, WSL 에서는 max 1,784.5 us 로 주기를 넘긴 주기가 있었다(러너는 max 608.9 로 안 넘김 — 환경의 꼬리).
- KPI 4 "500 Hz — ALLEX 프로필 기본 주기 (모델 걸음 2 ms). 실측 p99 러너 510 (26%) · WSL 1,000 us (50%)": 그래서 `robots/allex.yaml` 의 `loop_hz.sim` 을 1000 에서 500 으로 바꿨다 — 프로필의 숫자 하나이고 코드는 바뀌지 않는다. 모델 파일의 기본 걸음(timestep)이 2 ms 라서 500 Hz 는 모델 작성자의 운영점이기도 하다. 500 Hz 로 다시 잰 실측은 러너 p50 390.1 / p99 510.4 / max 684.6 us(2 ms 예산의 26%), WSL 326.7 / 999.8 / 1,589.4 us(50%).
- 글머리표 1 "왜 했나: …": 회사 모델의 액추에이터 48개가 전부 position 서보(`<position kp kv>`)이고 관절에 이름이 있어, 이 백엔드가 기대하는 꼴과 같았다 — SO-ARM100 과 똑같이 "목표 각도를 ctrl 에 쓴다"로 움직인다. 모델에는 관절이 60개 있지만 12개(손가락 DIP·IP, 허리 링크)는 등식 제약(equality)으로 다른 관절을 따라 움직이는 수동 관절이라 명령 대상이 아니다. 그래서 프로필에 이름 48개를 반드시 적는다 — 비워 두면 "모델 순서대로 앞 48개"가 되어 수동 관절이 섞인다.
- 글머리표 2 "무엇이 나왔나: …": 제어 코드·백엔드·노드 무변경은 `git show --stat` 로 확인했다. 물리가 예상보다 무거운 이유는 손가락 30개 관절의 접촉과 등식 제약 12개가 제약 풀이(solver)의 일을 자유도 비율 이상으로 키우기 때문으로 **본다(추정)** — 손을 뺀 모델로 재면 가를 수 있지만 "회사 모델을 그대로 돌린다"는 요점과 어긋나 하지 않았다. 500 Hz 결정에서 버린 대안 셋: 1 kHz 유지(p99 는 통과하지만 꼬리를 무시하는 것), 물리를 두 주기에 한 번(백엔드에 "이번 주기는 걸음을 건너뛴다"는 상태가 생겨 한 주기 = 한 걸음의 단순함이 깨짐), 물리를 별도 스레드로(제어가 읽는 상태가 몇 주기 전 것인지 불확실). 근거는 DECISIONS 11/06.
- 글머리표 3 "정직한 줄: …": 500 Hz 로 바꾸기 전에 "한 주기에 `mj_step` 1번은 그대로니 물리 비용은 같고 예산만 2배 → p99 31%" 라고 어림했는데, WSL 실측은 50%(p99 999.8 us)였다. p50 은 326.7 로 1 kHz 때(336.2)와 같고 꼬리만 나빠졌다. 러너에서는 1 kHz 458 → 500 Hz 510 us 로 +11% 뿐이라, WSL 의 +61% 는 환경(RT 커널 아님)의 꼬리가 주된 원인으로 **보인다(추정)**. 한 번씩 잰 값으로는 확정하지 못하므로 조건별 3회 반복과 10초 측정을 남은 일로 적었다. 결정(500 Hz)은 유지했고, 틀린 어림은 E21 4절과 DECISIONS 에 고치지 않고 그대로 남겼다 — "숫자를 믿기 전에 숫자를 만든 방법을 의심한다"는 3부의 태도를 자기 어림에도 적용한 것이다.
- 바닥 줄 "원본: docs/experiments/E21.md, docs/measurements/mujoco_backend_allex_{wsl_1khz, wsl_500hz, ci_1khz_run42172730308, ci_500hz_run42175845461}.json, docs/DECISIONS.md 11/06. 남은 것: 노드 안 work_us(500 Hz)·drop, 반복 측정": 측정 원본 네 파일의 이름과, 아직 안 한 두 가지.
- "다음 ▶" 다리 "끝 — 결국 로봇은 이렇게 움직인다": 덧붙임은 여기까지이고 다음은 마무리 세 장이다.

## 3. 용어와 단위
- ALLEX: 위로보틱스의 상체 휴머노이드. 공개 저장소 `github.com/wirobotics-rih/allex_model`(v0.2.0, 커밋 5e12052 로 고정). MJCF = MuJoCo 모델 파일 형식.
- 자유도(DOF): 독립적으로 움직일 수 있는 관절 수. 여기서는 명령을 받는 액추에이터 수 48 을 뜻한다. 모델의 관절 수(`nq`) 60 과 다르다 — 12개는 수동.
- position 액추에이터: 목표 각도를 주면 `kp`(강성)·`kv`(감쇠)로 토크를 만들어 따라가는 모터 모델. ALLEX 어깨는 kp 5000 — 관절 0 이 목표 0.300 rad 에 0.2976 까지 닿았다(오차 0.1°).
- 등식 제약(equality constraint): "관절 B 는 관절 A 의 몇 배로 움직인다" 같은 묶음. 손가락 끝마디가 가운데 마디를 따라 굽는 것을 이렇게 표현한다.
- 제어 주기 1 kHz = 1 ms, 500 Hz = 2 ms. p99 = 100번 중 99번은 이 값 이내. us = 마이크로초 = 1,000분의 1 ms. 622 us = 0.622 ms.
- 모델 걸음(timestep): 물리 엔진이 한 번에 전진시키는 시간. ALLEX 모델은 2 ms. 제어 주기가 더 짧으면 백엔드가 걸음을 줄여 맞춘다(올림 규칙, 장표 042).

## 4. 쉬운 예시
- 비유: 같은 운전석(제어 코드)에 경차(6축 팔) 대신 대형 트럭(48축 휴머노이드)을 붙였다. 핸들·페달은 그대로인데(코드 0줄) 엔진이 한 바퀴 도는 데 드는 시간이 70~100배 길어졌다. 1초에 1,000번 돌리던 박자(1 kHz)로는 한 바퀴가 박자의 절반을 먹으니, 트럭에 맞는 박자 500 Hz(모델 설계자가 정한 2 ms 걸음)로 돌린다 — 박자는 설정 파일의 숫자 하나다.
- 숫자 예시: 1 ms 를 1,000원 예산이라 하자. 6축 팔의 물리는 8.5원(러너). ALLEX 는 러너 458원, WSL 622원 — 나머지 일(제어·발행·기록)에 380~540원이 남는다. 예산을 2,000원(500 Hz)으로 늘리면 러너는 510원(26%), WSL 은 1,000원(50%). "예산을 두 배로 늘리면 비율이 절반이 된다(31%)"는 계산은 WSL 에서 맞지 않았다 — 한 걸음의 값(1,000원)이 1 kHz 때(622원)보다 올랐기 때문이다.

## 6. 자주 하는 오해·함정
- "ALLEX 실물을 움직였다"는 오해: 아니다. 공개된 시뮬레이션 모델을 MuJoCo 에서 돌린 것이다. 실물 ALLEX 는 물론 실물 SO-101 도 없다(DECISIONS 11/06 정정).
- "48 자유도에 맞추려고 코드를 고쳤다"는 오해: 관절 수 상한은 처음부터 컴파일 상수 `kMaxJoints = 64` 였고 노드는 `dof` 를 설정으로 받는다. 6 이 박혀 있던 곳은 테스트 코드 하나였고, 그것을 환경변수로 받게 고친 것이 유일한 코드 변경이다(테스트는 제어 코드가 아니다).
- "500 Hz 면 비용도 절반"이라는 함정: 비용은 한 걸음의 값이고 주기는 예산이다. 예산을 두 배로 늘려도 한 걸음의 값은 그대로이거나(러너 +11%) 오히려 올랐다(WSL +61%). 이 장표의 "정직한 줄"이 그 이야기다.
- `get_allex.sh` 가 찍는 "joint 태그 : 72" 를 관절 수로 읽는 함정: 등식 제약 안의 `<joint …>` 태그 12개가 섞인 수다. 실제 관절은 60(`nq`), 명령 대상은 48(`nu`). 스크립트의 설명 줄도 그렇게 고쳤다(LOG 11/06).
- CI 의 ALLEX 단계가 1 kHz 가 아니라 500 Hz 인 것을 "1 kHz 는 실패해서"로 읽는 오해: 러너 1 kHz 도 통과했다(p99 458 < 900). 운영점만 게이트로 두고 "어디까지 되나"는 측정(E21)에 두는 것이 이유다(장표 121).

## 7. 면접 한 문장
"귀사가 공개한 ALLEX 모델을 제 노드에 붙이는 데 바뀐 제어 코드는 0줄, 바뀐 것은 관절 이름 48개를 적은 프로필 하나였습니다. 물리 비용은 6축의 70~100배라 주기를 모델 걸음과 같은 500 Hz 로 두었고, '예산이 2배니 비율은 절반'이라던 제 어림이 WSL 실측에서 틀린 것까지 그대로 적어 두었습니다 — 다음은 반복 측정으로 그 꼬리의 출처를 가르는 일입니다."
