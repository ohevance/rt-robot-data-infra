# 장표 062 — ① 들머리 — 장치 에이전트: 끊겨도 잃지 않으려면
*위치: 2부 데이터의 길 · ① 장치 에이전트 · 들머리*

## 1. 이 장표가 왜 있나
2부의 지도(060)와 구조도(061)를 봤으니 이제 첫 상자, 장치 에이전트로 들어간다. 1부의 단계 들머리와 같은 꼴이다 — 들어온 것 → 문제 → ◇기준 → 확인 방법 → 결과 → 판단. 장치 에이전트가 풀어야 하는 문제는 하나다: 장치와 서버 사이의 네트워크·브로커는 반드시 끊기는데, 끊긴 동안의 데이터를 잃으면 2부 전체의 목표인 '유실 0' 이 처음부터 불가능하다. 그래서 이 묶음의 기준은 "끊김 동안 장치가 보존하고, 붙으면 전부 재전송하나"이고, 그 실험(E05)은 3부 장표 097 에 있다 — 여기서는 결과 숫자만 가져온다.

## 2. 장표를 하나씩 읽기
위 줄 왼쪽에서 오른쪽, 아래 줄 오른쪽에서 왼쪽으로 읽는다.

- 들어온 것(회색): "로봇(단계 10 의 다리) 또는 가상 장치 50대의 1 Hz 숫자". 1부 단계 10 의 `ros_status_bridge.py` 가 RT 노드의 rt_status 를 받아 DeviceAgent 로 올리고, 실물이 없을 때는 `virtual_fleet.py` 의 가상 장치 50대가 같은 클래스로 난수 걸음 값을 낸다. 둘 다 1초에 한 번.
- 문제(민트): "장치와 서버 사이의 네트워크·브로커는 끊긴다. 끊긴 동안의 데이터를 잃으면 '유실 0' 은 처음부터 불가능". 공유기·LTE 뒤의 장치, 재시작하는 브로커 — 끊김은 예외가 아니라 일상이다. 장치가 보내고 잊으면(QoS 0, 버퍼 없음) 끊긴 10초치 500개는 사라진다.
- 기준(마름모, 노랑): "끊김 동안 장치가 보존하고, 붙으면 전부 재전송되나(버퍼 수 = 재전송 수)? 비정상 종료도 서버가 아나?". 합격선 둘. ① 버퍼에 들어간 수와 재접속 뒤 재전송한 수가 같을 것 — 같으면 끊긴 구간 유실 0 ② 장치가 갑자기 죽어도 서버가 "offline" 을 알 것(유언). 왜 이 기준인가: ①은 store-and-forward 가 실제로 작동한다는 숫자 증거이고, ②는 '조용히 사라진 장치'를 서버가 알아차리는 유일한 방법이다.
- 확인 방법(파랑): "E05 — 브로커 10초 중단(docker compose stop mqtt) 뒤 버퍼·재전송 카운터, 유언(LWT)·보관(retained) 상태 → 3부 장표 97". 가상 장치 50대 1 Hz 를 띄우고 브로커 컨테이너를 10초 멈춘 뒤 살린다. 장치가 텔레메트리에 실어 보내는 `buffered`·`flushed`·`reconnects` 카운터(tick, 100~102줄)와 status 토픽의 online/offline 을 본다. 실험 자체는 3부 097(E05 → E06 → E07 사슬).
- 결과(보라 테두리): "버퍼 654 = 재전송 654(QoS 1). 유언으로 offline, 보관 online. 버퍼 상한 3,600개(1시간), 넘으면 오래된 것부터". 11/03 D2 실측: 50대 × 10초 = 500개가 기대값인데 끊김 감지·재접속 약 3초가 더해져 654개가 버퍼에 들어갔고, 654개가 QoS 1 로 재전송됐다 — 하나도 안 잃었다. 50대 전부 재접속. 버퍼 상한은 `MAX_BUFFER = 3600`(1 Hz 로 1시간), 넘치면 `popleft` 로 가장 오래된 것을 버린다.
- 판단 → 다음(진한 민트): "통과 → ② 브로커: 받는 쪽은 수집기가 없는 동안 대신 들고 있나, 재시작하면?". 장치 → 브로커 구간은 장치 버퍼가 지킨다. 다음 질문은 브로커 → 수집기 구간이다 — 수집기가 죽어 있는 동안 브로커가 들고 있나, 브로커가 재시작하면 그 큐가 남나(② 브로커, 설정 세 줄).

아래 상자: "이 묶음의 장표: ② tick·send_or_buffer 코드 · ② on_connect·flush_buffer·유언 코드 · ② 한 주기 흐름 그림 · ② 가상 장치 50대. 넘어가는 조건: 장치 쪽 보존(store-and-forward)이 숫자로 확인됐다". 다음 네 장표(063~066)의 예고와, ② 로 넘어가는 조건.

## 3. 용어와 단위
- store-and-forward(모았다 보내기): 끊기면 저장해 두고 붙으면 보내는 방식. 여기서는 메모리 `deque` 에 (토픽, 내용) 쌍으로.
- 버퍼(buffer): 모아 두는 자리. 상한 3,600개. buffered_total: 지금까지 버퍼에 들어간 누계, flushed_total: 재전송한 누계, reconnects: 끊겼다 다시 붙은 횟수.
- QoS 1: 브로커가 받았다는 확인(PUBACK)까지 기다리는 전달 등급. 재전송은 반드시 QoS 1 로(126~133줄).
- 유언(LWT): 접속할 때 브로커에 맡기는 "내가 비정상으로 끊기면 이것을 발행하라" 메시지. 여기서는 status "offline".
- 보관(retained): 브로커가 토픽의 마지막 값을 저장. status "online"/"offline" 이 보관이라 늦게 붙은 구독자도 바로 안다.
- 1 Hz: 1초에 한 번. 50대 × 1 Hz = 초당 50개.
- `docker compose stop mqtt`: 브로커 컨테이너를 멈추는 명령(프로세스는 종료, 데이터는 남음). `start` 로 되살린다.

## 4. 쉬운 예시
비유 — 지점과 메모장: 지점 50곳이 본사에 1분마다 매출 문자를 보낸다. 통신사(브로커)가 10분 먹통이 되면 지점 직원이 그동안의 문자를 메모장(버퍼)에 적어 두고, 복구되자마자 등기(QoS 1)로 몰아 보낸다. 메모장은 1시간치(3,600줄)까지만 — 더 길어지면 가장 오래된 줄을 지운다. 지점이 갑자기 문을 닫으면 통신사가 미리 받아 둔 "영업 종료" 문자(유언)를 본사에 대신 보낸다.

숫자 예시 — 50대 × 10초 × 1 Hz = 500개. 실측 654 — 브로커가 멈춘 것을 장치가 알아차리고(keepalive 기반) 다시 붙기까지 약 3초가 더 걸려 654 ÷ 50 ≈ 13초치가 쌓였다. 재전송 654 → 버퍼 수 = 재전송 수 → 그 구간 유실 0. 복구 직후에는 밀린 654개가 한꺼번에 들어와 초당 600개까지 치솟고, 메시지에 적힌 측정 시각 기준 전달 지연 max 가 12.5초로 찍힌다 — 유실이 아니라 지연이다(E05 4-3).

## 6. 자주 하는 오해·함정
- "버퍼가 있으니 유실은 없다"가 아니다. 버퍼는 장치 → 브로커 구간만 지킨다. 브로커 → 수집기 구간(수집기가 죽은 동안)은 QoS 1 + 지속 세션이 지키고(②③), 3,600개 상한을 넘는 긴 끊김은 잃는다 — 그래서 '잃었으면 센다'(seq)가 같이 필요하다.
- "654 ≠ 500 이니 이상한가?" — 아니다. 기대값 500 은 브로커가 멈춘 10초만 센 것이고, 장치가 끊김을 알아채고 다시 붙기까지의 시간이 더 있다. 중요한 것은 버퍼 수와 재전송 수가 같다는 것.
- "유언은 정상 종료 때도 발행되나?" — 아니다. 정상 종료(`stop`)는 장치가 직접 offline 을 발행하고 끊는다. 유언은 비정상 종료 전용. 둘 다 결과는 status offline.
- "텔레메트리를 QoS 1 로 보내면 버퍼가 필요 없나?" — 끊긴 동안은 publish 자체가 안 되므로 버퍼는 여전히 필요하다. QoS 는 붙어 있을 때의 보장이다.
- 함정(E09): 브로커가 종료되며 유언 50개를 한꺼번에 발행하다 소켓을 닫아 20개만 수집기에 닿았다 — 유언은 브로커가 살아 있을 때만 믿을 수 있다.

## 7. 면접 한 문장
"장치 에이전트는 끊기면 메모리에 모았다가 붙으면 QoS 1 로 전부 재전송하고 그 수를 텔레메트리에 실어 보내서, 브로커를 10초 죽였을 때 '버퍼 654 = 재전송 654' 로 끊긴 구간 유실 0 을 장치 스스로 증명하게 했고, 갑자기 죽는 경우는 브로커에 맡긴 유언이 offline 을 남깁니다."
