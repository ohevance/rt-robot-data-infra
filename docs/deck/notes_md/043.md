# 장표 043 — 단계 6 — 모델과 관절의 연결 — robots/so101.yaml 한 파일로 로봇을 바꾼다
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ② 설정 — 로봇 프로필 YAML*

## 1. 이 장표가 왜 있나
단계 6 의 앞 장표들(039~042)에서 백엔드 인터페이스(세 함수)와 두 구현(SimLag · MuJoCo), 그리고 MuJoCo 백엔드가 물리 걸음을 제어 주기에 맞추는 법까지 봤다. 그러면 마지막 질문이 남는다 — "MuJoCo 백엔드는 우리 관절 이름(shoulder_pan …)과 모델 파일 안의 관절 이름(Rotation …)이 다른데, 둘을 어떻게 잇나? 그리고 노드는 '어느 백엔드로, 몇 Hz 로, 어떤 안전값으로' 돌지 어디서 읽나?" 이 장표가 그 답이다. 설정 파일 하나(`robots/so101.yaml`)가 로봇의 관절 수·이름·주기·백엔드·모델 경로·안전값을 전부 들고 있고, 변환 스크립트가 그것을 ROS 2 노드의 파라미터 파일로 바꾼다. 그래서 로봇을 바꾸는 일이 "설정 파일 하나 바꾸기"가 된다. 이 장표가 끝나면 단계 6(백엔드)이 끝나고, 다음 ▶ 다리가 말하듯 "목표가 MuJoCo 액추에이터에 들어갔으니 물리는 목표를 따라갔나?"(단계 7)로 넘어간다.

## 2. 장표를 하나씩 읽기
왼쪽 칸 "로봇 프로필 (robots/so101.yaml)" — 파일의 내용을 위에서부터 요약한 것이다.

- "dof: 6 · joints: [shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper] (우리 쪽 이름)" — dof(degrees of freedom, 자유도) = 관절 수 6. `joints` 는 ROS 토픽(`/joint_command`, `/joint_states`)에 실리는 관절 이름이다. 이 이름은 로봇 모델과 무관하게 우리가 정한다. 노드는 이 수(6)만큼 버퍼를 시작할 때 한 번 고정 크기로 잡는다(루프 안에서 동적 할당 금지 — 파일 머리말 주석).
- "loop_hz: sim 1000 / real 200 (Feetech 서보 시리얼 1 Mbps 한계)" — 제어 루프 주기. 시뮬레이션(MuJoCo)은 1 kHz(1 ms 마다), 실물은 200 Hz(5 ms 마다). 실물이 느린 이유: Feetech STS3215 서보 6개와 시리얼 1 Mbps(초당 100만 비트) 버스로 주고받는 데 시간이 걸려 1 kHz 는 물리적으로 안 된다. 파일 주석에 "실측 후 조정"이라고 적혀 있다 — 아직 실물 측정은 없다.
- "backend: sim mujoco / real feetech_serial" — 시뮬레이션 모드의 기본 백엔드는 MuJoCo, 실물 모드는 Feetech 시리얼(아직 자리만, 단계 6 그림 장표의 구현 C). MuJoCo 가 없는 환경이면 변환 스크립트에 `--backend sim_lag` 를 줘서 1차 지연 모델로 바꿀 수 있다.
- "mujoco.model: third_party/mujoco_menagerie/trs_so_arm100/scene.xml" — 물리 모델 파일 경로. MuJoCo Menagerie(Google DeepMind 가 검증해 둔 로봇 모델 모음)의 SO-ARM100 모델. `scripts/get_mujoco.sh` 가 `third_party/` 에 받아 둔다. SO-ARM100 과 SO-101 은 같은 5축 + 그리퍼 구성이라 이 모델을 쓴다(파일 주석).
- "mujoco.joints: [Rotation, Pitch, Elbow, Wrist_Pitch, Wrist_Roll, Jaw] (모델 안 이름, 같은 순서)" — 위 `joints` 와 **같은 순서로** 적은 "모델 파일 안의" 관절 이름. 즉 shoulder_pan ↔ Rotation, shoulder_lift ↔ Pitch, elbow_flex ↔ Elbow, wrist_flex ↔ Wrist_Pitch, wrist_roll ↔ Wrist_Roll, gripper ↔ Jaw. 이 두 줄이 "이름표 번역표"다. 비워 두면([]) 모델의 1축 관절을 앞에서부터 6개 쓴다(파일 주석, 코드 `map_joints_in_order`).
- "safety: watchdog_ms 50, max_step_rad 0.05" — 안전값 둘. 명령이 50 ms 동안 끊기면 멈춤(단계 5 ② 워치독), 한 주기에 목표가 0.05 rad(= 2.9°) 넘게 뛰지 못하게(단계 5 ③ 변화량 제한). 제어 코드의 기본값과 같은 숫자지만, 로봇마다 바꿀 수 있게 여기 둔다.

오른쪽 칸 "노드로 가는 길" — 이 YAML 이 실제로 노드까지 어떻게 전달되나.

- "scripts/profile_to_params.py --backend mujoco → rt_control/ros2_adapter/config/so101_mujoco.params.yaml (손으로 두 번 쓰지 않기)" — ROS 2 노드는 자기 형식의 파라미터 파일을 읽는다. 같은 내용을 사람이 두 번 쓰면 둘이 어긋나기 마련이라, 스크립트가 프로필을 읽어 파라미터 파일을 만든다. 만들어진 파일 머리에 "자동 생성 … 손으로 고치지 말 것"이 적혀 있다. 내용은 `joint_names` 6개, `loop_hz: 1000`, `prio: 80`, `cpu: -1`, `watchdog_ms: 50`, `max_step_rad: 0.05`, `publish_hz: 100`, `backend: mujoco`, `sim_time_constant_s: 0.05`, `mujoco_model`, `mujoco_joints` 6개다.
- "노드는 파라미터로 받는다: backend, mujoco_model(RT_REPO_ROOT 기준 경로), mujoco_joints" — `rt_control_node.cpp` 69~79줄이 `declare_parameter` 로 이 값들을 읽는다. `mujoco_model` 은 저장소 기준 상대 경로라서, 노드를 저장소 뿌리에서 실행하지 않으면 못 찾는다 → 환경 변수 `RT_REPO_ROOT` 아래에서 다시 찾고, 그래도 없으면 "mujoco_model 파일을 찾을 수 없음 … (저장소 루트에서 실행하거나 RT_REPO_ROOT 설정)" 하고 치명 오류로 멈춘다(143줄).
- "MujocoBackend::init: load_model → tune_timestep → map_joints_by_name(이름이 틀리면 모델의 관절 이름 전체를 출력) → find_actuators → mj_forward → print_mapping" — 백엔드가 시작할 때 한 번 하는 일의 순서(`mujoco_backend.cpp:60-88`). ① 모델 파일을 읽어 설계도(mjModel)와 상태(mjData)를 만들고 ② 물리 걸음을 제어 주기에 맞추고(앞 장표 042) ③ 이름으로 관절을 찾아 위치·속도 배열의 주소를 기억하고(이름이 비었으면 순서대로) ④ 관절마다 붙은 액추에이터(모터)를 찾고 ⑤ `mj_forward` 로 초기 상태를 한 번 계산해 첫 `read_state` 가 유효한 값을 주게 하고 ⑥ 매핑 결과를 출력한다. ③이나 ④가 실패하면 `print_model_names()` 가 모델 안의 이름을 전부 출력하므로, 그것을 보고 YAML 의 `mujoco.joints` 를 맞추면 된다 — "틀리면 모델의 관절 이름 전체를 출력"의 뜻.
- "함정(11/04): 빈 배열 mujoco_joints: [] 는 타입 미정으로 노드가 안 뜸 → 빈 배열이면 키를 뺀다" — ROS 2 파라미터 파일에 `mujoco_joints: []` 를 쓰면 파서가 "빈 배열의 원소 타입"을 정하지 못해 노드 시작이 실패한다. 그래서 변환 스크립트가 배열이 비어 있으면 키 자체를 쓰지 않는다(`profile_to_params.py:41-44`). 노드 쪽 기본값이 빈 벡터라 결과는 같다. (LOG 에는 11/03 샌드박스 작업 항목에 적혀 있다 — 아래 5절.)
- "두 번째 프로필 robots/allex.yaml(11/06) — 위로보틱스 공개 ALLEX 48 자유도: 관절 이름 48개 + loop_hz 500. 제어 코드·백엔드 무변경(E21, 7부 덧붙임)" — 이 장표의 주장("YAML 한 파일로 로봇을 바꾼다")을 지원 회사가 공개한 48 자유도 상체 휴머노이드로 시험한 결과다. `robots/allex.yaml` 은 `so101.yaml` 과 같은 꼴에 `dof: 48`, 관절 이름 48개(MJCF 의 액추에이터 순서 그대로; 등식 제약으로 따라 움직이는 수동 관절 12개는 뺀다), `loop_hz: sim 500`(모델 기본 걸음 2 ms — 물리 한 주기 p99 가 1 kHz 예산의 46~62% 라 낮췄다), `mujoco.model: third_party/allex_model/mjcf/scene.xml` 을 적는다. 같은 `profile_to_params.py` 가 `allex_mujoco.params.yaml` 을 만든다. 바뀐 제어 코드는 없다(장표 136).

맨 아래 각주 "관절 이름이 두 벌인 이유: ROS 토픽 쪽 이름은 로봇과 무관하게 유지하고, 모델 쪽 이름은 모델 파일이 정한다. 둘을 잇는 표가 이 YAML 이다" — 상위(계획기·기록·관제)는 shoulder_pan 같은 우리 이름만 알면 되고, 모델 파일을 다른 로봇 것으로 바꿔도 번역표 한 줄만 고치면 된다는 뜻이다.

## 3. 용어와 단위
- YAML: 사람이 읽기 쉬운 설정 파일 형식. `키: 값`, 들여쓰기로 묶음, `[a, b]` 로 목록.
- 프로필(profile): 로봇 한 종류의 설정 묶음. 여기서는 SO-101 하나.
- dof(자유도): 독립적으로 움직일 수 있는 관절 수. 6.
- Hz: 1초에 몇 번. 1000 Hz = 1 ms 마다, 200 Hz = 5 ms 마다.
- Mbps: 초당 메가비트. 1 Mbps = 초당 100만 비트 = 초당 약 125,000 바이트.
- rad(라디안): 각도 단위. 1 rad = 57.3°, 0.05 rad = 2.9°.
- ms: 밀리초 = 1,000분의 1초. 50 ms = 0.05초.
- 백엔드(backend): 제어 코드가 "로봇"이라고 부르는 상대. SimLag(1차 지연 모델) · MuJoCo(물리) · Feetech 시리얼(실물, 예정).
- MuJoCo Menagerie: Google DeepMind 가 관리하는 검증된 로봇 모델 모음. 모델 파일은 XML.
- 액추에이터(actuator): 관절을 움직이는 모터에 해당하는 모델 요소. MuJoCo 에서 목표는 액추에이터의 `ctrl` 에 쓴다.
- ROS 2 파라미터: 노드가 시작할 때 읽는 설정값. 파일(`*.params.yaml`)이나 명령줄로 준다.
- `RT_REPO_ROOT`: 저장소 뿌리 경로를 담는 환경 변수. WSL 의 `.bashrc` 가 자동으로 설정한다(5부 ① 개발 PC 장표).
- 1차 지연 모델(SimLag): 목표를 향해 매 주기 일정 비율만큼 다가가는 간단한 흉내. 시정수 0.05초 = 목표의 63% 까지 가는 시간.

## 4. 쉬운 예시
비유 — 해외 배송 송장: 보내는 쪽(우리)은 물건 이름을 한국어로 적고(shoulder_pan), 받는 나라 창고(모델 파일)는 자기 언어의 품목 코드(Rotation)로만 처리한다. 송장에 두 이름을 같은 순서로 나란히 적은 표(`joints` 와 `mujoco.joints`)가 있으면 창고 직원(MujocoBackend::init)이 품목마다 선반 주소(qpos 주소)를 미리 찾아 둔다. 품목 코드 하나가 틀리면 창고는 "그런 코드 없음"과 함께 자기 창고의 코드 목록 전체를 보내 준다(`print_model_names`). 그리고 송장 양식이 두 가지(우리 YAML, ROS 2 파라미터 YAML)라서 손으로 두 번 쓰지 않고 변환기(`profile_to_params.py`)가 하나에서 다른 하나를 만든다.

숫자 예시 — 명령 `position[1] = -0.2` 가 왔다. `joints[1]` 은 shoulder_lift, `mujoco.joints[1]` 은 Pitch. 백엔드는 시작 때 "Pitch" 관절의 qpos 주소와 그 관절에 붙은 액추에이터 번호를 기억해 뒀으므로, 매 주기 `ctrl[그 번호] = -0.2` 를 쓰고 `qpos[그 주소]` 를 읽어 `/joint_states` 의 두 번째 칸(shoulder_lift)에 넣는다. 실측(단계 7)에서 그 값이 −0.181 rad 로 읽힌 것이 중력 처짐이다.

## 6. 자주 하는 오해·함정
- "관절 이름이 두 벌이면 헷갈리지 않나, 하나로 통일하면 되지 않나?" — 모델 파일의 이름은 모델 제작자가 정한 것이라 우리가 못 바꾸고, 우리 토픽 이름은 로봇이 바뀌어도 그대로여야 상위 코드가 안 바뀐다. 두 벌 + 번역표 한 줄이 가장 싸다.
- "YAML 만 고치면 끝인가?" — 아니다. 노드는 `*.params.yaml` 을 읽으므로 `profile_to_params.py` 를 다시 돌려 생성 파일을 갱신해야 한다. 생성 파일을 손으로 고치면 다음 생성 때 덮어써진다.
- "mujoco_joints 를 비워 두면 안 되나?" — 코드상 비우면 모델의 1축 관절을 앞에서부터 6개 쓴다. 다만 ROS 2 파라미터 파일에 `[]` 를 그대로 쓰면 노드가 안 뜨므로(타입 미정) 변환 스크립트가 키를 뺀다. 어느 관절이 몇 번째인지 모델 순서에 기대는 것이라 이름을 적는 쪽이 안전하다.
- "모델 파일 경로가 상대 경로라 노드가 못 찾는다" — 저장소 뿌리에서 실행하거나 `RT_REPO_ROOT` 를 설정한다. 못 찾으면 조용히 다른 백엔드로 바꾸지 않고 치명 오류로 멈춘다(의도된 동작).
