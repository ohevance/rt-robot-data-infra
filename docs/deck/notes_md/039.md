# 장표 039 — 단계 6 — 백엔드가 로봇에 쓴다 — 로봇 쪽의 '모양'(인터페이스) 세 함수
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ② 코드 — Backend 인터페이스*

## 1. 이 장표가 왜 있나
- 들머리(장표 037)에서 "로봇이 셋인데 제어 코드는 그대로 두려면 경계가 필요하다" 고 했다. 이 장표는 그 경계의 **실제 코드** 다. `backend.hpp` 17~33줄, 함수 세 개가 전부다.
- 이 파일을 보면 "제어 단계가 로봇에 대해 아는 것이 얼마나 적은가" 가 눈에 들어온다. 제어 단계는 로봇이 시뮬레이터인지 실물인지, 모터가 몇 개인지의 세부를 모른다. 알고 있는 것은 "시작할 때 init, 매 주기 write_command 와 read_state" 뿐이다.
- 다음 장표 040~042 는 이 모양을 채운 두 구현(SimLag, MuJoCo)이다. 모양을 먼저 보고 구현을 봐야 "왜 두 구현이 서로 전혀 다른데 제어 코드는 같은가" 가 이해된다.

## 2. 장표를 하나씩 읽기
파일 머리글(장표에는 없지만 `backend.hpp` 1~13줄)에 이 파일의 역할이 그림으로 있다: `ControlStep ──write_command()──▶ Backend ──read_state()──▶ ControlStep`. 제어 단계가 쓰고, 백엔드를 거쳐, 다시 제어 단계가 읽는다.

코드를 줄 단위로.
- 18줄 `namespace rt_core {`: 이 저장소의 실시간 핵심 코드는 전부 `rt_core` 라는 이름 공간 안에 있다. ROS 2 와 무관한 순수 C++ 이라는 뜻(DECISIONS 11/03 "RT 핵심은 ROS 2 와 무관").
- 20줄 `class Backend {` / 21줄 `public:`: 바깥에서 쓸 수 있는 함수들.
- 22줄 `virtual ~Backend() {}`: 가상 소멸자. 부모 포인터로 자식(SimLagBackend 등)을 지울 때 자식의 정리 코드가 제대로 불리게 하는 C++ 관례. MuJoCo 백엔드는 소멸자에서 모델·데이터 메모리를 반납한다.
- 24~25줄 `init(dof, period_ns)`: "시작할 때 한 번. 관절 수와 주기를 알려준다. 여기서는 할당해도 된다 (RT 스레드 밖)". `dof` 는 관절 수(SO-101 은 6), `period_ns` 는 제어 주기를 나노초로(1 kHz 면 1,000,000 ns). 반환값 `bool` 은 성공 여부 — 모델 파일이 없거나 관절 이름이 틀리면 false 를 돌려주고 노드는 시작을 멈춘다. 이 함수만 **RT 스레드 밖**에서 불리므로 여기서는 메모리 할당(모델 로드 등)이 허용된다.
- 27~28줄 `write_command(target_position, dof)`: "이번 주기의 목표 위치를 로봇에 보낸다 (RT 스레드, 매 주기)". 배열 포인터와 길이를 받는다. 제어 단계가 매 주기 `applied_` 를 넘긴다.
- 30~31줄 `read_state(position, velocity, dof)`: "로봇의 현재 위치·속도를 읽는다 (RT 스레드, 매 주기)". 제어 단계가 넘긴 배열에 값을 채워 넣는다. 위치는 rad, 속도는 rad/s.
- 32줄 `};`: 끝. 데이터 멤버가 하나도 없다 — 순수한 "약속" 만 있는 클래스다.
- `= 0` 표시: 순수 가상 함수. "이 클래스는 모양만 정하고, 실제 내용은 자식이 반드시 채운다" 는 뜻. 채우지 않은 자식은 컴파일이 안 된다.

읽는 포인트:
- "ControlStep 은 이 세 함수만 안다. 구현체를 바꾸면 로봇이 바뀌고 제어 코드는 한 줄도 안 바뀐다(11/04 SimLag → MuJoCo 교체로 확인)": 장표 029 의 `step()` 안에서 `backend_.write_command(...)` 와 `backend_.read_state(...)` 를 부르는 두 줄이 제어 단계가 로봇을 만지는 전부다.
- "init: 시작 때 한 번, 할당 허용(RT 밖)": 왜 구분하나 — RT 스레드 안에서는 시간이 얼마나 걸릴지 모르는 일을 하면 안 되는데, 모델 파일을 읽는 일은 수십 ms 가 걸린다. 그래서 그런 일은 전부 init 으로 몰아 둔다.
- "write_command / read_state: RT 스레드에서 매 주기 → 기다리는 일 금지": 파일 머리글의 규칙 그대로. 락·파일·할당 금지.
- "구현체: SimLagBackend(1차 지연) · MujocoBackend(물리) · FeetechSerialBackend(실물 서보, 자리)": 앞의 둘은 코드가 있고, 셋째는 머리글 주석에 이름만 있다(2주 계획 밖).
- "결정: DECISIONS 11/03 'RT 핵심은 ROS 2 와 무관', 11/03 (D5) 'MuJoCo 는 Backend 의 한 구현'": 이 모양이 우연이 아니라 기록된 결정이라는 것.

## 3. 용어와 단위
- **인터페이스 / 순수 가상 클래스**: 함수의 이름과 인자만 정하고 내용은 비워 둔 클래스. 자식 클래스가 내용을 채운다. "플러그 규격".
- **virtual / override**: 부모 포인터로 불러도 자식의 함수가 실행되게 하는 C++ 장치. 제어 단계는 `Backend&` 만 들고 있어도 실제로는 MuJoCo 코드가 돈다.
- **dof(degrees of freedom, 자유도)**: 독립적으로 움직일 수 있는 관절 수. SO-101 은 6(5축 + 그리퍼).
- **period_ns**: 제어 주기(나노초). 1 ms = 1,000,000 ns. 나노초 정수로 두는 이유는 실수 오차 없이 시각을 더하기 위해서(장표 026 의 절대 시각 타이머와 같은 이유).
- **rad / rad/s**: 각도와 각속도의 SI 단위. 1 rad ≈ 57.3°.
- **RT 스레드 밖 / 안**: 밖 = 노드 시작 때(시간 제한 없음), 안 = 1 ms 마다 반복되는 루프(시간 제한 엄격).

## 4. 쉬운 예시
- 비유: **택배 접수 창구**. 창구 직원(제어 단계)은 소포를 "접수(write_command)" 하고 "조회(read_state)" 할 줄만 알면 된다. 뒤에서 그 소포를 트럭이 나르든 드론이 나르든(SimLag/MuJoCo/실물) 창구 절차는 똑같다. 창구를 처음 여는 날 서류를 준비하는 일(init)은 손님이 없을 때 해 둔다.
- 숫자 예시: `init(6, 1000000)` — 관절 6개, 주기 1,000,000 ns(= 1 ms). 그 뒤 1초에 1,000번씩 `write_command(applied_, 6)` → `read_state(position_, velocity_, 6)` 가 반복된다. 30초를 돌리면 각각 30,000번. MuJoCo 백엔드에서 이 한 쌍의 비용이 p99 8.5 us 다(장표 037).

## 6. 자주 하는 오해·함정
- "함수가 셋뿐이면 토크 제어나 안전 정지는 어떻게 하나?" — 지금 모양은 위치 명령만 다룬다. 실물에서 토크 오프가 필요하면 `safe_stop()` 같은 함수를 **추가**한다(장표 031·058 에 '자리' 로 적혀 있다). 모양을 늘리는 것은 쉽고, 지금 범위(2주)에서는 셋으로 충분했다.
- "init 이 false 를 돌려주면 어떻게 되나?" — 노드가 예외를 던지고 시작하지 않는다(`rt_control_node.cpp` "backend init failed"). 조용히 반쯤 동작하는 것보다 낫다.
- "MuJoCo 를 쓰려면 항상 링크해야 하나?" — 아니다. 빌드 옵션 `RT_CORE_WITH_MUJOCO`(기본 OFF)가 꺼져 있으면 MuJoCo 코드는 컴파일에 들어가지 않고 SimLag 만 있다. 그래서 MuJoCo 가 없는 CI 1단계와 Pi 에서도 빌드된다.

## 7. 면접 한 문장
- "제어 단계가 로봇에 대해 아는 건 세 함수뿐입니다 — init 은 시작 때 한 번이라 할당을 허용하고, write_command 와 read_state 는 RT 스레드에서 매 주기라 기다리는 일을 금지했습니다. 그 경계 덕에 로봇을 물리 엔진으로 바꿔도 제어 코드는 그대로였습니다."
