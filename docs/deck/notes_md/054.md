# 장표 054 — 단계 10 들머리 — 관제로 올린다: 로봇이 51번째 장치가 되어 서버로
*위치: 1부 로봇을 움직이는 길 · 단계 10/10 관제로 · ① 들머리*

## 1. 이 장표가 왜 있나
단계 9(장표 051~053)에서 "원본은 로봇 안에 남기고, 서버로는 요약만"이라는 판단이 섰다. 그러면 마지막 질문이 남는다. "그 요약은 **어떤 길로** 서버까지 가나? 그리고 로봇 한 대의 숫자가 수십 대의 가상 장치와 나란히 한 화면에 보이려면 무엇이 필요한가?" 단계 10 은 본편 10단계의 마지막이고, 이 장표는 그 단계의 **들머리**다. 들머리는 모든 단계가 같은 꼴로 시작하는 장표로, 여섯 상자(들어온 것 → 문제 → 기준 → 확인 방법 → 결과 → 판단)로 "왜 이 단계가 필요하고, 무엇을 넘어야 다음으로 가나"를 한눈에 보여 준다. 이 단계를 넘으면 로봇 안의 길(1부)은 끝나고 서버 쪽 길(2부, 데이터의 길)이 시작된다.

## 2. 장표를 하나씩 읽기
여섯 상자를 순서대로 읽는다. 위 줄은 왼쪽에서 오른쪽으로(들어온 것 → 문제 → 기준), 아래 줄은 오른쪽에서 왼쪽으로(확인 방법 → 결과 → 판단) 뱀처럼 이어진다.

- **들어온 것(회색 상자)**: "로봇 안의 1 Hz 요약 rt_status (단계 8·9)". 단계 8 에서 노드가 1초마다 자기 상태를 JSON 한 줄(`/rt_status`)로 발행한다는 것을, 단계 9 에서 그 요약만 서버로 보내기로 했다는 것을 보았다. 이 토픽이 이 단계의 입력이다.
- **문제(민트 상자)**: "수십 대를 한 화면에서 보려면 로봇 밖(서버)으로 보내야 한다. 그런데 서버는 로봇이 가상인지 실물인지, ROS 2 인지 몰라야 한다". 두 가지 요구가 섞여 있다. 하나는 '밖으로 보내기', 다른 하나는 '서버가 로봇의 속사정을 몰라도 되게 하기'. 두 번째가 중요한 설계 원칙이다 — 서버가 "이 장치는 ROS 2 노드니까 특별 취급"을 시작하면 장치 종류마다 서버 코드가 늘어난다.
- **기준(마름모)**: "로봇의 숫자가 서버 DB·Grafana 에 유실 없이 도착하고, 가상 장치 50대와 같은 길·같은 코드로 가나?" 통과 조건이 둘이다. (1) 도착한다, 잃지 않는다. (2) 가상 장치와 **같은 길(MQTT 토픽 구조)·같은 코드(DeviceAgent 클래스)** 를 쓴다. (2)가 충족되면 서버는 로봇을 '장치 한 대'로만 본다.
- **확인 방법(파란 상자)**: "ros_status_bridge.py — /rt_status 구독 → 같은 DeviceAgent 로 fleet/rt-node-1/telemetry 발행 → 수집기 → DB → Grafana 'RT 노드 깨어남 지연 p99' 패널". 다리 프로그램이 ROS 2 토픽을 구독해서, 가상 장치가 쓰는 것과 똑같은 `DeviceAgent` 클래스로 MQTT 토픽 `fleet/rt-node-1/telemetry` 에 발행한다. 그 뒤는 2부의 길 그대로(수집기 → TimescaleDB → Grafana). 확인은 Grafana 의 "RT 노드: 깨어남 지연 p99 (us)" 패널(대시보드 10번 패널)에 선이 그려지는지로 한다.
- **결과(보라 테두리 상자)**: "51번째 장치로 보인다. watchdog tripped 면 state 도 tripped 로 올라가 '멈춤·고장 장치' 패널에 잡힌다. 가상 장치와 다른 것은 metrics_source 뿐". 가상 장치 50대 옆에 `rt-node-1` 이 한 대 더 붙어 51대가 된다. 워치독이 걸리면(명령 50 ms 끊김) 장치 상태(state)도 `tripped` 로 올라가서 "멈춤·고장 장치 (tripped/fault/updating)" 패널(6번)에 숫자가 1 올라간다. 코드 차이는 `metrics_source`(숫자를 어디서 가져오나: 난수 vs rt_status) 하나다.
- **판단 → 다음(진한 녹색 상자)**: "본편 끝 → 2부: 서버 쪽은 이 숫자를 잃지 않나, 장애와 업데이트를 견디나?" 기준 두 가지가 충족됐으므로 통과. 그리고 이 판단이 곧 2부의 질문이 된다 — 로봇은 숫자를 밖으로 냈는데, 서버 쪽은 그것을 잃지 않고 저장·표시하나, 브로커나 DB 가 죽으면 어떻게 되나, 펌웨어 업데이트는 안전한가.

- **아래 상자(이 단계의 장표)**: "② 다리 설명(1장). 그 뒤 가로지르기 2장: 명령이 끊기면(안전 경로) · 실물로 가면." 이 단계의 본문 장표는 다리 한 장(056)뿐이고, 그 다음 두 장(057, 058)은 특정 단계에 속하지 않고 10단계 전체를 가로지르는 주제다. "넘어가는 조건: 로봇의 숫자가 관제 화면에 보인다 — 여기서부터는 '데이터의 길'(2부)".

## 3. 용어와 단위
- **관제(fleet)**: 여러 대의 로봇·장치를 서버에서 한꺼번에 지켜보고(모니터링) 명령·업데이트를 내리는 일. 이 저장소에서는 `fleet/` 디렉터리.
- **rt_status**: 노드가 1 Hz 로 발행하는 JSON 문자열 토픽. 지난 1초의 깨어남 지연·작업 시간 통계, 드롭 수, 상태 머신 상태, 실행 환경(RT 커널인지 등)이 들어 있다.
- **DeviceAgent**: `fleet/agent/device_agent.py` 의 클래스. 장치 한 대가 서버에 자기 상태를 보고하는 프로그램. 가상 장치 50대도, 이 다리도 이 클래스를 쓴다.
- **metrics_source**: DeviceAgent 를 만들 때 넘기는 "호출하면 숫자 dict 를 돌려주는 함수". 가상 장치는 난수 걸음 함수, 다리는 마지막 `rt_status` 를 변환하는 함수(`StatusBridge.metrics`).
- **MQTT 토픽 `fleet/<id>/telemetry`**: 장치 `<id>` 의 측정값이 흐르는 이름. `rt-node-1` 이 이 다리의 장치 이름(기본값, `--device-id` 로 바꿀 수 있다).
- **수집기(collector)**: MQTT 로 오는 메시지를 받아 1초마다 묶어 DB 에 넣는 서버 프로그램(2부 ③).
- **TimescaleDB / Grafana**: 시간 데이터용 DB / 화면. Grafana 패널 = 대시보드의 그래프·숫자 칸 하나.
- **watchdog tripped**: 50 ms 동안 명령이 없어 로봇이 '지금 자리 유지' 상태로 들어갔다는 뜻(단계 5). 장치 상태로는 문자열 `tripped`.
- **p99, us**: 100번 중 99번째로 나쁜 값, 마이크로초(100만분의 1초). 1 ms = 1,000 us.

## 4. 쉬운 예시
- 비유: 택배 회사의 관제 화면에 배송 트럭 50대가 점으로 떠 있다. 새로 들어온 전기 트럭(로봇)은 내부가 완전히 다르지만, 관제 화면에 올라오려면 다른 트럭과 **같은 단말기 규격**(같은 앱, 같은 서버 주소, 같은 1분 보고)으로 위치를 보내면 된다. 관제실은 그 트럭이 전기인지 디젤인지 모른다. 다리(ros_status_bridge)는 전기 트럭의 계기판(ROS 2 토픽)을 읽어 표준 단말기(DeviceAgent)에 넣어 주는 어댑터다.
- 숫자 예시: 노드가 1초마다 `{"wake_us": {"p99": 350, "max": 900}, "loop_hz": 1000, "timing_drops": 0, "state": "RUNNING", ...}` 을 낸다고 하자. 다리는 여기서 `wake_p99_us = 350`, `wake_max_us = 900`, `loop_hz = 1000`, `timing_drops = 0` 을 꺼내 `fleet/rt-node-1/telemetry` 에 seq 를 붙여 보낸다. 수집기는 이것을 가상 장치 50대의 메시지와 똑같이 `telemetry` 표에 넣고, Grafana 10번 패널은 `wake_p99_us` 열을 선으로 그린다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 다리의 구조(구독 → DeviceAgent → 토픽 이름 `fleet/rt-node-1/telemetry`, 기본 1 Hz) — `fleet/agent/ros_status_bridge.py` 2~10줄(머리 주석), 71~83줄(`main`).
- 확인: "가상 장치와 다른 것은 metrics_source 뿐" — `fleet/agent/device_agent.py` 머리 주석 마지막 줄, `__init__` 의 `metrics_source` 인자.
- 확인: 패널 이름 "RT 노드: 깨어남 지연 p99 (us)"(10번), "멈춤·고장 장치 (tripped/fault/updating)"(6번) — `fleet/grafana/make_dashboard.py` 69줄, 83줄.
- 확인: "51번째 장치" — 가상 장치 50대(`virtual_fleet.py --count 50`) + 다리 1대. `ros_status_bridge.py` 6줄 주석.
- 확인: 상태가 `tripped` 로 올라가는 경로 — `ros_status_bridge.py` 62~68줄(`state()`: 상태 머신 이름이 없으면 watchdog 값), 87줄(`agent.state = bridge.state()`).
- 다시 보려면 [WSL]: 관제 컨테이너·수집기·가상 장치를 띄운 뒤 `python3 fleet/agent/ros_status_bridge.py --device-id rt-node-1`, 그리고 `localhost:3000` 의 Fleet Overview 에서 10번 패널.
- 추정: "유실 없이 도착"은 가상 장치 50대로 잰 표③의 결과(브로커 장애 유실 0 / 1400 등)를 같은 길을 쓰는 다리에도 적용한 것이다. 다리 한 대만 따로 장애 주입을 해서 세지는 않았다.

## 6. 자주 하는 오해·함정
- "서버가 ROS 2 를 알아야 하지 않나?" — 아니다. ROS 2 를 아는 것은 로봇 안의 다리뿐이다. 서버(수집기·DB·Grafana)는 MQTT 와 JSON 만 안다. 그래서 실물 로봇으로 바꿔도 서버는 바뀌지 않는다.
- "rt_status 전체를 서버로 보내나?" — 아니다. `metrics()` 가 고른 열 몇 개(loop_hz, wake_p99_us, wake_max_us, work_p99_us, timing_drops, watchdog_trips, rmw, backend, sched_fifo)만 간다. 온도·CPU 같은 가상 장치 필드는 `None` 으로 채운다(45~60줄).
- 다리는 ROS 2 환경에서만 돈다(`rclpy` 를 import 한다). 관제 컨테이너만 있는 PC 에서 띄우면 import 에러가 난다 — 이는 버그가 아니라 다리가 '로봇 안 프로그램'이기 때문이다.
- 상태 문자열은 소문자로 바꿔 올린다(`str(name).lower()`, 68줄). 상태 머신이 `RUNNING` 이면 장치 상태는 `running`. Grafana 의 '멈춤·고장' 패널은 `tripped/fault/updating` 을 센다.

## 7. 면접 한 문장
"RT 노드를 관제의 51번째 장치로 올렸다 — 서버는 그 장치가 ROS 2 인지 가상인지 모르고, 다른 것은 숫자를 어디서 가져오느냐(metrics_source) 하나뿐이라 실물 로봇으로 가도 서버 코드는 그대로다."
