# 장표 073 — ③ 수집기 — 1초마다 (2/2): backlog 를 오래된 것부터 DB 에, 하나라도 실패하면 거기서 멈추고 다음 초에 (drain_backlog)
*위치: 2부 데이터의 길 · ③ 수집기 · ② 코드 — drain_backlog*

## 1. 이 장표가 왜 있나

앞 장표(072)에서 1초 묶음을 backlog 끝에 붙였다. 이제 그 backlog 를 **실제로 DB 에 넣는 함수** `drain_backlog` 차례다. 질문은 두 가지다. (1) DB 가 죽어 있을 때 어떻게 해야 데이터를 잃지 않나? (2) DB 가 돌아오면 어떤 순서로 넣나? 답은 "맨 앞(가장 오래된 것)부터 하나씩 넣고, 하나라도 실패하면 **거기서 멈추고** 다음 초에 같은 자리부터 다시"다. 이 단순한 규칙 하나로 순서 보존과 재시도가 동시에 해결된다. 11/04 DB 장애 실험에서 "유실 0 / 1341, 뒤늦게 570행 적재"가 나온 것이 바로 이 함수의 동작이다.

## 2. 장표를 하나씩 읽기

파일 `fleet/collector/collector.py` 241~255줄.

- 241줄 `def drain_backlog(self):` — "backlog 비우기".
- 242줄 설명 문자열: "backlog 를 오래된 것부터 DB 에 넣는다. 하나라도 실패하면 거기서 멈추고 다음 초에 다시 시도."
- 243줄 `while len(self.backlog) > 0:` — backlog 가 빌 때까지 반복.
- 244줄 `batch = self.backlog[0]` — **맨 앞 묶음**(가장 오래된 것)을 집는다. 아직 목록에서 빼지 않는다 — 성공해야 뺀다.
- 245~246줄 `try: self.write_db(batch)` — 284줄의 write_db 를 부른다. write_db 는 세 가지를 한 트랜잭션으로 한다: ① telemetry 행들을 COPY 로 한 번에, ② devices 표의 장치별 마지막 시각·펌웨어·상태 갱신, ③ events 표에 online/offline 상태 줄. 끝에 commit.
- 247줄 `except Exception as e:` — DB 가 죽었거나 연결이 끊겼거나 어떤 이유로든 실패하면 여기로.
- 248줄 `self.db_errors += 1` — 실패 횟수를 누적한다(통계와 Grafana 패널에 보인다).
- 249줄 `self.drop_db_connection()` — 망가진 연결을 닫고 None 으로 둔다. 다음에 write_db 가 불리면 connect_db 로 새로 붙는다(284~286줄 `if self.conn is None: self.connect_db()`).
- 250~251줄 `if self.db_errors == 1 or self.db_errors % 10 == 0: print(...)` — 첫 번째 실패와 10번째마다만 로그를 찍는다. DB 가 10분 죽어 있으면 600번 실패하는데 그때마다 찍으면 로그가 넘친다. 메시지에는 예외 종류 이름과 지금 backlog 행 수, "retry next second" 가 들어간다(장표에서는 긴 줄이라 끝이 … 로 잘려 있다).
- 252줄 `return` — **여기서 멈춘다**. 뒤의 묶음은 시도조차 하지 않는다. 그래야 순서가 뒤바뀌지 않고, 죽은 DB 에 헛수고를 반복하지 않는다. 1초 뒤 flush_once 가 다시 부르면 같은 맨 앞 묶음부터 재시도.
- 253~254줄 `self.backlog.pop(0)`, `self.backlog_rows -= len(batch.rows)` — 성공했을 때만 맨 앞을 떼어 내고 행 수를 줄인다. 그다음 while 로 돌아가 다음 묶음.

읽는 포인트 네 줄:
- "backlog 의 맨 앞(가장 오래된 묶음)부터 write_db(COPY). 성공하면 pop, 실패하면 db_errors +1 하고 return — 다음 초에 같은 묶음부터 다시" — 위 244~254줄 그대로.
- "그래서 순서가 지켜지고(오래된 것 먼저), DB 가 죽은 동안의 묶음은 메모리에 남는다(11/04 db 장애: 10초 뒤 570행이 뒤늦게 적재, 유실 0 / 1341)" — 실패 시 pop 을 하지 않으므로 묶음이 그대로 남는다. 570 = 죽어 있던 약 11초 × 50대.
- "예외를 잡으면 db_errors +1, DB 연결을 끊어 두고(drop_db_connection → 다음 초에 다시 붙는다), 첫 번째와 10번째마다만 로그 — 로그 폭주 방지" — 248~251줄.
- "통계 한 줄(write_stats): msgs/s · insert_ms · 전달 지연 p50/p95/max · online · backlog_rows · db_errors → collector_stats 표 + Grafana 'backlog/DB 오류' 패널" — flush_once 의 뒷부분(218~232줄)이 매초 통계를 만들어 308줄 write_stats 로 collector_stats 표에 넣고 화면에도 찍는다. 장애 주입 도구는 이 표의 `backlog_rows = 0` 이 다시 찍히는 시각으로 "복구 완료"를 판정한다.

## 3. 용어와 단위

- **drain**: (물을) 빼내다. 쌓인 backlog 를 DB 로 흘려보내 비운다는 뜻.
- **트랜잭션 / commit**: DB 에 여러 변경을 한 묶음으로 넣고 마지막에 commit 으로 확정하는 것. 중간에 실패하면 전부 없던 일이 된다(rollback). 그래서 "묶음이 반만 들어가는" 일이 없다.
- **COPY**: PostgreSQL 의 대량 적재. `COPY telemetry (...) FROM STDIN` 으로 행들을 한 번에 흘려 넣는다.
- **예외(Exception)**: 프로그램이 "이건 못 하겠다"고 던지는 오류 신호. try/except 로 잡아 처리한다.
- **db_errors**: DB 쓰기 실패 누적 횟수. 11/04 db 장애 실험에서 11 까지 누적(E06).
- **collector_stats**: 수집기가 매초 자기 상태를 남기는 DB 표(초당 메시지, 적재 ms, 지연 p50/p95/max, 온라인, backlog_rows, db_errors).
- **% 10 == 0**: 10 으로 나눈 나머지가 0, 즉 10·20·30… 번째.

## 4. 쉬운 예시

- 비유: 은행 창구에 전표(묶음)가 줄 서 있다. 창구(DB)가 닫혀 있으면 맨 앞 전표를 들고 1초마다 "열렸나?" 두드려 본다. 뒤 전표를 먼저 처리하지 않는다(순서). 열리면 맨 앞부터 차례로 처리한다. "닫혔다"는 안내는 처음 한 번과 열 번째마다만 외친다.
- 숫자 예시: DB 를 10초 멈추면 매초 write_db 가 실패해 db_errors 가 1씩 늘고(약 10~11), backlog 에 10~11묶음(약 500~570행)이 쌓인다. DB 가 돌아온 다음 초의 flush_once 에서 while 이 11번 돌며 전부 들어간다 — 그래서 복구 뒤 insert_ms 가 그 1초만 크게 나온다. 실측: backlog 0 복귀 1.4초, 뒤늦게 570행, 유실 0 / 1341.

## 6. 자주 하는 오해·함정

- "실패하면 그 묶음을 버리고 다음으로 넘어가지 않나?" — 아니다. return 으로 멈추고 **같은 묶음**을 다음 초에 다시 시도한다. 버리는 것은 상한(enforce_backlog_limit)에서만, 그것도 세면서.
- DB 가 돌아온 직후의 insert_ms 가 평소(약 31 ms)보다 크게 튀는 것은 밀린 묶음을 한 번에 넣기 때문이지 이상이 아니다.
- 복구 직후 전달 지연(p95·max)이 크게 보이는 것도 "원래 측정 시각" 기준이라 그렇다 — 진단 도구(diag.py B절)는 이런 '홍수' 초를 튐 판정에서 제외한다.
- 연결을 끊어 두지 않고 재사용하면 깨진 연결로 계속 실패할 수 있다 — 그래서 실패마다 drop_db_connection 을 부른다.

## 7. 면접 한 문장

"backlog 는 맨 앞부터 넣고 실패하면 거기서 멈춘다 — 규칙 하나로 순서와 재시도가 해결되고, DB 를 10초 죽여도 570행이 뒤늦게 전부 들어가 유실 0 이었다."
