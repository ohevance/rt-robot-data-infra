# 장표 089 — 단계 4 검증 — 측정기 jitter_bench — RT 스레드는 파일을 만지지 않는다 (스레드 2개)
*위치: 3부 검증 · 단계 4 RT 1 ms 루프 · 측정기 jitter_bench*

## 1. 이 장표가 왜 있나
앞의 두 장표(025·026)에서 RT 루프 본체가 매 주기 "얼마나 늦게 깼나(wake_lat)"와 "일하는 데 얼마나 걸렸나(work)"를 재서 링 버퍼에 올리는 것까지 보았다. 그러면 자연스럽게 질문이 생긴다. "그 숫자를 누가 꺼내서 표로 만드나? 그리고 재는 행위 자체가 측정을 망치지는 않나?" 이 장표는 그 답이다. `jitter_bench` 라는 실행 파일이 RT 루프를 돌리면서 결과를 모으는데, 핵심 원칙은 **RT 스레드는 파일을 전혀 만지지 않는다**는 것이다. 파일을 쓰거나 화면에 출력하는 일은 느리고 언제 끝날지 모르는 일이라, RT 스레드가 그것을 하면 재고 있는 지연 자체가 커져 버린다. 그래서 스레드를 둘로 나눴다. 표①의 jitter_bench 줄 전부가 이 프로그램에서 나왔으므로, 이 그림을 이해해야 표①의 숫자를 믿을 수 있다.

## 2. 장표를 하나씩 읽기
그림(`diagrams/jitter_bench_td.mmd`)은 위에서 아래로 흐른다.

- **맨 위 상자 묶음 "main 스레드 = RT 스레드 (SCHED_FIFO, mlockall, 고정 CPU 선택)"**: 프로그램을 시작한 main 스레드가 그대로 RT 스레드가 된다. 별도의 스레드를 만들지 않고 main 이 `RtLoop::run` 을 부르면, 장표 024 의 준비 5단계(메모리 고정 mlockall, 우선순위 SCHED_FIFO, 필요하면 CPU 고정)를 거친 뒤 for 루프로 들어간다.
  - `RtLoop::run → 준비 5단계 → for 루프`: 장표 024·025·026 에서 본 그 루프다.
  - `BusyWorkStep::step — work_us 동안 바쁘게 돌기`: 측정기에서 "매 주기 할 일"은 제어가 아니라 **일부러 CPU 를 쓰는 흉내**다. 기본 50 us 동안 바쁘게 돈다. 왜냐하면 진짜 제어 노드도 매 주기 수십 us 의 일을 하므로, 일하는 도중에 밀리는지까지 보려면 일을 시켜 봐야 한다.
  - `Sample {iter, wake_lat_ns, period_err_ns, work_ns}`: 한 주기마다 만들어지는 기록 한 줄. 몇 번째 주기인가(iter), 깨어남 지연(wake_lat_ns), 주기 오차(period_err_ns), 일한 시간(work_ns). 단위는 전부 ns(나노초).
- **화살표 "g_ring.push (꽉 차면 drops++)" → "SpscRing 65,536칸 (2 MB)"**: 기록 한 줄을 링 버퍼에 넣는다. 링은 65,536칸이고(코드의 `kRingSize = 65536`, `rt_loop.hpp` 63줄) 한 칸이 Sample 32바이트이므로 약 2 MB 다. 꽉 차 있으면 기다리지 않고 버리며 `drops` 를 하나 올린다. 1 kHz 면 초당 1,000칸이 차므로 65초 분량의 여유가 있다. 로깅 스레드가 1 ms 마다 비워 주는 한 꽉 찰 일이 없다.
- **"pop" → "로깅 스레드 (일반 우선순위) 벡터에 모음, 비면 1 ms 쉼"**: 두 번째 스레드. 우선순위를 올리지 않은 보통 스레드다. 링에서 꺼내 메모리의 벡터에 쌓기만 한다. 링이 비어 있으면 1 ms 잔다(`std::this_thread::sleep_for(1 ms)`, jitter_bench.cpp 261줄). 측정이 끝났다는 신호(`running = false`)가 오면 남은 것을 전부 꺼내고 끝난다.
- **"끝난 뒤: compute_stats — min · avg · p50 · p99 · p99.9 · max"**: 측정이 다 끝난 뒤에야 통계를 낸다. 측정 중에는 계산도 하지 않는다. 계산 방법은 다음 장표(090).
- **"print_report / write_json / write_csv — 종료 코드: drops > 0 이면 1"**: 화면 표, JSON 파일, 필요하면 CSV 로 저장한다. 그리고 드롭이 하나라도 있었으면 프로그램 종료 코드를 1(실패)로 낸다.

오른쪽 글머리표:
- "main 스레드가 RT 스레드가 되어 RtLoop::run 을 돈다": 위에서 설명한 구조. 코드로는 main() 의 `loop.run(busy, g_ring, drops)` 한 줄(282줄).
- "로깅 스레드(일반 우선순위)가 링에서 꺼내 모은다 — 비면 1 ms 쉼": 소비자 쪽. 일반 우선순위라서 RT 스레드를 절대 방해하지 못한다(급한 스레드가 깨면 즉시 밀려난다).
- "끝난 뒤 정렬해 min·avg·p50·p99·p99.9·max": 깨어남 지연, 주기 오차, 일한 시간 세 가지 각각에 대해 여섯 숫자를 낸다. 주기 오차는 첫 샘플(iter 0, 비교 대상 없음)을 뺀다.
- "JSON 으로 저장 → make_table1.py → 표①": `--json 파일` 옵션으로 저장한 파일을 `scripts/make_table1.py` 가 읽어 `docs/measurements/table1_pi4.md` 의 한 줄로 만든다. 사람이 숫자를 옮겨 적지 않는다.
- "종료 코드: drops>0 이면 1 (CI 가 '로깅이 못 따라감'을 실패로)": CI 러너에서 `jitter_bench --no-rt 2초` 를 돌리는데, 드롭이 있으면 잡이 빨개진다. "RT 루프를 로깅이 못 따라갔다"는 것은 측정값을 믿을 수 없다는 뜻이기 때문이다.
- "옵션: --period-us --seconds --prio|--no-rt --cpu --work-us --label --json": 주기(기본 1000 us), 측정 시간(기본 10초), 우선순위(기본 80) 또는 일반 스케줄링, 고정할 CPU, 매 주기 일하는 시간(기본 50 us), 결과에 붙일 이름, 저장 파일. 표①의 Pi 줄은 예를 들어 `--seconds 60 --prio 80 --cpu 3 --work-us 50 --label pi4_rt_stress_isol --json …` 으로 돌렸다.

## 3. 용어와 단위
- **스레드**: 한 프로그램 안에서 동시에 도는 작업 흐름. 여기서는 "재는 스레드"와 "모으는 스레드" 둘.
- **SCHED_FIFO / mlockall / CPU 고정**: 장표 024 의 준비 5단계. 급한 스레드로 등록, 메모리를 RAM 에 고정, 특정 CPU 에 못 박기.
- **SPSC 링 버퍼**: 넣는 쪽 하나, 꺼내는 쪽 하나인 원형 저장소. 락이 없어 RT 스레드가 기다리지 않는다(장표 020).
- **drops(드롭)**: 링이 꽉 차서 버린 기록 수. 0 이어야 측정이 온전하다.
- **p50 / p99 / p99.9 / max**: 백분위수. 다음 장표에서 자세히.
- **ns / us**: 나노초(10억분의 1초) / 마이크로초(100만분의 1초). 기록은 ns 로 저장하고 표에는 us 로 나눠 적는다(1,000 ns = 1 us).
- **종료 코드**: 프로그램이 끝나며 운영체제에 돌려주는 숫자. 0 = 성공, 그 외 = 실패. CI 는 이 숫자로 통과/실패를 가른다.

## 4. 쉬운 예시
- 비유: 100 m 달리기 선수(RT 스레드)의 기록을 재는데, 선수가 매 바퀴마다 멈춰서 자기 기록을 노트에 적는다면 기록이 늦어진다. 그래서 선수는 바퀴를 돌 때마다 번호표 하나를 바구니(링 버퍼)에 던져 넣기만 하고, 옆의 기록원(로깅 스레드)이 바구니에서 꺼내 노트에 옮긴다. 경기가 끝난 뒤에 기록원이 정렬해서 "가장 느린 바퀴는 몇 초"를 발표한다.
- 숫자 예시: 60초 × 1,000 Hz = 60,000 바퀴. 기록 한 줄이 32바이트이니 60,000줄은 약 1.9 MB — 로깅 스레드의 벡터에 그대로 들어간다(main() 이 `reserve` 로 미리 잡아 둔다). 링은 65,536칸이라 기록원이 65초 동안 한 번도 못 꺼내야 비로소 넘친다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 링 크기 65,536 = `rt_control/rt_core/include/rt_core/rt_loop.hpp` 63줄 `kRingSize`; Sample 구조체(4개 × 8바이트) = 같은 파일 29~34줄.
- 확인: 로깅 스레드의 1 ms 쉼 = `rt_control/rt_core/src/jitter_bench.cpp` 261줄; 종료 코드 규칙 = 같은 파일 311~316줄; 옵션 목록 = 55~62줄(도움말 문자열).
- 확인: 기본값(주기 1000 us, 10초, 우선순위 80, 일 50 us) = 도움말 문자열 57~61줄.
- 다시 돌려 보기: `./build/rt_core/jitter_bench --no-rt --seconds 5` (일반 스케줄링, 권한 불필요). RT 로 돌리려면 `sudo` 가 필요하다(SCHED_FIFO).
- 결과 파일 예: `docs/measurements/jitter_pi4_rt_stress_isol.json` 과 같은 이름의 `.meta`(온도·스로틀·부하 조건).

## 6. 자주 하는 오해·함정
- "측정기가 결과를 파일에 쓰니까 그만큼 느려지는 것 아닌가?" — 파일 쓰기는 측정이 끝난 뒤, 그것도 로깅 스레드가 한다. RT 스레드가 하는 I/O 는 0 이다.
- "드롭 0 이면 측정이 정확하다는 뜻인가?" — 드롭 0 은 "기록을 하나도 안 잃었다"는 뜻이지 지연이 작다는 뜻이 아니다. 지연은 p99.9·max 로 따로 본다.
- "일반 스레드가 링에서 꺼내는 동안 RT 스레드가 밀리지 않나?" — 링은 락이 없고, 로깅 스레드는 우선순위가 낮아 RT 스레드가 깨면 즉시 비켜난다. 다만 같은 CPU 를 쓰면 캐시를 어지럽힐 수는 있어서, Pi 측정에서는 RT 스레드를 CPU 3 에 고정·격리했다(E19-b·c).
- 측정기 자체가 맞는지는 별도 실험(E19-d, 장표 093)으로 표준 도구 cyclictest 와 맞춰 보았다.

## 7. 면접 한 문장
"측정기도 제어 노드와 같은 규칙으로 만들었습니다 — RT 스레드는 링에 숫자만 던지고, 파일과 통계는 일반 스레드가 끝난 뒤에 처리합니다. 그래서 재는 행위가 재는 대상을 망치지 않고, 드롭이 있으면 종료 코드로 실패를 알립니다."
