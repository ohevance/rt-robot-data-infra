# 장표 080 — ⑥ OTA 배포기 — 한 단계 (2/2): 헬스 게이트 — 지켜본 뒤 하나라도 아프면 전부 되돌린다 (run_stage 뒷부분)
*위치: 2부 데이터의 길 · ⑥ OTA · ② 코드 — run_stage 2/2 헬스 게이트*

## 1. 이 장표가 왜 있나
앞 장표(079)에서 `run_stage` 의 앞부분 — 이번 단계 장치에 명령을 보내고 전부 적용될 때까지 기다리는 부분 — 을 읽었다. 적용이 끝났다고 끝이 아니다. "적용된 펌웨어가 **건강한가**"를 보고 다음 단계로 넘어갈지 결정하는 문이 필요하다. 그것이 헬스 게이트이고, 들머리(077)의 기준 "나쁜 펌웨어는 첫 단계에서 멈춘다"와 "판단은 서버 한 곳에서"를 실제로 구현하는 자리다. 이 장표는 `run_stage` 의 뒷부분(155~172줄)이다. 그림 078 의 "헬스 게이트 3초 → 비정상 3/3 > 허용 0 → 롤백 결정" 화살표가 이 열여덟 줄이다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/ota/rollout.py:155-172`. 앞 장표의 153줄 "전원 적용 완료" 바로 다음부터다.

- 155줄 주석 `# 헬스 게이트: health_wait 동안 지켜본 뒤, 지금까지 새 버전을 받은 모든 장치의 state 를 본다` — 두 가지가 적혀 있다. "지켜본다"(바로 판단하지 않는다)와 "지금까지 받은 모든 장치"(이번 단계만이 아니다).
- 156줄 `time.sleep(self.health_wait_s)` — `health_wait`(기본 5.0초) 동안 기다린다. 왜 기다리나: 새 펌웨어가 켜진 직후에는 아직 정상처럼 보일 수 있고, 장치의 상태는 1 Hz 텔레메트리로 올라오므로 상태가 서버에 반영되기까지 최대 1초가 걸린다. 몇 초 지켜봐야 "켜지고 나서 고장 나는" 펌웨어를 잡을 수 있다.
- 157줄 `snap = self.w.snapshot(self.updated)` — `FleetWatcher` 가 텔레메트리를 들으며 기억해 둔 장치별 최신 값(`fw`, `state`)의 복사본을, `updated`(지금까지 새 버전을 받은 모든 장치) 전부에 대해 가져온다. 복사본을 쓰는 이유는 판단하는 동안 값이 바뀌지 않게 하려는 것(74~80줄에서 잠금을 잡고 복사).
- 158~161줄 `unhealthy = []` / `for device_id in self.updated:` / `if snap.get(device_id, {}).get("state") != "ok":` / `unhealthy.append(device_id)` — 장치마다 상태가 `ok` 가 아니면 비정상 목록에 넣는다. 기준이 "`ok` 가 아니면 전부 비정상"이라는 점이 중요하다: `fault` 뿐 아니라 `updating`(아직 적용 중), `tripped`(안전 멈춤), 그리고 텔레메트리가 아예 없어 상태를 모르는 장치(`{}` → None)도 비정상이다. 모르는 것은 건강하다고 치지 않는다.
- 162줄 `unhealthy.sort()` — 이름순 정렬. 출력과 테스트가 매번 같은 순서가 되게.
- 163줄 `self.mark(f"단계 {pct}%: 헬스 검사 — 비정상 {len(unhealthy)}/{len(self.updated)} (허용 {self.max_fail})")` — 결과를 타임라인·화면·DB 에 남긴다. 그림 078 의 "비정상 3/3 > 허용 0" 이 이 줄이다.
- 164줄 `if len(unhealthy) > self.max_fail:` — 판단 기준 한 줄. 비정상 장치 수가 허용치(`max_fail`, 기본 0)를 **넘으면** 롤백. 기본 0 이면 한 대라도 아프면 되돌린다.
- 165~168줄 `shown = unhealthy[:10]` / `more = ""` / `if len(unhealthy) > 10:` / `more = " ..."` — 로그에 적을 장치 이름을 10개까지만. 50대가 다 아플 때 로그 한 줄이 너무 길어지지 않게.
- 169줄 `self.mark(f"비정상 장치: {shown}{more} → 롤백 결정")` — 어느 장치가 아팠는지와 롤백 결정을 기록. 나중에 "왜 되돌아갔나"를 이 줄로 안다.
- 170~171줄 `self.rollback()` / `return False` — 롤백(장표 081)을 실행하고 False 를 돌려 `run()` 이 다음 단계를 시작하지 않게 한다. 5 % 에서 멈추면 50 %·100 % 단계의 47대는 명령을 받은 적도 없게 된다.
- 172줄 `return True` — 비정상이 허용치 안이면 통과. `run()` 은 다음 단계(50 %)로 간다. 세 단계 모두 True 면 "완료: 50/50 장치가 <버전>" 을 찍고 `success=true`.

오른쪽 "읽는 포인트" 네 줄:
- "health_wait 초 동안 지켜본 뒤 '지금까지 새 버전을 받은 모든 장치(updated)'의 state 스냅샷을 본다 — 이번 단계 3대만이 아니라 누적 전부" — 156~157줄. 50 % 단계의 게이트는 25대를 본다. 5 % 단계에서는 괜찮았던 3대가 몇 초 뒤 나빠질 수도 있기 때문이다.
- "ok 가 아닌 장치 수 > max_fail(기본 0) 이면 rollback() → 이 단계에서 멈춘다. 50% · 100% 단계는 시작도 안 한다(47대는 명령을 받은 적도 없다)" — 164~171줄.
- "판단 기준(헬스 게이트·허용 수)이 서버 코드 한 곳에 있다 — 장치는 적용/복원만(DECISIONS 11/03 D3)" — 이 열여덟 줄이 판단의 전부다. 장치 쪽 코드에는 "나쁜가"를 판단하는 줄이 없다.
- "통과하면 True → 다음 단계(50%)로. 세 단계 다 통과 = success" — 172줄.

## 3. 용어와 단위
- 헬스 게이트(health gate): 단계 사이의 문. 건강 기준을 넘어야 열린다. 여기서 건강 = 텔레메트리 `state == "ok"`.
- health_wait(초): 판단 전에 지켜보는 시간. 기본 5.0초. 그림 078 의 실행은 3초.
- max_fail: 허용하는 비정상 장치 수. 기본 0.
- 스냅샷(snapshot): 그 순간 값의 복사본. 판단 도중 값이 바뀌는 것을 막는다.
- `snap.get(device_id, {}).get("state")`: 장치 기록이 없으면 빈 사전, 그 안에 state 가 없으면 None — 둘 다 "ok 가 아님"으로 처리된다.
- 상태 값: `ok` 정상, `updating` 적용 중, `fault` 고장, `tripped` 안전 멈춤(1부의 상태 머신), `recovering` 복구 중.
- `return True / False`: 함수의 결과. 호출한 `run()` 이 이 값으로 계속할지 멈출지 정한다.
- 1 Hz: 장치 상태가 1초에 한 번 올라온다 → 상태 반영 지연 최대 1초.

## 4. 쉬운 예시
새 약 임상 비유: 환자 3명(5 %)에게 새 약을 먹이고(앞 장표), 바로 판단하지 않고 5일(health_wait) 지켜본다. 5일 뒤 "지금까지 새 약을 먹은 모든 환자"의 차트(스냅샷)를 본다. 한 명이라도 정상이 아니면(허용 0) 새 약을 먹은 전원에게 원래 약으로 돌아가게 하고(롤백) 시험을 중단한다 — 나머지 47명은 새 약을 받은 적이 없다. 전원 정상이면 25명으로 넓힌다. 판단은 병원 본부가 하고 환자는 "먹기"와 "원래대로"만 한다.

숫자 예시: 50대, 기본값. 5 % 단계: 3대 적용 완료 → 5초 대기 → 스냅샷 3대 → 나쁜 펌웨어면 3 / 3 비정상 > 0 → 롤백(1.0초) → False → 끝. 피해 3 / 50. 좋은 펌웨어면 0 / 3 → True → 50 % 단계: 22대 더 보내고 25대 스냅샷 → 0 / 25 → True → 100 % 단계: 25대 더 보내고 50대 스냅샷 → 0 / 50 → True → success. 소요 시간은 단계마다 약 2(적용) + 5(헬스) = 7초, 세 단계 약 21초.

## 6. 자주 하는 오해·함정
- "이번 단계 장치만 검사한다"는 오해. 누적 전부(`updated`)를 본다. 앞 단계에서 괜찮던 장치가 나중에 나빠지는 것도 잡아야 하기 때문이다.
- "상태를 모르는 장치는 넘어간다"는 오해. 텔레메트리가 안 오는 장치는 `state` 가 None 이라 비정상으로 센다. 보수적인 쪽이 안전하다.
- `max_fail` 을 0 보다 크게 하면 "그 수만큼은 고장 나도 배포를 계속한다"는 뜻이다. 실험에서는 0 을 썼다. 실물에서는 장치 수와 고장의 뜻에 따라 정한다.
- health_wait 는 길수록 안전하지만 배포가 느려진다. 5초는 1 Hz 상태 반영(최대 1초)에 여유를 둔 값이고, 그림 078 의 실행은 3초로도 잡혔다.
- `time.sleep` 으로 기다리는 동안 서버는 다른 일을 못 한다. 배포기는 한 번에 한 배포만 하는 도구라 문제가 없지만, 여러 배포를 동시에 하려면 구조를 바꿔야 한다.

## 7. 면접 한 문장
"헬스 게이트는 열여덟 줄입니다 — health_wait 만큼 지켜본 뒤 지금까지 새 버전을 받은 모든 장치의 state 스냅샷을 보고, ok 가 아닌 수가 허용치를 넘으면 전부 되돌리고 멈춥니다. 판단 기준이 서버 이 한 곳에만 있어서 장치는 적용과 복원만 합니다."
