# 장표 072 — ③ 수집기 — 1초마다 (1/2): 묶음을 backlog 끝에 붙이고, 상한을 넘으면 오래된 것부터 버린다
*위치: 2부 데이터의 길 · ③ 수집기 · ② 코드 — flush_once · 상한*

## 1. 이 장표가 왜 있나

앞 장표(071)에서 받는 쪽은 메시지를 임시 목록(pending)에 넣기만 한다고 했다. 그러면 누가, 언제 DB 에 넣나? 이 장표가 그 답의 앞부분이다. 메인 스레드가 1초마다 부르는 `flush_once` 가 임시 목록을 통째로 꺼내 묶음(batch) 하나로 만들고, 그 묶음을 **backlog(밀린 일거리 목록)의 끝**에 붙인 뒤 DB 로 밀어 넣는다(밀어 넣는 함수 drain_backlog 는 다음 장표). 그리고 DB 가 오래 죽어 있어 backlog 가 한없이 커지는 것을 막는 상한 처리 `enforce_backlog_limit` 을 함께 보여 준다. 들머리의 기준 "DB 중단 중 유실 0(backlog)" 가 어떻게 코드로 구현되는지, 그리고 "그래도 메모리는 지켜야 한다"는 현실의 타협을 어디에 두었는지가 이 장표의 요점이다.

## 2. 장표를 하나씩 읽기

파일 `fleet/collector/collector.py`, 두 구간이다: 207~217줄(flush_once 앞부분)과 234~240줄(enforce_backlog_limit).

- 207줄 `def flush_once(self):` — "한 번 비우기". 메인 루프(main, 356줄)가 1초 간격(`--interval` 기본 1.0초)으로 부른다.
- 208줄 설명 문자열: "1초마다: 묶음을 만들고 DB 에 넣고(안 되면 backlog) 통계를 낸다. 반환: 통계 dict".
- 209줄 `batch, latencies, online = self.take_batch()` — 184줄의 take_batch 가 잠금을 한 번 잡고 pending 세 목록(행·지연·상태)을 통째로 빼 와 새 빈 목록으로 바꿔 놓는다. 돌려주는 것은 묶음(Batch 객체: 행들·상태들·장치 스냅샷·시각), 지연값 목록, 온라인 장치 수.
- 211줄 `t0 = time.monotonic()` — DB 적재에 걸린 시간을 재기 위한 시작 시각.
- 212줄 `if not self.dry_run:` — `--dry-run`(DB 없이 통계만) 이 아닐 때만 DB 일을 한다.
- 213줄 `self.backlog.append(batch)` — 이번 1초 묶음을 **backlog 끝에 붙인다**. DB 가 멀쩡해도 일단 backlog 를 거친다. 그래야 "밀린 것이 있으면 그것부터, 그다음 이번 것" 이라는 순서가 코드 한 곳(drain_backlog)으로 보장된다.
- 214줄 `self.backlog_rows += len(batch.rows)` — backlog 에 들어 있는 행 수 합계를 갱신(통계와 상한 판정에 쓴다).
- 215줄 `self.enforce_backlog_limit()` — 상한 검사(아래).
- 216줄 `self.drain_backlog()` — backlog 를 오래된 것부터 DB 에 민다(다음 장표 073).
- 217줄 `insert_ms = (time.monotonic() - t0) * 1000.0` — 적재에 걸린 밀리초. 통계 `insert_ms` 와 Grafana "DB 적재 시간" 패널의 값. (장표에 보이지 않는 218줄 이후는 통계 dict 를 만들고 write_stats 로 DB 에 남기는 부분이다.)
- 234줄 `def enforce_backlog_limit(self):` — "상한을 넘으면 가장 오래된 묶음부터 버린다 (메모리 보호). 버린 행 수를 센다."
- 236줄 `while self.backlog_rows > MAX_BACKLOG_ROWS and len(self.backlog) > 1:` — 행 수가 상한(60줄 `MAX_BACKLOG_ROWS = 200000`)을 넘고 묶음이 2개 이상일 때 반복. "2개 이상" 조건은 방금 붙인 최신 묶음 하나는 남기기 위해서다.
- 237~239줄 `oldest = self.backlog.pop(0)`, `self.backlog_rows -= len(oldest.rows)`, `self.backlog_dropped += len(oldest.rows)` — 맨 앞(가장 오래된) 묶음을 떼어 내고, 행 수를 빼고, **버린 행 수를 backlog_dropped 에 누적**한다. 잃었다는 사실을 숨기지 않고 센다.

읽는 포인트 네 줄:
- "flush_once 는 1초마다 메인 스레드가 부른다: take_batch 로 pending 을 통째로 꺼내(락 한 번) backlog 끝에 붙이고, drain_backlog 로 DB 에 민다" — 위 201·205·216줄. 잠금을 1초에 한 번만 잡으므로 받는 쪽을 거의 방해하지 않는다.
- "왜 1초 묶음 + COPY: 300대 × 1 Hz 를 행마다 INSERT 하면 DB 왕복 300번/초 → 묶으면 1번/초. 대신 DB 에 보이기까지 최대 1초(표③ 비고에 적음)" — 설계 결정 DECISIONS 11/03 (D2). COPY 는 다음 장표의 write_db 에서 쓴다.
- "enforce_backlog_limit: 상한 MAX_BACKLOG_ROWS(200,000행 = 50대 × 1 Hz × 66분)를 넘으면 가장 오래된 묶음부터 버리고 backlog_dropped 로 센다 — 메모리를 지키되 '잃었다'를 숨기지 않는다(DECISIONS D4)" — 200,000 ÷ 50 ÷ 60 ≈ 66.7분. 장치가 300대면 약 11분(코드 주석).
- "받는 쪽(on_message)은 여기를 모른다 — pending 에 넣기만" — 두 스레드의 역할 분리. 받는 쪽은 DB 상태를 전혀 신경 쓰지 않는다.

## 3. 용어와 단위

- **flush**: 모아 둔 것을 한꺼번에 내보내는 동작. "한 번 비우기".
- **backlog**: 밀린 일거리. 여기서는 아직 DB 에 못 넣은 묶음들의 목록(오래된 것이 앞).
- **행(row) / 묶음(batch)**: 행 = 메시지 1개가 DB 표의 한 줄로 바뀐 것, 묶음 = 1초치 행들의 덩어리.
- **상한(MAX_BACKLOG_ROWS)**: 200,000행. 메모리를 무한히 쓰지 않기 위한 선.
- **dry_run**: 연습 실행. DB 없이 통계만 찍어 본다(psycopg 가 없어도 돈다).
- **ms(밀리초)**: 1,000분의 1초. insert_ms 가 31 이면 적재에 0.031초.
- **monotonic**: 뒤로 안 가는 시계. 걸린 시간 재기에 쓴다.
- **COPY**: PostgreSQL 의 대량 적재 명령. 행마다 INSERT 하는 것보다 DB 왕복이 훨씬 적어 빠르다(write_db 에서 사용).

## 4. 쉬운 예시

- 비유: 택배 상하차장. 1분마다 들어온 상자(pending)를 한 팔레트(묶음)로 묶어 출고 대기열(backlog) 끝에 둔다. 트럭(DB)이 오면 대기열 맨 앞 팔레트부터 싣는다. 트럭이 며칠째 안 오면 창고가 터지므로 가장 오래된 팔레트부터 폐기하되 폐기 수량(backlog_dropped)을 장부에 적는다 — "잃었지만 몇 개 잃었는지는 안다".
- 숫자 예시: 50대가 1 Hz 로 보내면 1초 묶음은 50행. DB 가 10초 죽으면 backlog 에 약 10묶음 = 500행이 쌓이고(실측 570행 — 복귀 전후 1초 묶음 경계 때문에 조금 더), 복귀하면 다음 초에 전부 들어간다. 상한 200,000행에 닿으려면 50대 기준 66분 넘게 DB 가 죽어 있어야 한다.

- 확인: 300 왕복/초 → 1번/초 — `collector.py` 머리말 "왜 1초 묶음(batch)인가", `docs/DECISIONS.md` 11/03 (D2).
- 확인: DB 장애 때 뒤늦게 570행, 유실 0 / 1341 — `docs/measurements/table3.md` 표③-2.
- 확인: 단위 테스트 — `fleet/tests/test_collector_resilience.py` 의 `test_backlog_limit`(95줄)이 상한을 넘기면 가장 오래된 묶음이 버려지고 backlog_dropped 가 세어지는지 검사한다. 실행: `python3 fleet/tests/test_collector_resilience.py`.

## 6. 자주 하는 오해·함정

- "DB 가 멀쩡하면 backlog 는 안 쓰인다"는 오해 — 매초 묶음은 항상 backlog 를 거쳐 들어간다(append → drain). 평소엔 그 안에 머무는 시간이 0 에 가까울 뿐이다.
- 상한에 닿으면 데이터를 잃는다. 이것은 숨긴 것이 아니라 **설계상 선택**이고(디스크 큐는 2주 범위 밖), 버린 수를 세어 통계에 남긴다. 현장에서는 상한 = 허용 중단 시간 × 장치 수 × Hz 로 다시 정해야 한다.
- insert_ms 는 묶음 전체를 넣는 시간이지 행 하나의 시간이 아니다. 11/04 실측 평균 31.3 ms(표③-1).
- `--dry-run` 에서는 backlog 도 DB 도 건드리지 않으므로 유실 실험에 쓰면 안 된다.

## 7. 면접 한 문장

"1초마다 묶음을 backlog 끝에 붙이고 오래된 것부터 DB 에 민다 — 그래서 DB 가 죽어도 순서대로 보존되고, 상한 200,000행을 넘으면 오래된 것부터 버리되 버린 수를 세어 '잃었다'를 숨기지 않는다."
