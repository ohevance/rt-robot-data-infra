# 장표 122 — CI 결과를 보고 무엇을 판단하나 — 실패 유형별 첫 행동
*위치: 6부 믿을 수 있나 · CI — 실패 유형별 판단*

## 1. 이 장표가 왜 있나

119~121번에서 CI 세 잡이 각각 무엇을 돌리는지 봤다. 그러면 push 뒤 배지가 빨개졌을 때 **무엇부터 봐야 하나**? 6부의 질문은 "이 숫자들을 어떻게 믿나"였고, 믿음의 반쪽은 "깨졌을 때 원인을 빨리 가를 수 있다"는 것이다. 이 장표는 CI 결과를 읽는 **판단표**다 — 증상 7가지를 "뜻(어느 층이 깨졌나)"과 "첫 명령(무엇을 치나)"으로 잇는다. 아래 비고는 이 표가 머리로 만든 것이 아니라 실제로 CI 가 잡은 두 사고(11/04, 11/05)에서 나왔음을 밝힌다. 다음 장표(123)는 같은 내용을 Jenkins 에 익숙한 사람의 말로 옮긴다.

## 2. 장표를 하나씩 읽기

표는 세 칸이다 — 증상(무엇이 보이나), 뜻(어느 층의 문제인가), 첫 명령(제일 먼저 칠 것). 행마다 읽는다.

- 1행 "배지 빨강 / gh run list ✗ → 마지막 push 가 3잡 중 하나라도 실패. 다른 일보다 먼저 본다 — 포트폴리오 첫 화면 → gh run view <ID> --log-failed | tail -40": README 맨 위 배지는 **가장 최근 실행** 하나만 반영한다. 세 잡 중 하나라도 ✗ 면 빨갛다. 채용 담당자가 저장소를 열면 첫 화면에서 보는 것이 배지라서, 다른 어떤 일보다 먼저 고친다. `gh run list` 로 실행 ID 를 얻고 `--log-failed` 로 실패한 단계의 로그만 뽑아 마지막 40줄을 본다 — 거의 항상 마지막 40줄에 원인 문장이 있다.
- 2행 "rt_core 의 ctest 실패 → 코드 논리가 깨짐(WSL 에서도 깨질 것) → ctest --test-dir build/rt_core --output-on-failure": 잡 1 의 C++ 단위 테스트(링 버퍼·제어 단계·상태 머신·연기)가 떨어진 것. 러너와 환경이 무관한 순수 논리라서 WSL 에서 같은 명령을 치면 같은 자리에서 깨진다. `--output-on-failure` 는 실패한 테스트의 출력만 보여 준다.
- 3행 "rt_core 의 fleet 단위 FAIL: → 수집기·OTA·에이전트 논리 → python3 fleet/tests/test_*.py": 잡 1 뒷부분의 파이썬 단위 테스트 15건(`test_fleet_logic.py` 6 · `test_ota_rollout.py` 3 · `test_collector_resilience.py` 6). 가짜 브로커·가짜 DB 위라서 역시 WSL 에서 그대로 재현된다. 출력에 `FAIL:` 로 시작하는 줄이 어느 테스트인지 알려 준다.
- 4행 "fleet_integration '장치 0대' → 수집기나 가상 장치가 시작 직후 죽음 → 로그에서 traceback (11/05 NameError: request_stop)": 잡 2 에서 유실 집계가 "장치 0대"로 나오면 메시지가 유실된 것이 아니라 **보낼 쪽이나 받을 쪽이 처음부터 안 떴다**는 뜻이다. `build/integration/` 아티팩트의 `collector.log`·`fleet.log` 에서 파이썬 traceback 을 찾는다. 11/05 의 실제 사례: 수집기 `main()` 이 `NameError: name 'request_stop' is not defined` 로 즉사했다.
- 5행 "fleet_integration 복구 시간 초과 → 타이밍·컨테이너 준비(11/04 TimescaleDB 임시 서버) → migrate.py --wait 가 지났는지, settle 값": 수집기는 떴는데 "복구됨" 판정이 안 나오면 환경의 **시간** 문제다. DB 가 진짜 준비되기 전에 달려들었나(`--wait 120` 이 다 지났나), 장애 뒤 가라앉힘 `--settle 8` 이 러너의 느린 디스크에 충분했나를 본다. 11/04 1차 실패가 바로 TimescaleDB 초기화 중 임시 서버를 준비됨으로 착각한 경우였다.
- 6행 "mujoco 다운로드 실패 → 외부 URL·버전 → get_mujoco.sh 와 ci.yml 의 MUJOCO_VERSION 일치": 잡 3 은 외부 사이트(GitHub 릴리스, Menagerie 저장소)에서 내려받는다. 버전 문자열이 두 곳(`ci.yml` env 와 `scripts/get_mujoco.sh` 기본값)에 있어 한쪽만 바꾸면 없는 URL 을 받는다. 외부 사이트 장애면 재실행(`gh run rerun`)이 답이다.
- 7행 "Unable to resolve action → uses: 버전이 없음 → checkout@v5, upload-artifact@v5 확인": 잡 자체가 시작도 못 하는 경우. `uses: actions/checkout@v5` 처럼 GitHub 가 제공하는 액션의 버전 꼬리표가 틀리면 이 문구가 뜬다. 11/05 에 checkout·upload-artifact 를 v5 로 올렸으므로(커밋 58d22cf) 이 둘을 먼저 본다.
- 아래 비고 "CI 가 실제로 잡은 2건: 11/04 TimescaleDB 초기화 경쟁(WSL 볼륨엔 데이터가 있어 안 보임), 11/05 request_stop 삭제(단위 테스트가 main() 을 안 탔고 WSL 에서 수집기를 다시 띄운 적이 없음). 규칙: 문서 커밋이라도 push 뒤 gh run list -L 1": 두 사고의 공통점은 **내 PC 에서는 보이지 않았다**는 것 — 첫째는 볼륨에 데이터가 이미 있어 초기화 단계가 없었고, 둘째는 수정 뒤 수집기를 다시 띄워 보지 않았다. 그래서 규칙이 생겼다: 문서만 바꾼 커밋이라도 push 뒤 `gh run list -L 1` 로 마지막 실행 하나는 꼭 본다(11/05 는 문서 위주 push 가 이어져 빨간 배지를 한동안 못 봤다).

## 3. 용어와 단위

- 배지(badge): README 에 박힌 작은 그림. GitHub 가 마지막 워크플로 실행의 상태(초록 passing / 빨강 failing)를 그려 준다.
- `gh`: GitHub 명령줄 도구. `gh run list -L N` = 최근 N개 실행, `gh run view <ID> --log-failed` = 실패한 단계의 로그만, `gh run rerun <ID>` = 다시 실행.
- 실행 ID(run ID): 워크플로 실행 하나마다 붙는 긴 숫자. `gh run list` 첫 줄 끝에 있다.
- traceback: 파이썬이 죽을 때 남기는 호출 경로. 마지막 줄이 예외 이름과 메시지(`NameError: name 'request_stop' is not defined`).
- `NameError`: 정의되지 않은 이름을 불렀다는 파이썬 오류. 함수가 지워졌는데 부르는 쪽이 남아 있으면 난다.
- settle(가라앉힘): 장애를 끝낸 뒤 숫자를 재기 전에 기다리는 시간(초). 복구가 끝나기 전에 재면 "복구 안 됨"으로 보인다.
- `uses:`: GitHub Actions 에서 남이 만든 액션을 가져다 쓰는 줄. `@v5` 가 버전 꼬리표.

## 4. 쉬운 예시

- 비유: 자동차 계기판의 경고등이 켜졌을 때 "엔진 경고면 OBD 코드를 읽고, 타이어 경고면 공기압을 보고, 연료 경고면 주유소"처럼 **등 종류별 첫 행동**을 외워 두는 것. 이 표는 CI 의 경고등 7종과 각각의 첫 행동이다.
- 숫자 예시: 11/05 push 가 측정 파일·문서 위주로 여러 번 이어지는 동안 배지는 빨갰다(`request_stop`). 규칙 하나(`gh run list -L 1`, 1초)가 있었다면 첫 push 뒤 바로 알았을 일이다.
- 층 가르기 예시: 잡 1 초록 + 잡 2 빨강 = "논리는 맞는데 진짜 환경에서 깨짐"(환경·타이밍·진입점). 잡 1 빨강 = "논리가 깨짐"(WSL 에서 재현). 이 한 줄이 DECISIONS 11/03 D4 "2단계가 깨지면 1단계 통과 여부로 논리 문제냐 환경 문제냐를 먼저 가른다"의 실전 꼴이다.

## 6. 자주 하는 오해·함정

- "배지가 초록이면 코드가 다 맞다"는 오해: 배지는 **마지막 실행** 하나다. 그 뒤 push 가 없으면 옛 결과가 그대로 보이고, 러너에서 안 도는 것(RT 지연, 실물)은 처음부터 검사 대상이 아니다.
- "단위 테스트 초록 = 수집기 멀쩡": 11/05 가 반례다. 단위 테스트는 Collector 클래스만 썼고 `main()` 은 안 탔다. 그래서 진입점을 한 바퀴 타는 스모크 테스트를 추가했다(장표 129 비고의 규칙 1).
- "WSL 에서 되니까 CI 도 된다": 11/04 가 반례다. WSL 의 DB 볼륨에는 데이터가 있어 초기화 단계가 없었고, 러너는 매번 빈 볼륨이다. 헬스 체크는 소비자와 같은 경로(TCP)로 해야 한다.
- 로그 전체를 읽으려 하지 않는다. `--log-failed | tail -40` 이 먼저고, 거기에 없을 때만 넓힌다.
- 외부 다운로드 실패(6행)는 내 코드 문제가 아닐 수 있다. 같은 커밋을 `gh run rerun` 해서 두 번째도 실패할 때만 버전을 의심한다.

## 7. 면접 한 문장

"CI 가 빨개지면 어느 잡이 떨어졌는지로 층을 먼저 가릅니다 — 잡 1 이면 논리라서 WSL 에서 재현되고, 잡 2 만 떨어지면 환경이나 진입점 문제인데, 실제로 두 번 다 후자였고 둘 다 제 PC 에서는 보이지 않던 것이라 '문서 커밋이라도 push 뒤 CI 를 본다'는 규칙이 생겼습니다."
