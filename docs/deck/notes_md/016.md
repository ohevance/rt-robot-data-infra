# 장표 016 — 단계 2 — ROS 2 / DDS 가 전달한다 — 미들웨어가 하는 일과 QoS
*위치: 1부 로봇을 움직이는 길 · 단계 2/10 DDS 전달 · ② 미들웨어가 하는 일 · QoS*

## 1. 이 장표가 왜 있나
들머리(014)가 결론을, 그림(015)이 층 구조를 보여 줬다. 이 장표는 단계 2 의 마지막 장으로, 그 둘을 글로 정리한다 — DDS 가 하는 일, 구현체 둘, 결과를 가르는 QoS 두 가지, 표②가 잰 것과 결과, 그리고 실제로 겪은 함정 하나. 오른쪽 상자(callout)에는 이 단계의 소스 위치가 모여 있다. 단계 2 에는 우리 코드가 거의 없기 때문에(구독 선언 두 줄) 코드 장표 대신 이 설명 장표 한 장으로 끝내고, 아래 `다음 ▶` 다리로 단계 3(우편함)으로 넘어간다.

## 2. 장표를 하나씩 읽기
글머리표를 위에서 아래로.

- "ROS 2 토픽은 DDS(Data Distribution Service) 위에서 움직인다. 발행자와 구독자는 서로를 모르고, DDS 가 '발견'하고 실어 나른다 (RMW = ROS 가 DDS 를 부르는 층)": 단계 2 의 바탕 사실. ROS 2 자체는 통신을 하지 않는다. RMW 는 ROS 2 와 DDS 사이의 어댑터.
- "구현체가 둘: Fast DDS(Jazzy 기본) · Cyclone DDS. 환경변수 RMW_IMPLEMENTATION 으로 고른다. 노드의 rt_status 에 실제 쓰인 rmw 이름이 찍힌다": ROS 2 Jazzy 를 설치하면 기본은 Fast DDS. Cyclone 은 패키지를 더 깔고 환경 변수로 바꾼다. 노드가 자기 구현체 이름을 1초 상태 JSON 에 넣는 이유는 "어느 구현체에서 나온 숫자인지"를 나중에 알 수 있게 하려는 것.
- "QoS 두 가지가 결과를 가른다: reliable(못 받으면 재전송 — 늦어도 도착) vs best_effort(빠르지만 잃을 수 있음), 깊이(depth, 큐 길이)": 재전송 여부와 보관 개수. 우리 노드의 구독은 깊이 10.
- "이 단계에서 잰 것이 표②(E04): 구현체 × QoS × 크기(64 B~1 MB) 16조합의 왕복 지연(RTT)과 손실 — 측정기와 실험 사슬은 3부 장표 87~88": 2 × 2 × 4 = 16. 1부에서는 결과 두 줄만 아래에 적고 측정기와 판단 사슬은 3부로.
  - (하위) "작은 메시지(64 B~64 KB)는 전부 손실 0, RTT p50 0.9~1.2 ms(rclpy 오버헤드 포함) → 관절 명령(수십 B) 은 어느 조합이든 문제없다": 12조합 전부 받음 500/500. 괄호의 뜻 — 측정기가 파이썬이라 절대값에 수백 us 가 얹혀 있다.
  - (하위) "1 MB 에서 갈린다: Fast DDS best_effort 99.8% 손실, reliable 22.8%(깊이 10 초과) · Cyclone 0% → 큰 데이터(영상·점군)는 구현체·QoS 를 골라야 한다": "깊이 10 초과"는 reliable 인데도 잃은 이유 — 재전송은 보관함에 남은 것만 가능한데 100 Hz 로 밀려드는 1 MB 가 보관함(10개)에서 밀려났다. Cyclone 은 둘 다 0%.
- "함정(11/04): ros2 데몬이 다른 RMW 로 떠 있으면 토픽이 안 보인다 → ros2 daemon stop. 타입을 직접 적으면 데몬을 안 거친다(ros2 topic echo /rt_status std_msgs/msg/String)": 실제로 겪은 사고. 아침에 Cyclone 으로 실험한 뒤 Fast DDS 노드를 띄우자 `ros2 topic echo` 가 "아직 발행되지 않음"이라고 했다. 노드는 살아 있었고, 범인은 사용자당 하나뿐이고 처음 뜬 RMW 로 고정되는 ros2 데몬. 해결은 데몬 정지. 메시지 타입을 명령줄에 직접 적으면 데몬에 묻지 않으므로 바로 보인다.
- 오른쪽 상자 "이 단계의 소스": 측정기 `dds_bench/rtt_bench.py`(ping/pong, 191줄) 와 16조합을 돌리는 `run_matrix.sh`, 표를 만드는 `scripts/make_table2.py → docs/measurements/table2.md`, 실험 페이지 `docs/experiments/E04.md`, 결정 `DECISIONS` 11/03 "DDS 지연은 왕복(RTT)으로".
- 아래 다리(`다음 ▶`): "단계 3 — 관절 명령(수십 B)은 어느 조합이든 손실 0 (검증은 3부 장표 87~88). 도착한 명령을 일반 스레드에서 RT 스레드로 어떻게 넘기나? (우편함)". 전달이 해결됐으니 다음 걱정은 프로세스 안의 스레드 경계다.

## 3. 용어와 단위
- DDS / RMW / 구현체 / QoS / reliable / best_effort / depth: 014·015 장표와 같다. 한 줄씩 — DDS 는 발행/구독 표준 미들웨어, RMW 는 ROS 2 가 DDS 를 부르는 어댑터, 구현체는 그 표준을 만든 소프트웨어(Fast DDS·Cyclone), QoS 는 전달 품질 약속, reliable 은 재전송, best_effort 는 한 번만, depth 는 보관 개수.
- Jazzy: ROS 2 의 배포판 이름(2024년판). 이 저장소는 Ubuntu 24.04 + ROS 2 Jazzy.
- 환경 변수: 프로그램을 띄울 때 바깥에서 넘기는 설정값. `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp ros2 run …` 꼴.
- ros2 데몬(daemon): `ros2 topic list` 같은 명령줄 도구가 빠르게 답하도록 뒤에서 상태를 들고 있는 보조 프로세스. 사용자당 하나.
- RTT p50 0.9~1.2 ms: 왕복 중앙값. 1 ms = 1,000 us. rclpy 오버헤드 = 파이썬 ROS 2 라이브러리가 더하는 시간, 수백 us.
- 64 B~1 MB: 1 KB = 1,024 B, 1 MB = 1,024 KB. 관절 명령은 64 B 급, 카메라 영상은 수백 KB~MB, 점군(라이다 등 3차원 점 집합)은 MB 급.

## 4. 쉬운 예시
비유: 택배 회사(DDS 구현체)와 배송 등급(QoS)이다. 편지 한 통(관절 명령)은 어느 회사·어느 등급이든 전부 도착했다. 그런데 대형 가구(1 MB)를 1초에 100개씩 맡기자 A 회사(Fast DDS)는 일반 배송으로 100개 중 99.8개를, 등기 배송으로도 22.8개를 잃었다 — 등기라도 창고(depth 10)에 10개까지만 보관하니 재배송 전에 밀려났기 때문. B 회사(Cyclone)는 다 보냈다. 숫자 예시: 500개를 보내 1개가 왔으면 손실 (500 − 1) ÷ 500 = 99.8%, 386개가 왔으면 (500 − 386) ÷ 500 = 22.8%. 우리 명령 48 B 는 어느 조합이든 500/500 이다.

## 6. 자주 하는 오해·함정
- "Fast DDS 가 나쁘다"가 결론이 아니다. 기본 설정끼리의 비교이고, Fast DDS 도 공유 메모리 강제·소켓 버퍼 확대·depth 증가로 나아질 가능성이 있다(E04 §4, 추정). 결론은 "기본값으로 두면 이렇게 된다".
- reliable 을 "무한 보장"으로 읽지 않는다. 보관함 크기 안에서의 보장이다. 같은 주제가 관제 쪽(브로커 큐 상한 20000, 2부)에도 나온다.
- 측정값은 WSL2 같은 PC 프로세스 간이다. 네트워크 수치로 인용하면 틀린다.
- RMW 를 바꿔 실험한 뒤 데몬을 안 지우면 토픽이 안 보인다. 노드가 죽은 줄 알고 한참 찾게 되는 함정이다.

## 7. 면접 한 문장
"ROS 2 라고 통신이 다 같지 않습니다 — 같은 PC 에서 1 MB 를 100 Hz 로 보내니 Fast DDS 기본 설정은 best_effort 99.8%, reliable 도 22.8% 를 잃었고 Cyclone 은 0% 였습니다. 우리 관절 명령은 수십 B 라 어느 조합이든 손실 0 이지만, 그래서 노드는 자기가 어느 RMW 위에서 도는지 상태에 찍습니다."
