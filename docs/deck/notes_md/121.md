# 장표 121 — CI 잡 3 — mujoco (2단계, 러너 VM 3, 약 45초): 헤드리스 물리 — SO-ARM100 1 kHz, ALLEX 500 Hz, 비용 상한
*위치: 6부 믿을 수 있나 · CI 잡 3 mujoco*

## 1. 이 장표가 왜 있나

앞 두 장표에서 CI 잡 1(논리, 가짜 위에서 1분)과 잡 2(관제, 진짜 컨테이너 위에서 2분)를 봤다. 그런데 1부 단계 6·7에서 본 "물리 엔진(MuJoCo) 백엔드로 바꿔도 제어 코드는 한 줄도 안 바뀐다"와 "물리 한 걸음이 1 ms 주기 안에 들어온다(p99 8.5 us)"는 누가 다시 확인하나? 잡 1 은 MuJoCo 없이 빌드하기 때문에 물리 코드는 아예 컴파일조차 안 된다. 그래서 세 번째 잡 `mujoco` 가 따로 있다 — 새 가상 머신에 MuJoCo 3.3.2 와 SO-ARM100 모델을 내려받아 `-DRT_CORE_WITH_MUJOCO=ON` 으로 다시 빌드하고, 화면 없이(헤드리스) 2,000주기를 돌려 "관절이 움직였나"와 "한 주기 비용이 상한 아래인가"를 재는 잡이다. 이 장표는 그 흐름과, 셋이 다 통과했을 때 README 배지가 초록이 되는 마지막 매듭을 보여 준다.

## 2. 장표를 하나씩 읽기

순서도는 2열로 6개 상자가 뱀처럼 이어진다(11/06 에 ALLEX 두 상자가 더해졌다).

- 회색 상자 "잡 1 통과(needs: rt_core) → 새 VM": 잡 2 와 똑같이 `.github/workflows/ci.yml` 에 `needs: rt_core` 가 있어 잡 1 이 통과해야 시작한다. 잡 2 와 잡 3 은 서로 기다리지 않고 **동시에**(병렬) 돈다 — 둘 다 잡 1 만 기다린다. 러너는 또 새 ubuntu-24.04 가상 머신이라 cmake·g++·git 부터 설치한다.
- 민트 상자 "get_mujoco.sh 3.3.2 + menagerie SO-ARM100 → cmake -DRT_CORE_WITH_MUJOCO=ON": `scripts/get_mujoco.sh` 가 MuJoCo 공개 배포판(버전은 ci.yml 의 `MUJOCO_VERSION: "3.3.2"` 한 곳에서 정하고 스크립트에 넘긴다)과 MuJoCo Menagerie(검증된 로봇 모델 모음)의 `trs_so_arm100` 폴더를 `third_party/` 아래 내려받는다. 그 뒤 rt_core 를 `build/rt_core_mj` 라는 **별도 빌드 폴더**에 `-DRT_CORE_WITH_MUJOCO=ON -DMUJOCO_DIR=…` 로 다시 빌드한다. 기본값이 OFF 라서 옵션을 켜야 `mujoco_backend.cpp` 와 그 테스트가 빌드에 들어온다.
- 마름모 "ctest mujoco: 2,000주기 동안 관절이 움직이고 한 주기 비용 p99 < 900 us?": 테스트 `rt_control/rt_core/test/test_mujoco_backend.cpp` 가 환경 변수 `RT_MUJOCO_MODEL`(so_arm100.xml)로 모델을 열고, 관절 0 에 +0.3 rad 목표를 준 채 1 kHz 로 2,000주기(= 2초)를 돈다. 합격 기준은 셋이다. ① 2초 뒤 관절 0 이 0.15 rad 넘게 움직였다(목표의 절반 이상 — 물리 모델이 명령에 반응했다는 뜻). ② 0.6 rad 를 넘지 않았다(과도하게 튀지 않았다). ③ 한 주기 비용(`write_command` = `mj_step` + `read_state`)의 p99 가 900 us 미만 — 주기 1,000 us 의 90% 다. 답은 "예 → ✓ (실측 p99 8.5 us) / 아니오 → 잡 실패". 8.5 us 는 상한 900 us 의 약 1/100 이니 여유가 100배다.
- 민트 상자 "get_allex.sh — 위로보틱스 ALLEX 48 자유도 (고정 커밋) / 같은 테스트 바이너리, 프로필의 관절 이름 48개, 주기 2 ms": `scripts/get_allex.sh` 가 지원 회사의 공개 모델(`wirobotics-rih/allex_model`, BSD-3)을 커밋 5e12052 로 고정해 `third_party/allex_model` 에 받는다(약 250 MB — 모델이 바뀌면 숫자도 바뀌므로 커밋을 고정한다). 그다음 같은 `test_mujoco_backend` 바이너리를 환경변수만 바꿔 다시 돈다: `RT_MUJOCO_DOF=48`, `RT_MUJOCO_JOINTS`(`scripts/profile_joints.py robots/allex.yaml` 이 프로필의 관절 이름 48개를 쉼표로 이어 준다), `RT_MUJOCO_PERIOD_US=2000`. 주기가 2 ms 인 이유는 ALLEX 프로필의 기본이 500 Hz 이기 때문(모델의 기본 걸음 2 ms 와 같다, E21).
- 마름모 "1,000주기 동안 움직이고 p99 < 1,800 us (2 ms 의 90%)?": 기준은 SO-ARM100 과 같은 규칙 — 2초 분량(2 ms × 1,000주기)을 돌고, 관절 0(R_Shoulder_Pitch)이 목표의 절반 이상 움직였고, 한 주기 비용 p99 가 주기의 90 % 아래. 주기가 2배니 상한도 2배(900 → 1,800 us)다.
- 화살표 글 "예 → ✓ (러너 p99 510 us) / 아니오 → 잡 실패": 첫 통과(run 42175845461, 11/06)의 러너 실측은 p50 390.1 / p99 510.4 / max 684.6 us — 2 ms 예산의 26 %(p99). 6축의 8.5 us 와 견주면 60배 무겁지만 상한 1,800 의 3분의 1 이다.
- 진한 상자 "✓ JSON 2개 → 아티팩트 mujoco-ci. 셋 다 ✓ 면 README 배지 초록 (2단계 병렬)": 테스트가 결과를 `mujoco_backend_ci.json`(SO-ARM100: 자유도 6, 주기 1000 us, 2000 주기, substeps 1, p50/p99/max, 관절 0 이동량 0.2988 rad)과 `mujoco_backend_allex_ci.json`(ALLEX: 자유도 48, 주기 2000 us, 1000 주기, 이동량 0.2976 rad)에 적고, 두 파일이 아티팩트 `mujoco-ci` 로 남는다(`gh run download <run> -n mujoco-ci`). JSON 의 모델 경로는 `third_party/` 부터만 적는다 — 러너나 개인 PC 의 홈 경로가 측정 파일에 남지 않게. 세 잡이 전부 ✓ 면 README 맨 위의 배지가 초록이 된다. "합계"는 잡 1 → (잡 2 ∥ 잡 3) 의 벽시계 시간을 말한다 — 아래 5절 참고(장표의 2분 20초는 HANDOVER 의 1m13s + 1m52s 와 맞지 않는다).
- 아래 설명 상자 앞부분 "ALLEX 게이트를 운영점(500 Hz)으로 두는 이유: 1 kHz 는 '어디까지 되나'의 측정(E21)이고 CI 는 '운영점에서 통과하나'의 게이트 — 섞으면 러너 상태에 따라 빨개지는 날이 생긴다": ALLEX 를 1 kHz 로 재면 러너 p99 458 us 로 900 us 상한을 넘기지는 않지만(run 42172730308), WSL 에서는 622 us 에 max 가 1 ms 를 넘겼다. 느린 러너를 만나면 1 kHz 게이트는 코드가 안 바뀌어도 빨개질 수 있다. 그래서 CI 는 프로필이 실제로 쓰는 주기(500 Hz)만 묻고, "1 kHz 에서 어디까지 되나"는 실험 페이지(E21)의 표에 둔다.
- 아래 설명 상자 뒷부분: "물리 잡을 따로 둔 이유: MuJoCo 를 빌드 옵션(기본 OFF)으로 두어 MuJoCo 없는 환경(1단계·Pi)에서도 빌드되게 했고, 물리가 있는 환경에서만 '제어 코드 무변경 + 비용 상한'을 다시 확인한다(DECISIONS 11/03 D5)". 즉 잡 1 의 빌드가 성공한다는 것 자체가 "MuJoCo 없이도 빌드된다"의 증명이고, 잡 3 은 "MuJoCo 를 켰을 때도 같은 제어 코드가 돈다"의 증명이다 — 두 잡이 합쳐서 Backend 인터페이스의 주장을 지킨다.

## 3. 용어와 단위

- 헤드리스(headless): 화면(그래픽 창) 없이 돌리는 것. CI 러너에는 모니터가 없으니 물리 계산만 한다.
- MuJoCo: 중력·접촉·모터를 계산하는 물리 엔진. `mj_step` = 물리 시간을 한 걸음 전진시키는 함수. substeps = 제어 한 주기(1 ms)에 `mj_step` 을 몇 번 하나 — 여기서는 모델 걸음(timestep)이 1 ms 이상이라 1번이다.
- Menagerie: Google DeepMind 가 관리하는, 검증된 로봇 모델(MJCF) 모음. `trs_so_arm100` = SO-ARM100 팔(5축 + 그리퍼 = 자유도 6).
- 빌드 옵션(CMake `-D이름=값`): 컴파일할 때 켜고 끄는 스위치. `RT_CORE_WITH_MUJOCO` 가 OFF 면 MuJoCo 관련 파일은 빌드에 포함되지 않는다.
- ctest `-R mujoco`: 이름에 mujoco 가 들어가는 테스트만 고른다.
- p99(99 백분위): 100번 중 99번은 이 값 이내. us = 마이크로초 = 100만분의 1초. 900 us = 0.9 ms.
- rad(라디안): 각도 단위. 1 rad ≈ 57.3°. 0.3 rad ≈ 17°, 0.15 rad ≈ 8.6°.
- 아티팩트: 잡이 끝난 뒤 내려받을 수 있게 남긴 결과 파일(`if-no-files-found: ignore` 라 실패해 파일이 없어도 그 단계는 에러가 아니다).

## 4. 쉬운 예시

- 비유: 잡 1 은 "엔진 없이 차체 조립이 되나"를 보는 검사, 잡 3 은 "엔진을 얹었을 때도 같은 차체에 그대로 맞고, 시동 걸어 2초 달려 보면 바퀴가 돌고 한 바퀴 도는 데 상한 시간 안인가"를 보는 검사다. 엔진(MuJoCo)은 무겁고 내려받아야 하니 매번 모든 검사에 얹지 않고, 전용 검사장(잡 3)에서만 얹는다.
- 숫자 예시: 1 ms 주기 안에서 물리 한 걸음에 평균(p50) 6.4 us, 100번 중 99번은 8.5 us 안, 최악 한 번 29.4 us 걸렸다. 1 ms 를 1,000원짜리 예산이라 치면 물리는 6~30원을 쓴 셈이다. 내 PC(WSL)에서는 p50 4.9 / p99 6.3 / max 20.8 us 로 러너보다 조금 빨랐다 — 둘 다 상한 900 의 수십 분의 1.
- "관절 0 이 0.2988 rad 움직였다": 목표 +0.3 rad 에 2초 만에 거의 다 닿았다(99.6%). 기준 0.15 는 "절반 이상"이라 여유 있게 통과.

## 5. 숫자의 출처와 다시 확인하는 법

- 확인: 주기 수 = 2초 분량(`cycles = 2000000 / period_us` 139행), 합격선 `p99 < 0.9 * budget_us`(189행), 움직임 > 0.15 rad·< 0.6 rad(180~181행), 환경변수 `RT_MUJOCO_DOF/JOINTS/OUT/PERIOD_US`(94~118행) — `rt_control/rt_core/test/test_mujoco_backend.cpp`(11/06 판).
- 확인: ALLEX 러너 500 Hz p50 390.1 / p99 510.4 / max 684.6 us, 이동 0.2976 rad — `docs/measurements/mujoco_backend_allex_ci_500hz_run42175845461.json`. 1 kHz 러너 381.5 / 457.8 / 608.9 — `…_ci_1khz_run42172730308.json`. 잡 시간 48 s — `docs/LOG.md` 11/06.
- 확인: ALLEX 단계의 환경변수와 `pip install --quiet pyyaml`(관절 이름을 뽑는 스크립트가 YAML 을 읽는다) — `.github/workflows/ci.yml` mujoco 잡, `scripts/get_allex.sh`, `scripts/profile_joints.py`, `robots/allex.yaml`.
- 확인: 러너 실측 p50 6.4 / p99 8.5 / max 29.4 us, 관절 0 이동 0.2988 rad, substeps 1 — `docs/measurements/mujoco_backend_ci.json`(모델 경로가 `/home/runner/...` 로 러너의 것). WSL 실측 p50 4.9 / p99 6.3 / max 20.8 — 저장소 루트의 `mujoco_backend_ci.json`.
- 확인: `MUJOCO_VERSION: "3.3.2"`, `needs: rt_core`, `-DRT_CORE_WITH_MUJOCO=ON`, 아티팩트 `mujoco-ci`, 환경 변수 `RT_MUJOCO_MODEL`·`LD_LIBRARY_PATH` — `.github/workflows/ci.yml` 의 mujoco 잡.
- 확인: 잡 시간 "약 45초" — ALLEX 단계가 들어간 뒤 44 s(run 42172730308)·48 s(run 42175845461), `docs/LOG.md` 11/06. ALLEX 전에는 25 s(`docs/HANDOVER.md`).
- 추정 아닌 불일치: 장표의 "합계 약 2분 20초". HANDOVER 의 세 잡 시간(rt_core 1m13s, fleet_integration 1m52s, mujoco 25s)으로 계산하면 잡 1 → 잡 2∥3 의 벽시계 합계는 약 1m13s + 1m52s ≈ **3분 5초**(러너 배정 대기 제외)다. 세 잡 시간의 단순 합은 3m30s. "2분 20초"가 어느 실행의 값인지 저장소에 기록이 없다 — 발표 때는 "약 3분, 2단계 둘은 병렬"이라고 말하는 쪽이 안전하다. `gh run view <ID>` 의 Elapsed 값이 정답이다.
- 다시 보는 법 [WSL 창]: `gh run list -L 3` → `gh run view <ID>` 로 세 잡의 시간. 로컬에서 같은 테스트: `cmake -S rt_control/rt_core -B build/rt_core_mj -DRT_CORE_WITH_MUJOCO=ON -DMUJOCO_DIR=$PWD/third_party/mujoco && cmake --build build/rt_core_mj -j && RT_MUJOCO_MODEL=$PWD/third_party/mujoco_menagerie/trs_so_arm100/so_arm100.xml ctest --test-dir build/rt_core_mj -R mujoco --output-on-failure`.

## 6. 자주 하는 오해·함정

- "CI 러너의 8.5 us 가 실시간 성능 증명"이라는 오해: 러너에는 RT 커널도 RT 권한도 없다. 이 숫자는 "물리 한 걸음이 1 ms 예산의 1/100 급으로 싸다"는 **비용** 증명이고, 지연(지터) 증명은 Pi 실측(표①, 3부)이다. ci.yml 머리말에도 "돌아간다의 증거이지 지연 수치의 증거가 아니다"라고 적혀 있다.
- 잡 1 과 잡 3 의 빌드 폴더가 다르다(`build/rt_core` vs `build/rt_core_mj`). 같은 폴더에 옵션만 바꿔 다시 cmake 하면 캐시가 섞여 엉뚱한 결과가 난다.
- `MUJOCO_VERSION` 은 ci.yml 과 `scripts/get_mujoco.sh` 기본값 두 곳에 있다(ci.yml 주석: "바꾸면 둘 다 바꾼다"). 다운로드 실패의 첫 의심 지점(장표 122).
- 모델 파일은 `so_arm100.xml`(팔만)이지 `scene.xml`(바닥·조명 포함)이 아니다 — WSL 실측 JSON 은 scene.xml 로 돌렸고 러너는 so_arm100.xml 로 돌렸는데 자유도 6, 이동량 0.2988 은 같다.
- 테스트가 실패하면 `if-no-files-found: ignore` 때문에 아티팩트가 비어 있을 수 있다. 실패 원인은 아티팩트가 아니라 `--log-failed` 로그에서 본다.

## 7. 면접 한 문장

"MuJoCo 는 빌드 옵션 기본 OFF 라 1단계와 Pi 는 물리 없이 빌드되고, 세 번째 잡만 MuJoCo 3.3.2 와 SO-ARM100 을 내려받아 헤드리스로 2,000주기를 돌립니다 — 관절이 명령대로 움직였는지와 한 주기 비용 p99 가 900 us 아래인지를 보는데, 실측은 8.5 us 로 상한의 1/100 입니다. 같은 잡이 귀사의 ALLEX 48 자유도도 프로필의 운영점 500 Hz 로 한 번 더 돌립니다 — p99 510 us, 상한 1,800 의 3분의 1 입니다."
