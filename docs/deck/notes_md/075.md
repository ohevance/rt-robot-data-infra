# 장표 075 — ④⑤ 들머리 — TimescaleDB · Grafana: 쌓고, 보이게 한다
*위치: 2부 데이터의 길 · ④⑤ DB·Grafana · 들머리*

## 1. 이 장표가 왜 있나
앞 장표(074)까지로 ③ 수집기 묶음이 끝났다. 수집기는 1초마다 묶음(COPY)으로 `telemetry` 행을 DB 에 넣고, 자기 통계(`collector_stats`)와 일어난 일(`events`)도 남긴다는 것을 알았다. 그러면 다음 질문은 "그 데이터는 **어디에 어떤 꼴로 쌓이고**, 사람은 그것을 **어떻게 보나**?"이다. 2부의 ④ TimescaleDB(시계열 데이터베이스)와 ⑤ Grafana(대시보드 도구)는 "쌓는 곳"과 "보이는 곳"이라 한 묶음으로 다룬다.

이 장표는 그 묶음의 들머리다. 같은 꼴(들어온 것 → 문제 → ◇기준 → 확인 방법 → 결과 → 판단·다음)로, 시간 데이터가 끝없이 쌓이는 문제에 어떤 기준을 세웠고 어떻게 확인했는지를 적는다. 다음 장표(076)가 표 5개와 패널 14개를 펼쳐 보인다.

## 2. 장표를 하나씩 읽기
- 상자 1 "들어온 것"(회색): "1초 묶음(COPY)으로 들어오는 telemetry 행 + events + collector_stats (③)". ③ 묶음에서 넘어온 것. COPY 는 PostgreSQL 에서 여러 행을 한 번에 빠르게 넣는 명령이다(행마다 INSERT 하는 것보다 훨씬 빠르다). 50대 × 1 Hz 면 1초마다 50행이 한 묶음으로 들어오고, 수집기는 자기 통계 한 행(collector_stats)도 매초 남기고, 온라인/오프라인/OTA 같은 사건은 events 에 남긴다.
- 상자 2 "문제": "시간 데이터는 끝없이 쌓인다. 패널 질의가 가벼워야 하고, 대시보드 14개 패널의 SQL 을 손으로 관리하면 리뷰·수정·검사가 안 된다". 문제가 둘이다. 첫째, 텔레메트리는 1초마다 50행씩 영원히 늘어나므로 "최근 5초의 온라인 장치 수" 같은 질의가 표 전체를 뒤지면 점점 느려진다. 둘째, Grafana 대시보드는 패널(그래프 하나하나) 14개의 설정과 SQL 이 수백 줄짜리 JSON 파일인데, 그것을 Grafana 화면에서 손으로 고치면 무엇이 바뀌었는지 git 에서 읽을 수도, 검사할 수도 없다.
- 마름모 3 "기준": "하이퍼테이블·인덱스로 패널 질의가 가볍고, 마이그레이션이 순서대로 적용되고, 패널 JSON 이 코드로 관리되나?". 문제 둘에 기준 셋을 세웠다. (1) 시간으로 자동 분할되는 하이퍼테이블과 (device_id, time) 인덱스로 최근 구간 질의가 전체를 안 뒤지게. (2) 스키마(표 구조)가 바뀔 때 번호 붙인 SQL 파일을 순서대로, 두 번 돌려도 안전하게 적용. (3) 대시보드 JSON 은 사람이 아니라 코드가 만든다.
- 상자 4 "확인 방법"(파란색): "init.sql + migrations 001~003(migrate.py --wait: TCP 로 진짜 붙어 보며 기다림) · make_dashboard.py 가 JSON 생성 · CI 가 JSON 파싱". `fleet/db/init.sql` 이 새 DB 의 전체 스키마를 만들고, 이미 떠 있는 DB 에는 `fleet/db/migrations/` 의 번호 붙은 SQL 을 `migrate.py` 가 순서대로 적용한다. 확인: 지금 `migrations/` 에는 `002_ota.sql`, `003_collector_resilience.sql` 두 파일이 있고 001 은 없다(init.sql 이 바탕이다) — 장표의 "001~003" 은 번호 체계를 가리키는 표현으로 읽는다. `migrate.py --wait N` 은 DB 가 뜰 때까지 1초마다 **TCP 로 실제로 접속해 보며** 기다린다(이유는 아래 "넘어가는 조건"). `fleet/grafana/make_dashboard.py` 가 대시보드 JSON 을 생성하고, CI 는 그 JSON 을 파이썬으로 다시 읽어(파싱) 깨지지 않았는지 확인한다.
- 상자 5 "결과"(민트색): "표 5개(telemetry·events·collector_stats 하이퍼테이블, devices, ota_rollouts). Fleet Overview 14 패널: 온라인·msgs/s·지연·backlog·fw·이벤트·RT p99". 표 5개 중 시간이 축인 셋(telemetry, events, collector_stats)은 하이퍼테이블, 장치별 마지막 상태(devices)와 OTA 배포 요약(ota_rollouts)은 보통 표다. 대시보드 "Fleet Overview" 는 패널 14개로, 온라인 장치 수·초당 메시지·전달 지연·수집기 backlog·펌웨어 버전별 장치 수·이벤트 목록·RT 노드의 깨어남 지연 p99 를 보인다.
- 상자 6 "판단 → 다음"(진한 둥근 상자): "통과 → ⑥ OTA: 올라오는 길은 됐다. 반대 방향(서버 → 장치)으로 펌웨어를 안전하게 내리려면?". 장치 → 브로커 → 수집기 → DB → 대시보드, 즉 "올라오는 길"이 완성됐다. 다음 묶음은 반대 방향인 서버 → 장치(OTA, 무선 펌웨어 갱신)다.
- 아래 줄 "이 묶음의 장표: ② DB 표와 Grafana 패널(1장). 넘어가는 조건: 데이터가 쌓이고 보인다 — CI 1차 실패(TimescaleDB 초기화 경쟁)의 해결이 migrate.py --wait". 이 묶음은 들머리 다음 한 장(076)이다. 넘어가는 조건에 붙은 사고: 11/04 GitHub 첫 push 의 CI 에서 `fleet_integration` 이 깨졌다. TimescaleDB 컨테이너는 처음 뜰 때 임시 서버(유닉스 소켓만)로 init.sql 을 돌린 뒤 끄고 진짜 서버를 다시 띄우는데, 컨테이너 안의 `pg_isready` 는 그 임시 서버에도 "준비됨"이라 답한다. 그 1초 뒤 밖에서 TCP 로 붙은 `migrate.py` 가 "server closed the connection unexpectedly" 로 끊겼다. WSL 에서는 볼륨에 데이터가 이미 있어 init 단계가 없었기에 보이지 않았다. 해결이 "밖에서 실제로 붙어 보기", 즉 `migrate.py --wait`(CI 는 120초)다. 배운 것: 준비 확인은 소비자와 같은 경로로.

## 3. 용어와 단위
- PostgreSQL: 널리 쓰는 관계형 데이터베이스. 표(table)에 행(row)을 넣고 SQL 로 묻는다.
- TimescaleDB: PostgreSQL 에 시계열(시간 순서 데이터) 기능을 더한 확장(extension). 같은 SQL 을 쓴다.
- 하이퍼테이블(hypertable): TimescaleDB 가 시간으로 자동 분할(청크)해 관리하는 표. 겉보기엔 보통 표지만 "최근 5초" 질의가 최근 조각만 읽는다.
- 인덱스: 책 뒤의 색인처럼 특정 열로 빨리 찾게 해 주는 보조 구조. `telemetry (device_id, time DESC)` 는 "이 장치의 최근 행"을 바로 찾게 한다.
- COPY: PostgreSQL 의 대량 적재 명령. 1초 묶음 50행을 한 번에 넣는다.
- 스키마(schema): 표와 열의 구조. 마이그레이션(migration)은 이미 데이터가 있는 DB 의 스키마를 바꾸는 번호 붙은 SQL 파일.
- `--wait`: DB 가 준비될 때까지 기다리는 최대 초. 기본 60, CI 는 120.
- TCP / 유닉스 소켓: 네트워크로 접속하는 길 / 같은 컴퓨터 안에서만 쓰는 접속 길. 수집기는 TCP 로 붙으므로 TCP 로 확인해야 한다.
- Grafana: DB 에 SQL 로 물어 그래프·숫자·표를 보여 주는 대시보드 도구. 패널 = 화면의 그래프 하나. JSON = 그 설정 파일 형식.
- msgs/s: 초당 메시지 수. p99: 100번 중 99번은 이 값 이내(장표 090).

## 4. 쉬운 예시
도서관 비유: 날마다 들어오는 신문(telemetry)을 한 상자에 다 넣으면 "지난주 기사"를 찾을 때 상자를 다 뒤져야 한다. 하이퍼테이블은 월별로 상자를 나눠 두는 것이고, 인덱스는 상자마다 붙인 "신문사별 색인"이다. 마이그레이션은 서가 구조를 바꿀 때 "변경 지시서 002, 003"을 번호 순서로 적용하는 것이며, 이미 적용한 지시서는 장부(`schema_migrations`)에 적어 두어 두 번 하지 않는다. 대시보드 JSON 을 코드로 만드는 것은 게시판의 그래프 14장을 손으로 그리지 않고 "그래프 그리는 법"을 글로 써 두어 누구나 다시 그릴 수 있게 하는 것이다.

숫자 예시: 50대 × 1 Hz = 1초에 50행, 하루면 50 × 86,400 = 4,320,000행이다. "최근 5초 온라인 장치 수" 패널이 5초마다 그 전체를 뒤지면 안 된다 — 하이퍼테이블이 최근 조각만 읽는다. CI 에서 DB 가 뜨는 데 몇 초가 걸릴지 모르므로 `--wait 120` 으로 최대 120초를 1초마다 붙어 보며 기다린다.

## 6. 자주 하는 오해·함정
- "하이퍼테이블은 특별한 표"라는 오해. 겉으로는 보통 PostgreSQL 표이고 SQL 도 같다. 안에서 시간 조각으로 나뉘어 있을 뿐이다.
- "init.sql 이 있으면 migrate 는 필요 없다"는 오해. init.sql 은 컨테이너가 **처음** 뜰 때 한 번만 실행된다. 이미 데이터가 있는 DB 에 표·열을 더할 때는 migrate.py 가 필요하다(새 DB 는 init.sql 하나로 완성되게 002·003 내용이 init.sql 에도 들어 있다).
- 함정(11/04 CI 1차): `pg_isready` 가 "준비됨"이라 해도 믿을 수 없었다. 헬스 체크는 실제 소비자와 같은 경로(TCP)로 해야 한다 — WSL 에서는 재현되지 않아 CI 에서 처음 드러났다.
- "Grafana 화면에서 패널을 고치면 편한데 왜 코드로"라는 의문. 손으로 고친 JSON 은 수백 줄의 차이로만 보여 리뷰가 불가능하고, 다른 PC 에 같은 대시보드를 만들 수 없다. 생성기는 70줄 안에 14개 패널의 SQL 이 다 보인다.
- 장표의 "migrations 001~003" 과 실제 파일(002, 003)의 차이. 001 번 파일은 없다.

## 7. 면접 한 문장
"시계열은 하이퍼테이블과 (장치, 시각) 인덱스로 최근 구간만 읽게 했고, 스키마 변경은 번호 붙은 마이그레이션으로, 대시보드 14개 패널은 생성기 코드로 만들어 CI 가 파싱까지 확인합니다 — CI 첫 실패가 TimescaleDB 초기화 경쟁이어서 준비 확인을 '밖에서 TCP 로 실제로 붙어 보기'로 바꿨습니다."
