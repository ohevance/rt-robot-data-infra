# 장표 059 — 데이터의 길 — 장치에서 대시보드까지 (위에서 아래로)
*위치: 2. 데이터의 길 — 장치에서 대시보드까지*

## 1. 이 장표가 왜 있나
1부(장표 005~058)는 "명령 → 로봇의 움직임"의 길이었고, 그 마지막 단계 10 에서 로봇의 1 Hz 요약이 다리를 건너 관제로 올라갔다(장표 055·056). 이 장표는 2부의 문을 여는 장 구분 장표다 — 다리를 건넌 숫자가 그 뒤 어디를 지나 화면까지 가는지, 그리고 그 길이 **수십 대 규모에서 잃지 않고, 장애와 업데이트를 견디는지**가 2부의 질문이다. 모든 부(장)의 첫 장표가 같은 꼴(`[앞에서 안 것] → ◇[이 장의 질문] → [이 장의 답]` + 차례)이라 발표자는 이 장표에서 "지금까지 → 지금부터"를 한 문장으로 잇고 넘어간다. 공고의 ②(장치-서버 데이터 파이프라인)·③(원격 운영·OTA·장애 대응)에 답하는 부분이기도 하다.

## 2. 장표를 하나씩 읽기
- 큰 번호 "02" 와 제목 "데이터의 길 — 장치에서 대시보드까지 (위에서 아래로)": 2부. "위에서 아래로"는 1부와 같은 읽기 방향 — 데이터가 흐르는 순서대로 장표가 이어진다.
- 부제 "로봇(또는 가상 장치 50대)의 숫자가 MQTT → 수집기 → TimescaleDB → Grafana 로 가고, 서버가 OTA 와 장애를 다루는 길. 목표는 '잃지 않는 것, 잃었으면 세는 것'": 2부의 두 겹 — 데이터가 가는 길(①~⑤)과 서버가 장치를 다루는 길(⑥ OTA, ⑦⑧ 장애). "잃었으면 세는 것"은 유실을 0 이라고 믿는 대신 일련번호로 세어 증명한다는 뜻(E07 의 교훈).
- 흐름 상자 1 "앞에서 안 것 — 로봇의 상태가 1 Hz 요약으로 다리를 건너 관제에 올라간다 (1부 단계 10). 가상 장치 50대도 같은 길": 1부에서 넘어온 것. 2부에서는 RT 노드 하나 대신 가상 장치 50대로 길에 부하를 준다 — 실물이 없어도 서버 쪽을 시험하기 위해.
- 마름모 "이 장의 질문 — 수십 대의 숫자를 잃지 않고 서버까지 가져오고, 장애와 업데이트를 견디나?": 2부가 답할 한 문장. 1부의 질문이 "1 ms 안에"였다면 2부는 "잃지 않고, 견디나".
- 흐름 상자 3 "이 장의 답 — 8단계(6묶음)를 위에서 아래로 — 에이전트 → 브로커 → 수집기 → DB·Grafana → OTA → 장애 주입·판정·진단, 묶음마다 핵심 코드(파일:줄). 기준: 유실 0 · 복구 수초 · 나쁜 펌웨어는 5% 에서 멈춤. 실험(표③, '유실 0' 이 처음엔 가짜였던 이야기)은 3부로": 8단계는 ① 장치 에이전트 ② 브로커 ③ 수집기 ④ DB ⑤ Grafana ⑥ OTA ⑦ 장애 주입 ⑧ 판정·진단이고, 장표에서는 ④⑤ 와 ⑦⑧ 을 한 묶음씩 묶어 6묶음이다. 기준 셋은 표③의 합격선. 실험 이야기(E05 → E13)는 1부처럼 3부로 미룬다.
- 차례 1 "① 장치 에이전트 → ② 브로커 → ③ 수집기 → ④⑤ DB·Grafana → ⑥ OTA 배포기 → ⑦⑧ 장애 주입·판정·진단": 장표 번호로는 그림 두 장(060 한 장 그림, 061 토픽·설정 그림) 뒤에 ① 062~066, ② 067~068, ③ 069~074, ④⑤ 075~076, ⑥ 077~081, ⑦⑧ 082~085.
- 차례 2 "묶음마다 들머리(들어온 것 → 문제 → 기준 → 확인 → 결과 → 판단) → 핵심 코드. 실험(E05 → E13, 표③)은 번호만 적고 3부로": 1부와 같은 세 층 구조. 2부의 코드 장표는 10장(에이전트 2, 브로커 설정 1, 수집기 3, OTA 3, 유실 SQL 1).
- 차례 3 "→ 다음: 1·2부에서 '확인 → 장표 N' 으로 미뤄 둔 시험들을 단계 순서대로 본다 (3부 검증)": 2부가 끝나면 3부(086~100)로.

## 3. 용어와 단위
- 관제 / 데이터의 길: 여러 장치의 숫자를 서버로 모아 저장하고 보여 주는 일 / 그 숫자가 지나는 구성 요소의 순서.
- MQTT / 브로커(Mosquitto): 가벼운 발행-구독 메시지 규약 / 메시지를 중계하는 서버 프로그램. 장치는 브로커에만 연결한다.
- 수집기(collector): 브로커에서 받아 1초 묶음으로 DB 에 넣는 파이썬 프로그램.
- TimescaleDB / Grafana: 시계열 확장을 얹은 PostgreSQL / 그 DB 를 SQL 로 그려 보여 주는 화면 도구(패널 14개).
- OTA(Over-The-Air): 네트워크로 펌웨어를 배포하는 것. 여기서는 5% → 50% → 100% 단계 배포와 헬스 게이트(아픈 장치가 보이면 전부 되돌림).
- 장애 주입(fault injection): 브로커·DB·수집기를 일부러 10초 멈추거나 나쁜 펌웨어를 보내 감지·복구·유실을 재는 것(4종).
- 유실 / 일련번호(seq): 받아야 했는데 못 받은 메시지 수 / 장치가 메시지마다 붙이는 번호. 빠진 번호 = 유실. "잃었으면 세는 것"의 도구.
- 복구 수초: 장애 해제 → 전 장치 데이터가 다시 들어오기까지 1.4~2.9초(표③-2).
- 표③: 관제 실측 표 셋 — 처리량·지연(③-1), 장애 4종(③-2), OTA(③-3). `docs/measurements/table3.md`.

## 4. 쉬운 예시
- 비유: 1부는 "운전자가 핸들을 돌려 차가 움직이는 과정", 2부는 "택시 50대의 위치·속도가 1초마다 회사 관제실 화면에 찍히고, 무선이 끊겨도 나중에 다 들어오며, 새 앱을 깔 때 5대에 먼저 깔아 보고 문제가 있으면 나머지 45대에는 안 까는" 운영의 길이다.
- 숫자 예시: 가상 장치 50대 × 1 Hz = 초당 50개. 브로커가 10초 죽으면 500개가 위험한데, 장치가 모아 두었다가 재전송해 유실 0 / 1400(고치기 전엔 53 / 1434). 나쁜 펌웨어는 5% = 3대에서 fault 가 보여 1.0초에 롤백, 47대는 명령을 받은 적도 없다.

## 6. 자주 하는 오해·함정
- 2부의 "장치"는 대부분 가상 장치 50대다. 실물 로봇은 1부 단계 10 의 다리로 51번째 장치가 되어 같은 길을 쓴다 — 2부의 숫자는 서버 쪽 설계의 숫자이고 로봇의 숫자가 아니다.
- "유실 0" 은 처음 측정에서도 0 으로 나왔지만 그것은 기준점이 틀린 가짜 0 이었다(E07). 2부가 "잃었으면 세는 것"을 목표에 넣은 이유이고, 그 이야기는 3부에서 한다. 발표 때 2부에서는 결과 숫자만 말하고 "왜 믿을 수 있나"는 미룬다.
- 1부와 2부는 데이터의 종류가 다르다. 1부 단계 9 의 기록(rosbag2, 100 Hz 원본, 로봇 안 파일)과 2부의 관제(MQTT, 1 Hz 요약, 서버)는 다른 길이다(장표 053).
- 2부 ①~⑤ 는 "흐르는 길", ⑥~⑧ 은 "서버가 장치를 다루는 길"이라 방향이 반대다(서버 → 장치 명령). 한 장 그림(060)에서 화살표 방향을 보면 구분된다.

## 7. 면접 한 문장
"2부는 로봇(과 가상 장치 50대)의 1 Hz 숫자가 MQTT → 수집기 → TimescaleDB → Grafana 로 가는 길과 서버가 OTA·장애를 다루는 길을 8단계로 보여 주며, 기준은 유실 0 · 복구 수초 · 나쁜 펌웨어는 5% 에서 멈춤입니다 — 그리고 '유실 0' 을 믿지 않고 일련번호로 세어 증명했습니다."
