# 장표 116 — 가짜 브로커·가짜 DB — 컨테이너 없이 1초 만에 도는 단위 테스트의 바닥
*위치: 6부 믿을 수 있나 · 테스트 — 가짜 브로커·DB*

## 1. 이 장표가 왜 있나
앞 장표(115)는 이 저장소의 테스트 20건 목록이었다. 그중 Python 단위 테스트 15건(가상 장치·OTA·수집기 논리)은 "가짜 브로커·가짜 DB 위에서 돈다"고 적혀 있었다. 그러면 질문이 생긴다. "진짜 Mosquitto 와 PostgreSQL 없이 어떻게 수집기와 에이전트를 테스트하나, 그리고 그 결과를 얼마나 믿을 수 있나?"

이 장표는 그 바닥(가짜 두 개)을 설명한다. 왼쪽은 MQTT 라이브러리 paho 를 흉내 내는 `fake_mqtt.py`, 오른쪽은 PostgreSQL 라이브러리 psycopg 를 흉내 내는 `fake_psycopg.py` 다. 둘 덕분에 컨테이너 없이 1초 만에 단위 테스트가 돌고, 그래서 CI 1단계(rt_core 잡)와 작성 보조 작업본(샌드박스, 네트워크 없음)에서도 테스트가 된다. 동시에 아래 각주가 그 한계를 못 박는다. 가짜 위에서 통과한 것은 "논리가 맞다"이지 "진짜 위에서도 된다"가 아니고, 그래서 CI 2단계(진짜 컨테이너)가 따로 있다.

## 2. 장표를 하나씩 읽기
두 칸(two_col) 꼴이다. 왼쪽 칸의 머리와 글머리표 네 줄, 오른쪽 칸의 머리와 글머리표 네 줄, 마지막에 아래 각주 순서로 읽는다.

- 왼쪽 머리 "fleet/tests/fake_mqtt.py (209줄)": 파일 위치와 길이. `wc -l` 로 209줄이다.
- 왼쪽 첫 줄 "install(): paho.mqtt.client.Client 를 가짜 클래스로 바꿔치기 — 수집기·에이전트 코드는 자기가 가짜 위에 있는 줄 모른다": 테스트 파일 맨 위에서 `fake_mqtt.install()` 을 부르면 파이썬의 모듈 목록(`sys.modules`)에 `paho.mqtt.client` 라는 이름으로 이 가짜 모듈을 끼운다. 그 뒤 수집기나 에이전트가 `import paho.mqtt.client` 를 하면 가짜가 들어온다. 수집기 코드는 한 줄도 바꾸지 않는다 — 진짜와 가짜가 같은 함수 이름(`Client`, `connect`, `publish`, `subscribe`, `loop_start`)을 가지기 때문이다.
- 왼쪽 둘째 줄 "FakeBroker: 토픽 와일드카드(+, #) 구독, 보관(retained) 메시지, publish 즉시 콜백 전달": 프로세스 안의 "브로커 한 대". MQTT 의 토픽 와일드카드(`+` 는 한 단계, `#` 은 그 아래 전부)를 지원하고, retain 플래그가 붙은 메시지는 보관해 두었다가 새로 구독하는 쪽에 즉시 준다. `publish` 는 네트워크 없이 그 자리에서(동기로) 모든 구독자의 `on_message` 를 부른다 — 그래서 빠르다.
- 왼쪽 셋째 줄 "crash() / disconnect_all() / reconnect_all(): 브로커 죽음·재접속을 흉내 → 버퍼·재전송·유언 시험": `crash(client)` 는 장치가 갑자기 죽은 상황 — 브로커가 그 장치의 유언(LWT, 미리 맡겨 둔 "나 죽었어요" 메시지)을 발행한다. `disconnect_all()` 은 브로커가 죽은 상황 — 모두 끊고 `on_disconnect` 를 부른다. `reconnect_all()` 은 브로커가 돌아온 상황 — 모두 다시 붙이고 `on_connect` 를 부른다(paho 의 자동 재접속에 해당). 이 셋으로 2부의 "장치 쪽 버퍼(store-and-forward) → 재접속 뒤 재전송", "유언으로 오프라인 감지"를 컨테이너 없이 시험한다.
- 왼쪽 넷째 줄 "QoS 와 clean_session 인자를 기록해 '지속 세션으로 붙었나'를 검사할 수 있다": `FakeClient` 는 생성 때 받은 `clean_session` 과 `publish`·`subscribe` 의 QoS 를 기록한다. 그래서 테스트가 "수집기가 `--qos 1` 이면 지속 세션(`clean_session=False`)으로 붙고 QoS 1 로 구독했나"를 확인할 수 있다(`test_persistent_session_option`).
- 오른쪽 머리 "fleet/tests/fake_psycopg.py (120줄)": 파일 위치와 길이, 120줄.
- 오른쪽 첫 줄 "connect/cursor/execute/copy 를 흉내. STORE 딕셔너리에 telemetry 행이 쌓인다": psycopg 의 `connect(dsn)` → 커넥션 → `cursor()` → `execute(sql)` / `copy(sql)`(대량 적재) 를 같은 모양으로 제공한다. DB 대신 `STORE` 라는 파이썬 딕셔너리에 행이 쌓이고(`telemetry`, `events`, `devices`, `collector_stats`, 실행된 SQL 목록 `executed`), 테스트가 그 수를 세어 본다.
- 오른쬭 둘째 줄 "FAIL 스위치: 'write' 를 켜면 COPY 가 예외 → backlog 경로, 'schema_old' 면 003 미적용 스키마 → check_schema False": `FAIL` 딕셔너리의 스위치 셋(`connect`, `write`, `schema_old`). `FAIL["write"] = True` 면 `execute` 와 `copy` 가 `OperationalError`("connection lost")를 던져 수집기가 backlog(메모리에 밀어 두는 경로)로 가게 만든다 — DB 죽음을 흉내 내는 방법이다. `FAIL["schema_old"] = True` 면 `SELECT backlog_rows …` 에 "column does not exist" 오류를 던져, 마이그레이션 003(collector_stats 에 backlog 열 추가)이 적용되지 않은 옛 DB 를 흉내 낸다 — 수집기의 `check_schema` 가 False 를 돌려주고 안내 후 종료해야 한다.
- 오른쪽 셋째 줄 "test_collector_resilience: DB 죽음 → backlog 에 남음 → 복귀 → 오래된 것부터 전부, 순서 유지 → 상한 넘기면 가장 오래된 묶음 버림": 수집기 내성 테스트 파일이 가짜 둘 위에서 확인하는 흐름. 쓰기가 실패하면 1초 묶음이 backlog 에 남고 `db_errors` 가 센다(버리지 않는다). DB 가 돌아오면 다음 flush 에서 오래된 묶음부터 전부 들어가고 순서가 유지되며 backlog 가 0 이 된다. `MAX_BACKLOG_ROWS` 를 넘으면 가장 오래된 묶음을 버리고 `backlog_dropped` 로 센다(DECISIONS 11/03 "backlog 는 메모리, 상한을 두고 버린다"). 2부의 DB 장애 실험(장표 2부 ⑦⑧ 검증)에서 진짜로 본 것과 같은 논리다.
- 오른쪽 넷째 줄 "11/05 추가: main() 한 바퀴 스모크 — 인자 → 잠금 → 시그널 핸들러 등록 → 루프 0바퀴 → shutdown (request_stop 누락을 잡는다)": 11/05 CI 에서 수집기의 `request_stop` 함수가 지워진 채 push 되어 수집기가 시작 직후 `NameError` 로 죽었다. 단위 테스트가 `main()` 을 한 번도 타지 않아서 통합 테스트(2단계)에서만 드러났다. 그래서 `test_main_entry_smoke` 를 추가했다 — STOP 플래그를 미리 세워 두고 `main()` 을 부르면 인자 해석 → 잠금 → 시그널 핸들러 등록 → 루프 0바퀴 → shutdown 을 거쳐 0 으로 끝나야 한다. 시그널 핸들러 `request_stop` 도 직접 불러 본다.
- 아래 각주 "가짜 위에서 통과한 것은 '논리가 맞다'이지 '진짜 위에서도 된다'가 아니다 — 그래서 CI 2단계(진짜 컨테이너)가 따로 있다. DECISIONS 11/03 (D4) 'CI 는 2단계: 가짜로 빠르게, 진짜로 한 번'": 가짜의 한계와 그 보완. 가짜는 네트워크 지연·타이밍·컨테이너 준비 순서 같은 "환경"을 흉내 내지 못한다. 11/04 의 TimescaleDB 임시 서버 문제가 그 예다 — 가짜로는 영원히 못 잡는다. 그래서 1단계는 가짜로 1분 안에 논리를, 2단계는 진짜 컨테이너로 한 번 환경을 검사한다.

## 3. 용어와 단위
- 단위 테스트(unit test): 프로그램의 작은 부분(함수·모듈)을 따로 떼어 빠르게 검사하는 테스트. 통합 테스트는 진짜 구성 요소를 다 붙여 검사한다.
- 가짜(fake) / 스텁(stub): 진짜 구성 요소와 같은 인터페이스로 동작을 흉내 내는 테스트용 코드. 상태를 갖고 그럴듯하게 동작하면 fake, 정해진 값만 돌려주면 stub 이라 부른다.
- MQTT: 장치가 짧은 메시지를 토픽(주소) 단위로 주고받는 경량 프로토콜. 브로커가 가운데에서 중계한다.
- 브로커(broker): MQTT 메시지를 받아 구독자에게 전달하는 서버. 진짜는 Mosquitto(컨테이너 fleet_mqtt).
- paho: 파이썬용 MQTT 클라이언트 라이브러리(`paho.mqtt.client`).
- 토픽 와일드카드: `fleet/+/telemetry` 의 `+` 는 한 단계 아무 값, `fleet/#` 의 `#` 은 그 아래 전부.
- retain(보관) 메시지: 브로커가 토픽의 마지막 메시지를 기억해 새 구독자에게 바로 주는 것.
- 유언(LWT, Last Will and Testament): 클라이언트가 접속할 때 미리 맡기는 메시지. 비정상 종료로 끊기면 브로커가 대신 발행한다. 오프라인 감지에 쓴다.
- QoS(MQTT): 전달 보장 등급. 0 은 보장 없음, 1 은 최소 한 번.
- clean_session=False(지속 세션): 끊겨도 브로커가 구독과 밀린 메시지를 기억해 두는 세션. 수집기가 잠깐 죽어도 유실이 0 이 되는 근거.
- psycopg: 파이썬용 PostgreSQL 라이브러리. `connect` → `cursor` → `execute` / `copy`.
- COPY: PostgreSQL 에서 여러 행을 한 번에 넣는 빠른 적재 명령. 수집기가 1초 묶음을 이것으로 넣는다.
- backlog: DB 에 아직 못 넣어 수집기 메모리에 밀어 둔 행. `MAX_BACKLOG_ROWS` 가 상한.
- 스키마(schema) / 마이그레이션 003: DB 표의 구조와 그것을 바꾸는 번호 붙은 SQL. 003 은 `collector_stats` 에 backlog 열을 더한 것.
- 스모크 테스트(smoke test): "켜 보니 연기가 나나"만 보는 가벼운 테스트. 깊이는 없지만 진입점이 깨진 것을 잡는다.
- 1초: 장표 제목의 "1초 만에"는 가짜 위 단위 테스트 전체가 도는 시간의 어림이다(네트워크·디스크가 없으므로).

## 4. 쉬운 예시
- 비유: 비행기 조종사 훈련용 시뮬레이터다. 진짜 비행기 없이 조종 절차(논리)를 수백 번 연습하고, 엔진 꺼짐(DB 죽음)·관제 교신 끊김(브로커 죽음)도 버튼 하나로 만든다. 그러나 시뮬레이터에서 완벽해도 진짜 비행(통합 테스트)을 한 번은 해야 한다 — 바람·진동·실제 기체의 반응은 시뮬레이터가 다 흉내 내지 못한다.
- 숫자 예시: `test_db_outage_and_recovery` 는 가짜 장치가 1초 묶음을 몇 개 보낸 뒤 `FAIL["write"] = True` 로 DB 를 죽이고, 그 사이 들어온 묶음이 `STORE["telemetry"]` 에는 안 쌓이고 수집기의 backlog 에만 남는지 센다. `FAIL["write"] = False` 로 살리면 다음 flush 에서 전부 들어가 `STORE["telemetry"]` 의 행 수가 보낸 수와 같아지고 backlog 는 0 이 된다. 진짜 컨테이너에서 같은 실험을 하면(E06, CI 2단계) 유실 0 / 1341 같은 숫자로 나온다.

## 6. 자주 하는 오해·함정
- "가짜로 통과했으니 진짜도 된다": 가짜는 환경(타이밍·네트워크·컨테이너 준비)을 흉내 내지 못한다. 11/04 TimescaleDB 임시 서버 문제, 11/05 `request_stop` 누락은 둘 다 진짜(CI 2단계)에서만 드러났다.
- "가짜가 있으면 통합 테스트는 필요 없다" 의 반대도 틀렸다: 통합 테스트만 있으면 매번 컨테이너를 띄워 3~4분이 들고, 어디가 깨졌는지(논리 vs 환경)를 가르기 어렵다. 1단계가 통과했는지로 먼저 가른다.
- "수집기 코드에 테스트용 분기가 들어가 있다": 아니다. `install()` 이 모듈을 바꿔 끼우므로 수집기는 자기가 가짜 위에 있는 줄 모른다. 테스트가 제품 코드를 오염시키지 않는다.
- 함정(실제로 겪은 것): 진입점 `main()` 을 단위 테스트가 한 번도 안 타서 함수 하나가 지워진 것을 못 잡았다(11/05). 스모크 테스트 한 건이 그 구멍을 막는다.

## 7. 면접 한 문장
"paho 와 psycopg 를 같은 인터페이스의 가짜로 바꿔 끼워 컨테이너 없이 1초 만에 단위 테스트 15건을 돌리고, DB 죽음·브로커 죽음·옛 스키마를 스위치 하나로 만들었다 — 다만 가짜 위의 통과는 '논리가 맞다'까지라서 진짜 컨테이너 위의 2단계를 따로 둔다."
