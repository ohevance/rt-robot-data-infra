# 장표 110 — ② Raspberry Pi 4 — 측정이 유효하려면 (확인 5가지, 하나라도 아니면 그 숫자는 버린다)
*위치: 5부 어디서 · ② Pi 4 측정 유효 조건*

## 1. 이 장표가 왜 있나
앞 장표(109)는 ① 개발 PC 의 "정상 신호"였다. 이번에는 ② Raspberry Pi 4 다. Pi 는 이 저장소에서 표①(실시간 깨어남 지연)의 진짜 숫자를 재는 유일한 곳이고, 그 숫자는 포트폴리오의 핵심이다. 그래서 질문이 하나 더 엄격해진다. "그 측정이 유효한 조건에서 이루어졌나?" 실시간 커널이 켜져 있지 않았거나, CPU 가 격리되지 않았거나, 클럭이 흔들렸거나, 보드가 뜨거워 클럭이 내려간 상태였다면 그 숫자는 커널의 성능이 아니라 환경의 잡음이다.

이 장표는 측정 전후에 확인하는 다섯 가지와, 하나라도 어긋나면 그 숫자를 버린다는 규칙이다. 표①의 14줄 전부에 "스로틀 0" 이 붙어 있는 이유가 이 장표다. 5부의 마지막 장표이기도 해서, 아래의 "다음 ▶" 다리가 6부(이 숫자들을 어떻게 믿나)로 넘긴다.

## 2. 장표를 하나씩 읽기
표의 열은 넷이다. "확인"은 무엇을, "명령"은 Pi 창에서 치는 것, "정상"은 나와야 하는 값, "아니면"은 어긋났을 때의 조치다. 행을 위에서 아래로 읽는다.

- 행 1 "RT 커널인가": 명령은 "uname -r; cat /sys/kernel/realtime" — 커널 이름과 실시간 플래그 파일을 본다. 정상은 "…-raspi-realtime / 1" — 커널 이름이 `-raspi-realtime` 으로 끝나고(실측에서는 `6.8.0-2054-raspi-realtime`), `/sys/kernel/realtime` 이 1 이어야 한다. 이 파일은 PREEMPT_RT 커널에만 있다. 아니면 "pro enable realtime-kernel --variant=raspi, 재부팅" — Ubuntu Pro 로 실시간 커널을 다시 켜고 재부팅한다. 11/05 에 이 명령으로 켰고 약 2분 걸렸다.
- 행 2 "격리": 명령은 "cat /sys/devices/system/cpu/isolated" — 격리된 CPU 번호 목록. 정상은 "3" — CPU 3 하나가 격리되어 있어야 한다. 아니면 "/boot/firmware/cmdline.txt 끝에 isolcpus=3 nohz_full=3 rcu_nocbs=3" — 커널 부팅 인자 파일의 한 줄 끝에 세 인자를 덧붙이고 재부팅한다. `isolcpus=3` 은 CPU 3 을 일반 스케줄링에서 떼고, `nohz_full=3` 은 그 CPU 의 주기적 틱을 줄이고, `rcu_nocbs=3` 은 RCU 콜백 처리를 다른 CPU 로 보낸다. 이 설정이 max 311 → 189 us 를 만들었다(장표 095).
- 행 3 "클럭 고정": 명령은 "cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor" — CPU 주파수 정책. 정상은 "performance" — 항상 최고 클럭으로 고정. 기본값 ondemand 는 한가하면 클럭을 내리고 바빠지면 올리는데, 그 전환에 시간이 걸려 깨어남 지연에 잡음이 섞인다. 아니면 "echo performance | sudo tee …/scaling_governor" — 모든 CPU 의 governor 파일에 performance 를 써 넣는다(재부팅하면 돌아가므로 측정 전마다 확인한다).
- 행 4 "열·스로틀": 명령은 "cat /sys/class/thermal/thermal_zone0/temp; cat /sys/devices/platform/soc/soc:firmware/get_throttled" — 온도(밀리도, 예 51608 = 51.6 °C)와 펌웨어의 스로틀 플래그. 정상은 "시작 50 °C 아래, 플래그 0" — 측정을 시작할 때 50 °C 아래여야 120초 부하 동안 80 °C 를 넘지 않고, 플래그가 0 이어야 부팅 후 한 번도 클럭이 내려간 적이 없다는 뜻이다. 아니면 "식힌다. 플래그 ≠ 0 이면 그 측정은 버린다" — 온도가 높으면 기다려 식히고, 플래그가 0 이 아니면 이미 클럭이 내려간 적이 있으므로 그 측정값은 버린다. 비트 뜻은 장표 113(0x4 지금 스로틀 중, 0x8 지금 온도 제한 중, 0x40000·0x80000 이력).
- 행 5 "결과 판단": 명령은 "각 스크립트 끝의 temp: a -> b mC | throttled: 0" — 측정 스크립트(`jitter_run.sh`, `cyclictest_run.sh`)가 끝날 때 찍는 한 줄. 측정 전 온도 a 와 후 온도 b(밀리도)와 스로틀 플래그다. 정상은 "0" — 플래그가 0. 아니면 "0 아니면 재측정" — 측정 중에 클럭이 내려갔다는 뜻이므로 식힌 뒤 다시 잰다. 같은 값이 `.meta` 파일에도 남아 `make_table1.py` 가 표의 비고 칸에 "온도 a→b °C, 스로틀 0" 또는 "⚠ 스로틀" 로 옮긴다.
- 아래 글 "측정하는 동안 Pi 는 측정 외의 일을 하지 않는다(11/10 부터는 에이전트 서비스가 상시 돈다 — 표①을 다시 잴 때는 서비스를 멈추고 잰다). 11/04~05 실측: 부하 75초에 45 → 75 °C(방열판 없음) → 부하 측정 120초 상한. 출처: docs/ENVIRONMENT.md §4, docs/SETUP_RT_MEASURE.md": 표①을 잰 11/04~05 에는 Pi 에 ROS 2·Docker 가 없고 다른 프로그램도 돌지 않았다. 11/10 부터는 Pi 가 장치 에이전트(`pi_agent.py`, 사용자 서비스 `rt-pi-agent`)를 계속 돌려 서버에 1 Hz 로 보고하고 새 릴리스를 스스로 확인한다. 가벼운 프로그램이지만 **측정 조건이 달라진 것**이므로, 표①을 다시 잴 때는 서비스를 멈추고(`systemctl --user stop rt-pi-agent`) 잰 뒤 다시 켠다 — 표①의 14줄은 모두 서비스가 없던 때의 값이다. 방열판 없는 Pi 4 가 부하 75초에 45 → 75 °C 까지 올라간 것을 보고 부하 측정을 120초까지로 제한했다(한가 측정은 300초). 80 °C 가 스로틀 경계이므로 120초면 그 아래에서 끝난다.
- "다음 ▶" 다리 "6부 — 환경과 '정상 신호'를 알았다. 이 숫자들을 누가, 무엇으로, 언제 다시 재나? (측정 스크립트 · 테스트 37건 · CI 3잡)": 5부가 끝나고 6부로 넘어가는 이유다. 어디서 재는지는 알았으니, 그 숫자가 사람 손이 아니라 스크립트·테스트·CI 로 다시 만들어진다는 것을 보여 주러 간다.

## 3. 용어와 단위
- PREEMPT_RT / 실시간 커널: 리눅스 커널을 거의 모든 곳에서 선점 가능하게 바꾸는 패치. Ubuntu 에서는 Ubuntu Pro 의 `realtime-kernel` 로 설치한다.
- /sys: 커널이 자기 상태를 파일처럼 보여 주는 가상 파일 시스템. `cat` 으로 읽고 `echo … | sudo tee` 로 쓴다.
- isolcpus / nohz_full / rcu_nocbs: 커널 부팅 인자 세 개. 한 CPU 를 일반 작업·주기 틱·RCU 콜백에서 떼어 낸다.
- cmdline.txt: Raspberry Pi 의 커널 부팅 인자 파일(`/boot/firmware/cmdline.txt`). 한 줄짜리 파일이라 끝에 덧붙인다.
- governor(scaling_governor): CPU 주파수를 정하는 정책. performance 는 최고 클럭 고정, ondemand 는 부하에 따라 변동.
- 밀리도(m°C): 1,000분의 1 도. 51608 = 51.608 °C. `temp` 파일은 이 단위로 정수를 준다.
- 스로틀(throttling): 온도가 80 °C 를 넘으면 Pi 펌웨어가 클럭을 내리는 것. 그 상태의 지연은 "커널 때문"과 "클럭 때문"을 가를 수 없다.
- get_throttled: Pi 펌웨어의 스로틀 상태 플래그(16진수 비트). 0 이면 부팅 후 한 번도 없었다.
- .meta: 측정 결과 옆에 스크립트가 남기는 조건 기록 파일(커널·부하·vm 크기·우선순위·온도 전후·스로틀).
- us(마이크로초): 100만분의 1초. 189 us = 0.189 ms.

## 4. 쉬운 예시
- 비유: 혈압을 재기 전의 조건이다. 측정 직전에 뛰어 왔거나(온도 높음), 팔을 심장보다 높이 들었거나(클럭 변동), 다른 사람의 혈압계 설정이 남아 있으면(RT 커널 아님) 그 수치는 내 혈압이 아니다. 간호사가 "5분 앉아 쉬고, 팔은 책상 위에, 기계는 영점 확인"을 매번 하는 것과 같다. 다섯 가지 중 하나라도 어긋나면 수치를 적지 않고 다시 잰다.
- 숫자 예시: 11/04 일반 커널 부하 측정에서 온도가 50.1 → 75.0 °C 로 올라갔다(표①의 `pi4_generic_stress` 비고). 80 °C 까지 5 °C 남은 상태에서 끝났다. 만약 300초를 돌렸다면 80 °C 를 넘어 플래그에 0x4 가 켜지고 그 줄은 버렸을 것이다. 그래서 상한을 120초로 정했다.

## 6. 자주 하는 오해·함정
- "11/10 뒤의 Pi 로 표①을 그대로 다시 재도 된다": 에이전트 서비스가 1초마다 깨어 일한다. CPU 3 은 격리되어 있어 영향이 작을 것으로 보지만(추정 — 재 보지 않았다), 조건이 다른 숫자를 같은 표에 넣지 않으려고 멈추고 잰다.
- "RT 커널을 깔았으니 켜져 있다": 설치와 부팅은 다르다. 재부팅 뒤 어떤 커널로 올라왔는지는 `uname -r` 과 `/sys/kernel/realtime` 으로 매번 확인한다.
- "governor 는 한 번 바꾸면 유지된다": 재부팅하면 기본값으로 돌아간다. 측정 전마다 확인한다.
- "온도가 80 °C 를 안 넘었으면 괜찮다": 플래그는 "부팅 후 한 번이라도"를 기억한다. 이전 측정에서 넘었으면 지금 측정도 플래그가 0 이 아니다. 그래서 플래그로 판단하고, 필요하면 재부팅해 플래그를 지운다.
- "스로틀이 걸려도 숫자가 나쁘게 나올 뿐이다": 문제는 나쁘게 나오는 것이 아니라 원인을 가를 수 없게 되는 것이다. 커널을 바꾼 효과를 재는 실험에서 클럭이 섞이면 실험이 성립하지 않는다.
- 함정(실제로 겪은 것): 두 측정 스크립트가 쓰는 부하의 메모리 버퍼 크기가 달랐다(512M vs 256M). 온도·스로틀처럼 "조건"을 `.meta` 에 적지 않았다면 알아낼 수 없었다(11/05, 장표 114).

## 7. 면접 한 문장
"Pi 4 의 숫자는 다섯 가지 조건 — 실시간 커널, CPU 3 격리, 클럭 고정, 시작 온도 50 °C 아래, 스로틀 플래그 0 — 을 전부 통과한 측정만 표에 올렸고, 하나라도 어긋나면 그 숫자는 버렸다. 표①의 14줄 전부에 '스로틀 0' 이 붙어 있는 이유다."
