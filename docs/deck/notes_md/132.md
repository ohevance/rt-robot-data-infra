# 장표 132 — 남은 일 — 지원(11/17)까지, 그리고 그 뒤
*위치: 7부 왜·사고·방식 · 남은 일*

## 1. 이 장표가 왜 있나

앞 장표(131)는 "무엇이 작성자의 것인가"를 답하면서 "그래서 분석 기간이 있다"고 끝났다. 이 장표는 그 남은 일을 **우선순위 순으로** 적고, 면접에서 "다음 단계는?"이라는 질문에 꺼낼 선택 과제를 따로 둔다. 포트폴리오는 어느 날의 스냅샷이지 끝이 아니다 — 무엇이 끝났고(코드·측정·문서·CI 가 서로 맞는 상태, 첫 정식 릴리스 게시) 무엇이 남았는지(자율 업데이트 확인, 영상, 분석 기간, 서류)를 밝혀야 "지금 상태"라는 말이 뜻을 가진다. 이 장표는 11/11 에 다시 썼다 — 11/05 의 "남은 일" 가운데 끝난 것을 빼고, 11/10~11 에 생긴 것을 넣었다. 다음 장표(133)는 면접에서 바로 꺼내 쓰는 한 문장 12개다.

## 2. 장표를 하나씩 읽기

글머리표 두 묶음(굵은 제목 + 하위 항목)과 오른쪽 아래 설명 상자.

첫 묶음 "지원 전 (우선순위 순)":
- "Pi 의 첫 자율 업데이트(v0.9.0, 새벽 03~05시)와 연속 기록을 다음 날 아침에 세어 확인 → E22 · 이 장표의 숫자 갱신": 가장 먼저 할 일이고, 기다리면 되는 일이다. 11/11 오전에 정식 릴리스 v0.9.0 이 게시됐다. 실물 Pi 의 에이전트는 10분마다 "최신 정식 릴리스"의 매니페스트를 읽고, 새 버전이면 **03~05시 사이에, 상태가 정상일 때만** 스스로 내려받아 설치한다(장표 137 의 자율 모드). 그러니 첫 자율 설치는 다음 날 새벽에 일어나야 한다. 아침에 볼 것은 셋 — 대시보드의 펌웨어 버전이 0.9.0 인가, Pi 의 슬롯 기록(`state.json`)이 그 시각을 적었나, 서버가 센 연속 기록(`soak_report.sh`)에 유실이 없나. 확인되면 E22 와 장표 139 · 140 의 숫자를 갱신한다. 이 줄을 쓰는 시점에는 **아직 일어나지 않은 일**이다.
- "2분 영상 — 대본 v2·자막 상자(cue.sh)·순서표(CHEATSHEET) 준비됨. 원테이크 직접 타이핑 + Clipchamp TTS": 재료는 다 있다 — `docs/VIDEO_SCRIPT.md`(v2, 장면 6개 + 제목 카드, 내레이션 약 770자), `docs/video/cue.sh`(터미널에 자막 상자를 띄우는 스크립트), `docs/video/CHEATSHEET.md`(칠 명령 순서표). 녹화는 자동화 없이 작성자가 직접 명령을 치는 원테이크, 목소리는 Clipchamp 의 텍스트 음성 변환(TTS)으로 얼굴·육성 없이.
- "작성자의 분석 기간 5회차 — 표① 사슬 → 제어·물리 → 관제 → 장애 → OTA·CI·릴리스. 각 회차 끝에 혼자 하는 과제 1건(예: 2 kHz 측정 줄 추가, 테스트 1개, 패널 1개)": 이 장표 147장과 설명 문서를 교재로 작성자가 다섯 번에 걸쳐 직접 설명해 본다. 회차 순서는 저장소의 길과 같다 — ① 표① 사슬(1 ms 루프, Pi 실측), ② 제어 단계와 물리(ControlStep, MuJoCo), ③ 관제(브로커·수집기·DB), ④ 장애 주입·판정, ⑤ OTA 와 CI, 그리고 11/10 에 더해진 릴리스(태그 → 카나리 → 게시 → 장치 설치). 회차마다 끝에 AI 없이 혼자 커밋하는 작은 과제 하나(예시: jitter_bench 를 2 kHz 로 돌려 표①에 줄 추가, 단위 테스트 1개 추가, Grafana 패널 1개 추가). 막히는 장표는 `notes_md/NNN.md` 를 고치고 다시 만든다(HANDOVER §6).
- "제출 서류(이력서·설계서)에 11/10~11 의 것(릴리스 → 배포 · 운영 층 · 왕복) 반영": 제출용 이력서·자기소개서와 포트폴리오 설계서(PDF, 저장소 밖)는 11/06 에 썼다. 그 뒤에 생긴 세 가지 — 릴리스 → 배포 파이프라인, 클라우드 운영 층, 왕복 290 ms 의 측정 이야기 — 를 넣는다. 11/05 의 장표에는 이 자리에 "이력서 문장(docs/RESUME_LINES.md): 경력 숫자 5개 채우기 · 재직자 접촉"이 있었다 — 제출 서류는 11/06 에 저장소 밖에서 따로 썼고(경력은 그쪽에 적었다), 저장소의 `docs/RESUME_LINES.md` 는 초안 그대로 남아 있다. 지금 남은 것은 11/10~11 의 반영이다.

둘째 묶음 "선택 (면접에서 '다음 단계'로 말할 것)":
- "512M 부하로 cyclictest -S 한 번 더(E19-d 의 부하 정의 vs 격리 전후 가르기) · 방열판 달고 300초 부하": 표① 쪽 두 가지. E19-d 에서 cyclictest 와 jitter_bench 의 차이 중 "부하 정의(512M vs 256M)"와 "격리 전후"가 아직 한 덩어리(약 80 us)로 남아 있다 — 512M 부하로 `cyclictest -S` 를 한 번 더 돌리면 둘이 갈라진다. 방열판을 달면 300초 부하 측정이 스로틀 없이 가능하지만 조건이 바뀌므로 일반 커널도 다시 재야 한다(DECISIONS 2026-11-04).
- "수동 ACK(DB 적재 뒤 PUBACK) · 브로커 로그로 천둥 떼 가설 확정 · 기록 요약을 관제로 1 Hz 올리기": 관제 쪽 셋(EXPERIMENTS "남은 것"). 수동 ACK = 수집기가 메시지를 받은 즉시가 아니라 DB 에 적재한 뒤 PUBACK 을 보내 수집기가 죽어도 브로커가 재전송하게 하는 것(D5 실측에서 보류). 천둥 떼(thundering herd) = E07 에서 50대가 동시에 재접속하며 유실이 더 난 현상이 브로커 단일 스레드의 큐 방류 때문인지 브로커 로그로 확정하는 일. 기록 요약을 관제로 = E20 의 bag 요약(Hz·틈·추종 오차)을 1 Hz 로 MQTT 에 올려 Grafana 에서 보기.
- "중력 보상(토크 피드포워드) · 관절 한계 클램프 · 실물 Feetech 시리얼 백엔드 · JUnit 리포트": 더 먼 것들. 중력 보상은 E16 의 어깨 처짐 1.1° 를 없애는 제어 항(팔 무게만큼의 토크를 미리 더한다). 실물 Feetech 시리얼 백엔드는 `backend.hpp` 에 자리만 있는 `FeetechSerialBackend`(SO-101 실물 서보, 2주 계획 밖). JUnit 리포트는 CI 결과를 표 화면으로(ENVIRONMENT.md). 관절 한계 클램프(목표가 모델의 관절 범위를 넘지 않게 자르기)는 저장소 문서에는 없고 장표에서 덧붙인 항목이다 — 5절 참고. 11/05 의 장표에는 이 줄에 "TLS 인증"도 있었다 — 11/10 에 운영 설정으로 넣었으므로(8883 TLS + 비밀번호) 뺐고, 남은 부분(장치별 인증서)은 아래 줄로 갔다.
- "릴리스·운영: 산출물 서명(ed25519) · 헬스 게이트에 RT 지표 · 노드 재시작 훅 · 자율 모드에서 실패한 버전만 건너뛰기 · 장치별 인증서(mTLS) · 양쪽 TCP_NODELAY 측정"(11/11 에 더한 줄): 11/10~11 의 것을 만들며 "여기까지만 한다"고 선을 그은 여섯 가지다.
  - 산출물 서명: 지금 장치는 sha256 으로 파일이 **손상되지 않았는지**만 본다. 누가 만든 파일인지(진위)는 보지 않는다 — 서명 키를 어디에 두고 어떻게 바꿀지가 하루짜리 설계라 다음으로 미뤘다(DECISIONS 11/10).
  - 헬스 게이트에 RT 지표: 지금 건강의 기준은 `state == ok` 하나다. 새 버전에서 1 ms 루프의 지연이 나빠졌는지(예: p99.9)를 배포 판단에 넣는 것이 다음이다.
  - 노드 재시작 훅: 실물에서 바뀌는 것은 슬롯과 링크까지다. 새 실행 파일로 제어 노드를 다시 띄우는 훅(`post_switch.sh`)은 자리만 있다.
  - 자율 모드에서 실패한 버전만 건너뛰기: 자율 설치가 한 번 실패하면 장치는 `fault` 로 남아 재시작 전까지 다시 시도하지 않는다. 고친 릴리스가 나와도 스스로 받지 못한다(DECISIONS 11/11 의 "남은 한계").
  - 장치별 인증서(mTLS): 지금은 모든 장치가 비밀번호 하나를 같이 쓴다. 장치마다 인증서를 주면 한 대만 끊을 수 있지만 발급·폐기 절차가 필요하다.
  - 양쪽 TCP_NODELAY 측정: E23 에서 "한쪽만 끄면 부족하다"까지 확인했다. 브로커 쪽까지 끄고 재는 것은 브로커 재시작이 필요해 연속 기록 중에는 하지 않았다.

설명 상자 "지금 상태(11/11) — 코드·측정·문서·CI 가 일관된 상태이고, 첫 정식 릴리스 v0.9.0 이 게시됐다(러너 카나리 50/50, 깨진 빌드 3/50 에서 거부). 남은 큰 일은 영상 · 분석 기간 · 서류 제출 — 모두 작성자의 손이 필요한 일": 11/05 의 상자는 "전체 진행률 약 80%"였다. 퍼센트는 근거 없는 어림이라(그때의 설명 문서도 "붙이지 않는 쪽이 안전하다"고 적었다) 11/11 에 뺐고, 대신 확인할 수 있는 사실 둘을 적었다 — 저장소의 네 가지가 서로 어긋나지 않는다는 것과, 태그 `v0.9.0` 이 카나리를 통과해 게시됐다는 것. 남은 일은 AI 가 대신할 수 없는 일(사람이 치는 영상, 사람이 설명해 보는 분석, 사람이 내는 서류)이라는 점이 이 상자의 요점이다.

## 3. 용어와 단위

- 자율 업데이트: 지휘하는 서버(배포기) 없이 장치가 스스로 새 릴리스를 확인해 설치하는 방식. 시간대(03~05시)와 상태(ok) 조건이 붙는다.
- 연속 기록(soak): 장치가 오랫동안 끊김 없이 보고했는지를 일련번호로 센 기록. 그래프가 아니라 "보낸 수 · 받은 수 · 빠진 수".
- 분석 기간(5회차): 작성자가 교재(장표·설명 문서)로 저장소를 직접 설명해 보는 다섯 번의 세션. 공부 기간이지 개발 기간이 아니다.
- 원테이크(one take): 끊지 않고 한 번에 녹화. 실수하면 처음부터.
- TTS(Text-to-Speech): 글을 합성 음성으로 읽어 주는 기능. Clipchamp 는 Windows 의 영상 편집 앱.
- 수동 ACK / PUBACK: MQTT QoS 1 에서 "받았다"는 확인 패킷(PUBACK). 보통은 라이브러리가 받는 즉시 보내지만, 수동으로 바꾸면 DB 적재 뒤에 보낼 수 있다.
- 천둥 떼(thundering herd): 많은 클라이언트가 **동시에** 같은 일(재접속·재전송)을 해서 서버가 순간적으로 막히는 현상.
- 토크 피드포워드(torque feedforward): 측정값을 기다리지 않고 미리 아는 힘(팔 무게)을 명령에 더하는 제어 방식.
- 클램프(clamp): 값을 허용 범위 [최소, 최대] 안으로 자르는 것.
- JUnit 리포트: 테스트 결과를 적는 XML 형식. CI 화면에서 테스트별 통과/실패 표로 보여 줄 수 있다.
- 서명(ed25519): 만든 사람만 가진 비밀 키로 파일에 도장을 찍고, 받는 쪽이 공개 키로 그 도장을 확인하는 방식. ed25519 는 그 방식의 하나다. sha256(무결성)과 달리 **누가 만들었나**(진위)를 본다.
- mTLS: 서버만이 아니라 장치도 인증서로 자기를 증명하는 TLS.
- TCP_NODELAY: 작은 메시지를 모았다 보내는 TCP 의 기본 동작(Nagle)을 끄는 소켓 설정(장표 142).
- 2 kHz: 1초에 2,000번. 지금 루프는 1 kHz(1 ms 주기), 2 kHz 는 0.5 ms 주기.

## 4. 쉬운 예시

- 비유: 시험 범위 공부(코드·측정·문서)는 끝났고 모의고사(릴리스 카나리)도 통과했다. 남은 것은 **말로 설명해 보는 연습**(분석 기간)과 **시험장 가는 길 영상**(2분 영상), 그리고 원서(서류)다. 공부가 끝났다고 시험 준비가 끝난 것은 아니다 — 남은 것이 당락을 가른다.
- 숫자 예시: 11/11 에서 서류 제출 목표 11/14 까지 사흘, 마감 11/17 까지 엿새. 자율 업데이트 확인은 11/12 아침의 몇 분, 영상은 11/12~13, 서류 반영은 그 사이에. 분석 기간 다섯 번은 제출 뒤 면접 전까지 이어진다.
- "다음 단계" 예시(면접): "어깨가 1.1° 처진 것을 숫자로 봤으니, 다음은 그 관절에 토크 피드포워드를 넣어 처짐이 0.1° 아래로 가는지 같은 기록 파이프라인으로 재는 것입니다" — 숫자(1.1°)와 측정 방법(E20 요약)이 이미 있어 말이 된다. 릴리스 쪽이면: "지금은 sha256 으로 손상만 봅니다. 다음은 서명으로 누가 만든 파일인지를 보는 것이고, 키를 어디에 두느냐가 먼저 정할 일입니다."

## 6. 자주 하는 오해·함정

- "릴리스가 게시됐으니 Pi 도 0.9.0 이다"는 오해: 게시와 설치 사이에 시간대(03~05시)가 있다. 11/11 낮의 Pi 는 아직 옛 버전이고, 장표의 첫 줄이 "다음 날 아침에 확인"인 이유다. 확인 전에는 "자율 설치가 됐다"고 말하지 않는다.
- 선택 과제를 "안 한 일"로 말하지 않는다 — "다음 단계로 **고른** 일"이다. 각 항목에 숫자 근거(1.1°, 80 us, 53 유실의 천둥 떼, 290 ms)가 붙어 있어야 다음 단계로 설득력이 있다.
- 영상은 "설명할 수 있는 상태"에서 쳐야 한다. 대본에 나오는 명령과 숫자를 장표에서 찾아 설명할 수 있는지 먼저 본다.
- 서류의 경력 이야기는 이 저장소가 아니라 작성자의 **과거 경력**이다. 저장소 숫자와 섞지 않는다. `docs/RESUME_LINES.md` 의 [대괄호] 다섯 자리는 비어 있는 채다 — 제출 서류와 맞출지, 파일을 정리할지는 제출 뒤에 정한다.
- 방열판을 달고 재면 지금 표①의 Pi 줄과 조건이 달라진다 — 그 뒤 비교는 "방열판 있음" 줄끼리만.
- sha256 을 "보안"이라고 말하지 않는다. 손상은 잡지만 바꿔치기는 못 잡는다 — 그래서 서명이 다음 단계에 있다.

## 7. 면접 한 문장

"코드·측정·문서·CI 는 서로 맞는 상태이고 첫 정식 릴리스가 카나리를 통과해 게시됐습니다. 남은 것은 제가 직접 해야 하는 일 — 직접 치는 2분 영상, 장표로 설명해 보는 분석 기간, 서류 — 이고, 다음 단계로는 어깨 처짐 1.1° 를 없애는 중력 보상, DB 적재 뒤 PUBACK 을 보내는 수동 ACK, 그리고 릴리스 쪽에서는 산출물 서명을 같은 측정 방법으로 해 보고 싶습니다."
