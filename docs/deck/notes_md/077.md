# 장표 077 — ⑥ 들머리 — OTA: 50대에 새 펌웨어를 안전하게, 나쁜 펌웨어는 5% 에서 멈춘다
*위치: 2부 데이터의 길 · ⑥ OTA · 들머리*

## 1. 이 장표가 왜 있나
앞 장표(076)까지로 "올라오는 길"(장치 → 브로커 → 수집기 → DB → 대시보드)이 완성됐다. 그러면 반대 방향이 남는다: 서버가 장치 50대에 **새 펌웨어(장치 소프트웨어)를 내려 보내는 길**, 즉 OTA(Over-The-Air, 무선 갱신)다. 올라오는 길은 잃어도 데이터 몇 행이지만, 내려가는 길은 잘못되면 로봇 50대가 한꺼번에 고장 난다. 그래서 질문이 바뀐다 — "빠르게"가 아니라 "**나쁜 펌웨어가 왔을 때 피해를 어디까지로 막나**"가 기준이다.

이 장표는 ⑥ OTA 묶음의 들머리다. 같은 여섯 상자로 문제·기준·확인·결과를 적고, 다음 장표들(078 그림, 079~081 코드)이 그 과정을 그림과 코드로 보인다. 실측 표는 3부 장표 100 으로 미룬다.

## 2. 장표를 하나씩 읽기
- 상자 1 "들어온 것"(회색): "cmd 토픽을 듣고 있는 장치들 + DB 의 fw_version·state (①~⑤)". ①에서 장치는 `fleet/<id>/cmd` 토픽을 구독하고 있어 서버의 명령을 받을 수 있고, ③~④로 장치의 펌웨어 버전(`fw_version`)과 상태(`state`)가 1 Hz 로 DB 와 서버에 보인다. OTA 는 이 두 가지를 재료로 쓴다 — 명령은 cmd 토픽으로 내리고, 결과는 텔레메트리로 확인한다. 별도의 OTA 전용 통신이 필요 없다.
- 상자 2 "문제": "한 번에 50대에 내리면 나쁜 펌웨어가 50대를 고장 낸다. 장치가 스스로 판단하면 기준이 50곳에 흩어진다". 문제 둘. 첫째, 전부에게 동시에 내리면 피해 범위가 전부다. 둘째, "이 펌웨어가 나쁜가"를 장치 각자가 판단하게 하면 판단 기준이 장치 수만큼 흩어져 고칠 때마다 50곳을 고쳐야 하고, 장치 하나는 자기 고장만 알 뿐 "3대 중 1대가 고장"같은 집단 판단을 할 수 없다.
- 마름모 3 "기준": "나쁜 펌웨어는 첫 단계(5%)에서 멈추고 수초 안에 롤백, 좋은 펌웨어는 100% 도달. 판단은 서버 한 곳에서?". 세 가지를 동시에 묻는다. (1) 나쁜 펌웨어의 피해는 첫 단계 5 % 에서 멈추고 수초 안에 이전 버전으로 되돌아가야 한다. (2) 좋은 펌웨어는 끝까지(100 %) 가야 한다 — 안전 장치가 정상 배포까지 막으면 안 된다. (3) 단계·헬스 판정·롤백 결정은 전부 서버 한 곳(`rollout.py`)에서. 왜 5 % 인가: 50대의 5 % = 2.5 → 올림 3대. 3대면 피해가 작으면서도 "우연히 한 대만 이상한 것"과 구분할 수 있다.
- 상자 4 "확인 방법"(파란색): "rollout.py — 5 → 50 → 100% 단계, 적용 대기, 헬스 게이트(state ≠ ok 수 > max_fail 이면 롤백) · --bad 와 정상 1.1.0 → 3부 장표 100 · test_ota_rollout 3건(6부)". 확인 수단 셋. (1) 배포기 `fleet/ota/rollout.py` 가 누적 5 → 50 → 100 % 세 단계로 내리고, 단계마다 "적용 대기(장치들의 fw_version 이 새 버전으로 바뀔 때까지)" → "헬스 게이트(health_wait 초 지켜본 뒤 state 가 ok 가 아닌 장치 수가 max_fail(기본 0)을 넘으면 롤백)". (2) 실험: `--bad`(나쁜 펌웨어 흉내)와 정상 버전 1.1.0 을 실제로 50대에 돌린 결과가 3부 장표 100 의 표③-3. (3) 단위 테스트 `fleet/tests/test_ota_rollout.py` 3건(좋은 펌웨어 100 % 도달, 나쁜 펌웨어 롤백, 적용 시간 초과) — 6부 테스트 목록.
- 상자 5 "결과"(민트색): "나쁜 펌웨어: 닿은 장치 3 / 50(ceil 2.5), 롤백 1.0초(CI 0.4초), 47대는 명령을 받은 적도 없다. 정상 OTA success=true". 나쁜 펌웨어는 5 % 단계의 3대에만 닿았고(50 × 0.05 = 2.5 → 3), 롤백 결정부터 3대가 전부 이전 버전·ok 로 돌아오기까지 1.0초(WSL2 50대). GitHub CI 러너(10대 2 Hz)에서는 1 / 10 에서 멈추고 0.4초. 나머지 47대는 명령 자체를 받은 적이 없다 — 이것이 단계 배포(카나리)의 뜻이다. 정상 버전 1.1.0 은 50 / 50 에 도달해 `success=true`.
- 상자 6 "판단 → 다음"(진한 둥근 상자): "통과 → ⑦⑧: 정상 동작은 확인됐다. 이제 각 부품을 일부러 죽여 얼마나 잃고 얼마나 빨리 돌아오는지 잰다". 올라오는 길과 내려가는 길 모두 정상 동작이 확인됐으니, 다음 묶음은 브로커·DB·수집기를 일부러 죽이는 장애 주입(⑦)과 그 결과의 판정·진단(⑧)이다.
- 아래 줄 "이 묶음의 장표: ② run_stage 코드 · ② rollback 코드. 넘어가는 조건: '나쁜 펌웨어' 시나리오가 숫자(3/50, 1.0초)로 끝났고 판단 기준이 서버 코드 한 곳에 있다. 11/10 보탬: 여기까지의 실측은 버전 문자열만 바꾸는 '흉내' — 진짜 파일을 내려받아 설치하는 길과 태그 → 릴리스 파이프라인은 7부 덧붙임 장표 137~139". 이 묶음의 나머지 장표는 그림(078), run_stage 코드 두 장(079~080), rollback 코드(081)다. 넘어가는 조건은 기준 (1)(3)이 숫자와 코드 위치로 확인됐다는 것이다. 마지막 문장(11/10 보탬)은 범위를 밝힌다: 2부·3부의 OTA 숫자(3 / 50, 1.0초)는 장치가 "설치한 척" 버전 문자열만 바꾸는 경로에서 잰 것이다. 같은 배포기(`rollout.py`)가 11/10 부터는 매니페스트를 받아 진짜 파일을 깔게 할 수 있고(코드는 장표 079 에 이미 보인다), 그 길의 그림 · 장치 쪽 설치 코드 · 숫자는 137 · 138 · 139 에 따로 있다. 단계 배포 · 헬스 게이트 · 롤백이라는 판단 구조는 두 경로가 같다.

## 3. 용어와 단위
- OTA(Over-The-Air): 무선으로 장치 소프트웨어를 갱신하는 것. 여기서 "적용"은 흉내(apply_s 초 기다린 뒤 버전 문자열 교체)다.
- 펌웨어: 장치 안에서 돌아가는 소프트웨어. 버전 문자열(1.0.0, 1.1.0, 1.2.0-bad)로 구분한다.
- 단계 배포 / 카나리(canary): 소수에 먼저 내려 보고 괜찮으면 넓히는 방식. 광산에서 유독 가스를 먼저 알리던 카나리아 새에서 온 말.
- 누적 퍼센트 5 → 50 → 100: 전체 중 몇 %까지 새 버전을 받았는가. 5 % 단계는 3대, 50 % 단계는 25대까지(새로 22대), 100 % 는 50대까지(새로 25대).
- 적용 대기(apply wait): 명령을 받은 장치들의 텔레메트리 `fw_version` 이 새 버전으로 바뀌기를 기다리는 것. 제한 시간은 apply_s + 15초.
- 헬스 게이트(health gate): 단계마다 "건강한가"를 보는 문. 기준은 텔레메트리 `state == ok` 하나.
- max_fail: 비정상이어도 넘어가 줄 장치 수. 기본 0 = 한 대라도 아프면 롤백.
- 롤백(rollback): 이전 버전으로 되돌리기. 장치는 `prev_fw_version` 을 기억해 두었다가 돌아간다.
- ceil(올림): 2.5 → 3. 장치 수는 정수여야 하고, "5 % 미만"이 되지 않게 올린다.
- `success=true`: 배포 결과 JSON 과 `ota_rollouts` 표의 성공 표시.

## 4. 쉬운 예시
새 조리법을 전국 50개 지점에 바꾸는 식당 체인 비유: 본사(rollout.py)가 먼저 3곳(5 %)에만 새 조리법을 보내고 하루(health_wait) 지켜본다. 손님 항의(state=fault)가 한 곳이라도(max_fail 0) 나오면 세 곳 모두 옛 조리법으로(롤백) 돌리고 중단한다 — 나머지 47곳은 새 조리법을 받은 적도 없다. 항의가 없으면 25곳, 그 다음 50곳으로 넓힌다. 판단은 본사 한 곳이 한다 — 지점이 각자 "내 손님만 보고" 되돌리면 본사는 무엇이 왜 되돌아갔는지 모른다.

숫자 예시: 50대, 기본값 apply_s 2.0초 · health_wait 5.0초로 나쁜 펌웨어를 내리면 5 % 단계 3대 → 적용 2초 → 헬스 5초 → 3 / 3 비정상 > 0 → 롤백 1.0초. 약 8초 안에 사고가 끝나고 피해는 3 / 50 = 6 %. 좋은 펌웨어 1.1.0 은 3 → 25 → 50대, 단계마다 2 + 5초씩 약 21초 뒤 success.

## 6. 자주 하는 오해·함정
- "헬스 게이트가 있으면 나쁜 펌웨어는 한 대도 안 다친다"는 오해. 첫 단계의 3대는 다친다(그래서 1.0초 뒤 되돌린다). 카나리는 피해를 없애는 것이 아니라 **범위를 3 / 50 으로 묶는** 것이다.
- "장치가 스스로 롤백하면 더 빠르지 않나"는 생각. 빠를 수 있지만 집단 판단이 불가능하고 서버가 이유를 모른다. D3 의 결정이 그 절충이다.
- 헬스 기준이 `state == ok` 하나뿐인 것은 단순함이 장점이지만, 상태 반영까지 최대 1초(1 Hz) 지연이 있다 — health_wait 5초 안에 충분하다.
- 장치 쪽 "적용"은 흉내다. 실물에서는 그 자리에 실제 설치가 들어가고 서버 코드는 바뀌지 않는다.
- 50 % 단계에서 비정상이 나오면 롤백은 "지금까지 새 버전을 받은 모든 장치(25대)"에 간다. 이번 단계 장치만 되돌리는 것이 아니다(장표 080~081).

## 7. 면접 한 문장
"OTA 는 5 → 50 → 100 % 세 단계로 내리고 단계마다 서버가 헬스 게이트를 봅니다. 나쁜 펌웨어를 실제로 50대에 내렸을 때 3대에서 멈춰 1.0초에 롤백했고 47대는 명령을 받은 적도 없습니다 — 판단 기준은 rollout.py 한 곳에만 있습니다."
