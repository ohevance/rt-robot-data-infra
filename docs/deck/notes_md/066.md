# 장표 066 — ① 가상 장치 50대 (virtual_fleet.py) — 실물 없이 서버에 부하를 주고 흐름을 검증한다
*위치: 2부 데이터의 길 · ① 장치 에이전트 · ② 가상 장치 50대 · 단일 인스턴스 잠금*

## 1. 이 장표가 왜 있나
앞 장표(065)에서 장치 에이전트 하나가 1초마다 무엇을 하는지(보내거나, 모으거나, 다시 붙으면 비우거나)를 그림으로 봤다. 그런데 관제 서버가 정말 견디는지는 장치 **한 대**로는 알 수 없다. 수십 대가 동시에 보내야 브로커·수집기·DB 의 부하와 장애 때의 모습이 드러난다. 실물 로봇 50대를 살 수는 없으니, 같은 에이전트 클래스를 50개 띄우는 프로그램이 필요하다 — 그것이 `fleet/agent/virtual_fleet.py` 다. 이 장표는 질문 두 개에 답한다: 가상 장치 50대는 어떻게 만들어지고 어떤 옵션이 있나? 그리고 실제로 겪은 사고(두 벌이 서로 밀어냄)를 무엇으로 막았나?

## 2. 장표를 하나씩 읽기
- **첫째 줄 — "장치마다 DeviceAgent 하나(스레드 2개: 주기 스레드 + paho 네트워크 스레드). 숫자는 난수 걸음(random walk): cpu 20~60%, temp 40~55 °C, mem, rssi — 시드 고정이라 재현된다"**: `virtual_fleet.py` 는 `--count` 만큼 `DeviceAgent` 를 만든다. 장치 이름은 `<prefix>-001`, `<prefix>-002` …(기본 prefix `vdev`). 에이전트마다 스레드가 두 개라서 50대면 스레드 약 100개가 한 프로세스에서 돈다. 숫자는 `VirtualMetrics` 가 만든다 — 처음 값은 cpu 20~60%, 온도 40~55 °C, 메모리 30~50%, 신호 세기(rssi) −70~−50 dBm 사이에서 고르고, 그 뒤로는 매 초 조금씩만 움직인다(cpu ±3, 온도 ±0.3, 메모리 ±0.5, rssi ±2). 이렇게 "직전 값에서 조금씩 걷는" 난수를 난수 걸음이라 한다 — 진짜 센서처럼 그래프가 이어져 보인다. 범위를 벗어나지 않게 자른다(cpu 0~100, 온도 20~90 °C, rssi −90~−30). 장치 i 의 난수 시드는 i 로 고정(`VirtualMetrics(seed=i)`)이라, 다시 돌려도 같은 장치는 같은 숫자 흐름을 낸다 → 실험을 다시 해도 비교가 된다. 가상 장치의 `loop_hz`, `wake_p99_us` 는 비어 있다(None) — 이 칸은 실제 RT 노드(다리)만 채운다.
- **둘째 줄 — 옵션 `--count 50 --rate 1 --telemetry-qos {0,1} --keepalive 10 --keepalive-jitter N --prefix`**: `--count` 장치 수(기본 50), `--rate` 장치당 초당 메시지 수(기본 1.0 → 1 Hz), `--telemetry-qos` 텔레메트리 QoS(기본 0; 1 이면 수집기가 잠깐 죽어도 브로커가 대신 들고 있다), `--keepalive` 살아 있다는 신호 주기(기본 10초), `--keepalive-jitter` 장치마다 keepalive 에 더하는 0~N초(기본 0), `--prefix` 장치 이름 머리(기본 vdev). 이 밖에 `--broker`, `--port`, `--duration`(0 이면 Ctrl+C 까지)도 있다. 장치를 한꺼번에 붙이면 브로커가 순간 몰리므로 0.01초씩 시차를 두고 시작한다.
- **셋째 줄 — keepalive jitter 가 왜 있나(E10)**: 50대가 거의 동시에 접속하면 keepalive 박자가 맞아, 10초마다 50대의 PINGREQ(살아 있다는 신호)가 한꺼번에 처리된다. 그 순간 이 프로세스가 멈칫해 전달 지연 p95 가 평소 1~2 ms 에서 약 10 ms 로 튀었다(3부 E10, WSL2). keepalive 를 30초로 늘리면 튐은 사라지지만, 브로커가 끊김을 판정하는 시간(keepalive × 1.5)이 15초에서 45초로 늦어진다 — 죽은 장치를 45초 동안 모르게 된다. 그래서 감지 시간은 거의 그대로 두고 박자만 흩뜨린다: 장치마다 0~N초를 더한다(`keepalive = a.keepalive + rng.randint(0, a.keepalive_jitter)`). jitter 난수도 시드 0 으로 고정이라 장치 i 는 항상 같은 keepalive 를 받는다.
- **넷째 줄 — "같은 --prefix 로는 한 벌만: fleet/logs/fleet_<prefix>.lock (flock). 두 벌이 뜨면 같은 client_id 를 서로 밀어내 2초마다 재접속(11/04 reconnects 1,675 사고)"**: MQTT 브로커는 같은 client_id(접속 이름)로 새 접속이 오면 옛 접속을 끊는다. 가상 장치를 실수로 두 번 띄우면 vdev-001 이 두 개가 되어, 둘이 번갈아 서로를 끊는다. 11/04 실제로 그랬고, 끝났을 때 재접속 수가 1,675(50대 × 약 33회)였다. 그래서 시작할 때 잠금 파일을 잡고, 이미 누가 잡고 있으면 "pid 몇이 이미 떠 있습니다, 먼저 그쪽을 Ctrl+C 로 끝내세요"를 출력하고 종료 코드 3 으로 끝난다.
- **다섯째 줄 — "Ctrl+C 면 전부 정상 종료(offline 발행)"**: SIGINT(Ctrl+C)와 SIGTERM 을 받으면 반복을 멈추고 장치마다 `stop()` 을 부른다. `stop()` 은 status 에 "offline" 을 보관 메시지로 직접 보낸다 — 유언(비정상 종료용)이 아니라 정상 종료 인사다. 마지막에 `done. buffered=… flushed=… reconnects=…` 합계를 출력한다 — 장애 실험 뒤 "모은 수 = 보낸 수"를 여기서 바로 확인한다.
- **오른쪽 말풍선 — 단일 인스턴스 잠금(`fleet/common/single_instance.py`)**:
  - `acquire(name)`: `fleet/logs/<name>.lock` 파일을 열고 `flock(LOCK_EX|LOCK_NB)` — 운영체제의 파일 잠금을 "배타적(EX), 기다리지 않음(NB)"으로 건다. 잡으면 열린 파일을 돌려주고 자기 pid 를 적는다. 이미 다른 프로세스가 잡고 있으면 None.
  - `other_pid(name)`: 잠금 파일에 적힌 pid 를 읽어 "누가 잡고 있나"를 안내한다(없으면 '?').
  - "프로세스가 죽으면 커널이 잠금을 자동 해제한다": flock 잠금은 파일이 닫히면 풀리고, 프로세스가 어떻게 죽든(Ctrl+C, kill -9, 오류) 커널이 파일을 닫는다. 그래서 "잠금 파일이 남아 다음 실행이 막히는" 문제가 없다. 단, 잠금을 잡은 파일 객체를 변수로 계속 들고 있어야 한다 — 닫히면 풀린다.
  - "수집기('collector')와 가상 장치('fleet_<prefix>')가 공용으로 쓴다": 같은 사고가 수집기에서도 있었기 때문에(수집기 두 개 → 서로 밀어냄) 잠금을 공용 모듈로 뺐다(LOG 11/04).
- **아래 '다음 ▶'**: "② 브로커 — 장치는 끊겨도 모았다가 보낸다(654 = 654, 3부 장표 97). 받는 쪽 브로커는 수집기가 없는 동안 대신 들고 있나, 재시작하면? (설정 세 줄)" — 장치 쪽의 보존은 확인했으니, 다음은 가운데 우체국(브로커)이 잃지 않는지.

## 3. 용어와 단위
- **가상 장치**: 실물 대신 숫자를 만들어 보내는 프로그램 속 장치. 서버 입장에서는 실물과 구별되지 않는다.
- **난수 걸음(random walk)**: 매번 직전 값에서 작은 난수만큼 움직이는 값. 그래프가 끊기지 않고 이어진다.
- **시드(seed)**: 난수 생성기의 출발 값. 같은 시드면 같은 난수 순서가 나온다 → 재현 가능.
- **client_id**: MQTT 접속 이름. 브로커는 같은 이름의 새 접속이 오면 옛 접속을 끊는다.
- **keepalive / PINGREQ**: keepalive 초 동안 주고받은 것이 없으면 PINGREQ(살아 있다는 신호)를 보낸다. 브로커는 keepalive × 1.5 동안 조용하면 끊겼다고 본다.
- **jitter(흩뜨림)**: 일부러 조금씩 다른 값을 주어 동시에 몰리지 않게 하는 것.
- **flock**: 리눅스의 파일 잠금. LOCK_EX = 혼자만, LOCK_NB = 못 잡으면 기다리지 않고 바로 실패.
- **pid**: 프로세스 번호.
- **p95**: 100개 중 95개는 이 값 이내. 단위 ms(밀리초, 1/1000초).
- **rssi**: 무선 신호 세기, 단위 dBm(음수, 0 에 가까울수록 강함). 여기서는 흉내 값.

## 4. 쉬운 예시
- 비유: 식당 개업 전 리허설에 가짜 손님 50명을 부른다(가상 장치). 손님마다 주문 습관이 정해져 있어(시드 고정) 리허설을 두 번 해도 같은 주문이 들어온다. 모두 정각마다 "물 주세요"를 외치면(keepalive 박자가 맞음) 직원이 그 순간 멈칫한다 → 손님마다 외치는 시각을 조금씩 어긋나게(jitter). 같은 이름표를 단 손님 두 명이 들어오면 자리를 서로 빼앗으니(client_id 충돌) 입구에서 이름표 명부(잠금 파일)로 막는다.
- 숫자 예시: `--count 50 --rate 1` → 초당 50개 메시지, 스레드 약 100개. `--keepalive 10 --keepalive-jitter 5` → 장치마다 keepalive 10~15초, 끊김 판정 15~22.5초. 두 벌을 띄웠던 11/04: 50대 × 약 33회 = reconnects 1,675.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 초기 범위(cpu 20~60, 온도 40~55, 메모리 30~50, rssi −70~−50)와 걸음 크기 — `fleet/agent/virtual_fleet.py` `VirtualMetrics` (`sed -n '33,55p' fleet/agent/virtual_fleet.py`).
- 확인: 옵션과 기본값(count 50, rate 1.0, keepalive 10, jitter 0, qos 0, prefix vdev) — 같은 파일 `main()` 의 `add_argument` 줄들.
- 확인: 시작 시차 0.01초, 종료 합계 출력, 잠금 실패 시 종료 코드 3 — 같은 파일.
- 확인: p95 약 10 ms 튐, 10.0초 간격, keepalive 30초면 0회 — `docs/experiments/E10.md` (WSL2). 끊김 판정 15초 → 45초 계산도 같은 파일.
- 확인: reconnects 1,675 — `docs/LOG.md` 11/04 항목, `fleet/common/single_instance.py` 머리말.
- 확인: 654 = 654 — `docs/experiments/E05.md`, 3부 장표 097.

## 6. 자주 하는 오해·함정
- "가상 장치라 실제와 다르다" — 서버(브로커·수집기·DB)가 보는 것은 똑같은 MQTT 메시지다. 다른 것은 숫자의 출처(metrics_source)뿐이고, 같은 `DeviceAgent` 클래스가 실제 RT 노드의 다리에도 쓰인다. 다만 네트워크 지연·전파 끊김 같은 무선 환경은 흉내 내지 않는다(같은 PC 안).
- 실험을 하다 이전 실행을 끄지 않고 다시 띄우는 실수 — 두 벌이 서로 밀어낸다(11/04 사고). 지금은 잠금이 막고 "이미 떠 있습니다" 를 출력한다.
- keepalive 를 늘리면 다 해결된다고 생각하기 쉽다 — 튐은 사라지지만 끊김 감지가 3배 늦어진다. 대가를 숫자로 비교하고 jitter 를 택했다.
- 잠금 파일(`fleet/logs/*.lock`)을 지워야 다시 뜬다고 생각하기 쉽다 — flock 은 프로세스가 죽으면 커널이 푼다. 파일은 남아 있어도 된다.

## 7. 면접 한 문장
"실물 50대 대신 같은 에이전트 클래스를 50개 띄워 서버를 시험했고, 시드를 고정해 재현되게 했습니다 — 그러다 keepalive 박자가 맞아 10초마다 지연이 튀는 것과 같은 client_id 두 벌이 서로 밀어내는 사고를 찾아, 각각 jitter 와 flock 잠금으로 막았습니다."
