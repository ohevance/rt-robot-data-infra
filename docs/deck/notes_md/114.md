# 장표 114 — lib_stress.sh — 부하 정의는 한 곳에: start_stress · stop_stress
*위치: 6부 믿을 수 있나 · 측정 — 부하 함수*

## 1. 이 장표가 왜 있나
앞 장표(113)는 측정 조건 중 "온도·스로틀"을 결과 옆에 적는 함수였다. 이번에는 또 하나의 조건, "부하"다. 표①에서 "부하 중 max" 라고 말할 때 그 부하가 무엇인지(CPU 몇 개, 메모리 얼마) 정해져 있지 않으면 두 줄을 비교할 수 없다. 11/05 에 실제로 그 일이 있었다. 측정 스크립트 두 개가 각자 stress-ng 를 띄우면서 메모리 버퍼 크기가 달랐고(cyclictest_run 512M, jitter_run 256M), "표준 도구 132 us vs 우리 측정기 301 us" 의 차이를 쫓다가 일부가 측정기가 아니라 부하 정의의 차이에서 왔다는 것을 뒤늦게 알았다(E19-d).

이 장표는 그 교훈으로 만든 `lib_stress.sh` 의 핵심 18줄이다. 부하를 시작하는 함수와 끝까지 기다리는 함수 하나씩, 그리고 쓴 값을 `.meta` 에 남긴다는 규칙이다. 6부 "측정" 묶음의 마지막 장표라서 아래의 "다음 ▶" 다리가 "테스트"로 넘긴다.

## 2. 장표를 하나씩 읽기
코드 상자 위의 파일 표시는 `scripts/lib_stress.sh:21-38`. 이 파일의 18줄에 `STRESS_PID=""`(부하 프로세스 번호를 담을 변수, 처음엔 빈 값)가 있고, 장표의 코드는 그 아래부터다.

- 21줄 `start_stress() {`: 부하 시작 함수. 인자 두 개를 받는다.
- 22줄 `local seconds="$1"`: 첫 인자 = 부하 지속 시간(초). `local` 은 이 함수 안에서만 쓰는 변수.
- 23줄 `local vm_bytes="$2"`: 둘째 인자 = 메모리 작업자의 버퍼 크기(예 256M).
- 24줄 `if ! command -v stress-ng >/dev/null; then`: stress-ng 명령이 설치되어 있는지 검사한다. `command -v` 는 명령의 위치를 찾고, `!` 는 "없으면".
- 25줄 `echo "stress-ng 가 없습니다:  sudo apt install stress-ng" >&2`: 없으면 설치 명령을 오류 출력(`>&2`)으로 알려 준다.
- 26줄 `return 1`: 실패로 함수를 끝낸다. 부르는 쪽(`start_stress … || exit 1`)은 이 실패를 받아 스크립트 전체를 끝낸다. "부하 없이 조용히 재는 일"이 없게 하기 위해서다.
- 27줄 `fi`: if 끝.
- 28줄 `stress-ng --cpu "$(nproc)" --io 2 --vm 1 --vm-bytes "${vm_bytes}" --timeout "${seconds}s" >/dev/null 2>&1 &`: 부하 본체. `--cpu "$(nproc)"` 는 CPU 작업자를 코어 수만큼(Pi 4 는 4개), `--io 2` 는 I/O 작업자 2개, `--vm 1` 은 메모리 작업자 1개, `--vm-bytes` 는 그 작업자의 버퍼 크기, `--timeout "${seconds}s"` 는 지정한 초 뒤 스스로 끝남. 출력은 전부 버리고(`>/dev/null 2>&1`), 끝의 `&` 로 뒤에서(백그라운드) 돌린다 — 측정기가 앞에서 돌아야 하므로.
- 29줄 `STRESS_PID=$!`: 바로 앞에서 뒤로 보낸 프로세스의 번호(`$!`)를 변수에 둔다. 나중에 기다리기 위해서다.
- 30줄 `sleep 3     # 작업자들이 다 뜰 때까지 (측정 첫 1~2초가 "아직 한가"로 섞이지 않게)`: 3초 기다린다. stress-ng 가 작업자 여러 개를 띄우는 데 시간이 걸리는데, 그 사이에 측정을 시작하면 처음 1~2초가 "한가한 상태"로 섞여 부하 측정이 아니게 된다.
- 31줄 `}`: 함수 끝.
- 32줄: 빈 줄.
- 33줄 주석 `# 부하 끝까지 기다림 (측정이 먼저 끝나도 timeout 까지 돈다)`: 다음 함수의 뜻. jitter_run 은 부하를 측정보다 15초 길게 걸므로(STRESS_HEADROOM_S) 측정이 먼저 끝난다.
- 34줄 `stop_stress() {`: 부하 종료 대기 함수.
- 35줄 `if [ -n "${STRESS_PID}" ]; then`: 부하 프로세스 번호가 비어 있지 않으면(`-n` 은 "길이가 0 이 아니면"), 즉 부하를 시작했었다면.
- 36줄 `wait "${STRESS_PID}" 2>/dev/null || true`: 그 프로세스가 끝날 때까지 기다린다. 이미 끝났으면 `wait` 가 오류를 내는데 `|| true` 로 무시한다.
- 37줄 `STRESS_PID=""`: 변수를 비워 두 번 기다리지 않게 한다.
- 38줄 `fi`: if 끝(함수의 닫는 괄호는 39줄이라 장표에는 없다).

코드 아래 "읽는 포인트" 네 개:
- 포인트 1 "start_stress <초> <vm>: stress-ng --cpu N(코어 수) --io 2 --vm 1 --vm-bytes <vm> --timeout <초> 를 뒤에서 돌리고 PID 를 STRESS_PID 에 둔다. sleep 3 은 작업자가 다 뜰 때까지(측정 첫 1~2초가 '아직 한가'로 섞이지 않게). stop_stress 는 그 PID 를 wait": 두 함수의 요약이다.
- 포인트 2 "--vm-bytes 가 왜 중요한가: 메모리를 건드리는 부하가 클수록 CPU 간 인터럽트(IPI, TLB 비우기)가 잦아져 격리된 CPU 도 맞는다 → 같은 'stress' 라도 vm 크기가 다르면 다른 실험": 메모리 작업자는 버퍼를 할당(mmap) → 채움 → 해제(munmap)를 반복한다. 해제할 때마다 다른 CPU 들의 주소 변환 캐시(TLB)를 비우라는 IPI 가 날아가고, IPI 는 우선순위도 isolcpus 도 막지 못한다. 그래서 vm 설정이 지연에 영향을 준다(`lib_stress.sh` 머리말에 "추정"으로 적힌 설명). 장표의 "메모리를 건드리는 부하가 클수록"은 메모리 활동량을, 파일 머리말의 "버퍼가 작을수록 해제가 잦다"는 그 활동이 IPI 로 바뀌는 기전을 말한다 — 둘의 핵심은 같다. vm 설정이 다르면 IPI 빈도가 달라져 다른 실험이 된다.
- 포인트 3 "부하를 한 함수로 묶은 이유: E19-d 에서 두 스크립트의 vm 크기(cyclictest_run 512M vs jitter_run 256M)가 달라 도구 비교가 흐려졌다 → 쓴 값은 .meta 의 stress_vm_bytes 에(DECISIONS 11/05)": 이 파일이 생긴 사건. 기본값은 두 스크립트가 지금까지 쓴 값을 그대로 둬서 기존 14줄과의 비교가 깨지지 않게 했고, 바꾸려면 환경 변수 `STRESS_VM_BYTES` 로 한다.
- 포인트 4 "stress-ng 가 없으면 바로 실패한다 — 조용히 '부하 없이' 재는 일이 없게": 24~26줄. 부하 없이 잰 결과에 "stress" 라벨이 붙는 사고를 막는다.
- "다음 ▶" 다리 "테스트 — 측정은 '조건을 적는다'로 믿게 했다. 코드 논리는 무엇이 지키나? (테스트 20건, 가짜 → 진짜)": 측정 묶음(112~114)이 끝나고 테스트 묶음(115~118)으로 간다. 20건은 C++ ctest 4 + MuJoCo 1 + Python 15 다.

## 3. 용어와 단위
- stress-ng: 시스템에 여러 종류의 부하를 주는 도구. 작업자(worker) 종류별로 개수를 지정한다.
- `--cpu N`: CPU 를 바쁘게 돌리는 작업자 N 개. `$(nproc)` 은 코어 수(Pi 4 는 4).
- `--io 2`: 파일 시스템 동기화(sync) 같은 I/O 를 반복하는 작업자 2개.
- `--vm 1 --vm-bytes 256M`: 메모리를 할당·쓰기·해제하는 작업자 1개, 버퍼 256 메가바이트. M = 메가바이트(약 100만 바이트).
- `--timeout 75s`: 75초 뒤 스스로 끝남.
- PID(process ID): 운영체제가 프로세스마다 붙이는 번호. `$!` 는 마지막으로 뒤로 보낸 프로세스의 PID.
- `&` / 백그라운드: 명령을 뒤에서 돌리고 바로 다음 줄로 넘어가는 것. `wait PID` 는 그 프로세스가 끝날 때까지 멈춘다.
- `local`: 셸 함수 안에서만 보이는 변수.
- `>/dev/null 2>&1`: 표준 출력과 오류 출력을 모두 버림. `>&2`: 오류 출력으로 보냄.
- IPI(Inter-Processor Interrupt): CPU 가 다른 CPU 에 보내는 인터럽트. TLB 비우기(TLB shootdown)가 대표적이다.
- TLB(Translation Lookaside Buffer): 가상 주소 → 물리 주소 변환 결과를 담는 CPU 안의 작은 캐시. 메모리 매핑이 해제되면 다른 CPU 의 TLB 도 비워야 해서 IPI 가 간다.
- .meta / stress_vm_bytes: 측정 결과 옆 조건 기록 파일과, 거기에 적는 부하 버퍼 크기 항목.
- us(마이크로초): 100만분의 1초. 132 us, 301 us 는 깨어남 지연의 max 다.

## 4. 쉬운 예시
- 비유: 두 자동차의 연비를 비교하는데 한 대는 에어컨을 켜고 한 대는 끄고 달렸다면 비교가 성립하지 않는다. "부하"는 에어컨이고, `start_stress` 는 "에어컨은 항상 이 설정으로"라고 정한 매뉴얼이다. 설정값(vm 크기)을 주행 기록(.meta)에 적어 두면 나중에 "그때 에어컨이 달랐다"를 알아낼 수 있다 — 11/05 에 정확히 그렇게 알아냈다.
- 숫자 예시: `start_stress 75 256M` 은 Pi 4 에서 `stress-ng --cpu 4 --io 2 --vm 1 --vm-bytes 256M --timeout 75s` 를 뒤에서 돌리고 3초 기다린다. jitter_run 이 60초 측정이면 부하는 60 + 15 = 75초로 걸어 측정 끝까지 부하가 유지된다. 측정이 끝나면 `stop_stress` 가 남은 약 12초를 기다려 부하가 완전히 끝난 뒤 온도를 읽는다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 코드 21~38줄 — `scripts/lib_stress.sh`(`sed -n '21,38p' scripts/lib_stress.sh`). 18줄 `STRESS_PID=""`, 39줄 닫는 괄호.
- 확인: 512M vs 256M, 132 vs 301 — `scripts/lib_stress.sh` 머리말, `docs/DECISIONS.md` 2026-11-05(부하 정의 통일), `docs/experiments/E19d.md`. 표①에서 132 는 `pi4_rt_stress`(cyclictest, vm 512M) max, 301 은 `pi4_rt_stress`(jitter_bench, vm 256M) max 300.6 이다.
- 확인: 기본값 cyclictest_run 512M / jitter_run 256M, 환경 변수 `STRESS_VM_BYTES` — 두 스크립트의 `VM_BYTES=` 줄.
- 확인: STRESS_HEADROOM_S=15 — `scripts/jitter_run.sh`.
- 확인: 테스트 20건(4 + 1 + 15) — `docs/ENVIRONMENT.md` §5-7.
- 추정: vm 크기가 지연에 영향을 주는 기전(munmap → TLB IPI) — `lib_stress.sh` 머리말에 "추정"으로 적혀 있다. 직접 인터럽트를 세어 확인한 것은 아니다.
- 다시 확인하는 법(Pi 창): `source scripts/lib_stress.sh && start_stress 10 256M && pgrep -c stress-ng && stop_stress` 로 작업자 수를 본다. 측정 스크립트로는 `STRESS_VM_BYTES=512M sudo -E scripts/jitter_run.sh <label> 60 stress 3` 처럼 바꿔 돌리고 `.meta` 의 `stress_vm_bytes` 를 확인한다.

## 6. 자주 하는 오해·함정
- "stress 라벨이 같으면 같은 부하다": vm 크기(그리고 CPU·I/O 작업자 수)가 같아야 같은 부하다. 그래서 정의를 함수 하나로 묶고 값을 `.meta` 에 적는다.
- "부하가 세면 지연이 커지는 것은 당연하니 크기는 상관없다": 상관있다. 두 도구의 차이(132 vs 301)의 일부가 부하 크기 차이였다. 비교하려는 두 줄은 같은 함수에서 나온 부하여야 한다.
- "sleep 3 은 낭비다": 없으면 측정 첫 1~2초가 "아직 한가한" 상태로 섞여 p99 가 좋아 보인다. 3초는 그 오염을 막는 값이다.
- 함정(실제로 겪은 것): 도구 두 개가 다르게 나왔을 때 처음에는 측정기를 의심했다. `.meta` 가 없었다면 부하 정의 차이를 알아낼 길이 없었다(E19-d). `docs/SETUP_RT_MEASURE.md` §6-1 "도구 두 개가 다르게 나올 때"에 순서가 적혀 있다.

## 7. 면접 한 문장
"두 측정 스크립트의 부하 버퍼가 512M 과 256M 으로 달라 도구 비교가 흐려진 것을 알고, 부하 정의를 함수 하나로 묶고 쓴 값을 .meta 에 남겼다 — 비교하려는 두 줄의 부하가 같은 함수에서 나오지 않으면 그 비교는 성립하지 않는다."
