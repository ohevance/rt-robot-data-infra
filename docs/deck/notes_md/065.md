# 장표 065 — ① 장치 에이전트 — 한 주기의 흐름 (보내거나, 모으거나, 붙으면 비우거나)
*위치: 2부 데이터의 길 · ① 장치 에이전트 · ② 그림 — 한 주기*

## 1. 이 장표가 왜 있나
앞의 두 코드 장표(063·064)에서 장치 에이전트(`fleet/agent/device_agent.py`)의 함수들을 하나씩 읽었다 — `tick()` 과 `send_or_buffer()`(보내거나 모으기), `on_connect()` 와 `flush_buffer()`(다시 붙으면 비우기), 그리고 유언(LWT). 코드를 함수 단위로 읽으면 "언제 어느 함수가 불리는지"가 흩어져 보인다. 그래서 이 장표는 질문 하나에 그림 한 장으로 답한다: **1초마다 한 번 도는 이 에이전트는, 브로커와 붙어 있을 때·끊겼을 때·다시 붙었을 때·비정상으로 죽었을 때 각각 무엇을 하나?** 이 그림을 이해하면 "끊겨도 잃지 않는다(store-and-forward)"가 코드 몇 줄로 어떻게 만들어지는지가 한눈에 보인다.

## 2. 장표를 하나씩 읽기
그림(`diagrams/agent_flow_lr.mmd`)은 왼쪽에서 오른쪽으로 읽는다. 위 줄이 "1초마다 일어나는 일", 가운데 줄이 "다시 붙었을 때", 아래 줄이 "비정상으로 죽었을 때"다.

- **상자 `tick (1 Hz): metrics + seq + ts_ns → JSON`**: 에이전트의 주기 스레드가 1초에 한 번(`period_s` = 1.0 / rate) `tick()` 을 부른다(`device_agent.py:119`). 하는 일은 세 가지다. ① `metrics_source()` 를 불러 숫자(가상 장치는 cpu·온도 같은 난수, RT 노드 다리는 rt_status 숫자)를 받는다. ② 일련번호 `seq`(0, 1, 2 … 하나씩 늘어나는 번호 — 나중에 서버가 "빠진 번호"로 유실을 센다)와 `ts_ns`(측정한 순간의 벽시계 시각, 나노초)를 붙인다. ③ JSON 글자열로 만든다. 왜 seq 를 붙이나: 서버가 "몇 개를 받았나"가 아니라 "몇 번이 빠졌나"를 셀 수 있어야 유실을 숫자로 말할 수 있다(2부 ⑦의 유실 SQL 이 이것을 쓴다).
- **마름모 `브로커에 붙어 있나?`**: `send_or_buffer()`(`:138`)의 첫 질문 — `self.client.is_connected()`. 이 판단 하나가 "보내기"와 "모으기"를 가른다.
- **화살표 `예` → 상자 `publish(telemetry, qos=telemetry_qos)`**: 붙어 있으면 바로 `fleet/<장치>/telemetry` 토픽으로 보낸다. QoS(전달 보장 수준)는 실행 옵션 `--telemetry-qos` 로 0 또는 1. 기본은 0(보내고 잊음, 가장 가벼움).
- **화살표 `아니오` → 마름모 `버퍼 3600개 찼나?`**: 끊겨 있으면 보낼 수 없으니 장치의 메모리(버퍼, 파이썬 `deque`)에 넣는다. 그 전에 버퍼가 꽉 찼는지 본다. 상한 `MAX_BUFFER = 3600`(`:37`) — 1 Hz 기준 1시간 분량이다.
- **`예` → 상자 `가장 오래된 것 버림`**: 꽉 찼으면 `popleft()` 로 가장 오래된 한 개를 버린다. 왜 오래된 것인가: 1시간 넘게 끊긴 장치라면 가장 최근 상태가 더 쓸모 있다. 메모리가 끝없이 늘어 장치가 죽는 것보다 오래된 것부터 포기하는 쪽이 안전하다.
- **상자 `buffer.append → buffered_total += 1`**: 버퍼 끝에 넣고 "지금까지 모은 수" 카운터를 1 올린다. 이 카운터는 다음 텔레메트리에 `buffered` 로 실려 서버도 볼 수 있다.
- **가운데 줄 — 상자 `on_connect (재접속)`**: 끊겼던 연결을 paho(파이썬 MQTT 라이브러리)가 1~5초 간격으로 자동으로 다시 붙인다(`reconnect_delay_set(min_delay=1, max_delay=5)`, `:86`). 붙는 순간 paho 네트워크 스레드에서 `on_connect()`(`:149`)가 불린다.
- **상자 `status online (retained) 발행 / cmd 구독`**: 먼저 `fleet/<장치>/status` 에 "online" 을 보관(retained) 메시지로 보낸다 — 나중에 구독하는 쪽도 "지금 상태"를 바로 받는다. 그리고 서버의 명령 토픽(`cmd`)을 다시 구독한다(OTA 명령을 받기 위해).
- **상자 `flush_buffer: 모아 둔 것 전부 QoS 1 재전송 / flushed_total += n`**: 버퍼를 통째로 꺼내 비우고(`:156`), 하나씩 **QoS 1**(받았다는 확인이 올 때까지 다시 보냄)로 보낸다. 평소 QoS 가 0 이라도 재전송만큼은 1 로 보내는 이유: 한 번 끊겼다는 것은 네트워크가 불안하다는 뜻이고, 어렵게 모은 데이터를 다시 잃으면 모은 의미가 없다. 보낸 개수만큼 `flushed_total` 이 오른다 — 3부의 실험(E05)에서 "모은 수 654 = 보낸 수 654" 를 이 두 카운터로 확인했다.
- **아래 줄 — 상자 `비정상 종료` → 점선 `브로커가 대신` → 상자 `유언: status offline (retained)`**: 장치가 전원이 꺼지거나 프로세스가 죽으면 "나 죽어요"라고 말할 기회가 없다. 그래서 접속할 때 미리 유언(LWT, Last Will and Testament)을 맡겨 둔다(`will_set(..., "offline", qos=1, retain=True)`, `:82`). 브로커는 keepalive 시간(기본 10초)의 1.5배 동안 소식이 없으면 연결이 죽었다고 보고 이 유언을 대신 발행한다. 점선인 이유: 장치가 직접 하는 일이 아니라 브로커가 대신 하는 일이라서.

글머리표 네 줄:
- **"3600개 상한, 넘치면 오래된 것부터 버림"**: 위 마름모의 숫자. 1 Hz × 3,600초 = 1시간.
- **"재접속은 paho 가 1~5초 간격으로 자동"**: 우리 코드에 재접속 반복문이 없다. 라이브러리 설정 한 줄(`:86`)이다. 끊길 때마다 `on_disconnect()` 가 `reconnects` 를 1 올린다(`:167`).
- **"같은 클래스가 가상 장치 50대와 RT 노드 다리에 쓰인다 — 다른 것은 metrics_source 뿐"**: `DeviceAgent` 는 "숫자를 어디서 가져오나"(`metrics_source`, 호출하면 dict 를 돌려주는 함수, `:60`)만 바꿔 끼운다. 가상 장치는 난수 걸음(`virtual_fleet.py` 의 `VirtualMetrics`), 1부 단계 10 의 다리(`ros_status_bridge.py`)는 rt_status 의 숫자. 그래서 가상 장치로 검증한 버퍼·재전송·유언이 실제 로봇에도 그대로 적용된다.
- **"OTA 명령(ota/ota_rollback)은 on_message 에서, 별도 스레드로 — 명령에 url 이 없으면 흉내(apply_ota: apply_s 동안 updating → fw 교체 → ok 또는 fault), 있으면 진짜 설치(apply_ota_artifact, 7부 덧붙임)"**: 서버가 `cmd` 토픽으로 명령을 보내면 `on_message()`(`:169`)가 받는다. `ota` 면 적용을 별도 스레드에서 한다(`:191-199`). 왜 별도 스레드인가: 적용에 시간이 걸리는데, paho 네트워크 스레드에서 기다리면 그동안 다른 메시지를 못 받는다. 길은 둘이다(11/10 부터). 명령에 `url` 이 없으면 **흉내 경로** — 적용 스레드(`apply_ota`, `:237`)가 state 를 `updating` 으로 바꾸고 `apply_s` 초(기본 2.0초) 잠든 뒤 버전 문자열을 바꾸고, 정상 펌웨어면 `ok`, 나쁜 펌웨어(`bad=true`)면 `fault` 로 바꾼다. 장애 주입과 기존 단위 테스트가 이 길을 쓴다. 명령에 `url` 이 있고 장치에 슬롯 폴더가 있으면 **진짜 설치** — `apply_ota_artifact`(`:252`)가 파일을 내려받아 sha256 을 맞추고 슬롯에 풀어 자가 점검을 통과한 뒤에만 전환한다(장표 138). 어느 길이든 그동안 주기 스레드의 텔레메트리는 계속 나가므로 서버는 "updating → ok/fault" 를 실시간으로 본다. `ota_rollback` 은 직전 설치를 거부한 장치면 상태만 `ok` 로, 설치에 성공한 장치면 이전 슬롯으로, 흉내 경로면 이전 버전 문자열로 되돌린다(`:203-233`).

## 3. 용어와 단위
- **장치 에이전트(device agent)**: 장치(로봇·센서) 안에서 숫자를 모아 서버로 보내는 작은 프로그램.
- **MQTT**: 장치와 서버 사이의 가벼운 메시지 규약. 가운데 우체국 역할의 **브로커**(여기서는 Mosquitto)가 있고, 보내는 쪽은 토픽(주소)에 발행(publish), 받는 쪽은 그 토픽을 구독(subscribe)한다.
- **QoS 0 / 1**: 0 = 보내고 잊음(잃을 수 있음), 1 = 브로커가 "받았다(PUBACK)"고 할 때까지 다시 보냄(최소 한 번 도착, 중복은 가능).
- **store-and-forward(모았다가 보내기)**: 못 보낼 때 저장해 두었다가 나중에 보내는 방식.
- **보관 메시지(retained)**: 브로커가 그 토픽의 마지막 메시지 하나를 기억해 두었다가 새 구독자에게 바로 준다 — "지금 상태" 용도.
- **유언(LWT)**: 접속할 때 맡겨 두고, 비정상으로 끊기면 브로커가 대신 발행하는 메시지.
- **keepalive**: 이 시간(초) 동안 주고받은 것이 없으면 살아 있다는 신호(PINGREQ)를 보낸다. 브로커는 그 1.5배 동안 조용하면 끊겼다고 본다. 10초면 15초.
- **스레드**: 한 프로그램 안에서 동시에 도는 작업 흐름. 에이전트 하나에 주기 스레드 + paho 네트워크 스레드(+ OTA 적용 중이면 적용 스레드).
- **단위**: 1 Hz = 1초에 한 번. ns(나노초) = 10억분의 1초. 3,600개 = 1 Hz 로 1시간.

## 4. 쉬운 예시
- 비유: 택배 기사가 매시간 물건을 하나씩 배달한다. 다리가 끊기면(브로커 중단) 물건을 트럭에 쌓아 둔다(버퍼). 트럭이 꽉 차면(3,600개) 가장 오래된 짐부터 내려놓는다. 다리가 다시 열리면(재접속) 먼저 본사에 "다시 운행 중"이라 알리고(online), 쌓아 둔 짐을 등기 우편(QoS 1)으로 전부 보낸다. 기사가 갑자기 쓰러지면 본사에 미리 맡겨 둔 "연락 끊기면 운행 중단으로 처리" 쪽지(유언)를 본사가 대신 붙인다.
- 숫자 예시(3부 E05, WSL2): 장치 50대, 1 Hz, 브로커를 10초 멈췄다. 50대 × 10초 = 500개가 생길 것 같지만 실제 버퍼는 654개였다 — 끊김을 알아채고 다시 붙기까지 걸린 시간만큼 더 쌓여 장치당 약 13초분(654 ÷ 50 ≈ 13). 다시 붙자 654개를 그대로 재전송(`flushed`), 재접속 50대 전부.

## 6. 자주 하는 오해·함정
- "QoS 1 이면 끊겨도 안 잃는다" — 아니다. QoS 1 은 **연결된 상태에서** 브로커까지의 전달 확인일 뿐이다. 연결이 끊긴 동안에는 보낼 곳이 없으니, 장치 쪽 버퍼가 없으면 그 동안의 데이터는 생기는 즉시 사라진다. 그래서 버퍼(store-and-forward)가 따로 필요하다.
- "버퍼가 있으니 유실 0" — 버퍼 상한(1시간)을 넘는 장애에서는 오래된 것부터 버린다. 유실이 '없게'가 아니라 '세게'(buffered_total, flushed_total) 만들어 두었다는 것이 정확한 표현이다.
- 유언이 즉시 나간다고 생각하기 쉽다 — keepalive × 1.5(10초 설정이면 15초) 뒤에 나간다. "고장 장치"가 대시보드에 늦게 뜨는 이유.
- 재전송된 데이터의 전달 지연이 수 초~수십 초로 크게 찍힌다 — 지연을 "원래 측정 시각(ts_ns)" 기준으로 재기 때문이며 정상이다(LOG 11/03: 재전송 폭주 때 max 12.5 s).

## 7. 면접 한 문장
"장치 에이전트는 1초마다 seq 를 붙여 보내고, 끊기면 최대 1시간분을 모았다가 다시 붙는 순간 QoS 1 로 전부 보냅니다 — 브로커를 10초 죽였을 때 모은 654개와 보낸 654개가 같았고, 같은 클래스가 실제 로봇의 다리에도 그대로 쓰입니다."
