# 장표 079 — ⑥ OTA 배포기 — 한 단계 (1/2): 이번 단계 장치에 보내고, 적용될 때까지 기다린다 (run_stage 앞부분)
*위치: 2부 데이터의 길 · ⑥ OTA · ② 코드 — run_stage 1/2 보내기·적용 대기*

## 1. 이 장표가 왜 있나
앞 장표(078)의 그림은 나쁜 펌웨어 한 번의 흐름을 시간 순서로 보였다 — 서버가 3대에 명령을 보내고, 적용을 기다리고, 헬스를 보고, 되돌린다. 그러면 "그 서버 쪽 화살표가 **코드로는** 어떻게 생겼나?"가 다음 질문이다. 배포기 `fleet/ota/rollout.py` 에서 한 단계를 처리하는 함수가 `run_stage` 이고, 길어서 두 장으로 나눴다. 이 장표는 앞부분(141~154줄): "이번 단계 장치들에 명령을 보내고, 전부 적용될 때까지 기다린다". 뒷부분(장표 080)이 헬스 게이트다. 장표의 코드는 빌드 시점의 저장소 파일을 그대로 읽은 것이라 손으로 베낀 오류가 없다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/ota/rollout.py:141-154` 가 적혀 있다. `self` 는 `Rollout` 객체(이번 배포 한 번의 상태: 버전, 단계 목록, 적용 시간, 헬스 대기, 허용 실패 수, 나쁜 펌웨어 여부, 지금까지 새 버전을 받은 장치 목록 `updated`, 타임라인).

- 141줄 `def run_stage(self, pct, batch):` — 한 단계. `pct` 는 이 단계의 누적 퍼센트(5, 50, 100), `batch` 는 이 단계에서 **새로** 명령을 받을 장치 목록. 누가 batch 를 정하나: 바로 위의 `run()`(124~139줄)이 `target_count = ceil(n × pct / 100)` 을 계산하고 `devices[done_count:target_count]` 로 잘라 준다. 50대의 5 % = ceil(2.5) = 3대, 50 % = 25대까지(새로 22대), 100 % = 50대까지(새로 25대).
- 142줄 독스트링 `"""한 단계: 보내기 → 적용 대기 → 헬스 게이트. 통과하면 True"""` — 이 함수의 세 일과 반환값. True 면 다음 단계로, False 면 중단.
- 143줄 `self.mark(f"단계 {pct}%: {len(batch)}대에 ota 전송")` — `mark` 는 타임라인에 한 줄 남기고 화면과 DB(`events`, kind='ota')에도 쓰는 함수(116~122줄). 배포의 모든 결정이 이 줄들로 남아 대시보드 "최근 이벤트" 표에 보인다.
- 144~145줄 `for device_id in batch:` / `self.w.send(device_id, {"cmd": "ota", "version": self.version, "apply_s": self.apply_s, "bad": self.bad})` — 이번 단계 장치마다 `fleet/<id>/cmd` 토픽으로 QoS 1 명령을 보낸다(`FleetWatcher.send`, 82줄). 명령 내용: 할 일 `ota`, 새 버전 문자열, 장치가 적용에 쓸 시간 `apply_s`(초), `bad`(참이면 장치는 적용 뒤 `state=fault` 를 내어 "켜자마자 고장 나는 펌웨어"를 흉내 낸다). 장치 쪽(`device_agent.py:176 apply_ota`)은 별도 스레드에서 `updating` → apply_s 초 대기 → 버전 교체 → ok 또는 fault 로 바꾼다.
- 146줄 `self.updated.extend(batch)` — "지금까지 새 버전을 받은 모든 장치" 목록에 이번 단계 장치들을 더한다. 명령을 보낸 순간 더하는 이유: 되돌려야 할 때는 "적용이 끝난 장치"가 아니라 "명령을 받은 장치" 전부에 되돌리기 명령을 보내야 하기 때문이다. 다음 장표의 헬스 게이트와 롤백(081)이 이 목록을 쓴다.
- 147줄 빈 줄.
- 148줄 `took = wait_until(make_all_applied_check(self, batch), timeout_s=self.apply_s + 15.0)` — 적용 대기. `make_all_applied_check`(191~199줄)는 "batch 의 모든 장치의 최신 텔레메트리 `fw` 가 새 버전과 같은가"를 보는 함수를 만들어 주고, `wait_until`(90~98줄)은 그 함수가 참이 될 때까지 0.2초마다 확인하며 걸린 시간(초)을 돌려준다. 제한 시간은 `apply_s + 15초`(기본 2 + 15 = 17초) — 장치가 적용에 쓰는 시간에 넉넉한 여유를 더한 값. 시간 안에 안 되면 None.
- 149~152줄 `if took is None:` / `self.mark(f"단계 {pct}%: 적용 시간 초과 → 롤백")` / `self.rollback()` / `return False` — 한 대라도 시간 안에 새 버전이 안 보이면 적용 실패로 보고 즉시 롤백(장표 081)한 뒤 False 를 돌려 배포를 중단한다. 적용이 안 되는 것도 "나쁜 결과"다 — 단위 테스트 `test_apply_timeout` 이 이 길을 확인한다.
- 153줄 `self.mark(f"단계 {pct}%: 전원 적용 완료 ({took:.1f}초)")` — 전부 적용됐으면 걸린 시간을 소수 첫째 자리까지 기록(그림 078 의 "전원 적용 1.6초"가 이 줄의 출력).
- 154줄 빈 줄 — 다음 장표의 헬스 게이트로 이어진다.

오른쪽 "읽는 포인트" 네 줄:
- "단계 = 누적 퍼센트(5 → 50 → 100). 50대의 5% = ceil(2.5) = 3대 — batch 는 '이번 단계에서 새로 받는 장치들'" — 위 141줄 설명.
- "보내기: fleet/<id>/cmd 에 {cmd: ota, version, apply_s, bad} — bad=true 면 장치가 적용 뒤 state=fault 를 내는 '나쁜 펌웨어' 흉내" — 144~145줄.
- "적용 대기: 그 장치들의 텔레메트리 fw_version 이 새 버전으로 바뀔 때까지(시간 제한 apply_s + 15초). 시간 안에 안 바뀌면 timeout 으로 실패 처리 → 롤백" — 148~152줄. 서버는 장치에게 "다 됐니?"라고 따로 묻지 않고, 이미 1 Hz 로 올라오는 텔레메트리의 버전 문자열을 본다.
- "updated 에 '지금까지 새 버전을 받은 모든 장치'를 누적한다 — 다음 장의 헬스 게이트와 롤백이 이 목록을 쓴다" — 146줄.

## 3. 용어와 단위
- 메서드 / `self`: 파이썬 클래스 안의 함수와 그 객체 자신. `self.version` 은 "이번 배포의 버전".
- 독스트링(docstring): 함수 머리의 `"""…"""` 설명 글.
- f-string: `f"단계 {pct}%"` 처럼 중괄호 안 값을 글자에 끼워 넣는 파이썬 문법.
- 토픽 `fleet/<id>/cmd`: MQTT 의 주소. 장치 하나가 자기 이름의 cmd 토픽을 구독한다.
- QoS 1: 받았다는 확인을 받을 때까지 다시 보내는 전달 등급(장표 067).
- `extend`: 목록 끝에 다른 목록의 원소를 모두 붙인다.
- 타임아웃(timeout): 기다리는 최대 시간. 넘으면 실패로 본다. `apply_s + 15.0` 초.
- `wait_until(predicate, timeout_s)`: 조건 함수가 참이 될 때까지 0.2초마다 확인. 걸린 시간(초) 또는 None.
- 스냅샷(snapshot): 그 순간의 최신 값 복사본. `FleetWatcher` 가 텔레메트리를 들으며 장치별 `fw`, `state` 를 기억해 둔 것.
- ceil(올림): 2.5 → 3.

## 4. 쉬운 예시
학급 단체 문자 비유: 선생님(서버)이 "새 교재로 바꾸세요"라는 문자를 반 전체가 아니라 먼저 3명(5 %)에게만 보낸다(144~145줄). 보낸 사람 이름을 명단(`updated`)에 적어 둔다(146줄). 그리고 3명이 각자 "바꿨어요"라고 매일 보내는 일지(텔레메트리의 fw_version)를 보며 모두 바꿀 때까지 기다린다(148줄). 17분이 지나도 한 명이 안 바꿨으면 뭔가 잘못된 것이니 3명 모두 원래 교재로 돌리고 중단한다(149~152줄).

숫자 예시: 50대, 기본 apply_s 2.0초. 5 % 단계: batch 3대, 제한 17초. 장치가 2초 뒤 버전을 바꾸고 다음 1 Hz 텔레메트리에 실리니 서버는 보통 2~3초 안에 "전원 적용 완료"를 찍는다(실측 그림 078: 1.6초, 그 실행은 apply_s 1초). 50 % 단계: batch 22대(3 → 25), 100 % 단계: 25대(25 → 50).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 코드 — `sed -n '141,154p' fleet/ota/rollout.py`. `run`(124~139줄)의 `ceil`, `wait_until`(90줄), `make_all_applied_check`(191줄), `FleetWatcher.send`(82줄), `mark`(116줄).
- 확인: 장치 쪽 처리 — `fleet/agent/device_agent.py` 158~165줄(`ota` 명령 → `apply_ota` 스레드), 176~186줄(`apply_ota`: updating → sleep(apply_s) → prev_fw_version 저장 → 버전 교체 → ok/fault).
- 확인: 기본값 apply_s 2.0, stages 5,50,100 — `rollout.py` 290~300줄의 인자.
- 확인: 적용 시간 1.6초 — 그림 078(`ota_seq.mmd`)의 실행. 표③-3 의 실행들은 apply/health 2.0 / 5.0 기본값.
- 확인: 적용 시간 초과 경로의 테스트 — `fleet/tests/test_ota_rollout.py` `test_apply_timeout`(88줄).

## 6. 자주 하는 오해·함정
- "서버가 장치에게 적용 완료를 따로 묻는다"는 오해. 묻지 않는다. 1 Hz 로 이미 오는 텔레메트리의 `fw_version` 을 볼 뿐이다 — 별도 프로토콜이 없어 단순하지만, 확인에 최대 1초의 지연이 있다.
- `batch` 와 `updated` 를 혼동하기 쉽다. `batch` 는 이번 단계에서 새로 받는 장치(3, 22, 25대), `updated` 는 지금까지 받은 누적(3, 25, 50대). 적용 대기는 `batch`, 헬스 게이트와 롤백은 `updated` 를 본다.
- 명령을 보내는 순간 `updated` 에 넣는다. 적용 확인 뒤에 넣으면, 적용 시간 초과로 롤백할 때 그 장치들이 명단에 없어 되돌리기 명령을 못 받는다.
- `bad` 는 실험용 표시다. 실물 펌웨어에 "나는 나쁘다"는 표시가 있을 리 없다 — 실물에서는 그 자리에 실제 설치가 들어가고, 고장은 실제 상태로 나타난다. 서버 코드는 그대로다.
- 제한 시간 `apply_s + 15초` 는 코드에 박힌 여유값이다. 실물 설치가 몇 분 걸리면 apply_s 를 그만큼 크게 준다.

## 7. 면접 한 문장
"run_stage 앞부분은 이번 단계 장치들에만 cmd 토픽으로 ota 명령을 보내고 누적 명단에 적은 뒤, 텔레메트리의 fw_version 이 전부 새 버전으로 바뀔 때까지 apply_s + 15초 안에서 기다립니다 — 시간 안에 안 바뀌면 그것도 실패로 보고 바로 롤백합니다."
