# 장표 079 — ⑥ OTA 배포기 — 한 단계 (1/2): 이번 단계 장치에 보내고, 적용될 때까지 기다린다 (run_stage 앞부분)
*위치: 2부 데이터의 길 · ⑥ OTA · ② 코드 — run_stage 1/2 보내기·적용 대기*

## 1. 이 장표가 왜 있나
앞 장표(078)의 그림은 나쁜 펌웨어 한 번의 흐름을 시간 순서로 보였다 — 서버가 3대에 명령을 보내고, 적용을 기다리고, 헬스를 보고, 되돌린다. 그러면 "그 서버 쪽 화살표가 **코드로는** 어떻게 생겼나?"가 다음 질문이다. 배포기 `fleet/ota/rollout.py` 에서 한 단계를 처리하는 함수가 `run_stage`(183~232줄)이고, 길어서 두 장으로 나눴다. 이 장표는 앞부분: "이번 단계 장치들에 명령을 보내고(183~198줄), 전부 적용될 때까지 기다린다(`wait_apply`, 234~247줄)". 뒷부분(장표 080)이 헬스 게이트다. 장표의 코드는 빌드 시점의 저장소 파일을 그대로 읽은 것이라 손으로 베낀 오류가 없다. 11/10 에 이 함수가 바뀌었다 — 버전 문자열만 보내던 것에 "진짜 파일의 주소와 해시"가 더해졌고, 기다리는 방법이 "설치에 실패한 장치가 보이면 바로 멈춘다"로 바뀌었다. 이 문서는 바뀐 코드 기준이다.

## 2. 장표를 하나씩 읽기
코드 상자 위에 `fleet/ota/rollout.py:183-198 · wait_apply fleet/ota/rollout.py:234-247` 이 적혀 있다. 위 덩어리가 `run_stage` 의 앞부분, 빈 줄 아래 덩어리가 그것이 부르는 `wait_apply` 다. `self` 는 `Rollout` 객체(이번 배포 한 번의 상태: 버전, 단계 목록, 적용 시간, 헬스 대기, 허용 실패 수, 나쁜 펌웨어 여부, 매니페스트, 지금까지 새 버전을 받은 장치 목록 `updated`, 타임라인).

- 183줄 `def run_stage(self, pct, batch):` — 한 단계. `pct` 는 이 단계의 누적 퍼센트(5, 50, 100), `batch` 는 이 단계에서 **새로** 명령을 받을 장치 목록. 누가 batch 를 정하나: 바로 위의 `run()`(166~181줄)이 `target_count = ceil(n × pct / 100)` 을 계산하고 `devices[done_count:target_count]` 로 잘라 준다. 50대의 5 % = ceil(2.5) = 3대, 50 % = 25대까지(새로 22대), 100 % = 50대까지(새로 25대).
- 184줄 독스트링 `"""한 단계: 보내기 → 적용 대기 → 헬스 게이트. 통과하면 True"""` — 이 함수의 세 일과 반환값. True 면 다음 단계로, False 면 중단.
- 185줄 `real_count = sum(1 for d in batch if … .get("kind") == "real")` — 이번 batch 에 실물 장치(텔레메트리의 `kind` 가 "real")가 몇 대인지 센다. 장치 목록은 가상이 먼저, 실물이 맨 뒤로 정렬돼 온다(`FleetWatcher.online_devices`, 98~109줄) — 5 % 단계는 가상 장치가 맡고 실물은 앞 단계가 통과한 뒤에만 받게 하려는 것이다.
- 186줄 `self.mark(f"단계 {pct}%: {len(batch)}대에 ota 전송" + (… 실물 …대 포함 …))` — `mark` 는 타임라인에 한 줄 남기고 화면과 DB(`events`, kind='ota')에도 쓰는 함수(158~164줄). 배포의 모든 결정이 이 줄들로 남아 대시보드 "최근 이벤트" 표에 보인다. 실물이 들어 있으면 괄호로 알린다.
- 187~188줄 `for device_id in batch:` / `cmd = {"cmd": "ota", "version": self.version, "apply_s": self.apply_s, "bad": self.bad}` — 이번 단계 장치마다 보낼 명령을 만든다. 할 일 `ota`, 새 버전 문자열, 장치가 적용에 쓸 시간 `apply_s`(초), `bad`(참이면 장치는 적용 뒤 `state=fault` 를 내어 "켜자마자 고장 나는 펌웨어"를 흉내 낸다). 여기까지가 11/05 까지의 **흉내 경로**다.
- 189~194줄 `if self.manifest is not None:` 아래 네 줄 — **진짜 설치**(11/10)일 때 명령에 더 싣는 것. `url`(내려받을 파일 주소), `sha256`(그 파일의 지문), `size`(바이트 수), 그리고 `arch`(아키텍처별 항목 묶음). 매니페스트는 릴리스가 만든 목록 파일이고(장표 137), 장치는 `arch` 안에서 자기 아키텍처(x86_64 또는 aarch64) 항목을 골라 그 파일을 받는다 — 같은 명령을 보고 러너의 가상 장치와 Pi 가 서로 다른 파일을 받는다. 매니페스트가 없으면(`None`) 이 네 줄은 건너뛰고 흉내 경로가 된다. 장치는 명령에 `url` 이 있나로 두 길을 가른다(장표 065).
- 195줄 `self.w.send(device_id, cmd)` — `fleet/<id>/cmd` 토픽으로 QoS 1 명령을 보낸다(`FleetWatcher.send`, 119줄).
- 196줄 `self.updated.extend(batch)` — "지금까지 새 버전을 받은 모든 장치" 목록에 이번 단계 장치들을 더한다. 명령을 보낸 순간 더하는 이유: 되돌려야 할 때는 "적용이 끝난 장치"가 아니라 "명령을 받은 장치" 전부에 되돌리기 명령을 보내야 하기 때문이다. 다음 장표의 헬스 게이트와 롤백(081)이 이 목록을 쓴다.
- 198줄 `took, failed = self.wait_apply(batch)` — 적용 대기. 돌려받는 것이 둘이다: 걸린 시간(초, 시간 초과면 None)과 **설치에 실패한 장치 목록**.
- (빈 줄) 여기부터 아래 덩어리, `wait_apply`.
- 234줄 `def wait_apply(self, batch):` 와 독스트링(235~236줄) — "batch 전부가 새 버전을 보고할 때까지 기다린다. 설치에 실패한 장치(state=fault + ota_error)가 보이면 바로 멈춘다."
- 237~239줄 `start = time.monotonic()` / `while True:` / `snap = self.w.snapshot(batch)` — 시작 시각을 적고, 돌 때마다 batch 장치들의 가장 최근 텔레메트리 값(스냅샷)을 가져온다.
- 240~242줄 `failed = [d for d in batch if … "state") == "fault" and … "ota_error")]` / `if failed: return None, failed` — **설치 실패를 즉시 본다.** 장치는 설치가 어느 단계에서든 실패하면 `state=fault` 와 사유 `ota_error` 를 텔레메트리에 싣는다(장표 063 의 새 칸). 그런 장치가 하나라도 보이면 나머지를 기다리지 않고 돌아간다. 깨진 빌드를 헬스 대기(수 초)가 끝날 때까지 두지 않는 이유다.
- 243~244줄 `if all(… "fw") == self.version for d in batch): return time.monotonic() - start, []` — batch 의 모든 장치의 `fw` 가 새 버전이면 걸린 시간을 돌려준다. 서버는 장치에게 따로 묻지 않고, 이미 1 Hz 로 올라오는 텔레메트리의 버전 문자열을 본다.
- 245~246줄 `if time.monotonic() - start >= self.apply_timeout_s: return None, []` — 제한 시간을 넘기면 시간 초과. `apply_timeout_s` 는 따로 주지 않으면 `apply_s + 15초`(기본 2 + 15 = 17초), 진짜 배포에서는 매니페스트의 `rollout.apply_timeout_s`(릴리스는 60초).
- 247줄 `time.sleep(0.2)` — 0.2초마다 다시 본다.

장표에 보이지 않는 `run_stage` 의 199~212줄은 `wait_apply` 의 결과를 처리한다: 실패한 장치가 있으면 사유를 타임라인에 찍고 롤백(199~204줄), 시간 초과면 아직 안 바뀐 장치와 그 단계를 찍고 롤백(205~211줄), 둘 다 아니면 "단계 N%: 전원 적용 완료 (T초)"(212줄)를 찍고 헬스 게이트(장표 080)로 간다.

오른쪽 "읽는 포인트" 다섯 줄:
- "단계 = 누적 퍼센트(5 → 50 → 100). 50대의 5% = ceil(2.5) = 3대 — batch 는 '이번 단계에서 새로 받는 장치들'. 실물(kind=real)은 목록 맨 뒤라 마지막 단계에만 든다" — 위 183·185줄 설명.
- "보내기: fleet/<id>/cmd 에 {cmd: ota, version, apply_s, bad}. 매니페스트가 있으면(진짜 설치, 11/10) url · sha256 · size · arch 를 같이 보내고 장치가 자기 아키텍처 항목을 고른다. 없으면 흉내 경로 — bad=true 면 적용 뒤 state=fault" — 187~195줄.
- "적용 대기(wait_apply): 그 장치들의 fw_version 이 새 버전으로 바뀔 때까지 0.2초마다 본다. state=fault + ota_error 인 장치가 하나라도 보이면 그 자리에서 멈춘다 — 설치 실패는 헬스 대기를 기다리지 않고 바로 롤백" — 234~247줄.
- "시간(apply_timeout_s) 안에 안 바뀌면 시간 초과 → 롤백. 실패·시간 초과의 사유(ota_error · ota_stage)는 타임라인에 남긴다(run_stage 199-211줄)" — 장표에 안 보이는 처리 부분.
- "updated 에 '지금까지 새 버전을 받은 모든 장치'를 누적한다 — 다음 장의 헬스 게이트와 롤백이 이 목록을 쓴다" — 196줄.

## 3. 용어와 단위
- 메서드 / `self`: 파이썬 클래스 안의 함수와 그 객체 자신. `self.version` 은 "이번 배포의 버전".
- 독스트링(docstring): 함수 머리의 `"""…"""` 설명 글.
- f-string: `f"단계 {pct}%"` 처럼 중괄호 안 값을 글자에 끼워 넣는 파이썬 문법.
- 토픽 `fleet/<id>/cmd`: MQTT 의 주소. 장치 하나가 자기 이름의 cmd 토픽을 구독한다.
- QoS 1: 받았다는 확인을 받을 때까지 다시 보내는 전달 등급(장표 067).
- 매니페스트(manifest): 릴리스 하나의 목록 파일 — 버전, 아키텍처별 파일 이름·sha256·크기, 배포 정책(단계 비율·헬스 대기·제한 시간). 사람이 `--manifest <주소>` 로 주면 진짜 설치가 된다.
- sha256: 파일 내용에서 계산한 64자리 지문. 한 글자라도 다르면 지문이 달라진다. 장치가 받은 파일의 지문을 이것과 맞춰 본다.
- 아키텍처(arch): CPU 의 종류. 러너와 가상 장치는 x86_64, Pi 4 는 aarch64 — 같은 프로그램도 따로 빌드한 파일이 필요하다.
- `extend`: 목록 끝에 다른 목록의 원소를 모두 붙인다.
- 타임아웃(timeout): 기다리는 최대 시간. 넘으면 실패로 본다.
- 스냅샷(snapshot): 그 순간의 최신 값 복사본. `FleetWatcher` 가 텔레메트리를 들으며 장치별 `fw`, `state`, `kind`, `ota_stage`, `ota_error` 를 기억해 둔 것.
- ceil(올림): 2.5 → 3.

## 4. 쉬운 예시
학급 단체 문자 비유: 선생님(서버)이 "새 교재로 바꾸세요"라는 문자를 반 전체가 아니라 먼저 3명(5 %)에게만 보낸다(187~195줄). 진짜 배포라면 문자에 "교재를 받을 곳과 책의 바코드"(url · sha256)가 같이 적혀 있다. 보낸 사람 이름을 명단(`updated`)에 적어 둔다(196줄). 그리고 3명이 매일 보내는 일지(텔레메트리)를 보며 기다린다(234~247줄). 한 명이라도 "받은 책이 파본이라 못 바꿨다"(state=fault + ota_error)고 적으면 나머지를 기다리지 않고 바로 멈춘다. 모두 "바꿨어요"(fw 가 새 버전)면 걸린 시간을 적는다. 정해 둔 시간이 지나도 소식이 없으면 그것도 실패다.

숫자 예시: 50대, 5 % 단계 batch 3대. 흉내 경로(apply_s 1초)의 그림 078 실행은 "전원 적용 1.6초". 진짜 설치를 러너에서 잰 값(v0.9.0, 가상 50대)은 5 % 1.2초 → 50 %(22대) 2.2초 → 100 %(25대) 2.2초(장표 139). 장치는 1 Hz 로 보고하므로 이 숫자에는 "다음 보고까지 최대 1초"가 들어 있다. 깨진 패키지는 첫 단계 3대가 자가 점검에서 거부하고, `wait_apply` 가 그것을 1.0초에 보고 돌아왔다.

## 6. 자주 하는 오해·함정
- "서버가 장치에게 적용 완료를 따로 묻는다"는 오해. 묻지 않는다. 1 Hz 로 이미 오는 텔레메트리의 `fw_version` 과 `state` 를 볼 뿐이다 — 별도 프로토콜이 없어 단순하지만, 확인에 최대 1초의 지연이 있다.
- `batch` 와 `updated` 를 혼동하기 쉽다. `batch` 는 이번 단계에서 새로 받는 장치(3, 22, 25대), `updated` 는 지금까지 받은 누적(3, 25, 50대). 적용 대기는 `batch`, 헬스 게이트와 롤백은 `updated` 를 본다.
- 명령을 보내는 순간 `updated` 에 넣는다. 적용 확인 뒤에 넣으면, 적용 시간 초과로 롤백할 때 그 장치들이 명단에 없어 되돌리기 명령을 못 받는다.
- `bad` 는 흉내 경로의 실험용 표시다. 진짜 배포에서는 "나쁘다"는 표시가 없다 — 깨진 패키지는 자가 점검이 실패해 장치가 `fault` 와 사유를 알리고, 서버는 그것을 `wait_apply` 에서 본다. 릴리스 카나리가 일부러 깨진 패키지(`-bad`)를 만들어 이 길을 매번 확인한다.
- "설치 실패"와 "헬스 실패"는 다른 문이다. 앞의 것은 켜 보기 전에 거부된 것(이 장표, 즉시), 뒤의 것은 켜진 뒤에 아픈 것(다음 장표, health_wait 뒤).
- 11/05 의 설명에 있던 `make_all_applied_check` 는 없어졌다(`wait_apply` 가 대신한다). 옛 줄 번호로 찾으면 다른 코드가 나온다.
