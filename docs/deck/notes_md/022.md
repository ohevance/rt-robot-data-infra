# 장표 022 — 단계 4 들머리 — RT 스레드가 1 ms 마다 깬다: 늦게 깬 만큼이 전부 꼬리다 (표①)
*위치: 1부 로봇을 움직이는 길 · 단계 4/10 RT 1 ms 루프 · ① 들머리*

## 1. 이 장표가 왜 있나
단계 3(장표 017~021)의 결론은 "명령은 락 없는 우편함(링 64칸)에 들어 있고, RT 스레드가 꺼내 가면 된다"였다. 그러면 다음 질문이 자연스럽게 생긴다 — 누가, 언제 꺼내나? 답은 "RT 스레드가 1 ms 마다 '정확히' 깨서"다. 그런데 운영체제가 스레드를 정확히 1 ms 마다 깨워 준다는 보장은 기본으로 없다. 늦게 깨는 만큼(깨어남 지연)이 그 주기의 제어를 밀고, 그것이 1부 전체에서 가장 중요한 숫자인 표①이 된다. 이 장표는 단계 4 의 들머리로, 들어온 것 → 문제 → 기준 → 확인 방법 → 결과 → 판단 여섯 상자를 한 장에 둔다. 실험 자체(측정기, 백분위수, 실험 사슬 3장, 표①, 결론)는 3부 장표 89~95 로 미뤄 두고, 여기서는 결과 한 줄과 번호만 적는다.

## 2. 장표를 하나씩 읽기
여섯 상자는 왼쪽 위에서 시작해 뱀처럼 이어진다(첫 줄 왼쪽→오른쪽, 둘째 줄 오른쪽→왼쪽).

- 회색 상자 "들어온 것": "우편함(링)에 최신 명령이 들어 있다 (단계 3)". 앞 단계의 결과가 이 단계의 입력이다. 명령은 50 Hz 로 들어오고 우편함에서 기다리고 있다.
- 민트 상자 "문제": "1 ms 마다 '정확히' 깨는 스레드가 필요하다. 깨어남이 늦으면(깨어남 지연) 그 주기의 제어가 밀리고, 쌓이면 로봇이 멈칫한다. 평균이 아니라 최악(max)이 문제". 제어 루프는 1 kHz(1초에 1,000번)로 돌기로 했으므로 매 1 ms 마다 깨야 한다. 깨는 시각이 늦으면 그 주기의 "읽기 → 검사 → 로봇에 쓰기"가 통째로 늦는다. 평균이 18 us 라도 어쩌다 한 번 781 us 늦으면 그 한 번에 로봇이 명령을 놓친다 — 그래서 평균이 아니라 가장 늦은 한 번(max)을 본다.
- 노란 마름모 "기준": "부하 중에도 깨어남 지연 max < 200 us(1 ms 의 20%), 로깅 드롭 0, 측정 중 스로틀 0인가?". 세 조건이 한 마름모에 있다. ① 200 us 는 1 ms 예산 중 지연에 줄 몫(20%)이고 Pi 4 + RT 커널의 알려진 수준이기도 하다(E18 §1). "부하 중에도"가 붙은 이유는 한가할 때는 어느 커널이나 좋게 나오기 때문이다. ② 로깅 드롭 0 — 측정값을 벨트에 올릴 때 하나도 버리지 않아야 측정 자체가 믿을 만하다. ③ 스로틀 0 — Pi 4 는 80 °C 부터 클럭을 내리는데, 그 상태의 지연은 커널 탓인지 클럭 탓인지 가를 수 없으므로 스로틀이 걸린 측정은 표에 올리지 않는다.
- 파란 상자 "확인 방법": "RtLoop(준비 5단계 + 절대 시각 clock_nanosleep) · 측정기 jitter_bench + 표준 도구 cyclictest · Pi 4 에서 일반 → RT → 고정 → 격리 (E18, E19a~d) → 3부 장표 89~95". 확인은 두 겹이다. 코드 쪽: RtLoop 이 준비 5단계(메모리 고정, CPU 고정, SCHED_FIFO, 스택 미리 밟기 등)를 하고 절대 시각으로 잔다(장표 024~026). 측정 쪽: 내가 만든 측정기 jitter_bench 와 리눅스 표준 도구 cyclictest 를 같은 보드(Pi 4)에서 조건을 하나씩 바꿔 가며 돌렸다 — 일반 커널 → PREEMPT_RT 커널 → CPU 고정 → CPU 격리. 그 실험이 E18, E19-a/b/c/d 이고, 장표로는 3부 89~95번이다.
- 보라 테두리 상자 "결과": "jitter_bench 부하 max: 781(일반) → 301(RT) → 311(고정) → 189 us(격리). cyclictest 695 → 132. 도구 일치 274 vs 270. 비용: p99 146 → 185". 숫자를 하나씩 풀면: 부하(stress-ng) 중 깨어남 지연의 max 가 일반 커널 781.2 us, RT 커널 300.6 us, RT + CPU 3 고정 311.5 us, RT + CPU 3 격리 189.3 us. 표준 도구 cyclictest 도 같은 방향(일반 695 → RT 132 us). 두 도구를 같은 설정으로 맞추자 274 vs 270 us 로 일치해 "내 측정기가 틀린 것 아니냐"가 닫혔다. 비용: RT 커널은 공짜가 아니어서 부하 중 p99 가 146 → 185 us 로 조금 나빠졌다(상한을 사고 평균 근처를 조금 내준 것).
- 진한 둥근 상자 "판단 → 다음": "RT 커널 + isolcpus=3 으로 통과(189 us) → 단계 5. 비용(p99 조금 나빠짐)도 표에 그대로". 189 us < 200 us 이므로 기준을 넘었다. 나빠진 p99 도 숨기지 않고 표에 둔다 — 그래야 "RT 커널이면 다 좋아진다"는 오해를 막는다.
- 맨 아래 설명 상자: "이 단계의 장표: ② 준비 5단계 코드(1장) · 루프 본체 코드(2장). 측정기·백분위수·실험 사슬 3장·표①·결론은 3부 검증. 넘어가는 조건: 기준 200 us 를 넘은 조건(일반·RT·고정)마다 '왜 못 넘었나'가 다음 실험을 낳았고, 격리에서 넘었다". 즉 단계 4 안의 장표는 코드 3장(024·025·026)과 그림 1장(023)뿐이고, 실험은 3부로 갔다. "넘어가는 조건"은 단순히 189 가 나왔다는 것이 아니라, 못 넘은 조건마다 원인을 묻고 다음 실험으로 이어진 끝에 넘었다는 것이다(일반 781 → "커널 탓인가" → RT 301 → "CPU 를 옮겨 다녀서인가" → 고정 311, 효과 없음 → "그 CPU 의 다른 일 때문인가" → 격리 189).

## 3. 용어와 단위
- us(마이크로초): 100만분의 1초. 1 ms = 1,000 us. 200 us = 0.2 ms.
- 깨어남 지연(wake-up latency): "이 시각에 깨워 달라"고 한 시각과 실제로 깬 시각의 차이. 표①의 주인공.
- max / p99 / p99.9: 가장 나쁜 한 번 / 100번 중 99번이 이 값 이내 / 1,000번 중 999번이 이 값 이내. 제어 루프는 max 와 p99.9 로 판단한다.
- 부하(stress): stress-ng 로 CPU·입출력·메모리를 일부러 바쁘게 만든 상태. 한가할 때 좋은 숫자는 증거가 못 된다.
- PREEMPT_RT: 급한 스레드가 오면 커널이 하던 일을 중단하고 비켜 주게 만드는 리눅스 패치(실시간 커널). `/sys/kernel/realtime` = 1.
- isolcpus=3: 커널 부팅 인자. CPU 3 을 일반 스케줄링에서 떼어 두어 RT 스레드만 올린다. "고정(pin)"은 스레드를 그 CPU 에 묶기만 하는 것이고, "격리"는 그 CPU 에 다른 일이 못 올라오게 하는 것이다.
- 스로틀(throttle): Pi 4 가 80 °C 부터 클럭을 내리는 보호 동작. `get_throttled` 플래그가 0 이어야 깨끗한 측정.
- 로깅 드롭: 측정값을 벨트(링)에 올리다 꽉 차서 버린 수. 0 이어야 통계가 전부 반영된 것이다.
- cyclictest: 리눅스 실시간 지연을 재는 표준 도구. jitter_bench 는 이 저장소의 측정기(RtLoop 를 그대로 쓴다).

## 4. 쉬운 예시
- 비유: 알람을 매 분 정각에 맞춰 두고 "몇 초 늦게 일어났나"를 60,000번 재는 것과 같다. 평균 0.02초 늦게 일어나도, 한 번 0.8초 늦으면 그날 기차는 놓친다. 그래서 가장 늦은 한 번(max)을 본다. 집이 조용할 때(한가)만 재면 의미가 없고, 아이들이 뛰어다닐 때(부하)도 0.2초 안에 일어나야 합격이다.
- 숫자 예시: 1 ms 주기에서 깨어남 지연 781 us 면 남은 시간은 219 us 뿐 — 제어 계산과 로봇 쓰기가 그 안에 끝나야 하고 다음 주기가 밀릴 위험이 크다. 189 us 면 811 us 가 남는다. 2 kHz(500 us 주기)였다면 781 us 는 아예 한 주기를 통째로 넘긴다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 781.2 / 300.6 / 311.5 / 189.3 us (jitter_bench, 부하, 60초) 와 695 / 132 us (cyclictest, 부하, 120초) 는 `docs/measurements/table1_pi4.md` 의 pi4_generic_stress · pi4_rt_stress · pi4_rt_stress_pin · pi4_rt_stress_isol 줄과 cyclictest 줄. 전부 스로틀 0, 드롭 0.
- 확인: 274 vs 270 은 같은 표의 pi4_rt_stress_cpu2_p80(cyclictest, max 274) 과 pi4_rt_stress_pin_work0(jitter_bench, max 270.0) 줄. 해석은 `docs/experiments/E19d.md`.
- 확인: 비용 p99 146 → 185 는 같은 표의 jitter_bench 부하 줄 p99 145.7 → 185.2 (장표는 반올림).
- 확인: 합격선 200 us 의 근거는 `docs/experiments/E18.md` §1, `E19c.md` §1.
- 다시 보려면: `cat docs/measurements/table1_pi4.md`, 실험 사슬은 `docs/EXPERIMENTS.md` §0 표① 순서도, 장표로는 3부 89~95.

## 6. 자주 하는 오해·함정
- "SCHED_FIFO 로 우선순위를 올리면 해결된다"는 오해 — WSL 에서 p50 은 92 → 37 us 로 좋아졌지만 max 는 921 → 937 로 그대로였다(E02). 우선순위는 줄을 앞세울 뿐이고 꼬리를 자르는 것은 커널이다.
- "CPU 하나를 주면 된다"는 오해 — 고정(pin)만으로는 301 → 311 로 효과가 없었다. 그 CPU 에서 stress·IRQ 스레드·커널 스레드가 그대로 돌기 때문이다. 격리(isolcpus)가 따로 필요했다.
- 한가할 때 max(일반 24.9 / RT 27.8 us)는 커널과 무관하게 같다. 차이는 부하 중에만 난다 — 그래서 기준에 "부하 중에도"가 붙어 있다.
- 11/04 함정: 부하 75초에 Pi 가 45 → 75 °C 까지 올라 80 °C 스로틀 직전이었다 → 부하 측정은 120초 상한, 온도·스로틀을 .meta 에 기록(DECISIONS 11/04).

## 7. 면접 한 문장
"1 ms 루프의 깨어남 지연은 평균이 아니라 max 로 보고, 부하 중 200 us 를 기준으로 삼았습니다 — Pi 4 에서 일반 커널 781, RT 커널 301, CPU 고정 311, 격리 189 us 였고 표준 도구 cyclictest 도 같은 방향이었습니다. RT 커널의 비용(p99 146 → 185)도 표에 그대로 적었습니다."
