# 장표 120 — CI 잡 2 — fleet_integration (2단계, 러너 VM 2, 약 2분): 진짜 컨테이너에서 장애 3종 + 롤백 + OTA
*위치: 6부 믿을 수 있나 · CI 잡 2 fleet_integration*

## 1. 이 장표가 왜 있나

바로 앞 장표(119, CI 잡 1)에서 "1단계는 가짜 브로커·가짜 DB 위에서 1분 안에 논리를 검사한다"는 것을 봤다. 그러면 당연한 질문이 생긴다 — "가짜 위에서 통과한 것이 진짜 브로커·진짜 DB 위에서도 되나?" 이 장표는 그 질문에 답하는 두 번째 잡(job) `fleet_integration` 을 순서도로 보여 준다. GitHub 가 새로 빌려 준 리눅스 가상 머신(러너 VM 2) 위에 진짜 Mosquitto(MQTT 브로커)와 TimescaleDB(시계열 DB) 컨테이너를 띄우고, 2부에서 본 장애 3종·나쁜 펌웨어 롤백·정상 OTA 를 전부 다시 돌린 뒤, 판정 프로그램이 "유실 0 · 복구됨 · 롤백됨" 규칙으로 통과/실패를 가른다. 6부의 질문 "이 숫자들을 누가, 무엇으로, 언제 다시 재나?"에 대한 답의 한 조각이다 — 3부 검증(표③)에서 본 유실 0 이 사람 손이 아니라 매 push 마다 기계가 다시 확인하는 숫자라는 뜻이다.

## 2. 장표를 하나씩 읽기

순서도는 왼쪽 위에서 시작해 뱀처럼 내려온다. 회색 상자 = 앞에서 들어온 것, 민트 상자 = 실행 단계, 마름모 = 판단 기준, 파란 상자 = 확인 방법, 진한 상자 = 결론이다.

- 회색 상자 "잡 1 통과(needs: rt_core) → 새 VM 에 pip install": 이 잡은 혼자 시작하지 않는다. `.github/workflows/ci.yml` 에 `needs: rt_core` 라고 적혀 있어서 잡 1(rt_core)이 통과해야만 시작한다. 1단계가 떨어지면 2단계는 돌지도 않는다 — 싼 검사부터 하고 비싼 검사는 그 다음이라는 결정(DECISIONS 11/03 D4)이 여기서 코드로 보인다. 러너는 매번 새로 받는 빈 가상 머신(ubuntu-24.04)이라 파이썬 패키지(`pip install`)부터 다시 깐다.
- 민트 상자 "docker compose up mqtt db → migrate.py --wait 120 (TCP 로 진짜 붙어 볼 때까지)": 통합 테스트 스크립트 `fleet/tests/integration.sh` 의 1단계. 브로커와 DB 컨테이너 두 개를 띄우고, `fleet/db/migrate.py --wait 120` 이 최대 120초 동안 "DB 가 진짜 준비됐나"를 기다린다. 숫자 120 은 초 단위의 시간 제한이다.
- 마름모 "DB 가 진짜 준비됐나? (pg_isready 는 임시 서버에도 '예'라 한다)": 왜 이 기준이 따로 있나. TimescaleDB 컨테이너는 첫 기동 때 초기화용 임시 서버를 잠깐 띄웠다가 내리고 진짜 서버를 올린다. 컨테이너 안의 `pg_isready` 명령은 그 임시 서버에도 "준비됨"이라고 답한다. 그래서 11/04 CI 1차 실행이 "DB 준비됨"을 믿고 달려들었다가 실패했다(사고 표, 장표 128). 고친 방법은 수집기와 같은 길(TCP 접속)로 밖에서 진짜 붙어 보는 것이고, 그래서 이 마름모의 답은 "예 → 계속 / 시간 초과 → 잡 실패 (11/04 1차 실패 자리)"다. 즉 120초 안에 진짜 접속이 안 되면 이 잡은 여기서 빨갛게 끝난다.
- 파란 상자 "수집기(QoS 1) + 가상 장치 10대 2 Hz → 장애 주입 broker · db · collector 5초(settle 8)": 수집기를 지속 세션(`--qos 1`)으로 띄우고 가상 장치 10대를 1초에 2번(2 Hz)씩 보내게 한다. 러너는 작은 컴퓨터라 내 PC 의 50대 1 Hz 대신 10대 2 Hz 다. 그 위에 `fleet/chaos/inject.py` 로 브로커 중단·DB 중단·수집기 종료를 각각 5초씩 일으키고, 8초(settle)를 기다려 가라앉은 뒤 숫자를 잰다.
- 파란 상자 "나쁜 펌웨어 inject --fault bad_firmware(롤백돼야 정상) → 정상 OTA 1.1.0": 일부러 고장 나는 펌웨어를 5%→50%→100% 단계 배포로 내려 롤백이 일어나는지 본다. `inject.py` 는 결과 파일을 쓰면 종료 코드 0 을 내고(줄 끝 `|| true` 는 안전장치), 롤백이 실제로 됐는지는 다음 판정 단계가 결과 파일로 확인한다. 그 다음 정상 펌웨어 1.1.0 을 끝까지 배포한다.
- 마름모 "assert_results.py: 유실 0 · 복구됨 · 롤백됨 · OTA success?": `fleet/chaos/assert_results.py` 가 결과 JSON 5개를 규칙으로 판정한다. broker 장애는 유실 ≤ 장치 수, db 는 유실 0 과 backlog 0 복귀, collector(qos1)는 유실 0, 나쁜 펌웨어는 닿은 장치 = 5% 와 롤백 시간 존재, 정상 OTA 는 success=true. 답은 "예 → ✓ / 아니오 → 실패 줄에 어느 규칙인지" — 떨어지면 로그에 어느 규칙이 깨졌는지가 한 줄로 찍힌다.
- 진한 상자 "✓ table3_ci.md → 아티팩트 fleet-integration (11/05 실측 0/318 · 0/286 · 0/280, 롤백 0.4초)": 통과하면 `scripts/make_table3.py` 가 표③-2 를 `table3_ci.md` 로 만들어 GitHub 아티팩트(내려받을 수 있는 결과 파일 묶음) `fleet-integration` 으로 남긴다. 숫자는 broker 장애 유실 0 / 318, db 장애 0 / 286, collector 장애 0 / 280 — "/" 뒤는 그 장애 창에서 장치들이 만들었어야 할 메시지 수이고, 앞은 그중 잃은 수다. 롤백 0.4초는 나쁜 펌웨어를 되돌리는 데 걸린 시간이다. 러너(10대 2 Hz) 실측이며 내 PC(50대 1 Hz)의 0 / 1400 · 0 / 1341 · 0 / 1311 · 롤백 1.0초와 같은 모양이다.
- 아래 설명 상자: "2단계의 뜻: 가짜 위에서 맞던 논리가 진짜 브로커·DB 위에서도 맞는지 한 번 더. CI 가 실제로 잡은 2건이 전부 이 잡이다(TimescaleDB 초기화 경쟁 · request_stop 삭제)". 두 사고 모두 1단계(가짜)는 초록이었고 이 잡만 빨갰다 — 가짜 테스트로는 못 잡는 종류였다는 뜻이다.

## 3. 용어와 단위

- CI(Continuous Integration, 지속 통합): 코드를 올릴(push) 때마다 자동으로 빌드하고 테스트하는 일. 여기서는 GitHub Actions 가 한다.
- 잡(job)과 러너(runner): 잡은 한 묶음의 할 일, 러너는 그 잡을 돌리는 GitHub 의 가상 머신. 잡 3개는 각각 다른 러너(새 VM)에서 돈다. `needs:` 는 "이 잡이 끝나야 나를 시작하라"는 선후 관계.
- 컨테이너(docker compose): 브로커·DB 같은 프로그램을 설치 없이 상자째 띄우는 방식. `up` 은 띄우기, `stop`/`start` 는 멈추기/다시 켜기.
- QoS 1 · 지속 세션: MQTT 에서 "받았다는 확인(PUBACK)까지 하는 전달"과 "구독자가 없는 동안 브로커가 대신 들고 있는 것". 수집기가 죽어 있어도 메시지가 안 사라지는 이유.
- Hz(헤르츠): 1초에 몇 번. 2 Hz = 0.5초마다 한 번. 10대 × 2 Hz = 초당 20개.
- 유실 "0 / 318": 318 = 장애 창 동안 만들었어야 할 메시지 수(장치별 일련번호 seq 로 센다), 0 = 그중 못 받은 수.
- 아티팩트(artifact): 잡이 끝난 뒤 내려받을 수 있게 남기는 결과 파일.
- 종료 코드(exit code): 프로그램이 끝나며 남기는 숫자. 0 = 성공, 그 외 = 실패. 롤백은 "배포 실패"라 1 을 돌려주는 것이 맞다.

## 4. 쉬운 예시

- 비유: 새 요리법(코드)을 집 주방(가짜 환경)에서 먼저 해 보고(1단계), 통과하면 실제 식당 주방(진짜 브로커·DB)에서 손님 10명(가상 장치 10대)을 받으며 한 번 더 해 본다(2단계). 그 사이 일부러 가스를 5초 끊고(브로커 중단), 냉장고를 5초 끄고(DB 중단), 요리사를 5초 내보냈다가(수집기 종료) 주문이 하나도 안 빠졌는지(유실 0) 센다.
- 숫자 예시: 10대가 2 Hz 로 보내면 초당 20개. 브로커가 5초 멈추면 약 100개가 "보호 없었다면" 사라질 양이다(표③-2 CI 줄의 '보호 없었다면' 100). 실측은 0 / 318 — 창 전체(장애 5초 + 가라앉힘 8초 등)에서 만들어진 318개 중 0개를 잃었다.

## 6. 자주 하는 오해·함정

- "컨테이너가 떴으니 DB 도 준비됐다"는 오해: TimescaleDB 는 첫 기동 때 임시 서버를 잠깐 띄운다. `pg_isready` 는 그것도 준비됨이라 하므로 밖에서 TCP 로 진짜 붙어 봐야 한다. 11/04 CI 1차 실패의 원인이었다(내 PC 에서는 볼륨에 데이터가 이미 있어 이 경쟁이 안 보였다).
- "fleet 단위 테스트 15건이 초록이면 수집기는 멀쩡하다"는 오해: 11/05 `request_stop` 함수가 통째로 지워졌는데 단위 테스트는 Collector 클래스만 쓰고 `main()` 을 안 타서 못 잡았고, 이 잡만 "장치 0대"로 빨갰다. 그래서 main() 한 바퀴 스모크 테스트(`test_main_entry_smoke`)를 추가했다.
- `rollout.py --bad` 를 직접 부르면 롤백 때 종료 코드가 1 이지만, 통합 스크립트는 `inject.py` 를 거쳐 부르므로 0 이다. integration.sh 44줄 주석('종료 코드 1 이 정상')은 옛 설명이라 헷갈리기 쉽다.
- 러너의 숫자(10대 2 Hz)와 내 PC 의 숫자(50대 1 Hz)는 규모가 다르다. 비교할 것은 "모양"(유실 0, 복구 수초)이지 절대값이 아니다.
