# 장표 120 — CI 잡 2 — fleet_integration (2단계, 러너 VM 2, 약 2분 30초): 진짜 컨테이너에서 장애 3종 + 롤백 + OTA + 진짜 산출물 설치
*위치: 6부 믿을 수 있나 · CI 잡 2 fleet_integration*

## 1. 이 장표가 왜 있나

바로 앞 장표(119, CI 잡 1)에서 "1단계는 가짜 브로커·가짜 DB 위에서 1분 안에 논리를 검사한다"는 것을 봤다. 그러면 당연한 질문이 생긴다 — "가짜 위에서 통과한 것이 진짜 브로커·진짜 DB 위에서도 되나?" 이 장표는 그 질문에 답하는 두 번째 잡(job) `fleet_integration` 을 순서도로 보여 준다. GitHub 가 새로 빌려 준 리눅스 가상 머신(러너 VM 2) 위에 진짜 Mosquitto(MQTT 브로커)와 TimescaleDB(시계열 DB) 컨테이너를 띄우고, 2부에서 본 장애 3종·나쁜 펌웨어 롤백·정상 OTA 를 전부 다시 돌리고, 11/10 부터는 진짜 릴리스 패키지를 장치에 깔아 보고 깨진 패키지가 거부되는지도 본 뒤, 판정 프로그램이 "유실 0 · 복구됨 · 롤백됨 · 설치됨 · 거부됨" 규칙으로 통과/실패를 가른다. 6부의 질문 "이 숫자들을 누가, 무엇으로, 언제 다시 재나?"에 대한 답의 한 조각이다 — 3부 검증(표③)에서 본 유실 0 이 사람 손이 아니라 매 push 마다 기계가 다시 확인하는 숫자라는 뜻이다.

## 2. 장표를 하나씩 읽기

순서도는 왼쪽 위에서 시작해 뱀처럼 내려온다. 회색 상자 = 앞에서 들어온 것, 민트 상자 = 실행 단계, 마름모 = 판단 기준, 파란 상자 = 확인 방법, 진한 상자 = 결론이다. 상자는 여덟 개다(11/05 에는 일곱 개 — 진짜 패키지 설치 상자가 하나 늘었고, 글자가 조금 작아졌다).

- 회색 상자 "잡 1 통과(needs: rt_core) → 새 VM 에 pip install + cmake(패키지에 넣을 jitter_bench)": 이 잡은 혼자 시작하지 않는다. `.github/workflows/ci.yml` 에 `needs: rt_core` 라고 적혀 있어서 잡 1(rt_core)이 통과해야만 시작한다. 1단계가 떨어지면 2단계는 돌지도 않는다 — 싼 검사부터 하고 비싼 검사는 그 다음이라는 결정(DECISIONS 11/03 D4)이 여기서 코드로 보인다. 러너는 매번 새로 받는 빈 가상 머신(ubuntu-24.04)이라 파이썬 패키지(`pip install`)부터 다시 깐다. 11/10 부터는 cmake 와 g++ 도 깐다 — 릴리스 패키지 안에 넣을 실행 파일(`jitter_bench`)을 이 러너에서 빌드해야 하기 때문이다(앞 잡의 빌드 결과는 다른 VM 에 있어 쓸 수 없다).
- 민트 상자 "릴리스 패키지(정상 · 깨진 것) → 로컬 HTTP / docker compose up mqtt db → migrate.py --wait 120": 통합 테스트 스크립트 `fleet/tests/integration.sh` 의 0단계와 1단계. 0단계(11/10)는 릴리스 때와 같은 스크립트(`scripts/package_release.sh`)로 정상 패키지와 일부러 깨뜨린 패키지를 만들어, 이 러너 안에서만 닿는 작은 웹 서버(127.0.0.1:8089)로 내준다 — 뒤의 4b · 4c 에서 장치가 여기서 내려받는다. 1단계는 브로커와 DB 컨테이너 두 개를 띄우고, `fleet/db/migrate.py --wait 120` 이 최대 120초 동안 "DB 가 진짜 준비됐나"를 기다린다. 숫자 120 은 초 단위의 시간 제한이다.
- 마름모 "DB 가 진짜 준비됐나? (pg_isready 는 임시 서버에도 '예'라 한다)": 왜 이 기준이 따로 있나. TimescaleDB 컨테이너는 첫 기동 때 초기화용 임시 서버를 잠깐 띄웠다가 내리고 진짜 서버를 올린다. 컨테이너 안의 `pg_isready` 명령은 그 임시 서버에도 "준비됨"이라고 답한다. 그래서 11/04 CI 1차 실행이 "DB 준비됨"을 믿고 달려들었다가 실패했다(사고 표, 장표 128). 고친 방법은 수집기와 같은 길(TCP 접속)로 밖에서 진짜 붙어 보는 것이고, 그래서 이 마름모의 답은 "예 → 계속 / 시간 초과 → 잡 실패 (11/04 1차 실패 자리)"다. 즉 120초 안에 진짜 접속이 안 되면 이 잡은 여기서 빨갛게 끝난다.
- 파란 상자 "수집기(QoS 1) + 가상 장치 10대 2 Hz(A/B 슬롯) → 장애 주입 broker · db · collector 5초(settle 8)": 수집기를 지속 세션(`--qos 1`)으로 띄우고 가상 장치 10대를 1초에 2번(2 Hz)씩 보내게 한다. "(A/B 슬롯)"은 장치마다 설치 자리 폴더를 준다는 뜻이다(`--slot-root`) — 이것이 있어야 뒤에서 진짜 설치를 한다. 러너는 작은 컴퓨터라 내 PC 의 50대 1 Hz 대신 10대 2 Hz 다. 그 위에 `fleet/chaos/inject.py` 로 브로커 중단·DB 중단·수집기 종료를 각각 5초씩 일으키고, 8초(settle)를 기다려 가라앉은 뒤 숫자를 잰다.
- 파란 상자 "나쁜 펌웨어 inject --fault bad_firmware(롤백돼야 정상) → 정상 OTA 1.1.0 (흉내)": 일부러 고장 나는 펌웨어를 5%→50%→100% 단계 배포로 내려 롤백이 일어나는지 본다. `inject.py` 는 결과 파일을 쓰면 종료 코드 0 을 내고(줄 끝 `|| true` 는 안전장치), 롤백이 실제로 됐는지는 다음 판정 단계가 결과 파일로 확인한다. 그 다음 정상 펌웨어 1.1.0 을 끝까지 배포한다. "(흉내)"는 이 두 배포가 버전 문자열만 바꾸는 경로라는 표시다 — 다음 상자와 구분하려고 붙였다.
- 파란 상자 "4b 산출물 OTA: 내려받기 → sha256 → 슬롯 → 자가 점검 → 전환 / 4c 깨진 패키지: 첫 단계에서 거부·롤백"(11/10): 같은 배포기에 매니페스트를 주어 **진짜 파일**을 깔게 한다. 4b 는 정상 패키지 — 장치 10대가 1 → 5 → 10대 순서로 파일을 내려받고, 지문(sha256)을 맞추고, 자기 슬롯에 풀고, 켜 보고(자가 점검), 통과하면 전환한다. 4c 는 자가 점검이 무조건 실패하는 패키지 — 첫 단계의 1대가 거부하고, 배포기가 그것을 보자마자 되돌린다. 나머지 9대에는 닿지 않는다. 코드는 장표 118, 장치 쪽 설치는 장표 138.
- 마름모 "assert_results.py (JSON 7개) 유실 0 · 복구 · 롤백 · OTA · 거부?": `fleet/chaos/assert_results.py` 가 결과 JSON 7개(11/05 에는 5개 — 4b · 4c 의 둘이 늘었다)를 규칙으로 판정한다. broker 장애는 유실 ≤ 장치 수, db 는 유실 0 과 backlog 0 복귀, collector(qos1)는 유실 0, 나쁜 펌웨어는 닿은 장치 = 5% 와 롤백 시간 존재, 정상 OTA 는 success=true, 진짜 설치는 전 장치 갱신과 결과에 남은 sha256, 깨진 패키지는 롤백으로 끝났고 닿은 장치가 첫 단계뿐이며 타임라인에 "설치 실패"가 있을 것("거부?"가 이 규칙이다). 답은 "예 → ✓ / 아니오 → 실패 줄에 어느 규칙인지" — 떨어지면 로그에 어느 규칙이 깨졌는지가 한 줄로 찍힌다.
- 진한 상자 "✓ table3_ci.md → 아티팩트 fleet-integration (11/05 실측 0/318 · 0/286 · 0/280, 롤백 0.4초)": 통과하면 `scripts/make_table3.py` 가 표③-2 를 `table3_ci.md` 로 만들어 GitHub 아티팩트(내려받을 수 있는 결과 파일 묶음) `fleet-integration` 으로 남긴다. 숫자는 broker 장애 유실 0 / 318, db 장애 0 / 286, collector 장애 0 / 280 — "/" 뒤는 그 장애 창에서 장치들이 만들었어야 할 메시지 수이고, 앞은 그중 잃은 수다. 롤백 0.4초는 나쁜 펌웨어를 되돌리는 데 걸린 시간이다. 러너(10대 2 Hz) 실측이며 내 PC(50대 1 Hz)의 0 / 1400 · 0 / 1341 · 0 / 1311 · 롤백 1.0초와 같은 모양이다.
- 아래 설명 상자: "2단계의 뜻: 가짜 위에서 맞던 논리가 진짜 브로커·DB 위에서도 맞는지 한 번 더. CI 가 실제로 잡은 3건이 전부 이 잡이다(11/04 TimescaleDB 초기화 경쟁 · 11/05 request_stop 삭제 · 11/10 상대 경로 슬롯에서 자가 점검 exit 127). 걸린 시간은 11/11 의 두 실행이 2분 25초 · 2분 34초". 세 사고 모두 1단계(가짜)는 초록이었고 이 잡만 빨갰다 — 그때의 단위 테스트로는 못 잡는 종류였다는 뜻이다. 셋째(11/10)는 4b 단계가 처음 러너에서 돌았을 때다: 장치의 슬롯 폴더를 상대 경로로 주었는데 설치 코드가 슬롯 안으로 들어가 자가 점검을 돌리며 그 상대 경로를 그대로 써서, 스크립트를 못 찾았다(종료 코드 127). 단위 테스트는 임시 폴더(절대 경로)만 썼다. 그리고 그 빨강을 3시간 동안 보지 못했다 — 패치 다섯 개를 한꺼번에 push 하고 CI 를 확인하지 않았다(장표 141 의 "같은 실수 두 번"). 잡 시간이 11/04 의 1분 52초에서 약 2분 30초로 늘어난 것은 0단계(패키지 빌드)와 4b · 4c 때문이다.

## 3. 용어와 단위

- CI(Continuous Integration, 지속 통합): 코드를 올릴(push) 때마다 자동으로 빌드하고 테스트하는 일. 여기서는 GitHub Actions 가 한다.
- 잡(job)과 러너(runner): 잡은 한 묶음의 할 일, 러너는 그 잡을 돌리는 GitHub 의 가상 머신. 잡 3개는 각각 다른 러너(새 VM)에서 돈다. `needs:` 는 "이 잡이 끝나야 나를 시작하라"는 선후 관계.
- 컨테이너(docker compose): 브로커·DB 같은 프로그램을 설치 없이 상자째 띄우는 방식. `up` 은 띄우기, `stop`/`start` 는 멈추기/다시 켜기.
- QoS 1 · 지속 세션: MQTT 에서 "받았다는 확인(PUBACK)까지 하는 전달"과 "구독자가 없는 동안 브로커가 대신 들고 있는 것". 수집기가 죽어 있어도 메시지가 안 사라지는 이유.
- Hz(헤르츠): 1초에 몇 번. 2 Hz = 0.5초마다 한 번. 10대 × 2 Hz = 초당 20개.
- 유실 "0 / 318": 318 = 장애 창 동안 만들었어야 할 메시지 수(장치별 일련번호 seq 로 센다), 0 = 그중 못 받은 수.
- 아티팩트(artifact): 잡이 끝난 뒤 내려받을 수 있게 남기는 결과 파일.
- 종료 코드(exit code): 프로그램이 끝나며 남기는 숫자. 0 = 성공, 그 외 = 실패. 롤백은 "배포 실패"라 1 을 돌려주는 것이 맞다. 127 은 "그런 명령(파일)이 없다".
- 산출물 OTA / 릴리스 패키지: 버전 문자열이 아니라 빌드가 만든 파일(tar.gz)을 장치가 받아 설치하는 배포와 그 파일. sha256 은 파일의 지문, A/B 슬롯은 버전마다 폴더를 따로 두는 설치 자리, 자가 점검은 새 버전을 켜기 전에 장치가 돌려 보는 검사다(장표 138).

## 4. 쉬운 예시

- 비유: 새 요리법(코드)을 집 주방(가짜 환경)에서 먼저 해 보고(1단계), 통과하면 실제 식당 주방(진짜 브로커·DB)에서 손님 10명(가상 장치 10대)을 받으며 한 번 더 해 본다(2단계). 그 사이 일부러 가스를 5초 끊고(브로커 중단), 냉장고를 5초 끄고(DB 중단), 요리사를 5초 내보냈다가(수집기 종료) 주문이 하나도 안 빠졌는지(유실 0) 센다.
- 4b · 4c 를 비유에 보태면: 새 식재료 상자를 실제로 받아 본다. 멀쩡한 상자는 요리사 10명이 차례로(1 → 5 → 10명) 받아 쓰고, 일부러 상하게 한 상자는 첫 요리사가 열어 보고 돌려보낸다 — 나머지 9명은 그 상자를 본 적도 없다.
- 숫자 예시: 10대가 2 Hz 로 보내면 초당 20개. 브로커가 5초 멈추면 약 100개가 "보호 없었다면" 사라질 양이다(표③-2 CI 줄의 '보호 없었다면' 100). 실측은 0 / 318 — 창 전체(장애 5초 + 가라앉힘 8초 등)에서 만들어진 318개 중 0개를 잃었다.

## 5. 숫자의 출처와 다시 확인하는 법

- 확인: 유실 0 / 318 · 0 / 286 · 0 / 280, 롤백 0.4초 — `docs/measurements/table3_ci.md`(표③-2, 측정 2026-11-04 03:50 UTC) 와 `docs/experiments/E13.md`. 장표 제목의 "11/05 실측"은 CI 가 11/05 에도 같은 값으로 초록이었다는 뜻이고, 표에 적힌 원본 측정 시각은 11/04 다.
- 확인: 10대 2 Hz, 장애 5초, settle 8, `--wait 120`, 정상 OTA 1.1.0, 4b · 4c — `fleet/tests/integration.sh` 안의 `COUNT=10`, `RATE=2`, `--duration 5 --settle 8`, `migrate.py --wait 120`, `--version 1.1.0`, `--manifest …/manifest.json` · `manifest-bad.json`(68~71줄), 판정에 넘기는 파일 7개(74~75줄).
- 확인: `needs: rt_core`, cmake · g++ 설치(90~91줄), `timeout-minutes: 15`, 아티팩트 이름 `fleet-integration` — `.github/workflows/ci.yml` 의 fleet_integration 잡(81~101줄 — 11/11 에 rt_core 잡에 ZeroMQ 단계 7줄이 들어가 74~94 에서 밀렸다).
- 확인: 잡 시간 — 11/04 의 1분 52초는 `docs/experiments/E13.md` 와 `docs/LOG.md` 11/04, 11/11 의 2분 25초 · 2분 34초는 `docs/LOG.md` 11/11(작성자가 `gh run view` 로 본 값). 지금 값은 `gh run view <ID>`.
- 확인: 셋째 사고(11/10) — `docs/LOG.md` 2026-11-10 밤 "CI 가 3시간 빨강이었다", `docs/ENVIRONMENT.md` §5 의 사고 표.
- 주의: 진한 상자의 숫자(0/318 · 0/286 · 0/280, 0.4초)는 11/04 실행의 값이다. 4b · 4c 의 러너 값(10대)은 저장소에 사본을 두지 않았다 — 같은 일을 50대로 한 릴리스 카나리의 값이 장표 139 에 있다.
- 다시 보는 법: `gh run list -L 3` 로 최근 실행 3개의 ✓/✗, `gh run view <ID> --log-failed | tail -40` 으로 실패한 줄. WSL 에서 같은 스크립트: `bash fleet/tests/integration.sh`(약 3~4분, docker 가 떠 있어야 한다).

## 6. 자주 하는 오해·함정

- "컨테이너가 떴으니 DB 도 준비됐다"는 오해: TimescaleDB 는 첫 기동 때 임시 서버를 잠깐 띄운다. `pg_isready` 는 그것도 준비됨이라 하므로 밖에서 TCP 로 진짜 붙어 봐야 한다. 11/04 CI 1차 실패의 원인이었다(내 PC 에서는 볼륨에 데이터가 이미 있어 이 경쟁이 안 보였다).
- "fleet 단위 테스트가 초록이면 수집기는 멀쩡하다"는 오해: 11/05 `request_stop` 함수가 통째로 지워졌는데 단위 테스트는 Collector 클래스만 쓰고 `main()` 을 안 타서 못 잡았고, 이 잡만 "장치 0대"로 빨갰다. 그래서 main() 한 바퀴 스모크 테스트(`test_main_entry_smoke`)를 추가했다.
- `rollout.py --bad` 를 직접 부르면 롤백 때 종료 코드가 1 이지만, 통합 스크립트는 `inject.py` 를 거쳐 부르므로 0 이다. integration.sh 63줄 주석('종료 코드 1 이 정상')은 옛 설명이라 헷갈리기 쉽다.
- "4b 는 러너에서 만든 x86_64 패키지니까 실물과 무관하다"는 오해: 파일은 다르지만 **길은 같다** — 같은 패키지 스크립트, 같은 매니페스트 형식, 같은 장치 설치 코드(`ota_apply.install`). 아키텍처가 다른 실물(Pi, aarch64) 패키지는 릴리스 워크플로가 arm 러너에서 따로 만들고, Pi 가 받아 설치한 기록이 E22 에 있다.
- 러너의 숫자(10대 2 Hz)와 내 PC 의 숫자(50대 1 Hz)는 규모가 다르다. 비교할 것은 "모양"(유실 0, 복구 수초)이지 절대값이 아니다.
