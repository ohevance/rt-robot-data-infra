# 장표 096 — 단계 7 검증 — 물리 실험 사슬 E15 → E16 → E21: 6축 물리는 싸고, 새 사실을 보여 주고, 48축은 비싸다
*위치: 3부 검증 · 단계 7 로봇이 움직인다 · E15 → E16 → E21*

## 1. 이 장표가 왜 있나
앞 장표(095)에서 단계 4(1 ms 루프)의 검증이 끝났다. 루프는 Pi 4 + 실시간 커널에서 최악 189 us 안에 항상 깨어난다. 그런데 1부 단계 7 "로봇이 움직인다"에서 로봇은 수식 한 줄(SimLag)이 아니라 물리 엔진 MuJoCo 위에서 움직였다. 그때 두 가지를 "3부에서 확인"으로 미뤄 두었다. 첫째, 매 주기 물리를 계산하는 비용이 1 ms 예산 안에 넉넉히 드는가(E15). 둘째, 비싼 물리 엔진을 들여왔다면 수식으로는 못 보는 새 사실을 보여 주는가(E16).

이 장표는 그 두 실험을 순서도 한 줄로 이어 보여 준다. 상자(실험) → 마름모(기준) → 화살표 글(실제 값) → 다음 상자 꼴이라, "왜 다음 실험으로 갔나"가 화살표를 따라 읽힌다. 결론은 "물리는 싸다(0.9 %), 그리고 어깨 관절의 중력 처짐 1.1° 라는 새 사실을 보여 줬다"이다.

## 2. 장표를 하나씩 읽기
순서도(chain)는 왼쪽 위에서 시작해 한 줄에 4개씩, 뱀처럼 이어진다. 상자 여섯 개를 순서대로 읽는다.

- 상자 1 "E15 MuJoCo 한 주기 비용 / test_mujoco_backend 2,000주기": 실험 E15 의 내용이다. C++ 테스트 `test_mujoco_backend` 가 관절 0 에 +0.3 rad 목표를 주고 1 kHz 로 2,000주기(2초)를 돌리며 한 주기(물리 한 걸음 + 상태 읽기)에 걸린 시간을 전부 기록한다. 2,000번을 재야 p99 같은 꼬리 값이 의미를 가진다.
- 마름모 2 "1 ms 예산의 10% 아래?": 판단 기준이다. 테스트 코드가 기계적으로 검사하는 합격선은 p99 < 900 us(주기의 90 %)지만, 설계 목표는 더 엄격한 "예산의 10 % 아래"다. 물리가 10 % 를 넘게 먹으면 깨어남 지연(최악 189 us)과 제어 계산을 합쳐 1 ms 를 위협하기 때문이다. 왜 이 기준인가: 예산의 대부분을 "제때 깨어나는 것"에 남겨 두어야 한다.
- 화살표 글(답) "예: 러너 p50 6.4 / p99 8.5 / max 29.4 us = 0.9% ✓ (WSL 4.9/6.3/20.8)": GitHub 러너(CI 의 mujoco 잡)에서 2,000주기 중 가운데 값 6.4 us, 99 % 지점 8.5 us, 최악 29.4 us 였다. p99 8.5 ÷ 1,000 = 0.85 % ≈ 0.9 % 로 기준 10 % 를 크게 밑돈다. 괄호 안은 WSL2 에서 같은 테스트를 돌린 값(p50 4.9 / p99 6.3 / max 20.8 us)으로, 환경이 달라도 같은 급이다. 답이 "예"라서 다음 상자로 이어진다.
- 상자 3 "노드 안에서는? work_us(제어+물리) / 41 / 145 / 247 us (WSL 참고값)": 단독 테스트가 아니라 실제 ROS 2 노드 안에서 1 kHz 로 돌 때 "일한 시간"이다. `rt_status` 토픽의 `work_us` 가 제어 단계(최신 명령·워치독·변화량 제한·상태 머신) + 물리 + 상태를 링 버퍼에 올리는 시간을 합친 값인데 p50 41 / p99 145 / max 247 us 였다. 단독 6 us 와 20배 넘게 차이가 나는 이유(추정)는 1 kHz 로 돌며 캐시가 식는 것, WSL 가상 커널의 선점, RT 우선순위 없이 돌린 점이다. 그래도 1 ms 의 15 % 안이다. "WSL 참고값"이라 적은 것은 WSL2 의 지연 수치는 가상 커널 위의 값이라 절대값을 믿지 않기 때문이다.
- 상자 4 "E16 물리가 보여 주는 새 사실은? / 정상 상태 위치 읽기": 물리가 싸다는 것을 알았으니 다음 질문은 "그래서 물리여야만 보이는 것이 있나"다. 노드에 `/joint_command` 로 50 Hz 목표 [0.3, −0.2, 0.1, 0, 0, 0.5] rad 를 주고, 움직임이 멈춘 뒤(정상 상태) `/joint_states` 의 위치 6개를 읽었다.
- 마름모 5 "SimLag 와 결과가 같나?": 판단 기준이다. SimLag(1차 지연 모델)는 `위치 += (목표 − 위치) × 상수` 한 줄이라 중력이 없고, 어떤 관절이든 목표에 정확히 수렴한다. 물리 결과가 그것과 같다면 물리는 장식일 뿐이다. 다르다면 그 차이가 무엇이고 실물에서도 날 일인지 설명해야 한다.
- 화살표 글(답) "아니오: 어깨 Pitch −0.180 (목표 −0.200), 1.1° 처짐": 다른 다섯 관절은 목표와 0.001~0.009 rad 차이로 붙었는데 어깨 Pitch 만 −0.180 rad 에서 멈췄다. 목표 −0.200 과의 차이 0.020 rad × 57.3 = 1.15° ≈ 1.1°. 팔 전체 무게가 걸리는 관절에서 position 액추에이터(스프링처럼 토크를 내는 모터 모델)가 중력에 밀려 처진 정상 상태 오차다. 답이 "아니오"(같지 않다)라서 "물리가 장식이 아니다"로 이어진다.
- 상자 6 "E21 ALLEX 48 자유도 (위로보틱스 공개 모델) / 프로필만 바꿔 같은 테스트 (11/06)": 장표 본편(11/05)을 만든 다음 날 더한 실험이다. 지원하는 회사가 2026-06-29 공개한 상체 휴머노이드 모델 ALLEX(MJCF, BSD-3)는 액추에이터 48개가 전부 position 서보라 SO-ARM100 과 같은 방식으로 붙는다. 바뀐 것은 관절 이름 48개를 적은 프로필 `robots/allex.yaml` 과 모델을 고정 커밋으로 받는 `scripts/get_allex.sh`, 그리고 테스트가 관절 수·이름·주기를 환경변수로 받게 한 것뿐이다 — `control_step.cpp`·`mujoco_backend.cpp`·노드는 그대로다. "같은 테스트"란 상자 1 의 `test_mujoco_backend` 와 같은 바이너리라는 뜻이다. 모델에 관절은 60개 있지만 12개(손가락 DIP·IP, 허리 링크)는 등식 제약으로 따라 움직이는 수동 관절이라 명령 대상이 아니다 — 그래서 프로필에 이름을 적어야 한다.
- 마름모 "1 ms 안에 드나? 6축의 몇 배?": 기준은 상자 2 와 같다(p99 < 주기의 90 %). 두 번째 질문은 "자유도가 8배(6 → 48)면 비용은 몇 배인가"다 — 접촉(손가락)과 등식 제약이 있어 8배보다 클 것은 예상했지만 숫자는 재 봐야 안다.
- 화살표 글(답) "러너 p99 458 · WSL 622 us (46~62%) ≈ 6축의 70~100배 → 500 Hz 기본": 1 kHz 로 2,000주기. GitHub 러너 p50 381.5 / p99 457.8 / max 608.9 us, WSL p50 336.2 / p99 622.0 / max 1,784.5 us. 같은 PC(WSL)의 6축 4.9 / 6.3 / 20.8 과 견주면 p50 ×69, p99 ×99, max ×86 — "약 70~100배"다. 합격선(900 us)은 두 환경 모두 넘었지만, 물리만으로 1 ms 의 46~62 % 가 사라지면 제어·통신·기록에 남는 몫이 380~540 us 뿐이고, WSL 에서는 max 가 1 ms 를 넘겼다(러너는 609 로 안 넘김 — 환경의 꼬리). 모델의 기본 걸음(timestep)이 2 ms 라서 ALLEX 프로필의 주기를 500 Hz 로 두었다(프로필의 숫자 하나, 코드 무변경). 500 Hz 실측은 러너 p99 510 us(2 ms 의 26 %), WSL 1,000 us(50 %) — WSL 쪽은 "비용은 같고 예산만 2배"라는 어림(31 %)보다 나빴고, 그 사실도 E21 에 그대로 적었다(7부 덧붙임 장표 136).
- 끝 상자 "물리 통과 + 다음 단계 발견 / 중력 보상 · 48축 반복 측정": 결론 두 가지. 물리 비용은 6축·48축 모두 합격선 안이고, 동시에 다음 단계가 둘 생겼다 — "중력 보상(관절 각도로 중력 토크를 계산해 미리 더해 주는 것)"은 1.1° 라는 숫자 근거와 함께, "48축 반복 측정"은 500 Hz 의 p99 가 환경마다 다르게 나온 이유(걸음이 커져 제약 풀이가 늘었나, 1,000주기 p99 의 흔들림인가)를 조건별 3회·10초 측정으로 가르는 일이다. 둘 다 `docs/HANDOVER.md` 의 남은 일.
- 아래 글 "출처: docs/measurements/mujoco_backend_ci.json, mujoco_backend_allex_*.json, docs/LOG.md 11/04·11/06, docs/experiments/E15.md·E16.md·E21.md. CI 의 mujoco 잡이 매 push 마다 두 모델(6축 1 kHz, ALLEX 500 Hz)의 움직임 + 비용 p99 < 주기의 90% 를 다시 확인한다": 숫자의 원본 파일과, 이 검증이 한 번이 아니라 push 마다 자동으로, 이제는 두 모델에 대해 반복된다는 사실이다. ALLEX 의 CI 게이트가 1 kHz 가 아니라 운영점(500 Hz)인 이유는 장표 121.
- "다음 ▶" 다리 "2부 ⑦⑧ 검증 — 로봇 안의 검증은 끝. 다음 미뤄 둔 것: 관제의 '유실 0' 은 진짜였나 (표③ 사슬 3장 + 표)": 1부(로봇 안)의 미뤄 둔 검증은 여기까지이고, 다음은 2부(데이터의 길)에서 미뤄 둔 표③ 검증으로 넘어간다.

## 3. 용어와 단위
- MuJoCo: 로봇과 물체의 움직임을 뉴턴 역학으로 계산하는 물리 엔진(Google DeepMind). 모델 파일(XML)에 관절·질량·모터를 적어 두면 "힘을 주면 어떻게 움직이나"를 계산한다. 이 저장소는 3.3.2 버전과 Menagerie 의 SO-ARM100 모델(6자유도 팔)을 쓴다.
- SimLag(1차 지연 모델): 물리 없이 "목표를 천천히 따라간다"는 수식 한 줄로 만든 가짜 로봇. 노드의 흐름을 검증할 때는 충분하지만 중력이 없다.
- 백엔드(Backend): 제어 코드가 "로봇"과 이야기하는 인터페이스(init / write_command / read_state). SimLag 와 MuJoCo 가 같은 인터페이스의 두 구현이라 제어 코드를 한 줄도 안 바꾸고 로봇을 바꿀 수 있었다.
- us(마이크로초): 100만분의 1초. 1 ms = 1,000 us. 1 kHz = 주기 1 ms.
- p50 / p99 / max: 2,000개 값을 작은 순으로 늘어놓았을 때 가운데 / 99 % 지점 / 가장 큰 값. 제어 루프는 p99 와 max 로 판단한다.
- work_us: ROS 2 노드가 `rt_status` 에 1 Hz 로 찍는 "매 주기 일한 시간". 깨어남 지연은 `wake_us` 로 따로 찍는다.
- rad(라디안): 각도 단위. 1 rad ≈ 57.3°. 0.02 rad ≈ 1.1°, 0.2 rad ≈ 11.5°.
- Pitch(어깨 관절): 팔을 앞뒤로 들어 올리는 관절. 팔꿈치·손목·그리퍼 무게가 모두 이 관절에 토크로 걸린다.
- position 액추에이터: "이 각도로 가라"고 하면 토크 = kp × (목표 − 현재) 식의 스프링처럼 힘을 내는 모터 모델. kp 가 유한하므로 무게가 걸리면 오차 = 중력 토크 ÷ kp 만큼 처진다.
- 정상 상태 오차(steady-state error): 움직임이 멈춘 뒤에도 남는 "목표 − 현재".
- 중력 보상(gravity compensation): 관절 각도로 "지금 중력이 이만큼 당긴다"를 계산해 그만큼 토크를 미리 더해 주는 것. 그러면 스프링은 오차 없이 목표에 선다.
- 러너(runner): GitHub Actions 가 CI 를 돌리기 위해 매번 새로 켜는 리눅스 가상 머신(ubuntu-24.04). 실시간 커널이 없어 지연 수치의 증거는 아니지만, 물리 한 걸음의 계산 비용처럼 CPU 계산량은 잴 수 있다.

## 4. 쉬운 예시
- 비유(E15): 1 ms 주기를 "1분짜리 점심 시간"이라고 하면 물리 계산은 그중 0.5초(0.9 %)만 쓴다. 나머지 59.5초는 "제시간에 식탁에 앉는 것"(깨어남 지연)에 달려 있다. 그래서 표①의 실시간 커널 실측이 핵심이다.
- 비유(E16): 용수철 저울에 짐을 올리면 눈금이 0 이 아니라 짐 무게만큼 내려간 자리에서 멈춘다. 용수철이 세면(kp 큼) 덜 내려가지만 0 은 아니다. 어깨 관절이 그 저울이고, "짐 무게만큼 미리 들어 올려 두는 것"이 중력 보상이다.
- 숫자 예시: 어깨 처짐 0.02 rad 는 팔 길이 30 cm 끝에서 호 길이 = 0.30 m × 0.02 = 0.006 m = 6 mm 다. 그리퍼로 작은 물건을 집는 작업에서 6 mm 는 성공과 실패의 차이다.
- 숫자 예시(여유 계산): 깨어남 max 189 us(표① Pi 격리) + 노드 안 일 max 247 us = 436 us < 1,000 us. 1 kHz 에서는 예산의 절반 이상이 남지만 2 kHz(500 us)였다면 턱밑이다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 러너 p50 6.4 / p99 8.5 / max 29.4 us — `docs/measurements/mujoco_backend_ci.json` 의 `step_us`(CI mujoco 잡 아티팩트 `mujoco-ci`). 같은 파일의 `joint0_moved_rad` 0.2988(목표 0.3), 2,000주기.
- 확인: WSL 4.9 / 6.3 / 20.8 us — `docs/LOG.md` 2026-11-04 "D5 MuJoCo" 항목, `docs/experiments/E15.md` 결과 표.
- 확인: work_us 41 / 145 / 247 us — `docs/LOG.md` 11/04 의 `rt_status` 출력, E15 결과 표(41.3 / 145.1 / 247.4 를 장표에서는 정수로 적었다).
- 확인: 어깨 Pitch −0.180(목표 −0.200), 1.1° — `docs/experiments/E16.md` 결과 표, 원본은 `docs/LOG.md` 11/04 의 `joint_states` 출력 서술(별도 측정 파일은 없다).
- 확인: 0.9 % — 8.5 ÷ 1,000 = 0.85 %, E15 에 "0.85 % ≈ 0.9 %" 로 적혀 있다.
- 확인: 합격선 p99 < 주기의 90 %(1 kHz 면 900 us, 500 Hz 면 1,800 us) — `rt_control/rt_core/test/test_mujoco_backend.cpp` 189행(`p99 < 0.9 * budget_us`), 주기는 `RT_MUJOCO_PERIOD_US`(기본 1000).
- 확인: ALLEX 1 kHz 러너 381.5 / 457.8 / 608.9, WSL 336.2 / 622.0 / 1,784.5 us — `docs/measurements/mujoco_backend_allex_ci_1khz_run42172730308.json`, `mujoco_backend_allex_wsl_1khz.json`. 500 Hz 러너 390.1 / 510.4 / 684.6, WSL 326.7 / 999.8 / 1,589.4 — `…_ci_500hz_run42175845461.json`, `…_wsl_500hz.json`. 네 실행 모두 관절 0 이동 0.2976 rad. 배수(×69 / ×99 / ×86)는 WSL 1 kHz ÷ WSL 6축(4.9 / 6.3 / 20.8).
- 확인: 바뀐 파일에 제어 코드가 없다 — `git show --stat f1e89cb`(ALLEX 커밋 13개 파일: 프로필·스크립트 2·params 생성물·테스트·CI·문서 7).
- 추정: 48축 비용이 자유도 8배보다 큰 이유(손가락 30관절의 접촉·등식 제약 12개가 제약 풀이를 키움)와, WSL 500 Hz p99 가 1 kHz 보다 큰 이유(환경 꼬리 vs 걸음 증가)는 E21 4절의 추정이다 — 반복 측정 전까지 숫자로 단정하지 않는다.
- 추정: 노드 안 work_us 가 단독 테스트보다 20배 넘게 큰 이유(캐시·WSL 선점·RT 우선순위 없음)는 E15 의 추정이다.
- 추정: 실물 SO-101 에서도 같은 자리에서 같은 방향으로 처진다는 것. 크기는 실물 모터의 kp·마찰·백래시에 달려 실측 전에는 숫자를 옮기지 않는다.
- 다시 확인하는 법(WSL 창): `bash scripts/get_mujoco.sh` 뒤 `cmake -S rt_control/rt_core -B build/rt_core_mj -DCMAKE_BUILD_TYPE=Release -DRT_CORE_WITH_MUJOCO=ON -DMUJOCO_DIR=$PWD/third_party/mujoco && cmake --build build/rt_core_mj -j` 그리고 `RT_MUJOCO_MODEL=$PWD/third_party/mujoco_menagerie/trs_so_arm100/scene.xml ctest --test-dir build/rt_core_mj --output-on-failure`. E16 은 노드를 `so101_mujoco.params.yaml` 로 띄우고 50 Hz 로 목표를 발행한 뒤 `ros2 topic echo /joint_states --once`.

## 6. 자주 하는 오해·함정
- "물리 엔진은 무겁다": 6자유도 팔 한 걸음은 p99 8.5 us 로 예산의 1 % 도 안 된다. 다만 관절이 수십 개인 휴머노이드에서는 다시 재야 한다 — 이 수치를 그대로 옮기면 안 된다.
- "러너 숫자는 전부 못 믿는다": 깨어남 지연은 그렇다(실시간 커널이 없다). 그러나 물리 한 걸음의 계산 비용은 CPU 계산량이라 러너와 WSL 이 같은 급(6.4 vs 4.9 us)으로 나왔고, 비교 자료로 쓸 수 있다.
- "오차 0.02 rad 는 버그다": 아니다. 중력이 걸리는 관절에서 position 제어가 처지는 것은 물리 법칙이다. 다른 관절이 0.001~0.009 만 틀린 것과 비교하면 어깨만 중력 방향으로 틀린 것이 보인다. 버그였다면 모든 관절이 틀렸을 것이다.
- 함정(실제로 겪은 것): colcon install 뒤 `libmujoco.so` 를 못 찾는 rpath 소실(`CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE` 로 해결), 다른 RMW 로 떠 있던 ros2 데몬 때문에 `topic echo` 가 토픽을 못 봄(`ros2 daemon stop`). 둘 다 `docs/LOG.md` 11/04.

## 7. 면접 한 문장
"6축 팔의 MuJoCo 한 걸음은 p99 8.5 us, 1 kHz 예산의 0.9 % 였고, 제어 코드를 한 줄도 안 바꾸고 로봇만 수식에서 물리로 바꾸자 어깨 관절만 1.1° 처졌다. 같은 코드에 귀사의 ALLEX 48 자유도를 프로필 하나로 얹으니 물리가 70~100배(p99 458~622 us)라 주기를 모델 걸음과 같은 500 Hz 로 두었고, 어림이 틀린 곳은 틀렸다고 적었다."
