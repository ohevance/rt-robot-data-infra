# 장표 084 — ⑦ 장애 4종 — 무엇을 어떻게 죽이고, 무엇을 재고, 무엇을 기대하나
*위치: 2부 데이터의 길 · ⑦⑧ 장애·판정·진단 · ③ 표 — 장애 4종(주입·재는 것·기대)*

## 1. 이 장표가 왜 있나
앞 장표(083)에서 유실을 세는 식을 믿을 수 있게 고쳤다. 그러면 "그 식으로 **어떤 장애**를 재나?"가 다음 질문이다. 2부의 길은 브로커 → 수집기 → DB 로 이어지고 반대 방향에 OTA 가 있으니, 부품마다 하나씩 네 가지 장애를 일부러 낸다. 이 장표는 그 네 가지를 한 표로 정리한다 — 무엇을 어떻게 죽이고(주입 방법), 무엇을 재고(재는 것), 무엇이 나와야 하는지(기대)와 실제로 나온 숫자(실측). 네 장애의 공통점은 측정이 전부 DB 안의 숫자(`collector_stats`, `telemetry.seq`, `events`)로 이루어진다는 것이다(DECISIONS 11/03 D4). 실험 하나하나의 이야기는 3부(장표 97~100)에 있고, 여기서는 도구의 설계를 본다.

## 2. 장표를 하나씩 읽기
표의 열(머리글)부터.
- "장애": 장애 주입 도구 `fleet/chaos/inject.py --fault <이름>` 의 이름 네 가지.
- "주입 방법": 어떻게 죽이고 살리나.
- "재는 것": 그 장애에서 DB 로 재는 양.
- "기대 · 실측(WSL 50대 1 Hz)": 설계가 맞다면 나와야 할 값과, 2026-11-04 WSL2 에서 가상 장치 50대 1 Hz 로 실제 잰 값.

행 1 "broker":
- 주입 "docker compose stop mqtt → N초 → start": 브로커 컨테이너를 N초(실측 10초) 세운 뒤 다시 시작한다(`run_fault_broker`, 181줄). 정전 같은 브로커 자체의 장애를 흉내 낸다.
- 재는 것 "감지(msgs/s=0), 첫 메시지·전 장치 복귀, 유실(seq)": 감지 = 수집기 통계 `collector_stats.msgs_per_s` 가 처음 0 이 된 때(주입 뒤 몇 초인가), 복구(첫 메시지) = 재시작 뒤 `msgs_per_s > 0` 이 처음 보인 때, 복구(전 장치) = 기준선 장치 수가 모두 돌아온 때, 유실 = 장표 083 의 식.
- 기대·실측 "유실 ≤ 장치 수 → 실측 0 / 1400, 복귀 2.9초, 재전송 폭주 431 msgs/s": 기대는 "장치가 버퍼에 모아 두었다가(store-and-forward) 재접속 때 다시 보내므로 많아도 장치 수(50) 이하". 실측은 0 / 1400, 전 장치 복귀 2.9초(첫 메시지 1.9초, 감지 1.3초), 재접속 순간 50대가 버퍼를 한꺼번에 쏟아 최대 431 msgs/s(평소 50 msgs/s 의 약 9배). 이 0 은 `persistence true` 로 고친 뒤의 값이다 — 고치기 전은 53 / 1434(E07).

행 2 "db":
- 주입 "docker compose stop db → N초 → start": TimescaleDB 컨테이너를 10초 세운다(`run_fault_db`, 216줄).
- 재는 것 "DB 프로브 응답, backlog 0 까지, 뒤늦게 적재된 행": 감지 = 도구 자신의 DB 프로브(접속 시도)가 실패한 때, 복구(DB 응답) = 다시 접속된 때, 복구(backlog 0) = `collector_stats.backlog_rows = 0` 이고 메시지가 흐르는 때, 뒤늦게 적재된 행 = DB 가 죽어 있던 시각의 행이 나중에 들어간 수(수집기가 메모리 backlog 에 들고 있던 양).
- 기대·실측 "유실 0 → 실측 0 / 1341, 1.4초, 뒤늦게 570행": 기대 유실 0(수집기가 backlog 에 들고 있다가 넣으므로). 실측 0 / 1341, backlog 0 까지 1.4초(감지 0.4초, DB 응답 0.8초), 뒤늦게 들어간 행 570.

행 3 "collector":
- 주입 "호스트 프로세스 SIGTERM → N초 → 같은 명령·같은 venv 로 재시작": 수집기는 컨테이너가 아니라 호스트에서 돌고 있으므로 `HostCollector`(253줄)가 `pgrep` 으로 프로세스를 찾아 SIGTERM 을 보내고(장표 074 의 곱게 종료가 작동), 10초 뒤 `/proc/<pid>/cmdline`·`environ`·`cwd` 에서 읽어 둔 **같은 명령, 같은 환경**으로 다시 띄운다.
- 재는 것 "첫 메시지·전 장치, 유실": 감지는 없다(수집기가 죽으면 통계를 쓸 주체가 없다). 복구(첫 통계) = 재시작 뒤 통계가 다시 찍힌 때, 복구(전 장치), 유실.
- 기대·실측 "QoS 1 지속 세션 0 / 1311 · QoS 0 508 / 1312 (예측 500)": 수집기가 `--qos 1`(지속 세션)이면 브로커가 10초치를 들고 있으므로 유실 0 — 실측 0 / 1311, 전 장치 1.6초. `--qos 0` 이면 수집기가 없는 동안의 메시지는 그냥 사라지므로 50대 × 1 Hz × 10초 = 500 을 잃어야 한다(`loss_if_no_protection` = 기준선 msgs/s × 지속 시간) — 실측 508 / 1312. 예측과 실측이 맞는 것이 QoS 1 의 효과를 믿게 하는 근거다(E11).

행 4 "bad_firmware":
- 주입 "rollout.py --bad (5→50→100%)": 장애 주입 도구가 OTA 배포기의 `run_rollout` 을 나쁜 펌웨어 모드로 부른다(`run_fault_bad_firmware`, 394줄: 버전 `9.9.9-bad-HHMMSS`, 단계 5,50,100, apply 2.0, health 5.0, max_fail 0).
- 재는 것 "닿은 장치 수, 롤백 시간": 새 버전이 닿은 장치 수(`devices_touched`), 롤백 결정부터 전부 복구까지(`rollback_s`, 장표 081).
- 기대·실측 "3/50, 1.0초": 50 × 5 % = ceil(2.5) = 3대에서 멈추고 1.0초에 롤백.

아래 각주 "재시작 함정(11/04): /proc/<pid>/exe 로 다시 띄우니 venv 를 잃고 바로 죽음 → /proc/<pid>/environ 의 VIRTUAL_ENV·PATH 로 같은 환경. 출처: inject.py HostCollector(253-345), docs/measurements/table3.md ③-2": collector 장애의 첫 실행에서 재시작한 수집기가 바로 죽었다. 파이썬 실행 파일을 `/proc/<pid>/exe` 로 골랐는데 그것은 심볼릭 링크를 끝까지 푼 `/usr/bin/python3.12` 라서 가상 환경(venv) 정보가 사라져 `import paho` 가 실패한 것이다. 고친 뒤에는 `/proc/<pid>/environ` 의 `VIRTUAL_ENV`·`PATH` 를 그대로 주고 파이썬도 `VIRTUAL_ENV/bin/python3` 를 먼저 고른다(`pick_python`, 321줄). 이 사고가 E12 의 "수집기 7.5분 부재"를 만들었다 — 사고도 측정이 됐다.

## 3. 용어와 단위
- 장애 주입(fault injection / chaos): 고장을 일부러 내서 시스템이 어떻게 견디는지 재는 방법.
- docker compose stop / start: 컨테이너(격리된 프로그램 묶음)를 멈추고 다시 시작하는 명령. 브로커·DB 가 컨테이너다.
- SIGTERM: "끝내라" 신호. 수집기는 이것을 받으면 마지막 적재 뒤 끝난다(장표 074).
- venv(가상 환경): 프로젝트 전용 파이썬 패키지 모음. `/proc/<pid>/`: 리눅스가 돌아가는 프로세스의 정보(명령줄 cmdline, 환경 변수 environ, 작업 폴더 cwd, 실행 파일 exe)를 보여 주는 가상 폴더.
- msgs/s: 초당 메시지. 50대 1 Hz 의 평소 값은 50 msgs/s.
- 감지 / 복구(첫 데이터) / 복구(전 장치·backlog 0): 표③-2 의 세 시간. 주입 → 이상이 처음 보인 때 / 복구 명령 → 첫 데이터 / 복구 명령 → 전부 정상.
- backlog: DB 에 못 넣어 수집기가 메모리에 들고 있는 행(장표 073~074).
- QoS 0 / QoS 1 / 지속 세션: 장표 067.
- 유실 행 "a / b": a 는 잃은 수, b 는 창 동안 만들었어야 할 수(기대 개수).
- 재전송 폭주(burst): 재접속 순간 장치들이 버퍼를 한꺼번에 쏟아 msgs/s 가 치솟는 것.

## 4. 쉬운 예시
우편 체계 비유로 네 장애: ① 우체국(브로커) 셔터를 10초 내린다 — 집배원(장치)이 편지를 가방에 들고 있다가 열리면 한꺼번에 넣는다(폭주 431). ② 우편물 창고(DB)를 10초 잠근다 — 분류 직원(수집기)이 책상 위에 쌓아 두다가(backlog 570통) 열리면 넣는다. ③ 분류 직원을 10초 집에 보낸다 — 사서함 계약(QoS 1)이 있으면 우체국이 들고 있고, 없으면(QoS 0) 그 10초의 편지는 버려진다(500통). ④ 새 분류 규칙(펌웨어)을 3명에게만 먼저 적용해 보고 문제면 되돌린다.

숫자 예시: 평소 50 msgs/s. 수집기 10초 부재 → 보호 없으면 50 × 10 = 500 유실(QoS 0 실측 508 — 10초가 정확히 10.0초가 아니라 조금 더였기 때문으로 보인다), 보호 있으면 0(QoS 1 실측 0 / 1311). DB 10초 부재 → 수집기 backlog 약 500행(실측 570: 10초 + 재접속·적재 지연이 섞인 값)이 1.4초 안에 모두 들어간다.

## 6. 자주 하는 오해·함정
- "장애 4종이면 실험도 4번"이라는 오해. 같은 장애를 조건을 바꿔 여러 번 쟀다(QoS 0/1, 고치기 전/후, WSL/CI). 표③-2 는 고친 뒤의 대표값이다.
- "유실 0 / 1400 이 처음부터 나왔다"는 오해. 처음은 53 / 1434 였고(E07), 설정·코드를 고친 뒤의 0 이다. 3부 장표 97~98 이 그 순서를 사슬로 보인다.
- 수집기 장애의 "감지" 칸이 비어 있는 이유: 수집기가 죽으면 통계를 쓰는 주체가 없어 DB 로는 감지를 잴 수 없다. 모르는 것은 비워 둔다.
- 함정(11/04): "같은 명령으로 재시작"이 실행 파일 경로만 같으면 되는 줄 알았다. 환경(venv, PATH)까지 같아야 했다 — systemd 같은 프로세스 관리자가 환경을 통째로 기록하는 이유를 몸으로 배웠다. 그 사고로 수집기가 7.5분 없었고, 그 7.5분이 E12(큐 상한)의 측정이 됐다.
- `pgrep -f collector/collector.py` 로 수집기를 찾을 때 주입 도구 자신(`chaos/inject.py`)은 패턴에 걸리지 않게 했다. 자기 자신을 죽이는 실수가 흔하다.

## 7. 면접 한 문장
"부품마다 하나씩 네 가지 장애 — 브로커·DB 컨테이너 중단, 수집기 SIGTERM 과 같은 환경으로 재시작, 나쁜 펌웨어 — 를 도구로 주입하고, 감지·복구·유실을 전부 DB 안의 숫자로 잽니다. 50대 1 Hz 에서 세 장애 모두 유실 0, 복귀 1.4~2.9초, 나쁜 펌웨어는 3/50 에서 1.0초에 롤백이었고, QoS 0 으로 같은 실험을 하면 예측대로 약 500 을 잃습니다."
