# 장표 047 — 단계 8 들머리 — 상태를 읽어 올린다: 1 kHz 샘플을 RT 스레드 밖으로, 노드가 스스로를 설명한다
*위치: 1부 로봇을 움직이는 길 · 단계 8/10 상태 발행 · ① 들머리*

## 1. 이 장표가 왜 있나
단계 7(장표 044~046)에서 로봇이 실제로 움직였다는 것을 숫자로 봤다 — 어깨 −0.181 rad, 관절별 추종 오차 그래프. 그런데 그 숫자는 누가 어떻게 바깥으로 내보낸 것인가? RT 스레드는 1 ms 마다 로봇의 위치·속도를 읽지만(단계 5 ④ `read_state`), RT 스레드가 직접 ROS 메시지를 만들어 보내면 메모리 할당과 네트워크 전송이 1 ms 안에 끼어들어 깨어남 지연의 꼬리(max)를 키운다. 그래서 "RT 스레드는 벨트에 올리기만 하고, 다른 스레드가 자기 박자로 꺼내 발행한다"는 구조가 필요하다. 이 들머리 장표는 단계 8 전체의 문제·기준·확인 방법·결과·판단을 여섯 상자로 요약하고, 뒤에 오는 그림(048) · 코드(049) · rt_status 설명(050)이 각각 무엇을 보여 주는지 예고한다.

## 2. 장표를 하나씩 읽기
여섯 상자를 위 줄 왼쪽에서 오른쪽, 아래 줄 오른쪽에서 왼쪽(뱀 모양)으로 읽는다.

- 들어온 것(회색): "로봇이 움직였다 — 매 주기 read_state 로 읽은 위치·속도 (단계 7)". 단계 5 ④에서 백엔드의 `read_state()` 가 매 주기(1 ms) 위치·속도를 `position_`·`velocity_` 에 채운다. 이것이 이 단계의 입력이다 — 아직 RT 스레드 안의 변수일 뿐 바깥은 모른다.
- 문제(민트): "RT 스레드가 직접 ROS 메시지를 발행하면 할당·네트워크로 지연이 생긴다. 그런데 바깥은 100 Hz 상태와 '노드가 건강한가'를 알아야 한다". ROS 메시지 발행은 메시지 객체를 만들고(메모리 할당), DDS 로 보내는(네트워크) 일이라 걸리는 시간이 들쑥날쑥하다. 1 ms 예산 안에 넣기엔 위험하다. 반면 상위(기록·관제·사람)는 두 가지를 원한다 — 관절 상태를 100 Hz 로, 그리고 "노드가 지금 건강한가(지연·드롭·상태)"를.
- 기준(마름모, 노랑): "RT 스레드는 벨트(링 2048)에 올리기만 하고(state_drops 0), 상태 100 Hz · rt_status 1 Hz 가 설계대로 나오나?". 합격선 세 가지다. ① RT 스레드 쪽에는 발행 코드가 없고 링 버퍼 push 만 있을 것 ② 벨트가 넘쳐 버린 샘플(state_drops)이 0 일 것 — 넘친다면 발행 스레드가 못 따라가는 것 ③ 바깥이 보는 두 토픽이 설계한 주기(100 Hz, 1 Hz)대로 나올 것. 왜 이 기준인가: ①은 단계 4 에서 지킨 "RT 스레드는 기다리지 않는다"를 여기서도 지키는 조건이고, ②③은 그 구조가 실제로 작동한다는 증거다.
- 확인 방법(파랑): "publish_state(100 Hz 타이머: 벨트를 비우고 최신 1개) · publish_status(1 Hz: 지난 1초 타이밍 p50/p99/max + 카운터 JSON) · E20 기록 요약의 실제 Hz". 코드 두 함수(장표 049·050)와, 기록 파이프라인(E20, 단계 9)이 30초 기록에서 실제 발행 주기를 세어 준 숫자로 확인한다. 즉 "설계대로 나오나"를 코드로 믿는 게 아니라 기록에서 재서 믿는다.
- 결과(보라 테두리): "/joint_states 실제 100.0 Hz(30초 2,964행, 틈 0), state_drops 0, rt_status 한 줄에 wake·work·drops·state·rt 환경·rmw". 11/05 WSL 기록 30초(정확히는 29.6초 구간)에 `/joint_states` 가 2,964행, 계산된 실제 주기 100.0 Hz, 3주기 넘는 틈 0. `state_drops` 0. `rt_status` 한 줄에 깨어남 지연(wake)·일한 시간(work)·드롭·상태·실시간 환경(rt)·DDS 구현체(rmw)가 전부 들어 있다.
- 판단 → 다음(진한 민트): "통과 → 단계 9: 상태가 토픽으로 나온다. 사고 분석·튜닝용 원본을 어디에 남기나?". 세 기준을 넘었으니 다음 질문은 "그 토픽을 어디에 어떻게 남기나"다 — 단계 9 기록.

아래 상자: "이 단계의 장표: ② publish_state 코드(1장) · ② rt_status JSON 설명(1장). 넘어가는 조건: RT 스레드 쪽에 발행 코드가 없고(벨트만), 바깥이 보는 두 토픽이 설계 주기대로 나온다". (실제 순서는 그림 048 → 코드 049 → rt_status 050 이다. 들머리의 '이 단계의 장표'는 코드 장표 둘을 세고 있다.) 넘어가는 조건이 그것인 이유: 발행 코드가 RT 쪽에 하나라도 있으면 단계 4 의 깨어남 지연 수치(표①)가 노드 안에서는 성립하지 않게 된다.

## 3. 용어와 단위
- 벨트(상태 링, state ring): RT 스레드가 샘플을 올려 두고 발행 스레드가 꺼내 가는 링 버퍼(`SpscRing<JointStateSample, 2048>`). 단계 3 의 우편함과 같은 클래스, 방향만 반대(RT → 바깥).
- 샘플(JointStateSample): 한 주기의 기록 한 개 — 몇 번째 주기(iter), 시각, 깨어남 지연, 관절 수, 워치독 상태, 로봇 상태, 위치[6], 속도[6], 보낸 목표[6].
- state_drops: 벨트가 꽉 차서 버린 샘플 수. 0 이어야 정상.
- 발행(publish): ROS 2 에서 토픽에 메시지를 내보내는 것. `/joint_states`(관절 상태), `/rt_status`(노드 자기 보고).
- Hz: 1초에 몇 번. 100 Hz = 10 ms 마다, 1 Hz = 1초마다, 1 kHz = 1 ms 마다.
- p50 / p99 / max: 지난 1초 샘플을 작은 것부터 늘어놓았을 때 가운데 값 / 99% 지점 값 / 가장 큰 값.
- wake(깨어남 지연, us): 1 ms 마다 깨라고 했는데 늦게 깬 시간. work(작업 시간, us): 제어 단계 + 백엔드가 걸린 시간. us = 마이크로초 = 100만분의 1초.
- rt 환경: `sched_fifo`(실시간 우선순위가 걸렸나) · `mlockall`(메모리를 RAM 에 고정했나) · `kernel_realtime`(PREEMPT_RT 커널인가) · `kernel`(커널 이름).
- rmw: ROS 2 가 DDS 를 부르는 층의 구현체 이름(예: rmw_fastrtps_cpp).
- 틈(gap): 기록에서 연속 메시지 사이 간격이 설계 주기의 3배를 넘는 곳. 0 이면 끊김 없음.

## 4. 쉬운 예시
비유 — 공장 라인의 검사원과 보고 담당: 라인 작업자(RT 스레드)는 1 ms 마다 부품을 만들고 검사 결과를 컨베이어 벨트(상태 링)에 올려놓기만 한다. 사무실로 직접 전화를 걸면(ROS 발행) 라인이 멈칫하므로 하지 않는다. 보고 담당(발행 스레드)은 10 ms 마다 벨트에 쌓인 것을 전부 걷어 가장 최근 것 하나만 본사에 보내고(100 Hz `/joint_states`), 1초마다 지난 1초치 검사 기록을 모아 "지연 중앙값/99%/최악, 불량 수, 라인 상태" 요약 보고서(1 Hz `/rt_status`)를 쓴다. 벨트가 넘쳐 부품이 바닥에 떨어진 수(state_drops)는 따로 센다 — 0 이어야 한다.

숫자 예시 — 1 kHz 로 돌면 10 ms 동안 샘플 10개가 벨트에 쌓인다. 100 Hz 발행 타이머가 10개를 전부 꺼내 마지막 1개만 보낸다(1 kHz 샘플 10개 중 최신 1개). 벨트 칸은 2048개이므로 발행 스레드가 2초 넘게 안 돌아야 넘친다 — 그래서 state_drops 가 0 인 것이 당연하고, 0 이 아니면 발행 스레드가 심하게 밀렸다는 뜻이다. 30초 기록에서 100 Hz × 29.6초 ≈ 2,960 → 실제 2,964행, 100.0 Hz.

## 6. 자주 하는 오해·함정
- "100 Hz 로 보내면 1 kHz 샘플 10개 중 9개는 버리는 것 아닌가?" — 발행 토픽 기준으로는 그렇다. 1 kHz 원본이 필요하면 벨트 자체를 더 자주 비우거나 기록 쪽을 바꿔야 한다. 이 저장소는 '상태 100 Hz 면 상위에 충분하다'로 설계했고, 1 kHz 타이밍 통계는 rt_status 가 1초 단위로 요약한다.
- "RT 스레드가 발행하면 더 정확하지 않나?" — 시각은 더 정확할지 몰라도 1 ms 안에 할당·네트워크가 들어와 깨어남 지연 max 가 커진다. 단계 4 의 숫자(Pi RT 격리 189 us)는 RT 스레드에 그런 일이 없을 때 값이다.
- "state_drops 가 0 이면 발행 스레드가 한 번도 안 밀린 것인가?" — 아니다. 벨트가 2048칸이라 2초 가까이 밀려도 안 넘친다. 0 은 '넘칠 만큼 밀리지 않았다'는 뜻이다.
- 함정(11/04, LOG): `ros2 topic echo /rt_status` 가 "does not appear to be published yet" 이라고 할 때가 있다 — 아침에 다른 RMW 로 떠 있던 ros2 데몬이 Fast DDS 노드의 토픽을 못 본 것. 해결은 `ros2 daemon stop` 뒤 재시도. RMW 를 바꿔 가며 실험한 뒤에는 데몬을 지운다.

## 7. 면접 한 문장
"RT 스레드는 1 ms 마다 샘플을 링 버퍼에 올리기만 하고, 발행은 ROS 2 타이머 스레드가 100 Hz 와 1 Hz 로 자기 박자에 꺼내 갑니다 — 그래서 노드 안에서도 RT 스레드에 할당·네트워크가 없고, 30초 기록에서 100.0 Hz 틈 0, state_drops 0 으로 확인했습니다."
