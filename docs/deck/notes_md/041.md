# 장표 041 — 단계 6 — 백엔드 B — MuJoCo: 목표를 ctrl 에 넣고 물리를 한 주기 진행한다
*위치: 1부 로봇을 움직이는 길 · 단계 6/10 백엔드 · ② 코드 — 백엔드 B MuJoCo 쓰기/읽기*

## 1. 이 장표가 왜 있나
- 장표 040 의 SimLag 는 수식 한 줄이었다. 공고 ④ "시뮬레이션·CI" 에 답하려면 진짜 물리(중력·관절·모터) 위에서 **같은 제어 코드**가 돌아야 한다. 이 장표는 그 두 번째 구현, MuJoCo 백엔드의 핵심 두 함수(`write_command`, `read_state`)다.
- 보여 주려는 것은 두 가지다. ① 물리 엔진을 붙였는데도 함수의 모양은 장표 039 그대로다(그래서 제어 코드가 안 바뀐다). ② RT 스레드 안에서 매 주기 불리는데도 할당 없이 미리 잡은 메모리만 쓴다(그래서 1 ms 규칙을 지킨다).
- 다음 장표 042 는 이 코드 안의 `substeps_` 가 어디서 정해지는지(걸음 맞추기), 장표 043 은 `actuator_id_` · `qpos_adr_` 같은 "관절 매핑" 이 어디서 오는지(로봇 프로필)를 설명한다.

## 2. 장표를 하나씩 읽기
코드는 `mujoco_backend.cpp` 226~252줄. 파일 머리글(1~10줄)에 MuJoCo 용어 사전이 있다: mjModel = 로봇의 "설계도"(읽기 전용), mjData = 지금 이 순간의 "상태", qpos = 관절 각 배열, qvel = 관절 속도 배열, ctrl = 액추에이터 입력 배열.

`write_command` (226~239줄):
- 227~229줄: 모델(`model_`)이나 데이터(`data_`)가 없으면 아무것도 안 하고 돌아간다. init 이 실패했는데 루프가 돌아 버리는 경우의 방어.
- 230~232줄: 넘어온 `dof` 가 내 관절 수(`dof_`)보다 크면 내 것으로 자른다. 범위 밖 쓰기 방지.
- 233~235줄 `data_->ctrl[actuator_id_[i]] = target_position[i]`: **목표를 액추에이터 입력에 쓴다**. `actuator_id_[i]` 는 "우리 쪽 관절 i 가 모델 안에서 몇 번째 액추에이터인가" 를 init 때 이름으로 찾아 둔 번호(장표 043). 이 모델의 액추에이터는 position 타입이라 `ctrl` 에 "원하는 각도" 를 넣으면 내부에서 스프링처럼(kp) 끌어당긴다.
- 236~238줄 `for (s < substeps_) mj_step(model_, data_)`: **물리를 한 주기만큼 진행**한다. `mj_step` 이 한 걸음(timestep)이고, 제어 주기 1 ms 안에 몇 걸음 밟을지가 `substeps_` 다(이 모델은 1번, 장표 042).

`read_state` (242~252줄):
- 243~248줄: 같은 방어(모델 없음, dof 자르기).
- 249~251줄 `position[i] = data_->qpos[qpos_adr_[i]]`, `velocity[i] = data_->qvel[dof_adr_[i]]`: 관절 i 의 위치·속도를 **매핑 주소**로 읽는다. MuJoCo 에서는 관절마다 qpos 안의 시작 위치(`jnt_qposadr`)와 qvel 안의 시작 위치(`jnt_dofadr`)가 다를 수 있어서(자유 관절은 7칸/6칸을 쓴다) init 때 관절별 주소를 미리 적어 둔다.

읽는 포인트:
- "write_command: 관절 i 의 액추에이터(position 타입)에 목표를 쓰고 mj_step 을 substeps 번": 위 233~238줄.
- "read_state: qpos(위치)·qvel(속도)을 관절 매핑 주소로 읽는다": 위 249~251줄.
- "mj_step 은 mjData 의 미리 잡은 메모리만 쓴다 → 할당 없음 → RT 스레드에서 불러도 된다": `mj_makeData`(init 때, RT 밖)가 필요한 메모리를 전부 잡아 두고, `mj_step` 은 그 안에서만 계산한다. 그래서 1 ms 루프 안에서 불러도 "시간이 얼마나 걸릴지 모르는" 할당이 없다.
- "비용: SO-ARM100 6축 한 주기 p50 6.4 / p99 8.5 / max 29.4 us (러너) = 1 ms 의 0.9% (E15)": 쓰기 + 걸음 + 읽기 한 쌍의 시간. 2,000주기 측정의 통계. GitHub 러너 값이고 WSL 단독은 4.9 / 6.3 / 20.8 us 로 같은 급.

## 3. 용어와 단위
- **MuJoCo**: Google DeepMind 의 로봇 물리 엔진(C 라이브러리, 버전 3.3.2 사용). 모델 파일(XML)에 관절·질량·모터를 적어 두면 힘과 움직임을 계산한다.
- **mjModel / mjData**: 설계도 / 현재 상태. 설계도는 `mj_loadXML` 로 한 번 만들고 바뀌지 않는다. 상태는 `mj_step` 마다 갱신된다.
- **ctrl**: 액추에이터(모터) 입력 배열. position 타입 액추에이터에는 "목표 각도" 를 넣는다.
- **qpos / qvel**: 일반화 좌표(관절 각, rad) / 일반화 속도(rad/s) 배열. 관절 j 의 값은 `qpos[jnt_qposadr[j]]`.
- **액추에이터(position 타입)**: 목표각을 주면 `토크 = kp × (목표 − 현재)` 꼴로 힘을 내는 모터 모델. kp 가 유한해서 무게가 걸리면 조금 처진다(장표 045).
- **mj_step / timestep(걸음)**: 물리를 한 걸음 진행시키는 함수 / 한 걸음의 시간(이 모델 기본 2 ms, 우리가 1 ms 로 맞춤).
- **substeps**: 제어 주기 하나 안에 밟는 걸음 수. 여기서는 1.
- **us**: 마이크로초, 1/1,000,000 초. 8.5 us = 0.0085 ms.

## 4. 쉬운 예시
- 비유: **운전 시뮬레이터 게임**. 핸들 각도(ctrl)를 넣으면 게임 엔진이 1프레임(mj_step)만큼 차를 움직이고, 화면의 차 위치(qpos)와 속도(qvel)를 읽어 온다. 게임을 켤 때(init) 지도와 차를 메모리에 올려 두기 때문에 매 프레임에는 새로 로딩하지 않는다 — 그래서 프레임이 끊기지 않는다.
- 숫자 예시: 제어 주기 1 ms 마다 `write_command`(목표 6개를 ctrl 에 쓰고 mj_step 1번) + `read_state`(qpos·qvel 6개씩 읽기) = 한 쌍. 1초면 1,000쌍, 30초 기록(장표 052) 동안 30,000쌍. 한 쌍이 p99 기준 8.5 us 이므로 1초 동안 물리에 쓴 시간은 많아야 약 8.5 ms — 나머지 991.5 ms 는 쉬거나 다른 일을 한다.

## 6. 자주 하는 오해·함정
- "mj_step 을 부르면 화면이 뜨나?" — 아니다. 역학 계산만 한다(헤드리스). 화면(렌더링)은 별도 라이브러리이고 이 저장소는 쓰지 않는다. 그래서 GitHub 러너처럼 화면 없는 환경에서도 돈다.
- "ctrl 에 각도를 넣으면 그 각도로 '순간이동' 하나?" — 아니다. position 액추에이터는 스프링처럼 끌어당길 뿐이라 질량·중력에 따라 늦게 도착하거나 조금 못 미친다. 그것이 단계 7 의 관찰 대상이다.
- "qpos 배열의 i 번째가 관절 i 다" 라고 가정하면 틀릴 수 있다. 자유 관절(free joint)은 qpos 7칸·qvel 6칸을 쓰므로 주소가 어긋난다. 그래서 `qpos_adr_` / `dof_adr_` 를 따로 둔다.
- 함정(11/04, LOG): colcon install 뒤 `libmujoco.so` 를 못 찾음(rpath 소실) → `CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE`. 코드가 아니라 빌드 설정의 문제였다.

## 7. 면접 한 문장
- "MuJoCo 백엔드의 매 주기 일은 세 줄입니다 — 목표를 ctrl 에 쓰고, mj_step 을 한 번 밟고, qpos·qvel 을 읽습니다. 미리 잡은 메모리만 쓰기 때문에 RT 스레드 안에서 불러도 되고, 6축 팔에서 한 쌍이 p99 8.5 us 로 1 ms 의 0.9% 였습니다."
