# 장표 026 — 단계 4 — 루프 본체 (2/2) — 일하고, 벨트에 올리고, 다음 목표 시각을 정한다
*위치: 1부 로봇을 움직이는 길 · 단계 4/10 RT 1 ms 루프 · ② 코드 — 루프 본체 2/2*

## 1. 이 장표가 왜 있나
앞 장표(025, 루프 본체 1/2)는 한 주기의 앞부분 — 절대 시각에 깨서(`clock_nanosleep`) 얼마나 늦게 깼는지(`wake_lat_ns`)와 주기 오차(`period_err_ns`)를 재는 곳 — 을 다뤘다. 깼으니 이제 일을 해야 한다. 이 장표는 같은 for 문의 뒷부분 15줄이다: (c) 이번 주기의 일을 하고 걸린 시간을 재고, (d) 측정값을 로깅 스레드로 넘기고, (e) 다음 목표 시각을 정한다. 그림(023)의 민트 상자 "step() 일 → 벨트에 push → 다음 목표까지 잔다"가 코드로는 바로 이 15줄이다. 이 장표가 끝나면 단계 4(1 ms 루프)의 코드는 전부 본 것이고, 다음 장표(027)부터는 "깨서 꺼낸 명령을 어떻게 안전하게 만드나"(단계 5)로 넘어간다.

## 2. 장표를 하나씩 읽기
파일은 `rt_control/rt_core/src/rt_loop.cpp`, 144~158줄. 코드 상자 안의 줄을 차례로 짚는다.

- 145줄 주석 `(c) 이번 주기의 일. 측정기는 바쁘게 돌기, 제어 노드는 명령 읽기 → 안전 검사 → 로봇에 쓰기.`: 이 루프 클래스(RtLoop)는 "무슨 일을 하나"를 모른다. 일은 바깥에서 끼워 넣는다 — 측정기(jitter_bench)는 50 us 동안 바쁘게 도는 BusyWorkStep, 제어 노드는 ControlStep(단계 5). 그래서 측정한 루프가 곧 제어 루프다.
- 146줄 `std::int64_t work_start_ns = now_ns();`: 일을 시작한 시각을 ns(나노초) 단위로 찍는다. `now_ns()` 는 CLOCK_MONOTONIC(뒤로 가지 않는 시계)을 읽는 도우미.
- 147줄 `step.step(i, s.wake_lat_ns);`: 끼워 넣은 일을 한 번 부른다. `i` 는 몇 번째 주기인가, `s.wake_lat_ns` 는 이번 주기의 깨어남 지연(앞 장표에서 잰 값) — ControlStep 은 이 값을 상태 샘플에 실어 바깥으로 내보낸다.
- 148줄 `s.work_ns = now_ns() - work_start_ns;`: 일이 걸린 시간. 단계 8 의 rt_status 에서 `work_us` 로 보이는 값이 이것이다(제어 계산 + 백엔드 물리 시간). 측정기에서는 "50 us 바쁘게 돌기"가 실제로 얼마나 걸렸나 — 50 보다 많이 크면 일하는 도중 CPU 를 뺏긴 것이다(E19-c 에서 work max 135 → 53 us 로 준 것이 격리의 직접 증거).
- 150줄 주석 `(d) 로깅 스레드로 넘긴다. 꽉 차면 기다리지 않고 "드롭"으로 센다.`
- 151~153줄 `if (!ring.push(s)) { drops.fetch_add(1, std::memory_order_relaxed); }`: 측정값 한 묶음(`Sample s`: iter · wake_lat · period_err · work)을 타이밍 링(SpscRing, 65536칸)에 올린다. `push` 가 false(꽉 참)면 기다리지 않고 `drops` 를 1 올린다. `fetch_add(…, relaxed)` 는 원자 변수를 "그냥 더하기" — 다른 메모리 순서와 엮을 필요가 없어 가장 싼 방식을 쓴다. 로깅 스레드가 꺼내 가는 쪽은 여기 없다(jitter_bench 의 로깅 스레드, 노드의 publish_status).
- 155줄 주석 `(e) 다음 목표 시각 = 이번 목표 시각 + 주기 (실제로 깬 시각이 아니라 "목표"에 더한다)`
- 156줄 `next_wake_ns += cfg_.period_ns;`: 이 한 줄이 "드리프트 0"의 핵심이다. `cfg_.period_ns` 는 1,000,000 ns = 1 ms. 늦게 깬 시각(`woke_ns`)이 아니라 목표(`next_wake_ns`)에 더하므로 시간표는 처음 정한 그대로 간다. 앞 장표의 `clock_nanosleep(…, TIMER_ABSTIME, …)` 가 이 목표 시각을 받는다.
- 157줄 `++done;`: 끝낸 주기 수. run() 이 마지막에 이 값을 돌려주고, 측정기는 "60,000 주기 중 drops 0" 처럼 보고한다.
- 158줄 `}`: for 문의 끝 — 다음 주기로 돌아가 (0) stop 신호 확인 → (a) 잠들기 → … 를 반복한다.

오른쪽 "읽는 포인트" 다섯 개:
- "(c) step(): 매 주기 할 일. 측정기는 50 us 바쁘게 돌기(BusyWork), 노드는 ControlStep(단계 5) — 같은 루프에 다른 일을 끼운다(RtStep)": `RtStep` 은 "매 주기 할 일의 모양"을 정한 인터페이스(`rt_step.hpp`)이고 BusyWorkStep 과 ControlStep 이 그것을 구현한다. 측정기와 노드가 루프를 따로 가지지 않는다는 것이 DECISIONS D1 의 결정.
- "work_ns = step 이 걸린 시간. rt_status 의 work_us 가 이것(제어 + 물리)": MuJoCo 노드의 WSL 참고값은 p50 41 / p99 145 / max 247 us 였다.
- "(d) ring.push 실패 = drops++ — RT 스레드는 절대 기다리지 않는다. drops 가 0 이 아니면 로깅 스레드가 못 따라간 것": 측정 자체의 건전성 지표. jitter_bench 는 drops > 0 이면 종료 코드 1 을 돌려 CI 가 실패로 본다.
- "(e) 다음 목표 = 이번 목표 + 주기. 실제 깬 시각에 더하면 늦은 만큼 밀려 주기가 길어진다(드리프트) — 목표에 더해야 평균 주기가 정확히 1 ms".
- "++done: 완료한 주기 수. 측정 끝에 '60,000 주기 중 drops 0' 의 근거".

각주 "이 루프의 깨어남 지연을 잰 것이 표①(Pi 4: 일반 781 → RT 301 → 격리 189 us). 측정기·백분위수·실험 사슬·표·결론은 3부 장표 89~95": 이 코드가 만든 숫자가 어디로 갔는지.

아래 "다음 ▶" 다리: "단계 5 — 이 루프는 Pi 4 RT+격리에서 max 189 us, 1 ms 안에 항상 깬다(검증은 3부 장표 89~95). 깨서 꺼낸 명령을 그대로 쓰면 위험하다 — 끊김·튐·불법 전이를 어떻게 막나? (제어 단계)". 루프는 정확히 깨고 일하는 틀이 됐으니, 다음 질문은 그 "일"의 내용 — 명령을 그대로 로봇에 쓰면 왜 위험한가 — 이다.

## 3. 용어와 단위
- ns(나노초) / us(마이크로초) / ms: 10억분의 1초 / 100만분의 1초 / 1,000분의 1초. 코드는 ns 로 계산하고 표는 us 로 적는다(÷1,000).
- RtStep: "매 주기 할 일"의 인터페이스. `step(iter, wake_lat_ns)` 한 함수. 측정기는 BusyWorkStep, 노드는 ControlStep.
- 벨트 / 타이밍 링: `SpscRing<Sample, 65536>`. RT 스레드가 올리고 로깅(또는 발행) 스레드가 꺼낸다. 꽉 차면 버린다.
- drops: 벨트가 꽉 차 버린 측정값 수. 0 이어야 통계가 전부 반영된 것.
- std::atomic / fetch_add / memory_order_relaxed: 두 스레드가 같이 보는 카운터를 안전하게 1 올리는 방법. relaxed 는 "순서 보장 없이 값만 정확히"로 가장 싸다.
- 드리프트: 늦음이 매 주기 쌓여 시간표가 밀리는 것. 목표에 더하면 0.
- 1 kHz · 1 ms · period_ns = 1,000,000: 같은 말.

## 4. 쉬운 예시
- 비유: 공장 벨트 앞 작업자. 벨트가 매 1분(목표 시각)마다 부품을 보내면 작업자는 (c) 조립하고 (d) 결과표를 옆 상자에 던져 넣고(상자가 꽉 차면 그냥 버리고 "버림 1" 을 센다) (e) 다음 부품은 "지난 조립이 끝난 뒤 1분"이 아니라 "원래 시간표의 다음 1분"에 온다. 조립이 늦어도 벨트 시간표는 밀리지 않는다.
- 숫자 예시: 깨어남 지연 189 us + step() 50 us = 239 us 를 쓰고 761 us 를 잔다. 60초면 60,000번 반복하고, 로깅 스레드가 1 ms 마다 벨트를 비우므로 65,536칸 벨트는 꽉 찰 일이 없다 → drops 0.

## 6. 자주 하는 오해·함정
- `drops` 는 "명령을 잃었다"가 아니라 "측정값을 잃었다"다. 명령 우편함의 cmd_ring_full, 상태 벨트의 state_drops 와는 다른 카운터다(세 링이 각자 센다).
- 156줄을 `next_wake_ns = woke_ns + period` 로 고치면 겉으로는 돌지만 60초에 수십 주기가 사라진다 — DECISIONS 11/03 "절대 시각 타이머" 의 버린 대안이 바로 이것.
- work_ns 에는 백엔드 시간이 포함된다. MuJoCo 노드에서 work p99 가 145 us 인 이유는 물리 계산(E15: 한 주기 p99 8.5 us, 러너)이 아니라 WSL 가상 커널에서 CPU 를 뺏기는 시간이 섞여서다(참고값).
- 11/05 CI 사고와는 무관하지만 교훈이 같다: 루프 끝의 `++done` 처럼 "세는 코드"가 없으면 "60,000 중 0" 같은 주장을 할 수 없다.

## 7. 면접 한 문장
"루프의 뒷부분은 세 줄이면 설명됩니다 — 끼워 넣은 일을 하고 걸린 시간을 재고, 측정값은 벨트에 올리되 꽉 차면 기다리지 않고 세며, 다음 목표는 실제 깬 시각이 아니라 목표에 1 ms 를 더해 정합니다. 그래서 60초에 60,000번, 드롭 0 입니다."
