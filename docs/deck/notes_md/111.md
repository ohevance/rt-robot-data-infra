# 장표 111 — 믿을 수 있나 — 측정 · 테스트 · CI
*위치: 6. 믿을 수 있나 — 측정·테스트·CI*

## 1. 이 장표가 왜 있나
5부에서 숫자가 **어디서** 나왔는지(네 곳)를 봤다. 그러면 마지막 남은 질문은 "그 숫자를 **어떻게 믿나** — 누가, 무엇으로, 언제 다시 재나?"다. 숫자는 한 번 잘 나올 수 있다. 믿을 수 있는 숫자는 (가) 조건이 옆에 적혀 있어 다시 만들 수 있고, (나) 자동으로 다시 돈다. 이 장표는 6부의 표지로, 그 두 가지를 세 묶음 — 측정 스크립트(조건을 결과 옆에 적는다), 테스트 20건(단위·통합), CI 3잡(push 마다 다시 돈다) — 으로 예고한다. 답 상자의 마지막 "그리고 실제로 두 번 나를 잡았다"는 CI 가 장식이 아니라는 증거다. 6부는 표지 포함 13장(111~123)이다.

## 2. 장표를 하나씩 읽기
- 왼쪽 위 큰 번호 "06" 과 제목 "믿을 수 있나 — 측정 · 테스트 · CI": 세 단어가 6부의 세 묶음이다.
- 부제 "숫자를 만드는 스크립트는 조건(커널·부하·온도)을 같이 적고, 테스트와 CI 러너는 push 마다 다시 증명한다": (가) 재현 가능성과 (나) 자동 재증명.
- 흐름 상자 "들어온 것": "로봇을 움직이는 길(1부)·데이터의 길(2부)의 숫자 — 표① 189 us, 표② 손실 0, 표③ 유실 0 / 롤백 1.0초, 물리 0.9% — 와 그 검증(3부), 공고 표(4부), 환경(5부)". 1~5부 전부가 입력이고, 대표 숫자 네 개를 다시 적었다(표② 손실 0 은 Cyclone DDS 1 MB 메시지 손실 0%).
- 흐름 상자 "질문": "이 숫자들을 어떻게 믿나 — 누가, 무엇으로, 언제 다시 재나?"
- 흐름 상자 "답": 세 문장 + 증거. ① "측정 스크립트 5개가 조건(커널·부하 크기·온도·스로틀)을 결과 옆에 적는다" — jitter_run.sh · cyclictest_run.sh · lib_thermal.sh · lib_stress.sh · make_table1.py. 결과 파일 옆에 `.meta`(커널·RT 여부·부하·메모리 크기·우선순위·온도 전후·스로틀 플래그)가 같이 남고 표의 비고 칸에 들어간다. ② "테스트 20건(C++ 5 · Python 15)과 통합 스크립트" — C++ ctest 4 + MuJoCo 1, Python 6 + 3 + 6, 그리고 진짜 컨테이너를 띄우는 integration.sh. ③ "CI 3잡이 매 push 마다 1 kHz 루프·물리·장애 3종·롤백을 다시 돌린다" — rt_core(빌드·단위·연기·fleet 단위) → fleet_integration(장애 3종 + 롤백 + OTA) · mujoco(헤드리스 물리 2,000주기). ④ "그리고 실제로 두 번 나를 잡았다" — 11/04 TimescaleDB 첫 기동의 임시 서버에 pg_isready 가 속아 마이그레이션이 끊긴 것, 11/05 수집기의 request_stop 함수가 지워져(NameError) 시작 직후 죽은 것. 둘 다 WSL 에서는 안 보였다.
- 차례 첫 줄 "측정: 표① 한 줄이 만들어지는 길(스크립트 5개) · 온도·부하 함수": 장표 112(다섯 스크립트의 길), 113(lib_thermal.sh 코드), 114(lib_stress.sh 코드).
- 차례 둘째 줄 "테스트: 목록 20건 · 가짜 브로커·DB · 통합 스크립트": 장표 115(목록 표), 116(가짜 브로커·DB 로 1초 만에 도는 단위 테스트), 117~118(integration.sh 두 장).
- 차례 셋째 줄 "CI: 3잡 · 결과를 보고 무엇을 판단하나 · Jenkins 대응표": 장표 119~121(잡 셋), 122(실패 유형별 첫 행동), 123(Jenkins 대응표).

## 3. 용어와 단위
- 재현(reproduce): 같은 조건으로 다시 재서 같은 급의 숫자가 나오는 것. 조건이 적혀 있지 않으면 재현이 불가능하다.
- `.meta`: 측정 결과 파일 옆에 같은 이름으로 남기는 조건 기록(label·date·kernel·realtime·duration_s·stress·cpu·temp 전후·throttled_after·stress_vm_bytes·prio·work_us).
- 단위 테스트: 함수·클래스 하나를 가짜 환경에서 빠르게 확인. 통합 테스트: 진짜 컨테이너(브로커·DB)를 띄워 끝까지 돌려 본다. 연기(smoke) 테스트: "켜지고 돈다"만 확인.
- ctest: CMake 의 테스트 실행기. `add_test` 로 등록된 것을 돌리고 "100% tests passed" 를 낸다.
- CI 잡(job): 하나의 러너(새 가상 컴퓨터)에서 도는 단계 묶음. 이 저장소는 3잡: rt_core(약 1분 13초) → fleet_integration(약 1분 52초) · mujoco(약 25초).
- push: 로컬 커밋을 GitHub 에 올리는 것. 이것이 CI 를 깨우는 트리거.
- Jenkins: 회사에서 많이 쓰는 CI 도구. GitHub Actions 와 개념이 1:1 로 대응된다(장표 끝의 대응표).

## 4. 쉬운 예시
실험 노트 비유: 과학 실험에서 "결과 189" 만 적은 노트와, "189 — RT 커널, 부하 stress-ng 256M, 시작 44.8 °C 끝 64.8 °C, 스로틀 없음, 60초" 를 함께 적은 노트가 있다. 두 번째만 남이 다시 해 볼 수 있다. 그리고 그 실험을 누가 코드를 고칠 때마다 로봇(CI)이 자동으로 다시 해 주면, 어제의 189 가 오늘 코드에서도 유효한지 매번 안다.

숫자 예시: 테스트 20건 = C++ 5(링 버퍼·제어 단계·상태 머신·1 kHz 연기 + MuJoCo) + Python 15(6 + 3 + 6). 여기에 통합 스크립트 1벌(장애 3종 + 나쁜 펌웨어 + 정상 OTA → 판정)과 CI 단계의 연기 2개(jitter_bench --no-rt 2초 → 표 생성기, 대시보드 JSON 파싱)가 더 있다.

## 6. 자주 하는 오해·함정
- "테스트가 많다 = 믿을 수 있다"가 아니다. 11/05 사고는 단위 테스트가 다 통과했는데 진입점 main() 을 아무 테스트도 안 타서 수집기가 시작하자마자 죽은 것이었다 — 그래서 main() 스모크를 추가했다. 테스트는 **무엇을 타는가**가 수보다 중요하다.
- "CI 초록 = 빠르다"가 아니다. CI 러너는 RT 권한이 없어 연기 테스트는 `--no-rt` 2초, 지연 수치는 아니다. CI 는 "돌아간다"의 증거.
- 문서만 고친 push 라도 CI 를 봐야 한다 — 11/05 에 측정·문서 push 를 연달아 하며 CI 를 안 봐서 빨간 상태가 몇 시간 갔다(ENVIRONMENT.md §5-5 "배운 규칙").
- 부하 정의가 두 스크립트에 따로 있으면 "같은 부하"가 아니다 — 11/05 에 lib_stress.sh 한 곳으로 모으고 쓴 값을 .meta 에 남기게 했다(결정 기록 11/05).

## 7. 면접 한 문장
"숫자를 믿게 하는 방법은 둘입니다 — 측정 스크립트가 커널·부하·온도·스로틀을 결과 옆에 적어 재현할 수 있게 하고, 테스트 20건과 CI 3잡이 push 마다 다시 돕니다. CI 는 실제로 두 번, WSL 에서는 안 보이던 사고를 잡았습니다."
