# 장표 061 — 같은 길을 토픽·설정과 함께 — fleet 데이터 흐름
*위치: 2부 데이터의 길 · 구조도(토픽·설정)*

## 1. 이 장표가 왜 있나
앞 장표(060)는 여덟 상자를 한 줄로 늘어놓은 지도였다. 이 장표는 같은 길을 구조도(Mermaid, 왼쪽에서 오른쪽)로 다시 그리되, 상자 사이 화살표마다 "어느 토픽이, 어떤 QoS·세션으로" 지나가는지를 적었다. 2부에서 가장 자주 헷갈리는 것이 토픽 네 종과 설정 세 가지(QoS, 보관, 지속 세션)인데, 그것이 어느 화살표에 붙는지를 한 번에 보여 주려는 장표다. 1부의 구조도(008)에 해당한다.

## 2. 장표를 하나씩 읽기
그림(`img/fleet_flow.png`, 원본 `build/diagrams/fleet_flow.mmd`)의 상자와 화살표를 왼쪽부터 읽는다.

- 상자 "장치 에이전트 — tick 1 Hz: seq·ts_ns·cpu·temp·fw·state": `device_agent.py` 의 `tick`(92줄)이 1초마다 만드는 JSON 의 주요 항목. seq 는 일련번호(유실 세기), ts_ns 는 측정 시각(전달 지연 재기), cpu·temp 는 센서값(가상 장치는 난수 걸음), fw 는 펌웨어 버전(OTA 확인용), state 는 ok/updating/fault.
- 화살표 "fleet/<id>/telemetry (QoS 0/1)" 장치 → Mosquitto: 측정값 토픽. QoS 는 옵션(`--telemetry-qos`)이다 — 0 은 보내고 잊음(가볍다), 1 은 브로커의 확인까지(수집기가 잠깐 죽어도 지속 세션에 쌓인다). 기본은 0, '유실 0' 실험(3부 표③)에서 1 이 왜 필요했는지가 나온다.
- 화살표 "fleet/<id>/status online (retained) / 유언 offline (브로커가 대신)" 장치 → Mosquitto: 접속하면 장치가 "online" 을 보관 메시지로 발행하고(`on_connect`, 122줄), 비정상 종료 때는 미리 맡긴 유언 "offline" 을 브로커가 대신 발행한다(`will_set`, 56줄). 보관(retained)이므로 수집기가 나중에 붙어도 마지막 상태를 바로 받는다.
- 상자 "Mosquitto — persistence true / max_queued_messages 20000": `fleet/mosquitto/mosquitto.conf` 의 두 줄. 재시작해도 보관 메시지와 지속 세션을 디스크에서 되살리고, 구독자가 없는 동안 세션당 최대 20,000개까지 들고 있는다(50대 1 Hz 면 약 400초치).
- 화살표 "fleet/+/telemetry, fleet/+/status (지속 세션 clean_session=False)" Mosquitto → 수집기: 수집기는 `+`(한 단계 와일드카드)로 모든 장치의 두 토픽을 구독한다. 지속 세션은 수집기를 `--qos 1` 로 띄울 때다(`collector.py:132-136` — 기본 QoS 0 이면 clean_session=True, 고정 client_id 로 QoS 1 이면 False). 지속 세션이면 수집기가 죽어 있는 동안 QoS 1 메시지가 브로커 큐에 남는다.
- 상자 "수집기 — on_message → pending / 1초마다 take_batch → COPY": paho 콜백 스레드는 파싱해서 `pending` 에 넣기만 하고, 메인 스레드가 1초마다 꺼내 묶음(Batch)으로 COPY 한다(③ 묶음 장표 069~074).
- 화살표 "telemetry · events · collector_stats" 수집기 → TimescaleDB: 세 하이퍼테이블. 측정값 / 온·오프라인·장애·OTA 이벤트 / 수집기 자신의 1초 통계.
- 원통 "TimescaleDB — hypertable" → 상자 "Grafana — Fleet Overview 14 패널": DB 를 Grafana 가 읽어 14개 패널로 보인다(④⑤ 묶음, 장표 075~076).
- 상자 "rollout.py" → 화살표 "fleet/<id>/cmd {ota | ota_rollback}" → Mosquitto → "cmd" → 장치: 서버에서 장치로 가는 유일한 방향. OTA 배포기가 장치별 cmd 토픽에 명령을 보내고, 장치는 `on_message`(139줄)에서 받아 적용한다(⑥ 묶음, 장표 077~081).
- 화살표 "cmd_reply" 장치 → Mosquitto: 명령의 응답(ok, 적용 중 버전 등). 배포기가 이것과 telemetry 의 fw·state 로 적용 완료와 건강을 판단한다.
- 점선 "inject.py — docker compose stop/start mqtt·db / SIGTERM 수집기" → Mosquitto, 점선 "프로브·유실 SQL" → DB: 장애 주입기는 데이터 길의 바깥에서 컨테이너를 멈추고(stop) 살리며(start), 수집기 프로세스는 SIGTERM 으로 죽이고 다시 띄운다. 결과(감지·복구 시간, 유실)는 DB 에 SQL 로 묻는다(⑦ 묶음, 장표 082~085).
- 설명 줄 "토픽 4종: telemetry(측정값) · status(online/offline, 보관) · cmd(서버 → 장치) · cmd_reply. 장애 주입은 컨테이너를 멈추고(stop) 살리며(start) DB 로 결과를 잰다": 그림의 요약. 토픽 네 종의 이름은 `device_agent.py:48-51` 에 정의돼 있다.

## 3. 용어와 단위
- 토픽 와일드카드 `+`: 한 단계를 아무 값으로 받는다. `fleet/+/telemetry` 는 모든 장치의 telemetry.
- QoS 0 / 1 / 2: MQTT 전달 보장 등급. 0 보내고 잊음, 1 최소 한 번(확인 PUBACK), 2 정확히 한 번(여기선 안 씀).
- 보관 메시지(retained): 브로커가 토픽의 마지막 메시지를 저장해 새 구독자에게 즉시 전달.
- 유언(LWT): 접속 때 맡기는 "내가 비정상으로 끊기면 이것을 발행해 달라" 메시지.
- 지속 세션(persistent session, clean_session=False): 구독자가 끊겨도 브로커가 구독과 QoS 1 큐를 유지.
- persistence: 브로커가 세션·보관 메시지를 디스크에 저장해 재시작 뒤 되살리는 것(`autosave_interval 30` 초마다).
- 하이퍼테이블(hypertable): TimescaleDB 가 시간 열로 자동 분할하는 표. 겉으로는 일반 표처럼 쓴다.
- 프로브(probe): 장애 주입기가 "DB 가 살아 있나"를 주기적으로 찔러 보는 짧은 질의.
- SIGTERM: 프로세스에 "곱게 끝내라"고 보내는 신호(Ctrl+C 의 SIGINT 와 비슷). 수집기는 이것을 받으면 남은 것을 적재하고 끝낸다.

## 4. 쉬운 예시
비유 — 우체국과 사서함: 지점(장치)이 편지(telemetry)를 우체국(Mosquitto)에 낸다. 일반 우편(QoS 0)은 넣고 잊고, 등기(QoS 1)는 접수 확인을 받는다. 본사 직원(수집기)이 자리를 비우면 등기는 사서함(지속 세션 큐, 20,000통까지)에 쌓이고, 일반 우편은 버려진다. 지점은 문 앞에 "영업 중"(status online, 보관) 팻말을 걸어 두고, 갑자기 쓰러지면 우체국이 대신 "영업 종료"(유언 offline) 팻말을 바꿔 준다. 본사가 지점에 보내는 지시(cmd)와 그 회신(cmd_reply)은 반대 방향의 편지다.

숫자 예시 — 50대 1 Hz 에서 수집기를 10초 죽이면: QoS 0 이면 약 500개가 버려져 seq 에 틈이 생기고, QoS 1 + 지속 세션이면 500개가 브로커 큐에 남아 수집기가 돌아오면 전부 들어온다(3부 표③, E11·E13). 큐 상한 20,000 은 50대 1 Hz 로 400초, 300대면 약 67초치다 — 수집기가 그보다 오래 죽으면 그때부터 잃는다.

## 6. 자주 하는 오해·함정
- "QoS 1 이면 수집기가 죽어도 자동으로 안전한가?" — 수집기가 지속 세션(clean_session=False)으로 구독하고, 브로커 큐 상한을 넘지 않고, 브로커 persistence 가 켜져 있어야 한다. 세 가지 중 하나가 빠지면 '유실 0' 이 아니다 — 3부 표③의 이야기가 바로 그것이다(처음엔 유실 측정이 가짜 0 이었다).
- "status 가 offline 이면 장치가 죽은 것인가?" — 비정상 종료(유언) 또는 정상 종료(장치가 직접 offline 발행, `stop`, 77줄) 둘 다다. 구분은 events 와 재접속 카운터로.
- "브로커가 죽으면 telemetry 는 어디로?" — 장치 쪽 버퍼(3,600개)로. 브로커의 persistence 와는 다른 보호다(장치 → 브로커 구간 vs 브로커 → 수집기 구간).
- "cmd 는 모든 장치에 한 번에 보낼 수 없나?" — 토픽이 장치별(`fleet/<id>/cmd`)이라 배포기가 장치마다 보낸다. 그래서 5%·50%·100% 단계가 가능하다.
- 함정(E09): 브로커가 종료되며 모든 접속의 유언을 한꺼번에 발행하다 소켓을 닫아 50개 중 20개만 수집기에 닿은 일이 있다 — "offline 20" 의 정체.

## 7. 면접 한 문장
"장치와 서버 사이에는 토픽 네 종만 있습니다 — telemetry 로 측정값, status 로 온·오프라인(보관 메시지와 유언), cmd 와 cmd_reply 로 서버 명령과 응답 — 그리고 유실 0 은 QoS 1, 지속 세션, 브로커 persistence 와 큐 상한이라는 설정이 맞아야 나오는 숫자라는 것을 실험으로 배웠습니다."
