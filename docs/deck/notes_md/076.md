# 장표 076 — ④ TimescaleDB — 표 5개와 마이그레이션, ⑤ Grafana — 14 패널
*위치: 2부 데이터의 길 · ④⑤ DB·Grafana · ② 구조 — 표 5개 · 패널 14개*

## 1. 이 장표가 왜 있나
앞 장표(075, ④⑤ 들머리)에서 "쌓는 곳"과 "보이는 곳"의 기준을 세우고 통과했다고 판단했다. 그러면 실제로 **무슨 표가 있고 무슨 열이 있는지**, **대시보드에는 무슨 패널이 있는지**를 한 장에 펼쳐 보여야 "데이터가 쌓이고 보인다"가 구체적인 말이 된다. 이 장표는 두 칸이다. 왼쪽이 ④ DB(`fleet/db/init.sql` 의 표 5개와 마이그레이션 도구), 오른쪽이 ⑤ Grafana(`fleet/grafana/make_dashboard.py` 가 만드는 패널 14개). 2부에서 지금까지 흘러온 데이터(텔레메트리, 이벤트, 수집기 통계)가 결국 어느 열에 들어가 어느 그래프로 보이는지를 잇는 장표다.

## 2. 장표를 하나씩 읽기
왼쪽 칸 머리 "DB (fleet/db/init.sql, migrations/001~003)". 표 구조는 `init.sql` 에, 바뀐 부분은 `migrations/` 에 있다(확인: 지금 파일은 `002_ota.sql`, `003_collector_resilience.sql` 두 개이고 001 은 없다 — init.sql 이 바탕이다).

- 왼쪽 1줄 "telemetry(hypertable): time, device_id, seq, cpu_pct, temp_c, mem_pct, rssi, loop_hz, wake_p99_us, fw_version, state, ingest_latency_ms — 인덱스 (device_id, time DESC)". 장치가 1 Hz 로 올리는 측정값이 들어가는 표(시간으로 자동 분할되는 하이퍼테이블). 열마다: `time` 장치가 측정한 시각, `device_id` 장치 이름, `seq` 장치별 일련번호(빠진 번호 = 유실 — 장애 주입의 유실 계산이 이 열을 쓴다), `cpu_pct` CPU 사용률(%), `temp_c` 온도(°C), `mem_pct` 메모리 사용률(%), `rssi` 무선 신호 세기(dBm, 유선이면 비움), `loop_hz` 제어 루프 주기(RT 노드일 때), `wake_p99_us` 제어 루프 깨어남 지연 p99(us, RT 노드일 때), `fw_version` 펌웨어 버전, `state` 상태(ok, tripped, fault, updating …), `ingest_latency_ms` 전달 지연 = 수집기 도착 시각 − 장치 측정 시각(ms, 같은 시계일 때만 의미). 인덱스 (device_id, time DESC) 는 "이 장치의 최근 행"을 바로 찾기 위한 것이다.
- 왼쪽 2줄 "events(hypertable): kind(online/offline/fault/ota), device_id, detail". "일어난 일" 표. `kind` 가 종류(온라인·오프라인·워치독·OTA·고장), `detail` 은 JSON 으로 된 자세한 내용. 장애 주입 도구와 OTA 배포기도 여기에 자기 발자국을 남겨 대시보드의 "최근 이벤트" 표에 보인다.
- 왼쪽 3줄 "collector_stats(hypertable): msgs, insert_ms, lat_p50/p95/max, online, backlog_rows, db_errors(003)". 수집기가 매초 남기는 자기 통계. `msgs_per_s` 초당 메시지, `batch_rows` 묶음 행 수, `insert_ms` DB 적재에 걸린 ms, `lat_p50_ms/lat_p95_ms/lat_max_ms` 전달 지연의 중앙값·95백분위·최댓값, `online` 온라인 장치 수, `backlog_rows` DB 가 끊긴 동안 들고 있는 행 수(0 이면 정상), `db_errors` DB 쓰기 실패 누적 횟수. 마지막 둘은 마이그레이션 003 으로 추가된 열이다 — 장애 주입의 "복구 = backlog_rows 가 다시 0" 판정이 이 열을 본다.
- 왼쪽 4줄 "devices: 장치별 마지막 상태 · ota_rollouts(002): 배포 요약 한 줄". `devices` 는 장치 한 대당 한 줄(처음 본 시각, 마지막 본 시각, 펌웨어 버전, 상태) — "온라인 장치 수" 패널이 `last_seen` 으로 센다. `ota_rollouts` 는 OTA 단계 배포 한 번의 결과 요약 한 줄(버전, 나쁜 펌웨어였나, 단계 비율, 전체·닿은 장치 수, 성공 여부, 롤백 시간, 타임라인) — 마이그레이션 002 로 추가. 표③-3 의 롤백 시간이 여기서 나온다.
- 왼쪽 5줄 "migrate.py --wait N: 번호 붙은 SQL 을 순서대로, TCP 로 진짜 붙어 보며 기다린다(CI 의 TimescaleDB 초기화 경쟁 해결)". `fleet/db/migrate.py` 는 `migrations/NNN_*.sql` 을 번호순으로 읽어 `schema_migrations` 표에 없는 것만 실행하고 기록한다(두 번 돌려도 안전). `--wait N` 은 DB 가 받아 줄 때까지 1초마다 TCP 로 접속을 시도한다 — 컨테이너 안의 `pg_isready` 가 임시 서버에도 "준비됨"이라 답해 CI 1차가 깨진 사고의 해결책(장표 075).

오른쪽 칸 머리 "Grafana Fleet Overview (make_dashboard.py 가 JSON 생성)". 대시보드 이름이 "Fleet Overview — rt-robot-data-infra", 2초마다 새로 고침, 기본 시간 범위 최근 5분.

- 오른쪽 1줄 "stat: 온라인 장치(5초) · 초당 메시지 · 전달 지연 p95 · DB 적재 ms · 오프라인 이벤트(10분) · 멈춤·고장 장치". stat 패널(큰 숫자 하나) 6개. 온라인 장치 = 최근 5초 안에 본 장치 수(`devices.last_seen`), 초당 메시지 = `collector_stats` 의 마지막 `msgs_per_s`, 전달 지연 p95(ms), DB 적재 시간(ms), 최근 10분의 오프라인 이벤트 수(브로커가 대신 남긴 유언 포함), 상태가 tripped/fault/updating/recovering 인 장치 수.
- 오른쪽 2줄 "timeseries: 초당 메시지/온라인 · 전달 지연 p50/p95/max · 장치별 온도 · RT 노드 깨어남 지연 p99 · 수집기 backlog/DB 오류 · 펌웨어 버전별 장치 수". 시간 그래프 6개. 장애 주입 때 "msgs/s 가 0 으로 떨어지고 돌아오는 모양", "backlog 가 쌓이다 0 으로 빠지는 모양", OTA 때 "버전별 장치 수가 3 → 50 으로 바뀌는 모양"이 여기서 보인다. 장치별 온도는 앞 8대만(선이 50개면 읽을 수 없다). RT 노드 깨어남 지연 p99 는 1부의 1 ms 루프가 관제에 보이는 자리다.
- 오른쪽 3줄 "table: 최근 이벤트(장애 주입·OTA·온/오프라인) · 장치 목록". 표 패널 2개. 최근 이벤트 50건(`events`), 장치 목록(장치, 상태, 펌웨어, 마지막 본 시각, 몇 초 전인지).
- 오른쪽 4줄 "JSON 을 손으로 안 만지는 이유: 패널 14개의 SQL 을 코드로 두면 리뷰·수정·CI 검사(파싱)가 된다". 6 + 6 + 2 = 14개 패널의 SQL 이 파이썬 파일 한 곳에 보이므로 git 에서 변경을 읽을 수 있고, CI 가 생성된 JSON 을 다시 읽어 깨지지 않았는지 확인한다.

## 3. 용어와 단위
- 하이퍼테이블 / 인덱스 / 마이그레이션 / COPY: 장표 075 용어 절 참고.
- 열 자료형: TIMESTAMPTZ 시간대 포함 시각, TEXT 글자, BIGINT 큰 정수, REAL 실수, INTEGER 정수, JSONB JSON 데이터, BOOLEAN 참/거짓.
- seq(일련번호): 장치가 메시지마다 1씩 올려 붙이는 번호. 1, 2, 3, 5 가 들어왔으면 4 가 유실이다.
- rssi(dBm): 무선 신호 세기. 0 에 가까울수록 세고 보통 −30 ~ −90 dBm.
- p50 / p95 / p99: 값들을 작은 것부터 늘어놓았을 때 50 % · 95 % · 99 % 지점의 값. p95 가 10 ms 면 100번 중 95번은 10 ms 안.
- us / ms: 마이크로초(1/1,000,000초) / 밀리초(1/1,000초). 1 ms = 1,000 us. 깨어남 지연은 us, 전달 지연은 ms 단위라 자릿수가 다르다.
- stat / timeseries / table 패널: Grafana 패널 종류. 큰 숫자 하나 / 시간 그래프 / 표.
- `$__timeFilter(time)`: Grafana 가 화면의 시간 범위를 SQL 조건으로 바꿔 넣는 자리표시.
- schema_migrations: 어느 마이그레이션이 적용됐는지 적는 장부 표.

## 4. 쉬운 예시
병원 비유: `telemetry` 는 환자(장치)마다 매초 적는 활력 징후 기록지(체온 temp_c, 혈압 대신 CPU, 호흡 대신 메모리), `events` 는 간호 기록("입원", "퇴원", "약 교체(OTA)", "경보(fault)"), `collector_stats` 는 기록을 모으는 간호사 스테이션의 업무 일지(1초에 몇 장 처리했나, 밀린 기록이 몇 장인가), `devices` 는 병동 현황판(환자별 마지막 확인 시각과 상태), `ota_rollouts` 는 약 교체 캠페인 보고서 한 줄. Grafana 는 그 모든 기록을 벽의 모니터 14칸으로 보여 주는 중앙 모니터다.

숫자 예시: 50대 × 1 Hz 면 `telemetry` 에 1초에 50행, `collector_stats` 에 1초에 1행이 쌓인다. OTA 에서 나쁜 펌웨어 1.2.0-bad 를 내리면 "펌웨어 버전별 장치 수" 그래프에 1.2.0-bad 가 3대로 잠깐 나타났다가 1.0초 뒤 사라지고, `ota_rollouts` 에는 `success=false, devices_updated=3, rollback_s=1.0` 한 줄이 남는다.

## 6. 자주 하는 오해·함정
- `ingest_latency_ms` 는 "DB 에 보일 때까지"가 아니라 "수집기에 도착할 때까지"다. DB 에는 1초 묶음 적재 때문에 최대 약 1초 더 걸린다. 또 장치와 수집기의 시계가 같을 때만 의미가 있다(같은 PC 에서는 의미 있고, 실물 장치에서는 시계 맞춤이 필요하다).
- `seq` 로 유실을 세려면 기준점이 중요하다 — 장애 창 안의 첫 번호를 기준으로 하면 앞 가장자리의 유실이 숨는다(장표 083).
- "장치별 온도 (앞 8대)" 는 성능이 아니라 가독성 때문이다. 50개 선은 읽을 수 없다.
- Grafana 화면에서 패널을 고치고 저장하면 다음에 `make_dashboard.py` 를 돌릴 때 덮어써진다. 고치려면 파이썬 파일을 고친다.
- 마이그레이션 번호 001 파일은 없다. 장표의 "001~003" 은 번호 체계의 표현이다.

## 7. 면접 한 문장
"DB 는 표 다섯 개뿐이고 시간이 축인 셋은 하이퍼테이블입니다. 대시보드 14개 패널은 전부 70줄짜리 파이썬 생성기에서 나와, 장애 주입이나 OTA 때 msgs/s·backlog·버전별 장치 수가 어떻게 움직이는지 그 패널에서 바로 보입니다."
