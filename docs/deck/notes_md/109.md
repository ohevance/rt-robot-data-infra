# 장표 109 — ① 개발 PC — 무엇이 떠 있어야 하고, 무엇을 보고 판단하나
*위치: 5부 어디서 · ① 개발 PC 의 정상 신호*

## 1. 이 장표가 왜 있나
앞 장표(108)에서 네 곳 사이를 코드와 숫자가 오가는 길을 보았다. 이제 각 곳의 안으로 들어간다. 첫 번째는 ① 개발 PC(WSL2)다. 1부와 2부의 모든 것이 처음 실제로 도는 곳이므로 "지금 제대로 떠 있나"를 가장 자주 확인해야 하는 곳이기도 하다. 이 장표는 그 확인 목록이다. 구성 요소 여섯 개마다 띄우는 명령, "정상"이라고 판단하는 신호, 비정상일 때 첫 행동을 적었다.

이 장표가 답하는 질문은 "WSL 에서 무엇을 보고 '정상'이라고 하나"다. 발표에서는 "숫자가 아니라 신호를 본다"는 점을 강조한다. 수집기의 한 줄 통계, 노드의 시작 로그 한 줄, 기록 요약의 Hz 한 칸이 각각 정상 신호이고, 그 신호가 어긋났을 때 무엇이 죽은 것인지가 바로 읽힌다.

## 2. 장표를 하나씩 읽기
표의 열은 넷이다. "구성"은 무엇을, "띄우는 법"은 어떤 명령으로, "'정상' 신호"는 무엇이 보이면 되는지, "비정상이면"은 그때 어디를 보는지다. 행을 위에서 아래로 읽는다.

- 행 1 "WSL 터미널": 띄우는 법은 "새 창 (.bashrc 가 venv·ROS 2·RT_REPO_ROOT 자동 설정)" — 터미널을 새로 열면 `.bashrc` 의 블록이 파이썬 가상 환경(venv), ROS 2 환경(`/opt/ros/jazzy/setup.bash`), 저장소 경로 변수 `RT_REPO_ROOT` 를 자동으로 잡는다. 정상 신호는 "프롬프트 앞 (.venv), echo $RT_REPO_ROOT 가 저장소 경로" — 프롬프트가 `(.venv)` 로 시작하고, `echo $RT_REPO_ROOT` 가 저장소 폴더를 찍으면 된다. 비정상이면 "docs/SETUP_WSL.md 의 .bashrc 블록" — 그 문서의 블록을 `.bashrc` 에 다시 넣는다. 11/04 에 venv 가 사라져 이 블록을 만들었다.
- 행 2 "관제 컨테이너 3개": 띄우는 법은 "docker compose -f fleet/docker-compose.yml up -d" — compose 파일에 적힌 컨테이너 세 개(MQTT 브로커, TimescaleDB, Grafana)를 뒤에서(`-d`) 띄운다. 정상 신호는 "docker ps 에 fleet_mqtt·fleet_db·fleet_grafana Up, localhost:3000" — `docker ps` 에 세 이름이 Up 상태로 보이고, 브라우저에서 `localhost:3000`(Grafana)이 열린다. 비정상이면 "docker compose … logs <이름>" — 그 컨테이너의 로그를 본다.
- 행 3 "수집기": 띄우는 법은 "python3 fleet/collector/collector.py --qos 1 (한 번에 하나, flock)" — 장치 메시지를 받아 DB 에 넣는 수집기를 QoS 1 로 띄운다. 괄호의 flock 은 잠금 파일(`fleet/logs/collector.lock`)로 한 번에 하나만 뜨게 한다는 뜻이다(둘이 뜨면 같은 client_id 로 서로 끊는다). 정상 신호는 "1초마다 msgs/s=50 online=50 … backlog=0 db_err=0" — 수집기가 1초마다 찍는 통계 한 줄에서 초당 메시지 50, 온라인 장치 50, 밀린 행 0, DB 오류 0 이면 정상이다(가상 장치 50대가 1 Hz 로 보내는 상태 기준). 비정상이면 "backlog 증가 = DB 죽음, online 급감 = 브로커/장치, '이미 떠 있습니다' = 중복" — 어느 숫자가 어긋났는지가 곧 원인이다. backlog 가 늘면 DB 가 안 받는 것, online 이 뚝 떨어지면 브로커나 장치 쪽, "이미 수집기가 떠 있습니다" 메시지면 두 개를 띄운 것이다.
- 행 4 "가상 장치": 띄우는 법은 "python3 fleet/agent/virtual_fleet.py --count 50 --rate 1 --telemetry-qos 1" — 가상 장치 50대가 1초에 한 번씩 QoS 1 로 상태를 보낸다. 정상 신호는 "수집기의 online=50" — 장치 쪽이 아니라 수집기 통계로 확인한다(받는 쪽이 50대를 봐야 진짜 정상). 비정상이면 "reconnects 가 계속 늘면 client_id 충돌(두 벌)" — 끝날 때 찍는 `reconnects` 가 계속 늘면 같은 `--prefix` 로 두 벌을 띄워 같은 client_id 가 서로를 밀어내는 것이다.
- 행 5 "ROS 2 노드": 띄우는 법은 "./install/rt_control_ros2/lib/rt_control_ros2/rt_control_node --ros-args --params-file …so101_mujoco.params.yaml" — colcon 으로 설치된 노드 실행 파일을 SO-101 + MuJoCo 설정 파일로 띄운다. 정상 신호는 "backend=mujoco dof=6 loop=1000 Hz, rt_status 의 timing_drops: 0, state: RUNNING" — 시작 로그 한 줄에 백엔드가 mujoco, 관절 6개, 루프 1000 Hz 가 보이고, `ros2 topic echo /rt_status --once` 에 주기를 놓친 횟수 0 과 상태 RUNNING 이 보이면 된다. 비정상이면 "토픽 안 보이면 ros2 daemon stop (RMW 꼬임), 고아는 pkill -f rt_control_node" — 노드는 살아 있는데 토픽이 안 보이면 다른 RMW(DDS 구현)로 떠 있던 ros2 데몬 때문이니 데몬을 내리고, 이전에 띄운 노드가 남아 있으면(고아) 죽인다.
- 행 6 "기록": 띄우는 법은 "bash data_pipeline/record.sh 30 → bag_to_csv.py" — 30초 녹음한 뒤 CSV 와 요약으로 바꾼다. 정상 신호는 "summary.md 에 실제 Hz = 설계 Hz, 틈 0, 드롭 0" — 요약 문서에서 토픽별 실제 주파수가 설계값(joint_states 100 Hz, joint_command 50 Hz, rt_status 1 Hz)과 같고 틈과 드롭이 0 이면 된다. 비정상이면 "조용히 안 끝나면 정지된 것(SIGTTIN) — pkill -CONT 뒤 -INT" — 30초가 지나도 아무 출력 없이 끝나지 않으면 죽은 것이 아니라 터미널을 읽으려다 정지된 것이다. `pkill -CONT` 로 깨운 뒤 `-INT` 로 곱게 끝낸다(11/05 에 실제로 겪어 `timeout --foreground` 로 고쳤다).
- 아래 글 "WSL 에서 나오는 지연 수치는 전부 참고값(가상 커널). 출처: docs/ENVIRONMENT.md §3": 이 표의 신호들은 "제대로 돈다"의 확인이고, 여기서 나오는 깨어남 지연 같은 숫자는 가상 커널 위의 값이라 참고값이라는 주의다.

## 3. 용어와 단위
- .bashrc: 터미널을 열 때마다 자동으로 실행되는 설정 파일.
- venv: 파이썬 가상 환경. 프롬프트 앞의 `(.venv)` 가 활성화 표시다.
- docker compose: 여러 컨테이너를 파일 하나로 정의해 함께 띄우고 내리는 도구. `-d` 는 뒤에서(백그라운드) 띄우기.
- QoS 1(MQTT): "최소 한 번은 전달"을 보장하는 등급. QoS 0 은 보장 없음.
- flock: 파일 잠금. 같은 잠금 파일을 두 프로세스가 동시에 잡을 수 없어 중복 실행을 막는다.
- msgs/s: 초당 메시지 수. online: 지금 살아 있다고 보이는 장치 수. backlog: DB 에 아직 못 쓴 행 수. db_err: DB 쓰기 실패 누적.
- client_id(MQTT): 브로커가 접속을 구별하는 이름. 같은 이름으로 둘이 붙으면 브로커가 먼저 것을 끊는다.
- RMW(ROS Middleware): ROS 2 가 아래에서 쓰는 DDS 구현(Fast DDS, Cyclone 등). ros2 데몬은 처음 뜬 RMW 로 고정된다.
- dof(degrees of freedom): 관절 수. 6 은 SO-101 팔의 관절 6개.
- Hz: 1초에 몇 번. loop=1000 Hz 는 1 ms 주기.
- timing_drops: 1 ms 주기를 놓친 횟수. 0 이어야 한다.
- SIGTTIN: 뒤에서 도는 프로세스가 터미널을 읽으려 할 때 커널이 보내는 "정지" 신호. SIGCONT(`pkill -CONT`)로 다시 깨우고 SIGINT(`-INT`)로 곱게 끝낸다.

## 4. 쉬운 예시
- 비유: 식당 개점 점검표다. 간판 불(터미널 환경), 주방 설비 셋(컨테이너 3개), 홀 매니저(수집기), 손님 50명(가상 장치), 주방장(ROS 2 노드), CCTV 녹화(기록). 각 항목에 "켜졌다"가 아니라 "매니저 장부에 손님 50명이 적혀 있다"처럼 결과로 확인하는 신호가 있다. 손님 수가 갑자기 줄면 문(브로커)이나 손님 쪽 문제, 장부에 미처리 주문(backlog)이 쌓이면 주방(DB)이 멈춘 것이다.
- 숫자 예시: 수집기 통계가 `msgs/s=50 online=50 backlog=0 db_err=0` 이었다가 `msgs/s=50 online=50 backlog=1200 db_err=24` 로 바뀌면, 장치는 다 살아 있고 메시지도 오는데 DB 가 안 받는 것이다(2부의 DB 장애 실험이 정확히 이 모양). 반대로 `online=3` 으로 떨어지면 브로커가 죽거나 장치 프로세스가 끊긴 것이다.

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 표의 글자 전부 — `docs/ENVIRONMENT.md` §3.
- 확인: `.bashrc` 블록과 `RT_REPO_ROOT` — `docs/SETUP_WSL.md`.
- 확인: 컨테이너 이름 fleet_mqtt·fleet_db·fleet_grafana 와 포트 3000 — `fleet/docker-compose.yml`.
- 확인: flock 잠금과 "이미 수집기가 떠 있습니다" 메시지 — `fleet/collector/collector.py`(머리말과 `collector.lock`).
- 확인: 통계 항목 이름(backlog_rows, db_errors) — `fleet/collector/collector.py` 의 통계 딕셔너리. 장표의 `backlog=`·`db_err=` 는 화면 출력의 줄임 표기다.
- 확인: `reconnects` 와 두 벌 충돌 — `fleet/agent/virtual_fleet.py` 머리말과 끝 출력.
- 확인: 시작 로그 `backend=%s dof=%u loop=%d Hz` — `rt_control/ros2_adapter/src/rt_control_node.cpp`.
- 확인: `ros2 daemon stop` 함정 — `docs/LOG.md` 11/04(다른 RMW 로 떠 있던 데몬).
- 확인: SIGTTIN 정지와 `timeout --foreground` — `data_pipeline/record.sh` 머리말, `docs/LOG.md` 11/05.
- 확인: 기록 결과 100.0 Hz 틈 0, 50.0 Hz, 1.0 Hz, 드롭 0 — `docs/LOG.md` 11/05 "기록 파이프라인 2차", `docs/measurements/record_summary_wsl_20261105.md`.
- 다시 확인하는 법(WSL 창): 표의 "띄우는 법" 열을 위에서 아래로 그대로 치고, "정상 신호" 열과 비교한다.

## 6. 자주 하는 오해·함정
- "수집기를 두 개 띄우면 두 배 빨라진다": 같은 client_id 로 둘이 붙어 서로 끊는다. flock 이 두 번째를 막고 "이미 떠 있습니다"를 찍는다.
- "장치 프로세스가 떴으니 장치 50대가 붙었다": 장치 쪽 출력이 아니라 수집기의 `online=50` 으로 확인한다. 받는 쪽이 봐야 정상이다.
- "노드가 node list 에 보이면 토픽도 보인다": 다른 RMW 로 떠 있던 데몬이 토픽을 못 보는 경우가 있다(11/04). `ros2 daemon stop` 뒤 다시.
- 함정(실제로 겪은 것): `record.sh 30` 이 아무 출력 없이 30초를 넘겨도 안 끝났다. 죽은 것이 아니라 SIGTTIN 으로 정지된 것이었다(11/05). "조용히 멈춤"은 정지일 수 있다.
- 함정: 터미널을 새로 열었는데 `(.venv)` 가 없으면 이후 파이썬 명령이 전부 시스템 파이썬으로 가서 모듈을 못 찾는다(11/04 venv 소실). 먼저 프롬프트를 본다.

## 7. 면접 한 문장
"WSL 에서 '정상'은 느낌이 아니라 신호다 — 수집기 통계 한 줄의 online=50 backlog=0 db_err=0, 노드 시작 로그의 loop=1000 Hz 와 timing_drops 0, 기록 요약의 실제 Hz = 설계 Hz — 그리고 어느 신호가 어긋났는지가 곧 어디가 죽었는지를 말해 준다."
