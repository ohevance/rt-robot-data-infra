# 장표 049 — 단계 8 — 상태를 읽어 올린다 — 벨트를 비우고 가장 최신 샘플만 100 Hz 로 발행
*위치: 1부 로봇을 움직이는 길 · 단계 8/10 상태 발행 · ② 코드 — publish_state 100 Hz*

## 1. 이 장표가 왜 있나
앞 장표(048)는 그림으로 "RT 스레드는 벨트에 올리기만 하고, 발행은 다른 스레드가 자기 박자로 꺼낸다"를 보여 줬다. 이 장표는 그 그림이 코드로는 몇 줄인지 보여 준다. 두 함수다 — RT 스레드의 몸통인 `rt_thread_main`(3줄)과, 100 Hz 타이머가 부르는 `publish_state`(21줄). 보는 사람이 확인해야 할 것은 한 가지다: RT 스레드 쪽(`rt_thread_main`)에는 ROS 발행 코드가 한 줄도 없고, 발행은 전부 `publish_state` 안에 있다는 것. 그것이 단계 8 들머리(047)의 기준 ①이었다.

## 2. 장표를 하나씩 읽기
상자 위의 파일 위치: `rt_control/ros2_adapter/src/rt_control_node.cpp:205-230`. 코드는 빌드 시점의 저장소 파일 그대로다(cu.code 로 베껴 옴).

- `void rt_thread_main() {` (205): 생성자 120줄에서 `std::thread(&RtControlNode::rt_thread_main, this)` 로 만든 스레드가 처음 실행하는 함수. 이 스레드가 단계 4 의 1 ms 루프를 돈다.
- `rt_loop_->run(*control_, g_timing_ring, timing_drops_, &stop_);` (206): 단계 4 에서 본 `RtLoop::run` 에 네 가지를 넘긴다. ① `*control_` — 단계 5 의 ControlStep(매 주기 할 일) ② `g_timing_ring` — 깨어남 지연·작업 시간을 올리는 타이밍 벨트(65,536칸) ③ `timing_drops_` — 그 벨트가 넘쳐 버린 수 ④ `&stop_` — 노드가 끝날 때 멈추라는 깃발. 여기서 끝이다. ROS 객체(publisher)를 전혀 만지지 않는다.
- `}` (207): 함수 끝. 세 줄짜리 함수인 이유는 "RT 스레드는 루프 하나만 돈다"를 코드로 못 박기 위해서다.
- 빈 줄과 주석 `// ---------- 4) 상태 발행: 벨트를 비우고 가장 최신 샘플만 보낸다 ----------` (209): 파일 머리 "읽는 순서"의 4번째 항목. 노드 파일은 1) 매개변수 2) 백엔드 3) 토픽 4) 타이머·발행 5) 통계 순으로 읽게 되어 있다.
- `void publish_state() {` (210): 생성자 113~114줄의 `create_wall_timer(microseconds(1000000 / publish_hz_), …)` 이 10 ms(publish_hz 100)마다 부른다. 이 함수는 ROS 2 의 실행기 스레드(일반 우선순위)에서 돈다.
- `JointStateSample s;` (211): 벨트에서 꺼낸 샘플을 받을 그릇. 한 샘플은 주기 번호·시각·깨어남 지연·관절 수·워치독 상태·로봇 상태·위치[6]·속도[6]·목표[6](`joint_types.hpp:25`).
- `bool got_any = false;` (212): 이번 호출에서 하나라도 꺼냈는지 기억하는 깃발.
- `while (g_state_ring.pop(s)) {` (213): 상태 벨트(`StateRing`, 2048칸, `joint_types.hpp:41`)에서 꺼낼 수 있는 동안 계속 꺼낸다. 1 kHz 로 올리고 100 Hz 로 꺼내므로 보통 10개쯤 들어 있다.
- `got_any = true; last_state_ = s;` (214~215): 꺼낼 때마다 `last_state_` 에 덮어쓴다. 반복이 끝나면 `last_state_` 에는 가장 최근 샘플만 남는다 — "벨트를 비우고 마지막 것만". 중간 샘플 9개는 토픽으로는 나가지 않는다(타이밍 통계는 따로 `g_timing_ring` 에 전부 남는다).
- `}` (216): 반복 끝.
- `if (!got_any) { return; // RT 스레드가 아직 안 돌았거나 멈춘 상태 }` (217~219): 하나도 못 꺼냈으면 발행하지 않는다. 노드가 뜬 직후 RT 스레드가 첫 주기를 돌기 전, 또는 RT 스레드가 멈춘 뒤에는 `/joint_states` 가 조용해진다 — 거짓 상태(옛 값)를 내보내지 않는 것이 의도다.
- `sensor_msgs::msg::JointState msg;` (220): ROS 2 표준 관절 상태 메시지. 메모리 할당이 여기서 일어나는데, 이 함수는 RT 스레드가 아니므로 괜찮다.
- `msg.header.stamp = now();` (221): 메시지 시각은 노드 시계(ROS time). 샘플 안의 `stamp_ns`(RT 스레드가 찍은 단조 시각)가 아니라 발행 시각이다 — 기록(E20)의 Hz 계산은 이 stamp 기준.
- `msg.name = joint_names_;` (222): 관절 이름 6개. 매개변수 `joint_names`(생성자 69줄)에서 왔고, 그 값은 로봇 프로필 `robots/so101.yaml` 의 "우리 쪽 이름"(shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper)이다. MuJoCo 모델 쪽 이름(Rotation, Pitch…)이 아니다 — 단계 6(043)의 두 이름표 중 바깥용.
- `msg.position.resize(dof_); msg.velocity.resize(dof_);` (223~224): 관절 수(6)만큼 칸을 만든다.
- `for (std::uint32_t j = 0; j < dof_; ++j) { msg.position[j] = last_state_.position[j]; msg.velocity[j] = last_state_.velocity[j]; }` (225~228): 마지막 샘플의 위치·속도를 메시지에 복사. 단위는 rad 와 rad/s. 목표(`target`)는 보내지 않는다 — 목표는 `/joint_command` 쪽에 이미 있다.
- `state_pub_->publish(msg);` (229): `/joint_states` 토픽으로 발행(생성자 108줄에서 깊이 10 으로 만든 publisher).
- `}` (230): 끝.

오른쪽 요점 네 줄은 위 내용의 요약이다. "1 kHz 샘플 10개 중 최신 1개"는 1000 ÷ 100 = 10 에서 온 숫자다.

## 3. 용어와 단위
- 타이머(wall timer): ROS 2 가 일정 간격으로 함수를 불러 주는 장치. 벽시계 기준. `publish_hz_` 100 → 10,000 us = 10 ms 간격.
- 실행기(executor) 스레드: `rclcpp::spin` 이 돌리는 스레드. 구독 콜백(`on_command`)과 타이머 콜백(`publish_state`, `publish_status`)이 여기서 돈다. RT 스레드와는 별개.
- SPSC 링(단일 생산자·단일 소비자 링 버퍼): 쓰는 쪽 하나(RT), 읽는 쪽 하나(실행기)만 있으면 잠금 없이 안전한 원형 큐. `pop` 은 비어 있으면 false.
- `last_state_`: 노드가 기억하는 마지막 샘플. `publish_status` 도 이 값의 `iter` 를 JSON 에 쓴다.
- JointState: ROS 2 `sensor_msgs` 의 표준 메시지. `name[]`, `position[]`(rad), `velocity[]`(rad/s), `effort[]`(여기선 비움).
- dof: 자유도 = 움직이는 관절 수 = 6.
- rad: 각도 단위. 2π rad = 360°, 0.05 rad ≈ 2.9°.

## 4. 쉬운 예시
비유 — 공장 라인 끝의 사진사: 라인(RT 스레드)은 1 ms 마다 완제품을 벨트에 올린다. 사진사(publish_state)는 10 ms 마다 와서 벨트 위 제품을 전부 걷어 내고, 가장 마지막 것 하나만 사진을 찍어(JointState) 게시판(/joint_states)에 붙인다. 벨트가 비어 있으면(라인이 아직 안 돌았으면) 옛 사진을 다시 붙이지 않고 그냥 돌아간다.

숫자 예시 — 노드가 떠서 1초 지난 시점: RT 스레드가 1,000주기를 돌아 샘플 1,000개를 올렸고, 타이머가 100번 와서 매번 10개씩 꺼내 100장을 발행했다. 기록(E20) 30초(정확히는 29.6초 구간)에 2,964행 = 100.0 Hz 가 그 결과다. 만약 실행기 스레드가 어떤 이유로 25 ms 동안 못 돌았다면, 다음 호출에서 25개를 꺼내 마지막 1개만 보내고 `/joint_states` 사이에는 25 ms 틈이 한 번 생긴다 — 그래도 벨트는 2048칸이라 `state_drops` 는 0 이다(넘치려면 2초 이상 멈춰야 한다).

## 6. 자주 하는 오해·함정
- "`publish_state` 가 RT 스레드에서 도는 것 아닌가?" — 아니다. 타이머 콜백은 `rclcpp::spin` 의 실행기 스레드에서 돈다. RT 스레드가 하는 ROS 관련 일은 없다. 두 스레드가 만나는 곳은 `g_state_ring` 하나뿐.
- "`got_any` 가 false 면 오류인가?" — 아니다. 노드 기동 직후 첫 10 ms 는 자연스럽게 비어 있을 수 있다. 계속 비어 있으면 RT 스레드가 멈춘 것이고, 그때는 `/rt_status` 의 `iter` 가 늘지 않는 것으로 확인한다.
- "중간 샘플을 버리면 1 kHz 데이터가 사라지는 것 아닌가?" — 토픽으로는 100 Hz 만 나간다. 1 kHz 의 타이밍(깨어남 지연·작업 시간)은 `g_timing_ring` 에 전부 남아 `publish_status` 가 1초 단위 통계로 요약한다. 1 kHz 위치 원본이 필요하면 설계를 바꿔야 한다(현재 요구 아님).
- 함정(11/04 LOG): `ros2 topic echo /joint_states --once` 가 "A message was lost!!! total count change:10" 을 찍는다 — 100 Hz 발행을 늦게 구독한 CLI 가 자기 큐(깊이 10)에서 밀린 것을 알리는 소음이다. 노드 쪽 `state_drops` 는 0.

## 7. 면접 한 문장
"RT 스레드 함수는 세 줄 — 루프를 돌리는 것뿐이고, 발행은 실행기 스레드의 100 Hz 타이머가 상태 링을 비워 최신 샘플 하나만 JointState 로 내보냅니다 — 그래서 RT 스레드에는 할당도 네트워크도 없고, 30초 기록에서 100.0 Hz 틈 0 으로 확인했습니다."
