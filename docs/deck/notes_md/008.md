# 장표 008 — 같은 길을 구조도로 — 로봇 안(실시간) · 관제(데이터) · 측정
*위치: 1부 로봇을 움직이는 길 · 구조도(실시간 · 관제 · 측정)*

## 1. 이 장표가 왜 있나
바로 앞 장표(007)는 열 단계를 "시간 순서"로 한 줄에 그렸다. 그러면 "그 열 단계가 저장소의 어느 덩어리에 속하나, 로봇 안과 서버는 어떻게 나뉘나"가 궁금해진다. 이 장표는 같은 길을 "자리" 기준으로 다시 그린 구조도다. 왼쪽 상자가 로봇 안(실시간 쪽, 1부), 오른쪽이 관제(데이터 인프라 쪽, 2부), 아래가 측정·검증(3부와 6부)이다. 이 그림을 보면 1부에서 내려가는 길이 왼쪽 상자 안에서 위에서 아래로 가는 선이라는 것, 그리고 단계 ⑩에서 점선 하나로 오른쪽 상자에 건너간다는 것이 보인다.

## 2. 장표를 하나씩 읽기
그림은 Mermaid 원본(`docs/deck/build/diagrams/sw_overview.mmd`)으로 그렸고, 상자 세 묶음(subgraph)으로 되어 있다. 왼쪽 묶음부터 위에서 아래로.

- 묶음 "로봇 안 (실시간 쪽)":
  - `/joint_command 50 Hz (ROS 2 구독)`: 명령이 들어오는 토픽(단계 1·2).
  - → `rt_control_node (ROS 2 껍질) 스레드 3개 · 링 2개`: 명령을 받아 우편함에 넣는 노드(단계 3). "껍질"이라 부르는 이유는 제어 논리가 이 파일에 없고 rt_core 에 있기 때문. 스레드 3개는 ROS 2 실행기·RT·(main), 링 2개는 명령 링과 상태 링(타이밍 링까지 세면 3개 — 010번 장표).
  - → `rt_core RT 스레드 1 kHz — RtLoop → ControlStep — 워치독 · 변화량 제한 · 상태 머신`: 1 ms 마다 깨는 루프(단계 4)와 안전 검사(단계 5).
  - → `Backend — SimLag | MuJoCo | (실물)`: 로봇 쪽 창구(단계 6). 괄호의 실물은 자리만 있다.
  - RT → `/joint_states 100 Hz · /rt_status 1 Hz JSON`: 상태 발행(단계 8).
  - → `rosbag2 MCAP 기록 → CSV → summary.md`: 기록(단계 9).
- 묶음 "관제 (데이터 인프라 쪽)" (2부):
  - `장치 에이전트 ×50 (+RT 노드 다리) — 버퍼·재전송·유언·OTA 적용` → `Mosquitto 브로커 — persistence · QoS 0/1 · 큐 20000` → `수집기 — 1초 묶음 COPY · backlog · 곱게 종료` → `TimescaleDB — telemetry · events · collector_stats · ota_rollouts` → `Grafana 14 패널`.
  - `rollout.py — 5% → 50% → 100% · 헬스 게이트 · 롤백` 이 점선(cmd)으로 브로커에 붙는다: OTA 명령은 서버에서 브로커를 거쳐 장치로 내려간다.
  - `inject.py 장애 4종 — diag.py · assert_results.py` 가 점선(stop/start)으로 브로커와 DB 에 붙는다: 장애 주입은 컨테이너를 멈추고 살리는 식으로 한다.
- 두 묶음을 잇는 점선 `/joint_states·/rt_status → ros_status_bridge (51번째 장치) → 장치 에이전트`: 단계 10. 로봇의 1 Hz 요약이 가상 장치 50대 옆의 51번째 장치로 들어간다.
- 묶음 "측정·검증": `Pi 4 PREEMPT_RT — jitter_bench · cyclictest → 표①`, `dds_bench → 표②`, `GitHub Actions 3잡 — 단위 → 통합(컨테이너) · MuJoCo`. 3부(표①②③)와 6부(측정 스크립트·테스트·CI)의 자리.
- 설명 글(caption): 1부는 왼쪽 '로봇 안' 상자를 위에서 아래로 내려간다. 오른쪽 '관제'는 2부, 아래 '측정·검증'은 3부(검증)와 6부(측정 스크립트·테스트·CI).

## 3. 용어와 단위
- 구조도: 시간 순서가 아니라 "무엇이 어디에 있고 무엇과 연결되나"를 그린 그림.
- 토픽(`/joint_command` 등): ROS 2 에서 이름표 붙은 데이터 흐름. 발행하는 쪽과 구독하는 쪽이 이름으로 만난다.
- 링(링 버퍼): 두 스레드 사이에 값을 넘기는 원형 저장 칸. 락 없이 한쪽은 넣고 한쪽은 꺼낸다(단계 3).
- Backend: 제어 코드가 로봇에 쓰고 읽는 창구. SimLag(1차 지연 모델) / MuJoCo(물리) / 실물(자리).
- MCAP / rosbag2: ROS 2 의 기록 도구와 파일 형식(단계 9).
- 에이전트 / 브로커 / 수집기: 장치 쪽 프로그램 / MQTT 우체국 / 서버에서 받아 DB 에 넣는 프로그램(2부).
- persistence · QoS · 큐 20000: 브로커가 재시작해도 세션을 보존하는 설정, 전달 보장 수준, 수집기가 없는 동안 들고 있는 메시지 상한(`fleet/mosquitto/mosquitto.conf` 의 `persistence true`, `max_queued_messages 20000`).
- TimescaleDB: 시간 데이터용으로 확장한 PostgreSQL. Grafana: 대시보드 화면. 14 패널은 `fleet/grafana/make_dashboard.py` 가 만든다.
- 헬스 게이트 / 롤백: OTA 단계마다 장치 상태를 보고 통과 또는 되돌리기.
- jitter_bench / cyclictest / dds_bench: 깨어남 지연 측정기(직접 만든 것 / 표준 도구) / DDS 측정기.

## 4. 쉬운 예시
비유: 공장 배치도다. 왼쪽 건물(로봇 안)에서는 1 ms 마다 돌아가는 기계가 있고, 오른쪽 건물(관제)은 여러 로봇의 보고서를 모아 전광판에 띄우며, 지하(측정·검증)는 계측실이다. 두 건물 사이의 유일한 통로가 점선 하나(다리, 1 Hz 요약)다. 숫자 예시: 왼쪽 건물 안에서는 1 kHz(1 ms)·100 Hz·50 Hz 가 돌지만, 점선을 건너가는 것은 1 Hz(1초에 한 번) 요약뿐이다. 50대라면 서버는 초당 50개 메시지를 받는다 — 100 Hz 원본을 다 보내면 100배가 된다(단계 9 장표 53).

## 5. 숫자의 출처와 다시 확인하는 법
- 확인: 50 Hz · 1 kHz · 100 Hz · 1 Hz — `rt_control_node.cpp` 머리말과 `:70`, `:75`, `:116`, 시험 발행 `-r 50`(`docs/VIDEO_SCRIPT.md`).
- 확인: 큐 20000 · persistence — `fleet/mosquitto/mosquitto.conf:11,17`.
- 확인: 14 패널 — `fleet/grafana/make_dashboard.py` 머리말 "패널 14개".
- 확인: 5% → 50% → 100% — `fleet/ota/rollout.py` (2부 장표 79·80).
- 확인: 장애 4종(broker·db·collector·bad_firmware) — `fleet/chaos/inject.py` (2부 장표 84).
- 확인: 그림 원본 — `docs/deck/build/diagrams/sw_overview.mmd`.

## 6. 자주 하는 오해·함정
- 오른쪽 관제 묶음이 ROS 2 위에서 도는 것으로 오해하기 쉽다. 아니다 — 관제는 MQTT·파이썬이고, ROS 2 는 로봇 안에서만 쓴다(7부 결정 "장치 → 서버는 MQTT").
- 점선 다리로 건너가는 것은 100 Hz 원본이 아니라 1 Hz 요약이다. 원본은 로봇 안에 MCAP 으로 남긴다(단계 9).
- "rt_control_node 스레드 3개"의 셋째는 프로그램을 시작한 main 스레드다. 제어 코드가 도는 것은 RT 스레드 하나뿐이다.

## 7. 면접 한 문장
"구조는 세 덩어리입니다 — 로봇 안의 실시간 쪽(ROS 2 노드와 1 kHz 제어), 서버의 관제 쪽(MQTT → DB → Grafana), 그리고 그 둘을 재는 측정·검증. 로봇과 서버 사이는 1 Hz 요약을 나르는 다리 하나로만 이어집니다."
