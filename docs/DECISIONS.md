# 설계 결정 기록 (DECISIONS)

형식: 날짜 · 결정 · 이유 · 버린 대안. 면접에서 "왜 그렇게 했나"에 답하는 원본.

## 2026-11-03 — RT 핵심은 ROS 2와 무관한 순수 C++로 만든다
- 결정: `rt_core`(루프·큐·측정)는 POSIX/C++17만 쓰고, ROS 2 노드는 그것을 감싸는 얇은 어댑터로 둔다.
- 이유: (1) ROS 2 없는 어디서나 빌드·테스트 가능(CI 무료 러너 포함) (2) RT 규칙 위반 지점이 한 파일에 모여 설명이 단순 (3) 미들웨어 교체(ROS 2 ↔ ZMQ)가 설정 문제가 된다.
- 버린 대안: 처음부터 rclcpp 노드 안에 루프를 쓰는 것 — 테스트가 ROS 2 설치에 묶이고, executor 지연이 측정에 섞인다.

## 2026-11-03 — 로깅 큐는 "꽉 차면 버린다" (drop-on-full)
- 결정: RT 스레드는 SPSC 링이 꽉 차면 샘플을 버리고 드롭 수만 센다.
- 이유: 기다리거나(블로킹) 메모리를 늘리면(할당) 주기가 깨진다. 로그 한 줄보다 제어 주기가 우선.
- 버린 대안: mutex 큐(우선순위 역전 위험), 무한 벡터(할당·페이지 폴트).

## 2026-11-03 — 지연은 평균이 아니라 p99.9와 max로 판단한다
- 결정: 모든 표의 기준 열은 p99.9와 max.
- 이유: 제어 루프는 한 번만 늦어도 실패. 평균은 그 한 번을 숨긴다.

## 2026-11-03 — 절대 시각 타이머(TIMER_ABSTIME)로 주기를 잡는다
- 결정: `next += period`로 목표 시각을 누적하고 그 시각까지 잔다.
- 이유: 상대 시간(`sleep_for(1ms)`)은 늦게 깬 만큼 다음 주기가 밀려 드리프트가 쌓인다.

## 2026-11-03 — 로봇 프로필(YAML)로 로봇을 바꾼다
- 결정: 관절 수·주기·백엔드·한계·워치독을 `robots/*.yaml`에 두고, 노드는 시작 시 한 번 읽어 고정 크기 버퍼를 잡는다.
- 이유: SO-101(6관절, 시뮬 + 실물 자리)과 ALLEX(48관절, 시뮬)를 같은 코드로 돌린다는 주장을 설정 파일 하나로 증명. (정정 11/06: 실물 팔은 없다 — "실물 있음"은 잘못 적은 것.)

## 2026-11-03 — 6주 계획을 2주로 줄이며 뺀 것
- 뺀 것: 실물 팔(SO-101), ALLEX 프로필, Isaac Sim, MCAP 전체 파이프라인, 가상 300대(→50대), ZMQ SDK, EtherCAT.
- 이유: 지원 시점을 11/17로 당김. 얇아도 전부 설명되는 저장소가 우선.
- 복귀 순서(지원 후 면접 전): 팔 → 상태 머신 심화 → ALLEX → Isaac.

## 2026-11-03 (D1) — 매 주기 "할 일"을 RtStep 으로 바꿔 끼운다
- 결정: RtLoop 은 주기만 지키고, 매 주기 `RtStep::step()` 을 부른다. 측정기는 BusyWorkStep, 제어 노드는 ControlStep.
- 이유: 같은 루프 코드로 "측정"과 "제어"를 한다 → 측정기에서 잰 지연이 곧 제어 노드의 지연. 두 벌로 나누면 숫자가 서로를 설명하지 못한다.
- 버린 대안: 함수 포인터·std::function — 읽기 규칙(람다 금지)에 맞춰 추상 클래스 하나로.

## 2026-11-03 (D1) — 명령은 "가장 최신 것만" 쓴다 (우편함을 매 주기 비운다)
- 결정: ROS 2 콜백은 명령을 SPSC 링에 넣고, RT 는 매 주기 링을 전부 비운 뒤 마지막 것만 적용한다.
- 이유: 1 kHz 루프에 50 Hz 명령이 온다. 밀렸다 한꺼번에 온 오래된 목표를 순서대로 따라가면 로봇이 "과거"를 재생한다. 목표 위치 명령은 최신값만 의미가 있다.
- 버린 대안: 큐를 FIFO 로 하나씩 소비 — 궤적(trajectory) 명령이라면 맞지만 목표 위치 명령에는 틀린다.

## 2026-11-03 (D1) — 워치독은 "멈춤 = 현재 위치 유지"
- 결정: 명령이 watchdog_ms(50 ms) 동안 없으면 목표를 현재 위치로 바꾼다. 시작 시에도 명령이 올 때까지 멈춤 상태.
- 이유: 명령이 끊겼을 때 마지막 목표로 계속 가는 것이 가장 위험하다. 실물에서는 여기서 토크 오프까지 간다(Backend 에 safe_stop 추가 예정).

## 2026-11-03 (D1) — 로봇 프로필은 robots/*.yaml 하나, ROS 파라미터 파일은 거기서 생성
- 결정: `scripts/profile_to_params.py` 가 `robots/so101.yaml` → `config/so101.params.yaml` 을 만든다. 손으로 두 파일을 따로 고치지 않는다.
- 이유: 노드에서 yaml-cpp 로 직접 읽는 것보다 의존성이 없고, ROS 표준 방식(--params-file)을 그대로 쓴다.
- 비용: 프로필을 고치면 스크립트를 한 번 더 돌려야 한다.

## 2026-11-03 (D1) — DDS 지연은 한 방향이 아니라 왕복(RTT)으로 잰다
- 결정: ping/pong 메아리 구조. 한 방향 지연 ≈ RTT/2 로 본다.
- 이유: 두 기기의 시계가 다르면 한 방향 측정은 수십 ms 씩 틀린다. 왕복은 같은 시계로 잰다.

## 2026-11-03 (D2) — 장치 → 서버는 MQTT, 서버 안은 ROS 2 가 아니다
- 결정: 장치 텔레메트리는 MQTT(브로커 경유), ROS 2 는 로봇 안(제어·센서)에서만. RT 노드는 `/rt_status` 를 다리(bridge)로 MQTT 에 올린다.
- 이유: DDS 디스커버리는 같은 네트워크 안의 수십 대까지가 편하고, 수백 대·NAT·LTE 뒤의 장치에는 브로커 중계 모델(MQTT)이 맞다. 유언(LWT)·보관 메시지·QoS 1 재전송이 "끊김" 처리를 공짜로 준다.
- 버린 대안: DDS 로 전부 — 현장 네트워크를 넘어가는 순간 디스커버리·멀티캐스트 문제가 생긴다.

## 2026-11-03 (D2) — 수집기는 1초 묶음(batch) + COPY
- 결정: 메시지마다 INSERT 하지 않고 1초 모아 COPY. 수집 지연에 최대 1초가 더해지는 것을 통계에 그대로 드러낸다.
- 이유: 300대 × 1 Hz 를 행 단위로 넣으면 DB 왕복 300회/초. 묶으면 1회/초. 지연 1초는 관제(모니터링) 용도에 문제가 없고, 제어는 애초에 이 길을 타지 않는다.

## 2026-11-03 (D2) — 끊김 처리는 장치 쪽 버퍼(store-and-forward)
- 결정: 브로커와 끊기면 장치가 메모리에 모아 두고(최대 1시간 분), 재접속 때 QoS 1 로 재전송. 버퍼·재전송·재접속 수를 텔레메트리에 같이 실어 보낸다.
- 이유: 유실은 "없게" 가 아니라 "세게" 만드는 것이 먼저다. 일련번호(seq)로 서버가 유실을 계산하고, 버퍼 카운터로 장치가 자기 상태를 말한다.

## 2026-11-03 (D2) — 대시보드 JSON 은 생성기로 만든다
- 결정: `fleet/grafana/make_dashboard.py` 가 JSON 을 만든다. 손으로 고치지 않는다.
- 이유: 300줄짜리 JSON 을 사람이 읽고 설명하는 것은 불가능하다. 패널 11개의 SQL 이 한 파일 70줄에 보이는 쪽이 설명 가능하다.

## 2026-11-03 (D3) — 상태 머신은 if 문이 아니라 "전이 표" 하나로
- 결정: `RobotStateMachine` 은 `{지금 상태, 사건, 다음 상태}` 줄의 정적 표(`kTable`)를 뒤져 전이한다. 표에 없는 전이는 거절하고 `illegal_events` 로 센다.
- 이유: (1) 허용 전이가 한 화면에 전부 보인다 — 면접에서 표를 가리키며 설명할 수 있다 (2) 표 한 줄 = 테스트 한 줄 (3) "FAULT 에서 바로 RUNNING 으로" 같은 금지 규칙이 코드 구조로 보장된다.
- 버린 대안: 상태마다 switch/if — 전이가 코드 곳곳에 흩어져 빠진 경우를 찾기 어렵다.
- 사건은 ControlStep 이 매 주기 넣는다(`update_state_machine`): 워치독 끊김 → WATCHDOG_TRIP, 명령 도착 → COMMAND, 정상 100주기 → RECOVERED. RT 스레드 안이지만 표 조회(상수 시간)뿐이라 RT 규칙에 맞는다.

## 2026-11-03 (D3) — OTA 롤백 결정은 장치가 아니라 서버가 한다
- 결정: 장치는 "적용(updating → 새 버전)"과 "되돌리기"만 한다. 단계(5→50→100%)·헬스 판정·롤백 명령은 전부 `rollout.py`(서버).
- 이유: 장치 하나는 자기 고장만 안다. "3대 중 1대가 fault" 같은 **집단** 판단은 전체를 보는 쪽만 할 수 있다. 장치가 스스로 롤백하면 서버는 왜 되돌아갔는지 모른다.
- 헬스는 텔레메트리 `state == ok` 하나만 본다. 이유: 이미 1 Hz 로 오는 데이터를 재사용 → 별도 헬스 프로토콜 없이 단순. 비용: 상태 반영까지 최대 1초 지연(health_wait 5초 안에 충분).
- 장치 쪽 "적용"은 시뮬레이션(apply_s 초 대기 후 버전 교체)이다. 실물에서는 그 자리에 실제 설치가 들어간다 — 서버 쪽 코드는 바뀌지 않는다.

## 2026-11-03 (D4) — 수집기 backlog 는 디스크가 아니라 메모리, 상한을 두고 버린다
- 결정: DB 쓰기 실패 시 1초 묶음(Batch)을 메모리 리스트에 보관, 매초 재시도. 20만 행(50대 1 Hz 약 66분)을 넘으면 가장 오래된 묶음을 버리고 `backlog_dropped` 로 센다.
- 이유: DB 중단은 보통 수 초~수 분이고, 디스크 큐는 구현·복구 경로가 두 배로 복잡해진다. 2주 안에 "복구되고 유실을 센다"가 먼저. 상한은 메모리 보호(행당 약 500 B → 약 100 MB).
- 버린 대안: 디스크 WAL/SQLite 큐 — 수 시간 중단까지 견디지만 지금 단계의 복잡도가 아니다. 장치 쪽 버퍼(store-and-forward)도 같은 철학으로 메모리 1시간 분.

## 2026-11-03 (D4) — 텔레메트리 QoS 기본은 0, 옵션으로 1 — 그리고 그 차이를 표로 남긴다
- 결정: 장치 `--telemetry-qos 0`(기본)과 수집기 보통 세션이 기본. 수집기 끊김 때 유실 0 이 필요하면 장치 QoS 1 + 수집기 `--qos 1`(지속 세션) 조합을 **옵션**으로 켠다.
- 이유: QoS 1 은 메시지마다 확인(PUBACK) 왕복이 붙어 브로커·장치 부하가 는다. 300대 1 Hz 에서는 둘 다 가볍지만 "비용이 있는 선택"임을 숫자로 남기는 쪽을 택했다: 장애 주입 `collector` 를 qos0 / qos1 두 번 돌려 유실 n 대 0 을 표③-2 한 줄씩으로.
- 브로커 `max_queued_messages 20000`: 기본 1000 은 300대 × 10초를 못 담는다.

## 2026-11-03 (D4) — 장애 주입은 docker stop/start 와 프로세스 kill, 측정은 전부 DB 로
- 결정: 브로커·DB 는 컨테이너 stop/start, 수집기는 SIGTERM 후 같은 명령으로 재시작(또는 컨테이너), 나쁜 펌웨어는 rollout.py --bad. 감지·복구·유실은 collector_stats·telemetry(seq) 를 질의해서 낸다.
- 이유: 시스템이 "자기 숫자로" 장애를 설명해야 한다. 주입 스크립트가 따로 재서 알려 주는 숫자는 운영 중에 쓸 수 없다. DB 에 남은 것만 쓰면 면접에서 "그 숫자 어디서 났나"에 "이 표에서"라고 답한다.
- 복구 시간은 ±1초(1초 묶음 적재)가 섞인다 — 표에 그렇게 적는다. 정밀 측정이 필요하면 적재 주기를 100 ms 로(옵션 `--interval 0.1`).

## 2026-11-03 (D4) — CI 는 2단계: 가짜로 빠르게, 진짜로 한 번
- 결정: 1단계(rt_core 잡)는 브로커·DB 없이 가짜 모듈로 논리를 검사(1분). 2단계(fleet_integration 잡)는 진짜 Mosquitto·TimescaleDB 컨테이너를 러너에 띄워 장애 주입 3종 + OTA 롤백을 돌리고 판정(약 5분). MuJoCo 잡은 별도.
- 이유: 빠른 실패(1분)와 진짜 환경 증명(5분)은 목적이 다르다. 2단계가 깨지면 1단계가 통과했는지로 "논리 문제냐 환경 문제냐"를 먼저 가른다.
- 같은 스크립트(`fleet/tests/integration.sh`)를 WSL 에서도 돌린다 → "CI 에서만 되는" 일이 없게.

## 2026-11-03 (D5) — MuJoCo 는 Backend 의 한 구현이고, 빌드 옵션은 기본 OFF
- 결정: `MujocoBackend` 는 `SimLagBackend` 와 같은 인터페이스(init/write_command/read_state). CMake `RT_CORE_WITH_MUJOCO` 기본 OFF → MuJoCo 가 없는 PC·CI 1단계는 전과 똑같이 빌드.
- 이유: 제어 코드(`control_step.cpp`)와 노드가 한 줄도 안 바뀌고 로봇이 "물리"로 바뀌는 것이 Backend 인터페이스를 둔 이유였다 — 이번에 그 주장을 실행으로 증명. 옵션 OFF 기본은 "의존성이 없는 사람도 빌드된다"를 지키기 위해.
- 시뮬레이션 걸음은 올림(ceil)으로 맞춘다: 제어 주기 ÷ 걸음 수 ≤ 모델이 정한 걸음. 걸음을 키우면 물리가 불안정해지므로 작게만 바꾼다.
- 관절 연결은 **이름**으로(프로필 `mujoco.joints`), 이름이 없으면 모델 순서로. 틀리면 모델의 이름 전체를 출력하고 멈춘다 — 조용히 추측하지 않는다. 노드가 MuJoCo 없이 빌드됐는데 `backend: mujoco` 면 FATAL 로 멈춘다(SimLag 로 몰래 바꾸지 않는다).
- 모델은 Menagerie 의 SO-ARM100(SO-101 과 같은 5축+그리퍼). 전용 SO-101 폴더가 생기면 프로필의 경로만 바꾼다.

## 2026-11-04 (D5 실측) — 브로커는 persistence true, 수집기는 "곱게 종료", 수동 ACK 는 보류
- 결정: Mosquitto `persistence true` + 볼륨(세션·보관 메시지가 재시작을 넘긴다). 수집기는 SIGTERM/Ctrl+C 에서 수신을 끊고 pending 을 마지막으로 적재한 뒤 끝낸다.
- 이유: 실측에서 유실이 세 군데서 났다 — (1) 브로커 재시작 때 수집기 구독이 사라져 먼저 온 장치 버퍼를 버림 (2) 수집기 종료 순간의 1초치 pending (3) 큐 상한. (1)(2)는 설정 1줄·시그널 처리 20줄로 막힌다. (3)은 상한의 뜻을 이해하고 장치 버퍼와 역할을 나누는 문제.

## 2026-11-06 — ALLEX 프로필의 제어 주기는 500 Hz (1 kHz 가 아니다)
- 결정: `robots/allex.yaml` 의 `loop_hz.sim` 을 1000 → **500**. CI 의 ALLEX 게이트도 프로필과 같은 2 ms 주기로(`RT_MUJOCO_PERIOD_US=2000`, 합격선 p99 < 주기의 90 % = 1,800 us). 1 kHz 는 게이트가 아니라 측정으로 남긴다(E21 표).
- 이유: E21 첫 측정(WSL, 1 kHz, 2,000주기)에서 48 자유도 물리 한 주기가 p50 336 / p99 622 / max 1,785 us. p99 는 합격선(900 us) 안이지만 예산의 62 % 이고, max 는 주기를 넘었다(178 %) — 노드라면 마감 놓침이다. 모델의 기본 걸음(timestep)이 2 ms 이므로 500 Hz 는 모델 작성자의 운영점이기도 하다. 500 Hz 로 바꿔도 한 주기의 물리 비용은 같다(`mj_step` 1번) — 바뀌는 것은 예산(1 → 2 ms)이라 p99 31 %, max 89 %(어림). 제어 주기는 프로필의 숫자 하나이므로 코드는 바뀌지 않는다.
- 버린 대안: (1) 1 kHz 유지 — "p99 가 통과했으니 그대로"는 측정의 꼬리(max)를 무시하는 것. (2) 1 kHz 제어 + 물리는 두 주기에 한 번 — 백엔드에 "이번 주기는 걸음을 건너뛴다"는 상태가 생겨 "한 주기 = 한 걸음"의 단순함이 깨진다. (3) 물리를 별도 스레드로(비동기) — 제어가 읽는 상태가 몇 주기 전 것인지가 불확실해진다. (2)(3)은 1 kHz 가 정말 필요해질 때 다시 본다(실물 ALLEX 는 없다). (4) 손가락을 뺀 간소화 모델 — 회사 모델을 그대로 돌린다는 요점이 사라진다.
- 검증 방법: 500 Hz 단독 테스트의 p99 < 1,800 us 와 max, 노드 안 `work_us` 분포와 drop 0(500 Hz). CI 는 매 push 에 같은 게이트.
